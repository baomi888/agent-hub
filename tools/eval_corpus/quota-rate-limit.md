# 限流与配额设计笔记

## 每日问答额度

每个用户每天有固定的问答次数上限，存在 SQLite 里按天记账。
超过额度返回 429，前端提示明天再来。
额度判断必须在扣费之前先校验会话有效性：
无效请求（比如会话不存在）不该消耗用户的每日额度。

## 滑动窗口限流

短时限流用滑动窗口：同一用户每秒最多发起固定次数的问答请求。
窗口计数原本放在进程内存里，查起来是微秒级，基本零成本。

## 多 worker 下的失效问题

进程内字典限流在多 worker 部署下会失效：
四个 worker 各记各的账，实际放行量是上限的四倍。
修复方案是双层结构：本地窗口做快速拒绝，
数据库按秒桶记账做全局兜底，每次请求都查全局计数，
全局计数带 200 毫秒的进程内缓存，避免每请求都落一次磁盘读。
写入路径在写库后把增量补进缓存，保证缓存里是最新值。

## LLM 并发闸

除了次数限制，还有并发名额限制。
问答入口先抢一个 LLM 并发名额，抢不到直接返回 429 并带重试等待时间。
名额必须在 SSE 响应头发出之前抢：流一旦开始就没有机会再回 429 了。
如果请求在排队阶段失败，名额要当场归还，漏还一次就永久少一个位置。
