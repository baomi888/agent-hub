# 01 · 板块边界与架构

> 目的：让「校园工具集」能独立演进，同时不和主站互相踩脚。
> 本文规定**目录职责、依赖方向、与主站的接触面**。评审时以此判合规。

---

## 1. 定位差异（为什么要独立分区）

主站是「登录 → 选知识库 → 对话」的重链路，本板块是「打开即用、用完即走」的轻工具。
两者在产品形态上就不同，硬套一套架构会两头不讨好：

| 维度 | 主站 | 校园工具集 |
| --- | --- | --- |
| 登录 | 必须 | **不需要** |
| 后端 | FastAPI + SQLite + 向量库 | **无** |
| 数据 | 服务端 | **localStorage** |
| 首屏 | 工作台三栏 | 单页工具切换 |
| 更新节奏 | 跟主站版本 | **板块独立版本** |

结论：本板块按「**前端子应用**」治理，但物理上仍留在 `frontend/` 内，
复用构建链与设计令牌，**不单独部署**。

---

## 2. 目录职责

### 2.1 治理区 `campus/`

只放文档与版本，**不放可执行代码**。作用是让不写代码的人（负责人、产品）
也能完整掌握板块状态。

### 2.2 代码区 `frontend/src/campus/`

| 目录 | 职责 | 允许依赖 |
| --- | --- | --- |
| `types.ts` | 板块共享类型 | 无 |
| `storage/` | 读写 localStorage、版本迁移 | `types` |
| `logic/` | 纯计算函数（GPA、周次、抽签） | `types` |
| `components/` | 板块公共组件（导航外壳、空状态） | `types`、`styles` |
| `tools/<name>/` | 单个工具的实现 | `types`、`logic`、`storage`、`components` |
| `styles/` | 板块样式 | 只读全局令牌，不写全局 |

**依赖方向必须是单向的**：

```
tools/*  →  components  →  logic  →  storage  →  types
                                ↘ 不允许反向依赖
```

`logic/` 与 `storage/` **禁止 import React**，保证纯函数可单测。
`tools/a` 不允许 import `tools/b`，跨工具复用一律上提到 `components/` 或 `logic/`。

### 2.3 路由薄壳 `frontend/src/app/(campus)/`

`(campus)` 是 Next.js 路由组，不出现在 URL 里。

- `tools/page.tsx`：**只做挂载**，import `@/campus` 并渲染。不写业务、不写状态。
- 需要新增工具子页面时，同样只放薄壳，实现仍在 `frontend/src/campus/tools/`。

判断标准：薄壳文件超过 30 行，说明业务写错地方了。

---

## 3. 与主站的三个接触点

这是**唯一允许的耦合面**，改动需在 PR 描述里单独标注。

| # | 接触点 | 位置 | 约束 |
| --- | --- | --- | --- |
| 1 | 入口地址常量 | `frontend/src/components/chat/constants.tsx` → `TOOLS_URL` | 只允许改值，不允许改语义；切线上入口是独立提交 |
| 2 | 全局设计令牌 | `frontend/src/app/styles/tokens.css` | **只读**。板块差异写在 `campus.css` |
| 3 | 公共图标 | `frontend/src/components/CornIcon.tsx` | 只读复用 `name="tools"`，新增图标需单独提 PR 给负责人 |

除以上三点，本板块不得修改 `frontend/src/` 下任何既有文件。需要改则在 PR 里说明理由，
由负责人裁定。

---

## 4. 样式规则

- 板块内**不新建 CSS 框架**，沿用 Tailwind 4 + 全局令牌（`--bg-canvas`、`--card-bg`、
  `--ink`、`--muted`、`--accent`、`--line`、`--success` 等）。
- 板块专属变量一律定义在 `campus.css` 内，前缀 `--campus-`，避免和全局撞名。
- **必须同时支持浅色与深色**：`tokens.css` 用 `.dark` 类切换主题，
  所以板块内不允许写死 `#fff` / `#000` 这类绝对色，除非是遮罩层且两种主题都成立。

---

## 5. 性能红线

| 指标 | 上限 | 原因 |
| --- | --- | --- |
| `/tools` 首屏 JS（gzip） | 120 KB | 工具是「顺手用」，重了就失去意义 |
| 单个工具按需加载 | 必须 | 6 个工具不应全部进首屏 |
| 词库文件 | 沿用现有 JSON，不内联进 JS | 现有 `cet4.json` 已 6661 词，内联会撑爆包体 |

工具之间用动态 `import()` 拆包，切换时才加载对应工具实现。

---

## 6. 技术选型说明（为什么不单独建包）

考虑过用 npm workspace 把板块抽成独立包（`campus/package.json`），最终**没有采用**：

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A. 独立子包（workspace） | 边界最硬 | 需改构建链、`transpilePackages` 与 Tailwind 扫描范围都要调，三人小团队维护成本高 | ❌ |
| B. 同仓目录 + 路由薄壳 | 零构建改动，边界靠目录与评审约束 | 依赖靠人守规矩，不是编译期强制 | ✅ 采用 |
| C. 保持单文件继续加 | 改动最小 | 已到维护极限（132 KB），无法并行开发 | ❌ |

B 方案的边界靠两件事兜住：**ESLint 限制导入路径**（见 `04_开发与提交流程.md` 第 5 节）
+ **CODEOWNERS 把整个 campus 收口给一个人**。若后续团队扩到多人并行开发，
再升级到 A 方案，迁移成本可控（因为代码已集中）。
