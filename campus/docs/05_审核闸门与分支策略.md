# 05 · 审核闸门与分支策略

> **本文是硬约束，优先级高于「尽快交付」的直觉。**
> 核心一句话：**代码留在本地，审核报告先走，负责人点头、开发者开口，才允许推送。**

---

## 1. 分支：`school-tools`

### 1.1 命名

Git 分支名**不允许包含空格**（`git check-ref-format` 会直接拒绝），
所以「school tools」落地为 **`school-tools`**。

| 项 | 值 |
| --- | --- |
| 分支名 | `school-tools` |
| 角色 | 校园工具集**长期主线**，承载该板块的全部版本迭代 |
| 基线 | 从 `dev`（cb142a7）切出 |
| 归属 | 橙子（开发）；负责人 @baomi888 审核 |
| 推送条件 | **见第 2 节闸门，未通过不得推送** |

### 1.2 与团队短命分支规范的差异（需负责人在首份审核报告里确认）

`规范/03_流程规范.md` 规定特性分支生命周期 ≤ 5 天、用完即删。
`school-tools` 是**长期存在**的板块主线，属于对该规范的有意偏离，理由：

1. 本板块有独立版本号与发布节奏（`campus/VERSION`），需要一条稳定的版本线；
2. 板块与主站业务解耦，合入 `dev` 的时机应由负责人按版本决定，而不是每个提交都进；
3. 长期分支能保留完整的板块演进历史，便于回溯「哪个版本改了什么」。

**代价**：长期分支容易与 `dev` 分叉。应对方式是每次发版前 `git rebase origin/dev`，
冲突按 `规范/03` §1.4 逐块处理。

### 1.3 日常操作

```bash
git checkout school-tools
git pull --rebase origin school-tools   # 仅在远端已存在且有他人提交时需要

# 开发……（改动只在本地，不推送）

# 功能完成后：写审核报告（见第 3 节）→ 交给负责人
```

功能较大时可临时开子分支，但**子分支同样不推送**，合并回 `school-tools` 后再走闸门。

## 2. 三道闸门

```
①开发完成 → ②本地自测通过 → ③写审核报告 → ④负责人审核
                                              ├─ 不通过 → 改完重来（回到①）
                                              └─ 通过 → ⑤开发者明确说「上传」→ ⑥推送 school-tools
```

### 闸门 1 · 自测

跑完 `campus/docs/03_审核与验收清单.md` 第 1–3 节，把结果填进审核报告。
**没跑过的项不要勾**，勾了但没跑属于流程造假，比不勾更严重。

### 闸门 2 · 审核报告

每次功能交付**必须**写一份，存放于 `campus/reviews/`，命名见第 3 节。
审核通过前，报告只能留在本地——**本地 commit 无妨（防丢失），但绝不推送**。

### 闸门 3 · 推送授权（红线）

- ❌ 助手（AI）**不得自主执行 `git push`**，包括「顺手推一下」「怕丢先推上去」这类理由。
- ❌ 也不得通过 `gh`、GitHub 网页、其他工具绕道上传。
- ✅ 只有开发者**明确说出上传指令**（如「上传」「推上去」「可以推了」）后，才可以推送。
- ✅ 推送前必须确认：负责人已给出「通过」结论，且该结论写在审核报告里。

> 违反这条的代价不是「多推一次」，而是**负责人的审核流程被架空**——
> 一旦代码先上了远端，评审就变成「事后追认」，闸门等于没有。

## 3. 审核报告

### 3.1 存放与命名

```
campus/reviews/
├── TEMPLATE.md                        模板（复制它来写）
├── README.md                          规则说明
└── 2026-11-02_gpa工具排序修复.md      实际报告
```

命名：`YYYY-MM-DD_<一句话主题>.md`，主题与分支/功能对应，用中文，不用空格（用连字符或直接连写）。

### 3.2 报告必须回答的六件事

1. **做了什么**（一句话，不用术语堆砌）
2. **为什么做**（对应 ROADMAP 条目或内测反馈编号）
3. **改了哪些文件**（清单 + 每个文件一句话）
4. **怎么验证的**（命令 + 结果，不能只写「测试通过」）
5. **有什么风险 / 没做什么**（主动交代，不要等评审发现）
6. **审核结论**（留空，由负责人填）

### 3.3 报告怎么交给负责人

- 首选：把 `campus/reviews/xxx.md` 的内容直接发给负责人（聊天/文档/邮件均可）；
- 负责人可直接在报告末尾的「审核结论」栏填写；
- 结论只有三种：`通过` / `有条件通过（列条件）` / `打回（列条目号）`。

---

## 4. 审核通过之后

1. 把负责人的结论补进审核报告；
2. `campus/VERSION` 按语义化版本递增，`campus/CHANGELOG.md` 记录本次变更；
3. 提交（代码 + 报告 + 版本文件一起）：
   ```bash
   git add -A campus frontend/src/campus "frontend/src/app/(campus)"
   git commit -m "feat(campus): <简述>"
   ```
4. **等开发者说「上传」**，再执行：
   ```bash
   git push -u origin school-tools
   ```

### 首次推送（远端分支尚不存在时）

```bash
git push -u origin school-tools
```

GitHub 会自动创建该分支。若提示无权限，说明账号未被加入协作者，需负责人邀请。
