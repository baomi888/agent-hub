# 压测搬到 GitHub Actions：第一次拿到"不是压测机自己的天花板"的数字

日期：2026-10-20　runner：GitHub-hosted `ubuntu-latest`（**4 核 / 16 GB**，实测）
被测接口：`GET /api/auth/me/`（JWT 鉴权 + 一次查库），压测工具 `tools/loadtest_concurrency.py`

---

## 一、为什么要搬上 CI

本机压测有个绕不开的问题：**生成端会先于被测端饱和**。

| 本机（Windows）压测 | RPS |
|---|---|
| 20 并发，单进程生成 | 684 |
| 200 并发，单进程生成 | 138（并发越高吞吐越低 = 生成器自己排队） |
| 200 并发，4 个生成器进程 | ~1000（4 进程合计上限） |

也就是说本机测到的"天花板"常常是**压测机的天花板**。Runner 是干净的 Linux、与本机网络隔离，
至少能把这个混淆因素降下来（后面会看到：降下来一半，但没降干净——宿主是共享的）。

## 二、workflow 怎么设计的

`.github/workflows/loadtest.yml`，两档：

| 档 | 触发 | 参数 | 作用 |
|---|---|---|---|
| 冒烟档 | push `dev` | 50 并发 / 2 进程 / 5s / 2 worker | 把"某次改动把 p95 拉高一个数量级"挡在合并前，53s 跑完 |
| 正式档 | 手动 `workflow_dispatch` | 并发 / 进程数 / 时长 / workers / 场景 / p95 门槛 全可调 | 拿对照数字 |

三条硬约束写进了 workflow 注释，别改掉：

1. **只压 `/health` 与 `/api/auth/me`，不打 LLM** —— 真实并发会撞上游 TPM 限额并烧钱，
   而且要测的是本项目自身的框架/鉴权/SQLite 承载。
2. **冒烟档与正式档命令序列完全一致**，只差参数 —— 否则会出现"冒烟绿、正式挂"。
3. **结果进 job summary + artifact**（`loadtest.json` / `summary.md` / `loadtest-spec.txt`），
   规格文件一起存档：孤零零一个 RPS 说不清上限是被测端还是生成端。

## 三、实测数据（200 并发 / 10s / 0 错误，同一 commit `9997a55`）

| 组 | uvicorn workers | 生成器进程 | RPS | p50 | p95 | p99 |
|---|---|---:|---:|---:|---:|---:|
| A1 | 2 | 8 | **1143.0** | 152 ms | 414 ms | 809 ms |
| A2（A1 同参数复跑） | 2 | 8 | **618.0** | 308 ms | 520 ms | 918 ms |
| B | 4 | 8 | 405.4 | 455 ms | 883 ms | 939 ms |
| C | 4 | 4 | 419.5 | 439 ms | 698 ms | 1020 ms |
| D | 2 | 4 | 440.6 | 317 ms | 1354 ms | 2210 ms |

冒烟档（50 并发 / 5s / 2 worker / 2 进程）：**1042.1 RPS**，p50 31 ms，p95 148 ms，0 错误。

## 四、三条结论（比数字更重要）

### 1. Runner 的绝对值不可信，只能纵向比

A1 与 A2 参数完全相同，RPS 差 **1.85 倍**（1143 vs 618）。GitHub-hosted runner 是共享宿主，
隔壁租户在跑什么你不知道。所以：

- ✅ CI 压测的正确用法：**同环境纵向对比**，防止某次提交把 p95 拉高一个数量级；
- ❌ 错误用法：拿某一次的 RPS 当"系统能撑多少人"的依据——那是抽彩票。

### 2. 4 核上开 4 个 worker 并不更快（因为压测端在同机抢核）

| workers | 同并发下 RPS |
|---|---|
| 2 | 618 ~ 1143 |
| 4 | 405 ~ 420 |

B、C 两组把生成器从 8 进程降到 4 进程也没救回来（419 vs 405），**说明不是生成器争抢**，
是 4 个 worker 在 4 核上互相抢 + 压测端也在抢。

这与本机结论相反（本机 4 worker 比 1 worker 快 52%），原因是本机核数更多。
**结论不是"多 worker 好/不好"，而是"worker 数要看真实可用核数，且压测端必须另机"**。
生产 ECS 是 2 核 2G，`deploy.sh` 的 `detect_workers` 内存 <3G 封顶 2 → 落到 **workers=2**，
与 CI 上表现较好的那一档一致。

### 3. 门槛按 p95 设，别按 RPS 设

观测到的 p95 范围是 148 ms（50 并发）～ 1354 ms（200 并发最差组）。RPS 波动 1.85 倍，
拿它做门槛会随机报红；p95 相对稳定。冒烟档当前 `max_p95=3000` 是刻意留的噪声余量，
想收紧到 2000 也安全（仍高于最差观测值 1354）。

## 五、怎么用

```bash
# 手动跑正式档（GitHub 网页：Actions → Loadtest → Run workflow）
#   参数：concurrency / processes / duration / workers / mode / max_p95
# 或直接看 dev 每次推送的冒烟档结果：Actions → Loadtest → 最新 run 的 Summary
```

结果三处可见：job summary（表格）、artifact `loadtest-<run#>.zip`（含原始 JSON）、
以及本地复现同一套口径的 `tools/loadtest_report.py`。

## 六、踩过的两个 workflow 坑（都是会直接让 run 失败的）

1. **`${{ runner.temp }}` 不能写在 job 级 `env:`** —— 报
   `Unrecognized named-value: 'runner'`，整个 workflow 直接 Invalid。
   改用 runner 自带的 `$RUNNER_TEMP` 环境变量（或写在 step 级）。
2. **`upload-artifact` 的 `path` 不展开 shell 变量** —— `"$RUNNER_TEMP/spec.txt"` 会被当字面路径，
   文件静默丢失（不报错，只是产物里没有）。要上传的文件一律写到工作区再按名字写进 path。

## 七、后续可以做的

- 正式档加 `repeats` 参数：同参数跑 3 次取**中位数**，把 1.85 倍的噪声压下去；
- 把 workers × 并发的对照固化成一组矩阵，一次 run 出完整曲线；
- 单独加一个只压 SSE 建流的场景（不打 LLM，只测建流/断流开销），补全"200 人同时发问"这段的空白。
