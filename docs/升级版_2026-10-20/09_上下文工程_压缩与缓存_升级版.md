## 0. 一句话结论

**压缩算法的骨架是对的（增量分段 + 四级安全阀 + 乐观锁），但它现在是一个"黑箱优化"：压没压、压掉了什么、省了多少 token，一个数字都拿不出来。**

校赛口径是"长对话不失忆、不超窗口"——`[COMPRESSED-n]` 增量分段 + L0~L3 安全阀已经做到，且是本项目最拿得出手的自研设计。
省赛口径是"把这件事量化并讲清楚"：压缩触发次数、各级安全阀触发分布、压缩前后 token、缓存命中率、长会话的成本/质量拐点。**这五个数现在一个都没有**（`core/metrics.py:224-239` 预声明的 10 个指标里，与上下文相关的为 0）。这一层的升级就是："把已经做对的事，变成能出示的图。"

## 3. 升级项

### P0-1 压缩与上下文的可观测埋点

- **现状**：`maybe_compress` 返回 `{"ok","reason","upto","action"}`，调用方**只记日志不埋点**（`api/chat.py:1506` 直接 `await` 后丢弃结果）。
- **改什么**：在 `maybe_compress` 的返回点补 4 个指标（用既有 `core/metrics.py`，无需新依赖）：
  1. `compress_attempt_total{result}`（result = `below_threshold` / `nothing_to_compress` / `ok` / `race_lost` / `read_failed`）；
  2. `compress_valve_total{action}`（action = `accept` / `rollback` / `expand_keep` / `truncate`）——**四级安全阀各自的触发次数**；
  3. `context_chars`（直方图，每次组装时观测 `sum(len(content))`）；
  4. `context_messages`（直方图，组装后的消息条数）。
- **为什么省赛必须改**：现在唯一能证明"压缩在起作用"的只有代码评审。有了这 4 个数，答辩时可以说"我们的安全阀在 N 次压缩里拒收了 M 次，全部由 L1 回退兜住"——这是"技术方案 30%"里最难靠嘴讲、最容易靠数据赢的一块。而且成本极低（4 行 `metrics.inc` + 2 行声明）。
- **代价/风险**：零风险（纯计数）；风险在于**埋点位置的语义**——`maybe_compress` 的 `reason` 目前混了"正常不压"与"异常失败"，要先在代码里区分开，否则指标会误导。
- **反转条件**：无。这一项没有不做的理由。
- **验收口径**：跑一个 30 轮的脚本会话，`/api/metrics` 能看到 `compress_valve_total{action="accept"}` ≥ 1；人为构造含 URL 的对话并让抽取式压缩丢掉它，能看到 `{action="rollback"}` 或 `{action="expand_keep"}` 出现。

### P0-2 缓存命中率可算

- **现状**：命中时 `metrics.inc("retrieval_cache", {"kind": "hit"})`（`kb/rag_core.py:1295`），未命中时直接往下走——**没有 miss 埋点**，所以命中率 = hit / (hit + ?) 算不出来。同理查询向量缓存（`_EMBED_CACHE`）与来源缓存完全无埋点。
- **改什么**：在 `_cache_get` 返回 None 的分支加 `{"kind": "miss"}`，给 `_EMBED_CACHE` 与 `_SOURCES_CACHE` 各加一对 hit/miss；在 `/api/metrics` 的口径里补一句"命中率 = hit/(hit+miss)"。
- **为什么省赛必须改**：缓存省的是**真实 API 费用与时间**（embedding 约 250ms/次，`kb/rag_core.py:653-654`）。省赛"功能效果 20%"要"系统测试数据充分"——"我们的检索缓存命中率是 X%，省了 Y 次 embedding 调用"是可以直接写进作品的量化结论，而现在连 X 都算不出。
- **代价/风险**：零；唯一要注意 `neg`（负缓存）与 `miss` 的语义不要混（`kb/rag_core.py:235` 的 neg 是"BM25 通道因库太大而缺席"，是另一回事）。
- **反转条件**：无。
- **验收口径**：同一问题连问两次，第二次 `retrieval_cache{kind="hit"}` +1；问一个不同的问题，`{kind="miss"}` +1；两者可算出比率。

### P0-3 system 提示词的顺序稳定性（KV 前缀的真正根部）

- **现状**：`_build_messages` 里 `system = SYSTEM_PROMPT + grounding_note(grounding) + scenarios_mod.get_scenario_prompt(scenario)`（`api/chat.py:1351-1360`）。`grounding_note` 的输出**随本轮检索强度变化**（strong / medium / weak / 空，四种措辞，`kb/rag_core.py:395-412`），`scenario` 随请求变化。system 是消息序列的第一条，也就是 KV 前缀的**根**——它一变，后面全部缓存作废。
- **改什么**：把 system 拆成"常量段"与"动态段"：system 只留 `SYSTEM_PROMPT`（+ 场景提示，因为场景在一轮内稳定、跨轮才变，可按场景作为图缓存维度已有先例）；`grounding_note` 的动态约束挪到最后一条用户消息里（与"定位信息"同一位置，`api/chat.py:1367-1370` 已经证明这个位置对模型可见性足够且对缓存最友好）。
- **为什么省赛必须改**：卷九 §9.1 花了一整节论证"滑动窗口让 KV 前缀永不命中"，并为此设计了增量分段。但如果 system 根部本身逐轮变，**前面所有稳前缀的工作都被抵消了一半**——这是当前实现里一个真实的、可指出的矛盾。改掉它，才能把"我们懂 KV 缓存"这个故事讲圆（"主题创意 30%" + "技术方案 30%"双吃）。
- **代价/风险**：动态约束从 system 挪到末尾，模型对末尾的注意力略低（卷九 §9.10 已评估过同类取舍：50 token 换"不用判断意图"）。**必须做 A/B 回归**：同一批问题在两种拼法下对比"是否还会硬答"。`GROUNDING_NOTICE=0` 的回滚开关（`core/config.py:126`）保证出问题能一键退回——但注意它退的是"有没有这段"，不是"放在哪"，需要新增一个开关或在回归通过后直接改。
- **反转条件**：若回归显示末尾位置的约束明显压不住硬答（比如 weak 场景下的幻觉率上升 > 10%），则改回 system，并在答辩中如实说明"我们优先保证质量而非缓存命中率"。
- **验收口径**：同一会话连续 5 轮，`system` 字符串完全一致（加一条断言）；回归集上 weak/medium 场景的"示弱率"不下降。

### P1-1 长会话的成本/质量拐点实测

- **现状**：阈值 12000 字 × 0.8 是拍的（`core/config.py:270`）；没有跑过"一个会话聊到 60 轮"的实测。
- **改什么**：写一个 `tools/long_session_probe.py`：脚本化跑 60 轮固定问答，每 10 轮记录一次 `context_chars`、输入 token 估算（`context_compress.estimate_tokens`）、首字延迟、末轮回答质量（人工抽 5 条打分）。产出一张"轮次 vs 成本/延迟/质量"的表。
- **为什么省赛必须改**：这一层是本项目"最不显眼但最省钱"的地方（卷九 §9.0），但**省钱这件事从没被量化过**。省赛答辩最有说服力的一句话是"在 60 轮长会话下，我们的输入 token 从第 1 轮的 X 增长到第 60 轮的 Y，而不是线性增长到 30 倍"——现在说不出 X 和 Y。
- **代价/风险**：60 轮 × 真实 LLM 调用有成本（按 2026-10 的 DeepSeek 单价，一轮约几分钱，可控）；跑在业务低峰，且走独立的限流额度。
- **反转条件**：若实测显示 12000 字的阈值明显过早/过晚（比如第 20 轮就该压 / 第 60 轮还没触发），调整阈值并复测。
- **验收口径**：一张 6 行（10/20/30/40/50/60 轮）的表进作品材料；表格能读出"拐点在第几轮"。

### P1-2 压缩保真度的可追溯视图

- **现状**：被压掉的原文**没有删除**（`messages` 全量保留，`compressed_upto` 只是水位线，`core/context_compress.py:566`），所以数据上完全可追溯；但没有任何接口能把"压缩块 ↔ 被它取代的原文"展示出来。
- **改什么**：加一个只读接口（或调试端点）：给定 `sid`，返回 `[{segment: "[COMPRESSED-1] ...", covers_msg_ids: [12..47], original_chars: N, summary_chars: M}]`。数据来源是 `compressed_summary` 的分段 + `messages` 里 `id <= compressed_upto` 的部分，**不新增存储**。
- **为什么省赛必须改**：评委一定会问"压缩会不会丢信息"。现在只能答"有 L0 实体校验"；有了这个视图，可以**当场演示**："这段 8000 字的对话被压成 300 字，其中 3 个 URL 和 2 个待办全部保留，这是对照。"这是把"我们做了什么"变成"你看"，吃"作品呈现 20%"。
- **代价/风险**：只读接口，风险低；但要注意**权限**（只能看自己的会话，走既有 `owner` 校验）与**数据量**（长会话要分页）。
- **反转条件**：若前端排期紧张，可退化为在 `/api/metrics` 里加一个"压缩块平均压缩比"的数字。
- **验收口径**：一个 30 轮的会话，接口返回 3~5 段，每段的 `covers_msg_ids` 与 `messages` 实际 id 对得上。

### P1-3 多轮指代消解：把压缩块纳入改写的视野

- **现状**：`rewrite_query(req.question, history)` 的 `history` 来自 `store.get_messages(...)[:-1]`（`api/chat.py:1155-1158`），即**30 轮窗口的原文**。会话一旦被压缩，早期内容只存在于压缩块里，而压缩块不在改写输入中。于是"还记得我前面说的那个项目吗"这类问题——若"那个项目"在 40 轮前——改写无法补全指代。
- **改什么**：把改写的输入换成 `ctxcompress.assemble_history(uid, sid, raw)` 的结果（即"压缩块 + 最近 K 轮"），并限制条数（`QUERY_REWRITE_HISTORY=4` 的语义要重新定义为"N 条 + 压缩块摘要 1 条"）。
- **为什么省赛必须改**：省赛场景里"多轮追问"是演示高频动作，而压缩恰恰在长会话才触发——**两个特性在最需要它们同时工作的地方互相看不见**。这是本卷最实质的功能缺陷（不是可观测缺口，是真的少看了一块内容）。
- **代价/风险**：改写 prompt 变长（多 4000 字上限的压缩块），成本上升；需把压缩块截断后再喂（建议取最后 2~3 段而非全块）。且 `assemble_history` 多一次 DB 读——但 RAG 路径本来就要读历史，可复用同一份（`_build_messages` 已支持传 `history`，`api/chat.py:1335-1337`）。
- **反转条件**：若实测显示改写准确率无提升（多数追问的指代对象都在最近 6 轮内），则不做，改为在文档中标注这个已知边界。
- **验收口径**：构造一个 40 轮的会话（前 20 轮讲"六级备考"，压进压缩块），第 41 轮问"它怎么办"——改写后的问题里应出现"六级"（或原问题被正确补全）。

### P2-1 kv-cache 命中率的直接观测

- **现状**：我们只能通过"前缀是否稳定"**间接推断**缓存命中率；上游（DeepSeek）是否返回 `cached_tokens` 字段**待核对**。
- **改什么**：若上游返回 `usage.prompt_tokens_details.cached_tokens`，把它埋成直方图 `llm_cached_tokens_ratio`；若不返回，维持间接推断，并在文档中写明"上游不暴露，我们只能保证前缀稳定"。
- **为什么省赛必须改**：这是"主题创意 30%"里最能体现深度的一个点——能出示真实命中率的人是极少数。但优先级低，因为**依赖上游能力**且我们无法改变。
- **代价/风险**：零（一个埋点）；风险是把"推断"当成"实测"讲，那是造假——**必须如实标注**。
- **反转条件**：上游不提供该字段时，本项降级为文档说明。
- **验收口径**：`/api/metrics` 出现该指标，或文档里有一句明确的"上游不暴露，未做直接观测"。

### P2-2 提示词版本与回答质量的联动展示

- **现状**：`prompt_store` 已做版本快照 + `promote`/`rollback` + 评估留档（`prompt_variants` / `prompt_evals` / `prompt_replay_sets` / `prompt_replay_items` 四张表，`core/session.py:170-227`）；`prompt.evolve` 任务每天 4 轮产出 shadow 候选。
- **改什么**：把这些已有数据接到一个只读的"提示词演进时间线"接口/页面上（版本、diff、M1~M6 指标、是否 promote）。
- **为什么省赛必须改**：这是"提示词自进化"这个差异化能力的**唯一对外呈现**。现在它只活在数据库和日志里。属于"作品呈现 20%"的纯增量，但依赖前端排期，所以 P2。
- **代价/风险**：零技术风险；注意不要暴露 `prompt_text` 全量给非管理员（提示词是系统资产）。
- **反转条件**：无。
- **验收口径**：接口返回最近 5 个版本的状态与指标；页面上能看到"v3 被 promote，M1 提升 X%"。

## 4. 竞品对照

| 竞品 | 这一层怎么做 | 我们差在哪 | 跟不跟 |
|---|---|---|---|
| **Dify**（142k⭐，2核4G） | 有"对话变量 / 会话历史长度"配置；LLMOps 提供 token 消耗追踪与 A/B 测试 | 它的 token 追踪是**产品化的面板**，我们是裸指标；但它的历史管理是"截断 N 条"级别，没有压缩块概念 | **跟它的可观测面板（P0-1/P0-2/P2-2），不跟它的历史策略**——我们的增量分段比"截断 N 条"先进一代 |
| **FastGPT**（26.1k⭐，2核4G） | 有"上下文最大长度"与对话压缩（商业版）；商业版提供运行日志看板 | 差在量化与展示，同 Dify | 只跟看板部分 |
| **RAGFlow**（80.7k⭐，4核16G） | 重心在文档侧（切片/知识图谱），对话上下文管理相对朴素 | 上下文工程这一层我们明显更细（四级安全阀 + 乐观锁 + 增量分段） | 不跟；这是我们的差异化 |
| **Coze 扣子**（闭源 SaaS） | 上下文窗口与记忆由平台管理，用户不可见也不可调 | 不可比 | 不跟；但"用户不可见"正是我们要避免的——P1-2 的可追溯视图就是反其道而行 |
| **n8n**（188k⭐，1核1G） | 有"**上下文记忆窗口**"节点（保留 N 条 / 按 token 裁剪）；执行历史完整落库 | 它的记忆管理是"裁剪"，我们是"压缩 + 保留摘要"，且不丢实体 | 不跟实现；**跟它的"执行历史完整可见"理念**（对应 P1-2） |

**读法**：五个竞品里，只有 n8n 有明确的"记忆窗口"概念，其余都是"截断/不管"。我们的实现深度是够的，**差距全部在"能不能拿出来给人看"**。所以本卷 8 个升级项里有 5 个是纯可观测/展示类（P0-1、P0-2、P1-1、P1-2、P2-1、P2-2），只有 P0-3 和 P1-3 是真的改行为。

## 5. 落地顺序与验收口径

| 序 | 项 | 依赖 | 产出 | 验收（可演示/可截图） |
|---|---|---|---|---|
| 1 | P0-1 压缩埋点（4 个指标） | 无 | `core/context_compress.py` + `core/metrics.py` 各几行 | 30 轮脚本 → `/api/metrics` 出现 `compress_valve_total` |
| 2 | P0-2 缓存 miss 埋点 | 无 | 3 处 `_cache_get` 分支 | 同题两次 → hit+1；异题 → miss+1；可算命中率 |
| 3 | P1-1 长会话拐点实测 | 1 | `tools/long_session_probe.py` + 数据表 | 60 轮的表进作品材料 |
| 4 | P0-3 system 前缀稳定化 | 回归集就绪 | `_build_messages` 拆分 + 一条断言 | 连续 5 轮 system 字符串全等；示弱率不降 |
| 5 | P1-2 压缩追溯视图 | 无（只读接口） | 一个接口 | 30 轮会话返回分段与覆盖 id |

## 6. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| **换更大上下文的模型（梭哈 200K）** | 卷九 §9.0 的核心论点：成本随轮次线性增长，换大窗口只是把拐点推迟，不改变斜率。而且 2G 机器 + 按 token 计费的模式下，"不压缩"是最贵的方案 |
| **引入 Redis / mem0 之类的记忆中间件** | 压缩块已经落库（`conversations.compressed_summary`），再加一层外部记忆会出现"两份真相"，且违反卷七"所有状态都可打包"的原则 |
| **把历史做成可检索的向量记忆（memory RAG）** | 检索层（卷五）已经承担了外部知识的召回；对话历史的召回需求（"我上次说的那个"）由压缩块 + 30 轮窗口覆盖，再引一套向量检索是三份真相 |
| **LLM-as-judge 全量评估压缩质量** | 卷九 §9.4 明确论证过：评估集建好之前，"靠 judged 质量做安全阀"是真空的，而且会与"回退全量"形成死锁。L0 硬规则（零 LLM）是这个约束下的正确解，不改 |
| **自动调参（按指标自动改 `COMPRESS_KEEP_TURNS` / 阈值）** | 没有评估集就没有奖励信号（卷九 §9.13 承认的第二个技术债）。自动调参会在错误信号上收敛。要调，先有 P1-1 的实测数据和人工判断 |
| **流式过程中做压缩（为降延迟）** | 卷九 §9.6："压缩必须在 assistant 落库之后"，否则本轮问答会被当历史压掉，下一轮追问看不到原文。这是一条靠注释守着的隐含约束，不能为了延迟破它 |
| **给每个用户单独配置压缩参数** | 阈值是全局的（`core/config.py:267-277`）；按用户配会让"压缩块格式"出现多种形态，追溯与回归都变复杂。要个性化，先有 P1-1 的数据证明"不同用户的最优阈值确实不同" |
| **把压缩块塞进 system prompt** | `core/context_compress.py:416-422` 已论证：Agent 图按 `(has_kb, 场景, 激活集)` 做 LRU 缓存，压缩块进 system 会让每个会话都编译一张新图，缓存直接失效 |
