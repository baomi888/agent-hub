# 10_交付层_前端部署与运维_升级版（2026-10-20）

> 对应研讨卷：`docs/技术选型研讨_2026-10-20/10_交付层_前端部署与运维.md`
> 本卷回答的问题：从校赛到省赛，**交付层要改什么、为什么现在必须改、改完怎么验**。
> 评审口径参照《中国大学生计算机设计大赛·人工智能应用类》：功能效果 20% 明确要求"系统测试数据充分""已投入实用或具有应用前景、推广价值高"；作品呈现 20% 看文档规范与答辩。交付层是这 40% 里**唯一能被评委当场看见**的一层。

## 0. 一句话结论

**省赛对交付层的要求不是"更高性能"，是"评委随时打开都打得住，而且能证明它一直打得住"。** 因此本卷的升级主线是三件事：把 HTTPS 从"脚本就绪"推到"线上生效"（备案前用 cloudflared 过渡兜底）、把"能观测"从三行 up 指标推到"有错误率与延迟分布"、把回滚从"`git checkout` + 重装依赖"推到"一键回到上一个已知可用状态"。多 worker、首屏体积、预发灰度都是第二梯队——**它们提升的是分数上限，前三条决定的是会不会当场翻车**。

## 3. 升级项

### P0

#### D-P0-1 · HTTPS 落地（备案后 nginx 反代；备案期 cloudflared 过渡）

- **现状**：`https/setup-https.sh` + `agent-hub.conf.template` + `nginx-http-global.conf.template` 三件套就绪且幂等，因 ICP 备案未通过从未执行；生产仍是 `http://IP:3000`。
- **改什么**：① 备案通过后执行 `bash https/setup-https.sh <域名> <邮箱>`，产出 443 → 3000、`/api/` → 8000、SSE 独立 location；② 备案期先用 `cloudflared tunnel --url http://localhost:3000` 拿到一个 https 临时域名，用于申报材料与评委预访问；③ 两条路都在 `部署说明.md` 里写成"有先后顺序的操作手册"，并明确 cloudflared 只是过渡、域名下来即下线。
- **为什么省赛必须改**：一是申报书与演示二维码上写 `http://8.163.62.25:3000` 在"作品呈现"上是硬伤；二是 http 下 Cookie 无法加 `Secure`（`core/auth.py` 的 Secure 判定已按 `X-Forwarded-Proto` 修好，但没有 TLS 就没有意义）；三是移动端定位在无 https 时直接不可用，只能走 IP 兜底。
- **代价/风险**：nginx 常驻约 10~20MB、certbot 只在续期时跑；风险是**证书续期失败**（90 天到期），以及反代上线后 SSE 若被缓冲会"等很久才一次性出来"。前者靠 `certbot.timer` + 一条到期告警，后者靠模板里已有的 `proxy_buffering off`。
- **反转条件**：若备案在省赛材料截止前仍未通过 → 放弃路线 A，全程走 cloudflared，并在申报材料里注明"临时访问地址"。
- **验收口径**：`curl -I https://<域名>` 返回 200；浏览器地址栏无"不安全"；`curl -N https://<域名>/api/chat/stream` 逐帧到达（不等攒包）；`certbot renew --dry-run` 通过；`certbot.timer` 为 active。

#### D-P0-2 · systemd 接管三进程（开机自启 + 崩溃自拉）

- **现状**：`deploy.sh` 用 nohup 起三个进程，机器重启或进程崩溃后不会自动回来；systemd 三 unit 与 `install-systemd.sh`（含 `--rollback`）已在仓库。
- **改什么**：服务器上按 `docs/运维强化落地报告_2026-10-20.md:131` 的顺序执行 `bash systemd/install-systemd.sh`；同时**消除两套管理并存**——明确日常一律 `systemctl`，并（建议）把 `deploy.sh` 第 7 段的启动逻辑改成 `systemctl restart`，或者至少在脚本开头检测 systemd unit 已启用就拒绝 `start`。
- **为什么省赛必须改**：评审期大概率无人值守。nohup 下 worker 静默死亡的表现是"页面全正常、用户今天没收到提醒"——这正是卷十二定律 3 点名的静默失败，而且评委遇到的是"演示时啥都好，第二天委托没了"。
- **代价/风险**：迁移期内两套进程抢端口（`Address already in use`），已在 `docs/运维强化落地报告_2026-10-20.md:86-87` 列为已知行为变更。回滚路径是 `install-systemd.sh --rollback`，一键回 nohup。
- **反转条件**：若迁移后连续两次出现 unit 起不来且回滚过一次 → 暂停，回到 nohup + 每分钟 cron 存活检查的土办法。
- **验收口径**：`systemctl is-enabled agent-hub-{backend,frontend,worker}` 均为 enabled；`kill -9 <backend pid>` 后 5~10 秒内自动回来；`reboot` 后 3 分钟内 `curl 127.0.0.1:8000/health` 与 `curl 127.0.0.1:3000/` 均 200；`journalctl -u agent-hub-worker` 有心跳日志。

#### D-P0-3 · 监控真正接上（probe 拉应用指标 + 错误率告警 + 外部探测）

- **现状**：Prometheus + node-exporter + 3 条告警已备；`probe-health.sh` 只写 3 行 `agent_hub_up`；`GET /api/metrics` 已落地（8 类埋点：`retrieval_top1_similarity` 直方图、`retrieval_grounding_total`、`retrieval_gate_blocked_total`、`chat_truncated_total`、`chat_client_disconnect_total`、`llm_error_total`、`quota_rejected_total` 等），但**没有任何采集器去拉它**。
- **改什么**：① 在 `probe-health.sh` 里加一段：`curl -s -H "X-Metrics-Token: $METRICS_TOKEN" http://127.0.0.1:8000/api/metrics`，把关键几项原样透传进 textfile（改指标名前缀避免与 node-exporter 冲突）；② 新增第 4 条告警：`chat_truncated_total` 5 分钟增量 > 阈值，或 `llm_error_total{class!="title"}` 增量异常；③ 配一个**外部**存活探测（UptimeRobot / healthchecks.io 免费档，需账号自建），因为本机 Prometheus 在主机宕机时自己也没了。
- **为什么省赛必须改**：评分项明确写"系统测试数据充分"。评委问"你们怎么知道系统是好的"，现在的答案只有"组件 up"。有了 `/api/metrics` 却没人采集，等于**埋了点但没接**，比没埋更可惜。
- **代价/风险**：probe 每分钟多一次回环 HTTP，成本可忽略；风险是 `METRICS_TOKEN` 未配时探针静默拿到 403——所以探针必须把"取不到指标"也写成一个指标（`agent_hub_metrics_scrape_ok 0`），否则又是静默失败。
- **反转条件**：若 2G 内存下加 Prometheus 后应用频繁 OOM → 关掉 Prometheus 容器，只保留外部探测 + `/api/metrics/json` 人工查看。
- **验收口径**：Prometheus 里能查到 `chat_truncated_total` 且数值随一次真实截断增长；故意停掉 worker 后 2 分钟内 `AgentHubComponentDown` 触发；外部探测页面显示 30 天内可用率 ≥ 99%。

#### D-P0-4 · 备份与一键回滚

- **现状**：数据全部在 `data/`（sessions.db / scheduler.db / usage.db / chat_uploads）与 `chroma_db/`；无定时备份，无一键回滚脚本。代码侧只有补丁级的 `.bak-时间戳`。
- **改什么**：新增 `ops/backup.sh` 与 `ops/rollback.sh`：① 每天 03:30（避开 `report.backfill` 的 04:00）用 `sqlite3 .backup` 做一致性快照 + `tar` 打包 `chroma_db/`，保留 7 份；② 回滚脚本接受一个快照名，`systemctl stop` → 还原 `data/` → `systemctl start`，并打印"当前回滚到哪个 git commit"。
- **为什么省赛必须改**：评审期最大的单点事故是"演示前一天改了个功能，第二天数据乱了"。没有快照就无法在 5 分钟内恢复，只能清库重来——而清库意味着演示账号里的历史对话、知识库、委托全没。
- **代价/风险**：磁盘占用（SQLite 库 + Chroma，量级待核对，2G 机器 40G 盘通常够 7 份）；风险是**在写入过程中拷贝**导致快照不可用——所以用 `sqlite3 .backup`（WAL 安全）而不是 `cp`。
- **反转条件**：若快照耗时超过 3 分钟或磁盘占用超过 30% → 降到每周一次 + 只备份 SQLite（Chroma 可由知识库重新导入）。
- **验收口径**：手动执行 `bash ops/backup.sh` 产出带时间戳的目录；`bash ops/rollback.sh <快照>` 后 `/api/report/today` 与知识库检索结果与快照前一致；演练一次"删库→回滚"，全程 < 10 分钟。

### P1

#### D-P1-1 · 前端首屏与产物体积

- **现状**：已开 `output: "standalone"`（`next.config.ts:7`），依赖精简这一最大的一步已完成；但**没有产物体积基线、没有首屏指标**（待核对）；构建侧已知峰值约 800MB，脚本用 `--max-old-space-size=1536` 压住（`deploy.sh:311`）。
- **改什么**：① 在服务器上构建后记录 `du -sh .next/static` 与 `First Load JS`，写进本文档作为基线；② 首屏按卷十 §10.6 已经调整成"主次两层"（每日总结/委托/对话三个天天用的入口在主线），把这条产品决策落到**代码分割**上——模板广场等一次性页面做成动态 import，不进首屏 chunk；③ 加一个构建期门槛：首屏 JS 超过预算就告警（不阻断）。
- **为什么省赛必须改**：评委用手机 4G 打开，首屏超过 3 秒会直接判定"体验差"。而"首屏为什么慢"这个问题，现在**没有任何数据可以回答**——先要有基线，才谈得上优化。
- **代价/风险**：动态 import 会让模板广场首次点击有几十毫秒延迟；风险是拆错 chunk 反而让首屏变大。所以每拆一次都要重记基线。
- **反转条件**：若实测首屏 JS < 200KB 且 LCP < 2s → 本项降级为"只记录基线，不拆分"。
- **验收口径**：文档里有一张"日期 / `.next/static` 大小 / 首屏 JS / LCP"的表；手机 4G 模拟下首屏可交互 < 3 秒。

#### D-P1-2 · 多 worker 真正生效 + 并发闸 + 压测进 CI

- **现状**：`detect_workers` 在 2G 内存机器上封顶 2（`deploy.sh:53`）；压测显示 4 worker 收益明确（1050 RPS / p99 1012ms）；A3 双层限流已修掉"限流强度变 N 倍"这个前置障碍；但 **P0-2 的 LLM 并发闸与 P0-3 的 SSE 断连回收尚未实施**（`docs/并发承载测试报告_2026-10-20.md:109,116`）。
- **改什么**：① 把 `WORKERS` 显式写进 `.env`（2 核 2G 建议 2，若加内存再评估 3~4）；② 加全局 `asyncio.Semaphore(config.LLM_MAX_CONCURRENCY)`，超出的请求**排队而不是一起打上游**；③ SSE 客户端中断时立刻取消上游请求，避免幽灵请求继续烧 token；④ `tools/loadtest_concurrency.py` 作为冒烟进 CI。
- **为什么省赛必须改**：评委演示时最可能的操作就是"几个人同时提问"。没有并发闸时，表现是"转圈很久才出字"——这是唯一会让评委当场觉得"这系统不行"的场景，而它发生在 Web 层之外。
- **代价/风险**：并发闸参数定错会降低吞吐（设太小排队、设太大仍撞上游 TPM）；SSE 取消逻辑写错会误杀正常流。两者都要有开关（`LLM_MAX_CONCURRENCY=0` 表示不启用）。
- **反转条件**：若压测显示单 worker 已满足目标并发（>10 倍余量）→ 不开多 worker，本项只做并发闸。
- **验收口径**：服务器上（不是本机）复测 `/api/auth/me/` 与 `/health`，记录 RPS/p95/p99；模拟 20 路同时提问，断言全部在 N 秒内出首个字且无 5xx；`chat_client_disconnect_total` 在关闭页面后 +1。

#### D-P1-3 · 预发 3001/8001 变成必过关卡

- **现状**：`deploy-staging.sh` 有两条硬护栏（DATA_DIR 指向生产即拒绝；按端口精确 kill 不误杀生产），但**没有"上线前必须先在预发验一遍"的流程约定**。
- **改什么**：把"预发验证清单"写成 `知穗_服务器配置分享包/README.md` 的一节：改前端必先在 3001 构建并通过登录→问答→建库→委托→总结五步；通过后才允许动生产。
- **为什么省赛必须改**：评审期每次改动都直接上生产，等于把演示稳定性押在"这次不会写错"。预发的价值不是环境隔离（那已经有了），是**流程关卡**。
- **代价/风险**：2 核 2G 同跑两套实例吃紧，卷十已写明"不要同时构建两端"。所以预发是"用完即停"，不是常驻。
- **反转条件**：若预发构建时间超过 15 分钟导致没人愿意走流程 → 退化为"只改后端时跳过预发，改前端必须走"。
- **验收口径**：最近 3 次生产变更记录里，每一次都能指到对应的预发验证时间戳。

#### D-P1-4 · 演示稳定性包

- **现状**：无专门的演示账号、预置数据与降级预案。
- **改什么**：建一个 `demo` 账号，预置 2~3 个知识库、若干历史会话与已生成的每日总结/委托历史；写一份"演示 5 分钟脚本"（打开→登录→问一个知识库内问题→看总结→看委托）；准备断网/上游故障时的说法与截图。
- **为什么省赛必须改**：评委打开看到的是空空如也的新账号，等于没看到产品。这是"作品呈现 20%"里最便宜的 10 分。
- **代价/风险**：预置数据会混进真实统计（总结数、用量）；所以演示账号要在文档里标注，压测与评估时排除。
- **反转条件**：若评委明确要求注册自己账号体验 → 演示账号保留为兜底，主路径改为提供一键注册的引导。
- **验收口径**：用一台没登录过的手机，按 5 分钟脚本走完，全程无空白页、无 500。

### P2

#### D-P2-1 · 成本账单成文

- **现状**：ECS 2核2G + 域名 + 备案 + 带宽 + DeepSeek/百炼 API 按量；**具体金额未成文**（待核对）。
- **改什么**：在 `部署说明.md` 补一节"月度成本结构"，列四项（计算 / 带宽 / 域名 / 模型 API），并给出"模型 API 的大头在哪个调用路径上"的判断依据（可用 `DAILY_AUTO_LIMIT=120` 与 `DAILY_ASK_LIMIT=60` 反推上界）。
- **为什么省赛必须改**："推广价值高"这条评分标准隐含"可复制、可持续"。说不清成本 = 说不清能不能推广。
- **代价/风险**：金额是估算，必须标注口径与日期，避免答辩时被追问。
- **反转条件**：若团队不打算对外推广 → 本项降为答辩备查材料，不进正式文档。
- **验收口径**：一张四项成本表 + 一句"人均月成本"结论。

#### D-P2-2 · 前端错误上报

- **现状**：`window.onerror` 无人接收；线上前端白屏只能靠用户截图。
- **改什么**：在 `frontend/src/lib/api.ts` 旁边加一个极薄的上报：`window.onerror` / `unhandledrejection` → `POST /api/metrics/client-error`（或先只写 console + 落服务端日志）。
- **为什么省赛必须改**：优先级低于 P0，因为"看不到前端错误"影响的是排查效率，不是评委体验。
- **代价/风险**：上报本身可能失败或刷屏；必须有本地去重与采样。
- **反转条件**：若评审期没出现过前端白屏 → 不做的成本 < 做的成本，可推迟到赛后。
- **验收口径**：制造一次前端异常，服务端日志出现一条带 UA 与路径的记录。

#### D-P2-3 · CI 断言"跑了多少个测试"

- **现状**：CI 用 `pytest -q`，只看 exit code；卷十 §10.12 已经点名"假绿"是最高发现难度的失败。基线：审计后 `397 passed / 20 subtests`。
- **改什么**：CI 增加一条断言——`pytest` 输出里的 passed 数不低于设定的下限（如 397），并把脚本式自测单独一个 step。
- **为什么省赛必须改**：这是"代码质量"这 20% 里最容易被评委/助教抽查的一条——**能不能证明测试真的跑了**。
- **代价/风险**：下限写死会导致新增/删除测试时 CI 无谓变红；所以下限要随基线更新，并在 PR 模板里要求同步。
- **反转条件**：若测试数量频繁变动导致维护成本过高 → 改为断言"关键 6 个测试文件存在且通过"。
- **验收口径**：故意删掉一个测试文件，CI 变红。

## 4. 竞品对照

| 竞品 | 这一层怎么做 | 我们差在哪 | 要不要跟 |
|---|---|---|---|
| **Dify**（142k⭐） | Docker Compose 一键部署，官方基线 2核4G；自带 LLMOps 监控与 A/B 测试，应用层面直接看调用量与延迟 | 我们的监控要自己接（P0-3），且没有 A/B 能力 | **部分跟**：监控（自建 `/api/metrics`，已在做）；A/B **不跟**——3 人团队没有流量支撑 A/B 结论 |
| **FastGPT**（26.1k⭐） | 2核4G；商业版 10000 元/月起，卖点是多租户 / SSO / **运行日志看板** | 我们的"运行日志"分散在 journald 与 `job_runs` 表，没有统一看板 | **跟一半**：`job_runs`（`core/scheduler.py:137-157`）已经是运行日志的结构化载体，加一个只读页面即可，比接看板系统便宜 |
| **RAGFlow**（80.7k⭐） | Docker，官方建议 **4核16G**；自带解析与引用溯源展示 | 我们 2核2G 跑住同等能力，这是优势不是差距 | **不跟**：它的资源基线是我们的 8 倍，正是我们用裸机+venv+轻量前端换来的 |
| **Coze 扣子** | 注册即用，零运维，https/域名/并发全部托管；闭源且算力付费 | 演示稳定性上它天然满分（不用自己运维） | **不跟**：闭源意味着答辩时说不清"技术方案 30%"里的架构；但**借鉴它的演示形态**——一条链接打开即用，这正是 D-P0-1 + D-P1-4 的目标 |
| **n8n**（188k⭐） | 1核1G 即可跑；fair-code 许可证**禁止作为 SaaS 对外售卖** | 与我们无关（不做工作流 SaaS），但许可证这一条值得在答辩时主动提——说明我们看过许可证 | **不跟**：不适用；只作为"轻量部署也能成立"的旁证 |

**共同的差距一句话**：这些项目在"部署与运维"上的优势，几乎全部来自**容器化 + 托管**。我们在 2核2G、零运维、三人并行的约束下用裸机 + systemd + textfile probe 达成了同样的"能跑住"，这是**技术方案 30% 里可以主动讲的取舍**；但代价是"可观测的深度"要自己补，这就是 P0-3 与 P0-4 存在的理由。

## 5. 落地顺序与验收口径

| 序 | 项 | 依赖 | 耗时量级 | 验收口径（可复现命令/现象） |
|---|---|---|---|---|
| 1 | D-P0-2 systemd 接管 | 无 | 半小时 | `systemctl is-enabled` 三服务 enabled；`kill -9` 后自动回来；`reboot` 后两端口 200 |
| 2 | D-P0-4 备份与回滚 | 1（回滚依赖 systemctl） | 半天 | `ops/rollback.sh <快照>` 演练一次，10 分钟内数据一致 |
| 3 | D-P0-3 监控接上 | 1 | 半天 | Prometheus 能查到 `chat_truncated_total`；停 worker → 2 分钟内告警 |
| 4 | D-P0-1 cloudflared 过渡 | 无 | 1 小时 | 拿到 https 临时地址，手机能打开并完成登录 |
| 5 | D-P1-1 首屏基线 | 1 | 半天 | 文档里出现 `.next/static` 大小与 LCP 的第一行记录 |
| 6 | D-P1-2 并发闸 + workers | 1（A3 已修） | 1 天 | 服务器复测 RPS/p99；20 路并发提问全部出首个字 |
| 7 | D-P1-4 演示包 | 1 | 1 天 | 未登录手机按 5 分钟脚本走通 |
| 8 | D-P0-1 nginx 正式上线 | **备案通过** | 1 小时 | https 200、证书锁图标、`renew --dry-run` 通过 |
| 9 | D-P1-3 预发关卡 | 1 | 半天（流程） | 最近 3 次变更均有预发记录 |
| 10 | D-P2-* | 有余力 | — | 见各条口径 |

**顺序理由**：1→2→3 是"先让它不死、再让它能救、再让它可见"，任何一条跳过都会在评审期变成事故。4 与 8 是同一条路线的两个阶段，**4 现在就能做，8 等备案**。5~7 是加分项，做完一项就多一分证据。

**总验收（交付层一句话）**：把 `http://IP:3000` 换成一个 https 域名，用一台没登录过的手机从搜索到完成一次问答与一次总结查看，全程 < 3 分钟且无任何错误页；同时监控面板上有过去 7 天的可用率与错误率曲线。

## 6. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| **Docker Compose 化** | 2G 内存上 daemon 常驻 80~100MB（约 5%），且 Chroma 的 sqlite 在 bind mount 上有 WAL 文件锁风险（卷十 §10.7）。机器数仍是 1，容器化的核心收益"环境一致性"由 `requirements.txt` + venv + 分享包解决。**反转条件：出现第 2 台机器时立刻重评。** |
| **K8s / 多副本** | 机器数 = 1，控制面内存 > 应用内存。 |
| **CDN / 对象存储分离静态资源** | 首屏瓶颈尚未证实（D-P1-1 要先出基线）；且引入第二套域名会破坏"同源免 CORS"这个既有收益（卷十 §10.1 表最后两行）。 |
| **Redis 做严格限流** | A3 的双层方案已给出"约 N+ε"的护栏，且有开关可平滑升级；Redis 是又一份常驻内存（卷十二 §12.8）。 |
| **自建 CA / 自签证书** | 自签证书在评委浏览器上是红色警告页，比 http 更难看。宁可用 cloudflared 过渡。 |
| **Sentry / 商业 APM** | 内存与成本；且我们没有流量支撑它提供的聚合价值。P2-2 的极薄上报足够。 |
| **把 `frontend` 与后端拆成两个域名** | 会立刻引入 CORS + 双证书 + Cookie 域问题，毁掉当前最省事的一条架构决策。 |
| **自动扩缩容 / 弹性伸缩** | 目标规模是"3 人 + 评委"，压测余量 25 倍以上（`docs/并发承载测试报告_2026-10-20.md:62-68`），没有触发条件。 |
| **在答辩前大规模重构前端** | 卷十 §10.3/§10.4 的令牌体系与 `100dvh` 已经过视觉审查；重构的收益（代码质量）小于风险（演示崩）。相关技术债进 `docs/架构假设.md` 台账，赛后处理。 |
