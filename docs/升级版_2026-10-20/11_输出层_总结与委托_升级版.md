# 11_输出层_总结与委托_升级版（2026-10-20）

> 对应研讨卷：`docs/技术选型研讨_2026-10-20/11_输出层_总结与委托.md`
> 本卷回答的问题：从校赛到省赛，**这一层要改什么、为什么现在必须改、改完怎么验**。
> 输出层是全项目唯一"没有提问者"的产出（`service/daily.py` + `api/report.py` + `api/delegate.py`）。省赛评分里它同时命中两条：**功能效果 20%**（"系统测试数据充分""已投入实用"）与**主题创意 30%**（"天天来看"的机制是产品的差异化）。

---

## 0. 一句话结论

**校赛阶段输出层证明了"它写出来的每句话都能指回原文"，省赛要证明的是"它写出来的东西值得天天来看，而且能拿数字说明有多值得"。** 因此升级主线是三件事：把**覆盖率**（总结覆盖了多少条消息）显式化——现在它是静默的；给总结与委托各建一套**可复现的评测集**（检索侧已有 `tools/eval_retrieval.py`，输出侧是零）；把"每日批量任务的账"从**次数闸**（`DAILY_AUTO_LIMIT=120`）升级为**钱闸**（真实 token 记账）。推送渠道与个性化是第二梯队，但它们决定"推广价值"这条能不能讲圆。

## 3. 升级项

### P0

#### O-P0-1 · 覆盖率显式化（把静默截断变成可见数字）

- **现状**：`_gather_day_text` 在超 `_MAX_REDUCE_CHARS=20000` 时截断并追加"…（后续对话已截断）"，但这段文本只喂给模型；返回给前端的 `stats` 是**全量 SQL 统计**（`message_count` 可能 200），内容却是**部分**的。卷十一 §11.11 已把它列为"未解决的矛盾"。
- **改什么**：`collect_stats` 之外补一个"覆盖口径"：让 `_gather_day_text` 返回 `(text, covered_count, total_count, truncated)`，`summarize_day` 把它写进 `stats`；`api/report.py::_report_to_dict` 原样透传；前端在总结卡上显示"基于当天前 N / 共 M 条消息生成"。
- **为什么省赛必须改**：这是"数字与内容口径不一致"——卷十二缺陷清单里的**口径漂移**形态。评委只要问一句"这个总结是拿多少数据算出来的"，现在答不上来。而它同时是**加分项**：敢主动标注覆盖率，本身就是"可审计性"的证据。
- **代价/风险**：`stats_json` 是 TEXT，`INSERT OR REPLACE` 不需要迁移（`service/daily.py:285-304`）；风险是老报告的 `stats` 没有新字段，前端要做缺省（缺省视为"未知"而不是 100%）。
- **反转条件**：若实测 99% 的用户当天消息数 < 覆盖上限 → 本项降级为"只在极端日显示提示"，但**字段仍要落库**（因为它是评测集 O-P0-2 的输入）。
- **验收口径**：造 250 条消息的一天 → `stats.covered < stats.message_count` 且 `truncated=true`；造 5 条消息的一天 → `truncated=false`；老报告（无字段）前端显示"覆盖未知"而不是"100%"。

#### O-P0-2 · 输出质量评测集（`tools/eval_summary.py`）

- **现状**：检索侧有 `tools/eval_retrieval.py`（3 篇语料 16 题、recall@1/3/5、MRR、离题示弱率、可分性 AUC，且诚实标注了"假向量下评估的是管道口径而非向量质量"）。**输出侧一个评测都没有**。
- **改什么**：照抄检索侧的骨架——`tools/eval_summary.py` + `tools/eval_corpus/summary/`：① 造 5~8 个"合成的一天"（脚本灌入固定 messages，含一条明显可总结的事实、一条噪音、一条离题）；② 用**注入的假 LLM**（`summarize_day(llm=FakeLLM())`，`service/daily.py:321`）跑管道，测**管道口径**；③ 配 `DEEPSEEK_API_KEY` 时自动切真模型，测**生成质量**；④ 三个指标：**溯源率**（保留结论/产出结论）、**准确率**（人工标注 N 条期望事实，看是否被覆盖且未被曲解）、**有用率**（三人各打一次 1~3 分的盲评，取一致率）。
- **为什么省赛必须改**：没有评测集，"改提示词"就是掷骰子——卷十二 §12.7 缺陷 1 把这条列为"最大的方法论缺口"，原话是"没有评估集，就无法知道改一个参数是变好还是变坏"。而"系统测试数据充分"是**明文评分项**，评测集是唯一能直接出示的证据。
- **代价/风险**：人工标注要花时间（建议 20 条期望事实，半小时）；盲评有主观性，所以"有用率"必须报一致率（如 Cohen's κ）而不只报均值。最大风险是**把假 LLM 的分数当质量分**——所以脚本必须像 `eval_retrieval.py` 那样在输出里打印"当前是假 LLM 模式，本轮数字不代表生成质量"。
- **反转条件**：若标注成本超出预算 → 只保留"溯源率 + 覆盖率"两个**零人工**指标，准确率与有用率降级为答辩现场演示。
- **验收口径**：脚本可重跑且数字稳定（跑两次差异 < 阈值）；假 LLM 模式下溯源率 = 100%（构造的假输出全部可溯源）；真模型模式下三个指标均有数字且写进本文档；改动提示词后能说出"准确率从 X 到 Y"。

#### O-P0-3 · "今天为什么没收到"可自查

- **现状**：`job_runs` 有 `trigger` / `status` / `error` / `next_attempt_at`，`GET /api/delegate/{id}/runs` 已暴露；`on_failure` 会自动停用失效委托。但**没有指标**，也没有"我昨天到底发没发"的一眼视图。
- **改什么**：① `core/metrics.py` 增加 `delegate_dispatch_total{status}`、`report_generated_total{status}`、`report_empty_total`；② 委托列表卡片上直接显示"上次投递：今天 08:00 成功 / 昨天失败（原因：会话不存在）"，数据来自现有 `runs` 端点，不新增接口；③ `report.backfill` 补实装（`service/daily.py:512` 目前返回空）——至少把"当日 status=empty 但后来又有消息"的情况补一次。
- **为什么省赛必须改**：这是输出层唯一的**静默故障**形态（卷十二定律 3：定时任务漏投，用户可能不说）。评委如果注册账号试用，第二天没收到委托，那是最坏的一种演示。
- **代价/风险**：backfill 实装会引入重试语义，必须复用 `job_runs` 的 `idem_key`（`job_key|subject_id|planned_at`）避免重复打扰；风险是补生成与次日正常生成撞车——用 `INSERT OR REPLACE`（upsert，`service/daily.py:285`）天然幂等。
- **反转条件**：若 backfill 在 2G 机器上与 04:00 的其他 job 抢 SQLite 写锁 → 挪到 04:45 或改为按需手动触发。
- **验收口径**：人为让一条委托的 `deliver_sid` 失效 → 第二天委托被自动停用且列表上显示原因；人为让一次总结失败 → 04:00 后 `daily_reports.status` 变为 `ready`；`/api/metrics` 里三个新计数非零。

### P1

#### O-P1-1 · 响应形状收口（`content` object + `sources`）

- **现状**：D-002 裁决取 object 且必须补 `sources`，代码仍是 `list`（`service/daily.py:198,263`），`api/report.py::_report_to_dict` 无 `sources`（:27-36）。
- **改什么**：二选一，且**只选一个**（卷十一 §11.4 明说"不要两种都支持"）：
  - 方案 A（主）：`content` 改 object `{topics, questions, highlights, todo, suggestions}`，并补 `sources: {id: {title, ts}}`；
  - 方案 B（退守）：保留 list，**只补 `sources`**（只做加法不改形状）。
- **为什么省赛必须改**：`todo` 的 `done` 状态只有 object 能表达（卷十一 §11.4 原话："list 表达不了 done 状态"），而"待办能勾"是让总结从"看"变成"用"的关键一步；`sources` 则是溯源角标**能点出标题**的前提——溯源是我们最想给评委看的东西，现在它是灰的。
- **代价/风险**：方案 A 要动 `service/daily.py` 与 `_filter_by_traceability`，是**真实返工**（D-002 已诚实标注）；且前端 `report/page.tsx` 要改渲染。风险是两人并行改前端/后端再次形状不一致——所以先写一个契约测试锁住形状再改。
- **反转条件**：若距省赛材料截止 < 2 周 → 直接走方案 B（只补 `sources`），object 留到赛后。
- **验收口径**：契约测试断言 `content` 形状与 `sources` 键集合；前端角标显示标题且可点回原消息；一次真实总结的响应体能被这份契约测试复现。

#### O-P1-2 · 推送渠道（先站内，再考虑站外）

- **现状**：只有站内会话投递（`service/daily.py:575-577`）；全仓无 SMTP / 推送 / Webhook。
- **改什么**：分三档，**按成本从低到高做**：
  - 档 1（便宜，先做）：站内**未读红点 + 浏览器通知**（Notification API，需 https —— 与卷十 D-P0-1 是同一条链路，无 https 则不可用）；
  - 档 2（中）：企业微信/飞书群机器人 Webhook（一个 POST，成本极低，适合"每日委托"这种团队场景）；
  - 档 3（贵，赛后再说）：邮件（要 SMTP 服务 + 域名邮箱 + 反垃圾配置）。
- **为什么省赛必须改**："每日委托"如果不能主动触达，就退化成"打开时才看到"，产品故事讲不完整。而"推广价值高"这条评分标准，很大程度上取决于"能不能把内容送到用户面前"。
- **代价/风险**：浏览器通知需要用户授权且**依赖 https**——这是它排在 https 之后的原因；Webhook 会把内容发到第三方，必须让用户显式开启并在 UI 上说明。风险最小的是档 1，因为它不出站。
- **反转条件**：若备案在省赛前未通过 → 浏览器通知不可用，直接跳到档 2（Webhook），并在答辩时说明"因备案周期限制，主动触达采用 Webhook 方案"。
- **验收口径**：开启授权后，委托投递时刻（可用 `dry_run` 之外的手动 run 模拟）桌面出现通知；Webhook 版：群里收到一条带委托内容的消息；两者都可在设置里一键关闭。

#### O-P1-3 · 个性化（把已生成的画像用起来）

- **现状**：`RETRIEVAL_BIAS_ENABLED=1` / `ALPHA=0.08` 让画像影响**检索排序**（`core/config.py:254-255`）；`profile.aggregate` 每日 02:30 生成 `user_profiles` 快照（`core/scheduler.py:111-113`）；但 `summarize_day` 与 `plan_today` 的提示词**完全不读画像**。
- **改什么**：`summarize_day` 的 system 提示词里注入"该用户的 Top-N 兴趣标签"（来自 `store.get_user_tags`，`service/daily.py:559`），作用是**选题偏置**——同样一天对话，对"考研"标签重的人优先提炼备考相关结论；`plan_today` 同理，让委托语气与关注点跟随画像。标签注入要加开关（`SUMMARY_BIAS_ENABLED`），并做长度上限。
- **为什么省赛必须改**："个性化"是我们区别于"通用 AI 助手"的叙事核心，而现在它只在检索层生效，**用户看不见**。用户能看见的只有总结与委托——所以偏置必须下沉到输出层，否则这个故事讲不圆。
- **代价/风险**：注入标签会改变提示词前缀，可能破坏 KV 缓存（卷十二定律 5）——所以标签必须放在**末尾的用户消息**里，不能进 system；风险是偏置过头导致总结偏执（只看一个方向），所以要限制标签条数与权重阈值。
- **反转条件**：若评测集（O-P0-2）显示注入画像后准确率下降 → 关闭开关，只保留检索侧偏置，并在文档里写明"输出层不做偏置"的理由。
- **验收口径**：同一天数据、两个不同画像的用户，注入开关打开时结论排序不同；关闭时完全一致；O-P0-2 的准确率不下降。

#### O-P1-4 · 每日批量任务的钱闸

- **现状**：`DAILY_AUTO_LIMIT=120` 是**次数**上限（`core/config.py:171`）；`run_one` 无论总结还是委托都返回 `tokens_out: 0`（`service/daily.py:545,588`），所以 `job_runs.tokens_out` 恒为 0——**花了多少钱没有任何数据**。
- **改什么**：① 让 `summarize_day` / `plan_today` 把真实用量回填（DeepSeek 兼容接口通常在 `response_metadata` 里给 `usage`；取不到时记 0 并**打点标记 `usage_missing`**，不能直接猜）；② `core/metrics.py` 增 `auto_tokens_total{job_key}`；③ 在 `/api/usage` 或管理员视图里给出"昨日自动任务消耗"。
- **为什么省赛必须改**：次数闸挡的是"跑太多次"，挡不住"一次跑太大"（一个人一天 200 条消息 → 总结输入 20000 字符）。无人值守的定时任务烧钱是卷十二点名的静默失败；而"推广价值"要求能回答"每人每月多少钱"。
- **代价/风险**：不同 provider 的 usage 字段位置不同，取不到是常态——**必须显式标记缺失**，否则又是一个静默失败（重蹈 A1 截断检测的覆辙）。
- **反转条件**：若上游永远不返回 usage → 退化为"按输入字符数估算"并在文档标注是估算值。
- **验收口径**：造一次已知长度的输入 → `auto_tokens_total` 增长量与手工计算的字符数同量级；`/api/metrics` 里 `usage_missing` 计数可见；能给出"3 人 × 30 天"的月度估算。

#### O-P1-5 · 导出与分享

- **现状**：无导出；总结只在站内看。
- **改什么**：① Markdown 导出（前端直接把 `content` + `stats` 渲染成 `.md` 下载，后端不参与）；② 只读分享链接（后端加一个带过期时间的 token 端点，返回脱敏后的总结 JSON）。
- **为什么省赛必须改**："学习档案"这个定位天然要求能带走；分享链接则是"推广价值"最直接的证据（评委可以把链接放进评审记录）。
- **代价/风险**：分享链接是**新的公开读接口**，是新的攻击面——必须：只读、带过期、脱敏（`sources` 只给标题不给原文）、可撤销。
- **反转条件**：若分享链接的安全评审成本超过收益 → 只做 Markdown 导出（纯前端，零后端风险）。
- **验收口径**：导出的 `.md` 能在 Typora/记事本正常打开且保留溯源编号；分享链接过期后访问返回 410；分享内容不含其他用户数据。

### P2

#### O-P2-1 · map-reduce 上浮

- **现状**：单次调用（`service/daily.py:20-25` 已如实标注与 spec 的偏差），长日靠 `_MAX_REDUCE_CHARS` 截断。
- **改什么**：当"重度用户（200+ 消息/天）占比 > 10%"时（卷十二 §12.5 的触发条件）实装按会话分块摘要 → 合并。接口与落库结构不变，所以可平滑升级。
- **为什么现在不必须**：目标是学生用户，卷十一的判断是"每天 5~10 轮，单次足够"。有了 O-P0-1 的覆盖率数据后，这个判断才第一次有了证据——**如果数据说重度用户确实超过 10%，它就从 P2 升到 P1**。
- **验收口径**：`stats.truncated=true` 的日占比作为触发指标。

#### O-P2-2 · 总结变入口（可追问）

- **现状**：总结是终点，看完就完。
- **改什么**：每条结论旁一个"就这条继续聊"按钮 → 带着 `source_refs` 指向的原始消息开一个新会话（或跳到原会话）。
- **为什么不在 P1**：它需要 `sources`（O-P1-1）先落地，且涉及前端会话创建流程。
- **验收口径**：点击后新会话的首条消息包含被引用原文。

#### O-P2-3 · 周报 / 月报

- **现状**：只有日报。
- **改什么**：复用 `daily_reports` 做周聚合（同一套溯源与幂等思路，`report_id = md5(uid|week)`）。
- **为什么赛后再说**：增加调度任务 = 增加静默故障面，在 2G 机器上不划算；且评委不会等到下周。

## 4. 竞品对照

| 竞品 | 输出层怎么做 | 我们差在哪 | 要不要跟 |
|---|---|---|---|
| **Dify**（142k⭐） | 工作流可产出结构化结果；自带 LLMOps 监控与 **A/B 测试**，能直接对两个提示词版本做效果对比 | 我们有"可注入 LLM"的测试便利，但**没有 A/B 框架、没有线上效果对比** | **部分跟**：借鉴"版本化提示词 + 效果对比"的思路，但我们没有流量做 A/B；改为**离线评测集**（O-P0-2）+ 提示词版本号落库。不跟它的 A/B 平台 |
| **FastGPT**（26.1k⭐） | 商业版卖点是**运行日志看板**：每次工作流运行、每步耗时、成功失败一目了然 | 我们的运行日志在 `job_runs` 里（`core/scheduler.py:137-157`），但没有看板 | **跟**：`job_runs` 已经是结构化载体，加一个只读页面即可，成本极低，且正好补上 O-P0-3 |
| **RAGFlow**（80.7k⭐） | 强项是**引用溯源的可视化**：答案里每句都能点开看原文片段与位置 | 我们的溯源在数据层更严格（指不回就丢弃），但**展示层是弱角标**（`sources` 未补） | **跟**：这是 RAGFlow 最值得抄的一点，且我们后端已经更严格——补上 `sources` 就能超过它的展示效果（O-P1-1 方案 B 即可达到） |
| **Coze 扣子** | 定时触发器 + 机器人推送，天然多渠道（飞书/微信/钉钉），注册即用 | 我们只有站内投递；但 Coze 的定时任务是黑盒，失败不可自查 | **跟渠道，不跟黑盒**：档 2 的 Webhook 就是廉价版多渠道（O-P1-2）；而"失败可自查"（O-P0-3）恰恰是我们比它强的地方，要主动讲 |
| **n8n**（188k⭐） | 定时 + 多通道投递是它的主场（1核1G 即可跑）；fair-code 禁止作为 SaaS 对外售卖 | 我们自建调度是为了"幂等 + 可自查"，n8n 的外部编排会引入第二套状态（卷十二反模式 6：把状态管理交给框架） | **不跟**：把 `job_runs` 的幂等交给外部编排会失去"为什么今天没发"的自查能力 |

**共同的差距一句话**：这些产品在"输出"上并**没有**比我们更严格的信任机制——我们的强制溯源（指不回原文就丢弃）比它们多数都硬。真正的差距全在**两处**：**展示层**（溯源角标是灰的）和**评测层**（我们不知道自己写得好不好）。这两处正是 O-P0-2 与 O-P1-1 要补的，且都不需要换架构。

## 5. 落地顺序与验收口径

| 序 | 项 | 依赖 | 耗时量级 | 验收口径 |
|---|---|---|---|---|
| 1 | O-P0-1 覆盖率显式化 | 无 | 半天 | 250 条消息日 → `truncated=true` 且 `covered < total`；老报告显示"未知" |
| 2 | O-P0-2 输出评测集 | O-P0-1（覆盖率是指标之一） | 1~2 天（含标注） | 脚本可重跑、数字稳定；假 LLM 模式下溯源率 100%；真模型模式三指标有数 |
| 3 | O-P0-3 投递可自查 + backfill 实装 | 无 | 1 天 | 失效委托自动停用并显示原因；失败总结次日凌晨补上 |
| 4 | O-P1-1 方案 B（只补 `sources`） | 无 | 半天 | 契约测试锁住形状；角标显示标题且可点 |
| 5 | O-P1-4 token 钱闸 | 无 | 半天 | `auto_tokens_total` 有数；`usage_missing` 可见；月度可估算 |
| 6 | O-P1-3 画像下沉输出层 | O-P0-2（要有准确率做反转判据） | 1 天 | 开关开/关结论不同；准确率不下降 |
| 7 | O-P1-2 推送档 1/档 2 | 卷十 D-P0-1（https） | 1 天 | 授权后收到通知 / 群机器人收到消息；可一键关闭 |
| 8 | O-P1-5 导出（Markdown 优先） | 无 | 半天 | 导出 `.md` 可直接打开 |
| 9 | O-P1-1 方案 A（object 形状） | 4 + 前端排期 | 2 天 | 契约测试；`todo.done` 可勾 |
| 10 | O-P2-* | 有余力 | — | 见各条 |

**顺序理由**：1→2 是"先有数据，再谈质量"——没有覆盖率就无法解释评测集里的低召回是"截断"还是"模型差"。3 是防事故，与 1、2 无依赖可并行。4 是**最便宜的展示层提升**（半天），优先于需要重新排期前端的 9。5 是成本可解释性。6~8 依赖 2 与 https，排在后。

**总验收（输出层一句话）**：拿得出三张表——**覆盖率表**（每天覆盖了多少/多少条）、**质量表**（溯源率/准确率/有用率，含标注口径）、**成本表**（每人每天自动任务的 token 与折算金额）；并且评委点开任意一条总结，每条结论都能点到原文。

## 6. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| **两种形状都支持**（object + list 双解析） | 卷十一 §11.4 已裁决："都支持是最贵的方案，因为它把一次性的返工变成了永久的分支。" |
| **给截断做"自动续写"** | 审计报告 §5 已明确：续写会让一条回答变成两次计费，且拼接点语义可能断裂。**只报告，不猜用户意图**——这与 O-P0-1"显式标注覆盖率"是同一条原则。 |
| **总结写回会话 / 打标签 / 改标题** | "总结只读"是幂等的数学前提（`service/daily.py:15`）。一旦有副作用，backfill 重跑就会漂移。 |
| **接入 Redis / 消息队列做推送** | 2G 内存；且推送量级是"每天几条"。 |
| **做 A/B 测试平台** | 3 人团队没有流量支撑统计显著性；离线评测集（O-P0-2）在同等成本下更可解释。 |
| **自动重建/自动重生成总结** | 无人值守的批量重跑会触发未预期计费（同 A4 不选自动重建向量库的理由）。 |
| **邮件渠道（赛前）** | 需要 SMTP 服务 + 域名邮箱 + 反垃圾配置，成本远高于收益；且依赖备案完成。 |
| **为"想象中的未来"加配置项** | 卷十二反模式 10。每个新增配置（如推送渠道枚举）都要有**当前已知**的消费方，否则不落地。 |
| **在答辩前重做总结的 UI** | UI 重构的收益（作品呈现）小于风险（把已验证的溯源链路改坏）。先补 `sources`（半天），UI 重构进赛后台账。 |
