## 0. 一句话结论

**A1~A8 修的是"代码里的八个洞"，不是"清单上的十四条"——逐条对表后，§12.3 的隐含前提清单里真正被完全收口的只有 2 条（第 10 条时区、第 14 条 checkpointer），部分收口 3 条，还有 1 条被修复动作反向放大（第 2 条）。** 所以本卷的升级主线只有一件事：**把"未标定边界的决策"从一篇文档里的一张表，变成一份有责任人、有巡检周期、有看数的台账**（建议落 `docs/架构假设.md`），并把 §12.5 的"反转条件"翻译成"谁、多久一次、看什么数"。做完这件事，前十一卷的每一个"我愿意承受这种失败"就从**口头承诺**变成了**可验证的承诺**——这正是答辩时最值钱的东西。

## 3. 升级项

### P0

#### R-P0-1 · 建 `docs/架构假设.md`（十四条逐条收口）

- **现状**：§12.3 的清单只存在于研讨卷的一张表里，没有独立台账文件；§12.3 结尾自己就写了"建议建一个清单文件（比如 `docs/架构假设.md`）"，**至今未落地**。
- **改什么**：新建 `docs/架构假设.md`，把十四条按下面六字段逐条录入（模板见 §5），并把下表的"收口状态 / 兜底 / 巡检项"一并写进去；**每次新增架构级决策，必须先在这里加一行，再改代码**。
- **为什么省赛必须改**：卷十二自己的结论是——这类债"不会在代码评审中暴露，也不会在测试中失败"。一份研讨卷管不住它们，**只有台账能**。而答辩时"请说明你们的架构假设及其失效条件"是一道很可能的追问，有台账 = 有答案。
- **代价/风险**：台账会过时——所以它必须有**巡检项**字段（见 R-P0-2），否则它自己就变成"静默过期文档"的第 4 个例子。
- **反转条件**：若三个月内无人更新台账 → 说明它没进流程，应立即简化为"只在 PR 模板里加一条勾选：`本次改动是否触及架构假设？`"。
- **验收口径**：文件存在且十四条齐全；每条六字段非空；`docs/升级版_2026-10-20/` 三份文档各自能指到它；最近一次架构级改动（如多 worker）在台账里有对应行。

#### R-P0-2 · 反转条件 → 可执行巡检项

- **现状**：§12.5 的触发表给了"触发条件 / 翻案动作 / 预估成本"，但**没有责任人、没有周期、没有数据来源**。例如"单进程内存 > 1.4G 且优化无效"——没人每月去看这个数。
- **改什么**：给最危险的六条各配一条巡检项（谁 / 多久 / 看什么数 / 越线怎么办），写进台账同一张表；能自动化的用 `probe-health.sh` + `/api/metrics`（见 R-P0-3），不能自动化的写进"每月 1 号人工检查清单"。
- **为什么省赛必须改**："反转条件"是本方法论最被推崇的一段（卷十二 §12.6："写清什么情况下该翻案，等于给决策设了保质期"）。**没有巡检项的反转条件等于没有保质期**——它会变成一句漂亮话。而答辩时把"我们每月 1 号看这四个数"讲出来，比讲十条定律更有说服力。
- **代价/风险**：巡检要花时间（估算每月 30 分钟）；风险是设了一堆没人看的指标，所以**只给最危险的六条配**，其余保持文字描述。
- **反转条件**：若连续两个月巡检项全部"无变化" → 把周期从每月放宽到每季度。
- **验收口径**：台账里 ≥6 条有"巡检人 + 周期 + 指标名"；至少 3 条的指标能从 `/api/metrics` 或 `probe-health.sh` 直接取到；模拟一次越线（如把 `RETRIEVE_MIN_SIM` 临时改错），巡检能发现。

#### R-P0-3 · 探针接 `/api/metrics`（第 7 条的收口动作）

- **现状**：第 7 条隐含前提是"metrics 靠 textfile probe，脚本能访问 sqlite"。A5 加了应用指标端点，改变了这条的形态——**但探针没去拉它**，所以现在既没有"脚本访问 sqlite"那条路的数据，也没有新端点的数据。
- **改什么**：与卷十 D-P0-3 是同一动作：在 `probe-health.sh` 里拉 `/api/metrics` 并透传关键项进 textfile；同时把"取不到指标"本身写成一个指标（`agent_hub_metrics_scrape_ok`）。
- **为什么省赛必须改**：这是唯一一条**被 A5 改变了形态却没被收口**的债。它现在的状态是"新机制已建、旧机制未拆、中间没接线"——比改之前更含糊。而埋了点没人采集，正是卷十二缺陷 3 批评的那种"最可惜的缺失"。
- **代价/风险**：探针多一次回环请求；`METRICS_TOKEN` 未配时会拿到 403，必须显式记为 scrape 失败（否则又是静默失败，重蹈 A1 覆辙）。
- **反转条件**：若 2G 内存下 Prometheus 容器导致 OOM → 关容器，改为 cron 直接把 `/api/metrics/json` 落文件 + 人工查看。
- **验收口径**：Prometheus 能查到 `chat_truncated_total`；停掉后端后 `agent_hub_metrics_scrape_ok` 变 0 且告警可见。

### P1

#### R-P1-1 · 补 A1~A8 未覆盖的两条敞口（第 2 条被反向放大）

- **现状**：第 2 条（"同一 `with _get_conn()` 块内没有 `await`"）在 A6 之后**反而更危险**——A6 把 `api/chat.py` 的同步调用包进 `asyncio.to_thread`，意味着会切换线程；而 `_get_conn` 是 `threading.local()` 连接（审计报告 §2-A6 已点出"换线程等于换连接"）。第 11 条（缓存键 `(temperature, max_tokens)` 完备）仍是纯纪律，加 `top_p` 就静默失效。
- **改什么**：① 一条静态检查测试：扫描 `core/session.py::_get_conn` 的所有 `with` 块，断言块内无 `await`（与 A6 那条"扫描 `store.` 同步调用是否包 to_thread"是同一手法）；② 一条断言测试：`get_llm` 的缓存键集合 == 其函数签名里所有影响输出的参数集合（加参数而忘了加键就红）。
- **为什么省赛必须改**：这两条都是卷十二定律 2 的活靶子（"纪律型的债，比机制型的债严重一个量级"）。而且第 2 条是**我们自己的修复动作制造的新风险**——这种"修 A 引出 B"的情况必须显式记账，否则台账不可信。
- **代价/风险**：静态扫描有误报（`await` 可能在嵌套函数里）；所以先做成"告警 + 白名单"，不做硬门禁。
- **反转条件**：若误报率 > 30% → 退回人工 review 清单（在 PR 模板里列一条）。
- **验收口径**：两个测试文件存在且通过；人为在 `_get_conn` 块内加一行 `await asyncio.sleep(0)`，测试变红；人为给 `get_llm` 加一个 `top_p` 参数而不改缓存键，测试变红。

#### R-P1-2 · 决策记录进 `docs/decisions/`（一决策一文件）

- **现状**：自评"80 个决策只有 5 个 ADR"。
- **改什么**：不追求补 80 个，**只补省赛答辩会被问到的 8~10 个**：SQLite 而非 PG、单进程/多 worker、裸机而非 Docker、同源 rewrite、Chroma、不挂 checkpointer、强制溯源、手写 JWT（A7 之后这条的口径要重写）。每个文件六段式：问题域 → 候选面 → 判据 → 证据 → 决策与代价 → 反转条件。
- **为什么省赛必须改**："技术方案 30%"的评分依据是架构论证的**可追溯性**。研讨卷是叙述体，ADR 是可引用的独立文件——答辩 PPT 里一句"详见 D-00x"比"我们有 12 卷研讨"更硬。
- **代价/风险**：补 ADR 有"事后追认"的嫌疑（决策的理由会被现在的理解污染）。所以必须在文件里注明"记录日期晚于决策日期，理由依据当时的代码与注释"。
- **反转条件**：若补到第 5 个发现信息不足（记不清当时的判据）→ 停止补写，改为把研讨卷里已有的段落**链过去**，不再重造。
- **验收口径**：`docs/decisions/` 存在 ≥8 个文件；每个文件含六段且"反转条件"非空；本卷与卷十、卷十一的升级项能互相引用。

#### R-P1-3 · 过时注释扫描（反模式 5 的机制化）

- **现状**：已发现 3 处过时注释；反模式 5 写的是"注释承诺了代码没做的事"，正确做法是"凡注释说做了某事，就要有一条测试验证"——但**没有扫描机制**。
- **改什么**：加一条低成本的正则扫描（脚本式自测，不进 pytest 主流程）：搜 `"""..."""` 里出现"必须 / 只在 / 不会 / 从不"这类**强断言词**的注释，输出一份清单供人工确认；并把已知 3 处先修掉。
- **为什么省赛必须改**：过时注释在答辩时是**当场被打脸**的风险（评委照着代码问）。而且这是卷十二 §12.7 缺陷 5 唯一能低成本机制化的一条。
- **代价/风险**：正则会误报（很多注释是合理的强断言）；所以输出是"待确认清单"不是"失败项"。
- **反转条件**：若清单 > 100 条且无人维护 → 改为只扫 `core/` 与 `service/` 两个目录。
- **验收口径**：脚本可跑并输出清单；已知 3 处过时注释被修；清单里每条有"确认人 + 确认日期"栏位。

#### R-P1-4 · 半成品种类清理

- **现状**：主题标签（每次入库调一次 LLM，`$contains` 过滤无实际使用）、蒸馏检索（只有契约）、打卡后端（前端"接口待上线"）、混合引擎切换规则（初始为空）。
- **改什么**：逐个做二选一——**接上消费方**或**关掉**。最低成本是加开关：`TOPIC_TAGS_ENABLED=0` 直接省掉每次入库的 LLM 调用（这是唯一一个"半成品还在持续烧钱"的）。
- **为什么省赛必须改**：卷十二 §12.7 缺陷 2 的原话——"半成品的成本不是没做完，是每个读代码的人都要花时间确认它做没做完"。评委翻代码时看到一堆空字典，是"代码质量"的直接扣分项。
- **代价/风险**：关掉主题标签会损失画像的一部分输入（`profile.aggregate` 读 `user_tags`）。所以要先确认画像是否依赖它——（待核对：`store.get_user_tags` 的写入方是否唯一）。
- **反转条件**：若主题标签确实是画像的唯一输入 → 不关，改为"降低调用频次"（批量而非每条）。
- **验收口径**：每个半成品在台账里有"接上 / 关掉 / 保留并标注"三选一的结论与日期；`TOPIC_TAGS_ENABLED=0` 时入库路径零 LLM 调用（有测试锁住）。

### P2

#### R-P2-1 · schema 版本号 / migration

- **现状**：无版本号，建表靠 `CREATE TABLE IF NOT EXISTS`（`service/daily.py:71-111` 是典型）。
- **改什么**：加一张 `schema_meta(version, applied_at)` 表 + 顺序执行的迁移脚本目录。
- **为什么赛后再说**：12 张表的迁移历史要补齐，约 1 周；省赛前投入产出比低，且当前"幂等建表"在单机单库下工作正常。**反转条件：出现第一次需要改列的操作**（如卷十一 O-P0-1 要加列）时立即上。
- **验收口径**：新机器从零初始化与从 v1 迁移到 v2 得到相同 schema。

#### R-P2-2 · 端到端与覆盖率进 CI

- **现状**：`tools/audit_e2e.py` 存在但要起服务，CI 不跑；`tests/test_w1/w2/w3.py` 需真实 API。
- **改什么**：CI 加一个"起服务 + 跑 `audit_e2e.py` 的 health 子集"的 job（不打真实 LLM，用假 provider 或 mock 环境变量）。
- **为什么赛后再说**：CI 环境无 `.env` 是既定约束；且 18/18 的端到端已在本地验证过。**反转条件：出现第二次"单测全绿但接线断了"的事故**。
- **验收口径**：CI 里端到端 job 绿，且断言"跑了多少项"。

#### R-P2-3 · 十条定律进新人 onboarding

- **现状**：十条定律只在研讨卷里。
- **改什么**：提炼成 `规范/` 下的一页清单（尤其前三条：默认值落安全侧 / 机制替代纪律 / 静默失败最贵）。
- **为什么赛后再说**：团队只有 3 人且已进入评审期，onboarding 的收益要等新人进来才兑现。
- **验收口径**：新成员能在不看研讨卷的情况下说出前三条。

## 4. 竞品对照

| 竞品 | 在"反思与演进"这一层怎么做 | 我们差在哪 | 要不要跟 |
|---|---|---|---|
| **Dify**（142k⭐） | 自带 **LLMOps 监控与 A/B 测试**——本质是把"效果类参数"的标定做成了产品功能；142k⭐ 的社区意味着大量第三方评测 | 我们没有 A/B 平台，且**没有流量做 A/B**；刚有第一份离线评测集（检索侧） | **跟方法，不跟平台**：离线评测集 + 参数标定记录（审计 §6.4 的建议 1、2）是廉价版；A/B 平台不跟 |
| **FastGPT**（26.1k⭐） | 商业版卖点含**运行日志看板**——把"跑没跑过、失败算谁的"产品化 | 我们的运行日志在 `job_runs`（`core/scheduler.py:137-157`）且结构更细（有 `trigger` 区分手动/定时），但**没有看板** | **跟**：加一个只读页面即可，成本极低；这同时也是卷十一 O-P0-3 的载体 |
| **RAGFlow**（80.7k⭐） | 强调**引用溯源与可解释**，并有公开的检索评测（对中文场景做过针对性调优） | 我们的溯源在数据层更严格（指不回就丢弃），但**没有公开的评测数字**；且审计 §6 揭示阈值是"未标定的跨模型参数" | **跟**：这是最值得补的一项——`tools/eval_retrieval.py` 已有骨架，补一次真模型跑分并写进文档，就能把"可解释"从定性变成定量 |
| **Coze 扣子** | 闭源，内部是否有技术债台账不可知；对使用者而言"演进"不由你决定 | 我们的优势恰恰是**决策过程可展示**——这是"技术方案 30%"能拿分的地方 | **不跟**：但要把这个优势**变成物证**（ADR + 台账 + 评测数字），否则"我们做过严谨取舍"只是自述 |
| **n8n**（188k⭐） | fair-code 许可证**禁止作为 SaaS 对外售卖**——这是一条"由外部约束决定的架构边界"，且被明确写进许可证 | 我们的隐含前提里没有一条有这么强的外部约束力；最接近的是"第 9 条 WAL 依赖本地文件系统" | **跟写法**：学习它把"边界条件"写成**不可绕过**的形式（许可证 / 脚本守卫），而不是文档提醒——这正是 R-P0-1/R-P0-2 想达到的效果 |

**共同的差距一句话**：这些项目在"反思与演进"上的共同点是——**它们把边界条件做成了产品的一部分**（监控看板、评测、许可证条款），所以边界被触碰时**有人/有系统立刻知道**。我们的边界条件全在人的脑子里和研讨卷的表格里，被触碰时**只有代码知道**。R-P0-1~R-P0-3 要补的就是这个"有人立刻知道"。

## 6. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| **把十四条全部机制化** | 审计报告 §5 已明确："需要改部署形态（单进程依赖）与 Cookie 策略，超出修复范围，属演进议题。"台账 + 巡检是**在机制化之前**的最优解——先把"不知道"变成"知道"，再谈改。 |
| **迁 Redis / 引入分布式锁** | 卷十二 §12.8：Redis 是又一份常驻内存 + 一类新的失败模式。当前规模下"约 N+ε"的双层限流足够，且有开关可平滑升级。 |
| **上 A/B 测试平台** | 3 人团队、目标用户个位数，没有统计显著性可言。离线评测集在同等成本下更可解释。 |
| **补写 80 个 ADR** | 有"事后追认"的污染风险，且边际收益递减。只补答辩会被问到的 8~10 个（R-P1-2）。 |
| **为所有参数做标定** | 7 个检索参数的标定需要标注语料与真模型跑分，成本高。优先做 2 个阈值（审计 §6.4 建议），其余保持"经验值 + 明确标注未验证"。 |
| **给文档加自动同步检查** | 文档与代码的对应关系无法用正则可靠判定。**保留"过时注释扫描"（R-P1-3）这种低成本近似即可**，不做通用方案。 |
| **删掉研讨卷只留台账** | 研讨卷的价值是**论证过程**，台账的价值是**当前状态**。两者互补——台账没有过程，研讨卷没有状态。 |
| **在省赛前做大规模重构** | 卷十二 §12.4 列的"会改但成本高的 3 项"（migration / 应用埋点 / to_thread 工具化）里，应用埋点已由 A5 完成；剩下两项都不影响评分，且风险高于收益。记进台账，赛后按反转条件触发。 |
| **假装"十二条"与"十四条"的口径差异不存在** | §12.3 表格实际 14 行，团队口头常说十二条。**差异已在 §1 标注为待核对**，本卷按 14 行逐条收口——不为了对齐口径而合并或删行，那会丢掉真实条目。 |
