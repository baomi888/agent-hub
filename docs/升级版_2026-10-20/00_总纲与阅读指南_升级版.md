> 本卷回答的问题：从校赛到省赛，这一层要改什么、为什么现在必须改、改完怎么验。

## 0. 一句话结论

把文档体系从「**我们做了什么**」改成「**评审自己能验到什么**」：用一份四级证据链（研讨卷 → 升级版 → 落地报告 → 可执行验证）把 80 多条决策逐条挂到可复现的锚点上，并在答辩前把**公网入口、10 分钟演示视频、源码素材包、三人分工举证**四件物理物补齐。技术方案的 30 分不靠多写，靠**每条结论都能被人在五分钟内自己跑出来**。

## 3. 升级项

### P0

#### P0-1 · 建立四级证据链，并给每条决策一个"可执行验证"

- **现状**：研讨卷列了 80+ 条决策，但每条的"证据"是源码注释或事故描述，评审无法自己跑。
- **改什么**：新建一张**决策证据总表**（建议 `docs/升级版_2026-10-20/附录A_决策证据总表.md`），列为：`决策编号 | 一句话结论 | 研讨卷锚点 | 落地报告锚点 | 验证命令 | 期望结果`。验证命令必须是可复制的单行，例如 `python tests/test_slash_no_redirect.py`、`curl -s http://127.0.0.1:8000/health`。
- **为什么省赛必须改**：技术方案 30% 的评分对象是"方案是否成立"，而"成立"在评审席上等价于"能被独立复现"。源码注释是 A 级素材但**不是可执行证据**（`00_总纲:216` 自己标了 A 级"可能随版本漂移"）。只有 D 级（回归测试断言，`00_总纲:217`）是"改动即红"的。把 A/B/C 级决策尽量补一条 D 级锚，是把 30 分从主观拉到客观的唯一杠杆。
- **代价/风险**：80+ 条逐条补测试不现实。真实工作量是**挑 20~25 条核心决策**补锚，其余标注"仅契约，无测试锚"。风险是把文档工作误做成测试开发，挤掉功能时间。
- **反转条件**：如果省赛提交只要求文档 PDF 而不看仓库（**待核对赛事提交细则**），这张表的收益大幅下降，应降级为 P1，把时间让给演示视频。
- **验收口径**：总表里 ≥ 20 行带非空"验证命令"；随机抽 3 行在**干净目录**下执行，2 分钟内出结果且结果与该行"期望结果"一致。

#### P0-2 · 公网可访问入口（域名 HTTPS 或稳定 IP + 免登录演示路径）

- **现状**：`8.163.62.25:3000`，http，裸 IP；域名备案卡在"待提交管局"（域名注册未满 2 天）；`https/setup-https.sh` 已备好但无法执行。
- **改什么**：两条并行——① 跟备案流程，拿到域名后一条命令上 HTTPS；② 同时准备**Plan B**：Cloudflare 隧道（无需备案、不开 443、不动安全组），保证评审当天有一个 https 链接可用。两条线路的完整对比已在 `docs/运维强化落地报告_2026-10-20.md:37-44`。
- **为什么省赛必须改**："已投入实用或具有推广价值"这一条，评审的验证动作就是**打开链接**。裸 IP + http 会在浏览器地址栏显示"不安全"，且无 ICP 备案的境内站点存在合规风险。这不是加分项，是**这一栏能不能得分的前提**。
- **代价/风险**：Cloudflare 隧道绕海外节点，国内访问偏慢，且临时域名会变；备案走完需 1~2 周且要过工信部短信核验与公安联网备案（`运维强化落地报告:44`）。风险是**等到备案却没等来**，所以必须两条一起走。
- **反转条件**：若赛事明确要求"作品部署在境内可备案域名"（待核对），Plan B 只能作为临时演示，不能作为正式提交入口。
- **验收口径**：给评审的链接满足三条——① 浏览器地址栏无"不安全"字样；② 从**校外网络**（手机 4G）能打开并完成一次完整问答；③ 冷启动后 30 秒内首字出现。

#### P0-3 · 10 分钟演示视频：脚本化，不即兴

- **现状**：无演示脚本。可用的叙事骨架是 `01_方法论与约束场.md:138-207` 的 17 个接触点调用链。
- **改什么**：写一份**分镜脚本**（建议 `docs/升级版_2026-10-20/附录B_演示分镜.md`），按秒分配：0:00-0:45 一句话定位与公网链接；0:45-2:30 一次带知识库的 RAG 问答（展示引用角标可点开原文）；2:30-4:30 一次 Agent 五工具循环（展示工具轨迹）；4:30-6:00 每日委托 + 每日总结（展示无人值守链路）；6:00-7:30 管理侧（用量/指标/提示词自进化）；7:30-9:00 一段"故意注入"的失败演示（展示越权被 404、截断被提示）；9:00-10:00 技术栈与约束收尾。
- **为什么省赛必须改**：作品呈现 20% 里"答辩"是现场分，视频是**答辩的替身**。即兴录制的通病是中途翻车、重录耗时、且漏掉最能体现工程深度的部分。最后那 1:30 的"失败演示"是差异化点——绝大多数参赛作品只演成功路径。
- **代价/风险**：录制与剪辑要占一人约半天。风险是脚本写得太满导致超时，所以每段要标"可剪"标记。
- **反转条件**：若赛事要求现场答辩且不接受预录视频（待核对），脚本降级为**答辩排练稿**，但内容和顺序仍然有效。
- **验收口径**：成片时长 9:30~10:30，无剪辑跳帧；脚本里每一条"要给评审看到的画面"在成片里都能定位到秒；全程无口误重录超过 3 次。

#### P0-4 · 源码素材包与原创性举证

- **现状**：`pack.sh` 存在（内容待核对）；分工痕迹散落在 `docs/前后端对接报告_2026-10-15_刘佳林.md`、`core/config.py:171` 附近的裁决注释、`规范/决策记录.md:187`（`/api`→`/api/v1` 的合分支窗口）。
- **改什么**：三份材料——① **源码素材包**：`pack.sh` 产出的 zip，含目录树、第三方依赖清单（`requirements.txt` + `frontend/package.json`）、开源许可核对表；② **提交记录举证**：`git log --oneline` 按人/按模块统计（**待核对**：本环境无法执行 git，需在运行 git 的机器上补）；③ **三人分工表**：模块 → 主责人 → 贡献证据（PR/提交/文档）。
- **为什么省赛必须改**：原创性是人工智能应用类的硬性审查项。三人并行开发一个仓库，最容易出现的质疑是"是不是一个人写的"或"是不是拼的开源项目"。可举证的对抗手段不是声明，是**按人、按模块、按时间的可交叉验证记录**。
- **代价/风险**：提交记录统计需要 `git` 可用且历史完整。风险是历史里有大量"小改动"提交，统计出来不好看——处理方式是把统计口径定为"按模块聚合的文件变更行数"，而不是提交次数。
- **反转条件**：若赛事只收作品不收过程材料（待核对），② ③ 降级为附件，① 必须保留。
- **验收口径**：素材包解压后能在**另一台机器**上按 README 跑通 `bash deploy.sh`（至少走到 `.env` 检查那一步，见 `deploy.sh:219-259`）；分工表每一行都能在提交记录里找到对应时间段。

#### P0-5 · 把"测试数据充分"做成一张汇总表

- **现状**：数据分散——`docs/并发承载测试报告_2026-10-20.md`（200 并发 RPS/p99）、`tests/` 66 个文件、`docs/RAG与AI核心重构_回归测试报告_2026-10-16.md`。
- **改什么**：建一张**系统测试数据表**（建议 `docs/升级版_2026-10-20/附录C_系统测试数据汇总.md`），列为：`测试项 | 方法/工具 | 样本规模 | 通过口径 | 实测值 | 数据出处 | 可复现命令`。至少覆盖：并发承载（已有）、鉴权吞吐（已有）、SSE 断连（有 `tests/test_sse_disconnect.py`）、截断检测（有 `tests/test_truncation_detect.py`）、配额共享限流（有 `tests/test_rate_limit_shared.py`）、知识库隔离（有 `tests/test_kb_isolation.py`）、归属隔离（有 `tests/test_owner_isolation.py`）。
- **为什么省赛必须改**：功能效果 20% 的明文要求是"系统测试数据充分"。**有测试 ≠ 数据充分**，差的是"样本规模 + 通过口径 + 实测值 + 出处"这四列。评审不会去读 66 个测试文件，会看这张表。
- **代价/风险**：需要把已有测试跑一遍并记真实数字，不能用文档的旧数字。**标注"复测日期"**是关键，否则又是"可能漂移的 A 级素材"。
- **反转条件**：若某个测试在赛前跑挂了，**不要删行**，改成"未通过 + 原因 + 计划"，诚实标注比缺行安全。
- **验收口径**：≥ 7 个测试项，每项 7 列全非空；抽 2 项现场重跑，数值与表内一致或偏差 < 10%（并发类指标允许偏差 20%）。

### P1

#### P1-1 · 文档集统一编号与命名规范

- **现状**：`docs/` 下命名风格混杂，含 `剩余模块屎山治理与重构报告_2026-10-16.md`、`P0三条优化方案.md`（无日期）、`docs/技术选型研讨_2026-10-20/`（有日期目录）。
- **改什么**：定义一套规则 `YYYY-MM-DD_<类别>_<主题>.md`，并对**提交给评审的文档子集**统一重命名（不改动仓库内历史文件，只做一份"提交视图"目录）。
- **为什么**：作品呈现 20% 含"文档规范"。文件名是评审看到的第一层结构。
- **代价/风险**：改名会让已有文档里的交叉引用失效。所以只在**提交视图**里改名并附一份映射表，不动源文件。
- **反转条件**：若赛事要求提交完整仓库（待核对），改名的成本骤增，改为只补一份《文档导读》。
- **验收口径**：提交视图内 100% 文件名符合规则；映射表覆盖所有被改名文件。

#### P1-2 · 答辩叙事主线重写：从"技术栈清单"到"三条约束下的取舍"

- **现状**：研讨卷主线是"选最不容易在无人值守时静默出错的那一个"（`00_总纲:227`）。
- **改什么**：把主线压缩成答辩版的**三段式**：① 约束（2 核 2G / 零运维 / 三人并行 / 备案未下）；② 在约束下做出的三个非主流选择（SQLite 而非 PG、独立 worker 而非 Celery、服务端注入 kb_id 而非提示词劝导）；③ 每个选择对应的**可演示证据**（压测表 / 心跳三态 / 注入失败演示）。
- **为什么**：主题创意 30% + 技术方案 30% 都吃"为什么这么做"。讲"我们用了 FastAPI+Chroma+DeepSeek"是零分叙事；讲"在 2G 内存上为什么不能上 PostgreSQL，我们算了什么"是高分叙事。
- **代价/风险**：三段式讲稿需要三个人口径一致，否则答辩时三人说法不同是致命的。
- **反转条件**：若评委更关注功能演示而非技术论证（现场观察再定），保留三段式但把 ② 压到 90 秒。
- **验收口径**：三人各讲一遍， mutually 一致率 ≥ 90%；每段有对应的演示片段可衔接。

#### P1-3 · 代码质量证据补齐

- **现状**：CI 存在（`.github/workflows/ci.yml`），研讨卷记录了 CI 拆 pytest / 脚本式两个 step 的判据（`01_方法论:322-329`）；但 lint 报告、类型检查报告、覆盖率报告未见（**待核对**）。
- **改什么**：在 CI 里产出并归档三份报告（lint / 类型 / 测试计数），并在提交视图里附一份《代码质量说明》引用它们。
- **为什么**："代码质量"是作品呈现 20% 的明文组成。
- **代价/风险**：上 lint 会引出一堆历史告警，需要配置"只对新代码严格"。风险是引入告警后 CI 变红，反而难看。
- **反转条件**：若引入 lint 导致 CI 红且赛前修不完，**直接撤掉 lint step**，保留测试计数即可——红 CI 比没有 lint 报告更伤。
- **验收口径**：CI 绿；三份报告可在 CI 产物里下载；《代码质量说明》里的数字与产物一致。

### P2

#### P2-1 · 竞品对照表（对外版）

- **现状**：本系列四份升级版各有一节竞品对照，但没有一份对外的汇总表。
- **改什么**：做一张一页纸的《与主流平台的差异定位表》，只列评审会问的三列：能力覆盖 / 部署门槛 / 我们的取舍理由。
- **为什么**：推广价值这一栏，评审一定会问"和 Dify 有什么区别"。**主动给出**比被问到再答强。
- **代价/风险**：对照表容易被理解成贬低竞品，措辞必须中性（只写事实与门槛）。
- **反转条件**：若赛事不鼓励横向对比（待核对），降级为内部材料。
- **验收口径**：每个竞品一行，三列全非空，无主观形容词。

#### P2-2 · 用户反馈与使用痕迹归档

- **现状**：有 `docs/问卷调查_大学生智能体平台_2026-10-10.md`、`docs/场景示例素材_2026-10-11.md`。
- **改什么**：把问卷结果 + 真实使用痕迹（会话数、知识库数、委托投递次数）做成一页《实用情况》。
- **为什么**：直接支撑"已投入实用"。
- **代价/风险**：真实使用量可能很少，如实写小数字比编大数字安全。
- **反转条件**：若真实用户 < 10 人，改为写"推广路径与已验证场景"，不写"用户量"。
- **验收口径**：所有数字可在 `data/sessions.db` 里用 SQL 复算。

## 6. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| **不为了凑字数扩写研讨卷** | 12 卷已约 10 万字，远超评审阅读量。继续扩写会降低被读到的比例，且违反研讨卷自己定的"承诺决策密度，不是字数密度"（`00_总纲:193`）。升级版的价值在**索引与可执行化**，不在增量文字。 |
| **不伪造或美化测试数据** | 研讨卷明确"不做断言：线上真实 QPS、真实用户量"（`00_总纲:219`）。省赛评审会追问数字出处，编造一旦被拆穿是整体可信度崩塌，损失远大于一个不好看的数字。真实的小数字配清晰的口径，胜过漂亮但无出处的大数字。 |
| **不做商业版功能对标（多租户 SaaS / SSO / 计费）** | FastGPT 商业版含多租户/SSO/日志看板 10000 元/月起，Dify 协议禁止基于它做多租户 SaaS，这两条都说明"多租户商业化"是商业产品的赛道，不是学生作品的评分点。做不完且会被质疑"抄商业版的定位"。 |
| **不在赛前更换技术栈（不上 PG / Redis / 容器化）** | 研讨卷已经论证过这是 2 核 2G 下的跑不起来的解（`01_方法论:16-21`）。赛前换栈的唯一结果是引入未经验证的失败模式，与"失败必须响"这条主线直接冲突。 |
| **不做"一键部署到任意云"的通用化改造** | 推广价值的证明靠一个能打开的链接 + 一份 `deploy.sh`，不靠抽象出云平台无关层。后者是无底洞，且当前 `deploy.sh` 已经自动补齐 Node/Python/swap（见 `deploy.sh:106-213`），足够支撑"别人能装上"这个论点。 |
| **不做前端视觉重做** | 已有 `docs/前端视觉审查报告.md` 与 `docs/前端重构说明.md`，说明这一层已被评审过一轮。视觉不是本轮评分的关键变量，重做的机会成本高于收益。 |
| **不删掉研讨卷里的口语化/自嘲内容** | 那些内容（"屎山治理"、注释里的输入法误触 `āk`，见 `core/auth.py:67`）恰恰是**原创性与真实开发过程的证据**。为了"文档规范"把它们洗掉，等于自毁举证材料。规范化的动作只做在**提交视图的命名层**，不动源文件。 |
