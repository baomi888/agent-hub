## 0. 一句话结论

> **这一层现在是"机制很厚、刻度没标"。**
> 四段流水线、混合检索 RRF、MMR 去重、三层缓存、四档置信分级全都落地并有负向回归；但决定用户观感的两个数 `RETRIEVE_MIN_SIM=0.25` / `RETRIEVE_LOW_SIM=0.45` 是**未标定的跨模型经验常量**。
> 2026-10-20 用 `tools/eval_retrieval.py` 跑的实测已经把症状暴露得很清楚：**剔除字面盲区题后 recall@1=1.0、MRR=1.0，但相关题 100% 被判 weak**——也就是"明明找到了答案，却告诉用户没找到依据"。
> **省赛第一件事就是用真 embedding 模型重标定这两个阈值，并把评估做成回归门禁。** 其余（重排、溯源定位、复杂文档、切片）排在其后。

## 3. 升级项

### P0-1　阈值标定（本卷最该做的一件事）

- **现状**：`RETRIEVE_MIN_SIM=0.25`（丢不丢）与 `RETRIEVE_LOW_SIM=0.45`（够不够格）来自一段经验注释（`core/config.py:119-122`）：原文提问 ≈0.6+，换说法 ≈0.5，沾边 ≈0.3。这是**在某个具体 embedding 模型上的观测**，但代码里没有任何东西把这个绑定关系表达出来。

  **已实测的症状（2026-10-20，`tools/eval_retrieval.py` 走确定性假向量）**：

  | 指标 | 数值 | 说明 |
  |---|---|---|
  | recall@1 / MRR（剔除字面盲区题后） | 1.0 / 1.0 | 管道本身没问题，该召回了都召回了 |
  | 相关题被判 weak 的比例 | **1.0** | **14 题里 12 道相关题，一道都没判成 high** |
  | 含义 | "找到了正确答案，却对模型说这不算依据" | 直接表现为"知识库里好像没有相关资料" |

  必须说清一条：**这个 1.0 不能直接当成"生产就是 100% 误判"**。假向量是字面的、范数被稀疏化过的（`tools/eval_retrieval.py:160-167` 明说这是"为了让管道口径可测而对基线做的补偿"），它的相似度整体偏低。它证明的是两件事：① 管道逻辑正确；② **阈值对相似度尺度的漂移毫无抵抗力**——换一个分布整体下移的模型，整套"示弱闸门"就会轧isto过头。真模型下到底是多少，现在**没有数**。

- **改什么**（四步，全部可复跑）：
  1. **跑真值**。在有 `EMBEDDING_API_KEY` + `EMBEDDING_BASE_URL` 的机器上直接 `python tools/eval_retrieval.py --json tools/eval_baseline/real_<date>.json`（脚本 `:436` 会自动改用真向量，一支 `--fake` 都不用加）。这一步零改代码。
  2. **读分布，不看单点**。从 JSON 的 `summary` 里取 `rel_sim_mean` / `off_sim_mean` / `auc_fair` / `strength` / `relevant_weak_rate`；同时和线上直方图对照（`core/metrics.py:235-239` 的 `retrieval_top1_similarity`，产出点 `kb/rag_core.py:356`）。**两套数必须先看一致与否**：若线上分布与语料分布差很远，说明语料不代表真实使用，要先补语料而不是先改阈值。
  3. **按两条规则重定阈值**：
     - `LOW_SIM`：落在"相关题 top1 的下 10 分位"与"离题题 top1 的上 5 分位"之间，并满足 **离题示弱率 ≥ 0.9 且 相关题示弱率 ≤ 0.1**；
     - `MIN_SIM`：它是**丢弃线**，必须严格低于 `LOW_SIM`，且不低于"相关题最低 top1 − 0.05"（因为 `select_diverse` 在砍空时会强留一条，`kb/rag_core.py:462-465`）。
  4. **把绑定关系写出来**。新增 `RETRIEVE_SIM_PROFILE`，键 = `core/embed_guard.py:79` 的 `fingerprint()`（`model + base + dim`），值 = 标定出的那两个数 + 标定日期 + 评估集版本。启动时比对当前指纹：不匹配就 `metrics.inc("retrieval_thresh_uncalibrated")` + 日志警告（**不抛异常**——空间正确性由 `embed_guard` 负责，这里只负责尺度正确性）。

- **为什么省赛必须改**：
  - 这是唯一一项"改完立刻能把产品体验从错变对"的工作：现在的错误方向是**自贬**（拿到了资料还说不靠谱），而问卷里排第一的担忧是"答不准还装自信"——我们为了对冲它，把系统做成了另一个方向的错。省赛的功能效果 20% 里，这是能被评委现场问穿的点。
  - 评分要求"系统测试数据充分"。**阈值标定报告**（语料 + 分布 + 三个+"改前改后"的对照）就是最直接的一份测试数据，且比任何跑分截图都有说服力。

- **代价/风险**：
  - 真模型跑一次要花钱、依赖网络，不能在 CI 里常态化 → 所以拆成"离线假向量保管道 + 定期真值巡检"（见 P0-2）；
  - **AUC 才是跨模型可比的判据**（`tools/eval_retrieval.py:300-314` 已论证），绝对均值差不能用——这一点必须写进报告，否则下次换模型会被误读成"检索变坏了"；
  - 阈值向"少示弱"调会增加幻觉风险 → 必须**同步保留 medium 仍示弱**这一档：现有 `MARGINAL_CONFIDENCE_NOTE`（`kb/rag_core.py:385`）正是 medium 专用模板，它的存在可以避免把闸门一步开到"从不示弱"；
  - 阈值变化会影响 `_source_meta` 给前端的强弱标签（`kb/rag_core.py:1345-1358`），两处必须同源——已经是同源（都读 config），改完跑 `tests/test_grounding.py`。

- **反转条件**：若真模型下 `auc_fair < 0.8`（相关题与离题题的 top1 相似度本身分不开），说明**光调阈值治不好**，必须上 P1-1 的重排，阈值先维持现状并降级为"只决定丢弃线"。

- **验收口径**（写进 `tools/eval_retrieval.py` 的 checks，替换现有三条）：
  | 门槛 | 现值 | 目标 |
  |---|---|---|
  | 离题示弱率 | ≥ 0.5 | **= 1.0**（这 4 道题与语料完全无关，判不出 weak 就是 bug） |
  | 公平口径 recall@3 | ≥ 0.75 | **≥ 0.9** |
  | AUC（公平口径） | ≥ 0.9 | 维持 ≥ 0.9（这是跨模型可比的判据，不放松） |
  | **相关题被判 weak 的比例** | 无 | **≤ 0.10（新增，核心指标）** |
  | 门槛是否绑定指纹 | 无 | 指纹不匹配时 `retrieval_thresh_uncalibrated` 有计数 |

### P0-2　评估集常态化：从"一个脚本"变成"一道门禁"

- **现状**：脚本本身很完整（文档字符串写清了动机、临时目录隔离、teardown 清理，`tools/eval_retrieval.py:1-44,59-63,477-478`），但**没有任何自动化调用它**：CI 的脚本式自测清单只有 6 个文件（`.github/workflows/ci.yml:106`），`pytest.ini` 也没把它收进去。
- **改什么**：
  1. **双轨门禁**（关键设计）：
     - **离线轨（每次 PR）**：`python tools/eval_retrieval.py --fake`——**必须显式加 `--fake`**。因为 CI 环境变量里塞了假的 `EMBEDDING_API_KEY` 与 `EMBEDDING_BASE_URL=https://example.invalid/v1`（`ci.yml:80-82`），不加 `--fake` 时脚本会判定"有 Key"并真的去联网（`:232-236`），CI 必红且症状误导。这一轨的作用是"管道没坏"。
     - **真值轨（每周 / 每次交付前人工跑）**：真模型 + `--json`，结果存 `tools/eval_baseline/real_<date>.json`，与上一版 diff。这一轨的作用是"尺度没漂"。
  2. 基线文件入库，`tools/eval_compare.py` 比对三件事：recall/MRR 下降幅度、AUC 下降幅度、`relevant_weak_rate` 上升幅度，任一超过 5pp 就 FAIL。
  3. 顺手修掉口径漂移：`core/metrics.py:230` 的 HELP 改成 `level=high/medium/low`。
  4. 评估集扩到 ≥ 30 题：保留现有 12 道同类题，新增三类——**硬负样本**（同域但答非所问，如问"续期失败怎么办"而文档只讲"到期前会自动续期"）、**术语撞脸**（用相似但不同的专有名词）、**多跳题**（答案需要跨两个文件）。离题题从 4 道扩到 8 道。
- **为什么省赛必须改**：`tools/eval_retrieval.py:1-8` 自己的文档字符串已经写了这个理由——前面三层测试的能回答的只是"有没有接上"，没有一层回答"好不好"。省赛的功能效果一项要求"系统测试数据充分"，一个**只在你电脑手工跑过**的评估脚本，答辩时讲不圆。
- **代价/风险**：假向量轨跑一次要建库（3 篇文档、300 字切片），几秒级，可接受；引入 `--fake` 若被后人遗忘改回自动，会让"真值轨"永远不被跑 → 在 `tools/eval_compare.py` 里检查最新基线文件的年龄，超过 14 天直接报 WARN。
- **反转条件**：若 CI 时常因为网络/依赖抖动红 → 把离线轨挪到 nightly，PR 只做 diff 报警。
- **验收口径**：故意把 `RETRIEVE_MMR_LAMBDA` 改成 1（破坏去重）或把 `RETRIEVE_MIN_SIM` 改成 0.9（疯狂丢弃），CI 的 eval 步骤必须变红；改回后绿。这是负向验证，和研讨卷 §5.4 的"改坏实现、确认变红、改回来"是同一个手法。

### P0-3　引用溯源定位到原文

- **现状**：`build_sources`（`kb/rag_core.py:1370-1390`）输出的每条引用是 `{id, source, page, score, strength, preview, text}`；前端有引用卡片。缺的是**命中位置**——用户点开只看到一段 1500 字上限的正文，不知道哪一句支撑了答案。
- **改什么**：
  1. 切片时把字符区间写进 metadata：`split_documents`（`kb/rag_core.py:807`）改为保留 `RecursiveCharacterTextSplitter` 之外的 offset 计算，或在 `_ensure_vs/add_chunks` 阶段补 `char_start` / `char_end`；
  2. `build_sources` 输出增加 `locator`（`char_start/char_end` 或行区间）；老库片段没有该字段时置 `None` 并走退化路径；
  3. 前端引用点击 → 原文面板定位并高亮；panel 数据已有来源 `get_source_chunks`（`kb/rag_core.py:1153`）可拼回原文。
- **为什么省赛必须改**：引用可验证 = "答案可信"，这是作品呈现 20% 里最能直观加分的交互；RAGFlow 靠这一招出圈（见 §4）。
- **代价/风险**：老库片段没 offset → 必须允许 `locator=None` 并退化成"整段展示"，不能报错；改切片不影响向量（指纹是 `{model, base, dim}`，`core/embed_guard.py:79-87`），**因此不需要重建索引**，这点很关键。
- **反转条件**：前端排期不够 → 后端先把 `locator` 字段给出、前端下个迭代消费。
- **验收口径**：任一条引用点击后，原文面板滚动到该片段首字并高亮；老库引用不报错，退化路径可见。

### P1-1　重排（第二意见）

- **现状**：两通道 RRF 融合后直接进 MMR（`kb/rag_core.py:1317-1325`），`select_diverse` 的 `relevance()` 优先级是"融合 rank > 绝对余弦"（`:476-490`）。没有任何精排。
- **改什么**（按成本递增，建议只做前两档）：
  1. **零成本先把可扩展性做对**：把 RRF 的两路权重做成可配置（现在写死 `1/(k+rank)` 等权，`kb/rag_core.py:270-301`），使硬负样本场景（术语撞脸）能调；
  2. **低成本第二档：LLM / 小模型 as reranker，只覆盖候选池的前 12 条**，走现有的后台并发闸（（`core/llm_gate.py:191` 的 `try_ticket` 正是给这种 fire-and-forget 的活准备的：抢不到就跳过）；
  3. **cross-encoder**：2 核 2G 上本地 `bge-reranker-base` 大约要几百 MB 常驻，**判为风险项**（实际占用待核对）；更现实的路线是走云端 rerank 服务（阿里百炼是否提供兼容 rerank 端点：**待核对**）。
- **为什么省赛必须改**：P0-1 的反转条件说的就是它——当分布本身不可分时，重排是唯一能拉开相关题与硬负样本的手段。而且它是"技术方案"分里的经典加分项，讲得出 RRF→精排的两阶段理由。
- **代价/风险**：延迟 +100~500ms；引入一个新的判定 oracle 会让阈值二次漂移（标定要重做）；务必关 default off，用开关逐步放量。
- **反转条件**：P0-1 的 AUC ≥0.9 且示弱率达标时，重排**不作为必需项**，降级为 P1 增强。
- **验收口径**：在扩到 30 题的评估集上，`recall@3` 与 `auc_fair` 至少一项提升 ≥5pp，且 P95 检索延迟不超过现有 + 30%。

### P1-2　复杂文档解析

- **现状**：只支持 txt/md/pdf（`kb/rag_core.py:32`）。docx/xlsx/pptx 直接拒；PDF 走 `PyPDFLoader`（`:788`），表格会被撕成跨行文本；扫描件给出需要 OCR 的提示（`:790-797`）。
- **改什么**：
  1. **先做性价比最高的**：加 docx（`python-docx`），与 TextLoader 一样提取纯文本 + 段落结构；
  2. **表格行保持**：把表格行作为不可分割单元（在切片的 separator 表之前先做一次行级合并），避免"第 3 列的值跑到另一个片段"；
  3. 扫描件 OCR：**判为 P2**，2 核 2G 上跑 OCR 会把前台挤爆，且我们已有清晰的降级提示。
- **为什么省赛必须改**：学生的真实语料是老师发的 docx 课件与 PDF 表格。"主题创意 30%"要求场景真实，而"只支持 txt/md"在真实场景会露馅。
- **代价/风险**：每加一种格式就多一份依赖与版本锁（项目已经吃过 `chromadb==0.5.23` → Python 3.12 的链，`kb/rag_core.py` 相关注释）；新增格式必须同时进格式白名单与前端提示。
- **反转条件**：若docx conversion 引入的依赖装不上或太重，就保留"不支持"但在上传错误里给"请另存为 md"的明确指引（现有错误文案已经是这个风格）。
- **验收口径**：一个含表格的 docx 上传后，`get_source_chunks` 拼回的顺序正确、表格同一行不被切到两个片段；评估集里加 3 道依赖表格数据的题并全部 recall@3 命中。

### P1-3　切片策略：从"一个魔法数字"到"有评估支撑的档位"

- **现状**：全局 `CHUNK_SIZE=500` / `OVERLAP=50`（`core/config.py:42-43`）；`tools/eval_retrieval.py:252` 却用 300/50，`TOP_K=5` vs 生产默认 3（`:103`）。**评估与生产不同参数**——这意味着即便评估跑绿，也不能说明生产参数下的表现。
- **改什么**：
  1. 把评估脚本的 `chunk_size/overlap/top_k` 提为命令行参数或读取 config 默认值；至少让默认值与生产一致；
  2. 在 300 / 400 / 500 / 650 四档上跑同一个评估集，报告 recall@3 与相关题示弱率，选一档作为默认（经验区间 300~500 字是行业共识，但我们应当用自己的语料证实一次）；
  3. 结构感知切片（标题前缀、Markdown 层级）放到 P2，先把标记-评分-选档这件事做完整。
- **为什么省赛必须改**：它把"500 这个数哪来的"从小灶变成数据。而且这条与 P0-1 共用同一套评估基建，边际成本低。
- **代价/风险**：换默认切片参数意味着**知识库需要重建**（旧片段还在库里），必须有重建 SOP（见 P2-1）。
- **反转条件**：四档差异 < 3pp → 维持 500，只把"为什么是 500"写进文档并挂上评估截图。
- **验收口径**：产出一张四档对比表入 `docs/升级版_2026-10-20/`；选定档之后，新评估集在同一语料上 recall@3 不下降。

### P1-4　多路召回与负样本的量化目标

- **现状**：两路（向量 + BM25）。负样本只有 4 道完全无关题，且验收门槛是"离题示弱率 ≥ 0.5"——对一个只有 4 道题、且这些题完全不相干的集合来说，**0.5 太低了**，等于允许一半的误答。
- **改什么**：负样本扩到 8 道并分三级（完全无关 / 同域无关 / 术语撞脸）；把门槛提到 =1.0（前两级必须全 weak）；同时给"离题示弱率"做一个长期看板（已有 `retrieval_grounding` 计数，可按 `level` 分组出图）。
- **为什么省赛必须改**：这是"诚实示弱"这条产品主线的量化目标，没有它就只是在讲故事。
- **代价/风险**：硬负样本会让某些题被正确判成 medium/weak，反而拉低"相关题示弱率" → 因此两个指标必须**成对**看（`tools/eval_retrieval.py:423-425` 已经这么做了，把这个说明传播下去即可）。
- **反转条件**：若某些硬负样本在语义上确实与语料高度相关（这类题的标注本身有争议），就把它们移出"必须 weak"的集合，改为记录。
- **验收口径**：三级负样本的示弱率分别 = 1.0 / 1.0 / ≥0.67（第三级故意留作灰色地带，允许存在争议，超限只记录不卡门禁）。

### P2　（本期只列不做）

- **P2-1　换 embedding 的重建 SOP**：步骤写成文档——改模型 → `embed_guard.invalidate`（`core/embed_guard.py:192`）→ 全量 rebuild → 用 stamp 写新指纹 → 重跑 P0-1 标定并更新 profile。当前的风险点是"老库乐观放行"（`core/embed_guard.py:157-189`）会把已不一致的老库认证成一致，只能靠全量重建补救。
- **P2-2　向量 hit-rate 的在线漂移巡检**：把 `retrieval_top1_similarity` 直方图按天落一份，看分布是否整体平移。
- **P2-3　跨库检索**：现在是"会话绑一个库"（collection 物理隔离），跨库需要遍历 N 个 collection 逐个检索再合并，N>1 时延迟线性增长。

## 4. 竞品对照

| 产品 | 这一层怎么做 | 我们差在哪 | 要不要跟 |
|---|---|---|---|
| **RAGFlow**（80.7k⭐，DeepDoc/MinerU/Docling 深度文档解析、模板化分块、**引用溯源可视化定位到原文**、ES/Infinity 双引擎、知识图谱，需 4核16G） | 业内把"文档解析 + 溯源定位"做得最深的一个；rerank 位是它的标配 | 我们只有粗解析与 `preview/text` 级别的引用，**没有片段级/句子级定位**；没有重排 | **跟两件事**：P0-3 溯源定位（低成本高回报）、P1-2 表格/多格式解析。**明确不跟**它的引擎栈（4核16G 我们跑不动）与知识图谱 |
| **Dify**（142k⭐，Workflow+RAG+Agent+LLMOps，2核4G，已支持 MCP） | RAG 管线标准化，参数可视化配置，有召回/重排开关 | 我们的参数也是 env 可视，这点不差；差的是**没有"重排"这一格** | 部分跟：引入 rerank 位（对齐它的 UX 概念），但不改我们自研的 select_diverse 逻辑 |
| **FastGPT**（26.1k⭐，2核4G，中文问答优化、流式快、高并发） | 中文场景优化好，RAG 参数（相似度阈值、引用限制）暴露给用户调 | 我们同样有 env 可调，**还多了** mixed retrieval 与四档置信分级 | 不跟；我们在这一层的机制密度已经超过它 |
| **Coze 扣子**（闭源、插件生态丰富、一键分发、模型不可自定义） | RAG 是黑盒，参数不可控 | 反向差距：它是"不可调"，我们是"可调且有埋点" | 不跟；它的"不可自定义"正是我们答辩时的对照组 |
| **n8n**（188k⭐，400+ 集成、代码节点、MCP） | 本身不管检索，RAG 靠拼节点；重排要靠自己接 | 不适用 | 不跟 |

一句话对照：**RAGFlow 把"看得见依据"做成了行业标配，我们把"依据够不够格"做得更深。** 省赛要补齐的是"看得见"（P0-3），要守住的优势是"敢说不够格"——而这份优势现在最大的风险，恰恰是它**过头了**（P0-1）。

## 5. 落地顺序与验收口径

| 顺序 | 事项 | 依赖 | 验收口径 |
|---|---|---|---|
| **1** | **P0-1 真模型跑一遍 + 重定阈值 + 指纹绑定** | 有可用的 `EMBEDDING_API_KEY` | 产出一页《阈值标定报告》：真/假两套 summary、4 个指标的改前改后、最终阈值与 profile 表 |
| **2** | **P0-2 评估进 CI（离线轨 `--fake`） + 30 题扩集 + 真值基线库** | 1（阈值定了才知道门槛定多少） | 负向验证：改坏任一检索参数 CI 变红；`tools/eval_compare.py` 能比对两个基线 JSON |

| 4 | P1-1 重排（先做 RRF 权重可配 → 再谈 cross-encoder/云 rerank） | 1（阈值要重标一次） | 见 P1-1 口径 |

| — | P2-* | — | 只写文档，不动主线 |

统一红线：任何阈值/参数变更，**必须同时**（a）更新评估基线、（b）更新 `docs/` 下的标定报告、（c）保留一行 env 回退（沿用 `core/config.py:126,340-366` 那组"出问题一行 env 回退"的惯例）。

## 6. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| **不换向量数据库**（不上 Milvus/Qdrant/pgvector） | 2 核 2G + 零运维，独立进程的服务直接出局；我们真正缺的是刻度与评估，不是性能。研讨卷 §5.1 的反转条件（百万片段/多机）远未到 |
| **不做学习型排序（LTR / 微调 reranker）** | 需要大规模标注数据，而我们连 30 题的评估集都还没成型。没有数据就训练，得到的只是过拟合到我们语料的模型 |
| **不做自建 OCR**（扫描件） | 2G 内存上的 OCR 会把前台挤爆；且这不是学生场景的高频需求，现有错误文案已明确引导用户先转文本 |
| **不为了"更准"牺牲"敢示弱"** | 四档置信分级 + 两段中文约束 + medium 也算 weak，是本项目最有产品价值的设计（`core/config.py:117` 记录了 83.9% 的调研依据）。调阈值只能调**准度**，不能调掉这个机制本身 |
| **不把 `select_diverse` 换成 LangChain 的 `max_marginal_relevance_search`** | 它的实现不带离群过滤、且用 embedding 算相似度去重（`kb/rag_core.py` 相关注释），会同时丢掉"敢示弱"和"字符 bigram 去重叠的高性价比" |
| **不上知识图谱** | RAGFlow 有是因为它面向企业文档；我们的场景是个人知识库问答，图谱的实体抽取成本换不回 20 分里的任何一分 |
