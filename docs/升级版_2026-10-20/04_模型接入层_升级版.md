## 0. 一句话结论

> **校赛考的是"通不通"，省赛考的是"断了怎么办、花了多少钱、给别人能不能复用"。**
> 这一层现在的真实状况是：**单供应商、单点模型、每一次调用可达但不可观测、不可降级**。
> 三件事按优先级改：**① 主模型故障自动降级到备用模型；② 每次调用的 token/费用落库；③ 按任务分级选模**。
> 这三件做完，"技术方案 30%" 里最能拿分的"可靠性 + 成本治理"才有可演示的数据，而不是只有"它能跑"。

不改的一样值钱：**不接第三家模型做花哨路由、不做自研协议、不为了去供应商化上本地模型**——2 核 2G 与三人并行的约束不允许。

## 2. 校赛够用 vs 省赛不够

| 维度 | 校赛口径 | 省赛口径 | 差距 | 证据 |
|---|---|---|---|---|
| 可用性 | 老师跑一次能出答案 | 演示现场/评委自助试用时**不白屏、不 500** | 主模型单点故障 = 全站问答不可用 | 仅一家对话模型：`core/llm.py:35` |
| 稳定性 | 偶发超时可接受 | 有明确的降级链路与降级率 | 无降级，429/5xx 只能把英文/中文错误抛给用户 | `kb/rag_core.py:71` 只翻译不兜底 |
| 成本 | 自掏几百块额度够答辩 | "已投入实用或具有推广价值"要给出**单位成本账** | `usage` 只有次数，答不出"一次问答多少钱" | `core/quota.py:266-273` |
| 资源效率 | 统一一个模型简单 | 分类/摘要类任务用贵模型是浪费 | 所有任务（标题、画像、改写、回答）共用 `deepseek-chat` | `core/config.py:20-22`、调用见 `core/llm.py:43` |

| 供应链风险 | 一家能用就行 | 有切换路径与切换成本核算 | 换模型需要改配置并**重建向量库**；对话模型换了会影响 prompt 行为且无 A/B 数据 | `core/llm.py:67`、`core/embed_guard.py:157` |

## 3. 升级项

### P0-1　主模型故障自动降级到备用模型

- **现状**：`get_llm()` 是唯一出口，只能拿到 DeepSeek（OpenAI 兼容）客户端。任何 401/402/429/5xx/长时间超时，最终都走到 `describe_api_error` 变成一句中文提示给用户，服务"降级为不可用"而不是"降级为另一个模型"。
- **改什么**：在 `core/llm.py` 上加一层薄路由器：
  1. 新增配置项 `LLM_FALLBACK_MODEL` / `LLM_FALLBACK_BASE_URL` / `LLM_FALLBACK_API_KEY`（可直接复用百炼兼容端点，`core/config.py:32-34` 已经是同一形态）；
  2. `get_llm(..., role="answer"|"cheap")`：主模型调用失败且属于**可重试但重试仍失败**（429/5xx/超时）时，换备用模型重发**一次**，并 `metrics.inc("llm_fallback", {"from":..., "to":..., "err":...})`；
  3. 401/402/404 这类**确定性**错误不降级（换模型也一样），直接走现有文案；
  4. 降级时在 SSE 发一个 `status` 帧（复用 `api/chat.py` 已有的 status 通道），让用户知道"主模型拥堵，已切换"。
- **为什么省赛必须改**：这是"技术方案 30%"里唯一能被评委**现场触发**的能力——现场网络抖动或额度耗尽可以直接演示。而且成本极低（一个 try/except + 一个客户端），是投入产出比最高的一项。
- **代价/风险** ：
  - 答案风格切换可能让用户困惑 → 必须用 status 帧显式告知；
  - 跨供应商的 prompt 遵循率不一致（尤其 `【】` 结构化标记与 JSON 输出）→ 备用模型只用于"能回答就行"的主问答，**不用于**标题/画像/改写这类结构化输出；
  - 降级会额外花一次请求 → 用全局开关 + 每会话冷却限制，避免雪崩；
  - 缓存键必须加 `model`，否则 `core/llm.py:43` 的 `(temperature, max_tokens)` 会串到不同模型。
- **反转条件**：若只有一家可用额度 / 备用模型在中文问答上明显不可接受（抽样 20 题打分低于基线） / 单次调用预算不支持两次发送 → 退回单模型，但保留路由接口。
- **验收口径**：注入故障（把 `DEEPSEEK_API_KEY` 改成无效再发问）→ 请求不报错、自动走备用、SSE 出现明确的 status 提示、`/api/metrics` 里 `llm_fallback_total` 计数 +1；连续 20 次正常提问不触发任何降级。

### P0-2　每次调用的 token / 费用落库

- **现状**：`usage` 表只有 `count`（`core/quota.py:266-273`），配合 `DAILY_ASK_LIMIT=60` 做配额。也就是说：**系统知道每人每天问了几次，但不知道这次花了多少钱**。`core/metrics.py:224-239` 预声明了 10 个计数器 + 1 个直方图，里面没有一个是 token 或费用。
- **改什么**：
  1. 新增明细表 `llm_calls(day, user_id, path, model, role, tokens_in, tokens_out, latency_ms, retries, fallback, ok, err_class)`，按 7 天滚动清理；
  2. `usage` 表按现有迁移风格 `ALTER TABLE ... ADD COLUMN tokens_in/tokens_out/cost_cent`（照抄 `core/session.py:241-244` 的 try/except 迁移写法）；
  3. token 数从 OpenAI 兼容响应的 `usage` 字段取。注意**位置不定**——`api/chat.py:538-546` 已经在 `response_metadata` / `generation_info` / `additional_kwargs` 三处找 `finish_reason`，token 同样可能在这三处，必须同样的三处扫描；
  4. 费用用一个可写的单价表（`.env` 里的 `PRICE_<MODEL>_IN/OUT`，元/百万 token），不能硬编码进代码；
  5. `/api/usage/summary`（`api/usage.py:24`）返回当日估算费用，前端加一块"本月预计支出"。
- **为什么省赛必须改**：评分表里"已投入实用或具有推广价值"这一句，本质上问的是**运营得起吗**。答不出单位成本的 AI 项目，在这项是空的。另外这也是"系统测试数据充分"的量化素材（给出 N 次调用的平均 tokens/P95 延迟）。
- **代价/风险**：流式下 usage 往往只在最后一帧出现，被取消的请求（取消路径见 `api/chat.py:1080-1081`）拿不到 → 必须按"拿不到就标记 `unknown`"，不能猜；写入频率每请求 1 条，SQLite 单写者（`core/quota.py:302-310` 是原子 upsert，同风格）；多 worker 下写同一库，连接参数需照 `core/scheduler.py` 的既有写法处理（**待核对**：当前是否开 WAL）。
- **反转条件**：若供应商始终不返回 usage 字段 → 退回"按字符估算"，用 `core/context_compress.py:385` 的 `estimate_tokens` 估算，并在表里标 `estimated=1`。
- **验收口径**：同一条问题跑两遍，`/api/usage/summary` 返回的 token 数一致、且能按单价表算出估算费用；rag / agent / hybrid 三条路径都有数；与供应商后台账单对比误差 ≤ 10%（抽样 20 条）。

### P0-3　按任务分级选模

- **现状**：所有 LLM 任务都走同一个模型，只有 `temperature` 和 `max_tokens` 不同（`core/llm.py:43` 的缓存键就是这样设计的）。标题、用户画像、查询改写、上下文压缩这些"结构化小活"，付的是和主回答一样的单价。
- **改什么**：引入任务角色枚举：
  | 角色 | 用途 | 拟用模型档 |
  |---|---|---|
  | `answer` | RAG 主回答 / Agent 主循环 | 主模型（`DEEPSEEK_MODEL`） |
  | `cheap_struct` | 标题、画像标签、查询改写、主题标签 | 廉价模型（同一家的轻量版或百炼入门档） |
  | `vision` | 图片理解 | `VISION_MODEL`（已是独立配置） |
  实现为 `get_llm(role=...)`；`core/llm.py:13,25` 的缓存键扩展为 `(model, temperature, max_tokens)`。
- **为什么省赛必须改**：这是"技术方案"里能讲出设计感的一节——**不是所有 token 都等价**。而且它和 P0-2 是互补的：没有 P0-2 就证明不了省了多少，没有 P0-3 就省不了。
- **代价/风险**：廉价模型的 JSON 遵循率更低 → 现有受控词表/代码块剥离逻辑（`kb/rag_core.py` 的 tags 解析路径与受控过滤）已经兜了一层，改完必须在离线用例集合上验证遵循率；万一廉价模型质量差，会先劣化"看起来不重要"的功能，容易被忽略。
- **反转条件**：在 60 题离线集上，廉价模型的结构化输出通过率 < 95%，或综合质量打分低于主模型 5pp 以上 → 该角色退回主模型。
- **验收口径**：离线集 + 线上 AB（两天）：三种角色的单位成本下降 ≥ 30%，且 `hybrid` / `agent` / `rag` 三条主路径的回答质量（抽样人工评分）不下降。

### P1-1　超时与重试分级

- **现状**：全局 `LLM_TIMEOUT=60` + `LLM_MAX_RETRIES=2`（`core/config.py:58,60`）。`api/chat.py:342-343` 注释已指出"流式中途失败不应重试"，但目前依赖 httpx 的实现细节，不是显式保证。
- **改什么**：按角色分档（小输出 15s / 主回答 60s / 视觉 90s / embedding 30s），并把 `max_tokens` 很小的一次性调用改成"不重试或只重试 1 次"（标题生成失败不值得等 3 跳）。同时把"已产出 token 就不再重试"显式化。
- **为什么必须**：集中体现"外层的可靠性工程"——超时不是一个魔法数字，是一组按 SLO 定的数。省赛答辩时这是能一句话讲清的设计点。
- **代价/风险**：档位变多是认知负担；草稿成一帧表写进 `core/config.py` 并配 TLS 注释；改错会让长回答被误杀（已有前车之鉴：`config.py:57` 的注释解释了为什么 60 而不是 30）。
- **反转条件**：P95 延迟数据显示某两档无差别 → 合并档位。
- **验收口径**：注入 10s 延迟的服务端桩，各角色按预期超时且不出现"已产出 100+ token 后整体重发"。

### P1-2　取消语义完整化

- **现状**：`api/chat.py:1080` 每帧检查断连并 return，`_Acc.aborted`（`:514`）标记不入库。但**已吐出的 token 不会被回收**，也没有给前端一个"这是被取消"的帧。
- **改什么**：取消时主动 `aclose()` 上游生成器、发 `cancelled` 帧，并把"取消时已消耗的估算 token"记进 P0-2 的 `llm_calls`（`ok=0, err_class=cancelled`）。这让"看起来用户没损失"的取消，在成本账上是可见的。
- **为什么必须**：评委自助试用时最常见的动作就是中断，这是" failures are visible but free"的最后一格。
- **代价/风险**：需要 touching SSE 收尾的逻辑，风险在于改坏正常收尾 → 必须保留 `finally` 里的 closing，并用 `tests/test_truncation_detect.py` 同风格补一条。
- **反转条件**：若发现 `aclose` 在当前 langchain 版本上有兼容坑，先只做"记账"、不做强制关流。
- **验收口径**：连发 10 次并在 1 秒后取消，10 条 `llm_calls` 记录全部出现且 `err_class=cancelled`，服务无连接泄漏（`/health` 的 inflight 回落到 0）。

### P1-3　供应商锁定的显式化

- **现状**：已经比大多数项目好（三个客户端、三方配置、独立 model 字段、`describe_api_error` 用类名而不是 isinstance 避免 import 死锁 —— `kb/rag_core.py:71`）。但**缓存键是裸 tuple**（`core/llm.py:43`），新增构造参数时"忘了加进键"不会报类型错误，只会静默复用错误的实例。
- **改什么**：换成 frozen dataclass 作为键，所有构造参数都是字段；并写一份 `docs/模型能力矩阵.md`（支持哪些能力、不支持哪些：例如 reasoning_content 只在特定模型、缓存命中策略各家不同）。
- **为什么必须**：省赛要答"换供应商的成本是多少"，有矩阵才能给出数字。
- **代价/风险**：重构本身不难，但要同步改三个缓存点。
- **反转条件**：如果模型规模一直只有两家，此项可以只做矩阵文档，不动代码。
- **验收口径**：矩阵里每一项都能指到一个代码位置或一次验证记录；缓存键改成 dataclass 后所有离线用例通过。

### P2　（本期只列不做）

- 本地 embedding（`bge-m3` 一类）实现"数据不出校"：内存与首启时间是硬伤，2G 机器不现实；
- 长思维链 / reasoning 模型的正式接入与 reasoning 落库（`api/chat.py:20-28` 的事件与 `done.reasoning` 已预留，但 reasoning 未持久化）；
- 按用户等级分配模型额度。

## 4. 竞品对照

| 产品 | 这一层怎么做 | 我们差在哪 | 要不要跟 |
|---|---|---|---|
| **Dify**（142k⭐，Workflow+RAG+Agent+LLMOps，2核4G，已支持 MCP） | 内置"模型供应商"体系，多个供应商并行配置，应用里可切换；LLMOps 提供日志与 token 用量统计 | 我们没有第二家候选；没有 token 用量账本 | **跟一半**：P0-1/P0-2 就是这个方向，但不抄它的"大而全供应商市场" |
| **FastGPT**（26.1k⭐，2核4G，中文问答优化，流式快、支持高并发） | 模型渠道聚合（一个渠道多个模型），对话级 usage 统计 | 差别同上；它的定位偏"应用"，我们是"自建全链路" | 不跟形态，**跟它的"渠道聚合 + 用量可见"两点** |
| **RAGFlow**（80.7k⭐，DeepDoc 深度文档解析、模板化分块、引用溯源可视化、ES/Infinity 双引擎、知识图谱，需 4核16G） | 把 LLM / embedding / rerank **分开配置**且各自可换 | 我们已经是三份配置，这点不差；差的是没有 rerank 位（见 05 卷） | 部分跟：**给 LLM/Embedding/Rerank 三个独立位**，跟得上且成本低 |
| **Coze 扣子**（闭源，插件生态丰富，一键分发，**模型不可自定义**） | 平台托管模型，用户不可换 | 反方向：它的"不可自定义"是它的短板，我们的多供应商可配置是得分点 | **不跟**；答辩时可以把它当成反面论据 |
| **n8n**（188k⭐，400+ 集成、代码节点、MCP） | 模型只是节点的 credential，天然可换；失败走错误分支 | 它的"错误分支"正是我们缺的显式降级链路 | **跟思路**：降级是一种显式的控制流，不是一个 try/except |

一句话概括：**Dify/FastGPT 已经把"多模型 + 用量可见"做成标配，这一层我们再不动，省赛答辩会被问"你们凭什么说能运营"。**

## 5. 落地顺序与验收口径

| 顺序 | 事项 | 依赖 | 验收口径（可演示） |
|---|---|---|---|
| 1 | P0-2 token/费用落库 | 无（先做，因为它给后面两项提供判据） | 三条路径都有数；与账单误差 ≤10% |
| 2 | P0-1 主模型降级 | 1（有 fallback 计数才知道降过没降） | 注入故障演练：不报错、自动续说明、`llm_fallback_total` 计数可见 |
| 3 | P0-3 分级选模 | 1（有 token 数才知道省了多少） | 单位成本 ↓≥30%，质量不降 |
| 4 | P1-1 超时分级 + P1-2 取消记账 | 1 | 见各自口径 |
| 5 | P1-3 模型能力矩阵 + 缓存键 dataclass | 3（路由稳定后） | 矩阵每项有出处；回归全绿 |

统一红线：**每一项都必须带一个 env 开关**（沿用 `core/config.py:340-366` 那组"默认开启、出问题一行 env 回退"的既有惯例），并且每一步完成之后跑一次 `.github/workflows/ci.yml` 的离线子集。

## 6. 不做的事（及为什么）

| 不做 | 为什么 |
|---|---|
| **不以自杀式成本接第三家云端 LLM** | 三家才是"路由"产生正收益的门槛（研讨卷 04 §4.1 的反转条件已经算过），两家只做降级，不做 A/B，省下来的复杂度用在 P0-2/P0-3 上收益更大 |
| **不上 `init_chat_model`** | DeepSeek/百炼都 OpenAI 兼容，绕过 LangChain provider 路由的代价是零，收益是稳定（`core/llm.py:3-7` 已论证，并有经验编号） |
| **不做花哨的"智能路由"（按问题难度自动选模型）** | 需要标注数据，而我们的评估集还在建（见 05 卷 P0-2）；没有数据支撑的自适应＝随机切换，且不可复现 |
| **不本地化 embedding / 不上本地视觉模型** | 2 核 2G 上跑 `bge-m3` 或视觉模型会直接挤爆前台；而且仍未解决"合规"以外的任何用户可见问题 |
| **不自建 usage/计费服务** | SQLite 单表单写足够，多 worker 也是现有 `core/quota.py` 同一套路；引入 Prometheus exporter 进程违背这台机器的约束 |
| **不为指标而多加一层封装** | 三人并行、窗口有限，这一层的每一行新增都要能在答辩时被讲清"我为什么需要它" |
