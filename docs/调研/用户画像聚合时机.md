# 调研报告：用户画像什么时候聚合最合适

> 日期 2026-10-15 · 面向：标签钩子 C 方案的落地口径（征求意见稿待确认问题 3）
> 结论先行：**选「定时批量聚合」，触发点挂在每日总结之后**；不要写时聚合，也不要读时聚合。
> 本文可当学习材料读：§1-§2 讲原理与通用框架，§3-§4 讲业界怎么做，§5 给我们的具体答案。

---

## 1. 问题的本质：这是一次"物化视图 vs 按需计算"的取舍

"什么时候聚合用户画像"在数据工程里有个成熟对应物 —— **物化视图（materialized view）还是按需计算（view-on-demand）**：

| | 物化（写时/批时算好） | 按需（读时算） |
| --- | --- | --- |
| 成本 | 提前付，**可摊薄** | 每次查询都付 |
| 读延迟 | 低（读现成的） | 高（现算） |
| 一致性 | 有滞后（stale） | 最新 |
| 能否跨条目聚合 | ✅ 能 | ❌ 通常不能（只看到当前这一条） |

**用户画像有三个特质，把天平明确压向"物化"：**

1. **读远多于写**：一次画像会在很多轮对话里被反复注入，聚合算一次能用很久
2. **读发生在关键路径上**：问答是流式交互，读时聚合会直接变成用户可见的延迟
3. **聚合需要"看全体"**：判断"立体几何是薄弱点"需要看到**跨会话的多次**记录，
   而读时只拿到当前这一轮 —— 机制上就做不到

> 这也解释了为什么这个问题值得单独讨论：**它不是一个调参问题，而是架构选择。**

## 2. 通用框架：聚合点只有三个，各自的代价不同

| 聚合点 | 触发时机 | 成本 | 读延迟 | 能跨条目聚合吗 | 适合什么 |
| --- | --- | --- | --- | --- | --- |
| **① 写时** | 每轮对话结束立刻 | **高**（每轮一次 LLM 调用） | 低 | ❌ 只能看到本轮 | 单条事实型记忆（"用户住上海"） |
| **② 定时批量** | 固定周期（按天/按小时） | **低**（一天一次） | 低 | ✅ 能看到全天 | **统计型画像（薄弱点/偏好/习惯）** |
| **③ 读时** | 每次要注入画像时 | 中 | **高**（拖慢首字） | ⚠️ 有限 | 简单过滤、精确查表 |

**一个常被忽略的点**：写时聚合看起来"实时"，但它**永远做不出统计型判断**。
"用户经常在立体几何上卡住"这个结论需要 N 次观测，而写时只能看到第 N 次。
所以对于薄弱点这类画像，**写时聚合不是"更快的选择"，而是"做不到的选择"**。

## 3. 业界怎么做（可查证的三种形态）

### 3.1 Mem0：写时流水线 + 冲突对账

Mem0（Chhikara 等，2025，arXiv:2504.19413）走的是**写时**路线：每当一段新对话结束，
调用 LLM 抽取候选事实，然后对每条候选做**向量检索找相似旧记忆 → LLM 判断关系 → 四选一决策**：

| 决策 | 含义 |
| --- | --- |
| `ADD` | 全新信息，入库 |
| `UPDATE` | 补充或修正已有记忆 |
| `DELETE` | 新信息否定旧记忆，删除后者 |
| `NOOP` | 重复，不动 |

它的价值在于**把"选择性提取"和"冲突解决"统一在同一个机制里** —— 记忆库里每条记录都经过显式对账，
所以不会出现"用户住北京"和"用户住上海"同时存在。

> **可借鉴的是它的冲突处理，不是它的时机。** 写时对账适合"事实型"记忆（离散、可判定）；
> 我们的"薄弱点"是**累积型**的（要多次才成形），所以时机该换，但冲突策略照抄。

### 3.2 Memobase：用户画像 + 事件记忆，**缓冲批处理**

Memobase（开源 `memodb-io/memobase`）的设计更贴近我们的形态，它把用户记忆分成两部分：

- **用户画像（Profile）**：一组**可由开发者配置的槽位**，按**主题—子主题两级组织**
  （如 `basic_info→姓名`、`interest→游戏偏好`、`work→职位`），存从对话里提取的稳定属性
- **事件记忆（Event Memory）**：按时间线记录事件，回答"我们上次讨论预算是什么时候"

**它的工程策略正是我们要的答案**：*"对话先在缓冲区累积，达到一定规模或时限后再统一触发一次记忆提取，
以摊薄 LLM 调用成本，同时让查询侧只需读取已整理好的画像和事件，保证低延迟。"*

这句话把三个理由一次说全了：**成本摊薄 + 写侧攒够信息 + 读侧零计算**。

> 我们的 **`profile.aggregate` = Memobase 的缓冲批处理**。
> 而且它的"槽位 + 主题/子主题两级"正好对上 §4.5 的受控词表设计 —— 两条独立来源指向同一个形态，
> 这是很强的设计信号。

### 3.3 Hermes：离线整理 + 门槛（不每轮都学）

Nous Research 的 Hermes 是常驻本机的 Agent daemon，它的记忆分四层，其中两点直接相关：

- **提示词记忆**：`MEMORY.md` + `USER.md`，会话启动时注入，**刻意限制在几千字符内**
  —— "以逼迫 Agent 主动取舍"。这是个很硬的设计约束：**画像必须小到能全量注入**
- **技能沉淀有门槛**：只有满足特定条件（工具调用超过 5 次、从错误中恢复、
  **收到用户纠正**、跑通一个非显然的工作流）才固化成技能

> **"收到用户纠正"是高价值信号**：用户动手改过的地方，才是真正该记住的地方。
> 这与你早先在 `we/先进产品思路吸收.md:44` 定的门槛（`重复≥2次` 或 `你手动修正过它`）完全一致 ——
> 两个独立来源再次指向同一结论。

## 4. 几类"聚合点"分别适合存什么（把框架落到内容上）

书里 `chapter3.md:194-196` 给了认知科学的三分类，它决定了每类记忆该在哪个点聚合：

| 记忆类型 | 定义 | 例子 | **适合的聚合点** |
| --- | --- | --- | --- |
| **情景记忆** | 具体事件 | "10-15 问了立体几何辅助线" | ① 写时（事件天生离散，来一条存一条） |
| **语义记忆** | 从事件抽象出的一般知识 | "立体几何是薄弱点" | **② 定时批量**（要跨事件统计） |
| **程序记忆** | 行为流程 | "先给答案再给推导" | **② 定时批量**（要跨会话才能看出模式） |

**这张表就是答案的骨架**：我们画像里真正有价值的两类（语义 + 程序），**都指向批量聚合**。
写时该做的只是**情景记忆的落盘**（原始事件 + 标签），不是出结论。

> 书里还给了存储格式的四档：Simple Notes → Enhanced Notes → JSON Cards → Advanced JSON Cards
> （`chapter3.md:205`）。我们的 `user_profile_snapshots` 用 **JSON Cards 形态**（固定槽位 + 结构化值）
> 就够了，不必上 Advanced。

## 5. 三档压缩与冲突：聚合时还要做的两件事

书里 `chapter3.md:243-249` 给了可直接照抄的机制：

**三档压缩**（用于控制画像规模，避免"记忆爆炸"）：

| 档 | 做法 |
| --- | --- |
| ① 重要性评分 | 综合**访问频率** + **时间衰减** + 情感强度 + 信息独特性，低于阈值标记可压缩 |
| ② 聚类 | 相似记忆分组，每组生成代表性摘要（多次问天气 → "经常询问天气，特别关心降雨"） |
| ③ 抽象泛化 | 从情景记忆提取一般规律，转成语义/程序记忆 |

**冲突检测：版本化** —— "保留历史版本同时标记最新版本。对于某些信息（如当前地址）只保留最新版本，
其他信息（如工作经历）保留完整历史。"

> 落到我们：`weak_topic` 的 weight 累加+衰减（§6 已设计），
> 而 `mood` 这类**只保留最新**（旧情绪无意义）。**按标签类型决定保留策略**，不要一刀切。

## 6. 结论：我们的聚合时机

### 6.1 定论

| 决策 | 取值 | 依据 |
| --- | --- | --- |
| **聚合时机** | **定时批量（每天一次）** | 语义/程序记忆要跨事件统计；写时做不到，读时太贵 |
| **具体时刻** | **每日总结生成之后**（现有 `report.daily` 是 23:30） | 一天的对话已齐、stats 已算过，**复用同一次批处理窗口** |
| **为什么不选 03:00** | 征求意见稿建议 `0 3 * * *`。03:00 也**可以**（离线、避开高峰），但它与 23:30 的总结形成**两次夜间批处理**，且画像会滞后一天 | 建议**紧跟 `report.daily` 之后**（如 `35 23 * * *`），当天数据当天成型 |
| **写时做什么** | 只落**原始标签**（`user_tags` 累加） | 情景记忆写时落盘，成本低（一次小 max_token 抽取） |
| **读时做什么** | 只**读快照**，绝不现算 | 保证问答首字延迟不受画像影响 |
| **实时性例外** | 用户在**同一会话内**明确纠正时，可触发一次即时重算（可选） | 采纳 Hermes 的"用户纠正"信号，但用**事件触发的增量**而非全量重算 |

### 6.2 为什么"紧跟每日总结"是更优解（三个理由）

1. **复用已算好的东西**：`report.daily` 已经读过当天全部会话并算过 stats，
   画像聚合接在后面可以共享上下文，**不重复扫库**
2. **一次窗口，两个产物**：当天总结（给用户看）+ 画像快照（给模型用）同时成型，运维只需盯一条链路
3. **天然有追溯边界**：快照的 `generated_at` 与总结的 `date` 对齐，出问题好定位是哪天的数据

### 6.3 频率的上下界（防止走极端）

| 频率 | 问题 |
| --- | --- |
| 每轮（写时） | 成本 ×N；且**做不出统计结论** |
| 每小时 | 收益不明显（学习画像变化很慢），成本 ×24 |
| **每天一次** | ✅ 与总结同窗，成本可控，滞后一天对学习场景无感 |
| 每周一次 | 滞后太长；用户在周中换了目标，画像不跟 |
| 事件触发（攒够 N 条） | **可作为补充**：一天内攒够 50 条标签也触发一次，避免"聊得特别多的一天要等到晚上" |

> **推荐组合**：每日固定（主）+ 攒够阈值（补）。两个都写进 `enqueue_job` 的幂等键，
> 重复触发自动去重（你们已有 `job_runs` 的 `UNIQUE(idem_key)` 机制可直接用）。

### 6.4 与你已定的门槛的关系

门槛（`重复 ≥2 次` 或 `用户手动修正过`）**应该放在聚合层，不是抽取值**：

- **抽取**：能抽就抽，写进 `user_tags`（weight=1）—— 抽取阶段信息最全，先存下来
- **聚合**：在这里执行门槛 —— `weight ≥ 2` 或 `source = user_edited` 的标签才进快照

**为什么门槛放聚合层**：如果抽取时就按门槛丢弃，那些"第一次出现"的信号就永久丢了；
放在聚合层，它们留在 `user_tags` 里等第二次出现，**信息不丢、结论不乱**。
