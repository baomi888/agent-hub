> **面向**：前端对接同学
> **主题**：苞米agent「混合架构（工作流 × 自主 Agent）」对外接口契约
> **日期**：2026-10-14 ｜ **文档版本**：v1
> **后端实现**：`hybrid/` 引擎 + `api/hybrid.py` 管理面 + `api/chat.py` 的 `mode=hybrid` 分支（提交 `6e23a00` 引入，其后仅前端回退，后端接口未变）

## 一、对接范围

### 后端已具备（可直接对接）

| 能力 | 入口 |
|---|---|
| 混合模式聊天（流式） | `POST /api/chat/stream`，`mode: "hybrid"` |
| 新增 3 类 SSE 事件 | `hybrid_start` / `workflow_node` / `mode_switch` |
| 工作流定义 CRUD | `/api/hybrid/workflows` |
| 切换规则（系统默认 + 用户覆盖） | `/api/hybrid/rules` |
| 执行记录 / 全链路日志 | `/api/hybrid/runs` |
| 人工干预切换 | `/api/hybrid/runs/{run_id}/switch` |
| 内置资产 | 工作流 `builtin_plan_execute` + 4 条系统默认规则 |

### 前端建议实现（非后端职责）

1. 模式入口新增「混合」，发送时 `mode = "hybrid"`
2. hybrid 专属「起跑流程」选择器（自动编排 / 指定工作流）
3. 执行轨迹时间轴（节点进出 + 模式切换点 + 决策依据）
4. 运行中的「人工接管」入口（转交智能体 / 转回工作流 / 终止）
5. 工作流与切换规则管理界面（基于管理面 12 端点）

## 二、通用约定

| 项 | 约定 |
|---|---|
| 基址 | 同源相对路径 `/api/...`（沿用既有 `frontend/src/lib/api.ts` 的 `request()` 封装与 dev rewrites 代理） |
| 鉴权 | Cookie 会话，服务端从请求取当前用户；**流式请求必须带 Cookie**（`fetch` 加 `credentials: "include"`），否则首帧即被鉴权拦下 |
| 401 | 既有 `streamChat()` 会派发 `window` 事件 `baomi:unauthorized`，据此跳登录 |
| 错误体 | `{ "detail": "..." }` |
| SSE 帧格式 | `event: <name>\ndata: <json>\n\n`（沿用既有 `frontend/src/lib/sse.ts` 解析） |

### 状态码语义

| 码 | 含义 |
|---|---|
| 400 | 参数或结构非法（工作流定义校验失败 / 规则动作非法 / 规则条件语法错误 / action 非法） |
| 404 | 资源不存在或无权访问（含"系统内置不可改删"） |
| 409 | 状态冲突：仅出现在人工切换（执行已结束） |

## 三、聊天流式接口

### 3.1 请求：`POST /api/chat/stream`

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `sid` | string | 必填 | 会话 id |
| `question` | string | 必填 | 用户问题 |
| `top_k` | int | 服务端默认 | `> 0` 且 `≤ TOP_K_MAX`（默认上限 20，超限 422） |
| `kb_id_override` | string \| null | null | 覆盖当前会话绑定的知识库 |
| `mode` | string | `"auto"` | `auto` / `rag` / `agent` / `llm` / **`hybrid`** |
| `workflow_id` | string \| null | null | **仅 hybrid 有效**：指定工作流起跑；缺省时由后端选 |
| `attachments` | object[] | `[]` | 附件列表（图片理解用） |
| `location` | object \| null | null | `{ lat, lon }`（浏览器定位）或 `{ city }`（公网 http 下由服务端按 IP 推断） |

### 3.2 hybrid 起跑规则（后端逻辑，前端只需知道结果）

1. **传了 `workflow_id`**：校验归属（不是自己的按不存在处理）→ 校验定义 → 以 **`workflow`** 起跑；工作流不存在或无权限时直接回 `error` 事件：
   `{ "detail": "工作流不存在或无权限：<id>" }`
2. **未传 `workflow_id`**：按问题粗分——
   - 流程型 → 用内置 `builtin_plan_execute`，以 `workflow` 起跑
   - 开放型 → `agent` 裸跑（跑起来后仍有切换规则兜底）
3. **`HYBRID_MODE_ENABLED=0`**（服务端开关关闭）：`mode=hybrid` **静默回退 `agent`**，不报错；前端看到 `done.mode === "agent"` 即知未走混合。

> 参考（非契约，后端可能调整）：流程型关键词含「先 / 然后 / 接着 / 依次 / 步骤 / 流程 / 第一步 / 第二步 / 按照 / 最后 / 整理成 / 汇总 / 生成报告 / 制成 / 批量 / 并保存 / 并下载」；开放型关键词含「调研 / 研究 / 分析 / 比较 / 怎么看 / 如何 / 为什么 / 哪些 / 建议 / 聊聊 / 介绍 / 解释 / 探索」。打分持平或都不命中归开放型。

### 3.3 SSE 事件清单

| event | data | 说明 |
|---|---|---|
| `status` | `{ text }` | 状态提示（含节点重试提示、人工节点提示） |
| `tool` | **分两帧**：调用 `{ name, input }`、返回 `{ name, output }` | `input` 截断 200 字符、`output` 截断 300 字符；**工作流的 tool 节点只发调用帧**（无返回帧） |
| `token` | `{ text }` | 增量 token（**不带 node_id**） |
| `title` | `{ title }` | 自动生成的会话标题（仅首轮） |
| `hybrid_start` | `{ run_id, mode }` | **仅 hybrid**：起跑即发，`mode` 为初始模式（`workflow` / `agent`） |
| `workflow_node` | 见下 | **仅 hybrid**：工作流节点进出 |
| `mode_switch` | `{ rule, reason, from, to }` | **仅 hybrid**：模式切换 + 决策依据 |
| `error` | `{ detail }` | 错误（hybrid 下执行失败 / 超时 / 工作流不存在走这里） |
| `done` | 见下 | 收尾，**`run_id` 仅 hybrid 有值** |

**`workflow_node` 两种形态**：

| phase | data 字段 | 说明 |
|---|---|---|
| `enter` | `node_id`, `type`, `name` | 进入节点；`name` 是展示名（空则后端已回填为节点 id） |
| `exit` | `node_id`, `status`, `on_fail?`, `error?` | 离开节点；`status = "ok" \| "failed"`，`failed` 时附 `on_fail`（跳转目标）与 `error`（失败原因） |

**`mode_switch` 字段语义**：

| 字段 | 说明 |
|---|---|
| `rule` | 触发的规则名；`"manual"` = 人工干预；`"__max_switches__"` = 切换次数达上限被强制收工 |
| `reason` | 人类可读的决策依据（可直接展示在轨迹里） |
| `from` / `to` | 切换前后模式（`workflow` / `agent`） |

**`done` 字段**：

```json
{
  "answer": "最终答案正文",
  "refs": "引用来源 markdown",
  "title": "会话标题（可能为空）",
  "mode": "hybrid 或最终实际模式",
  "message_id": 123,
  "run_id": "hybrid 模式才有值，否则为 null"
}
```

### 3.4 典型事件序列（hybrid，字段真实）

```
event: hybrid_start  { run_id, mode: "workflow" }
event: workflow_node { phase: "enter", node_id: "plan", type: "llm", name: "任务规划" }
event: status        { text: "节点 plan 第 1 次失败，重试中：…" }   ← 仅重试时
event: workflow_node { phase: "exit", node_id: "plan", status: "ok" }
event: workflow_node { phase: "enter", node_id: "execute", type: "agent", name: "自主执行" }
event: tool          { name, input }      ← 调用帧
event: tool          { name, output }     ← 返回帧
event: token         { text: "…" }
event: mode_switch   { rule: "wf_node_failure", reason: "工作流节点失败且无补偿分支，Agent 降级接管", from: "workflow", to: "agent" }
event: workflow_node { phase: "exit", node_id: "execute", status: "failed", on_fail: null, error: "…" }
event: done          { answer, refs, title, mode, message_id, run_id }
```

## 四、工作流定义结构（`definition`）

### 4.1 顶层 `WorkflowDef`

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` | string | 否 | **不参与落库主键**（见 5.1），可留空 |
| `name` | string | 否 | 默认「未命名工作流」 |
| `version` | int | 否 | 默认 1 |
| `entry` | string \| null | 否 | 入口节点 id；`null` = `nodes` 第一个 |
| `nodes` | NodeDef[] | **是** | 至少 1 个 |
| `edges` | EdgeDef[] | 否 | 默认 `[]` |
| `timeout_seconds` | int | 否 | 流程整体超时；`0` = 用服务端默认 |

### 4.2 `NodeDef`

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `id` | string | 必填 | 唯一；边与 `on_fail` 都按它引用 |
| `type` | string | 必填 | `llm` / `tool` / `agent` / `condition` / `human` |
| `name` | string | `""` | 展示名（拓扑图与 `workflow_node.name` 用），空则显示 id |
| `config` | object | `{}` | 按类型不同（见 4.4） |
| `timeout_seconds` | int \| null | null | 节点级超时，`null` = 用服务端默认 |
| `retry` | int | 0 | 节点内重试次数（**先重试，再谈失败跳转/切换**） |
| `on_fail` | string \| null | null | 失败跳转节点 id；`null` 才进入切换规则判定 |
| `requires_agent` | bool | false | 执行到本节点主动让出给 Agent 模式 |

### 4.3 `EdgeDef`

| 字段 | 类型 | 说明 |
|---|---|---|
| `source` | string | 起点节点 id |
| `target` | string | 终点节点 id |
| `condition` | string \| null | 受限表达式；`null` = 默认兜底边 |

**路由规则**：按 `edges` 定义顺序求值带 `condition` 的边，第一个成立者走；都不成立则落**第一条无条件边**；若该节点所有边都有条件且无一成立 → 报错 `节点 xxx 的条件分支无匹配`（执行失败）。
**表达式作用域**：仅 `shared.<key>`；条件表达式中不可调用函数、不可访问黑名单属性（受限 AST 求值，拒绝任意 eval）。

### 4.4 `config` 逐类型键（前端表单需要的字段）

| type | config 键 | 说明 |
|---|---|---|
| `llm` | `prompt`（默认 `{question}`）、`output_key`（默认 `node_<id>`）、`stream`（bool，默认 false） | `stream=true` 时该节点产出 `token` 事件（"工作流逐字说话"）；产物写 `shared[output_key]` |
| `tool` | `tool`（工具名，必填）、`args`（对象，字符串值支持模板）、`output_key` | 工具名取自服务端注册工具集；未知名报错。产物写 `shared[output_key]` |
| `agent` | `goal`（默认 `{question}`）、`output_key`（默认 `agent_result`） | 流程内嵌一次自主执行；产物写 `shared[output_key]` |
| `condition` | 无 | 节点本身不做事，只是路由汇合点（分支逻辑写在边的 `condition` 上） |
| `human` | `prompt`、`output_key` | **本期为占位能力**：立即自动通过，回一条 `human_intervention` 事件，并把 `shared[output_key]` 置为 `"approved"` |

**模板语法**：字符串值中的 `{question}`（用户原始问题）与 `{shared.<key>}`（共享区取值）会被渲染；仅 `llm.prompt`、`tool.args` 的字符串值、`agent.goal`、`human.prompt` 支持。

### 4.5 落库前校验（不通过 → 400）

- 结构必须能通过模型校验（字段类型与枚举值，如 `type` 必须是五类之一；**未知字段会被忽略，不报错**）
- `nodes` 至少 1 个
- 节点 `id` 不重复
- 每条边的 `source` / `target` 必须指向存在的节点
- `on_fail` 必须指向存在的节点
- `entry` 若给值必须存在

### 4.6 内置样例（`builtin_plan_execute`，可在前端作为模板渲染）

```json
{
  "id": "builtin_plan_execute",
  "name": "规划-执行（内置）",
  "version": 1,
  "entry": "plan",
  "nodes": [
    {
      "id": "plan",
      "type": "llm",
      "name": "任务规划",
      "config": {
        "prompt": "你是任务规划器。请把下面的用户目标拆成 3~5 个可执行步骤，每步一行，只输出步骤清单，不要解释：\n{question}",
        "output_key": "plan",
        "stream": false
      }
    },
    {
      "id": "execute",
      "type": "agent",
      "name": "自主执行",
      "config": {
        "goal": "【用户目标】\n{question}\n\n【执行规划】\n{shared.plan}\n\n请按规划完成目标，直接给出最终结果。",
        "output_key": "agent_result"
      }
    }
  ],
  "edges": [{ "source": "plan", "target": "execute" }]
}
```

## 五、管理接口（前缀 `/api/hybrid`，整组需登录）

### 5.1 工作流

| 方法 | 路径 | 请求体 | 成功响应 | 错误 |
|---|---|---|---|---|
| GET | `/workflows` | — | `{ items: WorkflowRow[] }` | — |
| POST | `/workflows` | `WorkflowIn` | `WorkflowRow`（含新的 `id`） | 400 定义非法 |
| GET | `/workflows/{wf_id}` | — | `WorkflowRow` | 404 |
| PUT | `/workflows/{wf_id}` | `WorkflowIn` | `WorkflowRow`（`version` +1） | 400 定义非法；404 不存在或系统内置 |
| DELETE | `/workflows/{wf_id}` | — | `{ ok: true }` | 404 不存在或系统内置 |

**`WorkflowIn`**

| 字段 | 约束 |
|---|---|
| `name` | 必填，1–60 字符 |
| `description` | 可选，≤ 500 字符，默认 `""` |
| `definition` | 必填，第四节的 `WorkflowDef` |

**`WorkflowRow`**：`id`、`owner_id`、`name`、`description`、`definition`（已解析为对象）、`version`、`created_at`、`updated_at`、`builtin`（bool）

> ⚠️ **`id` 由后端生成**：创建时后端生成 12 位 hex 作为行 id，请求 `definition.id` 不参与主键。请以响应里的 `id` 作为后续 `workflow_id` 使用（`definition.id` 建议留空）。
> ⚠️ **内置只读**：`builtin: true` 的行对所有用户可见，改/删一律 404；列表按 `updated_at` 倒序。
> 时间字段均为 Unix 秒。

### 5.2 切换规则

| 方法 | 路径 | 请求体 | 成功响应 | 错误 |
|---|---|---|---|---|
| GET | `/rules` | — | `{ items: RuleRow[] }` | — |
| PUT | `/rules/{name}` | `RuleIn` | `{ ok: true }` | 400 `action` 非法 / `condition` 语法错误 |
| DELETE | `/rules/{name}` | — | `{ ok: true }` | 404 没有可删的用户规则（系统默认不可删） |

**`RuleIn`**

| 字段 | 约束 |
|---|---|
| `signal` | 必填，≤ 40 字符 |
| `condition` | 可选，≤ 500 字符；空 = 命中信号即触发 |
| `action` | 必填：`to_agent` / `to_workflow` / `terminate` |
| `reason` | 可选，≤ 200 字符（会写进日志与前端轨迹） |
| `priority` | 0–9999，默认 `100`（**数字小者先求值**） |
| `enabled` | 默认 `true` |
| `cooldown_seconds` | 0–86400，默认 `30`（防抖冷却；显式 `0` = 结构型规则豁免防抖） |

**`RuleRow`**：`id`、`owner_id`、`name`、`signal`、`condition`、`action`、`reason`、`priority`、`enabled`、`cooldown_seconds`、`builtin`（按 `priority` 升序）

**覆盖模型**：系统默认规则（`builtin: true`）删不掉；同名的用户规则**整体覆盖**系统规则；删除用户覆盖后系统默认重新生效。

> ⚠️ **列表只返回 `enabled = 1` 的规则**：把某条规则保存为 `enabled: false` 后，它会从 `GET /rules` 结果里消失（不会显示成"已停用"）。若 UI 需要展示停用项，请在前端本地保存状态。
> ⚠️ **`signal` 实际由引擎上报的只有四个**：`requires_agent`、`node_failed`、`budget_exhausted`、`goal_satisfied`。自定义 signal 能存下但不会有事件触发，等于不生效。
> **`condition` 作用域**：`shared.<key>`、`signal.<key>`、`ctx.goal` / `ctx.status` / `ctx.current_mode`。仅做**语法**校验（`ast.parse(mode="eval")`），语义（名字是否存在）在运行期判定。

**4 条系统默认规则（内置，可直接作为 UI 默认态）**

| name | signal | action | reason | priority | cooldown |
|---|---|---|---|---|---|
| `wf_requires_agent` | `requires_agent` | `to_agent` | 工作流节点声明需要自主执行，移交 Agent | 10 | 0 |
| `wf_node_failure` | `node_failed` | `to_agent` | 工作流节点失败且无补偿分支，Agent 降级接管 | 20 | 30 |
| `agent_budget_exhausted` | `budget_exhausted` | `to_workflow` | Agent 步数/时长/token 预算耗尽，收编回工作流 | 20 | 30 |
| `agent_goal_satisfied` | `goal_satisfied` | `to_workflow` | Agent 子目标完成，工作流从断点继续 | 30 | 0 |

### 5.3 执行记录与日志

| 方法 | 路径 | 查询/请求 | 成功响应 | 错误 |
|---|---|---|---|---|
| GET | `/runs` | `limit`（默认 20，上限 100） | `{ items: RunRow[] }` | — |
| GET | `/runs/{run_id}` | — | `RunDetail` | 404 |
| GET | `/runs/{run_id}/logs` | `limit`（默认 500，上限 2000） | `{ items: LogRow[] }` | —（无权限时 `items: []`） |
| POST | `/runs/{run_id}/switch` | `{ action }` | `{ ok: true }` | 404 / 409 / 400 |

**`RunRow`**（列表，不含大字段）：`run_id`、`task_id`、`workflow_id`、`status`、`created_at`、`updated_at`
**`RunDetail`**：`RunRow` + `owner_id` + `context`（`TaskContext` 快照对象，含 `goal` / `current_mode` / `workflow_state` / `agent_state` / `shared` / `mode_trace` / `version` 等）

`status` 取值：`running` / `completed` / `failed` / `timeout` / `stopped`

**`LogRow`**（按发生顺序正序）：`id`、`event_type`、`mode`、`node_id`、`decision`、`payload`、`ts`

| 字段 | 说明 |
|---|---|
| `event_type` | `node_enter` / `node_exit` / `tool_call` / `token` / `switch` / `error` / `status` / `human_intervention` |
| `mode` | 事件发生时的模式：`workflow` / `agent` |
| `node_id` | 工作流事件有值，Agent 事件为 null |
| `decision` | 仅 `switch` 事件：`{ rule, reason, from, to }` |
| `payload` | 摘要级数据，**序列化后截断 2000 字符**；无 payload 时为 `{}` |

> 刷新页面后要回显历史执行轨迹：用消息里回传的 `run_id` 调 `GET /runs/{run_id}/logs` 重建时间轴。

### 5.4 人工切换

`POST /api/hybrid/runs/{run_id}/switch`，请求体 `{ "action": "to_agent" | "to_workflow" | "terminate" }`

| 码 | 条件 |
|---|---|
| 404 | 执行记录不存在（或不是当前用户） |
| 409 | `detail: "任务已结束，无法切换"`（仅 `running` 允许） |
| 400 | `action` 非法 |

> 指令不会立即中断：正在运行的引擎在**安全点（节点边界 / 事件边界）**让出后生效，随后会推送一条 `rule = "manual"` 的 `mode_switch` 事件。前端据此更新轨迹与按钮态即可。

## 六、前端落地要点（可直接照做）

1. **零风险兼容**：不传 `workflow_id`、`mode` 保持原值，既有 `auto / rag / agent / llm` 链路行为完全不变。
2. **起跑流程选择器**：默认 `null`（自动编排）；选项来自 `GET /api/hybrid/workflows`；用户选中的工作流若在列表刷新后消失，发送前须回落为 `null`，避免带着不存在的 id 撞 `error`。
3. **轨迹配对**：`workflow_node` 的 `exit` 只带 `node_id`，不带 `name`；用 Map 记住同 `node_id` 的 `enter.name` 再渲染。
4. **轨迹分段着色**：建议以 `mode_switch` 为分段点（`from`/`to` 给前后模式），切换点展示 `reason` 文案。
5. **人工接管按钮**：仅在已收到 `hybrid_start`、且未收到 `done` 时展示；调用返回 409 时提示「任务已结束，无需切换」。
6. **节点 `config` 编辑**：建议用**非受控文本域 + 失焦提交**（受控写法在输入半截 JSON 时必然解析失败，导致无法输入），提交前本地 `JSON.parse` 校验并标红。
7. **拓扑视图**：`definition.nodes` + `edges` 足够画图；建议区分「带 `condition` 的条件边」与「默认边」，并标注 `entry`、`requires_agent`、`on_fail`。
8. **执行记录页**：列表用 `GET /runs`，点开调 `GET /runs/{run_id}` 看 `context`，时间轴调 `/logs`。

---

## 七、已知边界（前端需知）

- **并行节点未实现**：目前是顺序执行 + 条件分支。
- **`human` 节点为占位**：立即自动通过（回 `human_intervention` 事件），尚不能真正等待人工审批。
- **`token` 与 `tool` 事件不带 `node_id`**：hybrid 下由 SSE 透传时丢弃了节点归属；若要把它归到具体节点，需按事件顺序推断或用 `/logs` 回查。
- **轨迹不随聊天消息持久化**：`done.run_id` + `/logs` 是回显历史轨迹的唯一通道。
- **规则列表不返回停用项**（见 5.2）。
- **`definition.id` 不生效**（见 5.1）。
- 服务端开关：`HYBRID_MODE_ENABLED=0` 时混合模式静默回退 `agent`，前端无需特判，但会在 `done.mode` 与 `hybrid_start` 的缺失上体现出来。

## 八、联调清单（建议按此顺序自测）

| # | 断言 |
|---|---|
| 1 | 不传 `workflow_id` 发 `mode=hybrid`：能收到 `hybrid_start`，`done.run_id` 有值 |
| 2 | `mode=hybrid` + 不存在的 `workflow_id`：收到 `error { detail }`，无异常崩溃 |
| 3 | `mode=hybrid`、`HYBRID_MODE_ENABLED=0`：`done.mode === "agent"`，无 `hybrid_start` |
| 4 | 指定 `builtin_plan_execute`：先 `enter(plan)` → `enter(execute)` → `token` → `done` |
| 5 | 运行中调 `POST /runs/{run_id}/switch { action: "to_agent" }`：返回 `{ok:true}`，随后收到 `rule="manual"` 的 `mode_switch` |
| 6 | 执行结束后调同一 switch：返回 409 |
| 7 | `POST /workflows` 传非法定义（边指向不存在节点）：400 且 `detail` 可读 |
| 8 | `PUT /rules/{name}` 传 `condition: "shared.x >"`：400 语法错误 |
| 9 | `DELETE /workflows/builtin_plan_execute`：404（内置不可删） |
| 10 | 跑完一次后刷新页面用 `run_id` 调 `/logs`：能重建完整时间轴 |
