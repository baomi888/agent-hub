## P0-1 · 动态定位移出 system prompt

### 问题定位

| 位置 | 现状 |
|---|---|
| `agent/builder.py:173` | `note = location_note(location)` |
| `agent/builder.py:175` | `key = (bool(has_kb), note, scene, frozenset(activated))` —— 城市进了图缓存键 |
| `agent/builder.py:202` | `system_prompt += note` —— **动态信息进了静态前缀** |
| `api/chat.py:741-747` | Agent 路径：`build_agent(bool(...), location_ctx, req.scenario, activated)` |
| `api/chat.py:676` | hybrid 路径：`HybridOrchestrator(..., location=location_ctx)`（同样会透传进 prompt） |

**双重代价**：① LLM 前缀随城市变化 → 前缀缓存失效（你那份 kv-cache 报告实测命中率 90%→0%、成本 3.8×）；② 图缓存键 = `2 × #城市 × #场景 × #激活集`，而 `_AGENT_CACHE_MAX=32` → 城市一多就 LRU 抖动、反复重编译图。

### 目标原则（书第 2 章）

> 系统提示词与工具定义定下后别改；动态信息（时间/状态/定位）**追加到末尾**，不动前缀。

### 方案

1. **删** `builder.py:202` 的 `system_prompt += note`。
2. **改** `builder.py:175` 缓存键，去掉 `note`：
   ```python
   key = (bool(has_kb), scene, frozenset(activated))
   ```
   → 键种类降为 `2 × #场景 × #激活集`，32 槽绰绰有余。
3. **保留** `location_note()` 导出（调用方复用），但 `build_agent` 的 `location` 参数改为仅作兼容占位或直接移除（推荐移除，两处调用一起改干净）。
4. **Agent 路径** `api/chat.py`：在 `messages.append(HumanMessage(content=prompt_question))` 之后追加末尾 meta 消息：
   ```python
   messages.append(HumanMessage(content=prompt_question))
   if location_ctx:
       note = location_note(location_ctx)      # from agent.builder import location_note
       if note:
           messages.append(HumanMessage(content=note.strip()))
   ```
   定位仍在"回答之前"被看到，只是从前缀挪到了尾部。
5. **hybrid 路径**：`HybridOrchestrator` 收到的 `location` 不再进 system，改在拼 `ctx.shared["history"]` 之后、当前问题之后追加同款 meta 消息（改 `hybrid/agent_engine.py` / 编排器拼 prompt 处）。

### 风险与兜底

- **风险**：个别 chat template 对"连续两条 HumanMessage"敏感。
  **兜底**：退化为把 note 合并进最后一条用户消息 `prompt_question + "\n\n" + note` —— 前缀同样稳定，且天然单条 human 消息。优先试方案 4，实测异常就切兜底。
- **回滚**：只需还原三行，无数据变更。

### 验证

- 打同一会话连续两问，确认第二次前缀命中（对比 TTFT / 输入 token）。
- 确认问"今天天气"仍能免手输城市（行为不回归）。
- 观察 `_AGENT_CACHE` 命中：键种类应显著减少。

## P0-2 · 滑动窗口截断 → CORE-RAG 类性能驱动压缩

### 问题定位

| 位置 | 现状 |
|---|---|
| `core/session.py:37` | `MAX_HISTORY_TURNS = 10` |
| `core/session.py:432-455` | 尾部取 `limit_turns*2+10` 行再截最近 N 轮 |
| `api/chat.py` 五处 | `:549` `:750` `:840` `:886` `:955` 均 `get_messages(...)[:-1]` 喂给模型 |

**问题**：书第 2 章把滑动窗口列为反模式 —— 每轮窗口都在滑，前缀**每轮都变**，缓存永远不命中；且早期轮次被整体丢弃（"失忆"）。

> 附带发现：`api/chat.py:752-757` 只把 `user/assistant` 转成消息，**工具调用轨迹根本没进历史**。所以这里的"压缩"压的不是 tool results，而是**旧的问答轮次**。（工具轨迹不重放本身是第 1 章的另一个缺口，另案处理。）

### 目标原则：CORE-RAG 的"性能驱动"，取代预定义启发式

**先说清为什么是"类"**
CORE-RAG（*Less Is More: Elevating RAG via Performance-Driven Context Compression*，ICML 2026, Cui et al.）压缩的对象是**检索回来的文档**；agent-hub 这里要压的是**多轮对话历史**。对象不同，不能照搬。

但**病根相同**：现有压缩都依赖**预定义启发式**。CORE-RAG 批评的是"关键词重合度 / 摘要质量"这类代理指标；而 `MAX_HISTORY_TURNS=10`（保留最近 N 轮）正是最典型的预定义启发式。CORE-RAG 的核心主张可直接迁移：

> **不要用代理指标，直接用下游任务性能当反馈信号，迭代优化压缩策略。**

**迁移后的四条原则**

1. **性能即奖励**：压得好不好，由"下游回答质量"判定，不由 token 数或摘要流畅度判定。
2. **宁可不压**：压缩后若导致质量下降，就**回退不压缩**（论文原做法：degrade → empty summary，让策略学会"这种情况别压"）。这是安全阀，不是可选项。
3. **压缩时机放在两轮 API 调用之间**，不在请求关键路径上；**批量**压（接近阈值才压一次）—— 压完前缀就稳定下来，这是与滑动窗口的本质区别。
4. **硬规则兜底 + 策略决定其余**：结论 / 约束 / TODO / UUID·hash·URL / 文件名 **原样保留**（硬规则，不交给策略）；其余交给策略决定压不压、压多少。加 `[COMPRESSED]` 标记防重复压缩。

### 方案：CORE-RAG 类三阶段

**Stage 0 · 先造"性能"信号（没有评估集就没有奖励）**

CORE-RAG 的奖励是下游任务表现（论文用 EM/F1，因为评测集是 NQ/TriviaQA 这类**抽取式 QA**）。agent-hub 是开放式学习助手，论文的 Limitations 自己给了适配路径：开放式任务改用 **BARTScore / ROUGE / LLM-as-a-Judge**。

→ 所以先建 **60–100 例评估集 + Rubric（幻觉一票否决）+ LLM-as-a-Judge**。**评估集不是可选项，它就是这套方案的奖励函数** —— 这也正好接上第 6 章那条缺口。

**Stage 1 · 蒸馏温启动（离线，零 RL）**

教师 LLM 对"旧轮次"生成候选压缩块，产出三元组 `(原始历史, 压缩块, 下游 judged 质量)`：

- 压缩后**不劣化** → 保留为正样本；
- 压缩后**变差** → 标签记为「**不压缩**」（论文原做法：degrade → empty summary）。

产出的是策略先验：**什么样的历史该压、什么样的该原样留**。

**Stage 2 · 性能驱动迭代**

- **完整版（论文路线）**：压缩器当作 policy，用 **GRPO** 以 judged 质量为奖励迭代更新；压缩器是**轻量生成式插件**，下游 LLM 当固定黑盒。
- **务实版（推荐先上）**：不训权重，改**在线候选优选** —— 每次压缩产出 K 个候选块，用轻量打分器 / Judge 选最优；把"选了哪个 + 下游实际反馈"记进经验库，形成可回放的偏好数据。闭环保留"性能驱动"，但零训练成本，与项目"不改权重"的定位一致（书第 8 章"外部化学习"是同一条路）。

**在线部署形态（容器：压缩块落库 + 最近 K 轮原文）**

目标上下文结构（前缀长期稳定）：

```
[system + tools]  ← 固定不动
[压缩块 summary]  ← 只在压缩事件时变（批量、低频）
[最近 K 轮原文]    ← 逐轮增长（在尾部增长，不动前缀）
[当前问题]
```

**步骤**

1. **加字段**（`core/session.py` 建表处）：
   - `conversations.compressed_summary TEXT`（NULL 表示未压缩过）
   - `conversations.compressed_upto INTEGER`（已压缩到的最后 message id）
2. **新增 `core/context_compress.py`**：
   - `build_context(owner, sid, keep_turns=6)` → 返回 `[{"role":"system"...}]`：`[压缩块] + 最近 K 轮原文`，替换现有五处 `get_messages(...)[:-1]`。
   - `maybe_compress(owner, sid)` → 估算 `chars//2`（项目已有此折算口径，见 `service/daily.py:44`）；超过 `MAX_CONTEXT_CHARS * 0.8` 才触发；把"早于最近 K 轮"的旧轮次压成摘要块写入 `compressed_summary`，并推进 `compressed_upto`。
3. **调用时机**：每轮回答**结束后**异步调 `maybe_compress`（两轮之间，不在流式关键路径上）。
4. **`MAX_HISTORY_TURNS`**：从 10 提到安全上限（如 200）或置 `None`，只留一个防失控硬顶。
5. **保留清单**：压缩提示词里显式要求原样保留 —— 用户目标、已确认结论、URL/ID/文件名、待办项；摘要只写"发生了什么、结论是什么"。

**冷启动（Stage -1，评估集建好之前先用）**

评估集没建好就没有"性能"信号，先用**抽取式压缩**跑起来，同时作为后续 baseline：
- 保留**首轮**（通常含用户目标）+ **最近 K 轮**；
- 中间旧轮次每轮只留"用户问题的关键词 + 助手回答的首句/结论句"，拼成 `[COMPRESSED]` 块；
- 零 LLM 调用、零失败风险（与 `profile.aggregate` 的"零 LLM"风格一致）。

**安全阀（论文 degrade → empty summary 的直接迁移，必做）**

每次压缩后，若 judged 质量**低于阈值** → 立即**回退不压缩**，保留原历史。这条是防止"省了 token、回答却变差"的最后一道闸；没有它，这套方案就是裸奔。

### 风险与兜底

- **风险**：摘要丢失细节导致后续回答质量下降。
  **兜底**：`keep_turns` 先设大一点（8~10），压缩块只吃掉很老的部分；出问题把 `compressed_summary` 置 NULL 即回退到全量。
- **风险**：压缩块在压缩事件当轮会改前缀。这是**可接受的**——批量低频，不像滑动窗口每轮都改。
- **风险**：完整 RL 版（GRPO 训一个小压缩器）的成本与项目"不训模型"定位冲突。
  **兜底**：走务实版（在线候选优选，零训练），完整 RL 留作 Stage 3 备选。

### 验收指标（对齐论文口径）

- **主指标**：同一评估集上，压缩后的 judged 质量**不劣于**不压缩基线，最好**优于**（论文在 3% 压缩比下 EM 反而 +3.3）。
- **次指标**：输入 token 下降幅度；**前缀缓存命中率回升**（这是治"每轮破前缀"的直接证据）。
- **离线回归**：构造 30 轮会话，断言 ① 超阈值才压缩、② 压缩后 URL/ID/待办仍在（硬规则生效）、③ 未超阈值不压（防每轮压）、④ 质量低于阈值时回退不压缩（安全阀生效）。
- **统计纪律**：Judge 本身有噪声，必须按第 6 章口径算噪声带宽（100 例上 70% 即 ±9pp）——**分差小于噪声带宽就不切换**，别拿单次波动当结论。

## P0-3 · 让工具元数据真正生效（先做，这是安全洞）

### 问题定位

`retryable` / `needs_approval` / `max_output_chars` 三个字段**全仓只有 `core/tool_registry.py` 与 `tests/test_tool_registry.py` 引用**，执行侧无人消费。

最刺眼的一处：`download_file` 标了 `needs_approval=True`（`tool_registry.py:129`），但模型可以直接拉任意 URL 落盘并入库，**没有任何审批门**。而 `tool_registry.py:9-14` 的注释自己写着"这一层把它变成声明：引擎读它、确定性执行"——注释与实现矛盾。

### 目标原则（书第 4 章）

安全与输出上限必须是**机器策略**，不能是建立在模型阅读理解上的文案劝阻。

### 方案：在工具边界统一强制（一次改动，两条路径都生效）

新建 **`core/tool_guard.py`**，在 `agent/tools.py` 装配 `AGENT_TOOLS` 时统一包裹 —— Agent 直连路径与 hybrid 路径共用，避免两处各改一遍。

**三个强制点**

1. **`max_output_chars` 截断**
   - 工具返回后判断 `len(out) > meta.max_output_chars`；
   - 超限：全文落盘 `data/tool_outputs/<hash>.txt`，只回预览 + 显式说明：
     `…[已截断：省略 N 字符，完整结果已存至 data/tool_outputs/xxx.txt]`（书要求**注明省略量与续读方式**）。

2. **`needs_approval` 审批门**
   - 审批态从 `RunnableConfig.configurable` 读：`approved = {hash(name + args)}`（与 `kb_id` 同一注入通道，模型改不了）。
   - 未批准 → **不执行**，返回："该操作需用户确认后执行（download_file 会写磁盘/入库）。请在界面确认。"
   - 同时发一个 SSE 事件（如 `approval_request` `{tool, args, reason}`），前端弹确认；用户确认后**重发该轮**，服务端把 `approved` 放进 `configurable` → 工具正常执行。
   - **幂等**：审批绑定 `hash(name+args)`，改了参数就要重新批。

3. **`retryable` 熔断**
   - 非可重试工具（`kb_search` / `calculator`）失败后，把工具名写入 `configurable["banned_tools"]`；
   - 本轮内再次调用 → 直接拒绝并回："该工具本轮已因确定性失败禁用，请改用其他方案。"
   - 这把"靠文案劝模型别重试"换成确定性熔断（正是 `tool_registry.py` 注释里说的病根）。

**包裹方式（注意点）**

用 `functools.wraps` 保留原函数签名，否则 `@tool` 的 schema 与 `config: RunnableConfig` 注入会失效：

```python
def _enforce(fn, meta):
    @functools.wraps(fn)
    def wrapper(*args, config=None, **kwargs):
        # ① 审批  ② 执行  ③ 截断  ④ 失败标记 banned
        ...
    return wrapper

# agent/tools.py 装配
AGENT_TOOLS = [tool(_enforce(t.func, TOOL_META[t.name])) for t in _RAW_TOOLS]
```

> ⚠️ **必须先实测**：包裹后 `config` 注入与 `args_schema` 是否仍正确（LangChain `@tool` 靠签名内省）。
> **兜底方案**：若内省失效，退化到"在引擎侧强制"——审批在工具函数开头手动查 `configurable`；截断与重试标记放在 `api/chat.py` 处理 `updates` 事件、以及 `hybrid/agent_engine.py` 的工具结果处理处。

### 风险与兜底

- **风险**：审批门上线后，Agent 想下载文件会被拦，用户需多点一次。
  **兜底**：`needs_approval` 本身是声明式字段，可先只给 `download_file` 开；若线上反馈摩擦大，加配置项 `TOOL_APPROVAL_ENABLED`（默认开，可关）。
- **风险**：截断可能切掉模型需要的内容。
  **兜底**：`max_output_chars` 已按工具分档（4000/2000/1000），先按现状执行，观察后再调。

### 验证

新增 `tests/test_tool_guard.py`（离线、不联网）：

| 用例 | 断言 |
|---|---|
| A | 超长输出被截断，且回文含"省略 N 字符"与落盘路径 |
| B | `needs_approval=True` 且未批准 → 不执行、返回需确认 |
| C | 批准 hash 匹配 → 正常执行；hash 不匹配（改了参数）→ 仍拦 |
| D | `retryable=False` 工具失败后本轮再调 → 被 banned 拒绝 |

## 施工顺序与工作量（粗估）

| 顺序 | 项 | 改动面 | 量级 |
|:--:|---|---|---|
| 1 | **P0-3 元数据生效** | 新增 `core/tool_guard.py` + `agent/tools.py` 装配 + 新测试 | 半天（含实测内省是否失效） |
| 2 | **P0-1 定位移出 system** | `builder.py` 删 2 行改 1 行 + `api/chat.py` 2 处 + hybrid 1 处 | 1–2 小时 |
| 3 | **P0-2 上下文压缩** | `core/session.py` 加字段 + 新增 `core/context_compress.py` + `api/chat.py` 五处替换 + 测试 | 1–2 天（MVP 抽取式可压到半天） |

**P0-2 建议先上 MVP 抽取式**：零 LLM、零失败风险，先把"每轮破前缀"这个最贵的毛病治掉；LLM 摘要留作第二步。
