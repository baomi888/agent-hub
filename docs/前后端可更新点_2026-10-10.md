## 一、后端可更新点（新增）

### ★★★ 1. 三个大模型客户端全都没设超时：一次网络抖动可挂 30 分钟

**文件**：`core/llm.py:24-29`（`get_llm`）、`:40-45`（`get_embeddings`）、`:55-60`（`get_vision_llm`）

三个工厂函数没有一个传 `timeout` / `request_timeout`。**实测**（沙箱直接读包，非推测）：

```python
ChatOpenAI.model_fields["request_timeout"].default      = None
ChatOpenAI.model_fields["max_retries"].default          = None
OpenAIEmbeddings.model_fields["request_timeout"].default = None
OpenAIEmbeddings.model_fields["max_retries"].default     = 2
# openai 2.54.0 的兜底常量：
DEFAULT_TIMEOUT      = Timeout(connect=5.0, read=600, write=600, pool=600)
DEFAULT_MAX_RETRIES  = 2
```

`None` 不是"不限"，而是**落回 openai SDK 的 600 秒读超时 ×（1 + 2 次重试）= 最坏 30 分钟**。

后果链（这条比"慢"严重得多）：

1. `api/chat.py:188` 的 `async for chunk in llm.astream(...)` 挂住 ⇒ SSE **一个字节都不出**，
   前端 `sending` 永久 `true`、气泡永远"生成中…"。配合 10-08 #15（前端也没有任何超时），
   用户唯一的出路是刷新页面——而刷新后 `messages` 里躺着一条没有回答的提问。
2. **更糟的是 embedding**：`build_index` 是**持着 `kb_lock` 调 embedding** 的，
   而 10-08 #2 已实测证明 `delete_kb` 与上传路径的加锁顺序相反 ⇒
   embedding 挂住的这 30 分钟里，**整个知识库模块（列表/状态/归属校验）全部排队**。
3. 这些调用都包在 `asyncio.to_thread` 里（`api/chat.py:281/431`），默认线程池约 40，
   几个并发请求就能把线程池占满，之后**连普通的 SQLite 查询都排不上**。

**怎么改**（6 行）：

```python
# core/llm.py：三个工厂各加一行
request_timeout=(10.0, 120.0),   # (连接, 读)。视觉模型图片 base64 大，可放宽到 (10, 180)
# embedding 建议更短：(10.0, 60.0)，它跑在持锁路径上
```
再在 `api/chat.py:181` 的 `_stream_llm` 外面加一道总闸门
（`asyncio.wait_for(..., timeout=300)`），超时就 `yield _sse("error", {"detail": "模型响应超时"})`——
**给 LLM 看的超时和给用户看的超时是两件事**，前端那层（10-08 #15）也要有，但不能互相替代。

### ★★ 2. 后端几乎没有日志：线上排障只能靠用户在聊天框里截图

**实测**：全项目 `logging.*` 调用共 **6 处、分布在 3 个文件**——
`api/geo.py:113/118`、`core/upload.py:61`、`kb/pipelines.py:160/178/198`。
`api/chat.py`（519 行）、`api/kb.py`、`api/auth.py`、`agent/tools.py` 的命中数是 **0**。
连 `logging.basicConfig()` 都没有。

三个具体后果：

1. **登录/注册失败零记录**。`api/auth.py:76/94` 只调了 `quota.hit()` 做防爆破限流，
   失败本身不落任何日志 ⇒ 有人拿字典撞你的站，你**事后完全无从发现**（配额只挡速度，不留下痕迹）。
2. **异常的原文 traceback 从未落到任何地方**。`api/chat.py:204/310/423/434/455`、
   `api/kb.py` 各端点都是 `describe_api_error(e)` 转成人话 `yield` 给前端就完事，
   `logger.exception` 一次都没有 ⇒ 一个只在生产出现的报错，唯一副本是用户截图。
3. `/health` 是假探针（09-29 #10，**跨 11 轮未修**）⇒ 唯一能主动看的东西还是假的。

**怎么改**（约 20 行，一次到位）：

```python
# main.py：加一个中间件，逐请求记一行
@app.middleware("http")
async def access_log(request, call_next):
    t = time.perf_counter()
    resp = await call_next(request)
    ms = (time.perf_counter() - t) * 1000
    rec = logging.info if resp.status_code < 400 else logging.warning
    rec("%s %s -> %s (%.0fms)", request.method, request.url.path, resp.status_code, ms)
    return resp
```
顺带三处：`main.py` 顶部 `logging.basicConfig(level=logging.INFO)`；
`core/auth.py` 登录失败 `logger.warning("login failed: %s", username)`；
`kb/rag_core.py::describe_api_error` 内部 `logger.exception("api error")` 后再返回人话。

### ★★ 3. `/api/chat/upload` 完全不接配额与限流：单请求 180MB，且无格式白名单

**文件**：`api/chat.py:105-131`

对照看就很刺眼：知识库上传走 `quota.guard`（`api/kb.py:73`），
连**只读端点**都调了 `quota.hit`（`api/kb.py:423`、`:470`）；
而 `grep -n "quota\." api/chat.py` 只有 `:215` 一处（`/stream` 的 `consume "ask"`），
**`/upload` 端点的配额与限流调用点是 0**。

- 一次请求上限 = `MAX_CHAT_FILES=9` × `MAX_CHAT_UPLOAD_MB=20` = **180MB**（`:45-46`），
  没有任何每分钟次数限制 ⇒ 单机几十个请求就能写满 2G ECS 的盘。
- 文件类型**完全不筛**：`:119` `ext = os.path.splitext(f.filename or "")[1] or ".bin"`，
  `.exe` / `.iso` / `.zip` 照单全收，落进 `data/chat_uploads/`。
- 清理只在**下次有人上传时顺带跑一次**（`:89-102` `_cleanup_old_uploads`）：
  没人再上传，那些文件就一直躺着。

**怎么改**（约 10 行）：① 端点开头 `await asyncio.to_thread(quota.hit, uid)`；
② 加图片白名单（非图片后端本来也不消费，见 `:136-142` 的 `_has_image`），不是 `image/*` 直接 400；
③ 可选：按 uid 统计已占用字节数，超 200MB 拒。
> 磁盘这块别只靠 TTL——TTL 的触发条件是"有人再来上传"，攻击场景下不会有人来。

### ★★ 4. `downloads/` 只进不出：无 TTL、无大小上限，还会主动拉 .exe / .iso

**文件**：`kb/importer.py:241`（写到 `DOWNLOAD_DIR/owner/`）、`:230-231`（`f.write(resp.content)`）、
`:186-187`（`_DOWNLOAD_EXTS`）

- `chat_uploads` 有 24h TTL（`api/chat.py:89-102`），`downloads/` **全项目零清理**，
  抓下来的网页/文档正文**永久留存**（第三方内容，长期存还有合规上的麻烦）。
- 白名单里有六种格式**永远不会被索引**：`_DOWNLOAD_EXTS` 含

  这六种**下载完就永久躺在服务器上，一次都不会用到**。
- 这条通道由 Agent 工具 `download_file` 调用（`agent/tools.py:497` 的 `AGENT_TOOLS`），

**怎么改**：① `download_file` 改 `client.stream()` + 累计字节数超限即断（与 10-08 #6 同一套写法，**两处一起改**）；
② `_DOWNLOAD_EXTS` 砍到 `{.txt, .md, .pdf}`——其余六种下载了也没用，留着只是给注入一条"往服务器拉二进制"的路；
③ `downloads/` 复用 `_cleanup_old_uploads` 的写法加 TTL（比如 72h）。

### ★★ 5. 提示词与历史没有任何长度预算，`get_messages` 的 SQL 连 LIMIT 都没有

**文件**：`core/session.py:280-283`、`api/chat.py:533-536`、`:60`

```python

    "SELECT id, role, content, refs, created_at FROM messages "
    "WHERE conversation_id = ? ORDER BY id ASC",   # ← 没有 LIMIT
    (sid,),).fetchall()
```

`MAX_HISTORY_TURNS = 10`（`:35`）的截断是在 Python 里做的，SQL 侧一条不落全捞回来。

算一下最坏情况的上界（把前几轮各自报的"参数无校验"乘起来）：

| 变量 | 现状 | 最大取值 |
| --- | --- | --- |
| `top_k` | `api/chat.py:60` 只有 `gt=0`，无上界（10-08 #8） | 任意 |
| `chunk_size` | 裸 `int`，无校验（10-07 #4，`KBBuildRequest` 是死代码） | 任意 |

这是前两轮"参数没校验"的**连锁后果**——单看 `top_k` 无上界只是"浪费算力"，
乘上 `chunk_size` 决定的是 prompt 体积，而 prompt 体积是唯一能一次请求烧掉几十块钱的地方。

**怎么改**（三处，都很小）：

② `_build_messages:521-524` 拼 `references` 时按字符预算截断（比如 12000 字），超了丢尾部并在 status 里说一句；
③ `get_messages` 的 SQL 加 `LIMIT ?`（`limit_turns*2 + 8` 条足够，因为截断要数 user 消息，宁可多取几条）。

### ★★★ 7. `usePrefs` 的"不读回"不只是显示错，而是**把用户存的设置永久抹掉**

> 10-07 #16 / 10-08 #19 已经记过"三个数值字段存了从不读回"。
> 本轮往下推一层：**不读回 + 挂载即回写 = 用户改过的参数在每次刷新时被默认值覆盖，且再也回不来。**

**文件**：`frontend/src/lib/hooks/usePrefs.ts:52-58`（读回）vs `:62-72`（回写）；
`frontend/src/app/page.tsx:135-148`

推演一遍真实的挂载顺序（用户上次把检索条数改成 10）：

1. `:52-58` 的读回 effect：`saved = {topK: 10, ...}`，写进 `savedRef`，
   但**只 `setMode` / `setKbPanelPref` / `setFontScale`**，三个数值不 set ⇒ `topK` 仍是初始的 `3`。
2. `page.tsx:141` 的 `if (saved.topK === undefined) setTopK(d.top_k)` ——
   `saved.topK = 10` 不是 undefined ⇒ **后端默认值也不会应用**。
3. `:62-72` 的回写 effect：`prefsReady` 变 true 后触发 `writePrefs({topK: 3, ...})` ⇒
   **localStorage 里用户的 10 被 3 覆盖**。

由此产生两个可观察的现象：
① 改了检索条数/切片参数 → 刷新 → 回到 500/50/3；
② 第二次刷新时 `saved.topK` 已经是 3，`savedRef` 再也拿不到用户真实的选择 ⇒ **设置永久丢失**。

**怎么改**（3 行，两处）：

```ts
// usePrefs.ts:55-57 后面补三行（对齐已有的三个字段写法）
if (typeof saved.topK === "number") setTopK(saved.topK);
if (typeof saved.chunkSize === "number") setChunkSize(saved.chunkSize);
if (typeof saved.chunkOverlap === "number") setChunkOverlap(saved.chunkOverlap);
```
> 顺带：`page.tsx:141-143` 可以保持不动（有了读回，`saved.topK === undefined` 的兜底语义仍然正确）。
> 记住这个形状：**「读回不完整」+「挂载后无条件回写」= 静默数据销毁**，
> 比单纯的"读不回来"严重一档。
