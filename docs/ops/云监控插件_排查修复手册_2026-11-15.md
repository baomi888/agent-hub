# 云监控插件（argusagent）停止运行 —— 排查与修复手册

- 实例：`BaomiServer` / `i-7xve8cs4d301hag56zxb` / cn-guangzhou / 8.163.62.25
- 首次发生：**2026-11-14 22:09:32**，控制台「插件状态」显示异常，持续约 11.5 小时
- 处理时间：2026-11-15 09:38–09:41，**已恢复**（连续 6 轮上报成功）
- Agent 版本：`argusagent 4.1.0 (linux-amd64)`，commit `a05a704`

---

## 0. 本次的真实原因（不是网络、不是内存、不是被恶意杀）

排查结论与常见猜测相反：**守护进程一直活着，是采集子进程按自己的自保护规则自杀的，
然后父进程按"资源超限"把它永久禁用了。**

链路（每一步都是日志原文）：

1. `2026-11-14 22:09:32` 采集进程 `self_monitor` 报告：
   `io read speed=3378.813KB/s[>=256.00KB/s 4/4] ... => will exit`
   四项自监控阈值里，**磁盘读速连续 4 次超过 256KB/s**，触发自保护退出。
2. 退出被计入 `resourceCount`，`/usr/local/cloudmonitor/agent.status` 里写成 `resourceCount|4`
   —— **4 就是上限**。
3. 父进程 `argusagent -d` 从此拒绝拉起采集进程：
   `agent is disabled because of resourceCount exceed for 685m since 2026-11-14 22:09:32, waiting for next restart!!!`
4. 因为采集进程不在，控制台就没有新数据 → 显示「已停止」。但 `systemctl status` 仍是
   `active (running)`，**这就是"服务明明在跑、控制台说停止"的原因**，也是最容易误判的地方。

排除项（都有读数）：

| 猜测 | 实测 | 结论 |
|---|---|---|
| 内存不足 / OOM | `dmesg -T` 无 OOM 记录；`free -m` 520/1736 已用，available 1036MB | 排除 |
| 有人恶意杀进程 | 无 `kill`/`pkill` 痕迹，进程 23 天未重启过 | 排除 |
| 网络不通 | `metrichub-cn-guangzhou` TCP 通（404=可达）、`cms-cloudmonitor:443` 通（400=可达）、元数据 `100.100.100.200` 5ms | 排除 |
| 云助手异常 | `aliyun.service` active running | 排除 |
| `open.cms.aliyun.com:80` 不通 | TCP 超时，但**日志里该域名出现 0 次**，Agent 只走 metrichub / cmsproxy / cms-cloudmonitor | 与本故障无关 |

`22:09` 那 30 秒的读 IO 到底由谁产生，**没有结论**：这台机器没装 sysstat，没有 `sar` 历史，
无法回溯到进程级。可以确认的只有同期负载：后台面板每 30 秒并发 4 个统计查询、以及十余次整页加载、
且 `net` 模块采集超时、`gpu` 模块耗时 1450ms（说明整机当时确实在被 IO 拖慢）。

## 1. 判定标准速查（先看这一屏）

| 现象 | 判定 |
|---|---|
| `systemctl is-active` = active，但**只有一个** `argusagent -d` 进程 | 采集进程已死，父进程在等 → 看 `agent.status` 的 `resourceCount` |
| `agent.status` 里 `resourceCount` ≥ 4 | 确认命中自保护禁用，必须**手动清零**（重启服务无效，见 §2.2） |
| `argusagent.log` 最后一行是 `send metric summary ... error=0` | 正常在报 |
| `argusagent.log` 里出现 `=> will exit` | 自保护退出，往上翻看是哪一项 `[4/4]` |
| `argus-last-send-cms.txt` mtime 停在故障时刻 | 已停止上报的硬证据 |
| `journalctl -u cloudmonitor` 有 `Main PID: NNN (argusagent)` 且 `Tasks: 1` | 单进程 = 只有父进程，异常 |

## 2. Linux 操作手册

### 2.1 检查插件服务状态并尝试启动

```bash
systemctl status cloudmonitor --no-pager
systemctl is-active cloudmonitor
ps -eo pid,ppid,etime,rss,cmd | grep '[a]rgusagent'
cat /usr/local/cloudmonitor/agent.status
tail -20 /usr/local/cloudmonitor/local_data/logs/argusagentd.log
```

**判定**：正常应有 **两个**进程 —— 父 `argusagent -d`（约 7MB）+ 子 `argusagent`（约 37MB）。
只有一个、且 `agent.status` 里 `resourceCount|4`，就是本次这种「被自保护禁用」。

```bash
/usr/local/cloudmonitor/cloudmonitorCtl.sh status
/usr/local/cloudmonitor/cloudmonitorCtl.sh restart
```
（该脚本支持 `install | start | stop | restart | status | uninstall`；
**注意：`restart` 不会清 `resourceCount`**，本次实测重启后父进程依然是 disabled。）

### 2.2 真正的修复：清零 resourceCount（本次生效的动作）

```bash
cd /usr/local/cloudmonitor
cp -a agent.status agent.status.bak_$(date +%Y%m%d_%H%M)   # 必须备份
systemctl stop cloudmonitor
python3 - <<'PY'
import time, io
now = int(time.time())
p = "/usr/local/cloudmonitor/agent.status"
out = []
for ln in io.open(p, encoding="utf-8").read().splitlines():
    f = ln.split("|")
    if len(f) == 3 and f[1] in ("resourceCount", "startCount"):
        f[0], f[2] = str(now), "0"
    out.append("|".join(f))
io.open(p, "w", encoding="utf-8", newline="\n").write("\n".join(out) + "\n")
PY
systemctl start cloudmonitor
```

预期（30 秒内）：

```
$ ps -eo pid,ppid,etime,rss,cmd | grep '[a]rgusagent'
411332       1  00:36   7064 /usr/local/cloudmonitor/bin/argusagent -d
411334  411332  00:36  37092 /usr/local/cloudmonitor/bin/argusagent      ← 子进程回来了
```

```
$ tail -3 local_data/logs/argusagent.log
send msg to http://metrichub-cn-guangzhou.aliyun.com/agent/metrics/putLines, success
send metric summary,total=6,ok=6,error=0, records=44
```

判定成功：`ok` 的序号递增（3→4→5→6）、`error=0`、`argus-last-send-cms.txt` 的 mtime 在刷新、
`agent.status` 里 `startCount` 变 1。

### 2.3 云助手（控制台推送命令依赖它）

```bash
systemctl is-active aliyun.service
systemctl status aliyun.service --no-pager | head -5
```
**判定**：`active`。若 inactive，控制台的"安装/升级插件"会推送失败，需先修云助手。

### 2.4 内存与 OOM

```bash
free -m
dmesg -T | grep -iE 'out of memory|oom-killer|killed process'
grep -c 'will exit' /usr/local/cloudmonitor/local_data/logs/argusagent.log
```
**判定**：OOM 应无输出；`will exit` 计数 >0 说明自保护退出过（本次命中这一条）。
注意 `free` 里 `buff/cache` 高不算问题，看 `available`。

### 2.5 是否有进程反复终止 Agent

```bash
grep -rn 'argusagent' /etc/cron* /var/spool/cron/ 2>/dev/null
systemctl list-timers --all | grep -iE 'argus|kill|clean'
journalctl --since '2 days ago' | grep -iE 'kill.*argus|argus.*killed'
dmesg -T | grep -i 'argus' | tail
```
**判定**：全部空 = 无人为干预。本次即如此。

### 2.6 内网连通性

```bash
curl -s -m 5 -o /dev/null -w '%{http_code} %{time_total}s\n' http://100.100.100.200/latest/meta-data/instance-id
getent hosts metrichub-cn-guangzhou.aliyun.com open.cms.aliyun.com
for hp in "metrichub-cn-guangzhou.aliyun.com 80" "cms-cloudmonitor.aliyun.com 443" "open.cms.aliyun.com 80"; do
  set -- $hp; echo -n "$1:$2 -> "
  timeout 5 bash -c "cat < /dev/null > /dev/tcp/$1/$2" 2>/dev/null && echo 通 || echo 不通
done
```

**判定**：元数据 200；`metrichub...:80` **TCP 通**（HTTP 返回 404/200 都算通，404 只是没有根路径）；
`cms-cloudmonitor:443` 通。

`open.cms.aliyun.com` 在本机 **80/443 都 TCP 超时**，但它是云监控 OpenAPI 的内网地址，
**Agent 的上报链路不使用它**（本机日志出现 0 次）。只要 metrichub 通就不影响上报。
若控制台仍拿不到数据、且 metrichub 也不通，才对它提工单。

### 2.7 卸载重装（以上都无效时）

```bash
# 卸载
bash /usr/local/cloudmonitor/cloudmonitorCtl.sh stop
bash /usr/local/cloudmonitor/cloudmonitorCtl.sh uninstall
ls /usr/local/cloudmonitor 2>/dev/null || echo "目录已清理"

# 重装（地址已实测 200）
cd /tmp
curl -sSL -o cms_install.sh \
  https://cms-agent-cn-guangzhou.oss-cn-guangzhou.aliyuncs.com/release/cms_install_for_linux.sh
bash cms_install.sh
systemctl is-active cloudmonitor && ps -eo cmd | grep -c '[a]rgusagent'
```
**判定**：重装后 1–2 分钟内 `argusagent.log` 出现 `send metric summary ... error=0`。
注意重装会**重置 agent.status**，所以"清零 resourceCount"和"重装"在效果上有重叠 ——
能清零就不要重装，重装会丢本地配置（`conf/` 下的自定义任务）。

## 3. Windows 操作手册（同版本 Agent 语义一致）

> 说明：Windows 侧**没有公开直链安装包**（实测 `cms_install_for_windows.ps1/.bat/.zip` 等 6 个候选全部 404）。
> 官方路径是**控制台推送**：云监控 → 主机监控 → 选中实例 → 安装/升级插件（走云助手下发）。

### 3.1 服务状态

```powershell
Get-Service *argus*, *aliyun* | Format-Table Name, Status, DisplayName -Auto
sc.exe query argusagent
Get-Process argusagent -ErrorAction SilentlyContinue | Select-Object Id, WorkingSet64, StartTime
```
**判定**：正常应为**两个** `argusagent` 进程（父 + 采集子进程）。
只有 1 个且服务 running → 与 Linux 同因，看 §3.2。

### 3.2 清零 resourceCount（关键步骤）

```powershell
$dir = "C:\Program Files\Alibaba\cloudmonitor"
Copy-Item "$dir\agent.status" "$dir\agent.status.bak_$(Get-Date -f yyyyMMdd_HHmm)"
Stop-Service argusagent
# 把 resourceCount / startCount 置 0，时间戳置当前
(Get-Content "$dir\agent.status") -replace '^(?<t>\d+)\|(?<k>resourceCount|startCount)\|\d+$',
  "$([int][double]::Parse((Get-Date -UFormat %s)))|`${k}|0" | Set-Content "$dir\agent.status" -Encoding ASCII
Start-Service argusagent
Start-Sleep 30
Get-Process argusagent | Select-Object Id, WorkingSet64
Get-Content "$dir\local_data\logs\argusagent.log" -Tail 6
```
**判定**：两个进程、日志末行 `error=0`。
（PowerShell 替换里若 `${k}` 展开异常，直接手动编辑该文本文件亦可，格式是 `时间戳|键|值` 三行。）

### 3.3 内存 / OOM / 恶意终止

```powershell
Get-CimInstance Win32_OperatingSystem | Select-Object @{n='FreeMB';e={[math]::Round($_.FreePhysicalMemory/1KB)}}, @{n='TotalMB';e={[math]::Round($_.TotalVisibleMemorySize/1KB)}}
Get-WinEvent -FilterHashtable @{LogName='System'; Id=2004,2005,2006,2008} -MaxEvents 5   # Resource-Exhaustion
Get-WinEvent -FilterHashtable @{LogName='Application'; Level=2} -MaxEvents 20 | Where-Object Message -match 'argus'
Get-MpThreatDetection | Where-Object Resources -match 'cloudmonitor'                      # 被安全软件拦
Get-ScheduledTask | Where-Object {$_.TaskName -match 'argus|cloudmonitor'}
```
**判定**：无 Resource-Exhaustion、无 Defender 命中、无计划任务干预。

### 3.4 连通性

```powershell
(Invoke-WebRequest http://100.100.100.200/latest/meta-data/instance-id -UseBasicParsing -TimeoutSec 5).Content
Test-NetConnection metrichub-cn-guangzhou.aliyun.com -Port 80 -InformationLevel Detailed
Test-NetConnection cms-cloudmonitor.aliyun.com -Port 443
Test-NetConnection open.cms.aliyun.com -Port 80
```
**判定**：`TcpTestSucceeded : True`；`open.cms` 为 False 不影响上报（同 Linux 结论）。

### 3.5 卸载重装

```powershell
# 卸载
Stop-Service argusagent -Force
& "C:\Program Files\Alibaba\cloudmonitor\uninstall.bat"
# 或：控制面板 → 卸载「云监控插件」

# 重装：控制台 → 主机监控 → 实例 → 安装/升级插件
# 或在实例内用云助手执行下发命令后，验证：
Get-Service argusagent
Get-ChildItem "C:\Program Files\Alibaba\cloudmonitor\local_data\logs\*.log" | Sort LastWriteTime -Desc | Select -First 3
```

## 4. 在控制台确认恢复

1. **云监控控制台 → 主机监控 → 主机列表**，找到 `BaomiServer`，
   看「插件状态 / Agent 状态」列 → **运行中**。

3. 命令行核对（等价于控制台）：

```bash
aliyun cms DescribeMonitoringAgentStatuses --InstanceIds '["i-7xve8cs4d301hag56zxb"]'
```

返回里 `"Status": "running"` 即成功；`"Status": "stopped"/"install_fail"` 需继续排查。

## 5. 根治：放宽阈值 + 看门狗（2026-11-15 已实施）

**根本矛盾**：自保护阈值 `io read speed >= 256KB/s` 对这台机器太低。
一次 `next build`、一次 `cp -a frontend`、一次 chroma 全量加载（447MB）都能到几 MB/s，
连续 4 次 15 秒采样超限就自杀 —— 也就是说**每次部署都可能顺手把云监控干掉一次**。
`totalStartCount` 当时已是 7，说明这类重启反复发生。

### 5.1 先更正一条旧结论

早先的判断「阈值编译在二进制里、`conf/` 下没有自监控项」**是错的**。
`local_data/conf/agent.properties` 里注释着一整套自监控键，取消注释即生效：

| 键 | 默认 | 含义 |
|---|---|---|
| `agent.resource.io.read.speed.limit` | 262144 | 读速上限，**单位是字节/秒** |
| `agent.resource.io.write.speed.limit` | 1048576 | 写速上限，同上 |
| `agent.resource.cpu.limit` | 0.5 | CPU 上限（单核比例） |
| `agent.resource.memory.limit` | 200 | 内存上限 MB |
| `agent.resource.fd.limit` | 300 | 打开文件数上限 |
| `agent.resource.exceed.limit` | 4 | **连续**超限几次自杀 |
| `agent.status.resource.count` | 4 | 24 小时内累计几次后**不再拉起** |

**单位坑（必看）**：这个键填的是**字节/秒**。实测填 `20480` → 日志打印 `[>=20.00KB/s]`，
即 20480 字节 = 20KB。想要 20MB/s 必须填 `20971520`。填错方向相反（会比原来紧 12 倍）。

**验证方式**：agent 每 15 秒在 `argusagent.log` 打印一次生效阈值，直接读数即可，不用猜：

```bash
grep -a "self_monitor" /usr/local/cloudmonitor/local_data/logs/argusagent.log | tail -1
# io read speed=0.000KB/s[>=20480.00KB/s 0/8]   <- 括号里就是生效值
```

### 5.2 本机已应用的配置（`ops/cloudmonitor/agent.properties.append`）

```
agent.resource.io.read.speed.limit=20971520    # 20MB/s，事故峰值 3.3MB/s，留 6 倍
agent.resource.io.write.speed.limit=20971520
agent.resource.exceed.limit=8                  # 连续 8 次才自杀
agent.status.resource.count=8                  # 24h 累计 8 次才拒绝拉起
```

追加前**必须确认原文件末尾有换行** —— 原文件末行 `cms.module.tcp=true` 没有换行，
直接 `cat >>` 会把注释粘上去，使该键的值变成 `true# ===== ...`。

### 5.3 看门狗（`ops/cloudmonitor/argus-watchdog.{sh,service,timer}`）

每 5 分钟判定一次，四态：`service 非 active` / `父进程没了` / **父进程在但子进程没了**
（就是 resourceCount 闸住的形态）/ 上报文件超过 15 分钟没更新。健康时只写一行 `OK`，不碰服务。

```bash
install -m 0755 argus-watchdog.sh /usr/local/bin/
install -m 0644 argus-watchdog.service /etc/systemd/system/
install -m 0644 argus-watchdog.timer   /etc/systemd/system/
systemctl daemon-reload && systemctl enable --now argus-watchdog.timer
systemctl list-timers argus-watchdog.timer          # NEXT 必须有值
COOLDOWN=0 /usr/local/bin/argus-watchdog.sh         # 手动试跑
tail -5 /var/log/argus-watchdog.log
```

行为：`[OK] healthy` / `[ACT] reason=child_missing ... -> stop, reset latch, start` /
`[RECOVER]` / `[SKIP] cooldown` / `[SKIP] paused`。

**维护期暂停**：`touch /etc/argus-watchdog.disabled`，做完 `rm` —— 否则你手动停服务，
5 分钟后会被它顶起来。

**两个写脚本时必须踩住的坑**：

1. `pgrep -f "bin/argusagent -d"` 会把**外层 shell 包装层**也数进去（`bash -c "...bin/argusagent -d..."`
   的 cmdline 含同样字符串），父进程数虚高。必须锚定行首：`pgrep -fc "^$BASE/bin/argusagent -d"`；
   核对进程总数用 `pgrep -cx argusagent`（按进程名，不受 cmdline 影响）。
2. 改计数不能只 `systemctl restart`，必须先 `stop` -> 改写 `agent.status` -> `start`，
   否则父进程在启动瞬间读到的还是旧计数。

### 5.4 实测的四条分支（2026-11-15 09:48~09:51）

| 注入的故障 | 看门狗日志 | 结果 |
|---|---|---|
| 健康 | `[OK] healthy active=active parent=1 child=1` | 不动服务 |
| `resourceCount` 顶到 8 再重启（**与原事故同形态**：只剩 1 个进程、日志打印 `disabled because of resourceCount exceed`） | `[ACT] reason=child_missing` -> `[RECOVER] child=1`，7 秒恢复 | 计数归零、进程 2 个、采集恢复 |
| 刚恢复过再跑一次 | `[SKIP] cooldown 23s < 600s` | 不反复打死服务 |
| `last-send-cms.txt` 改成 20 分钟前 | `[ACT] reason=report_stale_1200s` -> `[RECOVER]` | 假活也能救 |

### 5.5 另外两个可选项（未实施）

1. `deploy.sh` 前后各 `cloudmonitorCtl.sh restart` —— 代价 15 秒数据缺口，
   在阈值已放宽到 20MB/s 之后没必要了。
2. 提工单让阿里云把默认 `io read` 阈值从 256KB/s 提高 —— 治的是**所有**实例的同类误杀。

## 6. 仍未解决时的升级路径

1. 保留证据：`agent.status`、`agent.status.bak_*`、`argusagent.log`、
   `argusagentd.log`、`VERSION`、`dmesg -T | grep -i oom` 输出。
2. 提工单时附：`instance-id`、`region`、Agent 版本与 commit、
   `=> will exit` 那一行原文、`resourceCount exceed for ...` 原文。
   本次这两个字符串足以让阿里云判断为"自保护触发"，比描述"插件挂了"有效得多。
3. 兜底：先用**云监控的 ECS 无 Agent 指标**（CPU/内存由 hypervisor 采集，不需要插件）
   维持基本告警，别让监控空窗。
