# 并发承载测试报告 2026-10-20

**目标**：今晚 21:00 前支撑 200+ 人同时在线。本文回答三件事——现在能不能撑住、
瓶颈到底在哪、要改什么。

**结论先说**：**框架层能撑，而且余量很大；真正的风险不在 Web 层，在 LLM 并发与
"200 人同时发问"这一个峰值场景。** 压测数据、瓶颈定位、按优先级的修改建议见下。

---

## 一、压测方法（先讲清楚数据是可信的）

| 项 | 内容 |
|---|---|
| 工具 | `tools/loadtest_concurrency.py`（httpx 异步并发，自带注册/登录拿 Cookie） |
| 被测服务 | 本地 `uvicorn main:app`，数据目录隔离到 `.loadtest/data` |
| 机器 | 本机（Windows），非 ECS——**绝对值仅代表本机，趋势可迁移** |
| 口径 | `health`（纯框架）/ `me`（JWT 鉴权 + 查库）/ `login`（PBKDF2 200k 轮） |

### 为什么不用 ab / wrk

被测的是带 Cookie/JWT 鉴权、每条请求都会摸一次 SQLite 的接口。ab 不会自己注册登录，
也不区分 401/429/500 的语义，测出来的 RPS 好看但没用。

### 踩到的坑：单进程压测脚本会先饱和

第一次用**单个 Python 进程**打 200 并发，结果是"并发越高、吞吐越低"：

| 并发（单进程生成） | RPS | p50 | p95 |
|---|---|---|---|
| 20 | 684 | 13.6 ms | 95 ms |
| 50 | 316 | 91 ms | 547 ms |
| 100 | 196 | 162 ms | 2271 ms |
| 200 | 138 | 495 ms | 5168 ms |

**吞吐随并发下降**是生成器饱和的特征，不是服务端顶不住。单进程 asyncio 受 GIL 限制，
200 个 task 互相抢一个事件循环。所以脚本加了 `--processes`，把总并发拆到多个独立进程，
才是真的 200 并发压力。**下面所有"可信数据"都是 4 进程 × 50 并发。**

---

## 二、可信数据：200 并发下的实际表现

每个场景持续 8 秒，200 并发（4 进程 × 50），**全部 0 错误**。

| 场景 | uvicorn worker | 请求数 | RPS | p50 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|
| `GET /health` | 1 | 8261 | **1034** | 108 ms | 654 ms | 2142 ms | 3064 ms |
| `GET /api/auth/me/` | 1 | 5582 | **693** | 251 ms | 399 ms | 1781 ms | 1955 ms |
| `GET /health` | 4 | 8033 | 996 | 126 ms | 734 ms | 1208 ms | 1816 ms |
| `GET /api/auth/me/` | 4 | 8421 | **1050** | 121 ms | 678 ms | 1012 ms | 1766 ms |

**读法：**

1. **鉴权接口 4 worker 比 1 worker 提升 52%**（693 → 1050 RPS），p99 从 1781 ms 降到
   1012 ms（-43%）。说明多进程确实在吃多核。
2. **`/health` 在 1 worker 和 4 worker 下都卡在 ~1000 RPS**——这不是服务端上限，
   是**压测机生成能力**的上限（4 个进程合计约 1000 RPS）。所以 health 的真实天花板
   **高于** 这个数，只是本机测不出来。
3. **0 错误、0 超时**：200 并发下没有一个 5xx、没有连接失败。

### 换算成"200 人在线"够不够

| 假设 | 需要 RPS | 余量 |
|---|---|---|
| 200 人，每人 10 秒一次操作 | 20 | **50 倍** |
| 200 人，每人 5 秒一次操作 | 40 | **25 倍** |
| 200 人，每人 1 秒一次操作（几乎不可能持续） | 200 | 5 倍 |

**所以：只要不是"200 人同时发问"，Web 层今晚完全够用。**

### 登录成本（单独说，因为它最容易打满 CPU）

`POST /api/auth/login/` 走一次 PBKDF2-SHA256（20 万轮），实测单次 **75~100 ms CPU**：

- 单核每秒最多约 **10~13 次**登录
- 200 人**同时**登录 → 约 **15~20 秒**才能全部登录完（会排队，但不会失败）
- 压测中很快出现 429，是**按用户名的 10 次/分钟限流在生效**（撞库防护），不是故障

**开学/活动开场那几分钟如果 200 人同时点登录，会明显变慢但不会挂。** 若这几分钟不可接受，
把打开登录页做"错峰提示"或者在网关侧限速排队，比调低 PBKDF2 轮数更安全。

## 三、瓶颈在哪（按真实影响排序）

| # | 瓶颈 | 证据 | 影响 |
|---|---|---|---|
| 1 | **LLM 并发 / TPM 上限** | 未在本机压测（需真实 API Key，会烧钱） | 200 人同时发问 = 200 条 SSE 流同时挂在上游，撞 DeepSeek 的并发与 TPM 限制，表现为"转圈很久才出字" |
| 2 | **SSE 长连接占位** | 每条形如一次请求占一个 worker 处理槽直到流结束 | 不是 RPS 问题，是**并发连接数**问题；4 worker 下理论上限受 worker 数量与事件循环影响 |
| 3 | **`RATE_PER_MINUTE` 在多 worker 下失效** | `core/quota.py` 是**进程内**字典 | workers=4 时实际限流是 10×4=40 次/分钟/人，限流强度悄悄变小了 4 倍 |
| 4 | **每次 `quota.hit` 都点查一次 users** | `_is_admin()` 按 uid 反查用户名 | 只有配了 ADMIN_USERNAMES 时才触发；管理员操作频繁时是额外 IO |
| 5 | 同步端点在 anyio 线程池里跑 | 默认 40 线程上限 | 已把 `/health`、`/api/config/defaults` 改成 `async def`（正确性修正）；但实测被生成器上限掩盖，未观察到收益 |
| 6 | SQLite 多进程写竞争 | WAL + `busy_timeout=5000` 已配 | 4 worker 下写会排队，读不受影响；用户量大时应把写集中到 worker 进程 |

## 四、修改建议（按优先级，今晚能做的）

### P0（今晚做，直接决定 200 人体验）

1. **uvicorn 起 4 个 worker**
   ```bash
   uvicorn main:app --host 127.0.0.1 --port 8000 --workers 4
   ```
   实测鉴权吞吐 +52%、p99 -43%。需要同步改 `deploy.sh` 与 `systemd/agent-hub-backend.service`。
   ⚠️ 注意：改了 workers 之后，**进程内限流的实际强度会变成 10×N**（见 P1-3）。

2. **给 LLM 调用加并发闸**（当前**没有**，这是 200 人同时发问时唯一会真正拖垮体验的点）
   ```python
   # 全局一个信号量，超出的请求排队而不是一起打上游
   _llm_sem = asyncio.Semaphore(config.LLM_MAX_CONCURRENCY)  # 建议 32~64
   ```
   建议把 `LLM_MAX_CONCURRENCY` 做成环境变量，先按上游账号的并发限额设。

3. **SSE 端点的超时与断开要能回收**：客户端中途关页面时，流要立刻停、上游请求要取消，
   否则一次"200 人同时点开又关掉"会留下 200 个幽灵请求继续烧 token。

### P1（本周做，防"越扩越乱"）

4. **限流改成共享状态**：`quota.hit` 的进程内字典在多 worker 下不再全局生效。
   最小改法是把"每分钟计数"搬到 SQLite（和每日用量同一个库），或用 Redis。
5. **`_is_admin` 加缓存**：uid→username 的映射缓存 60 秒，避免每请求一次点查。
6. **压测脚本进 CI**：`tools/loadtest_concurrency.py --mode health --concurrency 50 --processes 2`
   作为冒烟门槛，防止以后某次改动把 p95 拉高一个数量级。

### P2（有余力再做）

7. **同步端点逐步改 async**：现在 `api/sessions.py`、`api/hybrid.py`、`api/feedback.py`
   里大量 `def` 端点走线程池。并发再上一个量级时，线程池（默认 40）会成为新的排队点。
8. **HTTP/2 与 SSE 的关系**：nginx 侧已经给 SSE 单独 location 并关缓冲（`https/agent-hub.conf.template`），
   保持 HTTP/1.1，不要为了"更快"给 SSE 开 http2。

## 五、今晚 21:00 前的判断

| 问题 | 回答 |
|---|---|
| 200 人同时**在线**（浏览、翻会话、偶尔提问） | ✅ **能撑**，Web 层余量 25 倍以上 |
| 200 人**同时发问**（同一分钟集中提问） | ⚠️ **会排队**。上游 LLM 是瓶颈，不是本项目；必须靠 P0-2 的并发闸"体面地排队"，而不是一起打爆 |
| 200 人**同时登录** | ⚠️ 约 15~20 秒消化完（PBKDF2 成本），不会失败 |
| 需要加机器吗 | 不需要。先按 P0 改配置与并发闸 |

## 附：复现方式

```bash
# 1. 起服务（数据隔离）
set DATA_DIR=.loadtest/data
python -m uvicorn main:app --host 127.0.0.1 --port 8123 --workers 4

# 2. 200 并发、4 个生成器进程
python tools/loadtest_concurrency.py --base-url http://127.0.0.1:8123 \
    --mode all --concurrency 200 --processes 4 --duration 15 \
    --json-out .loadtest/result.json
```
