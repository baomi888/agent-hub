## 0. 一页纸：结论、边界与任务分配

### 0.1 结论

1. **方向是对的，但需要改三个说法。**
   - “受控词表”应是**共享的元数据层**，同时约束文档主题和用户画像；现在两边是两套词，继续各管各的，偏置仍然是错的。
   - “lambda 表达式”不适合承载词表。lambda 是代码，不是数据；同义词每加一个就要改代码、发版，非代码人员无法维护，还有 `eval` 安全风险。正确形态是**词表数据 + 匹配器**，lambda 只保留给极少数上下文例外规则。
   - “避免误生成其他检索路径”不能靠替换词实现。规范化只改“检索用词”，路由仍由现有 `_pick_mode` / 混合编排决定；要控制路径请单独加 `route_hint`，不要把两件事混在一个按钮里。
2. **“用户点击后确认”是这套方案里最有价值的部分，应保留并强化。** 必须是“预览—逐词接受/拒绝—再发送”，不能静默改写。用户看到的原文、发送的历史、检索用的标准词要分开存。
3. **先做确定性的“标准词替换”，不要在这一步引入 LLM 自由改写。** 点击按钮时最多允许一次“历史补全”LLM 调用；词表匹配本身必须离线、可复现、毫秒级。
4. **第一阶段不要碰检索链路。** 先做“词表 + 匹配器 + 预览接口 + 高亮 UI”，用金标集证明替换准确率，再开灰度接检索。否则一旦答错，分不清是词表错、匹配错还是召回错。

### 0.2 建议先做 / 暂不做

| 先做 | 暂不做 |
|---|---|
| 首批 3 个学科、100~200 个标准词 | 全学科大而全的词表 |
| 别名 + 反例（must-not-replace） | 只收同义词、不收反例 |
| 确定性匹配器（最长匹配、保护片段） | 用 lambda 逐词硬编码 |
| 预览接口 + 逐词确认 + 高亮 | 点击后直接静默改写并发送 |
| 聊天接入前先跑 50~100 条金标集 | 没有评估就直接全量上线 |
| 文档 `topics` 映射到 `term_id`（不重嵌入） | 为了词表重建整个向量库 |

### 1.2 当前实际数据流

```text
上传文档
  → 解析 / 递归切分 500+50
  → （每个来源一次 LLM）抽自由 topics → metadata["topics"]="|t1|t2|"
  → 向量化 + BM25 索引

用户提问
  → （有历史时）LLM 改写 → 向量 + BM25 → RRF → 过滤 + 字面 MMR
  → （有画像时）按 topics 子串重合做距离偏置
  → 拼 prompt → 生成答案
  → 回答结束后异步抽 0~3 个用户画像标签

现状：没有“增强提示词”按钮，也没有用户可见/可确认的查询改写 UI。
```

### 1.3 四个结构性缺口

1. **词表不对齐**：文档主题是自由文本，用户画像是受控 30 词；两边靠子串碰运气，必然一半命中、一半漏掉。
2. **标签只参与排序，不参与查询规范化**：用户问“OS 的进程调度”，检索词仍是“OS”，BM25 和向量都吃不到“操作系统”这个词面收益。
3. **没有中间层**：改写发生在服务端内部，用户看不到改了什么，出错只能重问；也无法把“用户不接受某个替换”沉淀成词表改进信号。
4. **没有版本与审计**：词表目前是代码常量，改一次要发版；无法回答“这次检索用的是哪版词表、谁批准的”。

## 2. 目标与非目标

### 2.1 目标

- 建立一份**共享受控词表**：文档主题、用户画像、查询规范化都用同一套 `term_id`。
- 用户点击按钮后，得到一份**确定性的标准词替换预览**：哪些词被替换、为什么、置信度多少。
- 用户逐词确认后，**只把标准词用于本次检索**；展示、历史、标题、画像抽取仍用原文。
- 在不增加热路径 LLM 调用、不明显增加延迟的前提下，提高召回准确率和可解释性。
- 让非代码人员可以独立完成“收词—审核—裁决—验收—运营”的闭环。

### 2.2 非目标

- 不做通用 LLM 改写器；不让模型在点击时自由重写整句。
- 不用主题标签做硬过滤（抽错标签会直接漏召回）。
- 不改变 `_pick_mode` 的路由规则；不在这个功能里“顺带”切检索路径。
- 不为了词表重建向量索引；文档主题是 metadata，可以映射，不需要重新 embedding。
- 不把用户画像标签拼进查询文本；画像只用于消歧和软偏置。

## 3. 受控词表设计

### 3.1 三层结构

```text
领域 Domain（如：操作系统、考研数学）
  └─ 标准词 Canonical（如：进程调度、泰勒公式）
       └─ 别名 Alias（如：调度器、进程切换、Taylor expansion）
```

- **标准词**是检索和展示的唯一口径，必须有稳定 `term_id`，不能拿中文名当主键（改名会断引用）。
- **别名**是用户可能说出的表面形式，包含：中文别称、英文、缩写、常见错写、教材不同译法。
- **反例**（negative alias）是“看起来像、但不能替换”的词，必须显式维护，例如“数学分析”不能因为含“数学”就被替换成“数学”。

### 3.2 词表条目字段（即“元数据”）

| 字段 | 必填 | 说明 |
|---|---|---|
| `term_id` | 是 | 稳定 ID，如 `os.process_scheduling`，一旦发布不改 |
| `canonical` | 是 | 标准词，建议 ≤6 个汉字 |
| `domain` | 是 | 所属领域，用于首批范围控制和匹配过滤 |
| `parent_id` | 否 | 上位词，支持“操作系统 → 进程调度” |
| `definition` | 是 | 一句话定义，供审核和 UI tooltip 使用 |
| `aliases` | 是 | 别名列表，`|` 分隔；至少 1 个 |
| `negative_aliases` | 否 | 禁止替换的片段/上下文 |
| `scope` | 是 | `global` / `domain` / `kb`；v1 先做 global+domain |
| `status` | 是 | `draft` / `reviewed` / `published` / `deprecated` |
| `version` | 是 | 词表版本号，检索缓存要带 |
| `updated_by` / `reviewed_by` | 是 | 审计；非代码人员也可署名 |
| `examples` | 否 | 2~3 条真实问法，验收用 |
| `notes` | 否 | 歧义裁决、来源、反对意见 |

### 3.3 治理规则（必须写进流程，否则词表一定会烂）

1. **一个别名在一个 scope 内只能指向一个标准词。** 若指向多个，标记 `ambiguous`，默认不自动替换，只在 UI 里让用户选。
2. **通用词不许做自动替换目标**：“数学”“方法”“问题”“系统”这类词单独出现时不做替换，除非有领域限定或上下文规则。
3. **标准词只增不删，废弃用 `deprecated`。** 删除会让历史 `query_plan` 无法解释。
4. **双人复核**：新增/修改标准词至少两人签字；歧义词必须留裁决记录。
5. **版本化发布**：每次发布生成 `vocab_version`；检索缓存、日志、`query_plan` 都要带版本。
6. **反例优先**：审核表里“不能替换”的优先级高于“能替换”；没有反例的词表不算合格。
7. **来源可追溯**：每个别名要记录来源（真实问法/文档标签/AI 候选/人工补充），方便以后判断是否过时。

### 3.4 冷启动：AI 生成候选 + 人工审核

推荐的冷启动顺序：

1. **先用现有资产做种子**：30 个 `USER_PROFILE_TAGS` + 文档 `topics` 导出 + 真实问题高频 n-gram。
2. **AI 只做候选生成**：让模型输出“标准词候选 + 别名 + 可能的反例”，不直接发布。
3. **人工审核三件事**：
   - 这个别名是否真的同义（不是上下位、不是相关但不同）；
   - 这个替换在用户 KB 语境下是否安全；
   - 有没有反例（更长词、否定句、跨领域歧义）。
4. **第三人裁决**：歧义、跨学科、影响面大的词，由教研负责人做最终结论。
5. **发布 v1 后冻结**：先跑金标集，不通过不进产品。

> 非代码人员不需要理解向量、BM25、RRF；他们只需要对“这个词换成那个词，用户会不会觉得被曲解”负责。这是本报告任务划分的核心边界。

## 4. 查询规范化：匹配器设计（替代 lambda 硬编码）

### 4.1 为什么不是 lambda

| 用 lambda 承载词表 | 用词表数据 + 匹配器 |
|---|---|
| 每加一个同义词都要改代码、走发版 | 改 CSV/后台，热加载或下次发布生效 |
| 非代码人员无法维护 | 教研/运营可独立维护 |
| 规则散落在代码里，无法审计“谁改了什么” | 有 `status/reviewed_by/version` 审计 |
| 动态 `eval` 有安全风险 | 只读数据，无执行风险 |
| 测试要覆盖每条 lambda | 金标集统一回归 |

lambda 可以保留的位置：**极少数上下文例外**，例如“OS 只在计算机类 KB 中替换”“苹果只在求职/公司语境替换”。这些规则应注册在规则表里、有单测、由代码人员维护；不要让它成为词表的主体。

### 4.2 匹配流程（确定性，无 LLM）

```text
输入 question
  1. 归一化：全角→半角、大小写、连续空白、去掉不可见字符
  2. 保护片段：公式、代码块、引号内原文、数字+单位、URL、文件名
  3. 多模式匹配：Aho-Corasick / Trie，按“最长优先”扫描
  4. 冲突处理：
     - 同一起止位置多个候选 → 取最长
     - 仍有多个 → 标记 ambiguous，不自动替换
     - 命中 negative_alias / 保护片段 → 跳过
  5. 生成 segments：原文段 + 替换段，保留原始 offset
  6. 返回 enhanced + edits + ambiguous + vocab_version
```

关键点：

- **中文没有空格边界**，不能 `str.replace("数学", "数学分析")`；必须最长匹配 + 保护片段。
- **只替换命中 span**，保留否定词、数量词、比较方向、标点。例如“不是操作系统”只替换“操作系统”，不能把“不是”吃掉。
- **宁可少替换，不可错替换**。置信度不够就进 `ambiguous`，让用户点选。
- **同一次点击最多替换 N 个词**（建议 8 个），超过就提示“问题里标准词较多，建议拆分提问”，避免整句被改得面目全非。
- **确定性**：同一输入 + 同一 `vocab_version` 必须得到同一结果；匹配器不调用 LLM。

### 4.3 示例与反例（金标集必须覆盖）

| 输入 | 期望 | 说明 |
|---|---|---|
| `OS 的进程调度` | `操作系统 的进程调度` | 别名 `OS` → 标准词；保留“的” |
| `泰勒展开怎么用` | `泰勒公式 怎么用` | 别名 `泰勒展开` → 标准词 |
| `数学分析中的极限` | **不替换“数学”** | 反例：更长词优先，禁止子串误伤 |
| `苹果的发布会` | 标记歧义，不自动替换 | 水果/公司；需要领域或用户选择 |
| `不是操作系统的问题` | `不是操作系统 的问题` | 只替换术语，不改否定 |
| `操作系统原理` | 整体命中更长词，不拆成“操作系统”+“原理” | 最长优先 |
| `Python 的 GIL` | `Python 的全局解释器锁` | 缩写展开；若词表未收录则保持原样 |
| `帮我对比 TCP 和 UDP` | 两个词都替换/标歧义 | 多词替换；保留“和” |

### 4.4 性能与降级

先校正一个预期：**标准词替换不会让 HNSW/向量检索本身变快**。它的主要收益是词面召回更准、BM25 更容易命中、可解释性更好；速度收益只来自“确定性匹配不调用 LLM”和“命中标准词后可能用更小 top_k”。不要把“提速”当成主卖点。

- 词表加载后编译成自动机，常驻内存；10 万级别名、100 字查询，目标 P95 < 30ms。
- 词表版本变更时重建自动机；旧版本请求继续用旧自动机，避免半途切换。
- 匹配器异常 → 返回原文 + 空 edits，**绝不阻塞发送**。
- 不引入网络调用；点击按钮的唯一可选网络调用是“历史补全”（见第 6 节），且必须可关闭。

## 5. “增强提示词”交互与接口

### 5.1 建议改名

“增强提示词”容易被理解成“让 LLM 把问题写得更好”，和实际功能（把口语词替换成资料库标准词）不一致。建议：

- 主标签：**校准检索词** 或 **标准词替换**
- 副文案：`把“OS”这类说法换成资料库里的标准词，只影响本次检索`

如果产品坚持用“增强提示词”，至少加副文案，避免用户以为整句会被重写。

### 5.2 用户流程

```text
输入问题
  → 点击“校准检索词”
  → 后端返回预览（原文 + 替换建议 + 歧义项）
  → 用户逐词接受/拒绝；可展开看定义
  → “应用并发送” / “只用原文发送”
  → 聊天请求携带 query_plan；展示仍是原文
  → 回答后可“查看本次检索词”并撤销下一次
```

硬性要求：

- **不自动发送**；不自动替换用户输入框里的文字。
- 用户修改输入框后，旧预览立即失效。
- 预览里明确写“原文不会被修改，只影响本次检索”。
- 任何替换都可撤销；撤销后回到原文检索。
- 词表没有命中时，明确显示“没有可替换的标准词”，不要让按钮看起来坏了。

### 5.3 高亮语义（不能只靠颜色）

| 类型 | 视觉 | 非颜色提示 | 交互 |
|---|---|---|---|
| 高置信替换 | 绿色背景 + 实线下划线 | 前缀标签“标准词” | 点击可拒绝，恢复原文 |
| 待确认/歧义 | 琥珀色背景 + 虚线下划线 | 图标“?” + “待确认” | 点击展开候选，选择或保留原文 |
| 历史补全 | 蓝色下划线（不填充） | 标签“来自上文” | 可展开看补全依据 |
| 被替换的原文 | 灰色删除线（对比视图） | 标签“原文” | 仅在“对比”开关打开时显示 |

补充要求：

- 对比度满足 WCAG AA；色盲模式下仍能靠下划线/图标/标签区分。
- 每个高亮段有 `aria-label`，例如“已将 OS 替换为操作系统，可撤销”。
- 键盘可 Tab 到每个替换项，Enter 切换接受/拒绝。
- 移动端不挤压输入框；预览面板可折叠。

### 5.4 接口契约

#### `POST /api/query/enhance`

请求：

```json
{
  "question": "OS 的进程调度",
  "sid": "s_123",
  "kb_id": "kb_xxx",
  "mode": "auto",
  "use_history": true
}
```

响应：

```json
{
  "original": "OS 的进程调度",
  "enhanced": "操作系统 的进程调度",
  "vocab_version": 3,
  "segments": [
    { "type": "edit", "start": 0, "end": 2, "before": "OS", "after": "操作系统",
      "term_id": "os", "canonical": "操作系统", "confidence": 0.98,
      "kind": "alias", "default_action": "apply" },
    { "type": "text", "text": " 的进程调度" }
  ],
  "ambiguous": [],
  "history_rewritten": false,
  "latency_ms": 4
}
```

约定：

- `segments` 是前端渲染的唯一事实来源；不要只给 `enhanced` 字符串，否则前端无法稳定高亮。
- `default_action` 只有 `apply` / `suggest`；`suggest` 必须用户点选后才进入 `enhanced`。
- `kind`：`alias` / `abbreviation` / `typo` / `history`；UI 文案不同。
- `vocab_version` 必返；聊天请求要原样带回。
- 失败降级：`200` + `enhanced=original` + `edits=[]` + `error_code`，不要 5xx 阻塞用户。

#### 聊天请求扩展

在 [ChatRequest](file:///c:/biancheng/agent-hub/api/chat.py#L297-L326) 增加：

```python
query_plan: dict | None = Field(
    default=None,
    description="用户在预览面板确认后的检索计划；只影响检索，不影响展示/历史"
)
```

`query_plan` 结构：

```json
{
  "original": "OS 的进程调度",
  "enhanced": "操作系统 的进程调度",
  "vocab_version": 3,
  "accepted_edits": [
    { "term_id": "os", "before": "OS", "after": "操作系统" }
  ]
}
```

服务端规则：

| 用途 | 用哪个文本 |
|---|---|
| 向量/BM25 检索 | `query_plan.enhanced`（若版本匹配） |
| 展示、会话历史、标题 | 原始 `question` |
| 拼给 LLM 的回答 prompt | 原始 `question`（可附一行“本次检索标准词：…”） |
| 用户画像抽取 | 原始 `question` + 答案，避免标准词污染画像 |
| 检索缓存 key | `(collection, enhanced, top_k, owner, vocab_version)` |

版本不匹配（用户预览后词表发布了新版本）：回退到原文检索，并在 SSE 里发一条轻量提示，不要静默用旧计划。

### 5.5 与 SSE 的关系

- 预览阶段是普通 HTTP，不走 SSE。
- 聊天阶段可选增加 `query_plan_applied` 事件，回传实际使用的标准词，便于前端在回答卡片上显示“本次检索词”。
- 该事件不是必需；如果不想改事件协议，可把 `applied_terms` 放进 `done` 事件。

## 6. 与历史改写、用户画像的关系

### 6.1 建议顺序

```text
用户原问题
  → （仅追问时）历史补全：把“它/那这个”补成完整问题
  → 受控词表规范化：把口语/别名换成标准词
  → 得到检索用 query
  → 向量 + BM25 → RRF → 过滤/MMR → 生成
```

为什么不是反过来：历史补全可能引入新的口语词，先补全再规范化，才能保证最终检索词干净。

### 6.2 不要让两套改写互相打架

- 现有自动改写 [rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L690-L759) 在聊天链路里还会跑。若请求带 `query_plan`，**跳过自动改写**，以用户确认的计划为准。
- 若用户在预览后修改了输入框，前端丢弃 `query_plan`，聊天回退到现有自动改写。
- 预览接口里的 `use_history=true` 才会做历史补全；补全结果用 `kind:"history"` 标出，和词表替换区分开。
- 历史补全仍要受现有 `needs_rewrite` 约束，并建议收窄误触发（短问题 + 指代词，而不是所有 ≤8 字问题）。

### 6.3 画像只做消歧和软偏置

- 画像标签应逐步迁移到 `term_id`，和词表共用 ID。
- 画像可用于：`OS` 在计算机类 KB/计算机画像用户下优先映射到“操作系统”；`苹果` 在求职/公司语境下优先映射到“苹果公司”。
- 画像不可用于：把用户画像标签直接拼进查询文本；这会引入用户没问的主题，造成召回漂移。
- 所有画像消歧都必须可解释：预览里显示“因为你的资料库/画像偏向计算机，OS → 操作系统”，并允许用户拒绝。

## 9. 验收指标

### 9.1 离线（M1 必须）

- **替换精确率** ≥ 95%：所有自动/建议替换中，正确替换占比。
- **反例误替换率** = 0：金标里 20 条“必须不替换”的 case 不允许被替换。
- **别名召回率** ≥ 85%：金标中期望被识别的别名，实际识别比例。
- **歧义标记率**：歧义词必须进 `ambiguous`，不允许静默选一个。
- **延迟** P95 < 30ms（100 字查询，10 万别名）。

### 9.2 在线（M2/M3）

- 预览点击率、**接受率** ≥ 70%、逐词拒绝率、编辑率。
- 零结果率相对基线下降；`Recall@k` 不下降（有金标时）。
- 答案忠实度不下降；用户“答非所问”反馈不上升。
- 热路径 LLM 调用次数不增加（历史补全除外，且可关闭）。
- 降级次数、P95 端到端延迟增量 < 100ms。

### 9.3 上线门槛

- M1 金标全过 + 代码评审通过 → 才能开 M2。
- M2 内部试用接受率达标 + 无 P0 事故 → 才能开 M3 灰度。
- M3 灰度指标不降 + 回滚演练通过 → 才能全量。
