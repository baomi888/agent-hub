## 二、P0-3：让 `TOOL_META` 真正生效

**问题**：元数据表早就声明齐了（category / retryable / needs_approval / max_output_chars），
但**没有任何执行路径读它**——声明躺在表里。

**三条守卫**（都不改变模型看到的 schema）：

| 守卫 | 行为 |
| --- | --- |
| 输出截断 | 超 `max_output_chars` → 落盘 `data/tool_outputs/` + 只回前 N 字与路径 |
| 不可重试封禁 | `retryable=False` 的工具失败后，本轮再调**直接拒绝**（不再真的执行） |
| 危险动作审批 | `needs_approval=True` 首次只回「确认串」，参数变了串就变 → 必须重新确认 |

**实现踩坑记录（值得留档）**：原地包装 LangChain 工具两次都失败——
包 `_run` 会被内省签名（`missing 1 required positional argument`）；
包 `func` 会打断 `RunnableConfig` 注入（config 变 None）。
最终用 `StructuredTool.from_function` **重建**工具，`functools.wraps` 保留原签名，
LangChain 的内省与注入完全不变，name/description/args_schema 原样沿用。
`api/chat.py` 的 Agent 路径用 `tool_guard.guard_scope()` 隔离每次执行的封禁状态。

## 三、P0-1：定位移出 system prompt

**问题**：`note = location_note(location)` 同时进了**缓存键**和 **system prompt**。
后果两层：① 图缓存键 = `2 × #城市 × #场景 × #激活集`，32 槽位一多就 LRU 抖动；
② 更贵的是 **system 前缀随城市变化 → KV 缓存命中率 90%→0%**（用户 kv-cache 实验实测）。

**改动**：
- 缓存键去掉 `note`：`key = (bool(has_kb), scene, frozenset(activated))`
- `system_prompt += note` 删除
- 定位改为**合并进最后一条用户消息**（`api/chat.py`），模型仍在回答前看得到，
  位置从头挪到尾。合并而不是追加第二条 `HumanMessage`：部分 chat template 对连续 human 敏感。

## 四、P0-2：上下文压缩（按评审反馈重做安全阀）

### 4.1 骨架

压缩块（稳定前缀）+ 最近 K 轮原文（滚动尾巴），替代 `MAX_HISTORY_TURNS=10` 滑动窗口。
压缩块落 `conversations.compressed_summary`，**增量化**：只追加 `[COMPRESSED-n]` 新段、
不改旧段 —— 评审指出「低频还不够，增量才真正稳前缀」。

### 4.2 评审三条反馈的处置（**这是本轮的核心**）

#### ① 安全阀从"二值回退"改成**分级 L0–L3**，且 L0 零 LLM、冷启动可用

评审指出原方案两个致命问题：安全阀依赖 judged 质量（评估集没建好 = 真空）；
"回退全量"在上下文接近硬顶时会死锁。

| 级别 | 触发 | 动作 |
| --- | --- | --- |
| **L0** | 压缩块丢失硬实体（URL / UUID / 长 hex / 文件名 / 待办关键词） | 有 prev → L1；无 prev → L2 |
| **L1** | L0 失败且存在上一版 | 回退**上一版压缩块**，绝不回全量 |
| **L2** | L0 失败且无上一版 | `keep_turns` 从 6 扩到 12，压缩块只吃更老的部分 |
| **L3** | 压缩后仍超 token 硬顶 | 按预算**硬截断最旧原文**，压缩块保留 |

`L0` 纯正则扫描（`extract_entities`），**零 LLM 成本，冷启动阶段即可生效**。
`conversations` 新增 `compressed_summary_prev` 字段，L1 才有东西可回退。

#### ② 压缩块自身有预算，且超限时**折叠**而非膨胀

`MAX_SUMMARY_CHARS`（默认 4000）/ `MAX_SEGMENTS`（默认 12）双约束。
超限时把最早的段折叠成 `[早期内容已折叠] …` 概述，而不是丢弃——
否则模型会以为更早的对话从未发生（评审说的"新的膨胀源"）。

#### ③ 异步压缩的竞态：`compressed_upto` 乐观锁

`commit_summary(..., expected_upto)` 用 `WHERE COALESCE(compressed_upto,0)=COALESCE(?,0)` 做 CAS，
失败就放弃本轮、下次再试。**`plan_context` 一律以 `compressed_upto` 为准过滤原文**，
只取 `id > compressed_upto`，所以即使压缩未完成也不会出现"压缩块 + 原文"重复。

### 4.3 冷启动压缩器

`extractive_compress`：规则抽取，**零 LLM**。保留首句 + 含实体句 + 末句。
评审说"中文规则提取准确率一般、冷启动又没有 Judge 安全阀"，所以压缩口径刻意保守：
默认 `KEEP_TURNS=6`、压缩块只吃非常老的轮次，把冷启动风险压到最低。
压缩器可注入（`build_compressed_segment(..., compressor=)`），后续接 LLM 摘要不用改调用方。

## 六、未做（**需要你拍板，我没有自行扩范围**）

按评审意见的优先级，以下属于"下一步"，本轮未动：

### 6.1 Stage 0 评估集（评审第 4 条：样本量与验收口径）

- 方案原定 60–100 例；评审指出在 ±9pp 噪声下**检测不了 +3pp 这类小效应**。
- **需你定**：扩到 200–300 例并把验收改成"配对比较置信区间下界不低于 -5pp"，
  还是接受"Stage 0 只排除灾难性劣化（如 -15pp）"？
- 另外建议分层（按轮次长度 / 是否含工具调用 / 是否含关键实体），避免过拟合到短对话。

### 6.2 压缩块接入请求路径

`core/context_compress.py` 已提供 `plan_context()`，但**还没接到 `api/chat.py` 的
五处取历史**。原因：接线会改变每轮喂给模型的上下文形状，属于**行为变更**；
你要求"按方案开发"，而方案把接线列为 P0-2 的最后一步，且需要先确认
"压缩块怎么进 prompt"（放 system 后 / 作为独立消息 / 带 `[COMPRESSED]` 说明）。
**建议**：先按 `[COMPRESSED]` 标记 + system prompt 加一句"这是压缩历史，细节缺失时不要编造"
接一处（Agent 路径）灰度，再铺开五处。

### 6.3 评审的其他建议（未做，按优先级留档）

| 建议 | 为什么没做 |
| --- | --- |
| Stage 1 蒸馏温启动 | 依赖评估集（6.1），先有集再谈 |
| 在线候选优选 / 经验库 | 评审自己的建议是"离线选策略、在线别引 Judge 噪声"；且需先定义 K 个候选来源，属 Stage 2 |
| 工具轨迹进历史 | 方案自己标注"另案处理"，且会显著改变 token 口径 |
| 验收指标分开报（问答轮次 vs 含工具轨迹） | 需真实评估跑数，当前无评估集 |

### 6.4 一个必须说清的边界

本轮 P0-2 **只压缩问答轮次，压的不是 tool results**（`api/chat.py` 只把 user/assistant 转成消息）。
所以验收里的"输入 token 下降幅度"应明确是相对**问答轮次**，不是相对含工具轨迹的完整上下文。
评审第 6 条正是提醒这一点，我把它写进这里，避免后续验收口径打架。
