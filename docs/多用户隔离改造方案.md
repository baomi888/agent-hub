## 〇、结论先说

**能改，而且不用推倒重来。** 你的技术栈（FastAPI + SQLite + Chroma）做多用户是成熟的组合，
业界常见的两种做法都不需要换掉任何一个组件。

真正的难点**不在"加个登录"**，而在两件事：

1. **默认不开放**：现在每个端点都裸着。多用户最容易出事的地方永远是"某个新端点忘了加过滤"——
   所以要做成**默认要求登录、显式放行**（而不是逐个记得去加），这也是本项目历史上反复踩坑的形状；
2. **Agent 工具的入参不可信**：`kb_search` 的 `kb_id` 现在是让模型自己填的，
   多用户之后这就成了一条越权通道（提示注入 → 让你检索别人的库），必须改成由服务端注入。

## 一、业界两种隔离路线（已查证）

| 路线 | 代表做法 | 优点 | 致命点 |
| --- | --- | --- | --- |
| **A · 逻辑隔离**：共享 collection / 共享表，查询时带 `tenant_id` 过滤 | Dify 的 Workspace（每张核心表加 `workspace_id`，ORM 层统一注入过滤）；RAGFlow 的 User / Tenant / UserTenant 三件套 + RBAC | 省资源、好做跨空间共享 | **靠"每层都记得过滤"来保证安全**。过滤写漏一次＝静默泄漏，而且是"返回别人的数据"而不是报错 |
| **B · 物理隔离**：每个租户一套独立 collection / 命名空间 | 主流 FastAPI+Chroma 多租户模板的做法（`tenant_{user_id}` collection） | ① 代码写错只会**查不到**，不会查到别人的；② 查询延迟只随**自己**的语料增长，不随总用户数增长；③ 删用户＝删一个 collection | collection 数量随用户数增长（小规模完全没问题） |

**本项目选 B。** 三条理由都很贴合你的现状：

- 你**没有 ORM**，全是手写 SQL（`core/session.py` 一把 annotations），
  缺少"ORM 层自动注入"这一保护站 ⇒ 逻辑隔离的风险比 Dify 那种项目更高；
- 你现在**已经是一个 KB 一个 collection**（`rag_core.py:261` `kb_{kb_id}`），改成按用户分只是改命名规则，**改动面最小**；
- 参考文章里那句总结值得抄进你的汇报：
  > "最好的多租户架构是让数据泄漏在结构上不可能，而不是依赖过滤器和代码没有 bug。"
  > —— 这句话正是本项目现在的情况的反面：我们目前**连过滤器都没有**。

> 未来如果真要做成产品级，更省心的路线是换 **PostgreSQL + pgvector + Row Level Security**（把隔离下沉到数据库层）。
> 但那是另一个量级的重构，现阶段不必动。

## 二、改造后的数据模型

```
users
  id / username / password_hash / created_at / is_active / role

conversations         ← 现有表，加一列
  owner_id  TEXT NOT NULL            -- 新增
  INDEX(owner_id, updated_at)

kb 归属               ← 逻辑上的表，实际体现在 Chroma collection 名 + json key
  (owner_id, kb_id)
```

**命名规则（这一条是整个方案的支点）**

| 资源 | 现在 | 改后 |
| --- | --- | --- |
| Chroma collection | `kb_{kb_id}` | `kb_{owner}_{kb_id}`（`_ensure_vs()` 一处改） |
| 原始文件目录 | `data/kb_sources/{kb_id}/` | `data/kb_sources/{owner}/{kb_id}/` |
| 内存注册表 | `_PIPELINES[kb_id]`、`_KB_FILES[kb_id]`、`_KB_NAMES[kb_id]` | 全部改成 `(owner, kb_id)` 复合键 |
| 落盘 json | `kb_files.json` / `kb_names.json` 里以 kb_id 为一级 key | 改成 `{owner: {kb_id: ...}}`，或按 owner 拆文件 |
| 会话 | 全表可见 | `WHERE owner_id = ?` |

## 三、认证怎么选（给你三个档）

| 方案 | 依赖 | 适合什么时候 |
| --- | --- | --- |
| **自己写 JWT + bcrypt** | `pyjwt` + `passlib[bcrypt]`（都是现成轮子，各不到 100 行） | **现在**。理解成本最低，作业里讲得清楚 |
| `fastapi-users` | 一个库，自带注册/登录/重置密码/ORM 适配 | 想省事、不在乎多一个重依赖 |
| Keycloak / Supabase Auth / OAuth | 外部服务 | 真上线给别人用时 |

推荐**第一档 + HttpOnly Cookie**：

- 你的前端已经走 Next 的 `/api/*` rewrite ⇒ **同源**，Cookie 天然带上，不用改 CORS；
- Token 别放 localStorage（现在是纯前端无状态，将来会变成 XSS 面）；
- `SameSite=Lax` + `HttpOnly` + 生产环境 `Secure`。

骨架（照着写，别整段复制）：

```python
# core/auth.py —— 关键三件事
pwd_context = CryptContext(schemes=["bcrypt"], deprecated="auto")

def create_access_token(uid: str) -> str: ...          # jwt.encode({"sub": uid, "exp": ...})

def get_current_user(request: Request) -> str:          # 读 cookie → decode → 返回 owner_id
```

## 四、最关键的工程约束：**默认关闭，显式放行**

现在漏数据是"每个都忘了加"，改完之后必须反过来——**用一个 router 级依赖统一兜住**：

```python
# 每个业务 router 都带上这个，个别公开端点再单独豁免
router = APIRouter(dependencies=[Depends(get_current_user)])
```

豁免清单应该短到一眼看完：`POST /api/auth/login`、`POST /api/auth/register`、`GET /api/config/defaults`、`/health`。

> 这条和本项目历史上的教训是同构的：凡是"靠人在每个地方记得写"的规则，
> 迟早会在某次补一个新端点时漏掉一次。**把它变成默认值，就没人能忘。**

另外三条同样要做成默认行为：

- **`source_path()` / `source_dir()` 必须带 owner**（`pipelines.py:270-286`）——路径层再兜一道，防止拼错；
- **`get_or_create()` 改成按 (owner, kb_id) 注册**，接口签名带上 owner，让"忘记传 owner"直接变成类型/参数错误；
- **`kb_search` 工具的 kb_id 由服务端注入**（见下节）。

## 五、Agent 侧的越权面（容易被忽略，但很重要）

今天 `agent/tools.py:20` 的签名是 `kb_search(kb_id: str, query: str, top_k: int = 3)`，
**kb_id 让模型自己填**。单用户时代这无所谓，多用户之后这是一条真实越权通道：
用户喂一段提示词让模型传别人的 kb_id ⇒ 拿到别人的知识库内容。

怎么改（两个都要做）：

1. **工具签名去掉 kb_id**，改成从 LangGraph 的 `RunnableConfig` / `configurable` 里读当前会话绑定的 kb_id
   （参考 `agent/builder.py` 的 `build_agent(kb_id, location_ctx)`，它已经在 `api/chat.py:329` 把 kb_id 传进去了——
   把这个值往下游传一层即可，不要给模型开口子）；
2. **服务端二次校验**：即使拿到了 kb_id，也要校验它属于当前 owner，否则返回"无权访问"。

同一节的 `download_file(url, kb_id)` 也是同一个形状（`:435`），一起改。

## 六、配额与限流（多用户之后必然要补）

一旦对外开放，最现实的损失是**额度被别人烧掉**，所以认证之后立刻要加：

- 每用户速率限制（可按 IP + uid 双键，慢的就是 `slowapi` 或自己写个内存计数器）；
- 每日 embedding 条数 / 问答次数上限（写进 users 表或一张 usage 表）；
- 上传大小与总量上限。

这几项同时也是汇报里"产品化考虑"的加分素材。

## 七、分批落地计划

| 阶段 | 内容 | 工作量 | 产出可见性 |
| --- | --- | --- | --- |
| **P0 · 临时开门禁** | Next middleware 加 HTTP Basic Auth（今天的报告已给方案） | 15 分钟 | 立刻止血，陌生人进不来 |
| **P1 · 账号 + 会话隔离** | users 表 / 注册登录 / JWT cookie / `conversations.owner_id` / 所有会话类端点按 owner 过滤 / 一个登录页 | 约 1 天 | 不同账号看到各自的会话历史 |
| **P2 · 知识库隔离** | collection 命名加 owner / `(owner,kb_id)` 复合键 / 磁盘目录分层 / 现有库迁移到一个初始账号 | 约 1 天（风险最高） | 不同账号看不到彼此的知识库 |
| **P3 · Agent + 配额** | kb_search 服务端注入 kb_id / 每用户限流与用量上限 | 约半天 | 越权通道关闭、账单可控 |
| **P4 · 协作能力**（可选） | 公共知识库、分享链接、RBAC（RAGFlow 那种 tenant 角色模型） | 按需 | 从"能隔离"进化到"能协作" |

**建议顺序 P0 → P1 → P2 → P3**，P1 和 P2 之间先补一个离线回归：
「用户 A 看不到用户 B 的会话 / 知识库」各一条断言（仿照现有 `tests/` 的写法，不联网不花钱）。

**P2 的迁移要点**（这一步最容易翻车）：

1. 先 `pipelines.warmup()` 能枚举出所有现有 collection（`kb_*`）；
2. 一次性迁移脚本把它们全部归到你的账号下（重命名 collection 在 Chroma 里是 `delete + add`，
   或者更简单：**只改注册表映射**，磁盘上的旧 collection 名保持不动、用一张映射表记录 `kb_id → 实际 collection 名`）；
3. 迁移前先备份 `chroma_db/` 与 `data/kb_sources/`。

## 八、每一阶段都能拿去汇报的话术

> 现有 Demo 是单用户共享态（无身份维度），所有访客共享同一份会话与知识库。
> 面向产品化的改造采用**物理隔离**而非标记过滤：每个用户拥有独立的 Chroma collection 命名空间、
> 独立的文件目录，会话与文件清单在存储层按 owner 分区；认证采用 JWT + HttpOnly Cookie，
> 所有业务路由**默认要求鉴权**、仅显式豁免公开端点；Agent 工具的知识库 ID 由服务端注入而非模型提供，
> 关闭提示注入导致的越权检索通道。
> 设计参考：Dify 的 Workspace 隔离模型、RAGFlow 的 User/Tenant 角色模型，以及社区主流的
> "每租户独立 collection"（而不是共享 collection + 元数据过滤）做法——后者在过滤条件写错时会静默泄漏，
> 且查询延迟随总用户数增长。
