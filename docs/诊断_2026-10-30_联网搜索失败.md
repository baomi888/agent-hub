# 诊断：联网搜索失败（agent-hub，2026-10-30）

- 诊断人：web-search-doctor（只读排查，未改任何代码、未提交、未推送）
- 代码基线：`main` / `HEAD=0ecc803`，工作树干净
- 环境：本机无 `.env` ⇒ `config.SERPER_API_KEY == ""`；未联网、未探测生产 `8.163.62.25`
- 结论：**已定位一个 100% 复现的代码级根因**（昨天的「安全修复」提交 `cf49ef2` 引入），
  与 10-29 的「模式入口收敛/执行前路由」改造无关。生产侧还需用户回答 3 个问题才能闭环（见 §6）。

## 1. 一句话结论

`agent/tools.py::web_search` 里有一处 **Python 名字遮蔽（shadowing）**：
函数在 2026-10-29 的 `cf49ef2`（安全修复）中新增了形参 `config: RunnableConfig`，
但函数体内第 135 行仍写着 `from core import config`，**后者把形参 `config` 覆盖成了 `core.config` 模块**；
随后第 150 行把 `config`（此时已经是模块对象）传给 `_configurable()`，触发
`AttributeError: module 'core.config' has no attribute 'get'`，被第 174 行的兜底 `except Exception`
吞掉，最终返回「联网搜索暂时不可用，请稍后再试或换个问法。」

影响：**只要配了 `SERPER_API_KEY`，Agent / 混合引擎里每一次 web_search 都 100% 失败**——Serper 请求已经发出（照样扣额度）、结果被丢弃，用户永远拿不到搜索结果。没配 key 时则走另一句「联网搜索需要 SERPER_API_KEY…」。两句都像"网络/配置问题"，所以线上看起来像联网不通。

> 任务卡里「绑库时根本不可能走 web_search」的假设**不成立**（见 §4.2），
> 真正把 web_search 打死的是上面这处遮蔽，而不是路由改造。

### P1-A 路由/模式让"该联网的问题"根本到不了 agent（同一现象的另一条来源）

10-29 路由改造本身没有"禁止 web_search"，但 auto 的实际去向是概率性的：

| 场景 | 去向 | 会不会调 web_search | 证据 |
|---|---|---|---|
| `mode=rag`（用户选「检索」） | RAG，无工具循环 | **不会** | `api/chat.py:330-331`、`api/chat.py:1303-1339` |
| `auto` + 绑库 + 模型判 `llm` | **强制改判 rag** | 不会 | `core/router.py:173-176` |
| `auto` + 绑库 + 模型超时/异常/非 JSON/闸满 | fallback = **rag** | 不会 | `core/router.py:146-148`、`core/router.py:218-230` |
| `auto` + 绑库 + 模型判 `rag` | rag | 不会 | `core/router.py:168-172` |
| `auto` + 未绑库 + 模型判 `rag` | 改判 agent | 会（但撞 P0-A） | `core/router.py:170-172` |
| `auto` + 模型判 `agent`（含绑库） | agent，绑定 5 工具 | 会（但撞 P0-A） | `core/router.py:177`、`agent/builder.py:244-257` |
| `auto` + 规则判 `flow` | hybrid，内置工作流 execute 节点是 agent | 会（但撞 P0-A） | `core/router.py:208-210`、`api/chat.py:336-337`、`hybrid/store.py:39-58`、`hybrid/agent_engine.py:113-117` |

实测（伪造路由 LLM，不联网）：
```text
未绑库 + 模型判 agent: route=agent source=model
绑库   + 模型判 agent: route=agent source=model      ← 绑库时 agent 仍可达
绑库   + 模型判 rag  : route=rag
绑库   + 模型判 llm  : route=rag （reason=绑库强制检索（原判 llm））
绑库   + 模型超时/异常: route=rag source=fallback
未绑库 + 模型判 rag  : route=agent
```
结论：
1. **"绑库时根本不可能走 web_search"不成立**——`_post_check` 只改写 `llm→rag`，`agent` 原样保留；
2. 但对绑库用户，路由器**任何一次失败都会落到 rag**（2s 超时等，`core/config.py:233-236`），
   且模型对"搜一下/查一下XX"这类说法未必判 agent ⇒ 表现为"我问它搜，它翻我的资料/直接答"。
3. 这类情况**不会报错**，只是没有工具调用，用户同样会描述成"联网搜索失败/没搜"。

### P1-B Serper 真实故障不可观测（`core/serper.py` 吞异常、零日志）

## 4. 任务卡假设 vs 代码事实（以代码为准）

1. **「昨天的模式入口收敛/执行前路由改造让该联网的问题到不了 agent」——不成立（至少不是本次直接原因）。**
   - `auto` 在非 flow 时仍可返回 `agent`（`core/router.py:177`），且 `agent` 分支完整保留（`api/chat.py:1160-1284`）；
   - 绑库时只是 `llm` 被强制改判 `rag`（`core/router.py:173-176`），`agent` 不受约束；
   - 真正打死 web_search 的是同一天、另一个工作流的 `cf49ef2`「安全修复」（§2 P0-A）。
2. **「绑库时根本不可能走 web_search」——不成立。** 实测 `build_agent(has_kb=True)` 绑定工具 =
   `['kb_search','web_search','calculator','get_weather','download_file']`，`web_search` 在列；
   绑库只是让 **rag/llm 两条分支**（本来就无工具）更容易被选中，且路由失败时回落 rag。
3. **「core/serper.py 异常吞掉返回 None」——属实，但不是本次主因。** 它是"无法观测"的原因；
   本机即使没有 key、不联网，也能用伪造 httpx 100% 复现主因（因为崩溃发生在 HTTP 成功之后）。
4. **「本机无 key 无法验证失败表现」——可验证。** 伪造 `httpx.Client.post` 返回 200 + organic 即可复现
   "请求成功但工具返回暂时不可用"；伪造失败响应可复现另一句文案。全程离线、零费用。

## 6. 复现步骤

### 6.1 本机离线（无 key、不联网，已实测）

把下面代码存成临时脚本（仓库外，如 `%TEMP%\diag.py`），在仓库根用 venv 运行：

```python
import sys, httpx; sys.path.insert(0, ".")
from core import serper, config
config.SERPER_API_KEY = "fake-key"          # 模拟生产已配 key
req = httpx.Request("POST", "https://google.serper.dev/search")
ok = httpx.Response(200, request=req, json={"organic": [
    {"title": "A", "snippet": "s", "link": "https://example.com/a"}]})
class Fake:
    calls = 0
    def post(self, *a, **k):
        Fake.calls += 1
        return ok
serper._client = Fake()
from agent.tools import web_search
print(web_search.invoke({"query": "量子计算最新进展"}))
print("POST 次数 =", Fake.calls)
```

实际输出（2026-10-30 实测）：

