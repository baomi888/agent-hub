## 二、后端本轮改了什么（逐条，含"要不要前端配合"）

### 2.1 新增：思考流 `event: reasoning`（前端可选实现）

**为什么会有这个事件**：原来的模型客户端是 `ChatOpenAI`，而 LangChain 官方文档明确写着它
不转发第三方 provider 的非标准字段（`reasoning_content`）。所以后端换用了 `ChatDeepSeek`，
并把思考增量单独发成一个事件——**不换的话，就算配置了思考模型，思考内容也会在框架层被静默丢弃**。

```
event: reasoning
data: {"text": "先看清问题"}          ← 增量（delta），前端自行累加

event: done
data: {..., "reasoning": "完整思考文本"}   ← 未启用思考模型时为空串 ""
```

**前端要做的**（照 DeepSeek 网页版的行为）：

1. 收到第一个 `reasoning` → 建思考块、展开、开始流式追加
2. 收到第一个 `token` → 思考块自动收起（**用户手动展开过就别再自动收**）
3. 收到 `done` → **用 `done.reasoning` 覆盖本地累加值**（防丢帧），状态置完成

**三个必须注意的点**：

- ⚠️ **这个事件可能完全不出现**。只有服务端 `.env` 配了 `DEEPSEEK_REASONER_MODEL` 才有；
  未配置时事件序列与改造前**逐字一致**。**不要把"等 reasoning"写进必经流程**，否则思考块会一直空转。
- ⚠️ **思考内容不落库**。刷新页面后历史消息里没有思考块（只在本轮流里给）。
  如果你要"刷新后仍能看到"，需要后端再加存储与读取接口 —— **这需要你先提需求，我这边没做**。
- 视觉理解路径（图片问答）不发 `reasoning`；Agent 路径的中间过程走既有的 `tool` / `status` 事件。

> 详细版见 `docs/AI模块-20261013/06-思考流接口说明-给前端.md`。

### 2.2 新增：人工节点真挂起 + 恢复接口（前端**需要**实现，否则功能不可达）

这是本轮最需要前端配合的一项。

**之前的问题**：`human` 节点是骨架实现——**自动通过**并写 `approved`。也就是说"人工确认"环节形同虚设，
演示时看不出来，真实流程里等于没有审批。现在改成了真挂起。

**新增状态**：`awaiting_human`（**不是终态**，恢复后回到 `running`）

**挂起时后端做了什么**：

- 工作流停在 `human` 节点，把续跑锚点与上下文**整体落库**（与模式切换同一套快照机制）
- `done` 事件里的 `run_id` 此刻指向一条 `status=awaiting_human` 的执行记录
- 执行轨迹里留下一条 `human_intervention` 事件，带人工提示语全文

**前端据此要做**：用 `run_id` 查执行记录，看到 `awaiting_human` 就显示"等待人工确认"，
并把 `human_intervention` 事件里的 `prompt` 渲染出来 + 给"通过 / 拒绝"两个按钮。

### 2.3 新增接口：`POST /api/hybrid/runs/{run_id}/resume`

```
POST /api/hybrid/runs/{run_id}/resume
Body: { "decision": "approve" | "reject", "note": "可选，人工意见，会进轨迹日志" }

200 → {
  "ok": true,
  "run_id": "...",
  "decision": "approve",
  "status": "running",
  "resume_from": "gate",          // 续跑锚点（被挂起的节点 id）；reject 时为 null
  "context": { ... },             // 完整任务上下文快照
  "workflow_id": "..."
}
```

**错误码**：

| 码 | 含义 | 前端处理 |
| --- | --- | --- |
| 404 | 执行记录不存在 | 该 run 不属于当前用户 |
| 409 | 当前状态不是 `awaiting_human` | 重复恢复 / 任务已结束，应刷新轨迹 |
| 409 | 快照里没有挂起点 | 数据异常，提示重新发起任务 |
| 400 | `decision` 不是 approve/reject | 前端传参错误 |
| 500 | 执行快照损坏 | 提示重新发起任务 |

**⚠️ 必须区分 `switch` 与 `resume`** —— 这是两个不同语义的接口，别混用：

| | `POST .../switch` | `POST .../resume` |
| --- | --- | --- |
| 语义 | **改道** | **唤醒** |
| 适用状态 | `running`（任务还在跑） | `awaiting_human`（任务已停下） |
| 触发方式 | 写指令，引擎在**安全点**消费 | 立即生效，写回标记并落库 |
| 常见错误 | 409 任务已结束 | 409 状态不是 awaiting_human |

**还差最后一跳（需要你确认方案）**：`resume` 返回了 `context` + `workflow_id`，
但**它不直接继续跑** —— 挂起时原来那条 SSE 连接已经结束，服务端没有可推送的通道。
所以续跑需要**前端再开一条新 SSE**（`POST /api/chat/stream`，`mode=hybrid` + 同一 `workflow_id`）。

我倾向的做法是：后端提供"**从挂起点续跑**"的显式参数，前端 resume 成功后拿它重开流。
**要不要这么做、参数叫什么名字，请你定** —— 定了我这边改，改动只在 `api/chat.py` 与 `api/hybrid.py` 两处。

### 2.4 契约不变、但前端要知情的两处内部加固

这两项**不改接口形状**，写在这里是因为它们会影响你们排查问题时的预期：

- **`shared` 加了容量上限**：单个值超过 8000 字符会**落盘并在 `shared` 里留一个预览指针**
  （形如 `[值 N 字符已落盘：路径 — 需要时读取该文件]`）。所以前端在轨迹面板里
  看到这种字符串是**正常现象**，不是后端把内容弄丢了。
- **任务目标 `goal` 变成只读**：起跑后不允许改。改目标会让执行轨迹失去可复现性
  （回放时不知道当时的目标是什么）。确需变更走 `override_goal(reason)` 并留痕。
  前端如果做了"编辑目标"的入口，**要么去掉，要么改成新建任务**。

### 2.5 修掉的两个后端 bug（前端只是在受害）

- 入库时抽主题标签的代码把模型客户端构造写在了 `try` 外面 ⇒ **没配 Key 的机器上建库直接 500**。
  这也是我本机跑全量测试时收集阶段就崩的原因。
- 同一形状的问题在"抽取用户画像标签"里也存在，一并修了。

**对前端的影响**：如果你们在没配 Key 的环境上试过"上传文档建库"并遇到 500，那不是你们的问题，已修。

## 四、验收：怎么自己确认后端是对的

沿用你已经在用的那套（`tools/check_hybrid_contract.sh`）——**我把它扩了 3 项新契约，并实跑通过**：

```bash

  bash tools/check_hybrid_contract.sh
```

**本轮实跑结果（本地 8132）**：

```

--- 错误语义 ---                          PASS ×2（不存在 404 / 内置只读 404）
--- 校验 ---                              PASS ×2（非法定义 400 / 条件语法 400）
--- ★ 字段名一致性 ---                    SKIP ×1（库里一个工作流都没有，需至少 1 条数据）
--- 规则列表语义 ---                      PASS ×2（builtin / cooldown_seconds）
--- 本轮新增契约（OpenAPI 权威核对）---    PASS ×3（resume / switch / hybrid）
--- 思考流前置条件 ---                    INFO（未设 DEEPSEEK_REASONER_MODEL，不出现 reasoning）
====================================
通过 12 项，失败 0 项
```

**新加的三项为什么用 OpenAPI 核对而不是直接打端点**：
`resume` 需要"一条真实处于 `awaiting_human` 的执行"才可能返回 200，拿不到就只会看到 404/409 ——
**那不代表端点不存在**，直接打会误报（这正是你脚本注释里说的"404 却报字段缺失"那个坑）。
服务端 `/openapi.json` 是后端自己生成的路由清单，免登录、不会误报。

> 另外：脚本里新增的思考流那一项只做"**是否具备条件**"的判断，不硬造一次真实模型调用
> （会烧 token 且需要 Key）。生产环境建议在 `.env` 里显式设 `DEEPSEEK_REASONER_MODEL` 再验。
