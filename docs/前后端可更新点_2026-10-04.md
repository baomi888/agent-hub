## 一、后端可更新点

### ★★★ 1. 联网导入向空库写入必然 500 —— 「联网建库」这条功能实际 100% 不可用

**文件**：`kb/importer.py:66-67`（`import_url`）、`kb/importer.py:222-224`（`download_and_index`）
**根因**：`kb/rag_core.py:409-416` 的 `get_or_open()`；**正确写法**在同一文件 `:266-274` 的 `_ensure_vs()`

```python
# importer.py:66-67
pipe.get_or_open()                 # ← 只在「库里已有片段」时才构造 Chroma
pipe._vs.add_documents(chunks)     # ← 空库时 _vs 是 None，这里直接炸
```

```python
# rag_core.py:409-416  get_or_open
def get_or_open(self) -> None:
    if self.peek() > 0:            # ← 新建的库 count()==0，这一支根本不走
        self._vs = Chroma(...)

# rag_core.py:266-274  _ensure_vs（build_index 用的，没有就创建）
def _ensure_vs(self):
    if self._vs is None:
        self._vs = Chroma(...)     # ← 构造函数内部会 ensure_collection
    return self._vs
```

**实测**（本轮跑的真实代码，非推测）：

```
create_kb('自动化测试库_20261004') → exists()=False、_vs=None、peek()=0
p.get_or_open(); p._vs.add_documents([])
  → AttributeError: 'NoneType' object has no attribute 'add_documents'
```

**为什么这是"整条功能不可用"而不是"偶发失败"**：前端 `page.tsx:374-402` 的 `webImport` 流程
恰好就是「先建空库，再导入」：

```tsx
const { kb_id } = await api.createKb(kbName);   // :380  建出来的库是空的
...
const r = await api.importUrl(kb_id, url, ...); // :385  必然 500
```

而失败发生在 `add_documents` **之前**，Chroma 里的 collection 始终没被创建 ⇒
**重试 N 次失败 N 次**，不存在"第二次就好了"。叠加 `page.tsx:396` 那句
`showToast("success", "联网建库完成：成功 0 / 10")`，用户看到的是"成功 0/10"配一个绿色成功提示。

**副产品**：`importer.py:55-56` 在抛错**之前**已经把原始文件写进了 `data/kb_sources/{kb_id}/`，
但 `add_file_records` 没执行 ⇒ 每尝试一次留一份**孤儿文件**。
10-03 第 3 条在 upload 路径修了这个（先整批校验再落盘 + 失败 `cleanup`），**import 路径没跟上**。

**怎么改**（2 行 + 10 行）：

1. `importer.py:66` 和 `:222` 两处 `pipe.get_or_open()` → `pipe._ensure_vs()`；
2. `import_url` 的写文件移到 `kb_lock` 内、失败时 `os.unlink(dest)`；
3. 顺手把 `api/kb.py:394-401` 的 500 改成 400 + 中文原因（现在是 `detail=str(e)` 直接吐英文栈）。

**验证方式**：`curl -X POST http://<host>/api/kb/create -d '{"name":"t"}'` 拿 kb_id，
再 `POST /api/kb/{kb_id}/import-url` 抓任意一个 URL，应当 200 且 `chunks > 0`。

### ★★★ 8. 参数输入框 `onChange` 不 clamp —— 清空即变 0，是后端 500 的直接入口

**文件**：`frontend/src/components/chat/Field.tsx:28-33`

```tsx
<input
  type="number"
  value={value}
  min={min}          // ← 只是 HTML 属性，手动输入不拦
  max={max}
  onChange={(e) => {
    const v = Number(e.target.value);
    if (!Number.isNaN(v)) onCommit(v);   // ← 完全没有 clamp
  }}
/>
```

两个坑叠在一起：

1. **`Number("") === 0`**。用户想改数字、习惯性全选删掉准备重输 ——
   输入框一空，`onCommit(0)` 立刻把参数打成 0。下一次上传/重建就是 `chunk_size=0`，
   后端 `RecursiveCharacterTextSplitter` 抛英文 `ValueError` → 500。
2. `min` / `max` 只约束步进箭头和表单提交校验，**键盘敲 99999 照样收**。

`ChatArea.tsx:605-624` 三个 Field（topK / chunkSize / chunkOverlap）**全部中招**，
而 `topK=0` 会被后端 `ChatRequest.top_k: gt=0` 挡成 400（还行），
`chunkSize=0` / `chunkOverlap ≥ chunkSize` 则会一路走到 500 英文栈。

**怎么改**（4 行，两种写法选一）：

```tsx
onChange={(e) => {
  const raw = e.target.value;
  if (raw === "") return;                       // 空串别提交，保留原值
  const v = Number(raw);
  if (Number.isNaN(v)) return;
  onCommit(Math.min(max, Math.max(min, v)));    // clamp 到 [min, max]
}}
```

或者更稳：改成 `onBlur` 才 commit，`onChange` 只改本地草稿字符串（顺带解决"输入中就被截断"的手感问题）。

主区只渲染最后 20 条，往上滚什么都没有 —— **看起来就像历史被吞了**。
10-03 第 18 条提过，当时说"依赖后端先返回 `has_more`"。

**本轮补充一个不依赖后端的最小改法**（半天工作量 vs 一天）：

```ts
const truncated = detail.messages.length < (detail.message_count ?? 0);
```
把这个布尔值存进 `useSessions` 的返回值，列表顶部渲染一条
`仅显示最近 10 轮 · 共 N 条` 的分隔条。**至少让用户知道"是被截了，不是丢了"**，
真正的"加载更早"再等后端加 `?before_id=` 分页。
