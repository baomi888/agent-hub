## 0. 结论（先看这里）

1. **现行代码里真正的"工具选择框"只有一个**：对话顶栏的「能力」弹层（`frontend/src/components/ChatArea.tsx:534-573`，数据 `frontend/src/components/chat/constants.tsx:117-152`）。四张卡是「查资料 / 联网搜索 / **数学计算** / **查天气**」——用户说的"算数、天气"就是从这来的。它看起来像"选工具"，实际点击**只做两件事**：把 mode 切回 `auto` + 预填一句示例问题，并不会真的"选择某个工具"（`ChatArea.tsx:379-383`）。
2. 另有 3 处会让"算数/天气"出现在用户视野里，但都不是选择框：设置页只读工具表（`settings/page.tsx:391-410`，显示英文工具名 `calculator`/`get_weather`）、回答气泡里的工具调用记录（`chat/Bubble.tsx:123-157`，中文"数学计算/天气查询"）、以及**旧备份/旧部署版本**的欢迎页四宫格（`frontend/src/_backup/...`，已排除出类型检查与构建，不是现行代码，见 §8）。
3. 现行欢迎页**没有**四宫格：只有 3 条文字示例、3 张日更入口卡、4 个一次性动作胶囊（`ChatArea.tsx:611-694`）。任务卡里说的「欢迎页四宫格」实际存在于 `_backup` 与旧部署，或指顶栏能力弹层——**删除时不要按"欢迎页四宫格"去找**。
4. 「模式选择」= 底部输入框上方的三段式切换条 `自动 / 检索 / 纯对话`（`ChatArea.tsx:828-852`，常量 `constants.tsx:11-15`）。它和「能力」弹层是**同一个 `mode` state** 的两个入口：能力卡点击会 `onModeChange("auto")`（`ChatArea.tsx:380`）。
5. 删「模式选择 + 自动档」分两种做法，改动量差一个数量级：
   - **方案 A（推荐，只删界面入口，后端 auto 路由保留）**：前端 **6 个文件、18 个必改点**（另有 5 处 CSS/注释清理页；若连 `types.ts`/`sse.ts` 的字段收敛也算上，共 8 个文件）；后端 **0 个必改点**。请求继续带 `mode:"auto"`，行为等价于今天默认状态，风险最低。
   - **方案 B（连"自动/模式"契约一起从代码删除）**：在 A 之上再加 **后端 10 个点 + 测试/脚本 5 处**，合计约 **33 个改动点**；会切断 `auto → 规则/模型路由 → hybrid 工作流` 这条链，牵动模板 `recommended_mode`、`done.mode`、`/flow` 页面与历史文档，**不建议在"清理选择框"这一轮做**。
6. 最大兼容性风险（B 方案）：**`auto` 不是一个孤立按钮，它是整个执行前路由（`core/router.py`）的入口**。删掉 auto 之后，后端不再有"该检索还是该调工具还是该直接答"的判断，等于回退到 10-29 之前的固定策略；同时 `done.mode`、hybrid 三事件、模板 `recommended_mode`、旧 `localStorage.mode`、旧 `?mode=` 链接会同时变成死字段。若只删前端而保留后端，则没有这个问题。
7. 最容易被误伤的迁移陷阱：字符串 **`auto` 在项目里是"一词三义"**——聊天模式 `auto`、字号档位 `fontScale:"auto"`（跟随系统，`lib/consolePrefs.ts:19-26`）、配额桶 `auto`（定时任务，`app/settings/page.tsx:52`、`app/delegate/page.tsx:696`）。任何"按值 grep 删除 auto / 清理 localStorage"的动作都会误伤后两者。

- **不传 `mode` 时后端默认就是 `auto`**（`api/chat.py:280`），所以"删掉模式选择"最省事的做法是前端写死/省略该字段，后端一行都不用动。

## 4. 删除改动点清单

> 两个方案应对两种理解：
> - **方案 A**：删掉「模式选择条」与「能力弹层（含算数/天气卡）」，即"用户不再选模式、也看不到自动档"；`auto` 降级为系统内部默认值，不再对用户可见。
> - **方案 B**：连 `auto` 这个概念（请求字段、后端 `_pick_mode`/`router`、`done.mode`、模板推荐模式）一起删。
>
> 如果用户原话「将自动删去」指的是"把自动这个档位删掉"，做完方案 A 就已满足；方案 B 属于另一轮架构改造。

## 9. 与 10-29 既有决策的关系（需要负责人拍板）

`docs/改造报告_2026-10-29_模式入口收敛与执行前路由.md:12` 的结论是：

> 用户界面上只剩「自动 / 检索 / 纯对话」，智能体与混合不再作为选项暴露。

而本次诉求是"把对话模式选择删掉、自动也删去"，方向相反。两种做法对应不同产品语义：

| | 现状（10-29 决策） | 方案 A（本次可做） | 方案 B（彻底） |
|---|---|---|---|
| 用户能选什么 | 三档 | 什么都不用选 | 什么都不用选 |
| 后端如何决定路径 | 显式档位直通；auto 走 router | 永远 auto → router | 固定单一策略（需另定） |
| 改动范围 | — | 前端 18 点 | 前后端约 33 点 + hybrid/flow |
| 风险 | — | 低 | 高（回滚 10-29 设计） |

建议：**先做方案 A**（满足"删选择框、界面不再出现算数/天气/自动"），把方案 B 作为独立决策（因为 B 会删掉自动路由这个核心能力，需要产品/后端一起定"没有自动之后，遇到该检索的问题怎么办"）。
