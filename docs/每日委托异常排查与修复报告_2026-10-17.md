# 每日委托「[object Object]」异常：排查与修复报告

日期：2026-10-17　　范围：`api/delegate.py`、`service/daily.py`、`frontend/src`（委托 / 错误处理 / SSE）　　状态：**已修复，回归通过（246 passed）**

---

## 一、摘要

| 项目 | 结论 |
| --- | --- |
| 现象 | 委托页点「创建」后，页面底部弹出纯文本 **`[object Object]`** 提示气泡，看不出错在哪 |
| 直接根因 | 前端提交的 body 用 `session_id` / `instruction`，后端 `DelegationIn` 只认 `deliver_sid`（**必填**）/ `prompt` ⇒ 每次创建都被 **422** 挡下 |
| 放大根因 | FastAPI 422 的 `detail` 是**数组**，前端 `new Error(body.detail)` 把数组转成字符串 ⇒ `[object Object]` |
| 影响面 | ①「创建委托」100% 失败；②「编辑指令 / 换投递会话」静默不生效；③**任何**端点的 422 都只能显示 `[object Object]`（错误信息全被吃掉） |
| 修复 | 后端输入字段加法兼容 + 默认会话解析 + kind 归一；前端统一错误体降级 + 委托契约漂移对齐 |
| 回归 | `pytest tests` → **246 passed / 19 subtests**（基线 229，+17 条新增）；`tsc --noEmit` 0 error |

## 二、取证链（异常是怎么被定位的）

1. **截图证据**：委托页右侧是创建表单（投递到会话 = 用户询问建议、生成指令 = 给我每天都生成一次复盘、长度上限 = 600、创建后立即启用 = 开），底部气泡是纯文本 `[object Object]`；表单注脚写着「同名会返回 409」。⇒ 异常发生在**创建提交**的失败路径上，且错误文案被"对象字符串化"吃掉了。

2. **前端提交的 body**（`frontend/src/app/delegate/page.tsx:285-300`）：

   ```ts
   const body = {
     name, kind, schedule,
     session_id: form.sessionId || null,   // ← 后端要的是 deliver_sid
     kb_id,
     instruction: form.instruction.trim(), // ← 后端要的是 prompt
     tone, max_chars, enabled,
   };
   ```

3. **后端请求模型**（`api/delegate.py:74-95`）：`prompt` 默认空串、**`deliver_sid: str = Field(...)` 是必填**，且模型里没有 `session_id` / `instruction` 的入口。⇒ 缺 `deliver_sid` ⇒ 校验失败。

4. **复现确认**（离线，直接构造模型）：

   ```
   DelegationIn(**前端body)  →  ValidationError: deliver_sid Field required
   ```

5. **为什么用户只看到 `[object Object]`**：FastAPI 的 422 响应体是

   ```json
   {"detail": [{"type": "missing", "loc": ["body", "deliver_sid"], "msg": "Field required"}]}
   ```

   `detail` 是**数组**。前端 `api.ts::httpError` 当时执行 `detail = body.detail || detail` 后 `new Error(detail)`，而 `String([{...}])` 在 JS 里就是 `"[object Object]"`（已用断言钉住，见第五节）。

6. **副产品发现**：同一次对照里还发现同模块的 3 处契约漂移（`kind`、`run` 响应键、UI 边界值，见第三节 5-8），它们的失败表现与本次异常**完全一样**——都是 422 之后变成一坨 `[object Object]`。

## 三、修复清单

### A. 后端 `api/delegate.py`

| # | 改动 | 位置 | 为什么 |
| --- | --- | --- | --- |
| 1 | 请求模型用 `AliasChoices` 同时接受两套字段名：`prompt`/`instruction`、`deliver_sid`/`session_id` | `DelegationIn`(74)、`DelegationPatch`(97) | 此前**只有输出** (`_out`) 做了加法兼容，**输入**没做 ⇒ 前端一发 `session_id` 就 422。这是本次异常的直接根因 |
| 2 | `deliver_sid` 改为可空，新增 `_resolve_deliver_sid()`：给了 sid 就校验归属（否则 404，不泄露存在性）；没给（前端「默认会话」发的 `null`）就落到**该用户最近更新的会话**；一个会话都没有则 400 | `_resolve_deliver_sid`(139)，create(约 221)、update(274) | 直接透传 `null` 会存下一条**永不投递**的委托——用户只会觉得「怎么又没收到」却查不出错。现在要么真投得出去，要么给一句能看懂的话 |
| 3 | `_validate_kind` → `_normalize_kind()`，把历史别名 `study` 归一成规范值 `study_plan` | `_normalize_kind`(118)、`_KIND_ALIASES`(54) | 前端 `DelegateKind` 曾写成 `study`，后端 `KINDS` 与规范文档（`规范/02_核心数据结构定义.md` 第 9 节）都是 `study_plan`。为一个枚举别名丢 422 不划算 |

> 兼容性：`_out()`（输出）未改动，`deliver_sid` / `prompt` / `delegation_id` 等字段名全部保留 —— 遵循本项目「委托 API 输出加法兼容」的既有约定。

### B. 前端：统一错误体降级（消除 `[object Object]` 的**根**）

| # | 改动 | 位置 | 为什么 |
| --- | --- | --- | --- |
| 4 | 抽出共用 `detailToMessage(detail, fallback)`：字符串原样用；**数组**按 `字段: 原因` 拼装；其余对象退化成 JSON；都没有则回落 `HTTP <status>` | 新建 `frontend/src/lib/errors.ts` | 这是"让用户看懂"的**根治点**：只要它还直接 `new Error(对象)`，全站任何 422 都仍是一坨 `[object Object]` |
| 5 | `httpError` 改用 `detailToMessage` | `lib/api.ts:62-84` | 见上。429 的 `retry_after` 提示保留 |
| 6 | `tryRequest` 的 404 分支先判类型再判内容 | `lib/api.ts:146-155` | 原写法 `detail.trim()`：若 404 的 `detail` 是数组会直接抛 **TypeError**（未捕获异常），把一次普通 404 变成崩溃 |
| 7 | `sse.ts` 非 200 分支同样改用 `detailToMessage` | `lib/sse.ts:70` | 同一处缺陷的**流式孪生体**：`/api/chat/stream` 被 422 时也会变成 `[object Object]` |

抽出 `errors.ts` 而非在两处各写一份，是为了避免这两份规则以后各自漂移（项目约定：跨模块复用的工具函数必须提取共用）。

### C. 前端：委托模块契约漂移对齐

| # | 改动 | 位置 | 为什么 |
| --- | --- | --- | --- |
| 8 | `kind` 取值 `study` → `study_plan` | `types.ts` DelegateKind、`page.tsx:37,59`、`consoleDemo.ts` | 与后端/规范对齐。否则选「学习计划」必 400 |
| 9 | 星期下拉 `0=周一 … 6=周日` | `page.tsx:59` WEEKDAYS | 后端 `ScheduleIn.weekday` 是 **0=周一**，前端原来是 `["日","一",…]`（0=周日）⇒ 每周委托**整体错一天**，且列表显示也跟着错 |
| 10 | 预览读 `content` 而非 `text`/`output` | `lib/api.ts:350-356`、`page.tsx:368` | 后端返回的键是 `content`，旧代码读 `text`/`output` 恒为 `undefined` ⇒ 预览弹层永远显示「后端未返回内容」 |
| 11 | UI 边界对齐后端：间隔 ≥60 分钟、长度上限 ≥200、指令框 `maxLength=1000` | `page.tsx:642,740,715` | 原来 UI 各自允许 5 分钟 / 100 字 / 无限长，后端分别要求 `ge=60` / `ge=200` / `max_length=1000` ⇒ 这三种输入都会 422 |

## 五、同类风险全量扫描

### A. 委托模块内（**已修**）

`kind` 枚举、`weekday` 基准、`every_minutes` / `max_chars` 边界、输入字段名、`run` 响应键 —— 全部是"前端契约与后端模型漂移"，且失败表现**都是** `[object Object]`。已在第三节 A/C 一次性对齐。

### B. 「错误体被串化」这一类（**已修**）

| 位置 | 状态 |
| --- | --- |
| `api.ts::httpError`（全站普通请求） | 已修（改走 `detailToMessage`） |
| `api.ts::tryRequest` 的 404 分支（数组上 `.trim()` 会抛 TypeError） | 已修 |
| `sse.ts` 非 200 分支（流式） | 已修 |

已核对**安全**、无需改动的点（避免过度改动）：

- 后端全仓 `HTTPException(detail=...)` 逐一核对，**全部是字符串**；全站唯一的非字符串 `detail` 来源就是 FastAPI 内建的 422 —— 所以 B 里的三处修完，这一类就没有出口了。
- SSE `error` 帧的 `detail` 恒为字符串（`api/chat.py` 里是 `acc.error = describe_api_error(e)` / `str(e)` / f-string），因此聊天页 `String(ev.data.detail)` 不会产出 `[object Object]`。

### C. 定时任务模块（**未修，列为遗留风险**）

扫描 `core/scheduler.py`（6 个 job：`delegate.dispatch` / `delegate.retry` / `report.daily` / `report.backfill` / `housekeeping` / `profile.aggregate`）与 `worker/scheduler.py` 后，发现**委托的日程字段目前只存储、不生效**——这不属于本次"报错可见性"缺陷，但属于委托链路最该补的坑：

1. `service/daily.py:479-509 due_subjects()` 只按 `next_run_at IS NULL OR next_run_at <= now` 挑对象，**完全不看** `freq` / `at` / `weekday` / `every_minutes`。
2. `service/daily.py:550` 派发后固定 `_bump_next_run(did, planned_at + 86400)`（"默认次日同刻"），不是按配置算下一次。
3. `service/daily.py:357-387 save_delegation()` 每次写入都把 `next_run_at` 置 `NULL` ⇒ **任何编辑 / 开关都会让委托在下一个 5 分钟轮询时立刻触发一次**（`delegate.dispatch` 是 `*/5 * * * *`）。

综合 1+2+3 的实际行为：**「每天 21:00」的委托会在创建后 5 分钟内先触发一次，之后按"触发时刻 +24h"重复**，而不是 21:00。截图里历史记录的时间点零散、且同分钟出现多条，与此吻合。

> 建议（列为下一轮，不塞进本次修复以控制爆炸半径）：把 `next_run_at` 的计算抽成 `next_fire_at(schedule, from_ts)`（daily / weekdays / weekly / interval 四支），`_dispatch_one` 改用它替换 `+86400`；`save_delegation` 不再无条件重置 `next_run_at`（仅当 schedule 变化或显式重新启用时才重算）。配套补一组"跨周、跨月、夏令时无影响（固定 Asia/Shanghai）、interval 对齐"的测试。

### D. 其他路由的请求契约（已枚举核对，**无新增 422 风险**）

逐一对照了前端 `api.ts` 全部请求 body 与后端各 router 的 pydantic 模型：

- `sessions`（`SessionCreate` / `SessionUpdate` 同时接受 `title`+`kb_id`）、`kb`（`CreateKbRequest` / `RebuildRequest` / `ImportSearchRequest` / `ImportURLRequest` / `ImportBatchRequest`）、`feedback`（`FeedbackRequest`）、`hybrid`（`WorkflowIn` / `RuleIn` / `SwitchIn`）、`chat`（`ChatRequest`）、`schedule`（`RunNowRequest` / `RetryRequest`）—— **字段名与必填/边界均一致**。
- `top_k` 是唯一有上界的常用参数：前端 UI 限 1~10，后端 `le=TOP_K_MAX(20)`，安全余量充足。
- 唯一残留（**低**，且当前无调用点）：`api.schedule.runNow` / `retry` 声明响应 `{ ok: boolean }`，后端实际返回 `{ accepted, job_key, queued, idem_key }` / `{ retried, run_id, ... }`。属于"没有用到所以没爆"，建议后续定契约时顺手对齐。

## 六、结论与建议

- 本次异常是**两个缺陷叠加**：一个"请求字段名漂移"（造成 100% 创建失败），一个"错误体降级缺失"（把失败原因吃掉，只留 `[object Object]`）。只修其中一个都不算修好：只修漂移，别的 422 仍会是一坨乱码；只修降级，用户会看到"字段必填"却仍创建不了。
- 修复遵循了项目既有约定：委托 API 输入/输出**加法兼容**、不破坏 `deliver_sid`/`prompt`/`delegation_id` 任一既有字段名、不引入新端点。
- 未提交 git（沿用本项目"由用户决定何时提交"的惯例）。
- 建议优先级：**①日程字段落地（C 节）** ＞ ②`save_delegation` 不再无条件重置 `next_run_at` ＞ ③`schedule.runNow/retry` 类型对齐 ＞ ④为 `detailToMessage` 补一个正式的前端单测（目前是临时脚本验证）。
