## 1. 四类查询转换：必要性打分
先定义尺度：**5 = 不做会明显伤核心体验；3 = 特定场景有效、可条件启用；1 = 当前规模不值得**。

| 方法 | 当前状态 | 必要性 | 判断 |
| --- | --- | --- | --- |
| a) 结合历史改写 | 已上线，带触发条件和失败回退 | ★★★★★ | 保留，但触发逻辑要收窄 |
| d) 多查询/多路召回 | 未实现 | ★★★ | 最值得做的“可选扩展”，必须条件触发 |
| c) 退后提示 | 未实现 | ★★☆ | 只适合“零召回/低置信”兜底 |
| b) HyDE | 未实现 | ★★ | 不建议默认开，容易把通用教材说法带进来 |


**a 已经做对了大方向**：[rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L690-L759) 里的 `needs_rewrite` 只在“有历史 + 短问题或含指代词”时触发，失败一律回退原问题，这个“增益不是必需”的定位是对的。

但有三个具体问题值得改：

1. **误触发**：`len(q) <= 8` 就判定为追问，导致“什么是RAG”（6 个字）在有历史时也会白花一次 LLM 调用，还可能被改坏。建议改成“短 **且** 含指代词/省略特征”才触发，或者对“什么是/为什么/如何”这类完整疑问句直接跳过。
2. **没有缓存**：同一个追问每轮都重新改写。可以按 `(question, 最近 N 条历史的 hash)` 做一个小 LRU；否则多轮对话里这次 LLM 调用是纯重复成本。
3. **覆盖不一致**：RAG 和视觉分支走了改写，Agent 模式的 `kb_search` 用的是模型自己生成的 query（[tools.py](file:///c:/biancheng/agent-hub/agent/tools.py#L40-L75)）。Agent 能看到对话历史，通常问题不大，但“追问指代”在工具调用里仍可能丢，后续可以统一。

**为什么 b/c/d 现在不该默认上：**

+ **你们的库是用户自传的学科资料，不是开放域网页**。学生问法通常自带术语；已经上线的 BM25 + RRF 正好补“专有名词/编号/缩写”的词面召回（[rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L1263-L1335)）。查询侧剩下的收益没有教程里那么大。
+ **成本结构不划算**：多查询 = 1 次 LLM + 3 次 embedding + 3 路检索；HyDE = 1 次生成（还要多花 2~4 秒）。你们聊天主链路有 LLM 并发闸，额外调用会和“生成答案”抢额度，200 人同时提问时这是实打实的体验问题。
+ **HyDE 的副作用在小学科库里更明显**：假设答案会生成“通用教材式”的表述，把用户自己资料里的独特说法挤掉，召回可能变“更像教科书”而不是“更像他的笔记”。
+ **无法验证收益**：现在没有评估集，b/c/d 上不上只能靠手感。这一点比选哪个方法更关键。

**如果要做，建议这样落地：**

+ **d 多查询**：只在“首次检索为空 / grounding 为 weak / 问题含‘分别、对比、各自、以及’等多子问题标记”时触发；最多 3 条子查询；复用现成的 `_rrf_merge` 做融合；子查询并行跑（已有 `_embed_pool`）；缓存键用“原问题 + 策略版本”，否则同一问题每次都要重新花 LLM 和 embedding。
+ **c 退后提示**：只生成 1 条更高层问题，和原查询一起走 RRF；只做“零召回兜底”，不要每题都做。
+ **b HyDE**：放在开关后面做小流量实验，假设答案限制在 100~150 字，并且**只对假设答案做 embedding**，不要把原文和假设答案拼在一起；先看评估结果再决定是否保留。

## 2. 检索增强：必要性和实现路径
这里把“检索增强”理解为**召回之后、送进模型之前的上下文增强**，不是“RAG 本身要不要做”。RAG 本身对你们是必要的：产品卖点就是“基于用户自己的资料回答、能指回出处”，换成纯长上下文 LLM 会同时输在成本、延迟和引用可信度上。

真正的问题是：**当前链路的召回已经不错，但“召回出来的东西够不够回答”没有保障**。按性价比排序：

| 优先级 | 增强项 | 改动面 | 预期收益 | 风险 |
| --- | --- | --- | --- | --- |
| P0 | 评估集 + 离线指标 | 只加测试脚本，不动产品 | 让后面所有优化可判定 | 无 |
| P0 | 结构化分块 + 标题路径前缀 | 入库 + 重建索引 | 最高，直接改善召回语义 | 需重新付 embedding |
| P1 | 邻片扩展（句子窗口） | 只在拼 prompt 时做 | 高，修复 500 字切片的上下文断裂 | 需控制 token |
| P1 | 精排（cross-encoder/rerank API） | 候选池后加一段 | 中高，改善 top_k 精度 | 延迟和并发成本 |
| P2 | Corrective RAG 单次重试 | 聊天 RAG 路径 | 中，专门救“低置信”查询 | 多一次检索成本 |
| P2 | 父文档 / 自动合并 | 入库结构 + 新存储 | 视文档结构而定 | 实现复杂 |
| P3 | 逐 chunk LLM 上下文前缀 | 入库时每片一次 LLM | 高但很贵 | 入库成本不可控 |
| P3 | 多向量 / RAPTOR | 重构索引 | 只适合全局总结类问题 | 当前库规模不值 |


**几个关键实现点：**

1. **评估集必须先做**。从真实会话里抽 30~50 条问题，标注“正确来源文件 + 正确片段（chunk_index）”，离线算 `Recall@fetch_k`、`MRR@k`、以及答案忠实度。注意要评估**MMR 之前**的候选池，否则你分不清是“没召回”还是“被 MMR 挤掉”。这一步会直接告诉你 b/c/d 和精排到底值不值得。
2. **结构化分块是当前最便宜的“上下文增强”**。你们现在 `.md` 也走纯文本递归切分（[rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L807-L809)），标题层级完全丢失。可以在 Markdown 上用 `MarkdownHeaderTextSplitter`，把 `文件 > 章 > 节` 作为 `heading_path` 写进 metadata，并在**向量化前**把这段路径拼到正文前面。这相当于零 LLM 成本的 contextual retrieval。PDF 至少拼“文件名 · 第 N 页”。
3. **邻片扩展**比父文档轻得多。检索命中 `(source, chunk_index)` 后，按 `source + chunk_index±1` 从 Chroma 取前后各一片，去重后拼进 prompt。注意：只扩展**送模型的上下文**，不要改 `docs_scores` 本身，否则 `sources` 和 `grounding` 的距离语义会乱。加一个 token 上限（比如原 top_k 内容的 1.5~2 倍）。
4. **精排要算延迟账**。候选池现在是 `top_k × 3`、下限 12（[config.py](file:///c:/biancheng/agent-hub/core/config.py#L78-L122)），精排 12~20 条是合适的。CPU 上的 cross-encoder 在 200 并发下会成为瓶颈，优先考虑 rerank API 或带并发限制的本地 ONNX；必须有超时回退到 RRF/MMR，不能因为精排挂了整条 RAG 挂掉。
5. **Corrective RAG 是比完整 Self-RAG 更现实的选择**。你们已经有 `assess_grounding`（[rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L313-L395)），当它为 `low/none` 时，允许“换一个查询再检一次”，最多一次，然后无论结果如何都进入“资料不足就示弱”的既有路径。这比引入 reflection token 训练便宜得多，也更符合你们的 SSE 交互。
6. **一个容易忽略的点**：`select_diverse` 的“去重”用的是 Jaccard 字面重合（[rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L504-L517)），不是语义 MMR。它能去掉相邻切片的重复，但抓不住“换了说法讲同一件事”的重复。如果后面上精排，可以顺手做“精排后再按向量相似度去重”，比现在更彻底。

## 3. 自动合并的潜力
**它解决的是什么**：自动合并不是“更聪明的切片”，而是“检索到叶子节点后，发现同一个父节点下多个兄弟都命中，就把父节点整体返回”。它同时解决三个问题：

+ 500 字切片把定义、公式、表格切断，单看一片答不完整；
+ top_k 名额被同一章节的相邻碎片占满（现在 MMR 只能缓解，不能恢复缺失上下文）；
+ “总结/对比/列举”类问题需要一章而不是一段。

**对你们的适配度：3.5/5（结构化教材），2/5（任意 PDF）。** 原因是当前入库是扁平结构：只有 `source/page/chunk_index`，没有章节层级（[rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L1082-L1097)）。Markdown/TXT 可以从标题恢复层级；PDF 的标题不可靠，只能按页做窗口，做不了真正的树状合并。

**如果做，建议的设计：**

1. 入库时切两层：叶子 300~500 字，父块 1200~2000 字；叶子带 `parent_id`、`heading_path`；父块正文放独立存储（SQLite/JSON），不要塞进 Chroma metadata（会让 `list_sources` 这类遍历变慢）。
2. 检索先取 12~20 个叶子，按 `parent_id` 分组；满足“同父 ≥2 片命中”或“同父命中比例 ≥50%”就替换成父块；父块上限 2000 字，最多保留 2~3 个父块。
3. 合并后再做去重和 token 预算控制；引用仍然保留叶子的来源/页码，并附 `heading_path`，前端展示会更像“第 3 章第 2 节”。
4. 风险：父块太大会挤掉其他文档的多样性；阈值需要评估集调；删除/重建时要同步清父块存储；缓存失效逻辑要跟着库版本走。

**我的判断**：先做“邻片扩展”，它能拿到自动合并 70%~80% 的收益，改动却小一个数量级。等你们的文档以“有章节结构的教材/讲义”为主，并且评估集里出现一批“召回对了但上下文不全”的失败案例，再上自动合并。现在直接做，属于用复杂度换一个还没被证明的问题。

## 4. 对照文章 12 个策略逐条看
| # | 策略 | 现状 | 缺口 | 必要性 | 建议 |
| --- | --- | --- | --- | --- | --- |
| 1 | 数据清洗 | `_strip_html`、PDF 加载、同名来源去重 | PDF 页眉页脚/断行、近重复文档、实体归一 | ★★★ | 先做 PDF 清洗 + 近重复；实体归一和时间失效暂缓 |
| 2 | 分块处理 | 递归切分 500/50 | 无标题结构、无特殊结构、无大小分层 | ★★★★★ | Markdown 标题切分 + 标题路径前缀；用评估集对比 500 vs 800 |
| 3 | 嵌入模型 | `text-embedding-v3` + 向量指纹校验 | 无 | ★ | 不微调，教程和你们现状一致 |
| 4 | 元数据 | `source/page/chunk_index/topics` | 缺 `heading_path`、`added_at`、文档类型 | ★★★ | 加标题路径和时间；这是自动合并/过滤的地基 |
| 5 | 多级索引 | 只有 topics 标签，用于画像偏置；`topic_where` 实际未用于检索 | 无路由、无多级索引 | ★★ | 不要用 topic 硬过滤（抽错标签会直接漏召回）；路由以后再做，且必须“结果不足就退回全库” |
| 6 | 索引/查询算法 | Chroma 默认 HNSW，向量已归一化，平方 L2 换算余弦 | 无 IVF/PQ/LSH 调优 | ★ | 当前库规模不值得动 |
| 7 | 查询转换 | 仅 a 上线 | b/c/d 未实现 | ★★★ | 按第 1 节条件启用，不默认全开 |
| 8 | 检索参数 | 向量+BM25+RRF(K=60)、top_k 3~10、min_sim 0.25、MMR λ=0.65 | RRF 无通道权重、top_k 固定、BM25 超 2 万片静默关闭 | ★★ | 用评估集调参；给 BM25 关闭加日志/指标；考虑加权 RRF，但先测 |
| 9 | 高级检索策略 | 上下文压缩只用于对话历史；无句窗/父文档/自动合并/多向量；grounding 算轻量 Self-RAG | 缺“召回后上下文恢复” | ★★★★ | 先邻片扩展；再做 Corrective RAG 单次重试；自动合并后置 |
| 10 | 重排 | 只有画像偏置和字面 MMR，无 cross-encoder | 无真正的语义精排 | ★★★★ | 最值得补的排序能力，但要先测 p95 延迟和并发 |
| 11 | 提示词 | `SYSTEM_PROMPT` + 依据强度提示，质量不错 | 引用编号可再严格、答案结构可约束 | ★★ | 小改即可，不是检索瓶颈 |
| 12 | 大语言模型 | DeepSeek，可配置，视觉单独模型 | 无 | ★ | 不动 |


**综合下来，我建议的优化顺序是：**

1. **P0：评估集**。30~50 条真实问题 + 金标片段，算 Recall@k / MRR / 忠实度。没有它，下面所有事都无法判断“变好还是变坏”。你们的[对照报告](file:///c:/biancheng/agent-hub/docs/对照ai-agent-book_逐章核对与待修改报告.md#L106-L111)也把“没有能力级评估”列为工程成熟度最大缺口。
2. **P0：Markdown 结构化分块 + 标题路径前缀**。一次重建索引，零额外 LLM 成本，直接改善召回语义。
3. **P1：邻片扩展**。只在拼 prompt 时做，先解决“片段被切断”的问题。
4. **P1：精排**。放在候选池之后，带超时和回退；先小流量对比。
5. **P1/P2：Corrective RAG 单次重试**。复用现有 `assess_grounding`，低置信时换查询再检一次，最多一次。
6. **P2：PDF 清洗 + 近重复删除**。属于数据质量，收益稳定但不惊艳。
7. **P2/P3：自动合并/父文档**。等结构化文档占比上来、评估集证明“上下文不全”是主要失败模式后再做。

**明确暂不做**：HyDE 默认开启、每题多查询、embedding 微调、HNSW/IVF 调优、多向量/RAPTOR、完整 Self-RAG、多级索引硬过滤。这些不是“错”，而是在你们当前的数据规模、并发模型和缺少评估集的前提下，投入产出比不成立。

如果继续往下走，我建议先把**评估集脚本 + 结构化分块**落地，这两件事能同时回答“b/c/d 要不要做”和“分块参数怎么选”。需要的话我可以直接按现有 `RagPipeline` 的接口写离线评估脚本，不动产品链路。
