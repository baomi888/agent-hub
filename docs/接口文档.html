通用约定

三块新模块与定时任务全部沿用现有约定，不另立一套。以下为要点摘录，完整版见文末「附录：契约提取件」。

响应形态

  • 本仓库没有统一响应信封：端点直接返回业务对象（或列表），错误统一走 FastAPI 的 {"detail": "..."}。
  • 新模块沿用这一口径——不引入 {code, data, msg} 包装层，避免前端为两组形状写两套解析。
  • 已知代价：前端 Mock 要按端点各自形状手写，不能一份通用拦截器兜住。这一点在「契约缺口」里如实记录。

鉴权

  • 业务路由整组挂 dependencies=[Depends(get_current_user)]（api/chat.py:46 同款），新增端点默认就要登录，漏写也落在安全一侧。
  • 免登录只有 6 个：api/auth.py 的 4 个 + /health + /api/config/defaults。
  • 登录态是 HttpOnly Cookie；未登录返回 401。

限流与配额

  • 每分钟：quota.hit(uid)，默认每用户 10 次/分钟（RATE_PER_MINUTE），超限抛 RateLimited 并返回 retry_after。
  • 每日：DAILY_ASK_LIMIT=60（用户主动提问）、DAILY_EMBED_LIMIT=1000（向量化分片）。
  • 定时任务烧的 token 不在上述任何一项里——本文档为此新增 kind="auto" 与 DAILY_AUTO_LIMIT，见定时任务一节。
  • 管理员（ADMIN_USERNAMES）不受配额与每分钟限流约束。

长任务：SSE 而非轮询

  • 帧格式沿用 api/chat.py:87-88：event: <name>\ndata: <json>\n\n。
  • 配额与限流必须在流开始之前校验——SSE 一旦发出 200 响应头就再也回不了 429（api/chat.py:289-297 的既有教训）。
  • 事件名沿用现有集合：status / token / tool / sources / grounding / title / done / error，新模块按需增加 run_start / node_start / node_end / checkpoint / run_end，不复用含义不同的事件名。

错误码口径

  • 新模块只用现有已出现的状态码：400 / 401 / 403 / 404 / 409 / 413 / 422 / 429 / 500 / 502 / 503，不新造 4xx 之外的语义。
  • 跨用户访问统一返回 404 而非 403：不泄露「这个 id 存在但不属于你」。
  • 配额类 429 带 kind + limit；限流类 429 带 retry_after（秒）。

2.3 Token 结构与 TTL
  • 形态：base64url(header).base64url(payload).base64url(sig)，base64url 去 padding（_b64e 用 rstrip(b"=")）——core/auth.py:100-106, 118。
  • header：{"alg":"HS256","typ":"JWT"}，json.dumps(..., separators=(",", ":")) —— core/auth.py:113, 115。
  • payload：{"sub": <user_id>, "iat": <unix秒>, "exp": <unix秒>}，只放这两类字段 —— core/auth.py:114。
  • 签名：HMAC-SHA256(secret, "header.payload") —— core/auth.py:117。
  • TTL 来源：config.AUTH_TTL_DAYS（环境变量 AUTH_TTL_DAYS，默认 "7"，即 7 天）—— core/config.py:98、core/auth.py:111；exp = now + days*86400（core/auth.py:114）。
  • 签名密钥优先级：AUTH_SECRET 环境变量 → data/.auth_secret 文件 → 生成 secrets.token_urlsafe(48) 并落盘 + chmod 600（只读文件系统时退化为每次重启换密钥）—— core/auth.py:75-97、core/config.py:95-96。
  • 校验：parts 必须 3 段 → compare_digest 比签名 → exp < now 判过期 → 返回 sub；任何失败返回 None —— core/auth.py:121-139。注意：不校验 header 的 alg 字段（算法由服务端固定，不受 token 内 header 影响）—— core/auth.py:121-139。
  • 测试佐证：签名自洽但用户不存在 → 401 —— tests/test_auth_gate.py:108。

5. SSE 协议（POST /api/chat/stream）

5.1 帧格式与收尾
  • 生成器：_sse(event, data) -> f"event: {event}\ndata: {json.dumps(data, ensure_ascii=False)}\n\n" —— api/chat.py:87-88。
  • 分隔符 \n\n；data 是单行 JSON（换行被 JSON 转义）；无 id:、无 retry: 字段。
  • 响应：StreamingResponse(..., media_type="text/event-stream", headers={"Cache-Control":"no-cache","X-Accel-Buffering":"no","Connection":"keep-alive"}) —— api/chat.py:58-62, 604。
  • 收尾方式：没有独立的结束事件。正常路径 done 之后生成器 return，HTTP 连接关闭（api/chat.py:596-604）；错误路径发完 error 即 return（例：api/chat.py:405-408, 515-516, 529-530）。此时响应头早已发出（200），错误不会改 HTTP 状态码。
  • 前置失败（会话不存在 404 / 配额 429）在 StreamingResponse 之前抛出，走普通 JSON 响应 —— api/chat.py:293-297。
  • 前端解析：按 \n\n 切帧、逐行读 event:/data:、JSON.parse（失败时退化为 {text: dataStr}）—— frontend/src/lib/sse.ts:9-22, 74-80。

Agent 编排

把「拆解任务 → 选工具 → 多步执行 → 落盘记忆」做成可视化可复跑的编排

实现现状：两个分支均无实现（已核实：无 agent 编排相关路由与文件），本节为接口设计稿

需求

功能需求

  • 编辑与执行分离：草稿（draft）可反复改，发布（published）生成不可变版本号，执行永远跑已发布版本。
  • 图结构校验在保存前完成：无环、无孤立节点、必填字段齐全、至少一个 start 与一个 end。
  • 执行过程可见：每个节点开始/结束、每次工具调用（名称/入参/出参摘要）、每个 token 增量都要能被前端订阅。
  • 可中断可恢复：执行到一半断开连接，能从最后一个成功节点继续，不重跑已完成的节点。
  • 依赖现成栈：LangGraph 1.2.11 + langgraph-checkpoint-sqlite 已在 requirements.txt，节点执行与落盘记忆不另造轮子。
  • 模型能力是硬约束：编排链路要求大模型支持 function calling / 并行工具调用，选型待定项在《API 选型对比表》里。

明确不做

  • 多用户协作编辑（评论、锁、变更集）不做。
  • 节点市场 / 节点插件化不做，节点类型固定为 5 种。
  • 不做前端拖拽编辑器的实现（20 号前只交付接口与 Mock）。
  • 不做多协议 schema 双格式（openai / anthropic）——本项目只走 DeepSeek（OpenAI 兼容），等真要切供应商再做。

工具契约与执行元数据

编排引擎要能替模型做决定（哪几个节点能一起跑、哪个失败该重试、哪个要先问用户），前提是每个工具与每个节点都自己声明能力，而不是引擎写死判断。这一节把工具与节点的执行元数据定成契约，它同时是「编排」相对「让模型自己循环」的核心差异——没有这层，图能画出来但引擎无法执行它。

工具结果三层预算（常数沿用参照实现，已按其源码核对）：

层阈值动作
单结果溢出15,000 字符落盘到 data/tool_results/{call_id}，上下文里换成「结果 N 字符已存到某路径」的预览标签

两条必须一起定的纪律（否则省钱会变成烧钱）：

1. 决策冻结：同一段历史重复构建请求时，必须产出逐字相同的前缀（已替换的预览串原样复用、不重算），否则会打掉模型侧的 prompt cache。

2. 落盘幂等：目标文件已存在且大小一致就跳过写入；写失败时降级为「保留原文」，不无限重试。

每日总结必须用这套预算：它要把当天全部会话喂给模型，没有硬阈值就只能靠调大上下文硬扛，成本不可控。这一步也是把「按会话分块摘要再合并」从架构描述变成可测数值口径的唯一办法。

每日委托

把「明天该做什么」在前一晚委托给系统，到点自动送达

实现现状：两个分支均无实现（已核实：无 daily / delegate / scheduler 相关文件），本节为接口设计稿

需求

功能需求

  • 委托 = 调度配置 + 生成指令 + 投递方式，三样齐了才算一条完整委托。
  • 每个用户最多 5 条启用中的委托：定时任务烧的是 token，且无人值守，必须有硬上限。
  • 到点生成内容要写回一个真实存在的会话（deliver_sid），用户在对话流里看到它，而不是一个独立通知列表。
  • 同一天同一委托只送达一次：重跑调度器不能变成重复打扰（幂等键见 4.3）。
  • 内容生成要能引用用户自己的知识库与当天上下文，否则只是模板套话。

明确不做

  • 推送通道只做站内（写回会话）+ 可选邮件；短信 / 微信 / App 推送不做。
  • 不做自然语言解析（「每天早上七点」这种自由文本转 cron）——20 号前用结构化表单。
  • 不做跨用户委托（不能替别人设委托）。

每日总结

把当天所有会话收敛成一页可溯源、可勾选的复盘

实现现状：两个分支均无实现（已核实：无 summary / daily 相关文件），本节为接口设计稿

需求

功能需求

  • 统计与正文分开：统计口径是确定的（会话数、消息数、活跃时段），由 SQL 直接算；正文才交给模型。
  • 可溯源是硬约束：正文里每条结论要能指回当天某个会话或消息，指不回去的不许写成结论——这是防幻觉固化的第一道闸门。
  • 不动用户数据：总结只读当天消息，不写会话、不改标题、不删任何东西。
  • 生成时间由服务端定（默认次日 23:30，见 4.2），用户可手动补生成；补生成与自动生成结果写同一张表。
  • 长上下文要压缩：一天可能有几十条消息，先按会话分块摘要（map）再合并（reduce），不能把全天原文一次性塞进 prompt。

明确不做

  • 不做跨天趋势分析（周报 / 月报）——院赛后再做。
  • 不做知识库写入：总结不会自动入库，避免把没验证的推断固化成知识。
  • 不做导出 PDF / 图片分享。

问题 1：调度周期怎么定

三类任务，三种周期，互不干扰：

任务周期触发时刻说明
每日委托投递按用户配置用户在委托里选的 HH:MM（默认 07:00 / 22:30 两个常用档）逐条委托独立触发，不批处理
每日总结生成每日一次次日 23:30（Asia/Shanghai）留出当晚补记的时间；当天 23:00 后新增的消息归次日
待办扫描（dispatcher）每 5 分钟整 5 分钟边界只做一件事：把到点的委托/总结任务排进执行队列

为什么总结放在次日 23:30 而不是当天 23:59：

当天最后一刻生成，用户还在写；次日生成时，昨天的会话已经全部落盘，且用户白天有时间看。

若用户当晚 23:40 才聊完，总结已经跑过一次，用户可手动 POST /api/report/generate 补生成（force=true 覆盖）。

为什么 dispatcher 是 5 分钟而不是 1 分钟：

1 分钟粒度对「早上七点提醒」这种需求没有意义，只会让 worker 每天多跑 1440 次空查询。

5 分钟意味着投递时间可能有 ±5 分钟的抖动——这一点必须写进产品文档，不能让用户以为 07:00 是 07:00:00。

周期表落库而不是写死在代码里：schedule_jobs 表存 (job_key, cron, enabled, next_run_at)，

改周期不用改代码、不用重新发版，也让「下一次什么时候跑」对运维可见。

问题 2：谁来触发（独立 worker + cron 表达式）

结论：独立 worker 进程 + 进程内 APScheduler，不用系统 crontab。

三个候选方案的对比（成本口径见 AI 信息助手的《API 选型对比表》，这里只给工程判断）：

方案优点缺点结论
A. 后端进程内 APScheduler零新增进程，deploy.sh 不用改与 API 抢同一事件循环；总结生成 20~40 秒会拖慢在线问答；后端重启/多副本会重复触发否
B. 服务器 cron + 独立 worker 脚本与 web 进程彻底隔离，崩了不影响问答多一个进程要管；cron 与业务时区/开关的关系要人工维护否（cron 表达式不可见于代码，且无法按用户配置逐条触发）
C. 独立 worker 进程 + APScheduler（选定）与 web 隔离；调度配置落库、可在代码里审；未来多副本部署可加 Redis jobstoredeploy.sh 要多管一个进程、多一条日志、多一处告警是

问题 3：幂等与重试

幂等键：(job_key, subject_id, planned_at) 三元组，落 job_runs 表的唯一索引。

CREATE TABLE job_runs (
  run_id      TEXT PRIMARY KEY,
  job_key     TEXT NOT NULL,        -- delegate.dispatch / report.daily ...
  subject_id  TEXT NOT NULL,        -- delegation_id 或 date
  planned_at  INTEGER NOT NULL,     -- 计划触发时刻（UTC 秒）
  idem_key    TEXT NOT NULL,        -- job_key|subject_id|planned_at
  status      TEXT NOT NULL,        -- pending/running/succeeded/failed/skipped
  attempts    INTEGER NOT NULL DEFAULT 0,
  started_at  INTEGER, finished_at INTEGER,
  error       TEXT,
  tokens_out  INTEGER DEFAULT 0
);
CREATE UNIQUE INDEX ux_job_runs_idem ON job_runs(idem_key);

为什么幂等键里要带 planned_at：同一委托今天 07:00 和明天 07:00 是两次不同的投递，都要发；

但「今天 07:00 这一次」无论被触发几次（worker 重启、重复扫描、手动重跑）都只能发一次。

worker 执行前先 INSERT ... ON CONFLICT(idem_key) DO NOTHING，插入影响行数为 0 就直接跳过——

用数据库唯一约束做幂等，而不是用「查一下有没有」，后者在并发下有竞态（这与 core/quota.py:111-123 的 upsert 记账是同一套思路）。

重试策略：

失败类型判定重试
大模型超时 / 5xx / 429可重试最多 3 次，间隔 1 / 5 / 15 分钟（指数退避），attempts 落库
大模型 401 / 402（额度耗尽）不可重试直接 failed，并触发告警（继续重试只会继续烧钱）
会话已删除 / 知识库不存在不可重试failed + 把委托 enabled 置 false（依赖已失效，重试无意义）
配额已达上限可重试延后到次日同刻（不是 15 分钟后——今天已经没额度了）

「超限时不扣」的沿用：core/quota.py:178-193 的 consume() 在触顶时不记账，本模块沿用同一口径——

否则重试会把计数越推越高，用户第二天零点也解不开。

投递幂等：写回会话时用 job_runs.run_id 作为消息的外部标记；

即使重试成功两次，也只在会话里出现一条（第二条按 run_id 判重丢弃）。

问题 4：时区：Asia/Shanghai

存储一律 UTC，解释一律 Asia/Shanghai，展示一律带时区标注。

环节规则
数据库时间戳全部 Unix 秒（UTC），与现有 sessions/messages 表一致
调度计算APSCHEDULER_TIMEZONE=Asia/Shanghai，cron 按上海时间解释
「今天」的定义report.date 用上海日历日（core/quota.py:94-99 的 day_key() 已经是本机时区口径，同一套语义）
接口返回时间戳为 Unix 秒；需要人读的地方另给 at: "07:00" + tz: "Asia/Shanghai" 字段
前端展示按浏览器时区渲染，但委托列表固定标注「Asia/Shanghai」，避免用户跨时区时误判

红线：禁止裸 datetime.now()。

必须写成 datetime.now(ZoneInfo("Asia/Shanghai"))。理由不是洁癖——

服务器的 TZ 环境变量一旦被改成 UTC（容器镜像默认常常就是 UTC），

所有「早上七点」会整体偏移 8 小时，而且不会报错，只会安静地错。

DST 说明：中国大陆自 1991 年起不实行夏令时，Asia/Shanghai 全年 UTC+8，

所以本项目的调度不存在 DST 跳变问题。但代码仍必须用带时区的库函数而不是手工 +8——

手工加 8 小时在跨年/跨时区迁移时没有任何防御力，而 ZoneInfo 是零成本的。

跨日边界的具体口径（必须写进产品文档，否则一定有人问）：

  • 总结的 date=2026-10-12 覆盖区间是 [2026-10-12 00:00, 2026-10-13 00:00)（上海时间）
  • 每日用量配额（DAILY_ASK_LIMIT）用的 day_key() 是服务器本地时区；

两者在服务器 TZ=Asia/Shanghai 时一致，若部署在 UTC 机器上则会差 8 小时——

本项目的部署要求明确写：服务器 TZ 必须设为 Asia/Shanghai，这样两套口径自然对齐。

问题 5：失败怎么告警

三层，从轻到重：落库 → 日志 → 外发。前三层都在 20 号前的范围里，第四层留待院赛。

层手段触发条件20 号前
1. 落库可见job_runs.status/error，委托与总结列表里直接显示「上次投递失败 + 原因」每次失败是
2. 结构化日志每轮调度写一行 JSON 日志（job_key / run_id / 耗时 / 结果 / 错误）任何时候是
3. 健康端点GET /api/schedule/health 返回各 job 的最后成功时间、连续失败次数、worker 心跳运维/前端轮询是
4. 外发通知连续 3 次失败 → 给管理员发邮件/Webhook连续失败院赛

「静默故障」才是真正要防的那个：worker 进程挂了，但 web 正常、接口全 200、

用户只是「今天没收到提醒」，没人知道出了事。所以 worker 每轮心跳写 worker_heartbeat 表，

/api/schedule/health 里 heartbeat_age_seconds > 600 就判 worker: down——

用一个「多久没心跳」的绝对量判断，而不是判断进程是否存在（进程在但卡死的情况同样要被抓到）。

健康端点返回示例见下方接口设计；告警文案统一为「每日委托连续 3 次投递失败，检查 worker 与模型额度」。

用户侧的告警与运维侧的告警分开：用户只关心「我的委托没送到」，

所以委托列表里直接展示 last_run.status 与错误摘要；不要把内部错误码抛给用户。

它的六个机制

机制实现形态解决什么
契约接口`Tool` 是 interface：name / description / category / schema / execute + `shouldDefer()` 默认方法任何能力都自描述，引擎不写死判断
结果载体`ToolResult(output, isError)` record + success()/error() 静态工厂失败也带文本，但错误位单独存在 → Agent 据此决定重试或停
注册表`ToolRegistry`：ConcurrentHashMap + discoveredTools 集合 + `getAllSchemas(protocol)`集中注册、按协议适配、延迟工具不占 token
延迟发现`shouldDefer()` 标记 + `ToolSearchTool` 元工具（select: 精确 / 关键词模糊）→ markDiscovered工具数增长时 schema 体积不线性上涨
读写分类调度`ToolCategory`：READ 并行 / WRITE、COMMAND 串行；StreamingExecutor 按类别分组并发并发策略由工具自己声明，不由引擎猜
结果预算`ToolResultBudget` 三层：15K 单结果落盘 / 20K 聚合溢出 / 保留最近 10 轮截断长任务不撑爆上下文；决策冻结保 prompt cache 前缀稳定

迁移分档

直接搬

  • `ToolResult` 三元组（text / is_error / retryable）——根治「模型被文案误导后原地重试」
  • 工具分类 → 编排节点的 parallel_group：5 个工具全是只读，今天就能并发
  • 工具 schema 按需发现：为工具数增长预留 defer 字段与发现端点

选做

  • 三层结果预算的常数与降级规则——每日总结必用
  • prompt cache 前缀稳定（决策冻结）——先确认现用模型的计费口径再实现
  • 危险动作权限闸（download_file / 删库 / 重建）——安全叙事加分项

不搬

  • 虚拟线程 / CompletableFuture —— Python 侧对应 asyncio.TaskGroup，概念照搬只会加复杂度
  • OpenAI + Anthropic 双协议 schema —— 本项目只走 DeepSeek，现在做是空转
  • 手写 Tool 接口替换 LangChain @tool —— 推翻现成 function calling 链路，改为另建 TOOL_META 元数据表
  • select: 强语法 —— 学习助手用不到，保留关键词搜索即可
一条必须说清的边界：mewcode 是编码 Agent（工具多、动作危险、结果海量），本项目是学习助手（5 个只读工具、风险面小）。所以只搬「契约与元数据」这层，不搬它的并发基建与协议适配。反过来，这次对照也暴露了本项目接口文档先前缺的一层——节点执行元数据，已在「Agent 编排」一节补齐。
