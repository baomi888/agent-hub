## 1. 用户名重名，报"邮箱已被绑定"（P2）

**现象**：用一个已存在的用户名去注册（哪怕邮箱是新的、验证也是真的），返回：

```
409 {"detail":"邮箱已被绑定，请重新验证其他邮箱"}
```

**根因**：

- `core/security_email.py:135 register_signup` 手写 `INSERT INTO users`，用户名唯一约束冲突抛 `sqlite3.IntegrityError`；
- `api/security_email.py:79` 把**任何** `IntegrityError` 都翻译成邮箱冲突。

**修法**：不要改 `call()` 的文案 —— 真正的邮箱冲突还要靠它兜。在 `register_signup` 的 `effect(db)` 里、写库之前按用户名显式查一次，命中就抛 `SecurityEmailError("该登录名已被占用", 409)`。写在 effect 内的好处是异常会让 `consume` 的整个事务回滚，验证码凭证不会被白白吃掉，用户换个名字还能重试。

**验收**：补一条测试，断言重名时 `status_code == 409` 且 `"登录名" in response.text`；同时保留真正的邮箱冲突用例，确认那条仍返回邮箱文案（别为了修这个把另一条改错）。

## 2. 未注册地址占满地址桶，可以打真实用户（P1）

**现象**：对 `victim@example.com` 连发 10 次找回密码验证码（**不需要这个邮箱存在**），当天受害者本人就再也发不出找回邮件。

**根因**：`core/security_email.py` 的 `send_reset` 在 `exists == False` 时仍然执行 `self.store.reserve(context, ip)`；`core/verification.py:reserve` 的第一条桶就是按地址哈希的，`Limits.daily = 10`。`cooldown = 60s` 会再叠一层。IP 桶换 IP 就绕过，全站桶 1000/天太大，挡不住。

**修法取舍**（这条要你定，别默默选一个）：

- **方案 A（推荐）**：未注册地址只计 IP 桶和全局桶，不计地址桶。地址桶本来也挡不住枚举 —— 枚举一次发一封就够，而且 verify 文案现在已经归一。代价是单 IP 可以换地址刷，但 IP 桶 + 全局桶还在。
- **方案 B**：未注册地址仍占地址桶，但单独设一个更小的上限（如 3/天），同时收紧 IP 桶。实现更绕，收益有限。

不管选哪个，建议给 send 端点加一个 **100~200ms 固定延迟**：已注册会真发信、未注册不发，响应时间本身也能泄露账号是否存在。固定延迟要加在两条分支的共同路径上，加在某一支里等于没加。

**验收**：

1. 对未知地址发到上限后，让同一个地址变成已绑定账号，再发一次找回 —— 必须能发出（200 且假 SMTP 收到信）。
2. 已注册/未注册的 send 响应时间差，在固定延迟后应落在同一量级；至少断言不会出现"未注册快一个数量级"。

## 3. `.env.example` 的注释会让人以为注册还开着（P1 文档）

**现状**：`.env.example:143` 写的是

```
# SECURITY_EMAIL_ENABLED=0 时三个功能整体关闸（前端注册不要求邮箱验证）。
```

**实际**：照 `.env.example` 抄下来不改（`ALLOW_SIGNUP=1`、`SECURITY_EMAIL_ENABLED=0`），`api/auth.py:51 signup_service()` 会一路走到 `get_service()` 抛 503「安全邮箱服务尚未启用」，**注册端点整体不可用**，前端只显示"邮箱验证暂不可用"。

**修法**：改成一句不含糊的，例如：

```
# 0 = 自助注册整体关闭（注册端点返回 503），不只是邮箱验证；已存在账号的密码登录不受影响。
```

`core/config.py:699` 的默认值和注释是我们集成时写的（ecdc2c23），口径已经对齐，你只改 `.env.example` 这一行就行。

**验收**：顺手补一条最小测试 —— 默认配置下 `POST /api/auth/register/` 返回 503，把文档承诺钉死在代码上。

## 4. 五张验证码表只增不减（P2，一起定）

**现状**：`verification_requests`、`verification_grants`、`verification_rate_limits`、`verification_cooldowns`、`verification_slots`（原审计稿漏了 slots）全部只 INSERT/UPDATE，全仓没有任何 `DELETE FROM verification_*`。`ops/_wb_week_1115_1122.py` 里出现的 `verification_requests` 只是周报统计，不是清理。按每天几百次发码估，一年十万级行。

**修法**：挂在 `worker/scheduler.py` 现有的 housekeeping 机制上，加日任务：

- `verification_requests` / `verification_grants`：删 `expires < now - 86400`；
- `verification_rate_limits`：删 `window` 已过期的（按 bucket 的窗口语义，别只按日期）；
- `verification_cooldowns`：删 `sent_at < now - 86400`；
- `verification_slots`：删 `latest_id` 已不在 requests 表里、且 `active_id` 为空的行。

**验收**：插入一批过期行和一批新鲜行，跑一次清理，断言过期行清零、新鲜行一条不少。别写成 `DELETE WHERE 1=1` 那种"测试绿了线上没了"。
