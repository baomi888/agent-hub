# 技巧仓库

解决过、验证过、能复用的东西。不写「今天学了什么」，只写**下次能直接用的判断**。

**怎么用**：开工前翻索引，挑 2~3 条相关的贴给 AI，加一句「这次别重复 T-xx 的错」。别贴整篇——相关性比完整性有用。

**怎么加**：每条四段，缺一段就不算条目。问题模式（什么时候会遇到）→ 关键约束（为什么不能那样做）→ 有效解法 → 触发场景（怎么认出又碰上了）。

## T-01　请求上下文别放 ThreadLocal

- **问题模式**：一条请求链路上要传用户身份 / 租户 id，中间隔着好几层函数，不想层层传参。
- **关键约束**：FastAPI 的同步依赖跑在 anyio 线程池里，**线程会被复用**。ThreadLocal 在低并发下一切正常，压力一上来 A 用户会拿到 B 的数据——偶发、无法复现、日志里看不出来。
- **有效解法**：`request.state`（同请求内可取）或显式传参；纯异步链路用 `contextvars.ContextVar`。
- **触发场景**：框架提供「中间件 / 依赖注入」且底层有线程池时。判断信号：数据只在并发时串，单测永远复现不出来。

## T-02　降级方向按失败代价选，不按「有就给它」选

- **问题模式**：主路径（模型判断、外部服务）会超时、会异常，要定回落到哪。
- **关键约束**：两条路的失败后果**不对称**。窄路（只能检索）挂掉后没有任何补救；宽路（智能体）还能换工具或直接作答。按「资源利用率」选会选错。
- **有效解法**：回落到能力更宽的那条；宁可多花一次调用，也不要给用户一个死胡同。
- **触发场景**：任何 fallback / retry / 超时降级设计。自检问句：「这条路失败之后，用户还剩什么？」

## T-03　开关用三态，`False` 不能兼任「没传」

- **问题模式**：接口要加新的布尔开关，但线上还有一批老客户端只发旧字段。
- **关键约束**：如果「没传」被折成 `False`，老客户端的全部请求会被静默降级成最保守行为——**不报错、不告警**，只表现为「功能忽然变笨」。这是最难查的一类线上问题。
- **有效解法**：`bool | None`，`None` = 未传 → 回落旧字段映射；`False` = 明确关。等旧客户端下线了再收紧成 `bool`。
- **触发场景**：给有存量客户端的接口加开关。判断信号：这个字段缺失时，默认值会不会改变已有行为。

## T-04　判据搬家（换调用面）必须重估误判代价

- **问题模式**：一段「效果不太好」的判断逻辑（词表、正则、启发式）想调参或换掉。
- **关键约束**：先看**谁在调用它**。同一个判据，只服务「主动选择这个模式」的少量用户时，误判由用户自己发现并绕开；变成所有人默认走它之后，同样的误判率直接等于产品故障率。误判的**代价**变了，不是准确率变了。
- **有效解法**：换调用面之前先问「误判一次，用户还能不能自己纠正」；不能，就必须换判据（交给模型 / 加人工确认），而不是调阈值。
- **触发场景**：把实验性逻辑设成默认路径、把内部工具开放给全部用户、把人工触发的功能改成自动触发。

## T-05　意图快照与执行值分开，现实修正只做一处

- **问题模式**：决策函数算出一个结果，下游还要按运行时现实（资源没了、权限变了）改一次。
- **关键约束**：如果直接在决策结果上原地改，改完就分不清「用户要什么」和「实际跑了什么」——日志、埋点、回放全部失真；改动点一多，还会互相覆盖。
- **有效解法**：决策产出**冻结的意图快照**（如 `PlannedRoute`，`frozen=True`）+ 一个可变的执行值（`mode`），现实修正集中在一处、紧挨调用点。
- **触发场景**：路由/调度/编排类代码，决策与执行之间隔了 I/O 或权限校验。

## T-06　缓存键漏维度 = 静默返回旧对象

- **问题模式**：某种构造很贵（编译状态图、构建客户端、拼 SQL 模板），参数组合有限，于是加一层进程内缓存。
- **关键约束**：最危险的不是漏了显式参数（漏了容易发现），而是漏了**那种改了但键不变的隐式输入**——版本号、环境开关、代码常量本身。缓存按设计工作，所以**不报错、不打日志、指标全绿**，只表现为「改了没生效，重启就好了」。
- **有效解法**：① 键覆盖所有影响构造结果的输入，宁可多一维；② 隐式输入要显式化——版本号进键，代码常量变动意味着必须重启，就把这点写进注释和文档；③ 想要热生效，让「改」这个动作本身改变键（走版本化存储 + promote）。
- **触发场景**：`@lru_cache`、模块级 dict 缓存、单例构造。自检问句：「我把这段代码改了，下一次调用会拿到新的吗？」

## T-07　死参数比没参数更危险

- **问题模式**：重构后某个参数不再需要，但为了不动调用方签名，先留着。
- **关键约束**：留着不用的参数会让人（尤其是 AI）**误以为它还在起作用**，从而往错的地方改——你想改行为，改了那个参数，实际毫无效果。比「没有这个参数」更糟：没有时会去读代码，有时会直接相信签名。
- **有效解法**：能删就删；删不掉（多调用方 / 兼容期）就在声明处写「⚠️ 当前未使用」，并在函数体第一行显式丢弃（`del location` 或 `_ = location`），让它看起来就是死的。
- **触发场景**：重构遗留、参数改名后只改了一半、配置项从「拼进提示词」改成「末尾追加」之后原入口没清理。

## T-08　缺省值别选在危险侧

- **问题模式**：要把「没有」和「有但是空」分开表示；或者要为一个能力参数定默认值。值域与「缺失」的表示空间重叠，必须挑一个语义。
- **关键约束**：默认一旦选在危险侧，错误就**不会暴露**。`get()` 用 `None` 表示 miss，值域里恰好允许 `None` 时，命中被当成未命中——缓存永久失效却不报错；能力开关默认 `True`，调用方漏传一个参数就静默拿到全量权限——也不报错。共同点是「少给了东西，结果反而更危险」。
- **有效解法**：① 「没有」用**专属哨兵**（`_MISSING = object()`）表示，别借用值域里的合法值；哨兵别在 API 边界上还原成 `None`（`get() -> Optional[V]` 等于把问题挪了个位置，没解决）。② 能力类默认值取**最保守**（`False` / 空集），漏传 = 少给能力，失败了看得见。
- **触发场景**：写缓存 / 注册表的 `get`；给权限、工具、开关、白名单这类参数定默认值。自检问句：「调用方漏传这个参数时，拿到的是更多还是更少？」

## T-09　抽被调用者 ≠ 抽调用者，复杂度看最大函数

- **问题模式**：一个 2000 行的文件、一个 800 行的函数要「解耦」。很自然地把里面的辅助逻辑抽成独立模块，抽完发现文件没怎么变短。
- **关键约束**：抽走的是**被调用者**（`_sse(...)`、检索组合拳），不是**调用者**（那几百行的分支本体）。调用点的行数几乎不变——`_sse("x", {...})` 变成 `sse.status("x")` 还是一行。实测：抽出 272 行新模块，主文件只减 71 行（3%），最大函数 826 → 809 行（2%），`yield` 55 处、`return` 18 处**一个没少**。
- **有效解法**：判断重构效果只量三个数——① 最大函数行数 ② 最长分支行数 ③ 新增一条同类路径要写多少行。要降复杂度就得搬「分支本身」（每个分支一个 handler + 统一收尾 + 显式状态对象），搬 helper 的收益是另一件事：可单测、消除重复口径——那也是收益，但别把它当成「结构解耦」。
- **触发场景**：看到「这个文件太长」想拆的时候；重构完写总结的时候。自检问句：「我抽完之后，再加一条同样的路径要写多少行？」

## T-10　批量改代码用 AST/缩进边界，不用文本模式

- **问题模式**：要批量改或删几十处同构代码——删一个旧函数、把 `f("x", {...})` 改成 `g(...)`、批量换装饰器。
- **关键约束**：文本模式会**越过不属于它的结构**。「从 `def x` 删到下一个 `def`」会吞掉夹在中间的模块级常量与 class（它们不是 `def`）；正则遇到 f-string 的花括号、嵌套引号会匹配错位。更要命的是这类破坏在 diff 里不显眼——它和真正要删的东西在同一段。
- **有效解法**：① 删除用缩进层级或 `ast` 的 `end_lineno` 定边界，不用「下一个 def」；② 批量替换用 `ast` 遍历拿到每个节点的 `lineno/col_offset/end_lineno/end_col_offset`，**从后往前**替换（否则前面一改，后面的偏移全失效）；③ 改完**先跑一次 import** 再跑业务测试——模块级名字缺失会在这里立刻炸，比跑业务测试早得多。
- **触发场景**：删函数/类/常量、改调用形式、批量改注解。判断信号：你写的脚本里出现了「下一个 def」「正则匹配代码」这类词。

## T-11　状态合并的判据是处置方式，不是语义相似

- **问题模式**：几个布尔状态字段能组合，想把它们并成一个「失败」谓词或状态枚举，让判断只写一次。
- **关键约束**：合并的判据不是「看起来都是坏情况」，而是**后续处置方式是否完全相同**。典型反例：截断的回答内容不完整但合法（必须落库 + 打标记）；命中泄露过滤的回答已被替换成固定拒答（也是合法内容，必须落库）；只有断连 / 上游报错才「不能落库」。把前两者并进 `dead` 会导致**该存的答案不存**，而且不报错。
- **有效解法**：先给每个状态写一行「接下来要对它做什么」，处置相同的才合并；不同的保留独立字段，用**分离的谓词**表达（往往一个 `interrupted` 就够），并在类的注释里写明「刻意不并入 X，因为……」，防止后人再合并一次。
- **触发场景**：给流式响应、后台任务、请求上下文写状态对象时。自检问句：「这两种情况，我下一步的代码真的一样吗？」

## T-12　抽公共服务不带走「失败怎么办」

- **问题模式**：三条以上调用路径都在调同一组步骤（建连 → 查询 → 整形 → 组装），于是抽成一个 service / client。
- **关键约束**：这组步骤里混着两种东西——**做什么**（可复用）和**失败了怎么办**（各路径不同）。把后者一起抽走，服务层就得替调用方决定降级策略，于是「某条路径必须中断报错」会被静默改成「返回空、继续跑」。行为变了，但测试绿、日志干净。
- **有效解法**：服务只返回数据、**异常原样抛**（必要时包一层带上下文的异常）；降级策略留在调用方，每个调用点自己 try。给一个可注入的 `pipe` / `client` 参数当测试缝，让服务能脱离外部依赖断言。不吞异常的另一个好处：调用方想知道「是失败还是真的没结果」时，信息还在。
- **触发场景**：抽 repository / service / SDK 封装时。自检问句：「调用方原来 catch 之后做的事，三条路径真的一样吗？」

## T-13　测试写完要验证它能失败

- **问题模式**：新增一批保护性测试（快照、基线、契约断言），跑通了就收工。
- **关键约束**：一个**永远绿**的测试等于没有测试，而且比没有更糟——它给人「有保护」的错觉。快照类尤其危险：把所有值都归一化掉之后，字段改名、少一帧、两帧互换照样全过。「跑通」只证明它现在不误报，不证明它将来能报。
- **有效解法**：① 写完立刻做变异验证——故意改坏三处（字段改名 / 删一帧 / 两帧互换），确认都报错、报错能定位到「第几帧、哪个字段」，再恢复；② 归一化只给真的固定不住的字段，并且**显式写在调用处**（`volatile={"run_id"}`），不要做成默认行为；③ 快照存列表，下标即顺序，顺序错误不需要额外断言；④ 写文件显式 `newline="\n"`，否则同一份快照在不同 OS 录出来字节不同，git diff 整文件变更。
- **触发场景**：写完 characterization / golden / 契约测试之后。自检问句：「我故意改坏一行，这个测试会红吗？」
