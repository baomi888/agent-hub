# 混合架构系统研讨报告：工作流模式 × 自主 Agent 模式

> 状态：研讨稿，未定稿。三个关键决策点（集成形态 / 工作流定义与编排 / 切换规则维度）待评审后拍板，再进入实施。

---

## 1. 背景与目标

现有系统的问答执行是**单模式**的：`api/chat.py` 的 `_pick_mode()` 在 `auto / rag / agent / llm` 中四选一，一次请求从头到尾只跑一种模式。这带来两个结构性短板：

- **确定性任务不可靠**：纯 Agent（ReAct 循环）执行"先 A 后 B 再 C"这类有严格顺序的任务时，依赖模型自觉，步骤可能漏、顺序可能乱、失败没有补偿。
- **不确定性场景不灵活**：固定流程无法应对开放式任务（如"帮我调研某个主题并整理报告"），而这类任务恰恰是 Agent 的主场。

目标是设计并实现一个**混合执行架构**：工作流模式保证确定性任务的可靠执行，Agent 模式处理非结构化场景，两者在一次任务执行过程中可以按上下文条件**无缝切换、动态融合**，并且：

1. 支持执行中自动切换与融合（要求 1）
2. 工作流具备节点定义、条件分支、超时控制、可视化编排（要求 2）
3. Agent 具备动态规划、环境感知、自主决策、工具调用（要求 3）
4. 统一任务上下文，切换时数据/状态/中间结果完整传递（要求 4）
5. 切换触发规则可配置 + 人工干预入口（要求 5）
6. 统一监控与全链路日志（要求 6）
7. 可扩展：支持新增执行模式接入、两种核心模式独立迭代（要求 7）
8. 单元 + 集成测试验证切换正确性、混合稳定性、边界容错（要求 8）

## 2. 现状基座盘点（可复用资产）

| 资产 | 位置 | 可复用方式 |
|---|---|---|
| Agent 构建与编译缓存 | `agent/builder.py` `build_agent()` | 混合架构的 Agent 模式直接复用；图编译按 `(has_kb, location_note)` 缓存已有先例，新引擎的图/流程编译应沿用同套 LRU 缓存模式 |
| 工具集（5 个 @tool） | `agent/tools.py` | Agent 模式与工作流的"Agent 节点"共用；`owner_id/kb_id` 由服务端经 `RunnableConfig.configurable` 注入的安全边界必须保留 |
| SSE 流式协议 | `api/chat.py` `_sse()` + `status/tool/token/title/done/error` 事件 | 混合执行新增 `workflow_node`（节点进出）、`mode_switch`（切换事件）两类事件，前端消费方式不变 |
| 模式路由 | `api/chat.py` `_pick_mode()` | 扩展为五选一（+`hybrid`），auto 路由规则加一个分支 |
| 会话/消息持久化 | `core/session.py` | `conversations` 表无 JSON meta 字段，需为任务状态新增独立存储（见 §5.4）；消息落库 `add_message()` 直接复用 |
| LLM 客户端 | `core/llm.py` `get_llm()` | 超时/重试已封装；已知缺口：内部推理调用无 `max_tokens`，混合引擎的规划/分类调用必须补上显式上限（project memory 硬约束） |
| 配置集中管理 | `core/config.py` | 新引擎的全部阈值（超时、步数、token 预算）走同一处，pydantic 风格延续 |
| 测试基线 | `tests/` + `pytest.ini` | pytest 风格用例为主、脚本式自测逐文件 `--ignore` 的约定延续；全量基线 39 项须保持绿色 |

**结论**：Agent 侧能力基本现成，主要新建工作量在**工作流引擎、切换引擎、统一上下文、监控日志**四块，前端取决于集成形态决策（§4）。

### 3.1 模式融合的三种切换形态

| 形态 | 方向 | 触发示例 | 上下文传递要点 |
|---|---|---|---|
| **降级接管** | 工作流 → Agent | 节点连续失败、条件分支无匹配、遇到流程外子目标 | 把已完成的节点产物 + 失败原因打包成 Agent 的初始任务描述，Agent 接管后产出回写 `shared` |
| **收编回归** | Agent → 工作流 | Agent 完成探索性子目标、达到步数/token 预算、产出满足工作流后续节点的输入契约 | Agent 产出按 schema 校验后写入 `shared`，工作流从**断点的下一节点**（而非从头）继续 |
| **人工切换** | 双向 | 用户在前端点切换按钮 / API 下发指令 | 与自动切换同一通道，只是触发源为 `manual`，优先级最高，立即生效 |

### 3.2 统一任务上下文（要求 4 的核心设计）

```python
# hybrid/context.py 设计草案
class TaskContext(BaseModel):
    task_id: str
    goal: str                      # 用户原始诉求
    current_mode: Literal["workflow", "agent"]
    workflow_state: dict | None    # 当前节点 id、已完成节点、各节点产物引用
    agent_state: dict | None       # 已走步数、token 消耗、工具调用计数
    shared: dict[str, Any]         # 跨模式中间结果（唯一数据交换通道）
    mode_trace: list[ModeSwitch]   # 每次切换：from/to/触发规则/理由/时间戳
    version: int                   # 每次变更 +1，切换移交时校验一致性
```

关键约束：

- **`shared` 是唯一交换通道**：工作流节点产物、Agent 最终产出都必须写入 `shared`，另一方只从这里读，杜绝"模式私有状态隔空引用"。
- **切换即快照**：每次切换把 `TaskContext` 整体序列化落库（`workflow_runs` 表），崩溃恢复时可从最近快照续跑。
- **一致性校验**：移交时 `version` 乐观锁 + `shared` 写入方的 schema 校验（收编回归时 Agent 产出不符合契约 → 不切换，转为 Agent 继续或报错）。

### 3.3 切换规则模型（要求 5）

```python
# 规则定义（存 switch_rules 表，支持热更新）
class SwitchRule(BaseModel):
    name: str
    priority: int                  # 数字小者先求值，manual 恒为 0
    when: RuleCondition            # 见下
    action: Literal["to_agent", "to_workflow"]
    reason_template: str           # 写入日志的决策依据（要求 6）
    cooldown_seconds: int = 30     # 防抖，防乒乓切换

class RuleCondition(BaseModel):
    dimension: Literal["task_type", "stage", "resource", "exception"]
    # task_type: 入口一次性分类（规则/LLM 分类器判定问题属于流程型 or 开放型）
    # stage:     workflow 节点声明 requires_agent=True / agent 步数达到 X
    # resource:  token 预算消耗比 > 阈值 / 单模式累计时长 > 阈值
    # exception: 工具连续失败 N 次 / 节点抛错且无匹配分支
    op: str                        # eq / gt / matches ...
    value: Any
```

默认预置规则（无论最终选哪个维度范围，这些是骨架）：

1. `manual_override`（priority 0）：人工指令，无条件优先。
2. `wf_node_failure_to_agent`：工作流节点失败且无 `on_fail` 分支 → to_agent（降级接管）。
3. `wf_requires_agent`：节点声明 `requires_agent=true` → to_agent（流程内嵌自主子任务，是"动态融合"最干净的形态）。
4. `agent_budget_exhausted`：Agent 步数 ≥ 上限 或 token 消耗 ≥ 预算 → to_workflow 或终止（收编回归/兜底）。
5. `agent_goal_satisfied`：Agent 自评产出满足下游契约 → to_workflow 从断点续跑。

### 3.4 工作流定义模型（要求 2）

```python
class WorkflowDef(BaseModel):
    id: str
    name: str
    version: int
    nodes: list[NodeDef]
    edges: list[EdgeDef]
    timeout_seconds: int           # 整个流程的超时护栏

class NodeDef(BaseModel):
    id: str
    type: Literal["llm", "tool", "agent", "condition", "human"]
    config: dict                   # llm: prompt 模板(可引 shared 变量)；tool: 工具名+参数模板
    timeout_seconds: int | None    # 节点级超时，asyncio.wait_for 实现
    on_fail: str | None            # 失败跳转节点 id；None 则走切换规则
    requires_agent: bool = False   # 执行到此节点自动触发 to_agent
    retry: int = 0                 # 节点内重试次数（先重试，再触发切换）

class EdgeDef(BaseModel):
    source: str
    target: str
    condition: str | None          # 对 shared 的表达式求值，如 "shared.score > 0.8"
```

- 条件分支：`condition` 节点或对边挂表达式，表达式用受限求值（沿用 `agent/tools.py` calculator 的白名单思路，拒绝任意 `eval`）。
- 超时控制：节点级 `asyncio.wait_for` + 流程级总时长护栏，超时视为节点失败进入切换判定。
- `agent` 类型节点：流程内直接声明"这一段交给 Agent"，是工作流/Agent 融合的一等公民，不需要切换规则介入。

### 3.5 监控与日志（要求 6）

统一事件流，一张 `exec_logs` 表 + SSE 实时推送：

| 字段 | 说明 |
|---|---|
| `task_id / run_id` | 任务与单次执行标识 |
| `event_type` | `node_enter / node_exit / tool_call / token / switch / error / human_intervention` |
| `mode` | 事件发生时处于哪种模式 |
| `node_id` | 工作流事件必填 |
| `decision` | switch 事件必填：触发规则名 + 求值输入 + 理由文案 |
| `payload` | 节点产物摘要 / 工具输入输出摘要（截断，避免大文本落库） |
| `ts` | 时间戳 |

前端按 `run_id` 可回放完整执行轨迹：时间轴上工作流段与 Agent 段异色标注，切换点展示决策依据 —— 这直接满足"执行轨迹、决策依据、状态变更全链路记录"。

### 3.6 可扩展性（要求 7）

- **引擎注册表**：`ExecutionEngine` 抽象基类（`run(ctx) -> AsyncIterator[ExecEvent]` + `can_resume(ctx)`），`workflow` / `agent` 是两个内置实现；新增模式（如"人工审批模式""批处理模式"）实现同一接口并注册即接入，编排器无感知。
- **模式独立迭代**：两个引擎各自独立演进，契约只有 `TaskContext` 与 `ExecEvent`；`TaskContext` 用 pydantic 版本化字段，新增字段带默认值，旧快照可前向兼容。
- **规则引擎数据驱动**：切换规则存库而非写死代码，新增维度只需扩展 `RuleCondition.dimension` 枚举与对应求值器。

## 4. 关键决策点研讨（待拍板）

### 决策点 1：集成形态

| 方案 | 说明 | 优点 | 代价/风险 |
|---|---|---|---|
| **A. 嵌入聊天页新 mode**（推荐） | `ChatMode` 加 `hybrid`，复用会话、SSE、消息落库、附件全链路 | 体验连贯；前端改动集中在 `constants.tsx`/`types.ts`/模式 tab + 一个执行轨迹侧栏；后端 `_pick_mode` 加一个分支 | 聊天语义与"长任务"语义有张力（工作流可能跑很久）；执行轨迹面板要新做 |
| B. 独立任务中心页 | 新增 `/tasks`，任务与工作流独立管理 | 概念干净，适合长任务；不污染聊天 | 前端工作量约为 A 的 2 倍；会话/鉴权/上传要接第二遍 |
| C. 仅后端引擎 + API | 只出 REST/SSE API + 最小演示入口 | 最快验证架构正确性 | 用户无感，价值闭环缺前端一半 |

**推荐 A**：混合架构的价值锚点是"一次对话里确定性步骤可靠、不确定探索自主"，与聊天场景天然一体；`ChatMode` 扩展链路（`types.ts` → `constants.tsx` → `usePrefs` → `sse.ts`）已被探明确认改动面小。长任务问题用"工作流总体超时护栏 + 轨迹侧栏实时反馈"缓解。

### 决策点 2：工作流定义存储与可视化程度

| 方案 | 说明 | 优点 | 代价/风险 |
|---|---|---|---|
| **A. DB 存储 + 自绘 SVG 展示 + 结构化表单编辑**（推荐） | 定义存 `workflow_defs` 表；前端 SVG 渲染拓扑与执行状态（节点亮灯），编辑用节点列表表单 | 无新依赖；展示与编辑解耦后各自简单；自绘 SVG 可控风格符合项目反模板化审美 | 编辑体验不如拖拽直观 |
| B. DB 存储 + reactflow 拖拽画布 | 引入 `@xyflow/react` | 编排体验最佳 | 重依赖；节点/边数据模型与 `WorkflowDef` 要双向映射；与现有设计体系融合成本高 |
| C. YAML 文件预置 | 启动加载，前端只读 | 最轻量 | 不支持在线编排，"可视化流程编排"要求只满足一半 |

**推荐 A**：要求 2 的关键词是"可视化流程编排、节点定义、条件分支、超时控制"，核心是让流程**可见、可配**，拖拽是体验加分项而非正确性必需。自绘 SVG 展示执行状态（节点高亮、切换点标记）+ 表单编辑，能以最小依赖满足要求且风格可控；若后续编排频率高，再升级 reactflow 不迟（`WorkflowDef` 模型不受影响）。

### 决策点 3：自动切换规则维度范围

| 方案 | 说明 |
|---|---|
| **A. 全维度**（推荐） | task_type（入口分类）+ stage（节点声明/步数）+ resource（token/时长预算）+ exception（连续失败）四类求值器 + manual，一次到位 |
| B. 异常 + 人工先行 | 只做 `exception`/`manual` 两个维度，其余下期 | 

**推荐 A**：四类求值器共享同一 `RuleCondition` 骨架，增量代码量不大（每个维度一个求值函数）；且 §3.3 的五条预置规则本来就横跨四个维度，砍掉 task_type 反而让"入口自动选初始模式"这个最自然的切换场景落空。其中 task_type 分类器**先用轻量规则**（问题长度、是否含流程关键词、会话是否绑库），不上 LLM 分类，避免入口多一次模型往返 —— 与 project memory 中"查询改写按条件启用以避免不必要 LLM 开销"的惯例一致。

### 5.2 复用要点

- Agent 引擎内部直接调 `agent/builder.py build_agent()` 与其编译缓存，**不重写** Agent 循环。
- 工具安全边界不变：`owner_id/kb_id` 仍由服务端经 `RunnableConfig.configurable` 注入。
- 编排器/工作流图编译沿用 `builder.py` 的 LRU 缓存模式（定义内容哈希做 key）。
- SSE 协议只加 `workflow_node` / `mode_switch` 两个事件类型，前端 `sse.ts` 解析扩展即可。
- 引擎内部所有 LLM 调用（规划、分类）显式传 `max_tokens`（补齐 project memory 记录的已知缺口）。

### 5.3 测试策略（要求 8）

**单元测试**（pytest 风格，沿用现有约定）：

- `TaskContext` 序列化/反序列化往返、版本号递增、schema 校验失败路径。
- 工作流引擎：线性流、条件分支命中/未命中、节点超时触发、节点内重试耗尽后进入切换判定、`on_fail` 跳转。
- 切换引擎：每条预置规则的命中/不命中、优先级排序、防抖窗口内同方向二次切换被抑制、人工切换插队立即生效。
- 表达式求值器：合法条件求值、注入式表达式被拒绝。

**集成测试**（mock LLM，沿用现有 api 层测试 mock 方式）：

- 端到端降级接管：工作流节点失败 → 自动切 Agent → Agent 产出回写 `shared` → 任务完成，断言 `mode_trace` 与 `exec_logs` 完整。
- 端到端收编回归：Agent 达到预算 → 校验产出契约 → 工作流从断点续跑而非从头。
- 边界容错：连续双向切换防抖、上下文快照损坏时报错而非带病运行、流程总超时兜底终止、Agent 产出不符合契约时拒绝切换。
- 回归：现有 39 项测试保持绿色。

## 6. 风险与开放问题

1. **乒乓切换**：规则配置不当可能在两种模式间来回抖动。已以防抖窗口 + 每任务切换次数上限（建议 5 次，超出则锁定当前模式并记日志）兜底。
2. **Agent 产出契约**：收编回归依赖"Agent 产出可被 schema 校验"。拟采用 system prompt 强约束 + 校验失败重试一次 + 再失败转人工/报错的阶梯策略，契约本身的健壮性需要真实任务打磨。
3. **工作流版本**：定义热更新时进行中的 run 仍按启动时快照执行，`WorkflowDef.version` 落库到 run 记录保证可回溯。
4. **开放问题**：`human` 节点（人工确认挂起/恢复）本期是否实现？建议本期只留类型与挂起/恢复协议骨架，UI 下期做——待评审确认。
