### 🔴 查出一处「重复实现」：auto 配额两边都做了

`core/quota.py` 冲突的真正原因不是位置，而是**我和队友各自独立加了同一个 `auto` 维度**：

| | main 侧（我，17:11 `20514eb`） | feat 侧（队友） |
|---|---|---|
| 配置名 | `DAILY_AUTO_LIMIT` | `DAILY_AUTO_LIMIT`（**同名**） |
| 默认值 | 20 | 20 |
| 中文文案 | 「每日定时委托」 | 「每日自动任务」（措辞不同） |
| `history()` 零填充 | ✅ **改成了由 `_LIMITS` 派生** | ❌ 仍硬编码 `("ask","embed")` |

⇒ **合并时保留我这版**。理由（实跑代码确认）：
- 我的版本 `history()` 用 `out.append({"day": d, **{k: 0 for k in _LIMITS}})`，
  **新增配额种类不必回来补这里**；他那边第 214 行还是
  `out.append({"day": d, "ask": 0, "embed": 0})` —— 只写死两种，
  `auto` 的历史数据在趋势图里会是 0，看起来像「从没调用过」。
- 第 230 行同理，我用 `r["kind"] in _LIMITS` 而他写 `in ("ask","embed")`。

**⇒ 这一条要同步给林宏亮**：不是「改 his 代码」，是「合并时取我这版，因为我的覆盖了 auto」。
文案差异（「每日定时委托」/「每日自动任务」）让他定，我倾向用「每日定时委托」
（更准确，`auto` 这个名字在别处指的是自动任务类别，不只是委托）。

⚠️ 这也说明**两边在同一个方向上独立干活会撞车** —— `auto` 配额、usePrefs 修复
都是同一件事做了两遍。好在两处都不是「我覆盖他」的坏结果（我的都是超集），
但**这个模式值得在组会上提一句**。

- dev 的改动以「性能优化 + 检索质量」为主，冲突集中在 5 个后端文件，人工可判断；

  合并基线更新，减少二次冲突。
