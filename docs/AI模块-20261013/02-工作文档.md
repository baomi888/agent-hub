## 一、为什么这么做（六个决定，以及当时否决了什么）

### 1. 为什么现有 5 个工具是「直接工具」而不是延迟工具

**你的原话**：「延迟工具那一块要做，现在我们已经拥有的作为直接工具，而不是延迟工具。
服务于以后的定时生成每日总结的功能」。

这条决定我完全按你说的落地，并且在代码里写成了硬约束：

- 5 个工具**全部 `defer=False`**，每轮全量下发（`core/tool_registry.py` 的 `TOOL_META`）
- 延迟机制（`shouldDefer` + 元工具发现）**照样实现**，服务对象是**未来的**打卡 / 导图 / 定时投递类工具
- 自测里专门有一条断言 `deferred_names() == []`，把"现在没有延迟工具"钉住——
  避免后来人看到机制就顺手把现有工具标记成延迟

**为什么这个顺序是对的**：延迟发现是**为规模买的保险**。它的收益取决于"工具数量多到 schema 体积肉疼"，
而现在只有 5 个工具，提前启用只会让 agent 多一次发现往返、还多一个失败点。
但机制要先建好——等真加了工具再补，就得改 Agent 主循环。

> 实测证据：`GET /api/agent/tools` 返回 5 个工具、`defer` 全为 `false`；
> `deferred=true` 返回空（正确行为，不是坏了）。

### 2. 为什么调度用「独立 worker」而不是在后端进程里跑

三个方案对比后选独立进程，理由是**故障隔离**而不是性能：

| 方案 | 否决理由 |
| --- | --- |
| 后端进程内 APScheduler | 总结生成要 20~40 秒，与在线问答抢同一个事件循环；后端重启会丢任务 |
| 服务器 crontab | cron 表达式活在机器上而不是代码里，看不见、审不到；**无法逐条按用户配置触发** |
| **独立 worker 进程（选定）** | 与 web 彻底隔离；调度表落库、可在代码里审；worker 挂了只影响定时任务，问答照常 |

**代价我明说了**：`deploy.sh` 要多管一个进程、多一条日志、多一处告警。
这不是白送的，已写进 spec §6 待定项与接口文档的定时任务一节。

**静默故障是这件事最危险的地方**：worker 挂了但 web 正常，用户只会觉得"今天没收到提醒"。
所以健康判定用**心跳年龄**（>300s `stalled`、>600s `down`），而**不是看进程表**——
进程在但卡死（比如被一次 LLM 调用挂住）同样要被抓住。

### 3. 为什么蒸馏检索是「叠加」而不是「替换」

你问过"这里的蒸馏检索是什么"，我给的判断是**上下文蒸馏**：入库时用一次 LLM 把对话提炼成结论，
检索阶段只负责"查找"结论。依据是你们自己的学习资料（`learning-materials/ai-agent-book/book/chapter2.md:954`
的"检索而非推理"；`:812` 给出正规名 Context Distillation）。

**关键决定：不动现有的文档层检索。** 你们已经在跑的"三段式重排"（候选池扩召回 → 余弦离群过滤 → MMR）
一个字都不改，结论层是**叠在上面**的第二层。理由：

1. 三段式重排是申报书里已经写进去的技术点（`申报书B3定稿.md:34`），推翻它等于推翻已定稿的内容
2. 两层的检索单位不同（chunk vs conclusion），混在一个候选池里会让 MMR 的去重逻辑失真
3. 申报书的叙事必须是"**两层检索**"，而不是"重做了检索"

**兜住幻觉的那道闸**：`source_refs` 是防幻觉固化的唯一手段——指向不存在消息的条目**不许入库**；
提炼结果默认进候选池（`status=candidate`），**系统不自动升级**为正式知识。
这正是你在 `we/先进产品思路吸收.md:40` 写的"不可指回原文的话不许入库"。

### 4. 为什么不推翻 LangChain 的 `@tool`，而是另建一张元数据表

参照 mewcode 的工具模块后，我的取舍是：**要它的元数据，不要它的运行时**。

- mewcode 用 `interface Tool` 把能力声明成接口方法（`category()` / `shouldDefer()`），引擎读声明做决定
- 本项目用 `@tool` 装饰器 + `bind_tools`，这是现成的 function calling 链路

推翻它等于自建协议层，成本极高、收益为零。所以**保留 `@tool`，另建 `TOOL_META` 表**：
引擎读表，LLM 只看到 schema。代价是"两处要人工同步"——所以 `assert_meta_complete()`
在**导入时**做全量校验，漏配直接让服务起不来。

> **为什么宁可起不来**：漏配元数据的后果是引擎在**运行时**按默认值做决定
> （比如把本该串行的写工具当成 read 并发出去）。那种 bug 极难定位，
> 远不如启动就炸来得痛快。

### 5. 为什么先写文档、再写测试文档、最后才实现

这是你的明确要求，而且顺序本身有技术理由：

1. **接口文档先冻结契约** → 实现时有唯一参照，不会出现"代码怎么写、文档回头补"的漂移
2. **测试文档先写** → 逼我在实现前想清楚"怎么证明它对了"。本轮的 13 组用例里有 4 组
   （幂等、重试分级、时区、静默故障）在写的时候就想清楚了判据，实现时直接照着写
3. **实现** → 有前两步兜着，出错时能立刻判断是"实现错了"还是"契约本身有问题"

### 6. 为什么用 Python 3.12 而不是机器上默认的 3.14

`requirements.txt` 钉死了 `chromadb==0.5.23` / `langchain 1.4.1` / `langgraph 1.2.11`，
这批版本**装不上 Python 3.14**。机器上有 uv 的 **Python 3.12.15**，用它建了 venv：

```
C:\biancheng\.scratch\ifdoc\venv312
pip install -r requirements.txt  → 成功（chroma-hnswlib 本地编译通过）
```

**这一步是整轮工作的前提**：环境跑不起来，后面"你亲自测"就无从谈起。
我没有为了让它在 3.14 上跑而改依赖版本——那会让线上与本机不一致。

### 2.4 本轮踩到并修掉的四个真问题

**① 跨库查表（我自己写的 bug，冒烟测试抓出来的）**
`GET /api/delegate/{id}/runs` 返回 500 `no such table: job_runs`。
根因：`job_runs` 住在**调度库**（`data/scheduler.db`，见 `core/scheduler.py::_db_path()`），

> 这个 bug 单元测试抓不到——必须真起服务打请求才暴露。这是"真机冒烟"必须存在的理由。

**② 合并留下的语法错误**
队友把 `main` 并入 `dev` 时，`api/chat.py` 的 `_build_messages` 合并残了一行 `) -> list:`，

**它自报"5 个文件冲突全部清除"，但 `git status` 里那三个文件仍是 `UU`（未解决）** —— 解了没 `git add`。

**③ Mock 时间戳整体差一年**
接口文档正文写 `2026-10-12`，但**全部 62 个 Mock 时间戳实际落在 2025 年**（`1760281200` = 2025-10-12）。
用脚本按"同年月日 +1 年"（+31536000 秒）确定性平移，带断言校验，改后 62/62 全部为 2026。

**④ 中国区搜索锚定差点丢掉**
合并时若直接取 dev 的 `core/serper.py` 统一入口，会丢掉 main 的 `gl=cn / hl=zh-cn`
（`edc781b` 的改进）——dev 版的请求体只有 `q` 和 `num`。已补回。

## 五、给评审/接手者的三个提醒

1. **改 `defer` 之前先读 `core/tool_registry.py` 的模块 docstring** —— 它写清了"现有工具是直接工具"
   这个口径的来由；顺手把现有工具标成延迟会让 Agent 多一次发现往返。
2. **`job_runs` 在 `data/scheduler.db`，不在 `sessions.db`** —— 跨库查表是本轮踩过的坑。
3. **两套 cron 时间要错开分钟**：SQLite 在 WAL 下是单写者，`delegate.dispatch`（`*/5`）与
   `delegate.retry`（`7,22,37,52`）刻意错开，同分钟并发会互相等锁。
