### ★★★ 1. 聊天附件的 `path` 完全不校验：任意登录用户可读服务器任意文件

**文件**：`api/chat.py:145-151`（`_image_to_data_url`）、`:154-168`（`_build_vision_user_message`）

```python
# :161-166
path = a.get("path")
if not path or not os.path.exists(path):
    continue
content.append({"type": "image_url",
                "image_url": {"url": _image_to_data_url(path)}})
```

`ChatRequest.attachments: list[dict]`（`:63`）里的 `path` **由前端原样回传**，
后端只做了 `os.path.exists()`，**没有任何"这个路径必须在 `CHAT_UPLOAD_DIR` 里"的判断**。

链路是这样的：`/api/chat/upload` 返回服务端绝对路径（`:127`），前端存下来再塞回 `/api/chat/stream`。
但 `/api/chat/stream` 不校验它。于是只要能登录，就能让服务端 `open()` 任意路径：

- `{"type":"image/png","path":"/root/.env"}` → 读走 **DeepSeek / 百炼 / 高德的 API Key**
- `{"type":"image/png","path":"C:\\...\\data\\.auth_secret"}` → 读走**会话签发密钥**，可伪造任意用户令牌
- 读走别人 `data/kb_sources/` 下的原始文档

`_image_to_data_url` 还会把内容 base64 后**发给第三方视觉模型**（阿里百炼 qwen-vl-plus），
等于是一条把本地文件内容往公网搬运的通道。

**为什么值得改**：这是本轮唯一一条**能直接拿到密钥**的缺口，而且门槛只是"注册一个账号"。
`ALLOW_SIGNUP` 默认开着（`core/config.py:70`），所以门槛 ≈ 0。
历史 9 份报告从未提过——因为大家都在看"上传"这条路径，没人看"回传"。

**怎么改**（5 行，零依赖）：

```python
# api/chat.py，_build_vision_user_message 里
base = os.path.realpath(CHAT_UPLOAD_DIR)
p = os.path.realpath(a.get("path") or "")
if not p.startswith(base + os.sep):
    continue          # 不在附件目录里，一律忽略
```
顺带两点：① `os.path.realpath` 而不是 `abspath`，软链接也能挡；
② `_image_to_data_url` 是**同步读文件 + base64**，在 async 生成器里会堵事件循环，
建议 `await asyncio.to_thread(_image_to_data_url, p)`。

### ★★★ 2. `delete_kb` 与 `upload` 的加锁顺序相反 → 死锁（已实测复现）

**文件**：`kb/pipelines.py:333-337`（`delete_kb`）vs `api/kb.py:120-121`（`upload` 的 `_build`）

两条路径的加锁次序正好反过来：

| 路径 | 位置 | 顺序 |
| --- | --- | --- |
| A 删库 | `pipelines.py:333` → `:336` | 先 `_REGISTRY_LOCK` → 再要 `kb_lock` |
| B 上传 | `api/kb.py:120` → `:121` | 先 `kb_lock` → 再要 `_REGISTRY_LOCK`（`get_or_create` → `owner_of`） |

`_REGISTRY_LOCK` 是 `RLock`，但**只在同一线程内可重入**，跨线程就是普通互斥锁。

**实测**（`/tmp/t_deadlock2.py`，严格复刻两条路径的加锁次序）：

```
日志: ['B 持有 KBLOCK', 'A 持有 REGISTRY，准备要 KBLOCK']
A 仍在等: True | B 仍在等: True
结论: ★ 死锁成立（A 持 REGISTRY 等 KBLOCK，B 持 KBLOCK 等 REGISTRY）
```

`api/kb.py:258-259` 的 `delete_file` 与 `kb/importer.py:86-87`、`:252-257` 的导入路径
**用的是同一套反向次序**，所以中招的不止上传。

**为什么值得改**：一旦触发，`_REGISTRY_LOCK` 被永久持有 ⇒
**所有知识库的列表/状态/归属校验全部卡死**（`owner_of` 也要这把锁），
现象是"整个页面转圈"，且必须重启进程。上传一个库要几十秒（embedding），
这个时间窗口并不窄。

**怎么改**（推荐 A，改动最小）：

- **方案 A**：`delete_kb` 里把 `kb_lock` 提到 `_REGISTRY_LOCK` **外面**：
  先 `lk = kb_lock(kb_id)`，再 `with lk: with _REGISTRY_LOCK:`，与上传路径对齐。
  `kb_lock()` 自身只在取锁对象时短暂拿 `_REGISTRY_LOCK`，不会引入新反转。
- **方案 B**：全局约定"**`kb_lock` 永远是最外层**"，并把这条写进 `pipelines.py` 文件头 docstring。
  本项目的历史教训就是"同一规则这处遵守、那处漏了"，写进 docstring 比靠记性好。

### ★★★ 3. 登录接口的"防计时侧信道"是假的：实测 0.00ms vs 65.56ms

**文件**：`core/account.py:143-147`

```python
row = get_user_by_username(username)
if not row:
    # 走一次等价耗时的散列，让"用户不存在"和"密码错"的响应时间一致
    verify_password(password, "pbkdf2_sha256$1$AA==$AA==")   # ← 轮数是 1
    return None
```

注释写的是"等价耗时"，但**哑串的轮数写死成 1**，而真实口令用的是
`config.AUTH_PBKDF2_ROUNDS = 200000`（`core/config.py:72`）。

**实测**（20 次取中位）：

| 场景 | 耗时 |
| --- | --- |
| 用户名不存在（dummy，**1 轮**） | **0.00 ms** |
| 用户名存在、密码错（**20 万轮**） | **65.56 ms** |

差了四个数量级，网络抖动都盖不住。⇒ `api/auth.py:99-101` 那句
「用户名不存在与密码错返回同一句话，不提供枚举线索」**只挡住了响应体，没挡住响应时间**。
攻击者只要遍历用户名看响应耗时，就能把注册用户名单摸出来。

**怎么改**（3 行）：把哑串的轮数改成真实轮数。

```python
if not row:
    # 轮数必须和真实散列一致，否则"用户不存在"会快四个数量级
    verify_password(password, _DUMMY_HASH_TEMPLATE % config.AUTH_PBKDF2_ROUNDS)
    return None
```
> 更稳的做法：直接用 `hmac.compare_digest` 比对两个**同样轮数**的摘要，
> 或者干脆给 `authenticate` 加一个进程内固定下限（比如"至少睡到 60ms"）。
> 前者的好处是机器变快时不用重调参数。

### ★★ 4. 部署在公网 HTTP 上，但 Cookie 没有 `Secure`：口令与令牌明文传输

**文件**：`core/auth.py:144-158`（`set_session_cookie`）

```python
kwargs = {
    "key": COOKIE_NAME, "value": token,
    "max_age": ..., "httponly": True, "samesite": "lax", "path": "/",
}   # ← 没有 secure=True
```

注释里写着「Secure 只在 https 下加，否则本地 http 调试会直接丢 Cookie」——
**这条注释对本地调试成立，但对公网部署不成立**。站点实际跑在
`http://8.163.62.25:3000`（`deploy.sh` 放行 3000），是明文 HTTP：

- 注册/登录时**口令原文**走公网明文（`:87`/`:103` 签发令牌前必然过一次登录请求）
- 之后**每个请求都带着 7 天有效的会话令牌**明文（`:179` `request.cookies.get`）

同一 WiFi / 任意中间节点抓一次包就能拿到 7 天令牌，且**令牌无法撤销**（见第 5 条）。

**怎么改**（按成本从低到高）：

1. 让 `Secure` 可配：`core/config.py` 加 `COOKIE_SECURE`（默认 `not DEBUG`），
   `set_session_cookie` 里 `"secure": config.COOKIE_SECURE`。本地 http 仍可关掉。
2. **真正的解法是上 HTTPS**：域名 + 免费证书 + 反向代理，然后 `Secure=True` + HSTS。
   这一步同时能顺手解决 10-02 记的「公网 http 下 clipboard / geolocation 不可用」——
   浏览器只在安全上下文暴露这两个 API，现在定位是服务端兜底才勉强能用的。
3. 过渡期缓解：`AUTH_TTL_DAYS` 从 7 调小（比如 1），缩小令牌泄漏后的可用窗口。

> 备注：本项目后端只监听 `127.0.0.1:8000`，前端走 Next rewrite，
> 所以"加密"这件事只发生在浏览器 ↔ 3000 端口这一段，正好是暴露在公网的那一段。

### ★★ 5. 令牌无法撤销，也没有任何改密入口

**文件**：`core/auth.py:109-118`（`create_token`）、`:161-162`（`clear_session_cookie`）、
`api/auth.py:107-110`（`logout`）

- **全项目没有修改密码的端点**：`api/auth.py` 只有 `config / register / login / logout / me`。
  口令一旦设置就改不了，也无法在疑似泄漏时自保。
- 顺带：改密/删号后，旧令牌仍可通过 `get_current_user`（`:171-183`），
  只有 `me()` 会在用户被删时兜一层（`api/auth.py:118-121`）。

**怎么改**（两档）：

- **只做一半也行**：先加 `token_version` 与改密端点，不做"退出所有设备"的 UI。

### ★★ 7. `create_kb` 不查重名：新建同名库会静默复用旧库（连旧文件一起带过来）

**文件**：`kb/pipelines.py:281-294`

```python
kb_id = new_kb_id(owner, name)     # md5(owner|name)[:12] —— 同名必然同 id
_KB_NAMES[kb_id] = name
_KB_OWNERS[kb_id] = owner
```

`api/kb.py:183-193` 的 `create_kb` 只校验了 `name` 非空，**没有查这个 owner 是否已有同名库**。
而 `new_kb_id` 是 `md5(owner|name)` 的确定性哈希 ⇒ **同一个用户建两个同名库，算出的是同一个 kb_id**。

后果：用户以为"新建了一个空库"，实际拿到的是**上次那个库**（连同里面的文件和片段都在）。
`list_all` 也不会多出一项（`mine` 是 kb_id 的集合）。
接着上传文档就成了往旧库里追加，用户完全不知道。

**怎么改**（二选一）：
1. `create_kb` 里先查：`if kb_id in owned_kb_ids(owner): 409 "已存在同名知识库"`。
   成本最低，语义也最符合直觉。
2. 允许重名：`new_kb_id` 掺入时间戳/uuid，展示名保留原名。改动大一些，还得处理重名展示。

### ★★★ 14. 登出不清理会话/消息/知识库 state：换账号能看到上一个账号的聊天记录

**文件**：`frontend/src/app/page.tsx:92-98`、`:475-480`；`lib/hooks/useAuth.ts:84-91`

```ts

const authedId = auth.me?.user.id ?? null;
useEffect(() => {
  if (!authedId) return;          // ← 登出时直接 return，什么都不清
  void reloadSessions();
  void refreshKbs();
}, [authedId]);
```

```ts
// useAuth.ts:84-91
const logout = useCallback(async () => {
  try { await api.logout(); } catch { }
  setMe(null);                    // ← 只清了自己这一个字段

```

`page.tsx:475` 是 `if (!auth.me) return <AuthGate .../>` —— **提前 return，但 `Home` 的 hooks 全部保持挂载**，
`useSessions` 里的 `sessions / messages / activeSid` 和 `useKnowledge` 里的 `kbs` 一点没动。

换一个账号登录后会连锁出三件事：

1. **`messages` 没被清** ⇒ 对话区直接显示**上一个账号的聊天记录**（跨账号数据泄漏，肉眼可见）。
2. `reloadSessions()` 换成了新账号的列表，但 `activeSid` **仍是上一个账号的 sid**（真值），
   于是 `useSessions.ts:145` 的自动选中守卫 `if (activeSid || !sessions.length) return;` **直接返回**，
   永远不会选中新会话。
3. 此时发一条消息 ⇒ `sendMessage` 拿 `activeSid`（旧 sid）请求 ⇒
   后端 `store.get_conversation(uid, req.sid)` 归属不符 ⇒ **404，且配额已经扣了**（第 9 条）。

**为什么值得改**：这是把 10-06 刚落地的多用户隔离**在前端又捅穿了**——后端守得再严，
上一个用户的聊天内容已经显示在屏幕上了。而且触发条件极普通：退出 → 换个号登。

**怎么改**（约 10 行，两处）：

```ts
// useAuth.ts：logout 里广播一个"已登出"事件（和 401 走同一套机制）
const logout = useCallback(async () => {
  try { await api.logout(); } catch { }
  setMe(null);
  window.dispatchEvent(new Event("baomi:signedout"));
}, []);
```
```ts
// page.tsx：新增一个 effect 收听，把三个域的 state 全清掉
useEffect(() => {
  const clear = () => {
    setSessions([]); setActiveSid(null); setMessages([]);
    useKnowledgeClear();        // 需要 useKnowledge 暴露一个 clear()
  };
  window.addEventListener("baomi:signedout", clear);
  return () => window.removeEventListener("baomi:signedout", clear);
}, [...]);
```
> 更彻底的做法是给 `Home` 加 `key={authedId}`，换人时整个子树重挂载。
> 但那会连带把 `prefs`、主题等一起重置，改动面大；先做上面的定向清理。

### ★★ 15. SSE 与所有 fetch 都没有超时：后端挂住就永远转圈

**文件**：`frontend/src/lib/sse.ts:38-45`、`lib/api.ts:36-47`

`sse.ts` 的 `fetch` 只传了 `signal`（由 `stopSending` 主动 abort 时才会有值），
**没有 `AbortSignal.timeout(ms)`**；`api.ts` 的 `request()` 连 `signal` 都没有。

后端 `/api/chat/stream` 一旦卡在 embedding / LLM 上不返回（或连接半开），
前端的 `for await` 会一直等，`sending` 永远 `true`，气泡永远是"生成中…"，
**用户既看不到错误也没法重试**（只能刷新页面）。

**怎么改**（2 行）：

```ts
// sse.ts：把调用方传进来的 signal 与超时信号合并
const timeout = AbortSignal.timeout(120_000);
const res = await fetch("/api/chat/stream", { ..., signal: signal ? AbortSignal.any([signal, timeout]) : timeout });
```
`api.ts:request()` 同理加 `signal: AbortSignal.timeout(30_000)`。
超时后 `catch` 里区分 `e.name === "TimeoutError"`，提示"响应超时，请重试"。

### ★★ 16. `useSessions.selectSession` 仍无请求序号守卫（沿用 10-07 #14，跨两轮未修）

**文件**：`frontend/src/lib/hooks/useSessions.ts:90-101`

`setActiveSid(sid)` → `setMessages([])` → `await getSession(sid)` → `setMessages(...)`，
**没有序号/取消守卫**。而同文件 init effect `:51` 有 `alive`、`:147` 用了 `setTimeout` 清理——
又是一处"同文件内不对称"。快速连点 A → B，`getSession(A)` 若更慢，**A 的历史会显示在 B 上**。

修法（3 行）：`const seqRef = useRef(0)`，进入时 `const seq = ++seqRef.current`，
返回后 `if (seq !== seqRef.current) return;`。

## 附：本轮的方法论（下次直接用）

1. **★ "输入是怎么回到服务端的"这条回路最容易漏审。**
   本轮头号发现（附件 `path`）就在这里：大家都审了"上传"（`save_stream`、扩展名、大小），
   没人审"上传成功后前端把服务端路径**原样回传**、后端直接 `open()`"。
   ⇒ **凡是"服务端生成 → 前端暂存 → 再回传"的字段（路径、id、文件名），一律当作不可信输入。**
2. **★ 两把锁 = 必须查锁序。** 项目里有 `_REGISTRY_LOCK` 和 `kb_lock` 两把锁之后，
   每次新增持锁代码都要问"别人的顺序是什么"。本轮实测复现了死锁（A 持 RL 等 lk / B 持 lk 等 RL），
   而这类 bug **靠读代码很容易看漏，靠 20 行复现脚本一测就出来**。
   ⇒ 有多把锁时，**写个复现脚本比反复读代码划算**。
3. **"注释声称做了防护"的地方要实测，不能看注释。**
   `core/account.py:145` 明写"让响应时间一致"，实测 0.00ms vs 65.56ms。
   这是"注释与代码不符"的第 3 例（前两例：`get_or_open()`、`KBBuildRequest`）。
   ⇒ **安全类注释一律当成待验证声明。**
4. **换维度扫，别在同一个维度里深挖。** 前几轮都在"功能正确性"和"性能"维度上扫，
   本轮换成"并发 / 侧信道 / 传输层 / 前端跨账号状态"四个新维度，**一天挖出 6 条新东西**。
   ⇒ 当 mtime 显示代码没动时，**换维度比加深度有效**。
5. **沿用项不要重复展开，但要在速查表里给"证据列"。**
   本轮 19 条沿用项压成一张表，每条只写"去哪一行能看到它还没改"，
   正文 100% 留给新增项——否则报告会被历史条目淹没，用户也看不出今天到底新发现了什么。
6. **"上一轮建议只做了一半"是高产切入点。** 本轮 #8（`top_k` 补了下界没补上界）、
   #12（写路径重读、读路径不重读）、#6（SSRF 修了、大小上限没修）全是这个形状。
