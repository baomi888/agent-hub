## 〇、一句话总纲

**C 方案拍板，一次性全量做，不拆 A/B 两期。**
理由：A（入库打标）与 B（对话画像）虽然解耦，但**它们的公共依赖是同一件事——受控词表**。
分两期做，等于把词表定两次、让两个钩子各写一套标签，最后必然对不齐。
**词表先行，然后 A、B 一次做完**，成本比分两次更低。

## 一、逐条回复六个待确认问题

### 问题 1：受控词表由谁定义？复用模板广场的 tags 还是另起学科/技能树？

**答：另起，且不与模板广场的 tags 混用。**

已核实：现有 `tags` 只有 `core/templates_catalog.py:35-153` 的 8 个模板标签
（`["时间规划","真题解析","考点梳理"]` 这种），前端 `page.tsx:174` 渲染成 chips。
**它是模板的营销标签、没有落表、也不是用户画像** —— 所以不存在"复用"的选择，
那两件事服务不同目的，混一起只会互相污染。

**词表设计已单独出稿**：[`受控词表设计稿.md`](受控词表设计稿.md)，要点：
- 三个维度：`weak_topic`（薄弱点）/ `interest`（关注）/ `skill`（技能）+ 文档侧 `topic`
- 命名三级：`math.geometry.solid_aux_line`，**ID 稳定不变，显示名可变**
- **别名映射表是真正的工作量**：模型说"空间向量"要能归到标准 ID
- 不在词表内的**不倒掉，进 `tag_candidates` 候选池**，每两周晋升一次（词表要能自己长大）
- **学科技能书 = 词表 + 先修关系 + 掌握度基线**，是同一样东西的高成熟度版本。
  **建议先做词表，下期挑 1 个学科试点技能树**——一上来写全学科树需要学科专家，且课程一变就僵化

### 问题 2：先做 A 部分最小演示，还是一次性做 C 全量？

**答：一次性做 C 全量。** 理由见 §〇。

### 问题 3：画像聚合频率，每天 03:00 合适吗？

**答：可以，但建议改成"每日总结之后"（约 23:35），而不是独立的 03:00。**

| | 03:00（原建议） | 23:35（建议改为） |
| --- | --- | --- |
| 当天数据成型 | 滞后一天 | ✅ 当天成型 |
| 与每日总结的关系 | 两次夜间批处理，各扫一遍库 | ✅ **复用同一个批处理窗口**，不重复扫库 |
| 追溯边界 | 快照时间与总结日期错开，排查麻烦 | ✅ `generated_at` 与总结 `date` 对齐 |
| 错峰折扣 | ✅ 22:00–8:00 有折扣 | ✅ 同样在错峰区间内 |

**并补一条**：每日固定之外，再加"攒够阈值触发"（如一天内攒够 50 条标签也跑一次），
避免"聊得特别多的一天要等到深夜"。两个触发都用现有 `job_runs` 的
`UNIQUE(idem_key)` 幂等键去重，**不新增机制**。

**完整论证（含 Mem0 / Memobase / 认知科学三分类的对照）见**：
[`../调研/用户画像聚合时机.md`](../调研/用户画像聚合时机.md)

> 补充一条你文档里没提但很重要的：**门槛应该放在聚合层，不是抽取层**。
> 抽取时能抽就抽（weight=1 先存），聚合时才执行"重复≥2 次或用户修正过"。
> 若在抽取时就按门槛丢弃，"第一次出现"的信号就永久丢了，等不到第二次。

### 问题 4：标签抽取模型复用 deepseek，还是换轻量小模型？

**答：抽取换轻量档，对话保持 deepseek 不动 —— 按任务分工，不搞一刀切。**

理由：抽取的本质是**"从封闭词表里选 + 输出 JSON"**，不需要推理能力，而它频次最高。
让最贵的模型干最不需要智商的活，是纯浪费。

已取到官方实价（百炼，$/百万 token）：

| 档位 | 输入 | 输出 | 用途建议 |
| --- | --- | --- | --- |
| `qwen-flash` | 0.022 | 0.216 | **标签抽取、蒸馏全量回溯** |
| `qwen3.7-flash` | 0.028 | 0.110 | 同上备选（≤32K） |
| `qwen3.7-plus` | 0.276 | 1.101 | 每日总结（输入大） |
| DeepSeek | 现状 | 现状 | **对话问答，不动** |

**另外三个省钱的杠杆比换模型更管用**（都是官方规则）：
1. **Batch 调用半价**：每日总结、标签回溯、蒸馏全量都是非实时任务 → 直接砍半
2. **上下文缓存命中按 10% 计费**：我们的 system + 词表 + 画像前缀每轮重复 → 正是缓存场景
3. **错峰折扣（22:00–8:00）**：定时任务本就跑在深夜 → 白捡

**完整对比、准入门槛（JSON 合法率/词表命中率/一致性/延迟）与行动项见**：
[`../调研/模型选型调研.md`](../调研/模型选型调研.md)

### 问题 5：对话钩子必须异步 fire-and-forget、不阻塞 SSE —— 认同吗？有更优解吗？

**答：认同，这是硬约束。但要补三件事，否则"异步"会变成"悄悄丢"。**

**为什么必须异步**（三个具体后果，不是洁癖）：
1. **首字延迟**：抽取要走一次 LLM 往返（2~8s）。同步做等于让用户等一个与他问题无关的操作。
   你们 `api/chat.py:289-297` 已经吃过同类教训——流一旦开始，想再回 429 都来不及。
2. **占着 worker**：uvicorn 单进程，一次问答占一个协程；同步抽取把"等模型"绑在用户请求上，并发一上来就拖住服务。
3. **失败会污染体验**：抽取失败（限流/超时）会变成用户看到的错误，而它**跟用户的问题毫无关系**。

**必须补的三件事**：

| 补什么 | 怎么做 | 为什么 |
| --- | --- | --- |
| **幂等去重** | `(sid, 最后一轮 message_id)` 做键 | 重复投递不能重复抽取（复用你们 `job_runs` 的 `UNIQUE(idem_key)` 风格） |
| **有界队列 + 背压** | 队列满则丢弃并**记日志** | 宁可少抽一条，不能把服务拖垮 |
| **失败可重试** | 按 `core/scheduler.py` 已有的 `CLASS_RETRY` / `CLASS_FATAL` 分级 | 超时/5xx 可重试；401/402 直接放弃（重试只烧钱） |

**一个必须点明的风险**：你方案里写"抽取失败静默降级（try/except 吞掉）"——
**吞掉异常可以，但不能吞掉记录**。至少要 `logging.warning` 留痕，
否则出了问题没有任何线索知道"画像为什么少了几天"。

### 问题 6：前端「我的画像」页要不要在组会前上？

**答：不上，而且这个页面本身要取消——画像对用户不可见。**

这是本次回复里唯一一条**改变方案原设计**的意见，理由：

1. **产品定位决定**：个性化能力是我们对**模型侧**的服务（让回答更贴这个用户），
   不是给用户看的功能。用户要的是"你懂我"，不是"你把我分析成了 47 个标签"。
2. **展示即承诺**：一旦做出来，用户会要求可编辑、可删除、可解释，
   而我们没有精力维护一套画像管理界面（那是另一个产品）。
3. **暴露风险**：画像里必然有"薄弱点""情绪状态"这类敏感推断。
   给用户看，等于把模型的误判直接摆到台面上。

**因此对方案 §4.4 的修改**：
- ❌ 删除"新增「我的画像」入口展示 `user_profile_snapshots`"
- ✅ **保留**"知识库 sources 角标旁展示 chunk `topics`" —— 这是**文档主题**（用户上传的资料讲了什么），
  不是用户画像，展示它有助于用户理解检索依据，**这条要留**

**但"不可见"必须配一个补偿机制**（否则错误会静默累积、无人可纠）：
- **内部审核通道**：一个仅管理员可见的接口/脚本，能查、能删、能改某个用户的画像
- 不要求界面，**哪怕只是个 CLI 脚本**也行 —— 但必须有

## 二、对方案本身的两条补充（不改设计，但建议加进实现）

### 补充 1：入库钩子的 `topic` 用受控词表，检索过滤才真的有效

方案 §2 方案 A 写"检索时 `where={"topics": {"$in": [...]}}` 直接按主题过滤"。
这条**只有在 topic 是稳定 ID 时才成立** —— 自由文本标签做 `$in` 过滤基本无效，因为写法对不上。
所以**受控词表是 A 部分能work的前提**，不是可选项。

### 补充 2：画像快照要带"溯源覆盖率"，并设硬门槛

建议快照结构里加 `stats.msg_backed`（多少条画像能指回原消息），
并规定：**覆盖率 < 90% 就不出快照**。理由：与其给模型一份掺假的画像，不如不给。
这也是你方案 §6 风险 1（词表爆炸）的另一半答案。

## 五、待你确认的两点（我给出的建议，需要你点头）
