> 撰写：冯靖豪 ｜ 日期：2026-10-15 ｜ 状态：**征求意见中，待林宏亮 / 刘佳林确认**
> 存放：仓库 `docs/规划/`（已从 `we/` 移至公开区，供团队评审，队友可提 issue / PR 评论）
> 背景：线上全链路已跑通（见 `项目完成状态总结_2026-10-15.md`），但「标签钩子 / 学习画像」仍是规划项（总结报告缺口 2）。
> 核心洞察：**当前向量库只有溯源级 metadata、完全没有语义标签，这个「空位」恰好是构建用户标签钩子的天然切入点**——
> 在「文件入库」和「对话落库」两个时点用 LLM 抽标签，既补全向量库 metadata（增强检索过滤），又沉淀用户画像。

---

## 一、现状（已核实）

| 层 | 现状 | 证据 |
|---|---|---|
| Chroma metadata | 只有**溯源级**字段：`source`、`source_path`、`chunk_index`、`page`；**无语义标签** | `kb/rag_core.py:706-770` |
| 会话 `messages` 表 | 只有 `role / content / time / refs`；**无 tag 列** | `core/session.py` |
| 数据模型规划 | T4 已写明：「标签未落独立表…若做学习画像，在 messages 之上另起 `user_tags` 表即可」 | `docs/数据模型_2026-10-15.md:268` |

**结论**：Chroma 本身支持 per-document metadata（且支持 `where` 过滤），只是当前代码没写入语义标签。这正是钩子的「空位」，也是本方案的出发点。

---

## 二、三套候选方案

### 方案 A：纯 Chroma metadata（轻量，检索期过滤）
- **做法**：文件入库时（**文件级**，非每 chunk）用 LLM 抽 3–5 个主题标签 → 写入每个 chunk 的 `metadata.topics`。
- **优点**：零新表；检索时 `where={"topics": {"$in": [...]}}` 直接按主题过滤；前端 sources 角标可展示标签。
- **缺点**：topic 在每 chunk 冗余存储；不适合跨文档聚合用户画像；Chroma 的 `where` 对「列表包含」支持有限、规模大时查询受限。

### 方案 B：独立 `user_tags` 表 + 对话钩子（画像向，T4 已规划）
- **做法**：新增 `user_tags(owner_id, tag, kind, weight, last_seen, source_msg_id)` 与 `user_profile_snapshots(owner_id, snapshot_json, generated_at)`；对话 `done` 时异步抽用户状态标签（薄弱点 / 关注主题 / 情绪）写入 `user_tags`；调度 worker 定期汇总成画像快照。
- **优点**：与现有 **owner 隔离**天然契合（所有函数 owner 第一参数）；画像可聚合、可溯源到消息；不污染向量库；直接支撑「学习画像」产品。
- **缺点**：多表 + 抽取调用成本；需控制抽取频率。

### 方案 C：混合（**推荐**）= A 的入库级 topics + B 的对话级 user_tags
- **入库钩子**补向量库 metadata（检索可过滤 + sources 展示）；**对话钩子**沉淀 `user_tags`（画像）；**调度钩子**聚合快照；二期再把用户 topics 作为 RAG 重排特征，实现「越用越懂你」。
- **优点**：把「向量库缺 metadata」这个缺陷正好补上（A），同时启动用户画像（B），二者解耦、可各自独立上线。
- **取舍**：工作量略大，但每块都能独立交付、独立回滚。

## 三、为什么选 C（选型论证）

> 一句话：**C 不是简单把 A、B 叠在一起，而是让 A、B 各自的短板互补，并额外形成一个 A、B 单独都给不了的闭环。**

### 3.1 只做 A（纯补向量库 metadata）的短板
A 的优点是零新表、改动小，顺手补上了「向量库缺 metadata」这个真实缺陷——这正是我们提的「据点」思路。
但它的标签**只散落在每个 chunk 上**，只能做「按主题过滤检索」，**做不出「这个用户是谁、在学什么」的跨文档画像**。标签用完即散，聚不成用户维度。也就是说：A 能告诉你「文档讲什么」，却回答不了「用户在关心什么」。

### 3.2 只做 B（独立 user_tags 表）的短板
B 能启动用户画像，且与现有 owner 强制隔离天然契合、可溯源。
但它**完全没碰向量库**：检索质量上不去（无法按主题 `where` 过滤），而且画像原料只能来自对话，**资料库上传的内容（最有价值的语料）反而没参与**——而这恰恰是我们系统里用户沉淀知识的主场景。

### 3.3 C 相对「只选 A 或只选 B」的四个优势
1. **保留「据点」思路为地基，又补完「用户钩子」**：C 的第一块就是 A（入库打标），尊重了「以向量库 metadata 为切入点」的初衷；第二块接上 B（会话级 user_tags），才真正把「用户钩子」做完整——A 给「文档有什么主题」，B 给「用户在关心什么」，两者叠加才有意义。
2. **多出一个 A、B 都没有的闭环：画像 → 检索偏置**：C 的二期把聚合出的用户画像**反向喂回 RAG 检索**，使同一句提问对不同用户返回更贴合其进度的答案。这是单纯补 metadata（A）或单纯做画像（B）都给不了的「个性化」体验，也是产品「个性化 AI 学习助手」定位的核心卖点。
3. **两块解耦，可独立上线、风险隔离**：入库打标（A）和会话画像（B）**互不前置**——A 先上、B 先上都行；A 抽标签失败不影响 B 出画像，B 调度任务挂了也不影响 A 的检索过滤，**没有单点故障拖垮整个标签体系**。
4. **成本可控、不碰现有表结构**：A 是「整文件抽一次标签」而非「每 chunk 调 LLM」；B 走异步 fire-and-forget 不阻塞 SSE；都不改 `messages` 表（独立 `user_tags` 表避开迁移），符合现有 owner 隔离与「不阻塞对话」的硬约束。

### 3.4 给组会 / 申报书的一句话结论
> 方案 C 以「补全向量库语义元数据」为切入点（补现状缺陷），叠加独立用户标签表启动学习画像，并通过二期检索偏置将画像反哺 RAG，形成「打标 → 画像 → 个性化检索」闭环；相较单独补 metadata 或单独做画像，C 既尊重工程现状又补齐个性化能力，且两块解耦可独立交付、互不拖累。

## 四、推荐方案 C 的详细设计

### 4.1 数据模型（新增，不改动现有表）
- `user_tags`：`id, owner_id, tag, kind(weak_topic|interest|mood|skill), weight(real), last_seen(int 秒), source_msg_id`。唯一键 `(owner_id, tag, kind)`，`ON CONFLICT` 累加 weight / 刷新 last_seen（幂等，符合现有 `idem_key` 风格）。
- `user_profile_snapshots`：`id, owner_id, snapshot_json, generated_at`。
- 新建 `core/tags.py`（与 `core/tool_registry.py` 同风格），所有函数 **owner 第一参数**，复用 `_conn()` 线程复用连接。

### 4.2 三个钩子点（落到具体文件行）
1. **入库钩子（ingest hook）**
   - 入口：`kb/rag_core.py` 的 `_ingest` / `upsert`（`:769-770`）前，对一个文件的全部 chunk 做一次 LLM 主题抽取（**文件级调用一次**，不是每 chunk 调一次，控成本）。
   - 写回：每个 chunk 的 `metadata["topics"] = [...]`；同时 `kb/pipelines.py:481 add_file_records` 的 files 清单加 `tags` 字段（源清单已有 JSON 落盘机制，直接扩字段）。
2. **对话钩子（chat hook）**
   - 插入点：`api/chat.py` 在 `store.add_message(assistant)`（`:429` 或 `:714`）之后、`emit done` 之前。
   - 方式：**fire-and-forget** `asyncio.create_task(extract_user_tags(owner, sid, q, a))`——**绝不阻塞 SSE**；抽取失败静默降级（try/except 吞掉，不抛前端）。抽取用 `core/llm.py::get_llm()`，结构化输出限定受控词表。
3. **调度钩子（schedule hook）**
   - 在 `worker/scheduler.py` 现有 `delegate.dispatch(*/5)` / `delegate.retry` 旁，加 `profile.aggregate`（如 `0 3 * * *`）定时汇总 `user_tags` → 写 `user_profile_snapshots`。

### 4.3 检索增强（二期，可选）
- `kb/rag_core.py` 的 `select_diverse()` 重排时，把当前用户 `user_tags`（按 `kind=interest`）作为偏置特征，提高相关 topics 的切片权重 → 「越用越懂你」。此步依赖 B 已上线。

### 4.4 前端
- 知识库 sources 角标旁展示 chunk `topics`（来自 `metadata.topics`）。
- 新增「我的画像」入口（设置页或独立页）展示 `user_profile_snapshots`。

## 六、风险与取舍

1. **标签词表爆炸** → 用**受控词表**（预定义学科/技能/主题树）+ 归并；自由文本标签另存并向量化到独立 collection（远期）。
2. **抽取成本** → 入库级每文件抽一次；对话级每轮抽但限定小模型 + 低 `max_token`；失败降级不影响主链路。
3. **owner 隔离** → 所有查询/写入带 `owner_id`（与现有强制约定一致）。
4. **不改动 `messages` 表** → 标签走独立表，避免数据迁移（与 T4 决策一致）。
5. **SSE 不被拖慢** → 对话钩子必须异步、可丢弃，绝不能让标签抽取卡住 `done` 帧。
