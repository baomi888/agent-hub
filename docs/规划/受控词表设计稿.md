## 0. 为什么先写词表

C 方案的三个钩子（入库 / 对话 / 调度）都往同一套标签上写。**词表不定，三个钩子各写各的**，
两周后就会出现：`立体几何` / `立体几何弱` / `空间向量` / `几何薄弱` / `math-geometry`
—— 同一个事实五种写法，**画像聚不起来、钩子命中不可靠、衰减无法计算**。

> 一句话：**词表是钩子、画像、检索偏置三者的公共契约。** 它先定，后面三块才可能解耦。

---

## 1. 定义与边界

**受控词表（Controlled Vocabulary）= 一张预定义的、带层级的、有取值的标签清单，
外加一份"模型怎么说 → 归到哪个词"的别名映射表。**

它做三件事：

| 做的事 | 不做的 |
| --- | --- |
| 限定**能打哪些标签**（不许编造） | 不限定"能看出用户什么"——那是提炼门槛管的 |
| 限定**每个标签的取值范围**（枚举 / 数值区间） | 不做语义检索（那是向量库的事） |
| 把**模型的自由说法映射到标准词** | 不替代 LLM 抽取本身 |

## 2. 与现有 tags 体系的关系（已取证，结论是"不冲突"）

我把仓库翻了一遍，**现有 tags 只有一处**：

| 位置 | 是什么 | 和本词表的关系 |
| --- | --- | --- |
| `core/templates_catalog.py:35-153` | 8 个模板各自的 3 个标签（`["时间规划","真题解析","考点梳理"]` 等） | **是模板的营销标签**，用于模板广场筛选。**不是用户画像，不是知识库标签，也没有落表** |
| `frontend/.../page.tsx:174` | 把上面这些渲染成 chips | 纯展示 |
| Chroma metadata（`kb/rag_core.py`） | 只有溯源级字段：`source / source_path / chunk_index / page`，**无语义标签** | 这正是 C 方案 A 部分要补的空位 |

新词表是**用户画像与知识库语义**的专用契约，独立存在。

## 3. 设计原则（四条）

1. **可枚举优先，自由文本兜底**：能枚举的绝不开放。模型只能"选"，不能"写"。
2. **不在词表内的不倒掉，进"待收录池"**：抽取时命中不了词表 → 写 `tag_candidates` 表。
   这样既保证画像是干净的，又不丢失新信号（每两周人工看一次，该晋升的晋升）。
3. **一个标签 = 一个稳定 ID**：ID 一旦发布**永不改变**，显示名可以改。
   否则改一次文案，历史画像全部断链。
4. **词表版本化**：`vocab_version` 随标签一起落库，这样能回答"这条画像当时是按哪版词表抽的"。

## 4. 词表结构

### 4.1 三个维度（kind）

| kind | 含义 | 记忆类型（认知科学） | 来自哪个钩子 |
| --- | --- | --- | --- |
| `weak_topic` | **薄弱点**：用户反复卡住的知识点 | 语义记忆 | 对话钩子 |
| `interest` | **关注主题**：用户主动关心的方向 | 语义记忆 | 对话钩子 + 入库钩子 |
| `skill` | **技能项**：做某类任务的熟练度 | 语义记忆 + 程序记忆 | 对话钩子 |
| `mood` | **情绪状态**：短期信号 | 情景记忆 | 对话钩子 |
| `topic` | **文档主题**：知识库这一篇讲什么 | —（文档属性，非用户） | **入库钩子** |
| `cause` | **错因归类**：为什么错 | 语义记忆 | 对话钩子（可选，二期） |

> `topic` 与 `user_tags` 的 kind 刻意分开：前者是**文档的属性**（写进 Chroma metadata），
> 后者是**用户的属性**（写进 `user_tags` 表）。C 方案的 A、B 两块就靠这两个 kind 解耦。

### 4.2 命名规则（ID 形态）

```
<domain>.<category>.<leaf>          例：math.geometry.solid_aux_line
```

- 全小写 + 下划线，**点分三级**，层级即前缀（便于 `LIKE 'math.geometry.%'` 聚合）
- **稳定 ID 与显示名分离**：`math.geometry.solid_aux_line` → 显示"立体几何·辅助线"

### 4.3 领域划分（domain）

不按"学科"一刀切，而是按**你们的真实使用场景**分：

| domain | 覆盖 | 说明 |
| --- | --- | --- |
| `math` | 高数 / 线代 / 概率 / 中学数学 | 考研与专业课主力 |
| `eng` | 英语：词汇 / 长难句 / 阅读 / 写作 / 听说 | 高频且错因清晰 |
| `cs` | 计算机：数据结构 / 算法 / 操作系统 / 网络 / 数据库 | 专业核心 |
| `sci` | 物理 / 化学 / 生物 | 按需扩 |
| `write` | 学术写作：文献 / 综述 / 润色 | 对应模板广场的论文类 |
| `exam` | 应试策略：时间分配 / 真题 / 心态 | 横切维度 |
| `career` | 求职：简历 / 面试 / JD 匹配 | 对应模板的求职类 |
| `meta` | **元标签**：学习习惯 / 交互偏好 / 工具偏好 | 这类**不绑学科**，但要画像 |

> **`meta` 这一域容易被忽略但很重要**：像"晚上更容易接受长解释""偏好先给答案再给推导"
> 这种偏好不属于任何学科，却直接决定"怎样服务这个用户"。书里说的
> User as Code / 显式槽位，主要就是存这类东西。

### 4.5 每个 kind 的取值形态

| kind | 值 | 范围 |
| --- | --- | --- |
| `weak_topic` / `interest` / `topic` / `skill` / `cause` | 枚举 ID 列表 | 必须命中词表 |
| `weight`（累积强度） | real | 0~∞，抽取命中 +1，衰减见 §6 |
| `mood` | 枚举：`confused` / `anxious` / `confident` / `frustrated` / `neutral` | 五档，**不许自创** |

## 5. 别名映射表（真正的工作量在这里）

**词表好写，映射表要养。** 模型会说人话，映射表把它拉回标准词。

```yaml
# vocab_aliases.yaml  —— 键 = 标准 ID，值 = 模型可能的说法（命中即归并）
math.geometry.solid_aux_line:
  - 立体几何
  - 空间几何
  - 辅助线
  - 做辅助线
  - 空间想象
  - 立体图形不会做
math.geometry.solid_vector:
  - 空间向量
  - 向量法解立几
eng.long_sentence.clause_nesting:
  - 定语从句嵌套
  - 从句套从句
  - 长难句看不懂
  - 句子结构理不清
eng.long_sentence.subject_verb:
  - 找不到主干
  - 主谓宾分不清
  - 主语谓语识别
```

**匹配策略（三级，先精确后模糊）**：

1. **精确命中别名** → 直接用（覆盖 80%）
2. 未命中 → 用 embedding 在**别名集合**里找最相近的（阈值 0.82），命中则归并
3. 仍未命中 → 写 `tag_candidates(tag_text, first_seen, count)`，**不进画像**
   —— 每两周人工审一次，够多的晋升进词表（这也让词表能自己长大，不用一开始就写全）

## 6. 聚合与衰减（画像快照怎么算）

对应征求意见稿的"调度钩子 `profile.aggregate`（如 `0 3 * * *`）"。

```
用户画像快照 = 按 kind 分组，对 user_tags 做加权聚合
权重 = Σ (1 × 命中次数) × decay(now - last_seen)
decay(d) = 0.5 ** (d / HALF_LIFE_DAYS)      # 半衰期建议 30 天
```

**快照结构（固定槽位，对齐 Memobase 的主题—子主题两级思路）**：

```json
{
  "vocab_version": "2026.10.15",
  "generated_at": 1760000000,
  "stable": {
    "domain_focus": ["cs.data_structures", "math.linear_algebra"],
    "learning_style": ["meta.prefer_example_first", "meta.night_long_form"],
    "skill_level": {"skill.code_handwrite": "shaky", "skill.apply": "stable"}
  },
  "dynamic": {
    "recent_weak": ["math.geometry.solid_aux_line"],
    "recent_mood": "anxious",
    "window_days": 7
  },
  "stats": {"tag_count": 42, "msg_backed": 38, "candidate_backlog": 7}
}
```

> `stats.msg_backed` 是**溯源覆盖率**：多少条画像能指回原消息。
> 建议设硬门槛：**低于 90% 就不出快照**——与其给模型一份掺假的画像，不如不给。

## 7. 抽取流水线（怎么写进两个钩子）

```
原文（一轮对话 / 一篇文档）
   ↓ LLM 结构化抽取（prompt 里给词表 + 要求只输出 ID）
候选标签（可能含自由文本）
   ↓ ① 词表校验：不在表内 → tag_candidates（丢弃，不进画像）
   ↓ ② 别名归并：自由说法 → 标准 ID
   ↓ ③ 溯源绑定：每条标签必须带 source_msg_id / chunk_index
通过
   ↓ ④ 幂等写入：UNIQUE(owner_id, tag, kind) + ON CONFLICT 累加 weight
user_tags
   ↓ 调度聚合（profile.aggregate）
user_profile_snapshots
```

**抽取 prompt 的三条硬要求**（决定词表能不能被守住）：

1. **只输出词表内的 ID**，并在 prompt 里附上当前 domain 的叶子词清单（不能给全表，太长）
2. **允许输出空**：`[]` 是合法答案。否则模型会为了"有输出"而硬凑标签
3. **要求给出证据**：每条标签附 `evidence`（原文片段），无证据的丢弃 —— 这是溯源闸门在抽取层的落实

## 8. 与三个钩子的对接点

| 钩子 | 写入什么 | 落到哪 | 对应文件（征求意见稿 §4.2） |
| --- | --- | --- | --- |
| **入库钩子** | `topic` 域标签 | Chroma `metadata.topics` + files 清单 | `kb/rag_core.py` upsert 前；`kb/pipelines.py:481` |

| **调度钩子** | 聚合结果 | `user_profile_snapshots`（含 `vocab_version`） | `worker/scheduler.py` 新增 `profile.aggregate` |

**词表对入库钩子的额外好处**：`topic` 是稳定 ID ⇒ Chroma 的 `where={"topics": {"$in": [...]}}`
才是**精确过滤**（自由文本标签做 `$in` 过滤基本无效，因为写法对不上）。

## 9. 受控词表 vs 学科技能书：关系与取舍

你问的第 1 问里有这一层。我的结论：**它们是同一样东西的两个成熟度**，不是两条路。

```
受控词表（现在要做的）    = 带层级的 ID 清单 + 别名映射 + 取值约束
        ↓ 加两样东西
学科技能书（可选的下一步）  = 词表 + ①先修关系（prerequisite）  ②掌握度评测基线
```

| 加什么 | 得到什么能力 | 成本 |
| --- | --- | --- |
| 受控词表 | 画像可聚合、钩子可精确命中、检索过滤可用 | 中（写词表 + 养映射表） |
| ＋先修关系 | "你卡在 B 是因为 A 没掌握" —— **可解释的学习路径** | 高（要懂学科的人写依赖） |
| ＋掌握度基线 | "你在立体几何上落后同龄 30%" —— **可比性** | 高（要基线数据） |

**建议路径**：
1. **本期**：只做受控词表（本文档）。标签从对话里长，词表人工维护 + 待收录池自动长大。
2. **下一期**：挑**一个** high-yield 学科（建议 `math.geometry` 或 `eng.long_sentence`）
   补先修关系，验证"可解释路径"能不能讲通、用户买不买账。
3. **不要一上来写全学科技能树**：那需要学科专家，且课程一变就僵化；
   而**词表能从真实对话里长出来**，这是它比技能树更适合早期产品的地方。

> 与书里的印证：`chapter3.md:224` 讲 Memobase 用"开发者配置的槽位、按主题—子主题两级组织"
> —— **受控词表正是把这句话落成可维护的形式**；而书里 `:237` 提醒"按业务需要取舍，
> 比追求大而全更符合工程现实"，这也是我建议先词表后技能树的依据。

## 11. 待你/团队确认的三点

1. **domain 划分是否够用**：我按"你们的真实场景"分了 8 个域（math/eng/cs/sci/write/exam/career/meta）。
   如果专业课覆盖不住，需要先补 `cs` 与 `sci` 的叶子表。
2. **`meta` 域要不要现在做**：它直接支撑"怎样服务这个用户"（对应你第 6 点的画像），
   但不属于任何学科，容易被漏。我建议**做**，因为它是画像里最有价值的一类。
3. **词表由谁维护**：建议指定一人每周花 30 分钟看候选池并晋升。
   没有人维护的词表会在两个月内失效——这是它最大的运维风险。
