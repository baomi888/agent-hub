# 对话页三端：输入框收小、正文拓宽、吉祥物跟着屏走

2026-11-14 第七批。用户的原话是三条：「iOS 端首页对话框小一点」「优化对话页面排版，
输出后吉祥物尺寸随页面变化」「手机能显示的文字区域不够多，要像 DeepSeek 但保留吉祥物」。

一句话结论：**手机上正文从每行 16.8 字提到 19.4 字，输入框从 72px 降到 56px，
滚动区多出 34px；桌面几乎不动（只验证，不改）。**

---

## 一、先把「不够多」量出来

一台 390×844 的手机打开「六级复习」，正文实测：

```
正文宽 268px / 字号 16px = 每行 16.8 字
```

而同一套样式在 768 与 1440 下都是 **38.5 字/行**、616px。也就是说手机上不是
"字小"，是**横向被吃掉了 56px**：

| 吃掉宽度的东西 | 改前 | 改后（≤560） |
|---|---|---|
| 消息区左右内边距 | 24 + 24 | **14 + 14** |
| AI 头像 | 44 | **26** |
| 头像与正文的间距 | 12 | **8** |
| 正文可用宽 | 268（16.8 字） | **310（19.4 字）** |

390 的物理满宽是 24 字（390/16）。要真做到 DeepSeek 那种满宽，就得把头像摘掉 ——
用户明确说「保留吉祥物」，所以 19.4 是**有意的上限**，不是没做完。
26px 的头像能认出是玉米、看得出思考态（嘴变○），但眨眼和腮红已经看不清了；
44px 才能看清那些细节。这条取舍写进了 CSS 注释，免得下一个人"顺手优化"回去。

---

## 二、改了什么

| 项 | 改前 | 改后 | 为什么要动 |
|---|---|---|---|
| 顶栏高（390） | 54 | **46** | `py-3` → `py-2`，手机上纯装饰的留白 |
| 能力条 + 间距 | 28 + 8 | 26 + 6 | 药丸高度与下边距各收 2px |
| 输入框（390） | 72 | **56** | 内边距 12/16 → 8/10，发送键 40 → 32，文本域行内边距 10 → 6 |
| 底部留白 | 20 | **12 + 安全区** | iOS home 指示条会压住输入框（见下） |
| 底部整块 | 128 | **102** | 以上三项合计 |
| 滚动区（390） | 644 | **678** | 多出的 34px 全给了消息 |
| 用户气泡最大宽 | 75% | **85%**（手机） | 243px 的提问比 310px 的回答更挤，看着错位 |
| 正文行高（手机） | 1.9（30.4px） | **1.8（28.8px）** | 每行 19 字时 1.9 会把 6 行段落拉成 182px |
| 首屏吉祥物 | 44（三处写死，桌面被压低） | **48 / 52 / 56 + 矮窗 38** | 一个变量 `--hero-mark`，JSX 里不再写尺寸 |
| 对话中头像 | 44 | **44 / 34 / 26** | `--ai-mark` 三档，桌面不变 |
| 表格（手机） | 5 列被压成"一个字一列" | **卡片式竖排** | 见第四节 |

桌面（1440）与平板（768）的横向**刻意不动**：768 的 616px、38.5 字/行本来就在
中文舒服区（30–40），为了"三端一致"去改它只会把它推出舒服区。平板只收顶栏
（56→52）、底部（130→126）和头像（44→34）。

## 三、iOS 安全区：这是真机上会坏的

`layout.tsx` 的 viewport 早就写了 `viewportFit: "cover"`，但首页输入区的
`pb-5` 是写死的 20px。cover 模式下 iOS 的 home 指示条（34px）会**压在输入框上** ——
发送键正好在横条底下。这次改成：

```css
.chat-dock { padding-bottom: calc(var(--chat-dock-pb) + env(safe-area-inset-bottom, 0px)); }
```

用 `calc` 而不是固定值：横屏时 env 为 0，多加的那截会自动消失。

> ★ **这一版被真机反馈推翻了**（当天晚上，用户附 iPhone 截图：「底部留白有点多」）。
> `calc` 的加法本身没错，错在**重复计算**：`main.workbench-main` 的底边距只有 8px，
> 那 8px 已经在 34px 安全区里面，卡片内再让整整 34px 就多出 8px；再加 `--chat-dock-pb`
> 的 12px，输入框离屏幕底变成 54px。修法与实测见第八节。

> 诚实标注：这一条**没有在真机上验过**。headless Chromium 里 `env()` 恒为 0，
> 探针量到的底栏 102px 就是"安全区为 0"时的值；真机 iPhone 上应该是 102 + 34 = 136。
> 公式对不对可以读代码确认，效果要等真机。

## 四、表格：先试了横向滚动，最后改成卡片

手机上那张六级分数表原来是 5 列挤在 310px 里：

```
板块            题数    分值        你的得分   得分率
A、               15      15          8        53%
B篇               题      分
（长
对话
+篇
章）
```

第一版修法是给 `.md-table` 加 `min-width: 28em` —— `.md-table-wrap` 本来就有
`overflow-x: auto`，只是 `width:100%` 让表格永远不溢出，那个 auto 从没起过作用。
加上之后确实能读，但实测两个问题：

1. **142px 之外看不见，而手机没有任何滚动条提示** —— 用户只会以为表格被裁坏了；
2. **滑到右边时表头已经滚出视野**，那一列是什么就不知道了（我们没做 sticky 表头）。

所以改成卡片：`thead` 隐藏，每个 `td` 靠 `data-label` 自己说明属于哪一列。
列名由 `content.tsx` 从表头剥掉 markdown 记号后写入：

```tsx
const labels = head.map((c) => c.replace(/[*`]/g, "").replace(/\[([^\]]*)\]\([^)]*\)/g, "$1").trim());
...
<td data-label={labels[ci] ?? ""}>
```

手机上每一行变成「板块 / A、B 篇（长对话+篇章）」这样 5 行，宽 310px 全部读得下，
不用滑、不会溢出。代价是高度：一张 3 行的表从约 120px 变成约 330px。
在 310px 的正文里，"看得全"比"省高度"重要。

桌面完全不受影响 —— 这条只在 `≤560` 生效，块级化漏到桌面会让列对齐全丢。

## 六、这一批自己踩的坑

1. **`_media()` 用 dict 存同条件的块会互相覆盖**。`chat.css` 里有两个
   `@media (max-width: 560px)`（令牌档、输入框档），第一版只剩后一个，
   于是"手机版心 14px"那条断言直接红。**如果反过来剩下的是前一个，
   那条"输入框变小"的断言就会永远绿** —— 改成同条件累加才安全。
2. **反证脚本第一版 5 条 SKIP**。原文片段是 `\n` 分隔，而文件是 CRLF，
   `old in src` 永远为假。SKIP 被我算成失败才没漏过去；
   如果判据写成"没红就算过"，这 5 条会静默消失。
3. **拍空态时以为 `?sid=` 指向的一定是空会话**。`ca6f88752d4b` 标题是"新对话"
   但里面有 6 轮消息，拍出来还是对话态。最后用 API 新建了一个真空会话，
   拍完删掉（27 个会话里没有残留）。
4. **公告遮罩每页都弹**。第一轮 7 张图全是"十一月更新 · 装到桌面"，
   而 DOM 量测照样是对的 —— 数据有效、图没用，两件事必须分开确认。
   这次每页导航后都摘一遍（`.ann-page` / `.guide-mask` / 任意 modal，
   再恢复 `body.style.overflow`）。
5. **桌面截图里量到的 `--chat-px` 是 24，而 CSS 里 base 也是 24** ——
   这条差点被当成"改动没生效"。真正变了的是手机档，桌面本来就该不变。

## 八、第八批：底部留白 54 → 34（真机反馈）

用户附 iPhone 截图：「现在手机端的底部留白有点多」。量出来的账是这样的：

| 组成 | 值 | 该不该留 |
|---|---|---|
| `main.workbench-main` 底边距（≤899 档） | 8px | 该，卡片浮起的呼吸 |
| `--chat-dock-pb`（手机档） | 12px | 该，输入框到纸边的呼吸 |
| `env(safe-area-inset-bottom)` | 34px | 该，home 指示条 |
| **合计** | **54px** | 但其中 8px 被算了两次 |

第三项是全份叠上去的，而卡片底边距屏幕只有 8px —— home 指示条那 34px 是从
**屏幕底**算的，卡片内只需要再让出 `34 − 8 = 26` 就能完全避开它。所以：

```css
/* 改前 */
padding-bottom: calc(var(--chat-dock-pb) + env(safe-area-inset-bottom, 0px));
/* 改后 */
padding-bottom: max(
  var(--chat-dock-pb),
  calc(env(safe-area-inset-bottom, 0px) - var(--app-edge-y))
);
```

用 `max` 而不是减法，是因为减完可能是负数（安全区为 0 时 `-8px`），
`max` 让"没有安全区"的环境自然落回令牌值，横屏也不会多出一条空白。

`--app-edge-y` 是新令牌（桌面 14 / ≤899 档 8），**必须与 base.css、fx.css 里
`main.workbench-main` 的真实 margin 一致**。这条漂了只在真机能看出来：扣多了输入框
压到指示条上（点不到发送键），扣少了又变回留白过多。`test_app_edge_matches_card_margin`
跨三个文件钉住了它。

### 三端读数（线上，注入 34px 安全区实测）

headless 里 `env()` 恒为 0，所以这一批的关键验证靠 CDP 的
`Emulation.setSafeAreaInsetsOverride` 注入真值：

| 视口 | env=0 时 pad | 注入 34px 后 pad | 输入框底到屏幕底 | 改前（env=34 时） |
|---|---|---|---|---|
| 390 | 12 | **26** | **35** | 46 / 55 |
| 768 | 16 | 26 | 35 | 50 / 59 |
| 1440 | 20 | 20 | 66 | 20 / 66（env 恒 0，不变） |

对照图是同一页面、同一 34px 安全区，只差那一条 `padding-bottom`：
`.workbuddy/tmp/shots-dock8/390_before.png`（46px）与 `390_after.png`（26px）。

### 这一批踩的坑

1. **`insets: null` 不复位**。Edge 157 上 `Emulation.setSafeAreaInsetsOverride({insets:null})`
   会静默失败，下一个视口的「env=0」读数其实还是上一轮的 34 —— 我第一次就据此读到
   768 的 pad 是 26，而它应该是 16。必须显式传 `{top:0,left:0,bottom:0,right:0}`，
   并在每次复位后重新量一次 `env()` 确认归零。
2. **反证脚本把异常吞了**。第一版 `try/finally` 里写 `return`，`finally` 的 return 会
   覆盖 try 抛出的异常，打印出来是「0/0 真红，异常 0」—— 反证脚本自己假绿了一次。
   结构改成 `try/except` 打印 traceback、`finally` 只做还原。
3. **`Path.read_text(newline=...)` 要 Python 3.13**，本地 3.12 直接 TypeError。
   本地绿、线上挂的老形状，只是这次落在脚本上而不是产品代码上。
4. **桌面不该拍「改前」**。桌面 env 恒为 0，改动前后都是 20px；在桌面上套
   `calc(pb + env)` 只会拍出一张带 34px 安全区的假对照图。对照只对手机那档成立。

### 仍未验

- 真机上的最终观感：26px 里 home 指示条会占去一部分，视觉上应该比截图更满；
  但"够不够贴"只有用户的眼睛能判。
- 键盘弹起 + 安全区叠加（`100dvh` 收缩时 dock 是否跟着抬）。
