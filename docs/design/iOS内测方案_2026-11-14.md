## 3. iOS 端功能矩阵（要你拍板）

### 3.1 核心发现：移动端导航与产品定位错配

`frontend/src/lib/nav.ts` 里，导航顺序是给**桌面侧栏**排的：

```
对话(1) 资料库(2) 论坛(3) 待办(4) 每日委托(5) 总结(6) 打卡(7) 四六级(8) 学习路径(9) 工具集(10) 设置(11)
```

而 `TAB_PRIMARY_COUNT = 4`，手机底部 tab **直接取前 4 个**。

⇒ **「学习路径」在手机上没有任何一级入口**，要进「更多」翻到第 9 项。而它的定位是「和对话平行」的核心（申报书 3.4）。

**这不是样式问题，是架构缺陷**：导航清单只有一个维度（桌面顺序），没有「移动端权重」。

### 3.2 建议的移动端结构

| 位置 | 模块 | 理由 |
|---|---|---|
| **tab 1** | 对话 `/` | 最高频 |
| **tab 2** | 学习路径 `/path` | 核心定位，必须一级可见 |
| **tab 3** | 论坛 `/forum` | UGC 浏览是手机原生场景 |
| **tab 4** | 打卡 `/checkin` | 轻交互、每天一次，最适合手机 |
| 「更多」 | 资料库 `/knowledge` | 检索型，手机可用但非高频 |
| 「更多」 | 待办 `/reminders` | 3769 行最重的页面，需真机重点验 |
| 「更多」 | 工具集 `/tools` | 独立单页，不套外壳 |
| 「更多」 | 设置 `/settings` | 低频 |
| **移出移动端** | 每日委托 `/delegate` | 1072 行，任务生成后实际看的是对话，手机无独立场景 |
| **移出移动端** | 总结 `/report` | 报表型，需横向对比，窄屏体验差 |
| **移出移动端** | 四六级 `/cet` | 长周期备考，主要在电脑做计划；单词卡已在工具集里 |
| 恒隐藏 | 工作流 `/flow`、看板 `/dashboard` | 已是 `adminOnly`，手机上永不需要 |

> **重要：「移出移动端」= 只删导航入口，不删代码、不删路由。**
> 桌面侧栏照旧能进，后端接口不动，代码零删除。这是一条可逆的改动。

### 3.3 实现方式（改 `lib/nav.ts` 的模型，不是改顺序）

```ts
export interface NavItem {
  href: string;
  icon: string;
  label: string;
  adminOnly?: boolean;
  /** 手机底部 tab 是否出现（不填 = 不进 tab） */
  mobileTab?: boolean;
  /** 完全不进移动端：侧栏可见，「更多」里也不出现（桌面仍可用） */
  desktopOnly?: boolean;
}
```

然后 `ConsoleTabBar` 从 `mobileTab === true` 取，不再按 `slice(0, TAB_PRIMARY_COUNT)`。
**这样桌面顺序可以继续为桌面服务，移动端有自己的排序**——两个维度解耦。

⚠️ 落地时必须同步 `tests/test_*` 里对 `TAB_PRIMARY_COUNT` / `visibleNav` 的断言，否则会出现「源码改了测试还绿」的假象（本项目踩过，见 `topics/05`）。

### P0（不做内测就不成立）

#### P0-1 `viewport-fit=cover` 缺失 → 刘海/灵动岛遮挡

**问题**：全站写了大量 `env(safe-area-inset-*)`，但 `layout.tsx` 的 `viewport` **没有设 `viewportFit: "cover"`**。
在 iOS 上，没有 `viewport-fit=cover` 时 `env(safe-area-inset-*)` **恒为 0** —— 也就是说那些安全区代码从来没生效过。

这直接解释了「论坛线未上真机」这个欠账的后果：**这套 PWA 从没在 iPhone 独立窗口里打开过。**

**改法**（`src/app/layout.tsx`）：
```ts
export const viewport: Viewport = {
  width: "device-width",
  initialScale: 1,
  viewportFit: "cover",        // ← 新增，safe-area 才会生效
  themeColor: [...],
};
```

**判据**：真机添加到主屏后打开，页头顶部不被刘海压住、底部 tab 不被 Home 指示条压住。

#### P0-2 暗色模式状态栏黑字不可见

**问题**：`appleWebApp.statusBarStyle: "default"`（黑字）。暗色模式背景是 `#1A1610`，状态栏黑字 = 看不见。

**改法**：改 `statusBarStyle: "black-translucent"`，配合 P0-1 的 safe-area padding 让内容延伸到状态栏下。
**副作用**：所有页面顶部必须有 `padding-top: env(safe-area-inset-top)`，否则内容被状态栏盖住。
**判据**：浅色 + 暗色两种模式下，状态栏文字都清晰可读。

#### P0-3 移动端导航重排（§3）

**改法**：`lib/nav.ts` 加 `mobileTab` / `desktopOnly`，`ConsoleTabBar.tsx` 改用筛选。
**判据**：手机上 tab 是「对话 / 学习路径 / 论坛 / 打卡」；「更多」里没有每日委托/总结/四六级。

## 9. 决定：暂停原生 App，移动端继续用 PWA（2026-11-14）

### 9.1 结论

**不做 iOS 原生客户端，至少现在不做。** 移动端继续用「Safari → 添加到主屏幕」的 PWA。

### 9.2 理由（三条，按硬度排序）

**① 推送这件事上，iOS PWA 反而是最优解 —— 这是硬证据，不是妥协。**

项目已完整实现 Web Push：`frontend/src/lib/push.ts` + `public/sw.js` 的 `push` 事件
+ `core/push_store.py` 订阅表。而 `push.ts` 开头的注释写明了底层事实：

> 安卓的 Web Push 底层一律走 Google 的 FCM，这个域名在中国大陆连不通（换浏览器不解决，
> 全走系统 FCM）。真正可用的只有：iPhone/iPad 装到主屏（走苹果 APNs）、Windows 上的 Edge（走微软 WNS）。

**⇒ iOS PWA 是当前环境下唯一真正能响的系统级推送。安卓端反而收不到。**
所以「PWA 够用」在提醒功能这个具体诉求上是成立的，不是将就。

**② 688 元不是最贵的方案，但它是「现在还不值得」的方案。**

要「像小软件一样浏览器下载安装」，技术上只有 Ad Hoc（$99/年 + 100 台 UDID 白名单），
或企业证书（$299 + D-U-N-S + 公司实体，学生团队申不下来且会掉签）。
用户提到的「改设置同意信任」属于后者，是别人替你把钱付了，不是零成本。

三条免费路都不成立：免费 Apple ID 只能 3 台 / 7 天重签（老师不可能每 7 天插电脑）；
学校 Fee Waiver 要法人实体 + 2–6 周审核且可被拒；越狱对现代 iOS 不现实。
**结论不是「贵」，是「内测阶段这 688 换不到对应的东西」。**

**③ Web 还没到「值得包一层」的程度。**

App 壳里的全部内容就是 `https://myzhisui.cn`。Web 一改，App 立刻同步 —— 这是优点，
但它也说明：**壳不增加任何功能，只增加分发渠道和图标。** 分发渠道现在只有 5 个人
+ 老师需要，用 PWA 能覆盖。

### 9.3 重启的三个触发条件（任一成立）

写下来是为了让「等 Web 成熟」不变成一句永远不兑现的话。

1. **出现非团队成员的真实用户想装。** PWA 的死穴就在这里：教不会陌生人「添加到主屏幕」，
   也没法出现在应用商店里被搜到。只要有人问「有 App 吗 / 在哪下载」，分发需求就真实存在了。
2. **推送到达率不够用。** PWA 推送依赖「已加到主屏 + 用户授权 + 未清站点数据」三件事
   同时成立，任何一环断了就静默失效，而**你无法知道用户的订阅什么时候掉的**。
   APNs token 比这稳定。
3. **有人愿意出这 688**（学校账号 / 教改经费 / 报销批下来）。成本一旦不是障碍，性价比立刻翻过来。

### 9.4 重启时怎么做（别从零开始）

`tsc` 退出 0、`expo-doctor` 20/20、`expo export --platform ios` 打出 612 模块 / 977KB。
恢复成本 = 账号到位后跑三条命令，详见 `mobile/README.md` 第十、十一节。

### 9.5 「Web 成熟」目前没有可衡量的定义，补三条

1. 有非团队成员的真实用户（不只是同学帮忙点）
2. 核心链路不用人教就会用：对话 → 学习路径 → 打卡
3. 一周内没有必须热修的问题

三条都达到，就是重启的时机 —— 那时候学校账号大概也有结论了。

### 9.6 这一轮哪些工作没有白做

暂停时最容易误判的是「前面做的都浪费了」。实际上**只有 `mobile/` 那个原生壳是闲置的**，
其余全部服务于现在正在用的 PWA：

| 改动 | 现在的用途 |
|---|---|
| `layout.tsx` 的 `viewportFit: "cover"` | PWA 全屏时安全区才生效，否则 iOS 上恒为 0 |
| 六处容器的 `safe-area-inset-top` | PWA 黑透状态栏下内容不被刘海压 |
| 9 张 `apple-touch-startup-image` 启动屏 | **PWA 从主屏幕启动同样用它** |
| `statusBarStyle: black-translucent` | PWA 的状态栏样式，同一份配置 |
| 学习路径挪进手机 tab | Web 端导航，与 App 无关 |
| `tools/make_ios_splash.py` / `make_app_icons.py` | 改尺寸表后重跑，PWA 与 App 共用素材 |

### 9.7 当前唯一的技术欠账

**没有任何一台真机看过效果。** 黑透状态栏是否真的压住内容、启动屏是否还闪白、
底部 tab 有没有被 Home 指示条盖住，全都只验到「HTML 里有这个标签」这一步。
`env(safe-area-inset-*)` 在 devtools 模拟器里恒为 0，模拟不出来。

→ **这条与做不做 App 无关，PWA 也得验。** 验收清单见 §6，判据不变。
