# 对话页左栏：把模块入口接回共享清单（2026-11-15）

> 这是 `docs/design/UI审查_oil-ui_2026-11-15.md` 里 **P0 第 1 条** 的执行记录。
> 线上 `BUILD_ID b5IzEkcgV6_X3eV2Gq3H2`（09:12:27 构建 / 09:12:33 启动）。

## 一、问题不是"入口太少"，是"入口是另一份清单"

审查时读到的事实：手机点开对话页左上角，抽屉里只有 **4 项** —— 委托 / 总结 / 待办 / 设置。
而对话页在手机上**没有底部 tab**（第十批之前为了给正文腾高度刻意撤掉的，用户当时的原话是
"手机端的能显示文字区域还是不够多"）。也就是说：

> 这一栏不是"侧栏"，它是手机在对话页的**唯一**模块入口。

于是资料库、论坛、学习路径、打卡、工具集、看板 —— 六个页面在对话页上无路可走。
论坛页更彻底：底栏没有、产品侧栏没有，只有左上角 28×28 的 logo 能回首页。

更矛盾的是抽屉里那两项：**委托 / 总结**。它们在 `lib/nav.ts` 里恰恰标着
`desktopOnly: true`，注释原文是"移动端彻底不出现"。同一份产品，两处清单给出了相反的答案。

根因很简单：`Sidebar.tsx` 里有一个 `CONSOLE_LINKS` 常量，硬编码了 4 个 href。
`nav.ts` 的头注释写着"三处共用一份清单，各写一份迟早漂移"—— 而实际上只兑现了两处
（`ConsoleLayout` 的桌面侧栏、`ConsoleTabBar` 的底部 tab +「更多」面板），
第三处从来没接上去。

## 二、改法：派生，而不是再抄一份

```ts
// lib/nav.ts
export function chatRailNav(isAdmin: boolean | undefined, narrow: boolean): NavItem[] {
  return visibleNav(isAdmin).filter((it) => it.href !== "/" && !(narrow && it.desktopOnly));
}
```

三个语义一次说清：
- 排掉「对话」自己 —— 当前页不该出现在导航里；
- `adminOnly` 交给 `visibleNav(isAdmin)`，看板与工作流只给管理员；
- `desktopOnly` **只在窄屏过滤**。窄屏的判据是 `overlay`（这一栏此时就是抽屉），
  而不是"是不是手机" —— 900 宽时它仍是常驻左栏，和工作流共用一套 12 项。

`Sidebar.tsx` 里 `CONSOLE_LINKS` 整个删掉，改成 `chatRailNav(isAdmin, overlay)`；
`page.tsx` 多传一个 `isAdmin={auth.me?.is_admin}`。

图标同时从 `CornIcon` 换成 `NavIcon`。这不是顺手改的：同一个功能在底部 tab、
「更多」面板里都是 NavIcon（book / forum / star / path / tools / dashboard），
而抽屉用的是另一套手绘图标（clock / calendar / task / settings）——
同一个「待办」在两处长得不一样，用户会以为是两件事。`nav.ts` 里存的 icon 名本来就是
NavIcon 的名字，接过来正好对上，一行都没改。

## 三、版面：3 列紧凑格

| | 改前 | 改后 |
|---|---|---|
| 手机（管理员） | 4 项，2×2 金描边按钮 | **8 项**，3+3+2，末行居中 |
| 手机（普通） | 4 项 | **7 项**，3+3+1 |
| 桌面（管理员） | 4 项 | **12 项**，4 行整 |
| 桌面（普通） | 4 项 | **10 项**，3+3+3+1 |
| 单格 | 101×56，14px | 65×46，13px |
| 会话列表可用高度（390） | — | 170px（仍能看见 2 组、4 条） |

三点判断：

1. **去掉金描边。** 4 个金框是"次按钮"，12 个金框就是一堵按钮墙。导航该像列表：
   默认无边框，hover 给底色 + 淡描边，`aria-current` 才算选中。描边保留为
   `1px solid transparent`，hover 只换颜色 —— 否则多出 1px 边框会让整格抖一下。
2. **13px 不是审美，是量出来的上限。**「学习路径」四个字 4×13 = 52px，
   格子内容宽 57px；14px 时会溢出成「学习路…」。实测 390/768/1440/1000 四个宽度、
   管理员与普通账号各一轮，`scrollWidth > clientWidth` 全部为 0。
3. **`flex-wrap + justify-content: center` 而不是 grid。** 8 项 ÷ 3 余 2，
   grid 的末行只能左对齐，右下角就空一格 —— 这正是第十批在「更多」面板里
   改掉的那个"缺角"。实测「设置」left = 108 = (390−175)/2 一类居中位置。

## 五、四个自己挖的坑

1. **`read_text` → `write_text` 会把 CRLF 归一掉。** 反证脚本第一版用它还原文件，
   把三个文件的混合行尾洗成纯 CRLF，md5 对不上 —— 差点被当成"还原逻辑写错了"。
   改成按字节读写。
2. **反证只验数据、不验逻辑会漏。** 把 `visibleNav(isAdmin)` 改成 `visibleNav(true)`
   （等于把看板/工作流给所有登录用户看），`nav.ts` 的数据一个字没变，所有数据断言照样绿。
   反证第 ④ 条就是这么"没红"的 —— 补了函数体断言才咬住。
3. **`Path.read_text(newline=)` 是 Python 3.13 的 API**（本地 3.12 直接 TypeError）。
   这个坑这个月踩了第三次，一律改 `open(..., newline="")` 或字节读写。
4. **手工 `el.remove()` 摘 React 管的节点，会把客户端路由弄坏。**
   取证脚本里为了截图干净，会删掉 `.guide-mask` 等遮罩；不点击时一切正常（截图照样出），
   但一让脚本去点侧栏链接，五个用例全落到浏览器的 "This page couldn't load"。
   排掉之后立刻 5/5。**截图脚本可以删节点，交互脚本不行** —— 两者别共用一个 cleanup。
