## 一、后端可更新点

### ★★★ 1. 「重建整库」是先删库再重建，中途失败 = 半个知识库（且界面看不出来）

**文件**：`kb/rag_core.py:332-339`（执行删除）、`api/kb.py:331-356`（循环 + 异常处理）、`api/kb.py:358-361`（清单收尾）

```python
# rag_core.py:332-339  build_index(mode="rebuild")
if mode == "rebuild":
    client = chroma_client()
    try:
        client.delete_collection(self.collection_name)   # ← 先把旧的全删了
    except Exception:
        pass
    self._vs = None
vs = self._ensure_vs()
for i in range(0, len(chunks), config.EMBED_BATCH_SIZE):
    vs.add_documents(chunks[i : i + config.EMBED_BATCH_SIZE])   # ← 这里失败就只剩半截
```

```python
# api/kb.py:331-361  _rebuild()
for name in names:
    path = pipelines.source_path(kb_id, name)
    if not os.path.exists(path):
        continue
    n = pipe.build_index(..., mode=("rebuild" if first else "append"), ...)
    first = False
    ...
# 异常直接往上冒 → :356 raise HTTPException(500)
# :360-361 的 retain_file_records / add_file_records 永远不会执行
```

**失败后的实际状态**（这个组合才是最值钱的部分）：

| 层 | 状态 |
| --- | --- |
| Chroma | 只剩**第 1 个文件**（或前 N-1 个成功的文件）的片段，`names` 里其余文件的向量已被 `delete_collection` 清掉 |
| `kb_files.json` | **完全没动**（`retain_file_records` 没跑到），仍列着全部 N 个文件 |
| `data/kb_sources/{kb_id}/` | 原始文件还在磁盘上 |
| 前端 | 文件列表照样显示全部 N 个；点开预览走 `archive` 分支（`kb.py:293-303`，磁盘有文件）**看着一切正常**；但检索永远召回不到那部分内容 |

**为什么这条排第一**：触发成本极低。重建意味着对全部内容**重新做一遍 embedding**（会重新计费），
所以 `402 余额不足` / `429 限流` / 网络抖一下都足以半途失败——`describe_api_error`（`rag_core.py:71-72`）里就专门写了 402 的中文说明，说明这条路径是被考虑过的，
唯独没考虑"删了之后失败"怎么办。

**怎么改**（三选一，按改动量递增）：

1. **最低限度（10 行）**：`_rebuild` 外面包 `try/except`，失败时 `pipelines.retain_file_records(kb_id, {d["name"] for d in done})`，
   让清单和向量库重新对齐，并在 `HTTPException.detail` 里明确写"重建在第 X/N 个文件失败，当前库只剩前 X 个文件的内容，原始文件仍在，可重试"。
2. **推荐（20 行）**：先建一个临时 collection（`kb_{id}__tmp`），全部成功后再 `delete_collection(旧)` 并把临时库接过来；失败则删临时库、原库完好。
3. 至少把 `rebuild` 的 UI（前端第 8 条）加上二次确认 + 当前文件数提示。

### ★★★ 2. 新增的 `add_chunks()` 与老的 `build_index()` 有 4 处不对称（`chunk_index` / 回滚 / 孤儿文件）

**文件**：`kb/rag_core.py:285-299`（新写入路径）、对照 `kb/rag_core.py:315-347`（老写入路径）、`kb/importer.py:53-76` 与 `:213-234`（两条导入路径）

这是本轮最纯粹的一条「新写入路径没和老路径对齐」：

| 项目 | `build_index()`（上传走这条） | `add_chunks()`（`5c1408b` 新增，联网导入走这条） |
| --- | --- | --- |
| 写 `chunk_index` 元数据 | ✅ `:326-330` | ❌ **没有** |
| 记 `self._params` | ✅ `:346` | ❌ 没有（见后端第 3 条） |
| 失败回滚 | 部分（由 `api/kb.py:89-92` 的 `upload.cleanup()` 兜底） | ❌ **没有** |
| 源文件何时落盘 | 上传完了才入库，`except` 里有 cleanup | ❌ **先落盘后入库**，中间出错就留孤儿 |

**(a) `chunk_index` 缺失 ⇒ 联网内容的预览/还原顺序是乱的**

`get_source_chunks()`（`rag_core.py:365-392`）靠 `(page, chunk_index)` 排序；
联网导入的是 txt，`TextLoader` 不写 `page`，而 `add_chunks` 又不写 `chunk_index`
⇒ 两段 key 全部退化成 0 ⇒ `sort` 变成稳定排序，**原样保留 Chroma `get()` 的返回顺序**。
而 `add_documents()` 不指定 id 时 LangChain 用的是 `uuid.uuid4()` ⇒ **返回顺序基本是随机 UUID 序**。
结果：一旦走到"chunks 兜底"那条预览路径（`kb.py:307-317`），正文是打乱的。
同一份文件如果是用户上传的，这条路径的顺序就是对的——纯粹的入口差异。

**(b) 失败留孤儿文件**

```python
# importer.py:53-56  先写文件
dest = pipelines.source_path(kb_id, name)
with open(dest, "w", encoding="utf-8") as f:
    f.write(...)
# importer.py:60-75  才上锁 + embedding + 入库
with pipelines.kb_lock(kb_id):
    pipe.add_chunks(chunks)            # ← 这里抛 ForeignKey/quota/网络错，dest 已经在磁盘上了
    pipelines.add_file_records(...)
```

而这个孤儿文件**再也不会被任何人看到**：`rebuild`（`kb.py:325`）遍历的是 `files.json`，不是目录。
对比上传路径 `api/kb.py:89-92` 的注释——"一条都没入库，已落盘的必须清掉，否则它们成了没人认领的孤儿文件"——
同一句话，昨天新增的这条路径没做到。`download_and_index`（`:213-217` + `:226`）是完全相同的形状。

**怎么改**（约 15 行）：

```python
# rag_core.py add_chunks 内，照抄 build_index:326-330
counter: dict[str, int] = {}
for c in chunks:
    src = c.metadata.get("source") or ""
    c.metadata["chunk_index"] = counter.get(src, 0)
    counter[src] += 1
```

```python
# importer.py import_url / download_and_index：写文件挪进 try，失败清理
try:
    with pipelines.kb_lock(kb_id):
        pipe = pipelines.get_or_create(kb_id)
        pipe.add_chunks(chunks)
        pipelines.add_file_records(...)
except Exception:
    if os.path.exists(dest):
        os.unlink(dest)
    raise
```

抽一个 `_persist_source(kb_id, name, chunks)` 让两个函数共用最省事。

### ★★ 3. 切片参数从没落盘 ⇒ 重启后所有库的参数都是 null，而「重建」用的是全局偏好

**文件**：`kb/pipelines.py:389-403`（读取）、`:408-422`（预热）、`kb/rag_core.py:346`（唯一写入点）、`frontend/src/lib/hooks/useKnowledge.ts:72-80`

```python
# pipelines.py:396-401  get_status()
params = pipe._params
return {"chunk_size": params[0] if params else None, ...}
```

`_params` 只在 `build_index()` 里赋一次值，是**纯内存状态**：

- `warmup()`（`:408-422`）重启后只调 `get_or_open()`，**不恢复 `_params`** ⇒ 每次重启后 `GET /api/kb/{id}/` 的 `chunk_size` / `chunk_overlap` 恒为 `null`；
- `add_chunks()` 压根不设 ⇒ **联网建的库从建好那天起就是 `null`**；
- 前端 `rebuildKb()`（`useKnowledge.ts:73-74`）传的是**全局偏好** `chunkSize/chunkOverlap`，不是这个库当初的参数。

**两端合起来的后果**：用户在「设置」里把参数改成 800/80，回头对 A 库点"重建整库"——A 被按 800/80 重做了一遍，
而**没有任何地方记录 A 原来是什么参数**（既没记在库上，也没在确认框里提示），改完连"改回去"的依据都没有。
叠加后端第 1 条（重建会先删），这是一条会对用户数据产生不可逆影响却毫无提示的链路。

**怎么改**（后端 20 行 + 前端 5 行）：

- 在 `pipelines.py` 加一份 `kb_params.json`（或并进现成的 `kb_names.json`），`{kb_id: [size, overlap]}`；
- `build_index` / `add_chunks` 都写入；`warmup()` 读回并赋给 `pipe._params`；
- 前端重建确认框显示「当前参数 500/50 → 将改为 800/80」。
  > 顺带补一句：`useKnowledge.rebuildKb` 目前把类型写得很宽松，加了显示之后这部分最好同时传 kb 自己的参数而不是全局偏好。

### ★★ 4. Agent 工具把真实错误一律吞成「暂时不可用」，模型会原地重试而不是换路子

**文件**：`agent/tools.py:65-66`、`:124-125`、`:171-172`、`:328-329`、`:463-464`

```python
# tools.py:65-66  kb_search 的兜底
except Exception:
    return "知识库检索暂时不可用，请稍后再试。"
```

**为什么这条比它看起来严重**：工具返回的是 Observation，会直接回灌给模型。
`kb_search` 里真正高频的失败是 `retrieve_with_score` 抛的 `RuntimeError("知识库为空，请先上传文档构建索引")`（`rag_core.py:455`）——
这是个**确定性**错误，重试一万次也一样。但被吞成"暂时不可用，请稍后再试"之后，
模型读到的语义是"也许过一会儿就好" ⇒ 连着调 2~3 次同一个空库才肯换 `web_search`，白烧两三轮 token 和几秒延迟。

这正是 10-05 后端第 3 条（`chat.py` 三处 `except Exception: pass`）的 **Agent 侧孪生**——
同一份 codebase，RAG 链路那边今年反复修了两轮，Agent 这边一次都没扫过。

**怎么改**（每处 3~5 行）：按类别给**可行动**的返回：

| 情况 | 应该告诉模型 |
| --- | --- |
| `pipe.peek() == 0` / 空库 RuntimeError | "知识库 `{kb_id}` 里没有内容，改联网搜索或让用户先上传文档" |
| `describe_api_error` 命中的 401 / 402 / 429 | "接口不可用（401/402/429），本轮不要再重试该工具" |
| 其它 | 保留"暂时不可用"，但把 `str(e)` 截 80 字带上 |

最低限度：`kb_search` 把 `except RuntimeError as e: return f"知识库不可用：{e}"` 单独拎出来（1 处 import 都不用加）。

### ★ 5. `calculator` 的 DoS 闸门拦不住真正的炸弹（沿用，但口径要改）

**文件**：`agent/tools.py:130-132`、`:156-160`

```python
_CALC_ALLOWED = set("0123456789+-*/%()., **")   # ← 死常量，全项目零引用
_CALC_MAX_DIGITS = 12
...
if any(len(n) > _CALC_MAX_DIGITS for n in re.findall(r"\d+", expr)):
    return f"数字过大（单个数字不能超过 {_CALC_MAX_DIGITS} 位）。"
```

门槛卡在**字面量位数**，而真正的杀伤来自**指数大小**：
`999999999999**99999999`（12 位指数，完全合法）在 CPython 里是要算出一个约 10^8 位的整数——内存与 CPU 直接打满。
当前规则连 `9**99999999` 都放行。**要限的是 `**` 右侧的值，不是字面量长度。**

**怎么改**（3 行）：

```python
if (m := re.search(r"\*\*\s*(\d+)", expr)) and int(m.group(1)) > 1000:
    return "指数过大（** 右侧不能超过 1000），请分步计算。"
```

顺手删掉 `_CALC_ALLOWED`（留着会让人误以为有白名单在起作用）。

### ★★ 9. `webImport` 串行 10 条、不可取消，且进度里「失败」和「无标题」长得一样

**文件**：`frontend/src/app/page.tsx:387-417`，对照 `frontend/src/lib/api.ts`（全文件无 `signal` / 无超时）

```tsx
for (let i = 0; i < urls.length; i++) {

  ok += 1;
```

## 附：专项 —— 为什么每个访客看到的都是同一份数据（隐私与数据隔离）

> 这条在历史报告里一直以「后端无鉴权」的名字挂着（09-29 起提过多次）。
> 本轮换一个更准确的说法重列：**它不是"没登录"，而是"压根没有用户这个维度"**，
> 所以昨天的补救（`--host 127.0.0.1`）并不解决问题，且可能造成了"已经安全了"的错觉。

### 1. 代码证据（逐条）

| 位置 | 事实 |
| --- | --- |
| `core/session.py:56-63` | `conversations` 表字段只有 `id / title / kb_id / created_at / updated_at` —— **没有 `user` / `owner` 列** |
| `core/session.py:126-130` | `list_conversations()` 是裸 `SELECT ... ORDER BY updated_at DESC`，**没有 WHERE** |
| `api/sessions.py:43-45` | `GET /api/sessions/` 直接把上面那张全表返回给任何请求者 |
| `api/sessions.py:48-55` | 只要知道 `sid` 就能读全部消息历史；`:73` 还能删 |
| `api/kb.py:149-153` | `list_all()` 同理，列出服务器上**全部**知识库 |
| `api/kb.py:274-319` | `GET /{kb_id}/file-content` 可以**直接读到任意文件的正文原文** |
| `frontend/src/app/page.tsx:74-80` | 首屏就是 `useSessions` 拉全量渲染；全项目无登录页、无身份标识（cookie/localStorage 里也没有） |

### 2. 为什么改了 `127.0.0.1` 也没用

`frontend/next.config.ts:12-15` 把 `/api/*` **rewrite** 到 `http://localhost:8000`。
这是 Next 服务端转发，不是浏览器直连 ⇒ 后端收端口只挡住"绕过前端直接访问 8000"这条路径，
**任何能打开 `http://8.163.62.25:3000` 的人，走的仍然是同一条链、拿到同一份数据**。

### 3. 实际风险（按兑现速度排序）

1. **账单**（最快）：任何人都能在你的界面上提问，烧的是你的 DeepSeek 与百炼 embedding 额度。
2. **隐私**：聊天记录、绑定的知识库、以及**上传文档的原文**（`file-content` 端点）都能被读到。
3. **破坏**：既是"谁都能看"也是"谁都能删"——`DELETE /api/sessions/{sid}/`、`DELETE /api/kb/{id}/` 同样不设防。

### 4. 三个方案

| 方案 | 做法 | 成本 | 效果 |
| --- | --- | --- | --- |
| **A · 关公网** | 阿里云安全组里 3000 端口只放行你自己的出口 IP | 0 改动，5 分钟 | 彻底，但别人（含老师远程）看不了；汇报时临时放行即可 |
| **B · 加 Basic Auth（推荐）** | Next middleware 对全站做 HTTP Basic 校验 | 新增 1 个前端文件 + 一次 `deploy`，约 15 分钟 | 陌生人进不来；**但知道密码的人看到的仍是同一份数据**（它是门，不是隔离） |
| **C · 真隔离** | `conversations` 加 `owner` 列 + 前端匿名标识（HttpOnly cookie）+ api 层全部查询加 `WHERE owner=?`；KB 侧要把 `pipelines._KB_NAMES` / `list_all()` 也按 owner 切 | 半天~一天 | 真正的多用户，但对阶段演示不划算 |

**推荐今天做 B，演示期间临时再叠 A。** 注意一个坑：`deploy.sh:334-335` 的自检会用 curl 打 `127.0.0.1:3000/`，
加了 Basic Auth 之后它会拿到 **401** 而不是 200，会让部署脚本误报失败。
解决办法是在 middleware 里对本机来源直接放行（`request.headers.get("host")` 以 `127.0.0.1`/`localhost` 开头就 `NextResponse.next()`），
这样部署自检链路不用改。

> 另外提醒：**演示期间别往知识库里传带个人信息的真实文档**——在方案 C 落地前，
> 所有绑定了这个后端的浏览器都能通过 `file-content` 把原文读出来。
