# 修改报告：模式入口收敛与执行前路由

日期：2026-10-29　分支：`main`
对应设计：`docs/改造报告_2026-10-29_模式入口收敛与执行前路由.md`

---

## 1. 一句话结论

用户界面从「五档模式」收成「自动 / 检索 / 纯对话」；`auto` 现在由**规则 + 模型**两级判断执行路径：规则只认高置信的顺序/批量特征（命中就直接工作流起跑），其余交给一次轻量模型判断；混合与智能体不再作为按钮，但**后端能力完整保留**（内部脚本、答辩演示、能力卡兼容）。同时补上了「两条路都没产出时用 LLM 兜底作答」。

---

## 2. 改动清单

### 2.1 新增 `core/router.py`（约 230 行）

执行前路由的唯一入口。三层结构：

| 层 | 函数 | 作用 |
|---|---|---|
| 规则 | `score_flow()` / `classify_flow_open()` | 关键词打分，命中即返回 `flow`，不问模型 |
| 模型 | `_ask_model()` / `_parse()` | 一次轻量调用，输出 `{"route":"rag\|agent\|llm","reason":"…"}` |
| 兜底 | `_fallback_route()` | 超时 / 异常 / 非法输出 / 开关关闭时回落 |

两条**代码级硬约束**（不依赖提示词自觉）：

```python
if route == "rag" and not has_kb:      # 没有库却要检索 → 必然检索不到
    return RouteDecision("agent", ...)
if route == "llm" and has_kb:          # 绑了库一律给引用（含"你好"）
    return RouteDecision("rag", ...)
```

### 2.2 规则加固（核心变更）

改造前的词表是「17 个 FLOW 词 + 13 个 OPEN 词，数多者胜」。实测 24 条真实问题**误判 4 条**，全部因为单字关键词没有边界：

| 问题 | 改造前 | 命中原因 | 改造后 |
|---|---|---|---|
| 优先看第三章 | 工作流 | `先` | 模型判 |
| 先生，请问图书馆几点关门 | 工作流 | `先` | 模型判 |
| 最后一个问题：这题怎么做 | 工作流 | `最后` | 模型判 |
| 按照你说的再讲一遍 | 工作流 | `按照` | 模型判 |
| 帮我把这份笔记整理成知识卡片 | 工作流 | `整理成` | 模型判（单步任务） |

加固后的规则：

| 档位 | 词 | 分值 |
|---|---|---|
| 强特征 | 第一步 / 第二步 / 第三步 / 依次 / 批量 / 并保存 / 并下载 / 然后 / 接着 | 各 2 分 |
| 中特征 | 步骤 / 流程 / 汇总 / 生成报告 / 制成清单 | 各 1 分 |
| 顺序配对 | `先` **必须**同时出现 然后 / 接着 / 最后 / 再 之一 | +2 |
| 开放减分 | 调研 / 研究 / 分析 / 比较 / 怎么看 / 如何 / 为什么 / 哪些 / 建议 / 聊聊 / 介绍 / 解释 / 探索 | 各 -1（比较用） |

判定：**总分 ≥ 2 且大于开放分**才判 `flow`。取向是「宁可漏判给模型」——漏判只多一次几百毫秒的小调用，误判要多一次 LLM 规划 + 智能体执行。

> 24 条样本中，4 条真流程案例仍全部命中；误判归零。

**代码审查阶段又抓到一条误判**：`步骤` / `流程` 原本是强特征（2 分），于是

- 「这个算法的步骤有哪些」→ 2 分 vs 开放 1 分 → 判成工作流
- 「混合模式的流程是怎样的」→ 2 分 vs 0 分 → 判成工作流

这两句都是**在问知识**，不是要你去执行。已把它们降到中特征（1 分）：单靠一个名词过不了 2 分阈值，真实指令（"按照以下步骤批量处理并保存" = 5 分）不受影响。两条样本已加进单测锁住。

### 2.3 `hybrid/switcher.py`

`classify_task()` 保留原名（`api/chat.py` 混合分支与既有测试都在用），实现改为委托 `core.router.classify_flow_open`。词表从该文件移除——避免两套口径。依赖方向修正为 `hybrid → core`（原来既有的方向）。

## 7. 已知缺口

| 编号 | 缺口 | 说明 |
|---|---|---|
| G-01 | 绑库 + 规则判 flow 时不强制检索 | 内置工作流是 `plan(llm) → execute(agent)`，没有检索节点；检索靠 execute 里的智能体自愿调 `kb_search`。这是既有行为，未在本次改动范围内 |
| G-02 | 路由多一次调用，首字增加 300–600ms | 只在"非 flow 的 auto 请求"上发生；超时 2s 即回落。压测时这部分会计入同一并发名额（路由在已持有的闸内执行，不二次抢闸） |
| G-03 | 规则对「先……再……」之外的弱顺序词仍会漏判 | 例如"读一遍总结一下"（无「然后/接着」）会走模型判断。属"宁可漏判"的预期代价 |
| G-04 | `flow` 目前只能由混合引擎承载 | `HYBRID_MODE_ENABLED=0` 时，flow 直接降级为 agent，工作流能力不可用 |

### 7.1 审查意见处理（同日）

代码审查提出两条 Major，处理如下：

| 编号 | 问题 | 状态 |
|---|---|---|
| M-01 | hybrid 用 `next(reversed(ctx.shared.values()))` 取答案，`plan` 的规划稿会被当成答案 | **已修**，见下 |
| M-02 | 非 flow 的 auto 请求多一次 LLM 往返 | 未改代码（同 G-02）。上线前压测确认 P95 涨幅，若 >15% 把 `ROUTER_TIMEOUT` 由 2.0 降到 1.0 |

**M-01 的成因**：内置工作流是 `plan → execute` 两节点。`plan` 成功、`execute` 失败时，`shared` 里最后一个值是 `plan` 写的规划稿，于是

1. 规划稿可能被当作答案回给用户（用户看到「1. 2. 3.」而不是结果）；
2. 更常见的是 `acc_text` 因拿到这段文字被判为"有产出"，**新加的 LLM 兜底永远不触发**，最后仍回「混合执行失败」+ 空白 —— 兜底在最需要它的场景下失效。

**修法**（三处）：

| 文件 | 改动 |
|---|---|
| `hybrid/workflow.py` | 成功的 `node_exit` 事件带上 `output_key`，让上层知道"最后一个真跑完的节点把产出写在哪" |
| `api/chat.py` | 新增 `_HYBRID_NON_ANSWER_KEYS` + `_pick_hybrid_answer()`：按「最后成功节点的 `output_key` → `agent_result` → 从后往前第一个非中间产物」取答案；`plan` / `history` / `score` / `retries` / `goal` / `question` / `node:*` 一律不认 |
| `api/chat.py` | `output_key` 只用于服务端取答案，从 `workflow_node` 事件里剔除，不向前端暴露内部键名 |

**回归**：`tests/test_hybrid_answer_pick.py`（8 条）——优先级函数 6 条、引擎带 `output_key` 1 条、"plan 成功 + execute 失败必须走 LLM 兜底且输出里没有规划稿"1 条。

# 九、前后端对接（接口契约）

## 9.1 请求：`POST /api/chat/stream`

```ts
interface ChatRequest {
  sid: string;
  question: string;
  mode?: "auto" | "rag" | "llm" | "agent" | "hybrid";  // 前端只发前三个
  kb_id_override?: string | null;
  workflow_id?: string | null;   // 仅当 mode === "hybrid" 有意义
  top_k?: number;
  plan?: boolean;
  attachments?: Attachment[];
  location?: LocationPayload | null;
}
```

**mode 语义（服务端最终判定）**

| 前端传 | 服务端行为 | 可能落到 |
|---|---|---|
| `auto`（默认） | 规则 → 模型两级判断 | `rag` / `agent` / `llm` / `hybrid` |
| `rag` | 直通，不做判断 | `rag`（库不存在时降级 `agent`） |
| `llm` | 直通 | `llm` |
| `agent` | 直通（内部/脚本用） | `agent` |
| `hybrid` | 直通，`HYBRID_MODE_ENABLED=0` 时静默回退 | `hybrid` / `agent` |

> 前端 UI 只暴露 `auto` / `rag` / `llm`。

## 9.2 响应：SSE 事件与模式的对应

| 事件 | 哪些模式下会出现 | 前端现有处理 |
|---|---|---|
| `status` | 全部 | 状态条文案 |
| `token` | 全部 | 累加正文 |
| `tool` | `agent`、`hybrid`（agent 段） | 工具折叠块 |
| `sources` / `grounding` | `rag` | 引用列表 + 依据强度提示条 |
| `hybrid_start` | **`hybrid`（含 auto 判成 flow 的情况）** | 初始化轨迹（`mode: workflow\|agent`） |
| `workflow_node` | `hybrid` | 轨迹节点进出 |
| `mode_switch` | `hybrid` | 轨迹换手（带 `rule` / `reason`） |
| `title` | 首轮 | 改名 |
| `done` | 全部 | 落库 id、`mode`、`run_id`、`truncated`、`plan_topic` |
| `error` | 全部 | 错误气泡 |

**唯一的新增语义**：`auto` 请求现在也可能收到 `hybrid_start / workflow_node / mode_switch`，以及 `done.mode === "hybrid"`。前端不需要改代码——`useHybridTrace` 早已按事件驱动，与用户选了哪个档位无关。

## 9.3 关键字段

- `done.mode`：**实际执行方式**（不是请求里的 mode）。前端据此决定是否展示轨迹、是否显示"已检索"。
- `done.run_id`：仅 hybrid 有值。人工切换接口 `POST /api/hybrid/runs/{run_id}/switch` 与执行日志查询都靠它。
- `workflow_id`：`auto` 判成 hybrid 时为 `null` → 后端用内置「规划-执行」流程。

## 9.4 环境变量契约

| 变量 | 默认 | 作用 | 影响面 |
|---|---|---|---|
| `ROUTER_ENABLED` | `1` | 关闭后 auto 退回旧规则（有库 rag / 无库 agent） | 全局 |
| `ROUTER_TIMEOUT` | `2.0` | 路由模型调用超时（秒），超时即回落 | 全局 |
| `ROUTER_MAX_TOKENS` | `48` | 路由输出长度上限 | 全局 |
| `HYBRID_LLM_FALLBACK` | `1` | 混合两段都没产出时用 LLM 兜底 | hybrid |
| `HYBRID_MODE_ENABLED` | `1` | 关闭后 flow 降级为 agent，`mode=hybrid` 也回退 | hybrid |

## 9.5 观测

- 路由决策只写服务端日志，**不下发前端**（用户要求不展示判断结果）：
  `route=<rag|agent|llm|flow> source=<rule|model|fallback> has_kb=<true|false> reason=<…>`
- 兜底触发时额外一条 `status` 帧："流程未产出结果，改用直接作答..."，让用户知道发生了什么。
