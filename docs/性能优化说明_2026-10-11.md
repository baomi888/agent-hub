## 第一梯队

### 1. SQLite 连接按线程复用（`core/session.py`）

**原问题**：每次读写都 `sqlite3.connect(...)` + 重设 WAL，一次问答累计开 6~7 个连接，
重开文件 + 重设 pragma 的开销全落在请求线程里。

**改法**：`threading.local()` 存连接，`_conn()` 命中同线程同路径直接复用；
pragma 只在建连时设一次。路径参与判断，是为了兼容测试把 `_db_path` monkeypatch 到临时目录——
路径一变必须换连接，否则会继续读写上一个库。

```python
def _conn() -> sqlite3.Connection:
    path = _db_path()
    conn = getattr(_LOCAL, "conn", None)
    if conn is not None and getattr(_LOCAL, "path", None) == path:
        return conn
    ...
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA synchronous=NORMAL")  # WAL 下不必每次 fsync
    conn.execute("PRAGMA busy_timeout=5000")   # 并发写等待而非立即报错
```

> 连接生命周期随线程，进程退出自然释放；不再每次 `close()`。

### 2. 归属校验并入 JOIN（`core/session.py`）

**原问题**：`get_messages` / `count_messages` 先 `_owned(owner, sid)` 发一次 EXISTS 查询，
再发一次消息查询——同一条归属规则查两遍。

**改法**：`messages JOIN conversations` 后按 `owner_id` 过滤，一次查询同时完成
「验归属 + 取消息」。不是自己的会话天然查不到，语义不变。

### 3. 历史查询尾部 LIMIT（`core/session.py`）

**原问题**：长会话每次都全量 `SELECT` 再在内存里截断，消息越多越慢、内存越大。

**改法**：`get_messages` 加 `limit_turns`，倒序取尾部 `limit_turns*2 + 10` 条再翻转，
等价于「全量后截断」但只读需要的行。多留 10 行缓冲，避免 Agent 一轮产出多段
assistant 时把窗口起点切掉。

### 4. LLM / Embedding 客户端记忆化（`core/llm.py`）

**原问题**：构造 `ChatOpenAI` / `OpenAIEmbeddings` 会建 httpx 连接池，
每次请求 new 2~3 个（标题生成 + 流式生成 + 可能的视觉模型），纯浪费。

**改法**：`get_llm` / `get_vision_llm` 按 `(temperature, max_tokens)` 缓存实例；
`get_embeddings` 直接单例。实例不带会话状态，可跨请求、跨线程复用。加锁保证并发首请求只建一个。

### 5. 查询向量独立缓存 + 按向量检索 + count 合并（`kb/rag_core.py`）

- 新增 `_embed_query()`：查询向量按文本做 LRU（上限 500）。embedding 只取决于文本、
  与库内容无关，因此**不随库内容失效**。给「同一问题、不同 top_k」这类结果缓存 miss
  的场景复用，省掉一次约 250ms 的 embedding 网络请求（也省真实 API 费用）。
- 检索改用 `similarity_search_by_vector_with_relevance_scores(vec, ...)`：用我们自己
  缓存的向量，而不是让 langchain 内部再 `embed_query` 一次。
  （已核对 langchain-chroma 源码：该方法与 `similarity_search_with_score` 一样返回
  原始 Chroma 距离，口径不变——只是「按向量」而非「按文本」。）
- `retrieve_with_score` 里 `count()` 原本被调用两次（判空 + 算 `fetch_k`），合并为一次。

## 第二梯队

### 6. Agent 图按参数缓存（`agent/builder.py`）

**原问题**：`create_agent` 每次请求都重新编译一遍 LangGraph 状态图（节点/边/路由），
是纯 CPU 开销，而图结构只由 `(has_kb, 定位片段)` 决定。

**改法**：新增 `_AGENT_CACHE`（LRU 32），键 `(bool(has_kb), location_note(location))`；
锁内编译，并发首请求只编译一次。编译好的图无会话状态（`checkpointer` 为共享实例，
状态每次 invoke 单独传），可跨请求、跨线程复用。

### 7. 会话标题异步并行生成（`api/chat.py`）

**原问题**：首轮回答收尾时，先等标题 LLM 往返（约 1~2s）才发 `done` 事件，用户白等。

**改法**：标题提示词**本来就没用到答案**（只用问题），于是把 `_generate_title(question)`
去掉答案参数，`event_generator` 开头就用 `asyncio.create_task(asyncio.to_thread(...))`
和答案流式**并行**跑；收尾 `await _take_title(task, acc_text)` 时它多半已完成，基本零等待。
用 `_BG_TASKS` 持强引用防 GC 警告，完成后自动移除。

### 8. 入库 embedding 分窗并发（`kb/rag_core.py` + `core/config.py`）

**原问题**：入库时 `for 批 in 分批: vs.add_documents(批)` 串行等待，
每批一次网络请求，N 批就是 N 个 RTT 首尾相接。

**改法**：新增 `_embed_and_store(vs, chunks)`，替换 `add_chunks` / `build_index` 两处相同循环。

- **embedding 并发、写入串行**：各批 `embed_documents` 丢线程池同时发出，向量回来后
  单线程 `_collection.upsert`。写入不并发，是因为多线程同时写同一个 Chroma collection
  会竞争 hnsw 索引与底层 sqlite，结果不确定；而写入是本地磁盘操作，不是瓶颈。
- **分窗限流**：按「窗口 = 并发度」逐窗处理，在途向量最多 `EMBED_CONCURRENCY × EMBED_BATCH_SIZE`
  条，既拿并发又不把整份文档的向量堆在内存里。
- 新增配置 `EMBED_CONCURRENCY`（默认 4，`1` 即退回串行）。`EMBED_BATCH_SIZE` 语义不变。

> 实测（离线、假 embedding）：95 条 / 10 批，并发 4 时 **0.637s vs 串行 2.028s（约 3.2×）**，
> 在途峰值钉死在 4，向量与文本严格按序对齐。

### 9. `list_sources` 分页 + 缓存 + 去重复扫（`kb/rag_core.py` + `api/kb.py`）

**原问题**：`list_sources` 一次 `get(include=["metadatas"])` 把整库元数据全物化进内存；
且 `api/kb.py::_resolve_source` 里连调两次，同一请求扫两遍。

**改法**：Chroma 没有 distinct/GROUP BY，聚合绕不开遍历，因此从两处把代价压下来：

- **分页拉取**：`limit`/`offset` 每页 `SOURCES_PAGE=1000` 条，峰值内存只跟页大小有关、
  与库大小解耦，大库不再瞬间吃掉几十 MB；
- **结果按库缓存**：新增 `_SOURCES_CACHE`（LRU 64，键=collection 名），列表页轮询、
  `_resolve_source` 多次解析直接命中，不再重复遍历；写入时随检索缓存一起失效
  （挂到既有 `_cache_invalidate` 上，四处写入路径已覆盖）；
- **去重复扫**：`_resolve_source` 把 `list_sources()` 取一次复用。

## 部署提醒

- 纯 Python 改动 + 新增一个可选环境变量 `EMBED_CONCURRENCY`（不设即默认 4）。
- 后端 `restart` 即生效；**前端零改动**，无需 build。
- 若入库时撞到向量化服务限流（429），把 `EMBED_CONCURRENCY` 调到 `2` 或 `1` 即可。
