# 苞米 agent · 前后端可更新点（2026-09-29）

扫描范围：后端 `main.py / api/* / core/* / agent/* / kb/*`，前端 `frontend/src/**`（约 4000 行 tsx + 12 个 CSS）。
结论：**后端 12 项、前端 9 项**，按"影响面 × 改动成本"排序。★★★ = 今天就能动手且收益明显。

---

## 一、后端

### ★★★ 1. Agent 流式在 async 里跑同步循环，会阻塞事件循环 —— **已修**
`api/chat.py:325` 的 `for event in agent.stream(...)` 是同步迭代，写在 `async def` 里。
DeepSeek 一次回答动辄十几秒，这段时间整个 uvicorn 事件循环被占住，其他请求（建库、上传、切会话）全部排队。
改法：换 `agent.astream(...)` + `async for`，其余事件解析逻辑不动。
对比：同一文件里 `build_agent` 和 `_generate_title` 都已经用 `asyncio.to_thread` 包过了，只有这一处漏了。

### ★★★ 2. 上传文件名消毒 —— **判断有误，已更正（并已加固）**

写这份报告时我判定这是"路径穿越真漏洞"，**这个判断是错的**。核实后：
`kb/pipelines.py:198` 的 `source_path()` 里有 `re.sub(r"[^\w.\-]", "_", name)`，
`/` 和 `\` 都不在白名单里，会被换成 `_`，所以 `../../evil.txt` 落到盘上是
`.._.._evil.txt` —— 穿越早就被这行正则挡住了，只是挡得很隐蔽。

真正剩下的只是边缘健壮性问题：超长中文名（`digest + safe` 可能撞上文件系统 255 字节上限）、
空名、纯 `.`/`..`。已做加固（不是修漏洞，是把"能落盘"从正则的副作用变成显式意图）：
- `kb/pipelines.py` 新增 `safe_source_name()`：显式 basename + 去控制字符 + 去 `..` + 主体截到 80 字符
- `source_path()` 整体长度再截到 120，避免 OSError
- `api/kb.py:76` 上传时先过一遍 `safe_source_name()`

边界已验证：`../../evil.txt`→`evil.txt`、`C:\Users\x\kb_up_1234.pdf`→`kb_up_1234.pdf`、
`''`/`'..'`→`unnamed.txt`、200 字中文名→83 字符，均无分隔符残留。

### ★★ 3. Agent checkpoint 只增不删，删会话不连带清理
`agent/builder.py:84` 的 `_CHECKPOINTER` 用 SqliteSaver 落盘到 `data/agent_memory.sqlite`，
但 `api/sessions.py` 的 `delete_conversation` 只删 SQLite 的会话表，**不会删对应 thread_id 的 checkpoint**。
长跑下去这个库只会变大。改法：删会话时同步清 thread，或加一个 TTL 清理任务。

### ★★ 4. `_PIPELINES` / 文件清单的并发竞态 —— **已修**
`kb/pipelines.py:26` 的全局 dict 无锁：`get_or_create` 在两个上传并发时可能给同一 kb 建出两个 Chroma 实例；
`_save_files()` 直接整文件覆盖写，并发导入会互相丢记录。
已改为：4 个全局容器由一把 `RLock` 保护；按 kb_id 再加一层串行锁；清单写盘走 `tmp + os.replace` 原子替换，
且每次改动前先重读磁盘（旧实现是全量覆盖写，后写的人会冲掉前面所有人的记录）。

### ★★ 5. 检索质量：裸 top-k，无阈值、无去重 —— **已修**
`kb/rag_core.py:272` 只用 `similarity_search_with_score`，问题有两个：
- 相似度很低的片段照样塞进 prompt，模型被迫"硬答"；
- 相邻切片高度重复，占了 top_k 名额。
改法：先取 `top_k*3` 候选 → 按 score 过滤 → MMR 去重 → 截到 top_k。这是提升答案质量收益最大的一块。
（`answer_stream` 里第一帧 yield 空串的逻辑现在也没人调用了，可以顺手确认是否死代码。）

**已实现**（`kb/rag_core.py` 新增 `select_diverse()`，`retrieve_with_score()` 接入）：
- 候选池 `max(top_k×3, top_k+6, 12)`，受库内片段数封顶
- 离群过滤：Chroma 返回平方 L2 距离，向量归一化时可换回余弦 `sim = 1 - d/2`，
  低于 `RETRIEVE_MIN_SIM`（默认 0.25）丢弃；距离 > 2 时换算不成立 → 自动跳过过滤，不乱砍
- MMR 贪心去重复：用字符 2-gram 的 Jaccard 判断片段重合（相邻切片重叠 50 字时重合度极高）

**踩到的坑（值得记）**：MMR 里的相关度一开始用批次内 min-max 归一化，结果失效——
重叠切片之间的距离只差 0.0x，归一化把这点差距放大成"最相关 vs 最不相关"，
三条重复片段靠微弱优势把名额全占了。改用**绝对余弦相似度**后正常。
另外阈值一开始定 0.35 太严：真实库（test_w1，11 片段）上问"苞米是什么"只剩 1 条，
放宽到 0.25 后同一问题留 3 条弱相关的，问真正相关的"RAG 是什么"留 0.74/0.72/0.52 三条，符合预期。

自测落在 `tests/test_retrieve_select.py`（纯函数、不联网）：去重、离群过滤、
不可换算时跳过、候选不足原样返回、lambda=1 退化为纯相关度排序，五种情况全过。

### ★★ 6. `/api/kb/download` 是开放 SSRF 代理
`api/kb.py:367` 接受任意 http(s) URL 由服务端拉取，没有域名白名单、没有响应体大小上限。
改法：至少加 `Content-Length` 校验 + 流式读取上限，内网部署场景可加域名白名单。

### ★★ 7. 长任务没有进度反馈
`upload_and_build` / `rebuild_kb` 都是同步跑完所有 embedding 才返回，大 PDF 会让前端一直转圈且无法取消。
对比：前端联网建库已经做了逐条进度（`page.tsx:361` 循环调 `importUrl`），本地上传反而是黑盒。
改法：任务化（job id + 轮询或 SSE 进度），或者至少分批返回。

### ★ 8. 三个导入接口的错误直接透传原始异常
`api/kb.py` 的 `import-search` / `import-url` / `import-batch` 用的是 `str(e)`，
而同文件其它接口用的是 `describe_api_error(e)`（会脱敏成中文提示）。统一一下，避免内部路径/堆栈漏给前端。

### ★ 9. `requirements.txt` 缺显式依赖
`agent/tools.py:82`、`kb/importer.py:9`、`api/kb.py:370` 都用 httpx，但 requirements 里没有；
现在能跑是因为 `duckduckgo-search` 间接带进来的。`tests/` 用的 `requests` 也缺失。建议显式声明。

### ★ 10. `/health` 是假的
`main.py:74` 永远返回 ok，不探测 embedding 服务、不探测 chroma 可写。加个 readyz 探针，排障能省很多时间。

### ★ 11. 无鉴权、无限流
所有接口裸奔，任何人可删库删会话。单机自用没问题，一旦放到局域网/公网就是事故。
最低成本方案：一个 `X-API-Key` 中间件 + 按 sid 的简单频率限制。

### ★ 12. 反馈接口缺失 —— **已修**

新增整套链路：
- `core/session.py`：新表 `feedbacks`（conversation_id / message_id / rating / comment），
  `message_id` 上带部分唯一索引 → 同一条消息重复提交是"改"不是"追加"；
  `delete_messages()` 顺带清掉挂在被删消息上的赞踩，不留悬空 id
- `api/feedback.py` + `main.py`：`POST /api/feedback/`、`GET /api/feedback/{sid}/`
- `api/chat.py`：SSE 的 `done` 事件新增 `message_id` —— 前端自己生成的 uid 后端不认，
  赞踩必须按 messages 表的 id 落库，这个 id 之前前端根本拿不到
- 前端：`api.ts` 加 `sendFeedback`；`page.tsx` 在 done 时把 id 挂到消息上；
  `Bubble` 的 `onFeedback` 改成 `(msgDbId, rating)`；`ChatArea` 真实发请求，失败才提示

已用 TestClient 端到端验证：点赞→改踩只留一条、非法 rating 返回 400、不存在的消息 404。

## 二、前端

### ★★★ 1. 本地上传没有进度，与联网建库的体验不一致
联网建库有"正在抓第 3/10 篇"，本地上传（`api.ts:65` `uploadFiles`）只有"转圈直到结束"。
依赖后端第 7 项；后端不改的话，前端至少可以先把文件分批上传，做出分段进度。

### ★★★ 2. 赞踩是假反馈 —— **已修（与后端第 12 项一起）**

### ★★ 3. 会话搜索只能搜标题
`Sidebar.tsx:95` 只 match `title`。会话一多，想找"上周问过的那个天气"就找不到。
改法：后端加 `GET /api/sessions/search?q=`（SQLite LIKE 扫 messages.content），前端接上。

### ★★ 4. 没有会话导出
无 Markdown / JSON 导出。对"问完的每一句都能翻回原文"这个定位来说，导出是自然延伸，成本也低（纯前端拼字符串即可，不用动后端）。

### ★★ 5. 输入框只收图片
`ChatArea.tsx:736` 的 `accept="image/*"` 是刻意的（后端只有视觉模型消费附件），但用户会困惑"为什么我的 pdf 选不了"。
要么后端支持文档解析，要么在选择器层面把提示写清楚（现在只在选完之后才提示"暂不支持"）。

### ★ 6. 流式重渲染粒度还可以再细
`page.tsx:197` 每个 token 都 `setMessages` 全量 map 一遍，Bubble 有 memo 兜底所以还好，
但长会话下每帧构建新数组的开销是实打实的。可考虑把流式中的那条消息单独抽 state。

### ★ 7. 无虚拟滚动
消息多了之后 DOM 只增不减。当前 `MAX_HISTORY_TURNS=10` 从后端限制了历史长度，所以暂时不痛；
一旦放宽历史窗口，这个会立刻变成性能瓶颈。

### ★ 8. 错误态偏弱
`Bubble.tsx:150` 只显示"暂时无法完成请求"+ 详情，没有"重试"以外的出路（比如切换模式重试、改 top_k 重试）。
`onRetry` 目前是原样重发，参数不变的话大概率再失败一次。

### ★ 9. 间距阶梯仍未做完
`tokens.css:147` 里自己写了"margin / padding 语义化留第二阶段，需逐组件定档"。
现在 gap 已经收口，padding 还是散的。纯打磨项，不影响功能。

## 四、下一步建议（按序）

1. **前端第 3 项**：会话正文搜索（后端加 `GET /api/sessions/search?q=`）—— 侧栏现在只能搜标题
2. **检索阈值调优**：新策略要用几天真实问答才能定准，`RETRIEVE_MIN_SIM` 现在 0.25 是刻意留宽的

4. **前端第 1 项**：上传进度（依赖后端任务化，工作量最大的一项）

纯视觉打磨（间距阶梯等）建议继续押后 —— 界面完成度仍明显高于功能完整度。
