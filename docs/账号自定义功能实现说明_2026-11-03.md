## 1. 一句话

设置页原来只有一行灰字「修改密码还没做好」。现在用户可以自己改**昵称、头像、
密码、登录名**，全部即时生效，不需要管理员介入。

四个操作的风险不一样，所以规则也不一样：

| 操作 | 要不要验密码 | 有没有次数限制 | 生效范围 |
|---|---|---|---|
| 改昵称 | 不要 | 无 | 立即（侧栏同步变） |
| 换头像（图标 / 上传照片） | 不要 | 上传 10 次/分 | 立即（侧栏同步变） |
| 改密码 | **要** | 10 次/分 | 立即，**其它设备被踢下线** |
| 改登录名 | **要** | **总共 3 次**，10 次/分 | 立即，令牌重签 |

## 2. 用户看到的样子

```
设置页
└─ 账号卡
   ├─ 圆形头像  ← 点一下 → 「换个头像」弹窗
   │                        ├─ 上传自己的照片 → 进「调整头像」：拖/缩选范围 → 用它做头像
   │                        ├─ 20 个内置图标（书/笔/闪电/星/玉米…）
   │                        └─ 用名字首字母（清空头像）
   ├─ 昵称      ← 行内编辑，回车保存 / Esc 取消 / 清空则回落登录名
   ├─ 登录名     ← 常驻显示 +「改」→ 弹窗（验密码、显示剩余次数）
   └─ 密码       ← 「修改密码」→ 弹窗（验旧密码、成功页说明其它设备已下线）
```

头像这一步是三屏，但用户只感觉到"选了一张图、挪一挪、确认"：
挑图案 → **调整头像**（圆形取景框 + 缩放滑块 + 复位）→ 上传完成关闭弹窗。
裁剪屏里「取消」和 Esc 都是**退一步**回到挑图案，不是把整个弹窗关掉。

登录名**始终显示**是刻意的：改完忘了自己改成了什么，是最常见的一种"账号找不回来"。

## 3. 数据模型

只动了一张表：`users`，新增 4 列。迁移是**幂等补列**，重启即生效，不停机、不写迁移脚本
（`core/account.py::_ensure_columns`，用 `PRAGMA table_info` 探测后再 `ALTER TABLE ADD COLUMN`）。

| 列 | 类型 | 默认 | 含义 |
|---|---|---|---|
| `nickname` | TEXT | `''` | 显示名。**可重复、可随意改**，空 = 回落 `username` |
| `avatar` | TEXT | `''` | `''`（首字母）/ `icon:<name>` / `img:<16位hash>` |
| `name_change_count` | INTEGER | `0` | 登录名改过几次，上限 3 |
| `token_valid_after` | INTEGER | `0` | 鉴权代数（列名为兼容历史保留），每次改密码 +1 |

**为什么昵称不唯一**：唯一的话「小猪佩奇」第二天就会被占完，用户注册时被迫想一个
自己都不喜欢的名字 —— 这恰好是他想改昵称的原因。唯一性交给 `username`，
昵称只负责"别人怎么称呼你"。

**为什么登录名限 3 次**：本站没有邮箱/手机号，改完忘了**只能靠管理员翻审计日志**
（`data/audit.log`）。设上限不是为了防攻击，是为了让"改名"这件事保有可追溯性。
用完返回 **403** 而不是 429 —— 429 的语义是"等会儿再来"，而这里是终身上限。

## 4. 接口清单

全部挂在 `api/auth.py`，前缀 `/api`，**不带尾斜杠**（`redirect_slashes=False`）。

| 方法 | 路径 | 鉴权 | 限流 | 说明 |
|---|---|---|---|---|
| `PATCH` | `/api/auth/profile` | 登录 | 10/分 | 改 `nickname` / `avatar`（只传要改的字段） |
| `POST` | `/api/auth/avatar` | 登录 | 10/分 | multipart 上传，字段名 `file` |
| `GET` | `/api/auth/avatar/{hash}` | **公开** | — | 返回 JPEG，`immutable` 缓存 |
| `POST` | `/api/auth/password` | 登录 | 10/分 | `{old_password, new_password}` |
| `POST` | `/api/auth/username` | 登录 | 10/分 | `{password, new_username}` |

`PATCH /profile` 的两个字段都是"传了才改"，因此可以只改昵称、只换头像，或一起改。
`avatar` 传空串是**合法操作**（清空 → 回落首字母），传非法值才 400 —— 所以后端
用的是 `is None` 判断而不是 falsy 判断（空串是合法值，这点很容易写错）。

### 4.1 `GET /api/auth/avatar/{hash}` 为什么公开

- 头像是门面，不是秘密；`<img src>` 是最简单的消费方式，强制鉴权会让每个头像
  都多一次 401 判定，还会让浏览器图片缓存失效。
- `hash` 是 sha256 前 16 位十六进制，正常流量下猜不出来。
- 响应头带 `Cache-Control: public, max-age=31536000, immutable`
  —— URL 里带内容指纹，换头像 URL 自动变，所以可以永久缓存。
- 另加 `X-Content-Type-Options: nosniff`：万一目录里被塞了别的文件，浏览器也不许改判类型。

## 5. 头像上传：裁剪 + 限额 + 峰值内存

这是本次唯一"看起来简单、实际处处是坑"的部分。完整实现 `service/avatar.py`（后端）
与 `lib/imageCrop.ts` + `AvatarCropper.tsx`（前端）。

### 5.1 现在只剩两道限额（原来是三道）

| 层 | 做什么 | 省什么 | 代码 |
|---|---|---|---|
| 前端裁剪 | 用户在圆框里拖/缩选范围，**只把选中的那块**画成 ≤640×640 JPEG q0.85 | **流量**：965KB 照片实传 **47KB** | `lib/imageCrop.ts`、`AvatarCropper.tsx` |
| 后端入口 | nginx `client_max_body_size 6m` + 应用层查 `Content-Length` 回 413 | **带宽/临时磁盘**：超限包不进 multipart 解析 | `ops/nginx-baomi.conf`、`main.py` 中间件 |
| 后端业务 | 硬限 5MB，分块写盘、超限立即中断并删半成品 | **磁盘/内存** | `core/upload.py::save_stream` |
| 落盘 | 只存 192×192 JPEG q85（约 12~18KB），**原图处理完立刻删** | **磁盘**：1000 人约 18MB | `service/avatar.py::store` |

★ **原图不上传了**，所以前端不再按 5MB 拦大小：20MB 的照片也能用（只受浏览器解码能力限制）。
原来那层"先压小再传"退化成裁剪的副产品 —— 传出去的永远是裁好的 640×640。

代价是"浏览器解不了的格式"当场失败（HEIC 是典型），见 §11。

原图是唯一能让磁盘爆掉的东西：5MB × 1000 人 = 5GB，而 192×192 成品只有 18MB 总量。
所以 `upload_avatar` 里那句 `finally: remove_file(tmp)` 是硬规矩。

前端的裁剪与压缩**都不是安全边界**（改 JS 就能绕过，直接把任意字节 POST 上去），
后端的所有校验都必须自己再做一遍。

### 5.1.1 裁剪器的坐标模型（改这块之前必读）

三个量，一个函数，预览和输出共用：

```ts
interface CropTransform {
  zoom: number;  // 相对"短边刚好铺满裁剪框"的倍数，范围 [1, 4]
  ox: number;    // 图片中心相对裁剪框中心的偏移，单位是"裁剪框边长的几分之几"
  oy: number;
}
drawCrop(ctx, bmp, t, side)   // 把 bmp 按变换画进 side×side 正方形
```

**为什么 `ox/oy` 存比例而不是像素**：预览画在 264px 的 canvas 上，成品画在 640px 上。
存像素就得在两边各乘一次换算系数，而那个系数正是最容易写反的地方；存比例则两边共用
同一份数据和同一个 `drawCrop`，**所见即所得是结构上保证的，不靠"记得对齐"**。

**夹紧**（`clampTransform`）：图片必须始终盖满裁剪框。
`|ox| ≤ (短边比例 × zoom − 1) / 2`，其中长边/短边 = 宽高比。zoom=1 时短边方向可动量
为 0（只能固定居中），长边方向可动 `(宽高比−1)/2`。探针里"拖过头不许露白"测的就是这条。

**输出边长** = `min(640, 短边像素 / zoom)`：小图不放大。放大不会增加信息，只会让上传
体积翻几倍，而服务器最终还要缩回 192。

**拖动换算用 `rect.width` 而不是常量 `VIEW`**：手机上取景框被 CSS 压窄了，手指走的
CSS 像素与逻辑像素不是 1:1；直接除 264 会"手指走 10px、图走 11px"。

三个缩放入口（双指 / 滚轮 / 滑块）都归到 `applyZoom()` 一个函数。滚轮必须用
`addEventListener(..., { passive: false })` 自己绑 —— React 的 `onWheel` 是 passive 的，
拦不住页面滚动。

取景框用**圆形**而不是方形：最终展示就是圆的，让用户在裁剪阶段看到成品。
圆比方少显示的是四个角，而 `zoom ≥ 1` 保证整圆被图片盖满，所以任何位置都不会露白。

### 5.2 真正的风险是峰值内存，不是磁盘

5MB 的 JPEG 解码成位图可能占 50~100MB；解压炸弹（几十 KB 的 PNG 声明 20000×20000）
能直接吃掉几 GB。2 核 2G 的机器上两个这样的请求同时到，挂的是**整个后端**。
四条对策：

1. **先读尺寸再解码**：`Image.open` 不 `load`，解压炸弹在"拿尺寸"这一步就死；
2. **`im.draft("RGB", 384)`**：让 JPEG 按 1/8 解码，4000×4000 从 ~48MB 降到 <1MB；
3. **显式 `Image.MAX_IMAGE_PIXELS = 16M`**：Pillow 默认只 warning 不报错，等于没有保护；
4. **`threading.Semaphore(2)` 限并发解码**。

第 4 条用线程信号量而不是 `asyncio.Semaphore`：解码本来就丢在 `asyncio.to_thread` 里，
而 asyncio 信号量绑定事件循环，测试里每个用例一个新 loop 会报
`Future attached to a different loop`。

### 5.3 处理流水线

```
UploadFile
  → save_upload      分块写临时文件（超 5MB 立刻中断并删除半成品）
  → Image.open       只读文件头，拿真实格式 + 尺寸
  → 校验             format ∈ {JPEG, PNG, WEBP}；边长 ≤ 4000
  → draft + 解码
  → ImageOps.exif_transpose   手机竖拍照片摆正
  → 居中裁正方形
  → thumbnail + resize        统一到 192×192（小图也放大到 192，尺寸契约恒定）
  → JPEG q85 → sha256 前 16 位命名
  → mkstemp 独立临时文件 + os.replace 原子落盘
  → 删原图（finally）
```

两个容易漏的点：

- **透明图必须垫白底**：JPEG 没有 alpha，直接 `convert("RGB")` 会把白底表情包变成
  **黑框头像**。
- **格式白名单校验的是 `im.format`，不是 `Content-Type`**：MIME 是客户端自己填的，
  改一张 GIF/BMP/TIFF 的头就能混过"只看 MIME"的检查。
- **临时文件名不能固定成 `<hash>.tmp`**：同一张图并发上传时两个线程争同一路径，
  Windows 上会出现"一个线程刚 replace、另一个再也找不到源文件"的 500。

### 5.4 同图共用一份文件 → 删旧图前要问一句

文件名是**内容 hash**，所以两个人可能选了同一张图、只存了一份文件。换头像时无条件
删旧文件，会把别人的图一起删掉，表现为「我换完头像，同事的头像变破图了」。
所以换之前先 `account.is_avatar_referenced(old)`（`api/auth.py::_release_avatar`）。

## 6. 改密码为什么会踢掉其它设备

令牌是 7 天有效的 JWT，无状态 —— 改完密码后，别的设备手上那张旧令牌**照样能进**，
"改了密码"就等于没改。所以引入**鉴权代数**：

```
users.token_valid_after   ← 改密码时 +1（原子 UPDATE ... WHERE password_hash = 旧值）
令牌里的 af 字段           ← 签发那一刻的代数快照
每次请求                   ← af 必须与库里的代数**精确相等**，否则 401
```

几个刻意的选择：

- **比的是代数，不是时间戳**。早期版本用 `iat < 水位`，但改密码和重签 Cookie 通常在
  同一秒内完成，秒级时间戳相等就判不出来。代数每次 +1、必须精确相等，
  同秒连改两次、服务器时钟回拨都不会漏。
- **`UPDATE ... WHERE password_hash = 旧值` 防并发**：两个改密请求都验过同一份旧密码时，
  只允许第一个落库；第二个返回「密码刚刚已被修改」。否则用户会以为自己改成功了，
  实际被另一边覆盖。
- **存量用户零影响**：老令牌没有 `af` 字段，按 0 处理，与默认值 0 相等 → 继续有效。
- 令牌校验对 `af < 代数` 的用户回 **401 "密码已修改，请重新登录"**，
  前端收到 401 广播后统一回登录页。

改密码、改登录名之后**当前设备会自动重签一次 Cookie**（带上新代数），
所以用户不会被自己的操作踢出去。

### 三个踩过的坑（改这块之前务必知道）

1. **`useConsoleAccount()` 只能在 `ConsoleLayout` 的子组件里用**。页面组件是它的父级，
   在页面函数体里读恒为 `null`（`/cet`、`/path` 踩过，表现是永远停在"正在加载"）。
   页面级一律用 `useAuth()`。
2. **改完昵称/头像，侧栏要立刻变**。原来的 Context 只暴露 `me`，改完得刷页面。
   现在 `ConsoleAccount = { me, refresh }`，页面里调 `refresh()` 就会重新拉 `/me`。
   `useConsoleUser()` 保持旧返回形状，老调用点零改动。
3. **`FormData` 上传必须把默认 `Content-Type` 覆盖成 `{}`**，否则浏览器不会自己补
   `multipart boundary`，后端会收到一个解析不了的 body。

### 裁剪屏的两个坑

4. **`touch-action: none` 不给就在手机上"拖图变滚页"**：手指一按一挪，图不动、弹窗在滚。
   `.acct-crop-stage` 和 `.acct-crop-canvas` 都加了。
5. **两屏必须共用同一个 `DialogShell` 实例**（不是 `if/else` 各 return 一份）。
   它里面那段 effect 只在 `open` 变化时跑，重挂会重新抓 opener、重新抢焦点，
   表现为"选完图，光标跳了一下"。

### 弹窗的焦点处理

三个弹窗叠在同一页上，焦点守卫必须让路：`DialogShell` 的 `focusin` 监听里，
如果焦点落在**别处**的 `[role="dialog"]` 内，就不抢回来 —— 否则两个弹窗会互相抢焦点
直到爆栈。Esc 用捕获阶段 + `stopPropagation`，保证只关最上面那一层。

## 8. 运维要点

### 8.1 部署时不要忘的两件事

1. **nginx 需要单独放开头像入口**（`/etc/nginx/conf.d/baomi.conf`）：

   ```nginx
   location = /api/auth/avatar {
       client_max_body_size 6m;      # 全局是 100m（给知识库）
       proxy_pass http://127.0.0.1:3000;
       ...
   }
   ```

   改完 `nginx -t && systemctl reload nginx`。仓库里 `ops/nginx-baomi.conf` 与
   `https/agent-hub.conf.template` 都已包含这段；但**线上那份是被 certbot 改过的
   HTTPS 版本，不能用仓库文件直接覆盖**，要手工把这段插到 443 server 块里
   （插在 `location /api/chat` 之前）。

2. **`data/avatars/` 必须可写**：后端首次上传会自动建目录；换机器或用非 root 跑
   要确认权限（线上现在是 `drwxr-xr-x root`，后端以 root 运行，OK）。

### 8.2 数据在哪

| 东西 | 位置 | 备份优先级 |
|---|---|---|
| 头像字段 | `data/sessions.db` → `users.avatar` | **高**（跟着主库一起备） |
| 头像文件 | `data/avatars/<hash>.jpg` | 中（丢了 = 头像变首字母，不影响登录） |
| 审计日志 | `data/audit.log`（JSONL，追加） | 高（改名/改密的唯一追溯来源） |

`audit.log` 记什么：`password_change`、`username_change`（含 `from`/`to`）、
`avatar_upload`。**绝不记口令明文** —— 日志泄露不能等于全站口令泄露。

### 8.3 运维命令

```bash
# 看还剩多少头像、占多大
ls /root/data/avatars | wc -l && du -sh /root/data/avatars
# 找某个用户的头像
python3 -c "import sqlite3;print(sqlite3.connect('/root/data/sessions.db').execute('select username,nickname,avatar from users where username=?',('张三',)).fetchone())"
# 用户忘了自己改成什么登录名
grep username_change /root/data/audit.log | tail -20
```

## 9. 排查手册

| 症状 | 最可能的原因 | 看哪里 |
|---|---|---|
| 上传返 413 | nginx 那个 location 没加 / 没 reload | `nginx -T \| grep -A3 'auth/avatar'` |
| 上传返 400「文件过大」 | 前端没压（老浏览器 / HEIC 解码失败）→ 原图直传超 5MB | 该用户浏览器控制台 |
| 上传返 400「这个文件打不开」 | HEIC / 损坏文件 | 同上，提示换 JPG/PNG/WebP |
| 头像变破图 | 文件被删但库里的 `img:` 还在 | `ls data/avatars/<hash>.jpg`；前端现在会自动回落首字母 |
| 用户说"改完密码被踢了" | **预期行为**，其它设备会下线 | 成功页文案已说明 |
| 用户改不了登录名 | 3 次用完了（403） | `select name_change_count from users where ...` |
| 改完密码后所有人都掉线 | 不可能：只 +1 当前账号的代数 | 若真发生，查 `token_valid_after` 是否被误改 |

## 10. 测试与验证

改这块之后，按这个顺序跑（前两条在本地，第三条对线上）：

```bash
# 1. 后端：账号 + 头像全链路（36 条，其中 20 条是上传专项，负向为主）
venv/Scripts/python.exe -m pytest tests/test_account_profile.py -q

# 2. 真浏览器（要本地前端 3100 + 后端 8000/8001 都在跑）
node .workbuddy/pp/account_probe.js        # 45 条：昵称/密码/改名的交互与负向
node .workbuddy/pp/avatar_upload_probe.js  # 32 条：上传全链路、压缩率、匿名读、缓存头、手机布局
node .workbuddy/pp/avatar_crop_probe.js    # 54 条：裁剪交互（拖动方向、夹住不露白、缩放、取消/Esc）

# 3. 线上（注册临时账号 → 全链路 → 精确清理）
venv/Scripts/python.exe .workbuddy/tmp/verify_prod_avatar.py
```

后端测试覆盖的负向用例值得单独记一下，因为它们都是"看起来能过"的洞：
6MB 文件、伪装成 jpg 的文本、SVG、GIF、BMP/TIFF（**含伪造 MIME**）、
20000×20000 解压炸弹、4001 像素边界、路径穿越、跨用户共用同一张图、
同 hash 并发落盘、未登录 401、管理员名抢注、改名超限 403。

**裁剪探针故意用了两张特制图**，这是它最有价值的部分：

| 图 | 用来测什么 | 为什么非它不可 |
|---|---|---|
| 2000×1000，左红右绿 + 中间深色竖线 | 拖动方向、夹住不露白、**存下来的到底是不是用户选的那块** | 中心点颜色就是"裁剪窗口落在哪"的坐标。把框拖到最右，取回的头像中心必须是**红色**——如果代码偷偷改成居中裁方，中心会是深色的分界线，一眼就露 |
| 1000×1000 竖条纹（周期 40px） | 缩放 | **画面里装得下几条**与倍率成反比，49→25→13 严格对应 1/2/4 倍。而"中心像素变没变""分界线宽了几 px"都不可靠：前者对对称构图完全瞎（放大时中心颜色不变），后者只有 3~5px、量化误差吃掉一半差异 |

这两条都属于"换一个指标才看得见"的教训：**指标可能对某类缺陷是瞎的**。
"上传成功了""avatar 字段变了"这类断言，在"根本没裁剪、只是居中裁方"时**全都成立**。

**线上验证脚本会注册一个临时账号**（`tmpavatarchk`），跑完必须清理：
删 `users` 行、还原 `usage` 里的 `signup:global` / `signup:ip` 计数、过滤 `audit.log`。
线上有真实用户，这一步不能省。

## 11. 已知限制（都是有意为之，不是没做完）

| 限制 | 影响 | 如果要做 |
|---|---|---|
| 不收 HEIC | 苹果默认格式的照片**在浏览器里就解不开**，进不了裁剪，会提示换一张 | 需引 libheif（前端 wasm 或后端 Pillow-heif），体积代价不小；也可只提示用户改相机格式 |
| 头像公开可读 | 知道 URL 的人能直接看 | 头像不是秘密；改鉴权会毁掉浏览器缓存 |
| 旧图只做引用检查，没有兜底扫描 | 极端情况（删文件前进程崩）会残留 | worker 每周扫一次 `data/avatars` 对比库 |
| 被踢下线没有原因提示 | 用户看到登录页，原因得自己想 | 401 广播里带一个 reason 参数 |
| 昵称可重复 | 两个人可以叫同一个名字 | 用 `uid` 区分身份，昵称只负责显示 |
| 裁剪只支持「拖动 + 缩放」，没有旋转和框外拉伸手柄 | 歪着的照片没法扶正（EXIF 的自动摆正仍然生效） | 加旋转按钮即可，坐标模型不用改（旋转发生在画之前） |
