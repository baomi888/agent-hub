## 一、三个严重问题（安全 / 稳健）

### ★★★ 1. 附件路径任意文件读取漏洞 → 已修

**文件**：`api/chat.py`（新增 `_resolve_upload_path`）

原缺陷：`attachments[].path` 完全由客户端提供，`_build_vision_user_message` 拿到 path 直接
`os.path.exists(path)` + `open(path)` 喂给第三方视觉模型。等于开放**任意本地文件读取**
（`.env`、`sessions.db` 都可以被读走再 base64 发给 qwen-vl-plus）。

修复：新增 `_resolve_upload_path()`，realpath 后做前缀 containment 校验，
只允许 `CHAT_UPLOAD_DIR` 目录内的文件；目录穿越、软链逃逸一律返回 `None` 跳过。

```python
def _resolve_upload_path(path: str) -> str | None:
    root = os.path.realpath(CHAT_UPLOAD_DIR)
    real = os.path.realpath(path)
    return real if (real == root or real.startswith(root + os.sep)) else None
```

### ★★★ 2. 计算器指数爆炸 OOM → 已修

**文件**：`agent/tools.py`

原缺陷：`calculator` 是唯一可被模型调用的高风险计算工具。`2**999999999999` 这种表达式
白名单和字面量检查都挡不住（12 位数字合法），`eval` 会试图生成约 10¹² 位的整数直接 OOM。
另外 Python 3.11+ 的 `int → str` 有 4300 位硬限制（CVE-2020-10735），
`len(str(result))` 本身就可能抛 `ValueError`。

修复：
- `_CALC_MAX_EXPONENT = 10000`：正则提取 `** 右侧指数`，超限直接拒绝；
- `_CALC_MAX_RESULT_BITS = 14000`：结果守卫改用 `bit_length()`（约 4215 位十进制，低于硬限制），
  既防 `999999999999**10000` 这类组合合法但算不出意义的大数，也避免触发 int→str 硬限制。

### ★★★ 3. `reverse_geocode_city` 同步调用阻塞事件循环 → 已修

**文件**：`api/chat.py`

原缺陷：`chat_stream` 是 async 端点，`reverse_geocode_city(flat, flon)` 是同步 httpx 阻塞调用，
一个定位请求就能让整个事件循环卡住几百毫秒到几秒，所有并发请求全部排队。

修复：`await asyncio.to_thread(reverse_geocode_city, flat, flon)`，阻塞 I/O 丢线程池。

## 二、成本优化（省真实 API 费用）

### ★★ 4. 检索结果 LRU 缓存：重复问题不再重复付 embedding 费

**文件**：`kb/rag_core.py`

- 新增 `_RETRIEVE_CACHE`（`OrderedDict` LRU，上限 200 条），键为 `(collection, question, top_k)`；
- `retrieve_with_score` 命中时返回浅拷贝（防止调用方误改污染缓存），并 `move_to_end` 保热；
- **写入路径全部失效**：`add_chunks` / `build_index` / `delete_by_source` / `delete` 按 collection 清缓存，
  保证知识库内容变更后不会读到旧片段。

> 效果：同一问题的重复提问（含前端并发、多轮追问）直接命中，跳过一次 embedding 调用 +
> 向量查询——省的是按量计费的 API 费用和用户等待时间。

### ★★ 5. 导入去重：同名 source 已入库则跳过

**文件**：`kb/importer.py`

- `import_url`：进锁后先 `pipe.get_source_chunks(name)`，已存在则返回 `skipped: True`，不再切片 + embedding；
- `download_and_index`：同上去重，返回 `chunks: 0, skipped: True`。

> 效果：重复导入同一文档（用户手滑、批量导入里混着重 URL）不再重复付切片 + embedding 费。

### ★★ 6. LLM 回答长度兜底：`max_tokens=2048`

**文件**：`core/llm.py` + `api/chat.py`

- `get_llm` / `get_vision_llm` 新增 `max_tokens` 参数透传给 `ChatOpenAI`；
- `api/chat.py` 三处流式生成（Vision / Agent / RAG / 纯 LLM）统一传 `max_tokens=2048`，
  给回答长度兜底，防止模型失控长文烧 token。

### ★★ 7. Agent 步数硬限制：`recursion_limit=10`

**文件**：`api/chat.py`

Agent 配置新增 `"recursion_limit": 10`。工具返回"不可用"时模型反复重试是纯烧钱
（每次都是完整 LLM 往返），硬限制整轮步数兜底。

### ★ 8. 配额扣费顺序：先验会话再扣费

**文件**：`api/chat.py`

原逻辑先 `quota.consume(uid, "ask")` 再查会话——会话不存在（无效请求）也消耗每日问答额度。
调整为先 `store.get_conversation` 校验，404 直接返回，**不扣费**；有效请求才扣。

## 三、速度优化（省用户等待）

### ★★ 9. 下载改流式 + 大小上限

**文件**：`kb/importer.py` `download_file`

原实现 `f.write(resp.content)`：整份读进内存、无 Content-Length 预检，2GB 的 .iso 直接 OOM。

修复：
- 改 `resp.iter_bytes(256KB 分块)` 流式写盘；
- 新增 `_MAX_DOWNLOAD_MB = 200`，累计超限删掉半成品文件再报错。

### ★★ 10. 图片压缩：长边 1024 / JPEG q85

**文件**：`api/chat.py` `_load_image_bytes` + `requirements.txt`（新增 `pillow>=10.0`）

原实现 20MB 原图直接 base64 发 qwen-vl-plus，慢且易被拒收。现在 Pillow 可用时先压缩：
长边压到 1024、JPEG q85（实测 17.2MB → 273KB，约 **65 倍**）。Pillow 缺失自动降级原图，不硬依赖。

### ★ 11. 上传扩展名白名单

**文件**：`api/chat.py` `upload_attachments` + `_is_supported_image`

原实现 `.exe / .iso / .zip` 照单全收。现在只收 `jpg/jpeg/png/gif/webp/bmp`，扩展名 + content-type 双保险；
**整批先校验再落盘**——有一张不合格整个 400 拒绝，不留下半批孤儿文件（顺带堵掉 10-08 #3 里
"上传无格式白名单"那一半）。

### ★ 12. Vision 检索失败降级提示

**文件**：`api/chat.py`

图片问答分支里知识库检索失败原来 `except Exception: pass` 静默吞掉，
用户看到的就是"AI 回答图片但没带资料"。现在 yield 一条 `status` 事件
「知识库检索失败，已仅按图片作答」，前端可见、不误导。

## 五、测试环境修复

**文件**：`pytest.ini`（新增）、`tests/test_geo_locate.py`

1. **pytest 收集阶段报 `no such table: users`**：根因是 `tests/` 里的脚本式自测（模块级执行 +
   `sys.exit`，设计上就是 `python tests/test_xxx.py` 直接跑的）被 pytest 当成用例收集，
   模块级执行时 monkeypatch 的 `_db_path` 建表顺序互相干扰。新增 `pytest.ini` 逐文件 ignore
   脚本式自测，`pytest` 只收集 17 个 pytest 风格用例。
2. **`test_geo_locate` 用例预期错误**：`203.0.113.25`（RFC 5737 TEST-NET-3 文档段）在 Python 3.10+
   归入 `is_private`，永远不会是真实用户 IP，判定非公网是预期行为——修正测试用例
   （原用例与该文件内 TEST-NET-2 一行的预期自相矛盾）。
