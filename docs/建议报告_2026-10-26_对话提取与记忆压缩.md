# 对话提取与记忆压缩 · 特征审计与升级建议报告（v2）

**报告编号**：AR-2026-10-26
**日期**：2026-10-26
**版本**：v2（当日修订）

> **v2 改了什么**：v1 把「压缩块里存的是原句、不是摘要」判定为**抽象化缺失**。
> 这个判据错了。你的修正是对的——**知识类内容整句保存是特性，不是缺陷**，因为它将来要进知识库，
> 一旦抽象（改写）就不可逆地损失原文，而知识库的价值恰恰在于可溯源、可核对。
> v2 把判据从「抽原句 = 没做抽象」改成「**该保真的东西去了不该去的地方**」：
> 需要整句保真的知识被挤在按 token 计费、会被折叠截断的**上下文压缩块**里，
> 而唯一能永久保真存放它的**知识库**，目前**没有从对话进来的门**。
> 三个特征的结论、三因素的用途、以及 P0 的顺序，都随之重写。

**审计对象**：对话历史的**提取**（组装进上下文）、**压缩**（落库压缩块），以及**沉淀**（进知识库）三条链
**回答两个问题**：
1. 对话提取方式是否具备 ①选择性 ②抽象化 ③结构化
2. 记忆压缩是否采纳了 ①访问频率 ②情感强度 ③信息独特性

---

## 0. 摘要：逐条对照（v2）

### 0.1 对话提取的三个特征

| 特征 | v1 结论 | **v2 结论** | 为什么改 |
|---|---|---|---|
| 选择性 | ⚠️ 有但标准单一 | ⚠️ **有，但只有一条链有选择** | "进知识库"这条链**根本不存在**，无从谈选择 |
| 抽象化 | ❌ 主链上没有 | ⚠️ **判据错了**：缺的不是抽象，是**分流** | 知识项本就该保真；真正缺的是"哪些该保真、哪些该抽象"的分流规则 |
| 结构化 | ⚠️ 只有分段号 | ❌ **比 v1 判得更重** | 入知识库必须有 `kind`/`source`/时间，现在只有自由文本，**连入的资格都没有** |

### 0.2 记忆压缩的三个因素

| 因素 | v1 结论 | **v2 结论** | 在"整句入库"语境下的真实用途 |
|---|---|---|---|
| 访问频率 | ⚠️ 部分采纳 | ⚠️ 部分采纳 | 用途变了：不该用于"折不折压缩块"，而该用于**知识库条目的检索提权**（命中次数可统计） |
| 情感强度 | ❌ 未采纳 | ❌ 未采纳 | 用途变了：它决定的是"**要不要入知识库**"（显式要求记住 → 直接入库），不是"要不要留在压缩块" |
| 信息独特性 | ❌ 未采纳 | ❌ 未采纳，且**重要性升级** | 它同时是入知识库的**准入判据**（防冗余污染检索）和压缩块的**免折判据**（singleton） |

### 0.3 v2 最该先知道的一条

> **对话里产生的知识，目前没有任何一条通路进入知识库。**
>
> 证据：`api/kb.py` 的入库接口只有 `upload`(:60)、`import-url`(:461)、`import-batch`(:479)、
> `import-search`(:449) 四条，**输入全是外源文件或 URL**；
> `kb/rag_core.py:1049 add_chunks(chunks)` 收的是带 `metadata.source` 的 LangChain Document，
> 全仓**没有任何会话侧调用方**。
>
> 后果是具体的：用户花 20 轮讲清楚的一条业务规则，会话结束后只能靠
> `COMPRESS_MAX_SUMMARY_CHARS=4000` 字符的压缩块承载，而这个块会被
> `_enforce_budget` 从头折叠、按 200/300 字硬截断（`context_compress.py:143-168`）。
> **唯一能永久保存整句的地方没开门，能开门的地方又在丢句子。**

## 1. 先立判据：三条链的目标函数是不同的

v1 的错误在于把"提取"当成一件只有一个目标的事。实际上它同时服务三个目标，
而这三个目标对"保真"的要求**方向相反**：

| 链 | 载体 | 目标 | 成本计量 | 对"整句保真"的态度 |
|---|---|---|---|---|
| ① 组装进上下文 | prompt | 让模型**这一轮**答得对 | token，每轮都要付 | **要少**，越精炼越好 |
| ② 压缩块落库 | `conversations.compressed_summary` | 让模型**后续轮**不失忆 | 字符预算 4000，会被折叠 | **要省**，省给还没被压的部分 |
| ③ 沉淀进知识库 | Chroma collection | 让**未来任何会话**能检索到 | 存储 + 一次 embedding，之后零边际成本 | **要全**，整句保真，永不截断 |

三条链的成本结构完全不同：③ 是一次性付费、永久持有、按需召回；
② 是每次请求都要重新付一遍 token。**把知识放在 ② 里，等于用最贵的载体存最该长期持有的东西。**

而现状是：**③ 这条路不存在**，于是所有需要长期持有的知识都被迫挤进 ②，
② 又有 4000 字符预算，只能靠折叠和截断来腾地方——丢句子是结构性的必然，不是 bug。

**这也解释了为什么"抽原句"不该被批评**：`extractive_compress` 保原句，
在"这些句子将来要进知识库"的前提下是**正确选择**。v1 判它错，是因为默认了压缩块就是终点。
v2 的判据是：**终点错了，不是方法错了。**

## 2. 对话提取：三个特征逐项审计（v2）

### 2.1 选择性 ⚠️ 有，但只有一条链有

现状里**确实存在**选择，但全部只服务于链 ①：

| 口径 | 实现 | 选择标准 | 出处 |
|---|---|---|---|
| 时间最近 | `plan_context` 过滤 `id > compressed_upto`，再取最近 `keep_turns*2` 条 | **位置** | `context_compress.py:369-372` |
| 含硬实体 | 保留含 URL/UUID/长 hex/文件名/待办关键词的句子 | **格式上可枚举** | `context_compress.py:59-68, 311-312` |
| 可溯源 / 词表内 | 每日总结结论必须 refs 指回真实消息；画像标签只能从固定词表选 | **可验证性 / 受控词表** | `daily.py:267-282`、`api/chat.py:1456-1474` |

**链 ③ 没有任何选择机制——因为链 ③ 本身不存在。**

补上链 ③ 之后，选择标准应当与链 ① **相反**：

| | 链 ① 进上下文 | 链 ③ 进知识库 |
|---|---|---|
| 倾向 | 宁缺毋滥（多一句多一份 token） | **宁滥毋缺**（多一条只多一份存储） |
| 冗余容忍 | 极低（重复浪费上下文） | 低（但原因不同：会污染检索，见 3.3） |
| 判据 | 与本轮相关 | **未来会不会被问到**（不可知 → 用代理指标） |

这条对照是 v2 的核心：**"选择性"不是一个标量，它的方向取决于载体。**
用链 ① 的标准去管链 ③，会把大量该留的知识筛掉。

### 2.2 抽象化 ⚠️ 判据修正：缺的是分流，不是摘要

v1 的事实陈述仍然成立，先复述：

```python
# api/chat.py:1506
await asyncio.to_thread(ctxcompress.maybe_compress, uid, sid)
```

**没有传 `compressor`** → 走默认 `extractive_compress`（`context_compress.py:290-320`），
它挑句子、原样拼接，**是抽取式不是抽象式**。

**但 v2 认为这个事实的定性要改**：

| | v1 判定 | v2 判定 |
|---|---|---|
| 抽原句 | ❌ 没有做抽象，是缺陷 | ✅ **对知识项而言是正确做法**，抽象会造成不可逆的信息损失 |
| 真正的问题 | 主链没接 LLM 摘要器 | **没有分流规则**：不知道哪些是知识项（该保真入库）、哪些是过程噪声（该抽象丢弃） |

抽象化对知识项的三个不可逆代价，是"整句保存"成立的理由：

1. **溯源断了**：知识库条目要能回到原文核对，摘要后的句子无法指回（`daily.py:267-282` 的 refs 校验会失效）；
2. **细节丢了**："预算三千"被抽象成"预算有限"，后者无法回答问题；
3. **不可撤销**：原文一旦不在，摘要无法还原。

所以正确的形态不是"给主链接个 LLM 摘要器"，而是：

```
                    ┌─ 知识项（事实/约束/待办/偏好/结论）→ 整句 → 知识库（保真，永存）
一轮对话 ── 分流 ───┤                                     └─ 压缩块只留一句指针（省 token）
                    └─ 非知识项（寒暄/试错/重复探讨/已被纠正的说法）→ 压缩块内抽象掉
```

**分流的产物同时解决了链 ① 和链 ③**：知识去了知识库（永久、可检索、不占 token），
压缩块里只剩指针，字符数自然下降——**这比"把压缩块再摘一遍"省得多，且不丢信息**。

项目里已经有两处能工作的抽象能力，只是接错了地方：
- 每日总结：LLM 提炼 1~4 条结论 + `source_refs`（`service/daily.py:321`），是真抽象且可溯源；
- 画像标签：把一轮问答抽象成词表里的 0~3 个标签（`api/chat.py:1452-1474`）。

v2 建议：**把 daily 的 `{text, source_refs}` 结构直接复用于分流判定**（见 4.2），不新造解析。

### 2.3 结构化 ❌ 比 v1 判得更重

落库形态（`context_compress.py:106-108`）：

```
[COMPRESSED-1] 用户问了 nginx 反代配置……AI 回答了转发规则……
[COMPRESSED-2] 用户问了证书续期……AI 回答了 certbot timer……
```

`segments: list[str]` —— **字符串数组**。无类型、无来源消息 id、无权重、无时间戳。

v1 说这决定了"按类型保护"和"按权重排序"做不到。v2 补一条更硬的：

> **它同时导致知识无法入库。**
> `add_chunks` 需要带 `metadata.source` 的 Document（`rag_core.py:1049`），
> 而从 `[COMPRESSED-1] 自由文本` 里**切不出** source、切不出时间、切不出说话人角色。
> 也就是说，**即使现在开了对话→知识库的门，也没有合格的输入**。
> 结构化因此从"优化项"变成"链 ③ 的前置阻塞项"。

对比已经结构化的旁路：
- 每日总结结论：`{"text": ..., "source_refs": [...]}`（`daily.py:263`）
- 画像快照：`{top_tags, weight_sum, tag_count, updated_at}` JSON（`session.py:471-495`）
- 知识库切片：`Document(page_content, metadata={source, chunk_index, ...})`（`rag_core.py:1092-1097`）

**压缩块是这四条里唯一没结构的**，而它偏偏是知识沉淀的原料。

## 3. 记忆压缩：三个因素逐项审计（v2）

### 3.1 访问频率 ⚠️ 部分采纳，且用错了地方

**已采纳的部分**：画像标签权重累加（`session.py:416-443`）

```sql
INSERT INTO user_tags (...) ON CONFLICT(owner_id, tag)
DO UPDATE SET weight = weight + ?, updated_at = ?
```

检索时按 `RETRIEVAL_BIAS_ALPHA=0.08` 做排序偏置（`config.py:254-256`）。

| 缺陷 | 说明 | 在 v2 语境下的后果 |
|---|---|---|
| 无时间衰减 | `weight` 只增不减，`updated_at` 不参与计算 | 三个月前的主题永久压制当前主题 |
| 用错了载体 | 频率只作用于**画像标签**，压缩块与知识库都没有 | 知识库条目被检索命中多少次，完全没统计 |
| 压缩链不看频率 | 折叠只看段序（:143-168） | 反复提及的核心内容照样最早被折 |

**v2 的关键修正**：在链 ③ 存在的语境下，"频率"最该落的地方是**知识库条目的检索命中次数**——
它天然可统计（`core/metrics.py` 已有 `retrieval_cache` 计数），且用途明确：命中多的条目在排序时提权。
用来决定"压缩块折哪一段"其实是次优用途，因为压缩块的生命周期只有一个会话。

### 3.2 情感强度 ❌ 未采纳

全仓检索 `sentiment / 情感 / 情绪 / emotion` **零命中**（代码无实现，仅前端提示词语料有中文表述）。

v2 补充：情感强度在"整句入库"语境下有了新的、更高价值的用途——

| 用户表达 | 系统现在的理解 | v2 下应触发的动作 |
|---|---|---|
| "顺便问下 X 是什么" | 一条普通问答 | 不入库 |
| "**千万记住**，我这个账号不能注销" | 一条普通问答 | **跳过打分，直接整句入库**（显式要求） |
| "不对，我说的是 Y 不是 X" | 一条普通问答 | **纠正后版本入库，纠正前版本标记作废** |
| "我预算只有三千块" | 可能被硬实体正则漏掉 | 类型=约束 → 入库 |

**纠正信号尤其重要**：整句入库会带入"被纠正的错误说法"，
如果纠正前后两句都进了知识库，检索时会互相冲突，且用户无法判断哪个对。
这是"整句保存"必须配套解决的一个副作用（见 5.2）。

### 3.3 信息独特性 ❌ 未采纳，且重要性升级

现状里最接近的是 `extract_entities`（:71-93），守的是**格式可枚举**的硬信息，不是语义独特性。
系统里没有任何一处计算"这条信息有多不可替代"。

折叠策略（:143-168）的走向与独特性**正好相反**：

```python
# 段数超限：把最早的几段折成一句
folded = " ".join(self.segments[:fold_n])
overview = f"[早期内容已折叠] {folded[:300]}"
```

v2 补充一个**链 ③ 特有的、v1 没写到的风险**：

> 整句入库最怕的不是"存多了"，是**冗余污染检索**。
> `core/config.py:79` 的注释已经写明了这个现象：
> 「先多取几倍候选再挑，否则 top_k 名额会被相邻重复切片占满」。
> 也就是说，**重复内容会挤掉真正相关的结果**。
> 在对话场景下这一点更严重——同一个意思用户会用三四种说法重复，
> 全量整句入库等于把 top_k 名额送给同一句话的几个变体。

所以独特性在链 ③ 上是**准入判据**，而且判据要拆成两个方向：

| 方向 | 判据 | 动作 |
|---|---|---|
| 只出现一次但重要（singleton） | 段内实体/术语在全会话只出现一次 | **必须入**——没有别处能兜住它 |
| 重复出现 | 与已入库条目相似度 > 阈值 | **只入一次规范化版本**，后续记为 hits+1，不重复建条目 |

这正好回应你说的"重复的不要，只出现一次但重要的要保存"。

## 4. 升级建议（v2，顺序已重排）

### 4.1 P0（新增，最高优先）：开一条「对话 → 知识库」的沉淀通路

**为什么排第一**：其余所有建议都假设知识有地方去。没有这条路，"整句保存"这句正确的话无处落地。

现状盘点：

| 组件 | 现状 | 够不够 |
|---|---|---|
| `add_chunks(chunks)` | 已存在，收 LangChain Document，自动建库 + 打向量指纹（`rag_core.py:1049-1066`） | ✅ 可直接复用 |
| 切片 | `split_documents(text, chunk_size, chunk_overlap)`，`CHUNK_SIZE=500`/`OVERLAP=50`（`config.py:42-43`） | ✅ 可复用 |
| 所有权隔离 | `_must_own(uid, kb_id)`（`api/kb.py:484`） | ✅ 已解决 |
| 配额 | `quota.guard(uid, "embed")` / `quota.bump_usage`（`api/kb.py:487,496`） | ✅ 已有 embed 配额位 |
| **取数 + 构造 Document** | **无** | ❌ 要写 |
| **前端入口** | **无** | ❌ 要写 |

要写的部分（增量，不重造）：

1. `kb/` 新增 `dialogue_import.py`：`extract_dialogue_knowledge(messages) -> list[Document]`
   —— 入参是会话消息，出参是带 `metadata={source: "对话·<会话标题>", chunk_index, message_id, role, ts}` 的 Document 列表。
2. `api/kb.py` 新增 `POST /{kb_id}/import-dialogue`，复用 `_must_own` + `quota.guard` + `add_chunks` 三件套。
3. 前端：会话详情页加"把本次对话沉淀到知识库"入口（选择目标库 + 预览待入条目）。

**不做的事**：不自动入库。自动入库会把寒暄、试错、错误中间态一起写进去，
且**不可逆污染**（用户要逐条删）。必须人工确认 + 可预览 + 可勾选。

**验收**：沉淀后在新会话里能检索到，且 `source` 字段显示来源会话；删除该条目不影响会话本身。

### 4.2 P0：压缩块结构化，且 `parse()` 必须兼容旧格式

补充 v1 没写的字段（入知识库必需）：

```python
@dataclass
class Segment:
    kind: str        # 目标 | 约束 | 待办 | 偏好 | 结论 | 事实 | 其它
    text: str        # 原文整句（不改写，见 2.2）
    refs: list[int]  # 来源 message_id —— 入知识库时作为溯源依据
    role: str        # user / assistant —— 入知识库要区分"谁说的"
    ts: int          # 时间戳
    salience: float  # 0~1，见 4.3
    hits: int = 0    # 被再次提及次数
    staged: bool = False  # 是否已沉淀进知识库
```

`staged` 是 v2 新增的关键字段：整句入知识库后，压缩块里的这一句就可以安全降级为指针，
**不必再占字符预算**。没有这个字段，就会出现"知识库和压缩块各存一份"的双写浪费。

**兼容要求（硬约束）**：`render()` 仍输出文本；`parse()` 必须能解析**旧格式**
（旧库里是 `[COMPRESSED-n] 文本`，无 kind）→ 旧段默认 `kind="其它"`、`salience=0.5`、`role="user"`。
否则一升级所有老会话的压缩块全废，**这是不可恢复的后果**。

### 4.3 P0：分流规则 —— 哪些整句入库，哪些抽象掉

复用 `daily.py:321` 已跑通的抽象格式（方案 B，v1 已论证，v2 保留并明确其用途）：

| 方案 | 做法 | v2 定位 |
|---|---|---|
| A 给压缩块接 LLM 摘要器 | `maybe_compress(..., compressor=...)`，预留位在 `context_compress.py:323-334` | **降级**：只用于非知识项 |
| B 复用 daily 的 `{kind, text, source_refs}` 结构 | 复用 `_parse_conclusions` / `_filter_by_traceability` | **主路径**：产出分流结果，知识项整句直出 |

分流判定零 LLM 的部分（先上，冷启动即可用）：

| 信号 | 判据 | 归向 |
|---|---|---|
| 显式要求记住 | 正则 `记住\|别忘了\|以后都\|记一下` | **直接入库**，跳过打分 |
| 纠正信号 | `不对\|不是这个\|我说的是\|你理解错了\|重新说` | 纠正后版本入库，前版本标作废 |
| 硬实体 | `extract_entities` 命中（:71-93） | 入库（格式可枚举 = 高置信度） |
| 约束/待办词 | `必须\|不要\|截止\|目标\|计划` | 入库 |
| 其余 | —— | 压缩块内可抽象，不入库 |

**L0 安全阀必须保留**（`apply_safety_valve:188-229`）：实体丢失即拒收。
换了摘要方式也不能绕过——这条规则救过一次。

### 4.4 P1：`salience` 怎么算 —— "只出现一次但重要"的实现

难点在于：**压缩时无法知道未来会不会用到**。不能靠预测，要靠可计算的代理指标。

| 信号 | 怎么算 | 为什么它能代表"重要" |
|---|---|---|
| **类型权重** | kind 先验：约束/待办/偏好/纠正 > 结论 > 事实 > 其它 | 用户说的"必须/不能/要做什么"，天然低频高价值 |
| **首现且唯一（singleton）** | 段内实体/术语在全会话出现次数 == 1 | 只说一次 → **没有别的段落能兜住它** |
| **离群度** | `1 - max_sim(该段, 其它段)` | 与其它内容都不像 → **不可从别处推导；不可推导 = 必须自留** |
| **纠正信号** | 正则命中 | 纠正后的内容才是真实意图 |

```
salience = 0.4·type_weight + 0.25·singleton + 0.2·outlier + 0.15·emotion
```

**两个用途**（v2 明确拆分）：

1. **链 ③ 准入**：`salience >= 阈值` 的段才建议入库（配合人工确认）
2. **链 ② 折叠**：从"折最早的"改成"**折 salience 最低的**"

```python
# 现在（context_compress.py:167）：无条件折最早的
self.segments[0] = f"[早期内容已折叠] {first[:200]}"
# 改成：折 salience 最低的那段，且只折已 staged（已入库）的段
```

**第二条是 v2 相对 v1 的实质改进**：只有已经沉淀进知识库的段才允许被折叠，
没入库的段即使 salience 低也不能折——因为折了就真的没了。
这把"折叠"从纯丢弃动作变成"**已备份后的释放**"，安全性由结构保证，不再靠阈值碰运气。

**代价（如实标注）**：singleton 会保留一次性噪声（随口提的冷僻名词），
所以权重压在 0.25 且必须配合类型权重——"只出现一次 + 类型是闲聊"仍然低分。

### 4.5 P1：情感强度 —— 用规则做，不引模型

不引入情感模型（多一个依赖、多一次调用、中文情感词典准确率不稳）。用**高置信度规则信号**：

| 信号 | 正则/判据 | 权重 |
|---|---|---|
| 绝对化强调 | `必须\|绝对\|千万\|一定\|永远\|再也\|无论如何` | 高 |
| 否定约束 | `不要\|别\|禁止\|不许\|不能` | 高 |
| 纠正（最强） | `不对\|不是这个\|我说的是\|你理解错了\|重新说` | **最高，直接置顶** |
| 重复强调 | `非常非常`、`真的真的`、连续 `！！` | 中 |
| 显式要求记住 | `记住\|别忘了\|以后都\|记一下` | **最高，直通入库** |

### 4.6 P1：访问频率 —— 补两件事（含知识库侧）

1. **知识库条目命中计数**（v2 新增，价值最高）：检索命中时给对应 chunk 记 +1，
   排序时按 `hits` 提权。数据落在哪要定：建议 SQLite 侧建一张 `chunk_hits(kb_id, chunk_id, hits, last_hit)`，
   不动 Chroma（避免向量库与关系库一致性问题）。
2. **时间衰减**：`user_tags.weight` 只增不减是真实缺陷。改成
   `score = hits / (1 + λ·Δt_days)`（λ 建议 0.05，20 天衰减一半）。
   压缩段同理：`effective_salience = salience · decay(age) + β·hits`。

### 4.7 P2 → 可提前：跨会话记忆（v1 判"不做"，v2 改判）

v1 的理由是隐私边界与跨会话污染。v2 认为**载体变了，这些理由大部分失效**：

| v1 顾虑 | v2 判定 |
|---|---|
| 隐私边界 | **已解决**：知识库按 `owner_id` 隔离（`_must_own`），用户自己的库 |
| 遗忘机制 | **已解决**：知识库条目可删（`api/kb.py:273 delete files` 一条链路） |
| 跨会话污染 | **部分存在**：A 会话的约束被 B 会话检索到，但这是**特性不是 bug**——只要 `source` 标明来源会话，用户可判断 |

**但要保留的前提**：必须人工确认后入库（4.1 已定），且 `source` 必须可辨识。
自动跨会话记忆仍然不做。

## 5. 整句入库的三个副作用（v2 新增，必须面对）

"整句保存没关系"这个判断是对的，但它不是零成本。三个副作用必须配套处理，
否则整句入库会反过来伤害检索质量：

### 5.1 噪声入册

对话里有大量中间态：试错、半句话、被自己推翻的说法。整句入库会把它们一起写进去。
**缓解**：人工确认 + 预览（4.1 已定），且默认只勾选 `salience` 高于阈值的条目。

### 5.2 纠正前后冲突

"端口是 8080" → "不对，是 3000"。两句都入库，检索时都可能被召回，模型无法判断哪个对。
**缓解**：纠正信号命中时，把前一句标记为作废（`staged=False, superseded=True`），
检索过滤掉 `superseded` 条目。这需要给 chunk metadata 加一个字段。

### 5.3 检索阈值未标定 → 存进去了也召不回

这是 2026-10-20 审计 §6 已经记录的发现，v2 必须把它串起来：

> 剔除字面盲区题后 `recall@1 = 1.0`、`MRR = 1.0`，**但相关题被判 weak 的比例仍是 100%**。
> 系统是"找到了答案，却告诉用户没找到依据"，根因是 `RETRIEVE_MIN_SIM=0.25` /
> `RETRIEVE_LOW_SIM=0.45` 这两个**未标定的跨模型常量**。

**这条对"整句入库"是致命的**：如果召回判据本身是错的，
那么整句保存做得再 faithful，用户也拿不到——
**沉淀的价值 = 存得下 × 召得回**，现在第二项接近 0。

所以 4.1（开通路）和阈值标定**必须成对做**，只做前者等于把知识倒进一个找不出来的仓库。

**验收工具已就绪**：`tools/eval_retrieval.py` + `tools/eval_corpus/`，
有真实 EMBEDDING_API_KEY 时用 `--live` 重跑，产出 `recall@k`/`MRR`/AUC 用于重定阈值。

## 6. 落地顺序与验收口径（v2）

| 顺序 | 事项 | 验收（可测） |
|---|---|---|
| 1 | `Segment` 结构化 + 旧格式兼容（4.2） | 老压缩块 `parse()` 后段数不变、内容不丢 |
| 2 | **开对话→知识库通路**（4.1） | 沉淀后新会话能检索到，`source` 显示来源会话 |
| 3 | 分流规则（4.3） | 单测：约束句归"入库"，寒暄句归"抽象"；含"记住"的句子直通入库 |
| 4 | salience 四信号（4.4） | 单测：约束句 > 闲聊句；singleton 句 > 重复句 |
| 5 | **折叠改为"只折已 staged 的最低 salience 段"** | 单测：**第 1 轮说过一次的关键约束，20 轮后仍在压缩块里**（现在必挂） |
| 6 | 纠正信号置顶 + 作废标记（5.2） | 单测：含"不对，我说的是"的轮次永不折叠；前版本被过滤 |
| 7 | 知识库命中计数 + 衰减（4.6） | 单测：被反复检索的条目排序靠前；老标签权重随天数下降 |
| 8 | 阈值标定（5.3） | `tools/eval_retrieval.py --live` 产出 AUC ≥ 0.8 |

**回归口径**：`tests/test_context_compress.py`、`tests/test_compress_wiring.py` 必须全绿；
全量 `pytest -q` 不得回退（当前基线 397 passed）。

**一条建议**：把"20 轮后追问早期约束"做成**固定回归用例**写进测试。
这是本系统最容易静默退化的地方——今天改好了，三个月后有人动一下折叠逻辑它又会坏，
而且坏的时候**没有报错、测试不红、日志无异常**，只是回答开始失忆。

## 7. 不做的事（诚实边界）

| 事项 | 为什么不现在做 |
|---|---|
| 引入情感分析模型 | 多一个依赖 + 一次调用；规则信号已覆盖最高价值场景（纠正/显式记住/绝对化） |
| 自动（无人确认）沉淀到知识库 | 噪声与错误中间态不可逆入库，用户要逐条删。**必须人工确认 + 可预览** |
| 给每段单独调 LLM 打 salience 分 | 每段一次调用，成本与延迟不划算；四信号里只有"类型"需要 LLM，可**整批一次调用**完成 |
| 换 Postgres / 迁 Redis | 与本次改动无关，且 2核2G 下 SQLite 仍够用 |
| 压缩块里做向量召回 | 方案比问题贵。知识沉淀的正确载体是知识库（已有检索链路），不是给压缩块再造一套 |

## 附：与省赛评分的对应关系

《中国大学生计算机设计大赛·人工智能应用类》"技术方案 30%"看"算法有延展、改进、优化"。

v2 相对 v1 多出一个**更好讲的故事**：

> 通用做法是"压缩对话历史以省 token"，我们把它拆成了三条目标函数不同的链
> （进上下文要少、压缩块要省、进知识库要全），
> 并按载体成本决定保真策略——**知识项整句沉淀进知识库，压缩块只留指针**。
> 这既解决了长期记忆，又把上下文成本降下来，且**信息零损失**。

这个故事的三个支撑点都是可测的：结构化兼容（老库不废）、折叠只折已入库段（早期约束不丢）、
沉淀后可跨会话检索（`source` 可溯源）。答辩时逐条演示，比堆功能更有效。
