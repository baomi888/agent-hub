## 一、后端：`top_k` 服务端上界（★★ 无界输入）

**问题**：前端 UI 已把「检索条数」限制在 1–10（`ChatArea.tsx` 的 `Field max={10}`），
但服务端三个入口都只校验了下界，没有任何上界：

| 入口 | 现状 |
| --- | --- |
| `api/chat.py:63` `ChatRequest.top_k` | `Field(default=..., gt=0)` |
| `api/schemas.py:23` `KBQueryRequest.top_k` | `Field(default=..., gt=0)` |
| `api/kb.py:158` `query_kb(..., top_k: int = 3, ...)` | 查询参数，无约束 |

客户端绕过前端直接调接口、传 `top_k=100000`，会把候选池（`top_k × RETRIEVE_FETCH_MULT`）
拉爆，检索耗时、MMR 计算量与返回体一起膨胀——属于最容易被忽略的「无界输入」。

**改法**：新增一个可配常量，三处入口统一加 `le` 约束。

```python
# core/config.py
TOP_K_DEFAULT = int(os.getenv("TOP_K", "3"))
# 检索条数上界：前端 UI 已限 1~10，服务端再兜一道，避免请求塞超大 top_k 拉爆检索与费用
TOP_K_MAX = int(os.getenv("TOP_K_MAX", "20"))
```

```python
# api/chat.py / api/schemas.py
top_k: int = Field(default=config.TOP_K_DEFAULT, gt=0, le=config.TOP_K_MAX)
```

```python
# api/kb.py（查询参数改用 Query 约束；同步补 Query 与 config 导入）
top_k: int = Query(default=3, gt=0, le=config.TOP_K_MAX)
```

超限请求由 FastAPI 直接拦成 **422**，不进检索。默认 20 给前端 1–10 留了余量；
自建环境想放宽设 `TOP_K_MAX` 即可，无需改代码。

## 二、前端：`usePrefs` 检索参数读回（★★★ 用户设置被抹掉）

**问题**：`usePrefs.ts` 挂载时只读回了 `mode / kbPanel / fontScale`，
**没读回 `topK / chunkSize / chunkOverlap`**。这三个状态于是停在 `useState` 默认值（3 / 500 / 50）；
`prefsReady` 置真后的落盘 effect 会把默认值写回 `localStorage`——
用户改过检索条数、一刷新就被改回默认，**等于设置被永久抹掉**（此前一直被误当成"只是不回显"）。

**改法**：挂载 effect 里补三行读回，与 `page.tsx` 的 defaults 兜底逻辑对齐
（本地存过就不用后端默认值）。

```ts
if (typeof saved.topK === "number") setTopK(saved.topK);
if (typeof saved.chunkSize === "number") setChunkSize(saved.chunkSize);
if (typeof saved.chunkOverlap === "number") setChunkOverlap(saved.chunkOverlap);
```

读回与落盘的时序：挂载 effect 先把 `saved` 写入状态并置 `prefsReady`，
同一次批渲染后落盘 effect 读到的就是已读回的值，不会再发生"默认值反向覆盖"。
