# JWT 登录改造报告 2026-10-20

**参照物**：`study_repo/Java/pritice_program/sky-take-out`（苍穹外卖）
**改造对象**：`core/auth.py`、`core/account.py`、`api/auth.py`、`core/token_store.py`（新增）
**一句话**：把 sky-take-out 的「登录四步 + 拦截器验令牌 + 身份上下文」完整搬到本项目的
JWT 上，并补掉它**故意留空**的一块（logout 不失效）。

## 一、先看 sky-take-out 到底做了哪几层

我把它的链路按调用顺序拆成 7 步（源码位置都是主工程 `sky-take-out/sky-take-out/`）：

| 步 | 位置 | 做了什么 |
|---|---|---|
| 1 | `EmployeeController.login` | 收 `EmployeeLoginDTO(username, password)` |
| 2 | `EmployeeServiceImpl.login` | **按用户名查库** → 查不到抛 `AccountNotFoundException` |
| 3 | 同上 | **MD5 比对口令** → 不匹配抛 `PasswordErrorException` |
| 4 | 同上 | **校验 `status`** → `DISABLE` 抛 `AccountLockedException` |
| 5 | `EmployeeController.login` | `claims.put(JwtClaimsConstant.EMP_ID, employee.getId())` → `JwtUtil.createJWT(adminSecretKey, adminTtl, claims)` |
| 6 | `EmployeeLoginVO` | 把 `token` 塞进返回体（`id / userName / name / token`） |
| 7 | `JwtTokenAdminInterceptor.preHandle` | 从请求头 `admin-token-name`（= `token`）取值 → `parseJWT` → 取 `empId` → `BaseContext.setCurrentId(empId)` → 放行；任何异常 `response.setStatus(401)` |

配套三件套：

- `JwtProperties`：管理端 / 用户端**各一套** `secret-key / ttl / token-name`
- `WebMvcConfiguration.addInterceptors`：`/admin/**` 挂管理端拦截器，**排除 `/admin/employee/login`**；
  `/user/**` 挂用户端拦截器，排除 `/user/user/login`、`/user/shop/status`
- `BaseContext`：一个 **ThreadLocal<Long>** 存当前操作人 id，Service 层用
  `BaseContext.getCurrentId()` 取"谁在操作"（省得每层都传参）

## 二、本项目对应实现了什么（逐项映射）

| sky-take-out | 本项目 | 状态 |
|---|---|---|
| `JwtUtil.createJWT(secretKey, ttlMillis, claims)` | `core/auth.py::create_token(uid, ttl_days, username)` | ✅ 等价。仍是 HS256，仍是手工实现（不加 PyJWT 依赖） |
| `JwtUtil.parseJWT(secretKey, token)` | `core/auth.py::decode_claims()` / `decode_token()` | ✅ 等价。`decode_claims` 返回全载荷，`decode_token` 保持"只取 uid"的老形状 |
| `JwtProperties.adminSecretKey` / `userSecretKey` | `config.AUTH_SECRET`（单套） | ✅ 本项目只有一个身份面，不需要两套密钥；密钥优先级：env > `data/.auth_secret` > 现生成落盘 |
| `adminTtl` / `userTtl` | `config.AUTH_TTL_DAYS`（默认 7 天） | ✅ |
| `adminTokenName` / `userTokenName`（`token` / `authentication`） | `config.AUTH_TOKEN_HEADER`（默认 `X-Auth-Token`） | ✅ 合并成一个头名，另兼容 `Authorization: Bearer` |
| `JwtClaimsConstant.EMP_ID` | `CLAIM_UID` + 标准字段 `sub` | ✅ 双写，老令牌仍能解 |
| `JwtClaimsConstant.USERNAME` | `CLAIM_USERNAME` | ✅ 多带的：省掉"每次渲染导航栏查一次库" |
| —（sky 没有） | `CLAIM_JTI` | ➕ 新增，用于吊销 |
| 拦截器从**请求头**取令牌 | `extract_token()`：`X-Auth-Token` → `Authorization: Bearer` → **Cookie** | ✅ 加了 Cookie 这一档（浏览器主路径） |
| `BaseContext.setCurrentId()`（ThreadLocal） | `request.state.uid / .username / .token_claims` | ✅ 等价，但**故意不用 ThreadLocal**（见 §三-2） |
| `WebMvcConfiguration` 注册拦截器 + 排除登录路径 | FastAPI `Depends(get_current_user)` + router 级 `dependencies=[...]` | ✅ 更严：**默认要登录**，新增端点忘写鉴权时默认是安全的那一侧 |
| `EmployeeServiceImpl.login` 的三步校验 | `core/account.py::login()` 返回 `(user, reason)` | ✅ 顺序完全一致 |
| `AccountLockedException` | `403` + `LOGIN_LOCKED` | ✅ 新增 `users.status` 列（1 正常 / 0 停用），老库用 `ALTER TABLE` 自动补列 |
| `StatusConstant.ENABLE / DISABLE` | `account.STATUS_ENABLE / STATUS_DISABLE` | ✅ |
| `EmployeeLoginVO.token` | `UserOut.token`（**默认不返回**） | ⚠️ 有取舍，见 §三-1 |
| `logout` → `return Result.success()`（**空实现**） | `api/auth.py::logout` 吊销 `jti` | ➕ **补上了 sky 的缺口** |

## 三、三处「刻意不照抄」，各自有理由

### 1. 不把 token 交给浏览器 JS（`AUTH_RETURN_TOKEN` 默认关闭）

sky 的做法是 `EmployeeLoginVO.token` 直接把令牌给前端，前端自己存着、每次请求塞头。
本项目**默认不返回**，原因：浏览器侧走 HttpOnly Cookie 已经够用，把 token 交给 JS
等于把 XSS 的收益从"偷不到"变成"直接拿走 7 天会话"。

需要 token 的场景（App / 小程序 / Swagger / 压测）用 `AUTH_RETURN_TOKEN=1` 打开，
那时候客户端本来也没有 Cookie 罐子，走 `X-Auth-Token` 头是对的。

### 2. 不用 ThreadLocal，用 `request.state`

sky 用 `BaseContext`（ThreadLocal）是因为 Spring MVC 一个请求独占一个线程，
请求结束线程归还、ThreadLocal 随之清理。

FastAPI 不一样：**同步依赖跑在线程池里，多个请求会复用同一个线程**。照抄 ThreadLocal
会出现"上一个请求的 uid 残留到下一个请求"的串号事故——这在多用户系统里是数据越权，
不是小 bug。所以改用 `request.state`（生命周期与请求严格绑定），语义等价、隔离正确。

### 3. "账号不存在"和"密码错误"对外合并成一句话

sky 分两个异常、给前端两句不同的话，因为它的"员工账号"是管理员在后台开的，
不存在枚举风险。

本项目**自助注册开放**，区分这两者等于免费提供一个"哪些用户名存在"的枚举接口。
所以对外统一 `401 用户名或密码不正确`，但**内部仍然区分**（`LOGIN_NO_USER` /
`LOGIN_BAD_PASSWORD`），并保留"查不到用户也跑一次等价耗时散列"——否则响应时间差
本身就泄露了用户是否存在。

**状态锁定必须区分**（403 `账号已被停用`）：这不是安全问题，是可用性问题——
用户得知道"不是密码错了，是号被停了"，否则会一直重试。

## 四、补上 sky 留空的那块：logout 真的能踢下线

sky 的 `logout` 是空实现（`return Result.success()`）。这在教学项目里没问题，
但意味着**令牌在到期前一直有效**：用户点了退出，换个客户端拿着旧 token 照样能进。

JWT 无状态，要做到"退出即失效"只有两条路：白名单（每枚令牌都落库）或黑名单（只存被吊销的）。
本项目选黑名单：

```
签发 → payload 里带 jti（secrets.token_urlsafe(16)）
退出 → token_store.revoke(jti, exp) 写一行
验令 → decode 通过后查一次 jti 是否在黑名单（主键点查，O(1)）
清理 → revoke 时顺手 DELETE WHERE exp < now，表不会无限长
```

为什么不用白名单：200 人在线就是 200 行常驻 + 每请求一次读；
黑名单只在退出时才写，绝大多数令牌一辈子不进去。


15 条覆盖：

| 组 | 覆盖点 |
|---|---|
| 载荷 | uid/username/jti 齐全、jti 每枚不同、`decode_token` 老契约不变（乱码/空串/过期都 None） |
| 取令牌 | `X-Auth-Token` 优先于 Cookie、`Authorization: Bearer`、Cookie 兜底、头里写 `Bearer xxx` 也能剥 |
| 身份 | 头部令牌能解出 uid 并写入 `request.state`；乱码/过期一律 401 |
| 吊销 | 黑名单命中 → 401（含"退出"字样）；logout 调用时带上正确的 jti 与 exp |
| 登录顺序 | 账号不存在与密码错**返回同一句话**；锁定 → 403 且提示"停用"；成功时下发 HttpOnly Cookie 且默认不回吐 token；`AUTH_RETURN_TOKEN=1` 时回吐 |

> 踩到的坑记录在案：这 15 条**单跑全绿、全量跑必炸**（`no such table: users`）。
> 原因是 `pytest.ini` 里早写过的那条——不少测试把 `core.session._db_path` 改到临时库，
> 而建表只在首次 import 跑一次。已加 autouse 夹具在每个用例前对**当前**库补建表，幂等。

## 六、还没做的（明确留白，避免"看起来做完了"）

| 项 | 为什么没做 | 建议 |
|---|---|---|
| 刷新令牌（refresh token） | sky 也没有；7 天有效期对本项目够用 | 要做的话：短 access（30min）+ 长 refresh（30d）+ 轮换 |
| 登录失败计数 / 自动锁定 | 现在只有"每分钟 10 次"限流，没有"连续错 5 次锁 30 分钟" | 属于账号风控，可复用 `users` 加两列 |
| 令牌版本号（改密码即失效） | 需要 `users.token_version` 参与验签 | 与 refresh 一起做更划算 |
| 每请求校验 `status` | **对齐 sky**：只在登录时校验（拦截器不查库），换来每请求零 DB 读 | 强制下线需求变强时，把 `status` 塞进令牌并接受"最长 7 天延迟"，或加短 TTL |
| 多设备登出（踢所有端） | 需要"按 uid 吊销"索引 | 加 `revoked_tokens.uid` 列即可 |

## 七、一句话总结

sky-take-out 给的是**一套形状正确但刻意简化**的 JWT 登录：签发、验签、拦截、上下文四步齐全，
但退出登录是空的、状态只在登录时看、令牌走请求头给前端存。

本项目把这套形状完整对齐了（四步顺序、claims 结构、拦截器语义、身份上下文），
此外补了三处它没覆盖的：**退出即吊销（jti 黑名单）**、**令牌可走 Cookie（HttpOnly + Secure）**、
**身份上下文用 request.state 而非 ThreadLocal（避免线程复用串号）**。
