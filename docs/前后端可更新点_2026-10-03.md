## 一、后端新增可更新点

### ★★★ 1. async 端点里裸调同步 Chroma 代码，每次请求新建 `PersistentClient` 并阻塞事件循环

**文件**：`api/chat.py:219`、`api/kb.py:142 / 162 / 174 / 63`、`kb/pipelines.py:243`、`kb/rag_core.py:269 / 354 / 364`

```python
# api/chat.py:219  —— 在 async def chat_stream 里
kb_exists = bool(kb_id and pipelines.exists(kb_id))
#   pipelines.exists → pipe.peek() → rag_core.py:354
#   → chromadb.PersistentClient(path=config.PERSIST_DIR)   ← 每次一条！
```

**实测**：`PersistentClient` 冷启动 **0.588s**，之后稳定 **0.098s/次**。也就是说：

- 每发一条消息 → `exists()` 建一次客户端，事件循环停 ~100ms；
- 每次 `GET /api/kb/`（右栏列表）→ `list_all()` 建一次，加上 `list_collections()`；
- `delete_kb` / `get_status` 同理；`build_index` 的 rebuild 分支还多建一次。

项目自己在 `MEMORY.md` 第四节定的规矩是「**async 端点里凡是同步阻塞调用都用 `asyncio.to_thread`**」，
`kb/pipelines.py` 的执行路径全都遵守了（upload/rebuild/delete_file 都包了 `to_thread`），
**唯独这几个"只读一下"的入口漏了**——又是熟悉的「同文件/同类路径不对称」。

**怎么改**（两条，一起做）：
1. `kb/rag_core.py` 顶部加一个模块级 client 单例：
   ```python
   _CLIENT_LOCK = threading.Lock()
   _CHROMA_CLIENT = None
   def chroma_client():
       global _CHROMA_CLIENT
       with _CLIENT_LOCK:
           if _CHROMA_CLIENT is None:
               _CHROMA_CLIENT = chromadb.PersistentClient(path=config.PERSIST_DIR)
           return _CHROMA_CLIENT
   ```
   把 `peek()`(:354)、`delete()`(:364)、`build_index()`(:269)、`pipelines.list_all()`(:243) 全换成它。
2. 那几个 async 端点包 `await asyncio.to_thread(...)`：
   `chat.py:219` 的 `exists`、`kb.py:142` 的 `list_all`、`kb.py:162` 的 `get_status`、`kb.py:174` 的 `delete_kb`。

顺带的副产品：多个 `PersistentClient` 指向同一个 sqlite 文件，本身就有锁竞争隐患，换单例一并消掉。

### ★★★ 2. 两处上传都「先整份读进内存，再判大小」——2G 机器上一次大文件就能打 OOM

**文件**：`api/kb.py:72-74`、`api/chat.py:120-124`

```python
# kb.py
content = await f.read()                              # ← 1GB 也照读
if len(content) > MAX_UPLOAD_MB * 1024 * 1024:
    raise HTTPException(status_code=400, detail=...)  # ← 判断在读完之后

# chat.py:120-124  一模一样的写法
content = await f.read()
if len(content) > MAX_CHAT_UPLOAD_MB * 1024 * 1024:
    raise HTTPException(...)
```

`MAX_UPLOAD_MB = 100` 这个上限**根本防不住**：它是"读完之后才发现超了"，
此时 1GB 已经进了进程内存。部署机是**阿里云 2 核 2G**，两个并发大文件就能让 uvicorn 被 OOM killer 带走，
而用户看到的只是"连接被重置"。

**怎么改**（半天，两条路选一条）：
- 便宜版：先读请求头 `Content-Length` 判一次（Nginx/uvicorn 都会给），超了直接 400，连 body 都不读；
- 稳妥版：改成流式写盘——`async for chunk in f.stream()`，边写边累加，超 `MAX` 立刻 `break` + `os.unlink` + 400。
  FastAPI 的 `UploadFile.file` 支持按块读，不用 `f.read()` 全量。

### ★★ 3. 上传中途失败会在 `data/kb_sources/` 留下永不回收的孤儿原始文件

**文件**：`api/kb.py:65-82`

```python
for f in files:
    ext = os.path.splitext(f.filename or "")[1].lower()
    if ext not in (".txt", ".md", ".pdf"):
        raise HTTPException(400, ...)     # ← 第 3 个文件不合法
    ...
    with open(dest, "wb") as out:
        out.write(content)                # ← 前 2 个已经落盘了
    saved.append((dest, name))
```

抛 400 之后，前两个文件**已经躺在磁盘上**，但：

- 没进 `add_file_records` → `kb_files.json` 里没有；
- 没进 Chroma → 检索不到；
- `rebuild` 走的是 `get_file_names()`（读记录）→ 也读不到它们；
- 只有 `delete_kb` 的 `shutil.rmtree` 才清得掉。

于是用户改个扩展名再传一次，磁盘上就多一份永久垃圾。

**怎么改**（10 行）：把「校验 + 落盘」拆成两趟——先对全部文件做扩展名/`Content-Length` 校验，
全过了再逐个写盘；或者 `except` 里把 `saved` 里已落盘的 `os.unlink` 掉。

### ★★ 4. 第三条 SSRF 通道：`import_url` / `import_urls_batch`，而且批量接口对 URL 数量没上限

**文件**：`kb/importer.py:31-46`，经 `api/kb.py:375-397` 暴露；批量处 `api/kb.py:388`

前两轮已经点过两条 SSRF 通道（`api/kb.py:400` 的下载代理、`importer.py:171` 的 Agent 工具 `download_file`），
**这条是第三条**，以前没人提：

```python

resp = httpx.get(url, headers=_HTTP_HEADERS, timeout=15, follow_redirects=True)
```
没有任何内网地址拦截，`http://169.254.169.254/…`、`http://10.0.0.1:8080/…` 照抓，
抓回来的正文还会**写进知识库**并回显到前端（`file-content` 预览），等于一个带回显的内网探测器。

**怎么改**：

- `urls: list[str] = Field(..., max_length=20)`。

### ★★ 5. `get_messages` 全表扫描后在 Python 里截断；会话详情因此永远只给最近 10 轮

**文件**：`core/session.py:205-221`（+ `:190` 的 `limit_turns=MAX_HISTORY_TURNS`）、`api/sessions.py:38`

```python
rows = conn.execute(
    "SELECT ... FROM messages WHERE conversation_id = ? ORDER BY id ASC", (sid,)
).fetchall()                 # ← 全量读进内存
msgs = [dict(r) for r in rows]
...
if len(user_indices) > limit_turns:   # ← 读完了才截

```

一个聊了 500 轮的会话，每次发消息要把 1000 条消息全读出来再丢掉 980 条——**磁盘 I/O 和内存都白付**。

### ★★ 7. `calculator` 还有一条 DoS 口子：12 位字面量的幂运算

**文件**：`agent/tools.py:125 / 142-157`

```python
_CALC_MAX_DIGITS = 12       # 单个数字字面量的最大位数
...
if any(len(n) > _CALC_MAX_DIGITS for n in re.findall(r"\d+", expr)):
    return f"数字过大..."
result = eval(expr, {"__builtins__": {}}, {})     # ← 这里
```

已经防了 `9**9**9`（`:149` 拒连续幂）和超大字面量，但漏了**一步到位的巨幂**：
`999999999999**999999999999` —— 两个操作数都是 12 位，**两道检查都过**，
`eval` 会去算一个约 1.4×10¹³ 位的整数，线程瞬间卡死 + 吃满内存。
这个表达式完全可以由模型（或被注入的提示）自己构造出来。

顺带：`:123 _CALC_ALLOWED = set(...)` 是**死常量**——真正的校验是 `:146` 的正则，这个 set 从没被读过。

**怎么改**：
- 把指数单独限死：`re.split(r"\*\*", expr)` 后，指数部分位数 ≤ 3（或结果位数预估 > 30 位就拒）；
- `_CALC_ALLOWED` 删掉（或改成真正用它做校验）；
- 更彻底：换 `ast.literal_eval` 之外的一个小表达式解析器，彻底不用 `eval`。

### ★★★ 14. `streamChat` 没有 `try/finally`，消费方一中断 reader 就永远不释放

**文件**：`frontend/src/lib/sse.ts:56-72`

```ts
const reader = res.body.getReader();
while (true) {
  const { done, value } = await reader.read();     // ← 卡在这一行
  ...
}
// 没有 try / finally，也没有 reader.cancel()
```

10-02 报告只写了"没有 `releaseLock()`"，但**真正的成因是没有 `try/finally`**——
光在循环结束后补一行 `releaseLock()` 解决不了问题：
`page.tsx` 的 `for await` 在收到 `error` 事件后 `return`、或者用户切会话导致组件卸载时，
生成器会被挂起在 `await reader.read()` 上，**`res.body` 不 cancel、连接不断、缓冲区不释放**。

**怎么改**（6 行）：
```ts
try {
  while (true) { ... }
} finally {
  try { await reader.cancel(); } catch { /* ignore */ }
  reader.releaseLock();
}
```
配合已经修好的 `AbortController`（`page.tsx:168`）就完整了。

## 附二：傍晚部署踩坑（`requirements.txt` 格式错误，已修）

**现象**：走「GitHub 源码包覆盖 /root」更新后，`bash deploy.sh deploy` 在前 4 步全 OK，
**第 5 步「后端依赖（venv）」中止**：

```
ERROR: Invalid requirement: '"""集合式 Agent 后端依赖（LangChain v1.x）'
  Expected package name at the start of dependency specifier   (from line 2 of requirements.txt)
[中止] 后端依赖安装失败
```

**根因**：`requirements.txt` 第 2~4 行写成了 **Python 文档字符串**：

```
# -*- coding: utf-8 -*-
"""集合式 Agent 后端依赖（LangChain v1.x）
版本固定，避免 pip 自动升级导致 API 不兼容。
"""
```

`requirements.txt` 是 pip 的格式，注释**只能以 `#` 开头**。pip 解析到第 2 行即判非法并退出。
这个写法**从首次提交 `9e7cd31` 起就存在**——说明服务器上的 venv 从来不是靠 `deploy.sh` 装起来的，
而是更早一次手工/旧包部署留下的；这次覆盖 `/root` 才第一次真正执行到第 5 步，问题才暴露。

**修法**：改成 `#` 注释，并补上格式警告。提交 `45cdbf0`，已验证
`packaging.requirements.Requirement` 逐行解析 **18 行全部通过**，且 18 个依赖在 PyPI 上均可解析
（顺带核实 `langgraph-checkpoint-sqlite>=3.1` → 3.1.1，与 `langgraph 1.2.11` 要求的
`langgraph-checkpoint<5.0.0,>=4.1.0` **不冲突**，所以它不是这次的拦路石）。

**两条副产品结论（本轮新增，值得记住）**：

1. **`deploy.sh` 的失败不会断服务**：`do_stop` 只在**第 7 步启动前**调用（第 293 行），
   第 1~6 步任何一步 `die` 都只是"没换成新代码"，线上照常跑旧版本。
   ⇒ 以后遇到部署中止，不必先慌"站点是不是挂了"。
2. **`restart` 跳不过 pip**：`restart` = `do_stop` + `start`，而 `start` 只设 `SKIP_BUILD=1`
   （仅第 6 步前端构建受它管），**第 5 步 `pip install -r requirements.txt` 任何模式都会执行**。
   ⇒ 纯 Python 改动想省时间也省不掉这一步。（可考虑给 `start` 加 `SKIP_PIP`，见下。）
3. **方法论**：这次是"**同一个文件里格式规范只对了一半**"——第 1 行写了 `# -*- coding: utf-8 -*-`，
   紧跟着第 2 行就写成三引号。与前几轮"同一个模式 A 处做对 B 处漏了"是同一种病，
   只是这次发生在**配置文件语法**上。⇒ 改配置类文件时，要按**消费方（pip/yaml/json）的解析器**
   逐行验一遍，不能靠眼睛看着像。
