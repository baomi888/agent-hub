## 一、后端可更新点

### ★★★ 1. SQLite **每调用开一次连接**：实测推翻 10-07 的「0.006~0.057ms」结论

**位置**：`core/session.py:49-61` 的 `_get_conn()`

```python
def _get_conn() -> None:
    conn = sqlite3.connect(_db_path())      # ← 每次调用都新建连接
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL") # ← 每次调用都重跑 PRAGMA
```

**为什么会记错**：10-07 那条 `0.006~0.057ms` 测的是**单次裸查询的 SQL 执行时间**，
没算「建连接 + 跑 PRAGMA + commit + close」。真实业务函数是前者 + 后者。

**本轮实测（本机，各 100~300 次取平均，已剔除冷启动）**：

| 操作 | 实测耗时 |
|---|---|
| `get_conversation` | **3.29 ms** |
| `list_conversations` | **3.87 ms** |
| `get_messages` | **6.20 ms** |
| `count_messages` | **9.22 ms** |
| `rename_conversation` | **19.31 ms** |
| `add_message` | **23.03 ms** |
| `create_conversation` | **21.47 ms** |

比旧记录高了 **2~3 个数量级**。

**根因定位（对照实验，非推测）**：

| 写法 | 单次 INSERT 耗时 |
|---|---|
| 现状：每调用新连接 + PRAGMA WAL | **15.27 ms** |
| 每调用新连接，但不跑 PRAGMA | 16.87 ms（**无改善**，PRAGMA 不是瓶颈） |
| **复用单连接** | **2.97 ms（省 80.5%）** |

顺带一个**阴性结果**：`PRAGMA synchronous=NORMAL` 在这个场景下**完全无效**
（14.26 ms → 15.37 ms，反而慢 7.8%，在噪声内）。别往这个方向优化。

**为什么值得改**：一次 `/api/chat/stream` 在 `event_generator` 内要打 5~7 次 `store.*`
（`api/chat.py:218/267/268/297/318/324/348/465/486/493`），按上表加总是 **~80ms 纯阻塞**。
而部署说明里写着的线上「SSE 首字节 58~78ms」——**这一项就吃掉了一整个首字节预算**。
2 核 2G 的 ECS 上，并发一上来这几个数字还会互相放大。

**怎么改（两步，可分开上）**：

- **立刻**：把上表那 10 处 `store.*` 用 `asyncio.to_thread(...)` 包起来。不降延迟，但**不再堵事件循环**。
- **根治**：`_get_conn()` 改成 `threading.local()` 复用连接。因为业务侧已经走 `to_thread`，
  线程局部存储天然满足 sqlite 的 `check_same_thread=True`，无需放宽校验：

```python
import threading, contextlib
_local = threading.local()

@contextlib.contextmanager
def _get_conn():
    conn = getattr(_local, "conn", None)
    depth = getattr(_local, "depth", 0)
    if conn is None:
        conn = sqlite3.connect(_db_path())
        conn.row_factory = sqlite3.Row
        conn.execute("PRAGMA journal_mode=WAL")
        _local.conn = conn
    _local.depth = depth + 1          # 支持嵌套调用
    try:
        yield conn
        if depth == 0:                # 只在最外层提交
            conn.commit()
    except Exception:
        if depth == 0:
            conn.rollback()
        raise
    finally:
        _local.depth = depth
```

> 注意：进程退出/线程销毁时连接由 GC 回收即可，不必显式 close；
> 若担心长连接占用，可在 `finally` 里按需 `del _local.conn`。

### ★★★ 2. 模板套用端点：零配额、零限流、且不幂等 —— 可无限造会话

**位置**：`api/templates.py:34-59` 的 `apply_template`

```python
@router.post("/{tid}/apply")
async def apply_template(tid: str, uid: str = Depends(get_current_user)) -> dict:
    ...
    kb_id, _ = await asyncio.to_thread(pipelines.create_kb, uid, kb_name)   # :49
    conv = await asyncio.to_thread(store.create_conversation, uid, title, kb_id)  # :52
```

按「新增写入路径四项体检表」逐项比：

| 体检项 | 结论 |
|---|---|
| 配额（quota） | ❌ **无**。对比 `api/kb.py:74/436/442/452` 每个写端点都 `quota.guard`，这里一行都没有 |
| 限流（rate） | ❌ **无**。对比 `api/kb.py:424/471` 的 `quota.hit(uid)`，这里也没有 |
| 大小上限 | ❌ **无**（`create_kb` 名字来自模板，长度不受控） |
| 类型白名单 | ⚠️ `tid` 走 `get_template` 精确匹配，安全 |

**关键不对称**：`create_kb`（`kb/pipelines.py:281-294`）用 `md5(owner|name)` 派生 kb_id，
**天然幂等**，重复点不会多出库；但 `create_conversation`（`core/session.py:139-149`）
每次 `uuid.uuid4().hex[:12]`，**完全不幂等**。

**实测**：连续 `create_conversation` **200 次，0 次被拒**，会话数线性增长到 200。
`core/session.py` 全文搜不到任何 `MAX_SESSION` / `LIMIT` / `count()` 上限。
前端的 `disabled={usingId === t.id}` 只挡 UI，脚本或网络重试照样穿透。

**为什么值得改**：这是「亲友限定部署」上的一条**免认证成本的资源放大器**——
一个已登录用户（甚至是被薅到的普通账号）用一行循环就能把 SQLite 和会话列表撑爆，
而全项目其他写端点都做了防护，唯独新加的这个没有。属于典型的
**"规则 A 处遵守、B 处漏了"**（第 9 轮规则）。

**怎么改**：在 `apply_template` 开头补两行即可，成本极低：

```python
await asyncio.to_thread(quota.hit, uid)                     # 分钟级限流
await asyncio.to_thread(quota.guard, uid, "ask")            # 或按需 consume
```

再加一道软上限（建议放在 `core/session.py`）：

```python
MAX_CONVERSATIONS = int(os.getenv("MAX_CONVERSATIONS", "200"))
# create_conversation 内 INSERT 前：
n = conn.execute("SELECT COUNT(*) FROM conversations WHERE owner_id=?", (owner,)).fetchone()[0]
if n >= MAX_CONVERSATIONS:
    raise RuntimeError("会话数量已达上限，请先清理旧会话")
```

### ★★ 3. `recommended_mode` 没有白名单：模板里的 `"llm"` 是靠 else 分支侥幸生效

**位置**：`api/chat.py:78-85` 的 `_pick_mode` + `api/chat.py:339/429/462` 的三分支

```python
def _pick_mode(req_mode: str, kb_id: str | None, kb_exists: bool) -> str:
    if req_mode != "auto":
        return req_mode          # ← 原样返回，不校验
    ...
```

下游是 `if mode == "agent": … elif mode == "rag": … else: 纯 LLM 模式`（`chat.py:462`）。

`core/templates_catalog.py:126` 给「四六级/雅思」模板写的是 `"recommended_mode": "llm"`。
这个值**不在** `{auto, rag, agent}` 里，靠落到 `else` 才刚好等于"纯 LLM"。

**为什么值得改**：这是**巧合，不是设计**。一旦有人（或后续的后台编辑功能）把模板写成
`"RAG"`（大写）、`"rag "`（尾空格）、`"chat"`，用户就会**静默丢掉 RAG 检索**，
界面上没有任何异常提示，只会觉得"它怎么不查我的资料了"。这类 bug 极难排查。

**怎么改**（`api/chat.py:78`）：

```python
_VALID_MODES = ("auto", "rag", "agent", "llm")

def _pick_mode(req_mode: str, kb_id: str | None, kb_exists: bool) -> str:
    mode = (req_mode or "auto").strip().lower()
    if mode not in _VALID_MODES:
        mode = "auto"                      # 未知值归一，不要静默走纯 LLM
    if mode == "llm" and kb_id and kb_exists:
        return "rag"                       # 有库时 llm 应让位给 rag，见前端 #9
    if mode != "auto":
        return mode
    return "rag" if (kb_id and kb_exists) else "agent"
```

## 二、前端可更新点

### ★★★ 7. 模板页一次网络错误 → **整个画廊被错误页顶掉**，且无重试

**位置**：`frontend/src/app/templates/page.tsx:114-121` 与 `:123`

```tsx
{!loading && error && (
  <div className="py-16 text-center"> … <Link href="/">返回工作台</Link> </div>   // :114
)}
{!loading && !error && grouped.map(...) }                                        // :123
```

两个分支**互斥**：`setError` 一旦被赋值（`:77` 的 `onUse` catch），
已经加载成功的 8 个模板卡片**全部消失**，页面变成一屏报错 + 一个「返回工作台」。

**触发路径很常见**：点「使用模板」时后端 429（配额/限流，见后端 #2 修好之后就会有）
或网络抖动 → `onUse` catch → `setError` → 画廊没了。用户想重试只能回工作台再进来。

**为什么值得改**：这是**模板广场唯一的主交互路径**，失败率不低（依赖登录 + 后端写入），
而失败后给出的出口只有一个"离开页面"。属于「失败回滚」维度的典型缺口。

**怎么改**：
1. 拆成两个 state：`loadError`（首屏加载失败 → 整页错误，合理）与
   `actionError`（套用失败 → 只在顶部挂一条可关闭的提示条，**画廊保留**）。
2. 错误条里加「重试」按钮，直接复用 `onUse(t)`。
3. 顺手把 `:117-120` 的「返回工作台」保留为次要出口。

## 附：本轮的方法论（下次直接用）

40. **★ 重测旧性能结论时，要测"业务函数"而不是"SQL 语句"。**
    10-07 的 0.006~0.057ms 就是只测了 SQL 执行、漏了「建连接 + PRAGMA + commit」，
    导致一条真问题被压了 5 轮。**凡"实测很快所以不用改"的结论，都要确认它测的是完整调用。**
41. **★ 下优化结论前先做对照实验定位瓶颈，别照经验开药。**
    本轮 `synchronous=NORMAL`（教科书式优化）实测**无效甚至更慢**，
    真瓶颈是连接复用（80.5%）。阴性结果同样值得写进报告。
42. **新功能上线后，第一件事是拿「四项体检表」比它的写入路径。**
    模板广场这次又是典型：老端点都有 `quota.guard`/`quota.hit`，新端点一行没有。
43. **"字段生成了但没人消费"是比"字段没生成"更隐蔽的半接线。**
    `recommended_mode` 后端返回、前端类型齐全、就是没人读 → 静默失效。
    **审新接口时，把返回体的每个字段都 grep 一遍前端消费点。**
44. **错误态的"互斥分支"要专门审。**
    `!loading && error` 与 `!loading && !error` 成对出现时，
    一次局部失败会清空整页数据。区分"首屏错误"和"操作错误"是通用解法。
45. **新页面接入时先问"它在不在 AuthGate 里"。**
    AuthGate 只包 `/` 是历史遗留，每加一个需登录的路由都要重新确认。
