# 修复说明 2026-10-13（第二档）：并发踩踏收口 + Serper 统一入口

承接同日第一档（成本与内存护栏）。本档两项：**缓存并发踩踏 single-flight**、
**Serper 调用收敛**。全量 33 项 pytest 通过（含新增 4 组）。

---

## 1. 缓存并发踩踏：BM25 索引 / 查询向量加 single-flight

**文件**：`kb/rag_core.py`

**问题**：`_get_bm25` 与 `_embed_query` 都是"锁内查 miss → 锁外构建 → 再锁写入"
的 check-then-act 模式。缓存在**每次入库/删库后失效**，失效后的第一波并发检索：

- N 个并发查询各自做一遍**全库 `collection.get()` + BM25 建索引**
  （每次都把全文载入内存，大库并发时内存翻倍）；
- 同一问题的并发检索各发一次 **embedding 请求**（约 250ms + 真实 API 费用）。

**改法**：两处都改为"条件变量 + in-flight 登记"的 single-flight：
同一 collection / 同一问题，同一时刻只许一个线程构建，其余线程 `wait()`
构建完成后从缓存拿结果。异常路径 `finally` 里保证登记清除 + 唤醒，不会死锁。

**顺带修掉的隐患——超大库负缓存**：原来库超过 `HYBRID_MAX_DOCS`（20000 片）时
返回 None 且**什么都不缓存**，导致超大库**每次检索都重新全库拉一遍**才发现
"还是太大"。现在记 300s TTL 的否定结果（`_BM25_NEG`），期间直接退回纯向量；
`_cache_invalidate` 会同步清掉它。

## 2. Serper 统一入口：`core/serper.py`

**文件**：新增 `core/serper.py`；改 `agent/tools.py`、`kb/importer.py`

**问题**：
- `web_search`（tools.py）与 `search_preview`（importer.py）**各写了一遍
  Serper POST**，超时、请求头、错误处理、`boost_app_query` 的使用已经分叉
  （tools 的 boost 是后补的拷贝）；
- 两处都是裸 `httpx.post`，每次调用重建 TLS 连接（约 100~300ms 白丢）；
- Serper **按次计费**：Agent 重试、多人搜同一热点，相同关键词重复扣费。

**改法**：收敛为 `core.serper.search_serper(query, count) -> dict | None`：
1. **模块级共享 `httpx.Client`**：连接复用，省重复 TLS 握手；
2. **TTL LRU 缓存**（10 分钟 × 64 条）：同词同数量命中即返回，零费用零延迟；
   缓存键用 **boost 后**的查询词，改写归一化也在缓存之前完成；
3. **single-flight**：并发同词只发一次真实请求；
4. **`boost_app_query` 迁入**：两个调用方共用同一份"App 查询补官网"规则；
   失败返回 `None` 且**不写缓存**（下次自动重试），降级文案由各调用方自定
   （tools 回固定话术、search_preview 抛 RuntimeError，行为与之前一致）。

**行为保持**：`web_search` 的 knowledgeGraph / answerBox 无结果兜底、
`search_preview` 的返回结构均未变；无 key 时不发请求直接走各自的提示分支。
