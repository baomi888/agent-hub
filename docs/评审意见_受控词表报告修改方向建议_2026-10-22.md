# 《受控词表与“增强提示词”技术报告》修改方向建议

> 日期：2026-10-22
> 评审对象：`docs/技术报告_受控词表与查询增强_2026-10-22.md` 及上一轮 RAG 讨论中的关键判断
> 评审目的：不是重写方案，而是指出“哪些结论要保留、哪些要收窄、哪些要先验证”，让报告从“方案全集”变成可执行的“决策 + MVP + 验证”文档
> 结论口径：代码事实优先；没有验证过的数字和交互，一律降级为“待验证假设”

---

## 0. 评审结论

### 0.1 一句话

**方案方向可以保留，但当前报告有三个偏重：范围偏大、交互偏重、指标偏虚。** 真正需要改的不是匹配算法，而是“第一版做多大、用户要不要每题都确认、用什么证明它有效”。

### 0.2 保留不动的部分

| 判断 | 为什么保留 |
|---|---|
| 词表用数据承载，不用 lambda 硬编码 | 可维护、可审计、非代码人员能参与；这是全文最硬的结论 |
| 检索用 `enhanced`、展示/历史用原文 | 避免改写污染历史，也避免用户觉得“我的话被改了” |
| 不做主题硬过滤 | 抽错标签会直接漏召回；v1 只做软偏置是对的 |
| 词表版本化 + 缓存 key 带版本 | 不做的话，词表一改就出现“同问题不同结果” |
| 金标集必须包含反例 | 只收同义词的词表一定会在“数学分析/数学”这类词上翻车 |
| 非代码/代码任务分开 | 词表治理和匹配器是两种工作，混在一起一定互相等 |

### 0.3 需要修改的三类问题

1. **范围**：3 个学科、100~200 个词、50~100 条金标，对第一版偏大；词表质量才是瓶颈，不是代码量。
2. **交互**：要求用户每次点击、逐词确认，操作成本高；大多数用户不会点，点了也多半直接“全部接受”。应改成“高置信默认生效、歧义才确认、按钮用于查看/调整”。
3. **指标**：95% 精确率、70% 接受率、P95<30ms 都是目标值，不是验证过的结论；缺少基线、样本量、置信区间和回滚门槛。

## 1. 建议修改的 12 个方向

> 优先级：P0 = 不改进会影响第一版是否值得做；P1 = 影响成功率/可维护性；P2 = 表达与长期治理。

### M1（P0）把“逐词确认”降级为“歧义确认”

| 项 | 内容 |
|---|---|
| 原文观点 | “必须是‘预览—逐词接受/拒绝—再发送’，不能静默改写。” |
| 问题 | 每问一句都点按钮、逐词看，交互成本高于收益；用户很容易形成“全部接受”的习惯，确认就失去意义。 |
| 建议改为 | **高置信替换默认生效，歧义替换必须确认**；发送后显示一枚“已校准 2 个词”的小标签，点开可查看/撤销。按钮保留，但定位为“查看/调整检索词”，不是每次发送的必经步骤。 |
| 影响 | 前端状态机简化；后端仍需返回 `segments`；产品文案要说明“默认校准、可撤销”。 |
| 验收 | 用户不点按钮也能得到标准词收益；点按钮的用户能逐词改；两条路径结果可解释。 |

> 这样既不违背“用户可确认”，也避免把确认做成新的使用门槛。

### M2（P0）第一版缩到“1 个学科 + 30~50 个词”

| 项 | 内容 |
|---|---|
| 原文观点 | “首批 3 个学科、100~200 个标准词。” |
| 问题 | 词表不是代码，规模一大，审核、歧义裁决、反例维护都会失控；第一版无法证明“是词表带来的提升”还是“某个学科碰巧有效”。 |
| 建议改为 | 先选 **1 个学科**（建议操作系统或考研数学，术语边界相对清楚），30~50 个标准词、100~150 个别名、20~30 条反例；跑通后再复制到第二个学科。 |
| 影响 | N1/N3/N5 的工作量下降；B3 的匹配器规模假设从“10 万别名”改为“1k~5k 别名”。 |
| 验收 | 单学科金标精确率达标，且能说清失败案例属于词表、匹配还是召回。 |

### M3（P0）金标集从 50 条改为“分层 100+ 条”

| 项 | 内容 |
|---|---|
| 原文观点 | “50~100 条金标；精确率 ≥95%；接受率 ≥70%。” |
| 问题 | 50 条里错 2.5 条就是 95%，置信区间很宽；没有基线，95% 可能还不如“完全不替换”。接受率也不是质量指标，用户可能接受错误替换。 |
| 建议改为 | 至少 **100~150 条**，按“单别名/多别名/歧义/反例/无命中”分层；同时跑 **基线（不替换）vs 规范化** 的配对对比，报告 `Recall@k`、`MRR`、nDCG 和 Wilson 置信区间；反例误替换率作为硬门槛（必须为 0）。 |
| 影响 | N5/B7 工作量上升，但这是唯一能证明方案有效的手段。 |
| 验收 | 不只看“替换对了多少”，还看“检索结果有没有变好”。 |

### M4（P0）补一个“词表校验器”，不能只靠 CSV

| 项 | 内容 |
|---|---|
| 原文观点 | “非代码人员用 CSV 往返，先不依赖后台。” |
| 问题 | CSV 很容易出现：同一别名指向两个标准词、`term_id` 重复、`scope` 拼错、别名含 `|`、空定义、废弃词仍被引用。没有校验，错误会直接进入检索。 |
| 建议改为 | 在 B1/B2 之间加一个 **`validate_vocab.py` + CI 检查**：唯一性、必填、scope 枚举、别名冲突、反例冲突、废弃引用、长度限制。非代码人员提交前先跑校验，错误用行号回报。 |
| 影响 | 多一个后端小任务；审核后台可以后置。 |
| 验收 | 一份故意写错的 CSV 能被拦住，并指出具体行和原因。 |

### M5（P1）第一版不要在预览里跑“历史补全”

| 项 | 内容 |
|---|---|
| 原文观点 | “点击按钮时最多允许一次‘历史补全’LLM 调用。” |
| 问题 | 这会引入第二条改写路径、额外延迟和费用；而且补全后再做词表替换，预览里的“改了什么”会混着两种来源，用户很难判断。 |
| 建议改为 | v1 **只规范化当前问题**；历史补全仍由聊天链路现有的自动改写负责，带 `query_plan` 时跳过自动改写。追问场景如果出现指代词，预览提示“建议先补全问题”，不强行补。 |
| 影响 | 点击路径零 LLM、零网络依赖；失败模式更少；代价是追问预览可能不完整。 |
| 验收 | 点击耗时稳定在毫秒级；追问场景不会因为补全失败而阻塞发送。 |

### M6（P1）弱化“用户画像消歧”，v1 只用 KB 领域

| 项 | 内容 |
|---|---|
| 原文观点 | “OS 在计算机画像用户下优先映射到操作系统；苹果在求职语境下优先映射到苹果公司。” |
| 问题 | 画像标签是历史行为推断，可能过时/误判；用它决定标准词，会把“用户没说的事”带进查询。隐私解释成本也高。 |
| 建议改为 | v1 只用 **当前 KB 的领域/标题**做消歧；画像只做“建议排序”，不自动决定。所有消歧必须显示理由，并允许用户改选。 |
| 影响 | 后端少读一张表；预览更容易解释；画像消歧放到 v2 并有开关。 |
| 验收 | 用户能看懂“为什么这个词被这样替换”。 |

### M7（P1）修正“文档 topics 用于偏置”的技术前提

| 项 | 内容 |
|---|---|
| 原文观点 | “文档 topics 映射到 term_id，不重嵌入即可改善偏置。” |
| 问题 | 当前 `_inject_topics` 是**每个来源只取前 4000 字**抽 3~6 个标签（[rag_core.py](file:///c:/biancheng/agent-hub/kb/rag_core.py#L879-L903)）。一本 300 页教材，前 4000 字基本是前言/目录，标签代表不了全书；拿它做偏置，收益有限甚至会误导。 |
| 建议改为 | 二选一：① 按章节/切片抽主题（成本上升，但准确）；② v1 **先不把文档 topics 用于偏置**，只把词表用于查询规范化，等主题抽取改造后再接。不要在报告里把“映射 topics”写成已成立的收益。 |
| 影响 | 可能减少一个后端任务（B8 后置）；偏置逻辑不变，避免“看起来做了个性化，实际是噪声”。 |
| 验收 | 用 20 篇长文档抽查 topics 覆盖率；若章节覆盖率低，就不接偏置。 |

### M8（P1）把“不重嵌入”写清楚适用条件

| 项 | 内容 |
|---|---|
| 原文观点 | “词表是 metadata，可以映射，不需要重新 embedding。” |
| 问题 | 这句话对“只改 topics → topic_ids”成立；但对“加标题路径前缀 / 改分块”不成立，那些必须重建索引。读者容易误以为所有词表相关改动都不用重建。 |
| 建议改为 | 明确区分：**纯词表/标签映射 = 不重嵌入**；**改切片正文/前缀 = 必须重建**。同时说明 Chroma metadata 批量更新的成本，以及 `vocab_version`/`topic_map_version` 要进缓存 key。 |
| 影响 | 避免后端误排期；B8 的验收标准更准确。 |
| 验收 | 报告里能一眼看出“哪些改动要重建、哪些不要”。 |

### M9（P1）性能目标先做基准，不要先写死 10 万/30ms

| 项 | 内容 |
|---|---|
| 原文观点 | “10 万级别名、100 字查询，目标 P95 < 30ms。” |
| 问题 | Python 下纯 Trie 不一定达标；Aho-Corasick 也需要 `pyahocorasick` 这类 C 扩展；Unicode 归一化、重叠匹配、最长优先都会增加耗时。这个数字没有基准，容易变成无法验收的目标。 |
| 建议改为 | 先按 **1k/5k/10k 别名**三档做基准，记录 P50/P95/P99；目标改为“在真实规模下 P95 不超过点击交互可接受阈值（建议 100ms 内）”，30ms 作为优化目标而非上线门槛。 |
| 影响 | B3 验收更现实；如果纯 Python 不达标，提前决定是否引入 C 扩展。 |
| 验收 | 有基准报告，不靠猜。 |

### M10（P1）补“实验设计 + 回滚预案”，不要只有验收指标

| 项 | 内容 |
|---|---|
| 原文观点 | 第 9 节列了离线/在线指标和上线门槛。 |
| 问题 | 缺少基线、分流单位、实验周期和回滚条件；“接受率≥70%”不能证明答案变好。 |
| 建议改为 | 增加一节“实验与回滚”：离线配对对比（基线 vs 规范化）；在线按**用户级**分流（避免同一用户来回切）；护栏指标为答案忠实度、零结果率、P95 延迟；任一护栏恶化超过阈值即按学科关闭开关。 |
| 影响 | 需要数据/后端配合；但这是把“功能上线”变成“可证明有效”的关键。 |
| 验收 | 灰度前能回答：基线是多少、提升多少算成功、什么情况回滚、谁有权回滚。 |

### M11（P2）调整报告结构：先决策，后方案

| 项 | 内容 |
|---|---|
| 原文观点 | 第 0 节是一页纸，但后面仍是完整方案书；任务总表放在最前，读者容易直接进入执行细节。 |
| 问题 | 总负责人需要先拍板“做多大、先做哪步、什么算成功”，再看 schema/API；当前结构把决策和实现混在一起。 |
| 建议改为 | 0 节保留“结论 + 3 个决策问题”；新增“1. 范围与 MVP”“2. 成功标准与实验”“3. 方案（词表/匹配/交互）”“4. 任务与排期”“附录：schema/API/代码索引”。把 12 个策略的细节移到附录。 |
| 影响 | 不改技术内容，只改阅读路径；报告更像决策文档。 |
| 验收 | 总负责人只看前 2 页就能拍板。 |

### M12（P2）措辞降级：把“必须/绝不/安全风险”改成可验证表述

| 项 | 内容 |
|---|---|
| 原文观点 | “lambda 有 eval 安全风险”“必须逐词确认”“绝不阻塞发送”。 |
| 问题 | 只有动态 `eval` 才有安全风险；如果只是普通 lambda 字典，主要问题是可维护性。绝对化措辞会让评审把注意力放在争论上，而不是执行。 |
| 建议改为 | “lambda 的主要问题是词表被写进代码、非代码人员无法维护；只有在动态 `eval` 用户输入时才有安全风险。”其他“必须”改为“建议/验收要求”，并给出原因。 |
| 影响 | 表达更可信；不影响方案。 |
| 验收 | 每条强结论都能指向一个代码事实或一个实验。 |

## 2. 建议的 MVP 重排

### 2.1 原报告的任务顺序

```text
N1 范围 → N2 采集 → N3 词表 → N4 裁决 → N5 金标
B1 模型 → B2 审核 API → B3 匹配器 → B4 预览 → B5 聊天接入
F1 按钮 → F2 高亮 → F3 发送
```

问题：B2 审核 API 和 F4 后台在早期占资源；B5 聊天接入太早；N5 金标太晚，导致“先做功能、后想验收”。

### 2.2 建议的 MVP 顺序

| 阶段 | 做什么 | 不做什么 | 退出标准 |
|---|---|---|---|
| MVP-0 | 1 个学科、30~50 词、20~30 反例；CSV + 校验器 | 不做后台、不做聊天接入 | 词表可导入、校验通过 |
| MVP-1 | 匹配器 CLI + 100~150 条分层金标 | 不做 UI、不做 LLM | 反例 0 误替换；精确率/召回率有基线对比 |
| MVP-2 | `POST /api/query/enhance` + 最小预览 UI | 不接检索、不做历史补全 | 内部 20~30 个任务试用，能看懂改了什么 |
| MVP-3 | 聊天接入（仅 rag 模式）+ 用户级灰度 + 护栏 | 不做画像消歧、不做 doc topics 偏置 | 护栏不降；可一键回滚 |
| V1 | 第二学科、审核后台、doc topic ID、画像消歧 | — | 运营闭环跑通 |

### 2.3 依赖变化

- **校验器**从“可选”提升为 MVP-0 必做。
- **审核后台**从 B2/F4 后置到 V1；MVP 用 CSV + 校验器 + 代码评审。
- **金标**从 N5 后置提升到 MVP-1，先于任何 UI。
- **聊天接入**从 M3 保持不变，但只开 rag 模式，避免影响 agent/hybrid。

## 3. 需要先验证的 6 个假设

| 假设 | 怎么验证 | 不成立时怎么办 |
|---|---|---|
| H1：标准词替换能提升检索指标 | 同一批金标问题，基线 vs 规范化，配对比较 Recall@k/MRR | 若提升 < 3%，放弃查询侧，转做分块/精排 |
| H2：用户愿意用“查看/调整检索词” | 预览打开率、逐词修改率、撤销率 | 若打开率 < 10%，改为默认自动 + 事后标签 |
| H3：匹配器在真实规模下够快 | 1k/5k/10k 别名基准，P50/P95/P99 | 不达标则引入 C 扩展或缩小词表 |
| H4：规范化不会引入重复召回 | 金标中统计同来源重复片段、MMR 后 top_k 多样性 | 若重复上升，调整去重/MMR 或限制替换数 |
| H5：metadata 映射不需要重嵌入 | 在测试库上批量更新 topics→topic_ids，测耗时与一致性 | 若成本高，改为查询时映射，不写回 |
| H6：当前 per-source topics 能代表文档 | 20 篇长文档抽查章节覆盖率 | 覆盖率低则不接偏置，先改抽标签粒度 |

> 这 6 条假设比“再做 10 个功能”更重要。任何一条不成立，都应该调整方案，而不是继续堆代码。

## 4. 报告结构调整建议（可直接照做）

### 4.1 建议的新目录

```text
0. 一页纸：结论、3 个待拍板决策、MVP 范围
1. 现状：代码事实（两套词表、偏置、改写）
2. 目标与非目标（含“本版不做什么”）
3. 成功标准与实验设计（基线、指标、回滚）
4. 方案
   4.1 受控词表（字段/治理/冷启动）
   4.2 匹配器（最长匹配/反例/歧义）
   4.3 交互（默认校准 + 歧义确认 + 撤销）
   4.4 接口与数据流（enhance/query_plan）
5. 任务分解（MVP-0~3 / V1 / RACI / 里程碑）
6. 风险、成本、隐私
附录 A：schema 与 API 示例
附录 B：CSV 模板
附录 C：代码位置索引
```

### 4.2 具体合并/移动

- 把当前第 0.3 节的任务总表保留在前，但只留 **MVP 相关任务**；B2/F4/B8 移到 V1 表。
- 把第 3、4、5 节的实现细节压缩 30%，schema/JSON 示例移到附录。
- 第 9 节“验收指标”拆成“离线实验”和“在线护栏”，不要混在一起。
- 新增“成本与隐私”：点击路径 0 LLM、金标标注人力、日志脱敏与保留期。
- 新增“回滚预案”：按学科关闭、按用户关闭、保留原文路径。
- 新增“术语表”：受控词表、标准词、别名、反例、规范化、改写、路由，避免评审时各说各话。

| 位置 | 原文 | 建议改为 |

## 5. 不建议修改的部分

以下内容不要为了“简化”而删掉，它们是报告的价值所在：

1. **数据驱动词表 + 匹配器**：这是整个方案的地基，不能退回 if-else/lambda。
2. **检索文本与展示文本分离**：`enhanced` 只给检索，原文给展示/历史/画像。
3. **反例与歧义处理**：没有反例的词表一定误伤；歧义必须显式。
4. **词表版本 + 缓存 key**：不做会出现“同问题不同结果”。
5. **非代码任务清单**：这是给总负责人分派的抓手，格式可以压缩，内容不能省。
6. **不做主题硬过滤**：v1 保持软偏置，避免抽错标签直接漏召回。

## 6. 建议的决策顺序（给总负责人）

1. **先拍板范围**：是否接受“1 个学科、30~50 词”的 MVP？如果不接受，词表质量无法保证。
2. **再拍板交互**：是否接受“高置信默认生效、歧义才确认”？如果坚持每题逐词确认，需要接受更低的点击率。
3. **再拍板验证**：是否接受“金标先于 UI、聊天接入最后”？如果不接受，上线后无法归因。
4. **最后拍板运营**：词表由谁签字、多久发一版、谁有权回滚。

这四件事定下来，B/F 任务才有意义；否则代码人员会先做后台，非代码人员会先收一堆无法验收的词。

---

## 7. 结论

这份报告的技术判断基本成立，但**执行版本应该更小、更晚接检索、更早做验证**。最值得改的三件事：

1. **范围减半再减半**：1 个学科、30~50 词、100~150 条金标。
2. **交互减负**：高置信默认生效，歧义才确认；按钮用于查看/调整，不是每次必经。
3. **指标落到实验**：基线、配对比较、置信区间、回滚门槛；接受率只做 UX 指标，不做质量指标。

如果只改一件事，建议先改第 1 件——因为词表质量是非代码人员的工作，范围一大，后面所有代码任务都会被“等词表”拖住。
