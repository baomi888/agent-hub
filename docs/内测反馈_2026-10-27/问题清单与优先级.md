## 二、问题详述（含代码证据）

### P0-1 · 备考计划只能生成一次，生成后锁死

**用户视角**：设了 46 天，想改成别的天数 → 页面上没有任何入口。想放弃这个计划 → 同样没有入口。

**代码证据**

| 位置 | 现状 |
|---|---|
| `api/cet.py` | 只有 `POST /plan`，**没有 DELETE / PATCH** —— 接口层面就没有"取消"这个动作 |
| `service/cet.py:105 create_plan` | 只 `INSERT INTO cet_plans` + `INSERT INTO cet_tasks`，**不删旧计划** |
| `frontend/src/app/cet/page.tsx:332` | `!plan ? 生成表单 : 任务列表` —— 有计划时，生成入口整个消失 |

**两个后果**

1. 功能缺失：改不了、退不出。
2. **潜在脏数据**：`create_plan` 不去重。用户若能重复调用（或前端将来加重建入口），
   每调一次就多写 `days × 5` 条 `cet_tasks`（46 天 = 230 条），
   旧任务永远留在库里，`_latest_plan` 只取最新那份，旧的全成垃圾。
   目前没暴露，是因为前端把入口藏了 —— **这是"藏起来"而不是"解决了"**。

**修复范围**

- 后端：`DELETE /api/cet/plan`（取消当前计划）
- 后端：`create_plan` 增加"已有计划先退役"的语义，避免重复生成堆垃圾数据
- 前端：计划卡右上角「计划设置」→ 展开面板（天数 / 考试日 / 重新生成 / 取消计划）
- 前端：取消与重建都要二次确认

**★ 一个必须先想清楚的连带影响（核实代码后发现的）**

"取消计划"不只是这一页的事，它还牵着另外两处数据：

| 依赖位置 | 现状 | 硬删计划的后果 |
|---|---|---|
| `service/cet.py:151 _streak_days` | 连续天数 = `cet_tasks` 里 `done=1` 的日期集合 | **连续天数立刻归零** |
| `service/path.py:223/236` | 学习路径的关卡要数 `cet_plans` 和 `cet_tasks` | **相关关卡会倒退**（"生成备考计划"那一关从已过变回未过） |

也就是说：用户点一下"取消计划"，会发现连续学习天数清零、学习路径掉关。
如果没提前告知，这会被当成新 bug 报上来。

**两个方案对比**

| | 方案 A：硬删（DELETE 真删行） | **方案 B：归档（推荐）** |
|---|---|---|
| 做法 | `DELETE FROM cet_tasks WHERE plan_id=?` + `DELETE FROM cet_plans` | `cet_plans` 加 `archived_at INTEGER NULL`，取消 = 打时间戳；`_latest_plan` 加 `WHERE archived_at IS NULL` |
| 连续天数 | 归零 | **保留**（用户没白学） |
| 学习路径关卡 | 倒退 | **不回退** |
| 改天数 | 只能重建，进度全丢 | 旧计划归档、新计划生效，历史仍在库里可查 |
| 数据卫生 | 干净 | 旧数据留在库里，但有 `archived_at` 标记，不是垃圾 |
| 迁移成本 | 0 | 一次幂等 `ALTER TABLE`（照 `delegations` 加 `last_error` 的现成写法） |
| 可恢复性 | 不可恢复 | 数据在，将来想加"查看历史计划"随时能加 |

**推荐 B**。理由：用户按"取消"的真实意图是"我不想再看到这个计划了 / 我想换一个"，
而不是"请把我学过的记录全部抹掉"。B 既满足前者，又不产生用户没预期的副作用。
A 的唯一优势是省 20 行迁移代码，但代价是每次取消都要弹一个吓人的警告。

**工作量**：约半天（B 方案含一次幂等迁移）。
**验收**：取消后 `overview.plan` 为 null、页面回到空状态、**连续天数不变**、
`/path` 关卡不倒退；再生成一份新计划后 `overview.plan.total_days` 为新值，
且旧任务行仍在库里（`archived_at` 非空）。

### P0-2 · `/flow` 工作流页把内部架构摊给普通用户

**用户视角**：侧边栏点「工作流」，看到一堆 32 位 UUID、「任务 43df5e571038」、
「看日志」、可编辑的 JSON 定义、`requires_agent` / `goal_satisfied` 这种内部信号。
用户的评价是「这个为啥要给用户看」「不能让你们开这些」。

**代码证据**

| 位置 | 现状 |
|---|---|
| `ConsoleShell.tsx:48` | `{ key: "flow", href: "/flow", label: "工作流" }` —— **对所有人可见，无 adminOnly** |
| `frontend/src/app/flow/page.tsx:233` | 直接暴露 `<details>定义（N 个节点）</details>` 可编辑 JSON |
| 运行记录 tab | 展示完整 uuid + 任务 id + 日志入口 |

这页本质是**开发者调试面**（它自己的注释写的是「混合架构管理面」），
和 `/dashboard` 同一性质，但 `/dashboard` 已经做了 adminOnly + 404 隐藏，`/flow` 漏了。

**三个方案对比**

| 方案 | 改动量 | 内测用户 | 你自己 | 评委演示 |
|---|---|---|---|---|
| A. 删掉导航入口（路由保留） | 1 行 | 看不到 | 只能手敲 URL | 看不到 |
| **B. 加 `adminOnly`（推荐）** | 3 行 | 看不到 | 正常用 | 能看到（你登录管理员） |
| C. 改造成产品化界面（"我的自动化"） | 2–3 天 | 看得懂 | 正常用 | 能看到 |

**推荐 B**：与 `/dashboard` 完全一致的机制，复用已有的 `adminOnly` 过滤逻辑
（`ConsoleShell.tsx:116`），改造成本最低、可逆、评委演示时你仍能打开。

C 方案（把它变成用户能懂的「我的自动化」）是真正的长期解，但不是内测前该做的事。

**工作量**：10 分钟。**验收**：普通用户侧边栏无「工作流」；
手动敲 `/flow` 应走 404（与 `/dashboard` 一致，需要同时改后端 `/api/hybrid/*` 的 403→404 才叫真隐藏，见 §五）。

### P1-2 · 没有新手引导，新用户靠瞎点

**用户原话**：「因为我的太多东西需要图片了」「不然感觉在乱摸索」「我还没写使用说明」。

**注意这里有个误解值得先澄清**：他把"缺少引导"和"需要视觉大模型"绑在一起了，
但**引导的第一层根本不需要视觉模型**——先把"这个页面是干什么的、第一步点什么"写清楚，
用纯文字就能解决 80% 的"乱摸索"。

**分层方案**

| 层 | 内容 | 依赖视觉模型 | 工作量 |
|---|---|---|---|
| L1 空状态引导 | 每个页面的空状态写清"这是干什么的 + 第一步做什么"（部分页面已有，如 /cet 的空状态；/path、/flow 需补） | ❌ 不需要 | 2 小时 |
| L2 首次进入提示 | 首页首次登录时一行横幅：「先选学习方向 → 建知识库 → 开始提问」，可关闭 | ❌ 不需要 | 2 小时 |
| L3 截图式教程 | 带真实界面截图的步骤引导 | ✅ 需要 | 等视觉模型 |

**建议先做 L1 + L2**，L3 与视觉模型一起做。

## 四、「到底有没有好好测评」这条怎么回

这不是技术任务，但**必须正视**：用户点出的两条（计划取消、技术页暴露）
都是"打开页面 30 秒内就能发现"的问题。根因是我们之前只跑了
"接口能不能通 / 断言是不是绿"，没跑"一个没用过的人能不能走通"。

**可落地的对策**（不是喊口号）：
1. 每改完一条，补一条**真浏览器探针**断言（已有这套基建：`.workbuddy/pp/*.js`）
2. 新增一条硬规矩：**任何页面改动，必须用普通用户账号（非管理员）走一遍完整流程**，
   而不是只测管理员视角 —— 这次 `/flow` 漏掉，正是因为一直用管理员账号测
3. 把"用户能不能在 30 秒内看出这页是干什么的"写成验收项，和"接口 200"同等权重

```
第一次来？三步就能用起来                                知道了
① 选个学习方向       ② 建一个知识库        ③ 在下面问一句
  在模板广场勾几个标签   把课件、PDF 传进去   不用会写提示词
```

- 三步**都能点**：① 跳 /templates ② 打开右侧资料库面板 ③ 聚焦输入框

**三个实现要点（都是踩过坑才这么写的）**

1. **用 `useSyncExternalStore` 而不是 `useEffect` + `setState`**：
   服务端没有 localStorage，`getServerSnapshot` 固定返回 true（隐藏）才不水合报错；
   而且本项目 eslint 开了 `react-hooks/set-state-in-effect`，effect 里同步 setState 直接 error。
2. **第 2 步要用"打开"不能用"切换"**：宽视口（≥1280）资料库面板本来就常驻，
   传 `onToggleKbPanel` 会让用户点「建一个知识库」时面板反而收起来。
   探针第一次就是被这个真实缺陷打红（`true -> false`）。
3. **挂在欢迎页内部**：开始对话后它随空态一起消失。挂到三栏之外就等于常驻公告条，
   对已经会用的人是纯噪音。

## 八、二轮反馈（2026-10-28）

新的两条，都来自林宝宝。第一条是使用中的新诉求，第二条是 10-27 那批之后**又发现**的
功能缺陷（他自己先发现，我们没测出来）。

### 8.1 看板只能改状态，不能回话

**用户原话**：「这个用户反馈这里我只能选这三个按钮，不能给用户发消息吗，就是给对应的用户，
虽然我看不到他的信息」

**现状**：`PATCH /api/admin/feedback/{fid}` 只能把状态从「待处理」推到「处理中 / 已处理 / 不处理」，
没有任何回话的通道。

**★ 关键设计判断：光加输入框没用，得让用户真能看到。**
用户侧的「设置 → 我提过的」列表（`FeedbackCard` + `GET /api/user-feedback/mine`）本来就有，
所以回复存到 `user_feedback` 行上、由那份列表读出来 —— **不需要用户留联系方式**，
这也是对「虽然我看不到他的信息」的正确回答：站内回复本来就不需要看到他是谁。

**改动**

| 层 | 内容 |
|---|---|
| 表 | `user_feedback` 加 `reply TEXT NOT NULL DEFAULT ''`、`replied_at INTEGER`，幂等 `ALTER`（建表语句**不改**，理由同前） |
| 服务 | `set_reply(fid, text)` + `get(fid)`；`_EXTRA_COLUMNS` 驱动迁移 |
| 接口 | `POST /api/admin/feedback/{fid}/reply`（与 PATCH 分开，见下） |
| 用户侧 | 回复渲染在「我提过的」每条下面（`.fb-reply`，金线 + 淡金底，像纸边批注） |

**两个实现取舍**

1. **为什么不并进 PATCH**：PATCH 的契约是"改属性 + 状态流转表 + 409"，回复是另一件事，
   还带"顺手把 open 推到 doing"的副作用。混在一起，将来想加"谁回的、改过几次"的审计就无处落脚。
2. **回复不走 `_TRANSITIONS` 校验**：拿流转表去卡回复，会得到「已处理 → 已处理」这种无意义 409，
   管理员就再也回不了已经关掉的反馈 —— 而那恰恰是最该回一句"这个不做，原因是…"的一类。
   所以规则是：`open` 时顺手推到 `doing`，其它状态原样不动。

**验收**：`tests/test_feedback_reply.py` 7 条（含"老库补列"与"不许把 done 改回 doing"两条负向）、
`.workbuddy/pp/feedback_reply_probe.js` **12/12**（普通用户提单 → 管理员回复 →
换回普通用户真的读到）。探针里踩到一个坑：同一 browser 的多个 page **共享 cookie**，
管理员一登录就把普通用户顶掉，必须用两个独立 `browserContext`。

### 8.2 单词卡：复习队列把用户卡死了

**用户原话**：「我点击不认识复习」「我去不了下一个单词」「必须全部都是认识才能走」「但是点了认识就重来了」

**★ 根因（比反馈更严重）**：`frontend/public/tools.html` 里池子是
`const pool = wWrong.length ? wWrong : WORDS`，于是

1. 点第一张「不认识」→ `wWrong=[abandon]` → 池子立刻变成"只有这一张"，
   **剩下 15 个词用户再也看不到**。这就是"必须全部都是认识才能走"的真相：
   不是他不想走，是池子里只剩他刚说不认识的那张。
2. 复习轮走完一遍时 `wIdx` 归零但 `wWrong` 不清空 → 无限重来同一批。
3. 复习轮里把 `wWrong` 清空后池子瞬间切回 `WORDS`、而 `wIdx` 停在中途
   → 表现为"点了认识就重来了"。

**修法**：**池子只在一轮开始时确定，轮内绝不改动**。
一轮 = 把这批词从头走到尾；不认识的进下一轮的池子。
这样"能不能走完一轮"变成结构上必然的事，不依赖任何边界判断。
判断按钮的两个分支**都前进**，这是旧版最缺的一条。

顺带补齐（用户要的"整体优化"）：

- 轮次标签（第 N 轮 · x / 总数）+ 进度条 + 本轮统计（累计判断 / 认识 / 本轮还剩 / 待复习）
- 完成态："这一轮认完了 · 共 N 轮"，判断按钮禁用，按钮改名"再来一轮"
- 键盘：空格翻转、→ 认识、← 不认识（**只在单词卡可见时生效**，否则在别的工具里方向键会被抢）
- 词库 16 → 40 个（16 张一轮两分钟就完了）

**验收**：`.workbuddy/pp/wordcard_probe.js` **27/27**。
其中 6 条在注入旧行为后立刻变红（点不认识不前进 / 走不到第 2 轮 / ← 不前进 / …），
失败详情里能直接看到 `abandon` 原地不动 —— 和用户描述的现象一致。

  打开「校园工具集」会看到一片浅色。要修得整页补一套 dark 变量，不是本轮范围。

### 8.4 词库只有 40 个词（同一处功能的第二层）

**用户原话**：「然后这个单词卡就只有40个单词吗，这么少」

上一版（8.2）修的是「复习队列把用户卡死」，词库本身仍是 40 条内联常量。
40 条不是"少"，是**没有分组也没有下一天** —— 一轮两分钟就完了，之后无事可做。

**改法：词库外置 + 按级别分组**

| 项 | 之前 | 现在 |
|---|---|---|
| 词条 | 40（硬编码在 `tools.html`） | 6661（四级 4543 / 六级扩展 2118） |
| 来源 | 手写 | `KyleBing/english-vocabulary`（BSD-3-Clause，中英对照） |
| 组织 | 一个平铺数组 | 级别 × 每组 20 词（四级 228 组 / 六级 106 组） |
| 进度 | 无（刷新即清零） | `localStorage` 记住级别、练到第几组、哪几组已练完 |
| 加载 | 随页面 | `index.json` + 按级别懒加载（四级 214KB / 六级 103KB） |

**生成链** `tools/build_wordlist.py`（可复跑，不是一次性脚本）：下载上游 txt →
去掉音标列（上游有 2 行混进了音标字段）→ 同词多释义合并取最长 → 释义截断到 52 字
（断在分号/逗号处）→ 洗掉「意图， 意向」这类中文标点后多余空格 → 跨级别去重
（六级文件里 1873 个词四级已有，归四级）。

**两个判断**

1. **为什么不做「全量 4500 词一次性加载」**：一次发 4500 张卡没人练得完，
   也没有"今天该练哪些"的支点。分组 20 词对齐记忆科学的单次量，
   也和备考档案里「词汇 20 词」这个模块的量对得上。
2. **为什么六级显示 2118 而不是 5651**：六级大纲本身包含四级词汇，
   上游两份文件有 1873 个重叠。重叠词归四级，六级那档叫「六级扩展」——
   名字和数字必须自洽，否则用户会以为六级词库少了 3500 个。

**验收**

- `.workbuddy/pp/wordcard_probe.js` **44/44**（上一版 27 条 → 现在 44 条）。
  新增：级别切换（组数 228 → 106）、组切换、完成一组后出现「下一组」、
  **刷新后回到上次练到的那一组**、**词库请求全 404 时仍能出词并说明"没加载上"**（负向）。

- `tests/test_wordbank.py` **6 条**把词库契约钉住：清单与文件一一对应、
  数量/组数对得上、无跨级重复、释义不超长不含多余空格、许可证文件在。
  反证：把 `count` 改成 999 → 立刻红。
- 全量 pytest **582 项 0 失败**。

### 8.5 每个词配一句例句

8.4 把词库从 40 条扩到 6661 条，但卡背仍只有「n. 意图，意向，目的」。
用户接着提了一句「带例句吧」——**认得这个词长什么样，不等于会用**。
一个只有中文释义的卡片，练的是"英→中"的选择题，练不出语感。

**改法：翻面后，释义下面跟一条「批注」**

```
┌──────────────────────────────┐
│  intention                   │  ← 正面：只有词
└──────────────────────────────┘
            ↓ 点卡片
┌──────────────────────────────┐
│  intention                   │
│  n. 意图，意向，目的           │
│  ▎例句                        │  ← 批注：左金线 + 淡金底
│  ▎She had no intention of    │
│  ▎changing her mind...       │
│  ▎听完他的解释后，她无意改变… │
└──────────────────────────────┘
```

为什么做成「释义下面的一行批注」而不是第二张卡 / 第二个气泡：
卡片翻一次只该给**一层**新信息。释义和例句是同一件事的两种说法（一个解释、一个示范），
拆成两块会把视线从"理解这个词"引到"读两个框"。

**例句从哪来（6661 条全覆盖）**

| 来源 | 条数 | 说明 |
|---|---|---|
| 上游真题原句 | 1867 | `exam-data/CETVocabulary`（CC BY-NC-SA 4.0），真语料，优先级最高 |
| 上游模型句 | 2472 | 同上，非真题部分 |
| 我们补生成 | 2322 | 上游没有 / 上游那条是片段，用 DeepSeek 重写，过 `tools/gen_examples.py` 的 9 道校验 |

生成结果落在 `tools/word_examples_extra.json` 并**随仓库提交** —— 它不可复现
（模型每次写的不一样），重建词库时必须读它，否则这 2322 条会凭空消失。

**一个判据，救了 32% 的例句**

上游 `cet_full_list.json` 的「例句」字段里，约三分之一其实是**试卷片段**：
`lose faith`、`a bedroom carpet`、`rock the world`、`Abundant funds.` ——
后面补个句号就当例句显示，卡面写着「例句」，用户读到的不是句子。

试过三种判据，只有**句末标点**这条不误伤：

- 词数 < 5 当短语 → 砍掉 `You scared me.`（完整句，短句更好背）
- 首词是冠词当短语 → 砍掉 `The results support this hypothesis strongly.`
- 找助动词/动词表 → 砍掉 `She gave me a maternal smile.`（gave 没进表）

实测：无标点的 1799 条**全是**片段，有标点的 3479 条**全是**完整句。
边界干净得像是上游替我们标好的。判据写在 `tools/wordrules.py::is_sentence`，
生成侧和组装侧共用同一个函数 —— 两边各写一份，就会长出"生成时判不合格、入库时判合格"。

**顺手清掉的 13 条脏译文**

上游译文里有 13 条长这样：

```
她读了一首被命名为《苹果树》的诗( 她读了一首题为《苹果树》的诗)。
改变( 资金、材料等) 的用途, 转移 / 娱乐        ← 这条根本不是译文，是释义
```

正文后面用括号又补了一遍同义译法，还有两条直接把**释义**塞进了译文栏。
卡面上"例句"下面跟这么一行，比没有例句更糟 —— 用户在读"翻译"，读到的是排版垃圾。

逐条修（不是正则能盖的：括号里有时是更好的那句、有时是比喻解释，只能人看一眼取哪句），
修复表留在 `tools/build_wordlist.py::REPAIR_TRANSLATIONS`，重建词库时自动套用。

**验收**

- `.workbuddy/pp/wordcard_probe.js` **54/54**（8.4 时 44 条 → +10）。
  新增 6 条正向：例句块存在 / 带「例句」标签 / 句末有标点 / 有中文译文 /
  **渲染内容与词库数据逐字一致** / **句子里真的出现了这个单词**；
  2 条负向：**翻面前不许出现例句块**（`w-eg = 0`，否则等于提前看答案）、
  **兜底那 39 个词也得带例句**（词库挂了不能退回"只有词没有例句"的旧体验）。
- `tests/test_wordbank.py` **9 条**（6 → 9）：每个词都有例句（`with_examples == count`）、
  例句过关（复用 `wordrules.check_bank`）、译文里不许留括号补注 / 译文不许等于释义。
  词库条目形状从"必须二元组"改成"二元组或四元组"（3 元组、5 元组一律算坏）。
- 全量 pytest **585 项 0 失败**（+3）。

**两个判断**

1. **为什么不给每个词配 2~3 条例句**：卡片是"一次一个词"的闪卡，例句多了翻面就变成阅读页，
   判断按钮会被挤出视口。**一条**例句的作用是"证明这个词能这么用"，不是"教完这个词"。
2. **为什么兜底 39 词也要带例句**：兜底路径是**网络出问题时**的体验，
   恰恰最不该降级成"半成品"。词库 404 时用户看到的 39 个词，和正常时的卡长得一样。

**已知不足**：没有发音（要接 TTS，本轮没做）；例句只有一条，没有"换个语境再看一遍"；
`tools.html` 仍无深色主题。

### 9.1 首屏"打开就少了半屏"

**根因不是一个，是两个叠在一起**（只修任何一个都看不出来）：

| # | 问题 | 实测数字 |
|---|---|---|
| 1 | 空态被"新消息贴底"的副作用也滚到了底 | 1080×629 窗口，一进来 `scrollTop = 316` |
| 2 | 欢迎页本来就比可视区高一倍 | 内容 `616px`，可用 `340px`（629 − 顶栏 55 − 输入区 204） |

第 1 条的修法：`ChatArea` 里那段 `messages` 变化就 `scrollTop = scrollHeight` 的副作用，
对**空态直接跳过并回到顶部**。欢迎页没有"最新消息"要贴，贴底只会把标题推出视口。

第 2 条不能靠"少写点东西"解决 —— 616 → 340 要砍掉 45%。所以按**窗口高度分两档**：

| 档 | 触发 | 留下什么 | 让掉什么 |
|---|---|---|---|
| A | ≤919px 高 | 吉祥物 / 眉题 / 标题 / 副标题 / 三步引导 / 三张日更大卡 / 一行小胶囊 | 三句示例、「让知穗每天做点什么」小标题、页脚信任文案 |
| B | ≤720px 高 | 同上（字号与间距再收一档） | 再加：三步引导每步下面那半句"怎么做" |

断点不是拍脑袋定的：完整版 616 + 容器上下 40 = 656，加上顶栏与输入区 259，
**窗口要高过 915px 才可能一屏放全**。所以 919 这条线之下必须让东西。

**一个坑**：这两段 media query 一开始写在文件开头（跟着原来的 `max-height:800` 那一档），
结果量出来的高度**一个像素都没变** —— 同名基样式在文件后半部分，同特异性下后者胜。
CSS 分档规则必须放在基样式之后，这条已经写进 `welcome.css` 的注释里。

内容一旦高于容器，普通 `center` 会把上下两头都裁掉（顶部先没），
`safe` 让它在溢出时退化成 `flex-start`，至少保证吉祥物和标题永远在视线里。

## 十、四轮反馈（2026-10-28 16:00）

一条：**「给新用户再在初次进入我们这个平台的时候写一个有弹窗的使用说明，这个说明要比较清晰」**。

### 10.1 为什么已经有引导条，还要一个弹窗

首页那张「第一次来？三步就能用起来」是**动作入口**：三个能点的按钮（去模板广场 / 开资料库 / 聚焦输入框），
一屏只说三句，出现条件是"还没开始问"。它治不了第一次进来的人真正的问题：

- 知穗是谁、能干什么、和直接问 ChatGPT 有什么不一样；
- 资料放哪里、放了有什么用；
- 左边那排「每日委托 / 总结 / 打卡 / 学习路径」是干嘛的。

这些**必须一次讲完**，而且节奏要由用户自己控制（能停在第二页看、能退回去再看一遍）。
所以做的是一个四步弹窗，和引导条分工：**弹窗讲"这是什么"，引导条给"现在点哪个"。**

### 10.2 四步的切分方式

一步只答一个问题，每步配两条"要知道的坑"——说明弹窗最容易写成产品宣传页，读完还是不知道从哪下手。

| 步 | 标题 | 回答的问题 | 两条要点 |
|---|---|---|---|
| 1 | 知穗是个会自己动手的学习助手 | 它和普通对话有什么不一样 | 模式可手动切 / 引用能翻回原文 |
| 2 | 先把课件和 PDF 放进来 | 资料放哪、放了有什么用 | 支持格式 / 不传也能用但更泛 |
| 3 | 每天那几件事，可以交给它 | 左边那几页是干嘛的 | 委托失败会写明原因 / 12 关条件是真数据 |

文案里刻意写了两处"负面信息"：**「不传也能用，只是回答更泛」**、**「委托连续失败会自动停用并写明原因」**。
说明弹窗里只讲好话，用户第一次撞上失败时的落差会更大。

### 10.3 交互上的几个决定

- **点遮罩空白处不关。** 引导只弹一次，手抖点一下空白就再也看不到，代价太大。
  退出只有两个显式动作：「跳过」或 `Esc`。这两条都算"看过了"，之后不再自动弹。
- **`←` / `→` 能翻页**，`Tab` 锁在卡片内，`Esc` 退出。
- **底部一直显示「第 N 步 · 共 4 步」和「跳过也记住，下次不再自动弹」**——
  用户最怕的是"这玩意儿会不会天天弹"，这句话必须在弹之前就回答。
- **标记按人存**（`baomi.guide.v1.<uid>`）：同一台电脑换个人登录，新用户仍然看到说明，
  而不是继承上一个人的"已读"。
- **设置 → 账号 → 「再看一次上手说明」**：一次性不等于不可找回。走的是自定义事件
  （`lib/guide.ts` 的 `openGuide()`），因为弹窗挂在首页和控制台两处，按钮在第三处，
  提状态要穿好几层 prop，收益不成比例。

### 10.4 一个真实踩到的坑：焦点被输入框抢走

第一版只在弹窗打开时 `card.focus()` 一次。探针立刻红了：`activeElement` 是 **textarea**。
原因是首页输入框有自己的"挂载后自动聚焦"逻辑，它比弹窗晚一步跑，把焦点从卡片抢了回去。

后果不只是"焦点不对"：这时候按 `←` `→` 是在输入框里移光标，不是翻页；`Tab` 也会从输入框往页面里跳，
锁焦点那段判断等于没生效。

修法不是加 `setTimeout` 碰运气，而是**弹窗开着的时候守一层**：监听 `focusin`，
焦点一旦跑出卡片就立刻拉回来。这也是 modal 本来就该有的行为——遮罩挡着背景，键盘焦点不该在外面。

反证保留在探针里：`焦点落在弹窗内` 这条，把 `focusin` 守卫去掉就会红。

### 10.6 撤回一句不实的说明：现在读不了图片

弹窗第 2 步原来写的是「先把课件和 PDF 放进来」，要点第一条是
**「支持 PDF、Word、Markdown、纯文本」**。用户当场挑出来：

> 你要说明现在还读取不了图片呀，课件里面不一般就是有图片吗，应该说把资料放进那个地方。

**去核了一遍，文案里有两处不实**（`api/kb.py` 与 `kb/rag_core.py::load_document` 是唯一事实来源）：

| 文案说的 | 实际 | 后果 |
|---|---|---|
| 支持 Word | 只放行 `.txt` `.md` `.pdf`，Word 直接 400「不支持的文件格式」 | 用户拖 .docx 进去，第一次就撞墙 |
| 「先把课件放进来」 | PDF 走 `PyPDFLoader` 只抽**文字层**，图片/PPT/扫描件一律读不出，报「未提取到任何文字内容」 | 课件恰恰大半是图，等于教他一条走不通的路 |

两处叠加起来很糟：**说明弹窗本来是为了让人少撞墙，结果它自己在教一条走不通的路。**

改法（不是加一句免责，而是把这一步重写成"能读什么 / 读不了怎么办"）：

```
资料放进右侧「资料库」
右侧「资料库」→ 新建 → 把文件拖进去。之后问到相关内容，知穗会先翻你的资料再答，不是凭空编。
· 现在只读得了文字：TXT / Markdown / 文字版 PDF。图片、PPT、Word 还读不了
  —— 课件要先导出成文字，或另存成带文字层的 PDF
· 板书、教材截图这类图片不用入库：贴进输入框的「+」，视觉模型当场看；
  但它不进资料库，之后翻不回原文
· 一份都不放也能用，只是回答更泛，也没法翻回原文核对
```

三个判断：

1. **标题不再承诺"课件"**，改成「资料放进右侧『资料库』」—— 说的是**动作落在哪**，不是**什么东西读得了**。
   标题是最容易被只扫一眼的人记住的一行，不能让它替后端许诺。
2. **每条限制都跟一条出路**。只写"图片读不了"等于把人劝退；写清"导出成文字 / 另存带文字层 PDF"
   和"截图可以贴到输入框让视觉模型当场看"，才是可执行的。
   第二条同时也是**真的**：聊天附件走的是视觉模型（`ChatArea` 的 `accept="image/*"` 就是为此设的），
   只是它不入库、不可检索 —— 这层区别必须讲，否则用户会以为贴过的图能"被引用"。
3. **要点从 2 条变 3 条**。多的那条不是凑数，是"读不了图片"的替代方案；
   删掉它，第 1 条就只剩坏消息。

**这条限制该写在哪里**：只写在弹窗里不够 —— 真正的撞墙点在资料库面板。
核了一下 `KnowledgePanel.tsx` 的提示是「支持 TXT / Markdown / PDF」，**本来就是对的**，
错只在弹窗；所以这次只改弹窗，并加断言钉住，防止文案再飘回去。

**验收**：`guide_modal_probe.js` **40/40**（36 → +4）：

- 第 2 步标题里不许出现「课件」
- 第 2 步必须同时说明 TXT / Markdown / PDF

- **负向**：要点里出现 Word / PPT 时，同一句必须带否定或「导出 / 另存」的补救 ——
  否则就是又把人往坑里带（旧文案正是「支持 PDF、Word、Markdown」）

`tsc` 0、`eslint` 0、pytest **585 项 0 失败**。

**已知不足**：讲清了"读不了图片"，但没做 OCR / 视觉入库 —— 那是一条独立的功能线

## 十一、五轮反馈（2026-10-28 18:55）

一条：**「在主页也放一个提供反馈的按钮，点了和在设置那块提一样，给开发者看到」**。
顺带要求出一份今晚宣传用的图。

### 11.1 为什么不是加个链接跳去设置页

反馈的价值取决于**提的那一刻离现场有多近**。用户想提意见的时机是：
刚被答错、刚发现某个按钮按不动、刚发现少个功能——**他人正在对话里**。

把他送到另一个页面，中间要重新定位"我到底要说什么"，
再加上"跳过去还要找表单"这一步，多半就不提了。
所以做成**顶栏一颗胶囊 + 弹窗**，人在哪儿就在哪儿提。

### 11.2 两处入口共用一份代码

`FeedbackCard` 加了一个 `chrome` 参数（默认 `true`）：

| 用在哪 | chrome | 结果 |
|---|---|---|
| 设置 → 反馈 | `true`（默认，不用改） | 一张带标题栏的卡片 |
| 首页顶栏 → 弹窗 | `false` | 只有表单本身，外壳交给弹窗 |

这样分类按钮（来自后端 `/api/user-feedback/dict`）、字数下限、
提交、"我提过的"、开发者回复展示，**全部是同一份代码**。
如果复制一份到弹窗里，两边迟早会长歪——最典型的是"这边能提、那边看不到回复"，
而回复恰恰是用户判断"提了有没有人管"的唯一凭据。

### 11.3 交互上的四个决定

- **点遮罩不关**（和上手说明弹窗一致）。反馈是刚敲的一段话，误触空白就没了；
  关闭走右上角「关闭」或 `Esc`，都是显式动作。
- **打开时焦点给第一个分类按钮**，不是文本框：先确认"我要说的是哪一类"。
- **关掉后焦点回到那颗「反馈」按钮**。键盘用户不该被扔回页面顶部。
- **分类按钮的选项仍然来自后端**，不写死在前端——前端硬编码一份、后端校验另一份，
  加一个分类就要改两处，而这类不一致的表现是"按钮能点、提交 400"。

### 11.4 两个坑

**① 触发元素抓晚了。** 弹窗组件是常驻挂载的（`open=false` 时返回 `null`），
第一版把 `document.activeElement` 放在 `useState` 的惰性初始值里 —— 那是**组件挂载时**，
用户还没点按钮，抓到的是 `body`。结果就是关掉弹窗后焦点落在别处。
改成在 `open` 变化的 effect 里抓，那一刻 `activeElement` 仍是刚点的按钮。

**② `onClose` 必须是稳定引用。** `FeedbackModal` 的 Esc / 焦点 effect 依赖 `onClose`，
如果父组件每次渲染都传一个新箭头函数，effect 会反复重跑 ——
每次重跑都会"把焦点抢到第一个按钮"，用户在文本框里打字会被不断打断。
父组件里用 `useCallback` 包一层。

### 11.5 落地位置

顶栏右侧：「用量胶囊 · 能力 · **反馈** · 资料库开关」。
720px 以下只留图标（气泡 + 三个点），`aria-label` 仍是"提点意见"——
顶栏还要放用量和资料库开关，第三个带字的胶囊挤不下，实测 390px 宽时页面横向溢出为 0。
