## 1. 一句话结论

把「五档互斥模式」收成「一个入口 + 三类可组合手段」：**规则只判"这条是不是固定流程"，是就直接走工作流，不是就把"该检索 / 该调工具 / 直接答"交给模型判一次**。用户界面上只剩「自动 / 检索 / 纯对话」，智能体与混合不再作为选项暴露。

## 4. 目标决策流

```
进入 chat（mode 已过白名单）
│
├─ mode = rag   → 强制检索（用户明确要求，不判断）
├─ mode = llm   → 纯对话（用户明确要求，不判断）
├─ mode = agent → 智能体（内部/脚本/能力卡兼容入口，不判断）
├─ mode = hybrid→ 混合（内部/答辩演示入口，起跑按 classify_task）
│
└─ mode = auto（默认）
   │
   ├─ ① 规则快判：classify_task(question) == "flow"？
   │     关键词打分（先/然后/汇总/批量/整理成… vs 调研/分析/怎么…）
   │     是 → 以工作流起跑（hybrid 引擎，builtin_plan_execute）
   │            └ 工作流内部：plan(llm 节点) → execute(agent 节点)
   │               execute 里智能体自主决定调不调工具、调几次
   │               agent 段预算耗尽 → 回工作流收尾
   │
   └─ ② 否 → 模型判断（一次轻量调用，见 §5）
         ├ route=rag   → 检索路径
         ├ route=agent → 智能体路径
         └ route=llm   → 纯对话路径
```

**要点：flow 分支不问模型。** 规则能判的绝不多花一次往返，这与你说的"规则直接走工作流"一致。

## 5. 模型判断的契约

新增 `core/router.py`（放 core 而非 hybrid：它要在 rag / agent / llm 三个方向之间选，不属于混合引擎）。

```python
@dataclass(frozen=True)
class RouteDecision:
    route: Literal["rag", "agent", "llm"]
    source: Literal["rule", "model", "fallback"]
    reason: str        # 服务端日志用，不给前端

def decide(question: str, has_kb: bool, *, timeout: float = 2.0) -> RouteDecision
```

**输入**：问题原文、`has_kb`（只传布尔值，绝不传 `kb_id`——与既有安全边界一致）、可选一句"用户最近在做什么"（V1 不做，留字段）。

**输出**：严格 JSON `{"route": "rag|agent|llm", "reason": "≤20 字"}`，`temperature=0`、`max_tokens=48`。

**四条兜底**（任一触发即回落，不允许因路由器故障阻断主请求）：

| 情况 | 回落结果 |
|---|---|
| 超时（>2s） | `has_kb ? rag : agent` |
| 模型返回非枚举值 / 解析失败 | 同上 |
| `llm_gate` 抢不到闸（后台任务占满） | 同上，立即返回 |
| `has_kb=false` 却返回 `rag` | 改判 `agent` |

**system prompt 里的判断规则**（写给路由模型看，不是用户文案）：

```
1. 需要实时信息、计算、天气、下载文件 → agent
2. 问题指向"我的资料/这份笔记/我之前上传的"且 has_kb=true → rag
3. 寒暄、身份、常识、纯写作/翻译/润色 → llm
4. 判断不了时优先 agent（宁可多调一次工具，也不要凭空作答）
```

**成本**：约 60–150 token / 次，仅在非 flow 的 auto 请求上触发。按当前量级可忽略，但并发压测时要计入 `llm_gate` 压力（见 §8）。

## 6. 改造项

### P0-1　前端收档（3 项）

- `MODE_LABELS` 删「智能体」「混合」两项，文案保持白话。
- `usePrefs` 恢复时归一旧值 → `auto`。
- `ChatArea` 的 `willRetrieve` 降级为"可能检索"，避免把承诺写死。

**验收**：刷新带旧 `agent` 值的 localStorage，界面高亮「自动」且请求体 `mode=auto`。

### P0-2　能力卡改为「切回自动 + 预填问题」

四张卡（查资料/联网搜索/数学计算/查天气）当前点击会 `setMode("agent")`。改为 `setMode("auto")` 并预填示例问题。**否则"删按钮"只是表面功夫**——用户点一下卡片，等于又替你选了一次智能体。

保留 `setMode` 而不是"只填问题"的原因（2026-10-29 已定）：用户可能先把档位切到了「检索」或「纯对话」，点能力卡却不切回来，会出现"我点的是查天气，它去翻我的资料"的错配。切回「自动」等于把决定权交还给路由，与本次改造的语义一致。

**验收**：在「纯对话」档下点"查天气"，档位自动回到「自动」，请求 `mode=auto`，最终由路由判成 agent。

### P0-3　新增 `core/router.py` + 接入 auto

`_pick_mode` 改为：

```python
def _pick_mode(req_mode, question, kb_id, kb_exists):
    if req_mode == "hybrid":
        return "hybrid" if config.HYBRID_MODE_ENABLED else "agent"
    if req_mode in VALID_MODES and req_mode != "auto":
        return req_mode
    return router.decide(question, has_kb=bool(kb_id and kb_exists)).route_final
```

`route_final` 要能和现有分支名对齐：`rag`/`agent`/`llm`；`flow` 的结果由 `_pick_mode` 返回 `"hybrid"`（因为只有 hybrid 引擎能"工作流起跑"），与现有 §3.2 的入口合并。

**验收**：6 条样本问题各走对路径（见 §9）。

### P0-4　决策已记录、但不外显

`logger.info("route sid=%s route=%s source=%s reason=%s ...")`，同时把 `source` 计入 `core/apilog.py` 的既有请求日志范围之外（不加字段、不改表结构）。

**验收**：`grep route` 能看到每轮决策，前端 SSE 帧列表里**没有**新增事件（帧类型仍为 status/token/tool/done/error/hybrid_start…）。

### P1-1　补齐「大模型兜底」

现状：`terminate` 就是收工（`orchestrator.py:207-210`），没有独立兜底环节。agent 段预算耗尽 → 规则 `agent_budget_exhausted` 转工作流；工作流也没跑出东西时，用户拿到的是空或半截。

建议新增：hybrid 终态为 `stopped/failed` 且 `full_text` 为空时，用**已有上下文**（问题 + 压缩块 + 最近 K 轮）走一次纯 LLM 生成，作为最后兜底，并在答案前标注"未能完成完整流程，以下是基于现有信息的回答"。

**这一步才真正对应你说的"最后大模型兜底"**，但它会多一次主模型调用，建议单独开关 `HYBRID_LLM_FALLBACK=1`。

### P2-1　路由模型可选配小模型

V1 直接用主模型（`get_llm`），`max_tokens=48` 成本已很低。若实测延迟不可接受，再引入 `ROUTER_MODEL` 环境变量指向小模型。**不在 V1 做**，避免"两个模型两套超时"的复杂度。
