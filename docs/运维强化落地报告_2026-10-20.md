## 三、HTTPS：两条路线与当前选择

| | 线路 A：域名 + Let's Encrypt | 线路 B：Cloudflare 隧道 |
|---|---|---|
| 流量 | 浏览器 → nginx:443（TLS 终结）→ 反代 `:3000` / `/api` → `:8000` | 浏览器 → CF 边缘 → 服务器 `cloudflared` **主动出站** → `:3000` |
| 前提 | 域名 + ICP 备案通过 + DNS 解析到本机 | 无需备案、不开 443、不动安全组 |
| 代价 | 需要备案等待 1~2 周 | 绕海外节点、国内偏慢；临时域名会变 |
| 结论 | **正路，备案通过后走** | 过渡备选 |

**备案进度**（截图已核对）：10-20 提交、初审通过，卡在"待提交管局"（域名注册未满 2 天），后续还有工信部短信核验 → 管局审核 → 公安联网备案（通过后 30 天内单独办）。

## 四、运维强化：4 组动作的判断与落地

| # | 原需求 | 判断 | 理由 |
|---|---|---|---|
| 1a | SSH 密钥化 + fail2ban | ✅ 采纳 | 纯加固，不影响业务 |
| 1b | 禁 root 登录 | ⚠️ **改做法** | 项目就在 `/root`、deploy 以 root 跑；直接禁会把自己锁在门外。改为「先建 sudo 用户 → 另开终端验证 → 再锁 root」，脚本内置守卫 |
| 1c | 防火墙收敛到 80/443/SSH | 🚫 **今天不能做** | 应用还跑在 **3000**，HTTPS 未上线。现在关 3000 = **立刻断服**。脚本加 `--after-https` 守卫：443 未监听即拒绝执行 |
| 1d | SSE 拆独立 HTTP/1.1 server block | ✅ 采纳（改实现） | 当前配置**根本没有开 http2**，"http2+SSE 故障"这个前提不成立。改用**独立 location**（HTTP/1.1 + `proxy_buffering off`）达到同等效果，且不必为此另签一张证书 |
| 2 | 安全头 + Gzip + timed 日志 | ✅ 采纳 | 纯配置层，零架构风险 |
| 3 | nohup → systemd（或 Docker Compose） | ✅ 采纳（选 systemd） | 2G 内存上 Compose 偏重；先拿自动重启 + journald 结构化日志，容器化以后再决定 |
| 4 | Prometheus + node_exporter + 3 告警 + 外部探测 | ✅ 采纳（有前提） | 2G 上 Prometheus 约 150–250MB，已 `mem_limit 256m` + `retention 15d`；**外部 uptime 需你自己的账号**（UptimeRobot / healthchecks.io），无法代注册 |

### 落地清单

| 目录 | 产物 | 说明 |
|---|---|---|
| `https/` | `setup-https.sh`、`agent-hub.conf.template`、`nginx-http-global.conf.template` | 安全头（HSTS/nosniff/frame/referrer）、gzip、timed 日志、SSE 独立 location（关缓冲、600s 超时）、`client_max_body_size 50m` |
| `systemd/` | 3 个 unit + `install-systemd.sh`（含 `--rollback`）+ `README.md` | uvicorn / next / worker 三个进程；unit **不配 EnvironmentFile**（应用自己 `load_dotenv`，避免 systemd 解析 `.env` 报错） |
| `hardening/` | `harden-server.sh` + `README.md` | 带三层守卫：`--after-https` 要 443 在听；`--lock-root` 要有非 root 的 sudo+key 用户；改 sshd 前备份 + `sshd -t`，失败回滚 |
| `monitoring/` | `docker-compose.yml`、`prometheus.yml`、`alerts.yml`、`probe-health.sh` + `README.md` | 3 条告警：组件挂 / 主机失联 / 磁盘 <10%；`probe-health.sh` 写 textfile 指标，**能抓到 worker 静默死亡** |

### ⚠️ 迁移 systemd 后的行为变更

`deploy.sh start/restart` 与 systemd **会抢同一批端口**。迁移后日常一律用 `systemctl`，
不要再跑 `deploy.sh start`。是否把 `deploy.sh` 第 7 段启动逻辑改成 `systemctl restart`，待确认（见 §七）。

## 六、Bug 修复：登录 Cookie 缺少 Secure（issue #14）

完整分析见 **`docs/修复说明_2026-10-20_登录Cookie缺少Secure.md`**，此处只留结论：

- **缺陷**：`core/auth.py::set_session_cookie` 的注释写「Secure 只在 https 下加」，但函数不接收 `request`、`kwargs` 里也没有 `secure` → **Secure 永远不生效**。
- **为什么以前没炸**：全程 http 调试，Secure 本就不该出现；且没有任何测试断言过 `Set-Cookie` 内容。
- **为什么现在必须修**：正是 HTTPS 上线的必经路径——切过去就会暴露（登录态丢失 / 反复登录）。
- **修法关键**：判定**优先读 `X-Forwarded-Proto`**。因为 `deploy.sh:307` 启动 uvicorn **没开 `--proxy-headers`**，反代场景下 `request.url.scheme` 仍是 `http`，只判 scheme 等于没修。
- **验证**：新增 8 条测试，`8 passed`；全量 **237 passed**（基线 229，零回归）。
