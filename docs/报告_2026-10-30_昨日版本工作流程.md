### 4.2 入口分流 `_pick_mode`（旧版唯一的路由层）

代码（`api/chat.py:310-323`，逐字）：

```python
VALID_MODES = ("auto", "rag", "agent", "llm")

def _pick_mode(req_mode: str, kb_id: str | None, kb_exists: bool) -> str:
    """auto → rag / agent 自动路由；hybrid 不受知识库影响，只认功能开关；"""
    if req_mode == "hybrid":
        return "hybrid" if config.HYBRID_MODE_ENABLED else "agent"
    if req_mode in VALID_MODES and req_mode != "auto":
        return req_mode
    if kb_id and kb_exists:
        return "rag"
    return "agent"
```

| 用户选的档位 | 实际执行 | 说明 |
|---|---|---|
| 混合 hybrid | `hybrid`（引擎开关关闭则退回 `agent`） | 工作流×智能体换手，用户手动进 |
| 检索 rag | `rag`（库不存在时在 `api/chat.py:742-744` 降级 `agent`） | 强制检索 |
| 智能体 agent | `agent` | 强制工具循环 |
| 纯对话 llm | `llm` | 不检索、不调工具 |
| **自动 auto** | **绑库且库非空 → `rag`；否则 → `agent`** | **旧版 auto 只有两条路** |
| 脏值/未知值 | 走 auto 同一逻辑（白名单外一律 auto） | 不报错 |

**旧版的核心特征：`auto` 到不了 `llm`，也到不了 `hybrid`。** 想“纯聊天不检索”必须手动点「纯对话」；想用工作流必须手动点「混合」；绑了库的用户即使在「自动」下问“你好”，也会被拉去检索（`rag`），且没有任何模型判断参与。

7. **旧版取答案（有 bug，后来已修）**（旧版 `api/chat.py:1023-1030`）：
   - 若 `ctx.status in ("failed","timeout")` → 直接 `error` 帧「混合执行失败」；
   - `acc_text = full_text or shared.agent_result`；
   - 还没有就 `shared` 里**取最后一个写入的值**——`plan` 成功、`execute` 失败时，规划稿会被当答案；且因为 `acc_text` 非空，后续“兜底”永远不会触发（旧版本来也没有兜底）。
8. 收尾 `done.mode = "hybrid"`、`run_id` 有值。

#### 4.3.4 纯对话路径（`mode=llm`）

旧版 `api/chat.py:1250-1284`：发 `status`「纯 LLM 模式...」→ 取历史并组装 system（“友好、专业的 AI 助手”+场景）+ 压缩块 + 最近 K 轮 + 本轮问题 → `_stream_llm()` 流式回答 → `done.mode = "llm"`。不检索、不调工具、不走 agent。

#### 4.3.5 覆盖分支：图片理解（与 mode 正交，优先于所有路径）

## 5. 新版（三档 + 执行前路由，`0ecc803`）工作流程

### 5.1 界面只剩三档

`MODE_LABELS` = 自动/检索/纯对话（`frontend/src/components/chat/constants.tsx:11-15`）；能力卡全部 `auto`（`:117-152`）；旧偏好 `agent/hybrid` 在读偏好时归一为 `auto`（`frontend/src/lib/hooks/usePrefs.ts:27-28,55`）；引导文案同步为“检索 / 纯对话”（`GuideModal.tsx:54`）。后端 `ChatRequest.mode` 仍是字符串（`api/chat.py:280`），`VALID_MODES = ("auto","rag","agent","llm")`（`:315`），`hybrid` 在 `_pick_mode` 里单判——**旧值仍然可用**。

### 5.2 入口分流 `_pick_mode`（新版）

`api/chat.py:318-338`：

```python
async def _pick_mode(req_mode, question, kb_id, kb_exists) -> str:
    if req_mode == "hybrid":
        return "hybrid" if config.HYBRID_MODE_ENABLED else "agent"
    if req_mode in VALID_MODES and req_mode != "auto":
        return req_mode
    has_kb = bool(kb_id and kb_exists)
    decision = await route_engine.decide(question, has_kb=has_kb)
    if decision.route == "flow":
        return "hybrid" if config.HYBRID_MODE_ENABLED else "agent"
    return decision.route
```

（真实代码含注释与类型标注；此处为便于阅读的等价摘录，行号见上。）

| 请求 mode | 最终路径 | 说明 |
|---|---|---|
| `hybrid` | `hybrid` / `agent` | 内部/脚本/答辩演示入口；前端已无按钮 |
| `agent` | `agent` | 同上，前端已无按钮 |
| `rag` | `rag`（库不存在则降级 `agent`，`api/chat.py:820-822`） | 用明确要求，不再判断 |
| `llm` | `llm` | 用明确要求，不再判断 |
| **`auto`（默认）** | `hybrid`（flow）/ `rag` / `agent` / `llm` | **规则 + 模型**两级判断 |
| 脏值/未知值 | 同 `auto` | 不报 422，静默按 auto 路由 |

### 5.3 `core/router.py`：三层结构

**第一层：规则（高精度，宁可漏判；命中就不问模型）**

- 强特征 2 分：`第一步 / 第二步 / 第三步 / 依次 / 批量 / 并保存 / 并下载 / 然后 / 接着`（`core/router.py:46-56`）
- 中特征 1 分：`步骤 / 流程 / 汇总 / 生成报告 / 制成清单`（`:63`）
- 顺序配对：`先` 必须同时出现 `然后/接着/最后/再` 之一才 +2（`:68,97-98`）
- 开放减分：`调研/研究/分析/比较/怎么看/如何/为什么/哪些/建议/聊聊/介绍/解释/探索` 各 -1（`:71-85`）
- 判定：**总分 ≥ 2 且 > 开放分**才是 `flow`（`:90,103-109`）；否则 `open`，交给模型

**第二层：模型（只在非 flow 时调用一次）**

- system prompt（`core/router.py:114-124`）：三选一 `rag/agent/llm`，只输出一行 JSON `{"route":..., "reason":...}`；判断不了优先 `agent`；
- 调用：`temperature=0.0`、`max_tokens=ROUTER_MAX_TOKENS=48`；`asyncio.wait_for(..., timeout=ROUTER_TIMEOUT=2.0)`（`:180-195`）；
- **只传 `has_kb` 布尔值，绝不传 `kb_id`**（安全边界，路由模型没有机会指定查哪个库）。

**两条代码级硬约束**（`:168-177`，不依赖提示词自觉）：

```python
if route == "rag" and not has_kb:   → 改判 agent   # 没库要检索必然检索不到
if route == "llm" and has_kb:       → 改判 rag     # 绑库一律给引用（连"你好"也走检索）
```

**第三层：兜底（任何异常都不阻断主请求）**

- `ROUTER_ENABLED=0`、模型超时/异常、输出非 JSON、路由值非法 → 一律回落 `has_kb ? rag : agent`（`:146-148,204-230`）；
- 决策只写服务端日志 `route=... source=<rule|model|fallback> has_kb=... reason=...`（`:221-239`），**不下发前端**（沿用“判断结果不给用户看”的产品决定）。

**flow 的承载**：`flow` 只能由混合引擎承载，所以 `_pick_mode` 把 `flow` 翻译成 `hybrid`；`HYBRID_MODE_ENABLED=0` 时降级 `agent`（`api/chat.py:335-337`）。

### 5.4 路由之后的执行分支

与旧版完全相同的四条分支（注释头分别在 `api/chat.py:986 / 1160 / 1302 / 1373`，`if/elif` 在下一行），只有 hybrid 分支有两处新增：

1. **取答案不再靠“shared 最后一个值”**：
   - `hybrid/workflow.py:294-301`：成功的 `node_exit` 事件带上 `output_key`；
   - `api/chat.py:347-377`：`_HYBRID_NON_ANSWER_KEYS = {plan, history, score, retries, goal, question}` + `_pick_hybrid_answer(shared, last_ok_key)`，优先级 = **最后成功节点声明的 output_key → `agent_result` → 从后往前第一个非中间产物**；`node:*` 前缀同样排除；
   - 透给前端的 `workflow_node` 帧会剔除 `output_key`（内部键名不外泄，`api/chat.py:1079-1092`）；
2. **空产出时用 LLM 兜底**（P1，`api/chat.py:1117-1148`）：

   - 先发 `status`「流程未产出结果，改用直接作答...」，再用 `_plain_llm_messages()`（与 `llm` 模式共用同一份上下文拼装，`api/chat.py:774-795`）流式作答；
   - 兜底文本同样带 `truncated` 标记；

### 5.5 关键问题：工作流 / 智能体到底在谁手里？

| 决策 | 旧版（A） | 新版（B） | 模型能否参与 |
|---|---|---|---|
| **要不要走工作流** | 用户必须手选「混合」；进混合后规则 `classify_task` 判 flow/open | `auto` 下**规则** `classify_flow_open` 判 flow；是→工作流起跑，**不问模型** | **不能。** 模型只在“非 flow”时从 rag/agent/llm 三选一，代码里没有任何“选 workflow”的取值 |
| 工作流内部走哪些节点 | 内置 `plan → execute`；自定义流程需 API 传 `workflow_id`（前端无入口） | 同左（`workflow_id` 仍只对 hybrid 有意义；auto 判 flow 时用内置流程） | 不能，节点由定义决定 |
| **要不要走智能体（工具循环）** | 手选「智能体」，或旧版 auto 在**没绑库**时进入 | 模型判 `agent`（有库也可）；或 hybrid 起跑 open→agent；或切换规则把任务交给 agent | 模型可判 agent，但不选“哪个 agent/工作流” |
| **要不要检索** | 手选「检索」，或旧版 auto 在**绑库**时进入（强制） | 模型判 `rag`；绑库时模型判 `llm` 会被**代码强制改判 rag**；flow 分支不强制检索（已知缺口） | 部分：模型可判 rag，但绑库时“不检索”被硬约束拦掉 |
| 纯对话 | 只能手选 | 模型可判（无库场景） | 是（仅无库、非 flow） |
| 用不用工具/用哪个/用几次 | 模型在 ReAct 循环里自主 | 同左（`agent/`、`tool_guard` 两版没改） | **是**，但受常量与守卫封顶（见 §7） |
| 查哪个知识库 / 下载哪些 URL | 服务端注入 | 服务端注入 | **否**（安全边界） |

**结论（应写进答辩/说明的一段话）**：这套系统里“工作流”是**规则**选出来的，不是模型选出来的；模型只在“非流程型”的任务上决定“检索、用工具、还是直接答”。把工作流选择说成“完全交给 AI”是不准确的，准确说法是“**规则先判固定流程，模型只做剩下的三选一**”。

## 7. 工具决策归属表（两版完全相同）

先强调：`agent/builder.py`、`agent/tools.py`、`core/tool_guard.py`、`core/tool_registry.py` 在 `f55e439 → 0ecc803` 之间**没有任何改动**，所以下表对两版都成立。

| 决策 | 谁决定 | 机制/上限 | 证据 |
|---|---|---|---|
| 要不要进工具循环 | 路由（见 §5.5）/ 用户显式 agent | auto 下模型可判 agent；显式 agent 直通 | `api/chat.py:318-338` |
| 是否调用工具 | **模型** | ReAct：模型看 system prompt + 工具 schema 自主决定 | `agent/builder.py:25-46` |
| 用哪个工具 | **模型** | 5 个工具全量下发（全部 `defer=False`） | `agent/tools.py:656`、`core/tool_registry.py:28,105-143` |
| 调用几次 | **模型提出，常量封顶** | Agent 直连 `recursion_limit=10`（LLM 往返+工具都占步）；hybrid Agent 段 10 步 / 300s / 8000 token | `api/chat.py:1205`；`core/config.py:212-214`；`hybrid/agent_engine.py:137-184` |
| 工具参数 | **模型** | 参数 schema 由 `@tool` 定义；`kb_id` 不在参数里（服务端注入） | `agent/tools.py:47-61` |
| 失败后是否重试 | **守卫 + 模型**（守卫定死边界） | `retryable=False` 的工具（`kb_search`/`calculator`）确定性失败后**同一轮禁止再调**；模型看到的 schema 不变，守卫不告知模型 | `core/tool_guard.py:14-26,134-210`；`tool_registry.py:105-143` |
| 连续失败怎么办 | **常量** | hybrid Agent 段连续 3 次失败 → `agent_stuck`，该段终止 | `hybrid/agent_engine.py:35,242-251` |
| 危险动作（下载文件） | **守卫 + 审批常量** | `download_file` `needs_approval=True`：Agent 路径首次只返回确认串，模型带同一串再调才执行（参数变则 hash 变）；工作流 tool 节点没有交互位，**直接拒绝** | `tool_registry.py:134-142`；`tool_guard.py:96-101,161-179`；`hybrid/workflow.py:512-527` |
| 工具输出长度 | **常量（按工具分档）** | `kb_search/web_search=4000`、`get_weather=2000`、`calculator/download_file=1000` 字符；超限落盘+只回预览 | `tool_registry.py:105-143`；`tool_guard.py:113-128` |
| 查哪个知识库 | **服务端**（模型无权） | `kb_id` 走 `RunnableConfig.configurable` 注入；模型只能决定“查不查” | `api/chat.py:1204-1217`；`agent/tools.py:12-21,34-41` |
| 下载哪些 URL | **服务端白名单** | 只认本轮 `web_search` 返回的链接 ∪ 用户原话里的链接 | `api/chat.py:1210-1215`；`hybrid/agent_engine.py:150-153`；`hybrid/workflow.py:561-564` |
| 工作流内工具调用次数 | **常量** | `HYBRID_MAX_TOOL_CALLS=20`（单次运行） | `core/config.py:223`；`hybrid/workflow.py:531-545` |
| 工具说明书 | **system prompt + 工具 docstring** | 5 个工具全是 `defer=False` → 每轮全量下发 schema+description；`TOOL_PLAYBOOK`（四小节 SKILL 说明）只在延迟工具被 discover 时下发，**当前不参与** | `core/tool_registry.py:23-42,145-190` |

**要点**：

- “用不用工具/用哪个/用几次”的第一决策者是**模型**，但所有上限是**常量**，且守卫逻辑不暴露给模型（模型不知道自己被截断/封禁/要求审批，只会收到一条工具返回文本）；
- `download_file` 是唯一会改外部状态的工具，所以唯一带审批；工作流里的 tool 节点干脆拒绝，避免绕过审批；
- 两版都没有“根据问题自动决定工具列表”的机制——工具集是固定的 5 个（延迟工具机制存在但当前 5 个全部常驻）。

## 9. 疑点与待确认

### 9.1 解释歧义（最需要拍板的一条）

你说的是「删对话模式选择之前的版本」，仓库里有两个候选：

- 若指 **10-29 21:21 之前**的五档版 → 看 §4（`f55e439`）；

两版差异不是“小改”，**最核心的是 `auto` 从“两条固定规则”变成了“规则+模型两级路由”**（§6 有逐项表）。本报告没有猜死，两个都给了完整流程；你确认一个后，可以把另一节当背景资料。

### 9.2 文档与代码的漂移（读旧报告时要注意）

10-29 的三份文档（改造报告/修改报告/代码审查）结论大体成立，但以下 8 处与当前代码有出入或有遗留，**以代码为准**：

1. **行号漂移**：改造报告写 `api/chat.py:918-941`（混合起跑）、`:1321`（done 帧）等，是当时版本的行号；现在混合分支在 `:986`、done 在 `:1425`。旧版（`f55e439`）的对应行号是 `:908` / `:1315`。引用旧报告时不要按行号跳。
2. **`api/chat.py` 模块 docstring 说“三条路径”**，但正文实际列了 5 条后端分支（旧版 `:5-9` 也一样）。这是历史遗留措辞，不影响行为。

7. **`core/tool_guard.py` 的 docstring 示例写着“用法（api/chat.py 的 agent 路径）：with tool_guard.guard_scope()”**，但全仓只有 `tests/test_tool_guard.py` 使用 `guard_scope`，生产路径（`api/chat.py` 的 agent 分支与 hybrid 的 AgentEngine）都没有显式作用域；守卫状态靠 `contextvars` 在请求任务内首次调用时懒初始化。功能上可用（异步任务各自复制上下文），但“显式隔离”这层意图没有落到调用点，属于注释与实现不一致，改动这块时要小心。
