# 技术方案：关闭标签页后继续生成

日期：2026-11-23
状态：A 阶段代码已落地，验证记录见下方实施说明
目标：一次回答一旦开始，就不再依赖"那个标签页还开着"；关页、刷新、换端回来都能接着看。

## 2026-11-23 实施说明

以下记录对应当前代码，后续章节保留设计与评审过程。

- 后台任务由 `core/chat_runs.py` 持有，独立消费现有 LLM、RAG、Agent、hybrid、视觉路径的事件生成器。HTTP 连接负责订阅，断连释放自己的读取位置。
- 回放采用递增事件游标，`GET /api/chat/stream/{sid}?after=N&message_id=M` 返回后续事件。`meta` 标识消息，`replay_end` 区分历史与实时部分。错误消息 ID 返回 409，避免旧连接拼上新一轮回答。
- 回放日志最多在内存保留 `CHAT_RUN_BUFFER_BYTES` 字节，默认 512KB。超过阈值转入临时文件，保留文字、工具、引用等完整事件。消息正文仍通过 `_StreamDraft` 批量落库。数据库写入暂时失败时，未保存部分仍可从日志回放。该阈值限制额外回放缓存，模型路径原有的全文累积仍占用内存。
- 每个订阅者独立记录文件位置，读取与追加在事件循环中同步完成。慢连接不会堆积无界 Queue，也没有回放后才挂订阅的空隙。
- 单用户同时一个运行任务，预留发生在并发排队、扣费和消息插入之前。准备阶段也独立持有执行权，客户端消失后仍完成准备或释放预留。刷新遇到尚未建消息行的准备阶段时，前端轮询会话并接入后续流。
- 上游关闭与并发名额释放由后台任务收尾持有。`done` 在清理后发出，并带 `status`、`finish_reason`。停止与最终写入竞争时，以已成功提交的终态为准。取消中的线程写入先完成，再进行最终收尾，避免迟到的 streaming 写覆盖终态。
- `POST /api/chat/{sid}/stop` 显式停止。删除会话、删除正在生成的消息轮次、退出登录、应用正常退出均等待对应任务收尾。
- 配置项为 `CHAT_RUN_BUFFER_BYTES=524288`、`CHAT_RUN_HEARTBEAT_SECONDS=15`、`CHAT_RUN_TIMEOUT_SECONDS=600`、`CHAT_RUN_TERMINAL_TTL_SECONDS=60`。
- A 阶段要求一个 API worker。`deploy.sh` 与 `systemd/install-systemd.sh` 默认单 worker，并拒绝其他值。已有 systemd unit、手动启动命令需要同样使用单 worker。进程重启后消息按现有启动收割逻辑变为 interrupted。
- B 阶段需要另外设计执行权、任务交接、跨进程通知和失败恢复。独立执行进程可承受 API 重启，执行进程自身重启后的模型请求恢复仍需专门策略。

验证使用隔离数据库和假模型，不调用真实模型服务。具体命令记录于 `docs/superpowers/plans/2026-11-23-background-chat.md`。

## 0. 结论先行

现在生成跑在 **HTTP 请求的协程里**。浏览器一断，服务端在下一帧检测到 `is_disconnected`
就把上游关掉、把消息标成 `interrupted` —— 所以"后台继续"不是前端加个定时器能解决的，
必须把**生产**（调模型、写库）和**推送**（SSE 给客户端）拆开。

拆开之后：

- 生产归一个"任务"持有，直到 `done` / 用户停止 / 超时；
- 客户端只是订阅者，可断、可重连、可多端同时看；
- 关标签页 = 退订，不是取消。

涉及三块：后端 5 处、前端 6 处、**布局/交互 6 处需要配合**（第 6 节，最容易漏）。

## 1. 现状：一次回答的真实生命周期

以 `api/chat.py` 为准：

| 步骤 | 位置 | 行为 |
|---|---|---|
| ① 建壳 | `chat_stream` (1169) → `_StreamDraft` (802) | 先 `INSERT(content='', status='streaming')`，拿到 `msg_id` |
| ② 生成 | `_stream_llm` (1058) | `async for chunk in llm.astream(...)`，每个 delta `yield _sse("token")` |
| ③ 边流边存 | 同上 1111-1114 | 每累积 N 字 `draft.flush()` 写一次库（间隔 ≤4 秒） |
| ④ 断连 | 同上 1087 | 每 16 帧查一次 `request.is_disconnected()`；命中 → `acc.aborted = True` → `return` |
| ⑤ 收尾 | 1486 / 1745 / 2098 | `draft.seal(interrupted)`；正常结束走 `seal(done)` |
| ⑥ 重启收割 | `core/session.py:436` | 进程重启时把残留 `streaming` 统一改判 `interrupted` |

**关键点**：`yield` 在，协程就在；协程在，上游就在。`return` 之后 `aclosing` 会 `aclose` 上游 ——
模型调用当场结束。所以今天的"切到论坛不断"（上一批做的）只是因为**页面卸载但请求没取消**；
一旦关标签页，TCP 断了，④ 立刻命中。

## 2. 目标语义（先把规则写死，避免实现时各处理解不同）

1. **生成的所有权**：从第一帧开始归"任务"（run），不归请求。
2. **可订阅**：任意时刻可以连上来看；断线不产生副作用。
3. **取消只有三种**：用户点停止、同一会话发起新一轮、登出/删会话。
4. **必须有上限**：单用户并发 1、全局并发受 `llm_gate` 约束、单次生成硬超时（建议 10 分钟）。
   —— 用户明确要求"不要离开多久就停"，所以不设"空闲超时"，但硬超时必须留着兜底。
5. **进程重启**：第一阶段接受"中断"（已有收割逻辑），跨进程续跑放第二阶段。

## 3. 后端改造：5 处

### 3.1 生成任务化（`api/chat.py`）—— 核心

新增一个进程内注册表：

```python
class Run:                      # 一次生成
    sid: str
    message_id: int
    text: str                   # 已生成全文（同时是回放缓冲）
    state: "running" | "done" | "interrupted"
    subs: set[asyncio.Queue]    # 订阅者（每个 SSE 连接一个）
    task: asyncio.Task
    started_at: float
    last_flush: float
```

改造点：

- `_stream_llm` 从"生成器"变成 **producer 协程**：不再 `yield`，改成
  `run.emit(part)` —— 追加到 `run.text`、广播给所有 `subs`、按节奏 `draft.flush()`。
- 原来的 HTTP handler 变成 **consumer**：`async for frame in run.subscribe(offset=0)`，
  把帧写给客户端；客户端断开只是 `run.unsubscribe(q)`。
- ④ 的 `is_disconnected` 分支**删除**（或改为"只退订，不 abort"）。
- 收尾收敛到 producer 的 `finally`：`seal(done | interrupted)`，然后 `state` 落终态，
  广播一个 `done` 帧给还连着的订阅者。
- registry 里保留终态 N 秒（建议 60s），供"刚好在这时重连"的客户端拿到收尾信息。
- 内存上限：`run.text` 超过 512KB 时停止缓存（只留库里的），重连改用"读库 + 从库尾续"。

### 3.2 重连接口（`api/chat.py` 新增）

```
GET /api/chat/stream/{sid}          # SSE
  ?from=<offset>                    # 可选，默认 0（从头回放）
```

逻辑：

1. registry 有 `running` 的 run → 先回放 `text[from:]`，再挂到 `subs` 上继续 tail；
2. 有终态 run → 直接发 `done` 帧（含 `message_id`、`finish_reason`）；
3. 没有 run → `204`，前端退回"读 `/api/sessions/{sid}`"的静态渲染。

配套：首帧统一发 `meta {message_id, started_at}` —— 现在只有 `done` 帧带 `message_id`，
重连时就认不出"这条是不是我刚才那条"。

### 3.3 会话级互斥（`api/chat.py` + `core/session.py`）

同一 `sid` 已有 running 的 run → 新请求直接 `409`，body 带 `message_id`。
现在只有全局 `llm_gate`（并发闸），它防的是"打爆上游"，不是"同一会话两条回答交叉落库"。

### 3.4 心跳与运行期超时（`core/session.py` + `api/chat.py`）

- 每 15 秒往 SSE 写一行注释 `: ping`（nginx 默认 60s 空闲会断，长回答会被切）；
- 每个 run 记 `last_flush`；后台巡检（复用 `worker/scheduler.py` 的 tick）发现
  `now - last_flush > 120s` → 标 `interrupted` 并从 registry 摘掉；
- 启动收割已有（`session.py:436`），不动。

### 3.5 worker 要不要参与

| 方案 | 做法 | 代价 | 适用 |
|---|---|---|---|
| **A（推荐先做）** | 任务跑在 API 进程的 asyncio 里，worker 不参与 | 进程重启会中断（已有收割） | 单机部署、关标签页续跑 |
| B | 生产搬到 worker/独立进程，用表或队列传任务；API 只读 DB/缓冲 | 多一个进程、部署与调试复杂 | 要求"服务重启也不丢"时 |

先 A。B 只有在"服务器重启/发版也要接着跑"时才需要，届时 registry 换成 DB 表即可，
协议和前端都不用再改。

## 5. 前端改造：6 处

1. **`ChatProvider` 的 `sendMessage`**：请求断开不再 `abort`；把 `{sid, message_id}` 存起来。
2. **挂载/切回对话页**：`GET /api/sessions/{sid}` 里若有 `status=streaming` 且有 active run
   → 调 `GET /api/chat/stream/{sid}?from=<已显示长度>` 续看。
3. **`useSessions.toUi`（当前第 17-19 行）**：不再丢弃 `streaming` 行，转成"生成中"气泡。
4. **气泡三态**：`streaming`（光标 + 停止）/ `interrupted`（"已中断，继续生成"）/ `done`。
5. **打字机**：数据层全速累积；渲染层挂载时把"已显示长度"对齐到当前长度，只对新字做节奏播放
   （不能从头重播 —— 否则切回来像重新生成一遍）。
6. **停止**：新增 `POST /api/chat/{sid}/stop`，由服务端取消 run 并 `seal(interrupted)`。
   现在前端 `abortRef.abort()` 只是断自己的连接，服务端会当成"客户端走了"继续跑 ——
   语义反了，必须换。

## 6. 布局/交互要配合的地方（重点）

这一节是"整体布局会不会有没配合到"的答案：**有 6 处，不改就会出现"后台在跑但界面装作没有"**。

| 位置 | 现状 | 需要补 |
|---|---|---|
| 会话列表卡片 | 只有标题 + 时间（`session-kb` 可选） | 生成中的会话加一颗脉冲点（`.session[data-generating]`）；否则用户在论坛页完全不知道后台在跑 |
| 对话页顶部 | 无状态行 | 切回来先显示"正在生成…"，拿到首帧后转成正常流 |
| 输入区按钮 | `sending` / `playing` 决定 | 后台生成时你要能"停止"；`playing` 现在只反映本页打字机，需改成读 run 状态 |
| 会话切换 | 直接 `selectSession` | 切到另一个会话时，原会话的 run 仍在跑 —— 卡片上要有标记，否则会以为它停了 |
| 手机底部 tab / 抽屉 | 无状态 | 同上；另外移动端切后台可能被系统冻结定时器（见 §7） |
| 删除会话 | 直接删 | 有 running 的会话要先取消 run，否则任务继续写一个已删除的 message_id |

另外两处"看起来无关、其实会被问到"的：

- **配额展示**：额度是发送时扣的，后台继续不影响，但"停止"要不要退额要提前定（建议不退）。
- **通知**：done 时是否推一条（已有 push 通道）？不做也行，但列表脉冲必须有。

## 7. 失败模式与边界

| 情况 | 现在的表现 | 改造后 |
|---|---|---|
| 关标签页 | 上游被 aclose，半截落库为 interrupted | 继续跑完，done 落库 |
| 刷新 | 同上 | 重新订阅，从已显示位置续 |
| 手机切后台 | 定时器被冻结、SSE 可能断 | 服务端不受影响；回前台重连即可 |
| nginx 60s 空闲 | 长回答可能被切 | 15s 心跳注释行解决 |
| 进程重启 | streaming 全部改判 interrupted | 第一阶段仍是；第二阶段（worker 化）才解决 |
| 内存 | — | 单 run 缓冲上限 512KB，超出只留库 |
| 同会话并发 | 两条回答交叉落库 | 409 + 前端禁用输入框 |

| 阶段 | 内容 | 验收 |

## 9. 测试计划

**后端（pytest）**
- `disconnect` 后 producer 仍继续：mock 客户端断开 → 断言 `seal(done)` 且 `text` 完整。
- 重连回放：`?from=N` 只回放 `text[N:]`，不重复。
- 互斥：同 sid 第二次请求 409，且不新建 message 行。
- 超时巡检：`last_flush` 过期 → interrupted。

**前端（CDP 实测）**
- 发问 → 3 秒后关标签页 → 等 15 秒 → 重开同会话：气泡是 done 且内容完整。
- 发问 → 切到论坛 → 回对话：同一气泡续写，不新建。
- 发问 → 刷新：显示半截 + 生成中，随后补全。
- 断言列表卡片的 `data-generating` 在 running 时为 true、done 后消失。

## 10. 风险与待拍板

1. **成本**：后台继续 = 继续烧 token。用户要求"不停"，所以不加空闲超时，但要有硬超时（10 分钟）。
2. **`beforeunload` 不可靠**：不能靠它通知服务端"我走了"，只能靠 TCP 断开这一事实。
3. **多端语义**：第二台设备今天会跳过 `streaming` 行（`context_compress.py:852`）；
   改造后建议"只读跟随"——能看，但不能发（避免两条 run）。
4. **删除/登出**必须先取消 run，否则会往已删行里写。
5. **A→B 的迁移成本**：先做 A 不会白做 —— 协议、前端、布局都不变，B 只是把 registry 换成 DB 表。

## 11. 一句话总结

把"生成"从请求里拿出来，交给一个有名字、可订阅、可取消的任务；
后端改 5 处（核心是 `_stream_llm` 变 producer），前端改 6 处，
**布局必须补 6 处状态可见性**，否则用户会以为"它停了"，而实际上还在跑。
好问题。你这个方案我读下来，**架构考量的方向是对的，但有三处"看起来为扩展设计、其实埋了雷"的地方，恰恰在可维护/可扩展/可测试上会反噬**。我一条条拆，只讲真话，不吹。

## 一、producer/consumer 拆分：这是对的，而且恰好是"三原则"的教科书做法

**可测试性**是这里最漂亮的点。拆开之后，producer 不再依赖"有没有 HTTP 连接"这个外部状态，变成**一个纯协程**：

- 测试时不需要真的起一个 SSE 连接、不需要模拟浏览器断连；
- 直接调 producer，断言它把 token 写进了 `run.text`、写进了库、状态落对了；
- consumer 单独测，断言它从队列取帧、写 SSE、断开时正确退订。

一句话：**拆开前，"生成"和"网络"耦合，没法单独测；拆开后两者都能脱离对方测试。** 这就是方案第 9 节测试计划里"mock 客户端断开 → 断言 seal(done)"能成立的前提。

**可扩展**也对：将来要加"多端同时看"（手机电脑一起看同一个回答），加一个 consumer 订阅同一个 run 就行，producer 一行不用改。这正是拆分的红利。

---

## 二、最大的隐患：A→B 那句"registry 换成 DB 表即可，协议和前端都不用再改"

这句话**方向对，但严重低估了工作量，而且埋了一个可测试性的雷**。我把它当反面教材讲。

方案第 10 节第 5 条写："先做 A 不会白做——协议、前端、布局都不变，B 只是把 registry 换成 DB 表。"

**这话只说对了一半。** 协议和前端确实不变，但**"registry 换 DB 表"这个动作本身，比它字面上看起来重得多**，原因有三个：

### 1. 内存 registry 是"进程内单点"，换 DB 表会引入"多进程竞争同一份状态"

现在 A 方案是单进程（或 uvicorn 多 worker，但每个 worker 各自一份内存 registry）。一旦换 DB 表，马上要面对：

- **谁拥有这个 run？** 两个 worker 都可能看到"有个 run 在 running"，谁继续写？谁 seal？需要租约（lease）、锁、心跳续约。
- **订阅者怎么办？** DB 表存不了 `asyncio.Queue` 这种内存对象。跨进程之后，"广播 token 给订阅者"必须走 Redis Pub/Sub 或消息队列，而不是直接往内存 queue 里塞。

**这意味着 B 不是"换个存储"，而是"从共享内存模型换成分布式消息模型"**——这是两种架构。方案里用"只是把 registry 换成 DB 表"一笔带过，会让人严重低估 B 的成本。

### 2. 这违反了"单一职责"和"可替换抽象"的一个经典陷阱

A 方案里，run 的状态、缓冲、订阅者**三样东西塞在一个内存对象里**，没抽象出边界。等要换 DB 时，会发现这三样东西根本不该一起换：

- **状态**（running/done/interrupted）→ 该落库，进程无关；
- **缓冲**（run.text）→ 该落库或进消息队列；
- **订阅者**（subs）→ 是进程内概念，根本不能"换 DB 表"，必须走 Pub/Sub。

方案如果把这三者先拆清楚（比如定义一个 `RunStore` 接口，内存实现 + 将来 DB 实现），那才是真"可扩展"。现在混在一个 dict 里，A→B 迁移时得把这坨全拆开重写。

### 3. 可测试性：DB 表版本会引入"测试顺序依赖"

内存 registry 测试很简单：每个测试起一个新进程、新内存，天然隔离。一旦换 DB 表，测试就要面对：

- 测试之间共享 DB，得小心清理（你上一轮写 `test_forum_social.py` 就踩过这个坑——`_reset()` 没先 `_ensure` 就 `DELETE`，报了 `no such table`）；
- run 的租约、锁、超时这些**时间相关**逻辑，测试要用假时钟（freeze time）才能稳定复现。

这都不是"换 DB 表"三个字能覆盖的。

**我的建议**：方案里那句"只是把 registry 换成 DB 表"要么删掉，要么改成"B 需要把内存 registry 抽象成 `RunStore` 接口 + 订阅走消息队列，是独立的分布式改造，不是换个存储"。**现在这么写，会误导未来的自己低估 B。**

---

## 三、"进程内单进程"这个假设，本身也要先说清

A 方案成立有个隐含前提：**生成任务跑在哪个进程，重连请求就得打到哪个进程。**

但项目现在**已经是多 worker**（你之前的记忆里写了 `deploy.sh detect_workers`，`WORKERS` 环境变量，`LLM_MAX_CONCURRENCY 是每进程值`）。这意味着：

- 用户发请求 → 打到 worker 1 → run 在 worker 1 的内存里；
- 用户关标签页，10 秒后重连 → **可能被负载均衡打到 worker 2** → worker 2 的内存里**没有这个 run** → 重连失败，退化成"查库"。

这就是"sticky session（粘性会话）"问题。方案 A 里 registry 是进程内的，**要么要求重连必须打到同一个 worker（需要 nginx 配 sticky），要么重连逻辑里要能跨 worker 找 run（那又回到分布式问题）**。

方案里**完全没提这一条**。这在单 worker 部署下无所谓，但你已经是多 worker 了，这是 A 方案能不能成立的关键前提，漏了会直接导致"关标签页重连，发现答案没续上、而是从头查库"。

## 四、魔法数硬编码，违背可维护性（小但真实）

方案里出现了 `60s`（终态保留）、`512KB`（缓冲上限）、`15s`（心跳）、`120s`（超时巡检）、`10 分钟`（硬超时）。这些**全是硬编码**。

按照项目里已有的约定（你记忆里 `LLM_MAX_CONCURRENCY`、`RATE_LIMIT_SHARED` 这些都进 config），这些数字应该：

- 进 `config`（环境变量可调），而不是写死在代码里；
- 至少集中在一个常量区，方便将来调。

否则将来"60s 太短，用户回来慢就查库了"要改，得去代码里翻。这是小事，但**可维护性**恰恰体现在这种小事上——现在的方案是"方案文档"，落地时这些数字散落各处，就是"维护债"。

## 五、真正该补的架构动作（如果要把方案升级成"经得起推敲"）

如果按三原则去审视，我会建议方案补三样东西：

1. **先抽象 `RunStore` 接口**（内存实现），把"状态 + 缓冲 + 订阅"的边界划清楚。这比"一个 dict"多花半天，但换来 A→B 迁移时不用重写，且能对接口直接 mock 测试。

2. **把"多 worker 下 registry 的可见性"写进方案**——明确：P0 先假定 sticky session（或单 worker），并在文档里标注"多 worker 需 nginx sticky 或改走 Redis"。

3. **魔法数集中进 config**，给每个数一个语义名（`RUN_TERMINAL_TTL=60`、`RUN_BUFFER_LIMIT=512*1024`），而不是散在代码注释里。
