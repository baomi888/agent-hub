## 一、后端

### ★★★ 1. 【新增 · 最要紧】Agent 多轮记忆根本没落盘，静默退回内存版

`agent/builder.py:67-84`

```python
def _make_checkpointer():
    try:
        from langgraph.checkpoint.sqlite import SqliteSaver   # ← 这一行在本机是失败的
        ...
    except Exception:
        return MemorySaver()                                   # ← 于是每次都走这里
```

**实测**：`langgraph.checkpoint` 包下只有 `base / memory / serde` 三个子模块，**没有 `sqlite`**
（`ModuleNotFoundError: No module named 'langgraph.checkpoint.sqlite'`）。
证据是硬的：`data/agent_memory.sqlite` 这个文件**从来没被创建过**（`data/` 目录下不存在）。

后果三条，一条比一条实际：
1. 服务一重启，Agent 的多轮记忆全丢——而这个函数自己的 docstring 写的正是
   「MemorySaver 只在进程内有效：服务一重启 Agent 的多轮记忆就全没了」，**它精确地踩中了自己要防的坑**；
2. `MemorySaver` 是纯内存 dict，**永不淘汰**，每个会话的完整 Agent state 一直攒在内存里；
3. `except Exception` 把所有失败都吞了，**没有任何日志**，从外部完全看不出来。

改法：
```
pip install langgraph-checkpoint-sqlite     # PyPI 有 3.1.1，已 dry-run 确认可拉取
```
再把 `except Exception:` 换成 `logging.warning("SqliteSaver 不可用，Agent 记忆将不持久化：%s", e)`——
降级可以，但不能是静默的。

> **修正昨天的结论**：2026-09-29 报告第 3 项写「`_CHECKPOINTER` 用 SqliteSaver 落盘到 `data/agent_memory.sqlite`，
> 删会话不带清 thread」。这个前提是错的——落盘从来没发生过。
> 所以「删会话不清 checkpoint」目前是**假问题**（内存版随进程走）；
> 真正的优先级更高：**先让它落盘**，落盘之后清理才有意义。

### ★★★ 2. 【新增】重试只在前端截断，后端历史被重复提问污染

`frontend/src/app/page.tsx:296-307` + `api/chat.py:242`

前端 `retryMessage` 把旧的问答对从界面上抹掉，然后重发：
```js
setMessages(list.slice(0, start));   // 只动前端 state
void sendMessage(question);          // 后端照旧 add_message
```
而后端 `chat_stream` 第 242 行每次都 `store.add_message(req.sid, "user", req.question)`，**从不删旧的**。

后果：
- 重试 N 次，SQLite 里就躺着 **N+1 条重复的 user 消息 + N 条 assistant 回答**；
- `get_messages` 按 `MAX_HISTORY_TURNS=10` 取最近 10 轮，**重复提问会把真实历史挤出上下文窗口**，
  模型看到的是一串重复问题，回答质量随之下降；
- 刷新页面旧的问答又全部冒出来——前端显示的和后端存的对不上。

改法（后端已有现成零件，不用新写接口）：`core/session.py:249` 的 `find_turn_ids()` +
`api/sessions.py:80` 的 `DELETE /{sid}/messages/{msg_id}/` 已经能整轮删除。
`retryMessage` 里在 `sendMessage` 之前先 `await api.deleteMessageTurn(sid, 原 assistant 的 dbId)` 即可。
或者更省事：给 `/api/chat/stream` 加一个 `replace_from_msg_id` 字段，落库前先删那一段。

这是**用户重试两次就能感觉到**的 bug，优先级应该排在多数打磨项前面。

### ★★★ 3. 【新增】删会话留下 feedbacks 孤儿行

`core/session.py:157-163`

```python
def delete_conversation(sid):
    conn.execute("DELETE FROM messages WHERE conversation_id = ?", (sid,))
    cur = conn.execute("DELETE FROM conversations WHERE id = ?", (sid,))   # feedbacks 呢？
```

`feedbacks` 表（`session.py:76-83`）建表时**没写 FOREIGN KEY**，所以没有 `ON DELETE CASCADE` 兜底，
删会话后这些赞踩记录永久悬空。

对照一下就知道这是漏的而不是故意的：昨天加的 `delete_messages()`（`session.py:345`）
是**清了** feedbacks 的——只有「删整个会话」这条路没清。

改法：一行 `DELETE FROM feedbacks WHERE conversation_id = ?`；
讲究一点的话给 feedbacks 补上 FK 并在连接里开 `PRAGMA foreign_keys=ON`。

### ★★ 4. 【沿用 · 未修】三个 import 接口仍透传原始异常

`api/kb.py:372 / 382 / 397` 仍然是 `detail=str(e)`。
同文件其它接口用的是 `describe_api_error(e)`（脱敏成中文提示）。
三处替换，零风险。

### ★★ 5. 【沿用 · 未修，但有变化】`requirements.txt` 缺显式依赖

缺的仍是 `httpx`（`agent/tools.py:82`、`kb/importer.py:9`、`api/kb.py:403`）和 `requests`（`tests/test_w2.py`、`test_w3.py`）。

**今天的新发现**：`duckduckgo-search` 这个依赖已经**完全没人用了**
（全项目 grep 无 `duckduckgo / ddgs / DDGS`，工具早就换成 Serper）。
它现在唯一的实际作用就是**间接把 httpx 带进来**——也就是说 httpx 能跑纯属侥幸，
哪天这个包被摘掉，四个文件同时炸。

改法：`+ httpx`、`+ requests`、`- duckduckgo-search`，一次把侥幸变成显式。

### ★★ 6. 【沿用 · 未修】`/api/kb/download` 仍是开放 SSRF 代理

`api/kb.py:400-432`：任意 http(s) URL，无域名白名单、无大小上限，`resp.content` 整包读进内存。
改法：`Content-Length` 预检 + 改 `client.stream()` 边读边截断（如 50MB）。

### ★★ 7. 【沿用 · 未修】`/health` 是假探针

`main.py:76-79` 永远 `{"status":"ok"}`，不探测 embedding 也不探测 chroma 可写。
加一个 readyz，排障时值回票价。

### ★★ 8. 【新增】上传 / 重建的切片参数没有任何校验

`api/kb.py:45-47` 的 `chunk_size: int = 500, chunk_overlap: int = 50` 是裸 Form 字段，
直接喂给 `RecursiveCharacterTextSplitter`；`chunk_size=0` 或负数会在切片层炸成 500。
`api/kb.py:124` 的 `top_k: int = 3` 同样无下界。

对照：`api/chat.py:58` 的 `top_k` 写的是 `Field(default=..., gt=0)`——**同一个项目里已经有两种写法**，
照抄严格的那边就行，成本几行。

### ★ 9. 【新增】标题生成挡在 `done` 事件前面，白白多等 1~3 秒

`api/chat.py:454-461`：

```python
gen_title = await asyncio.to_thread(_generate_title, ...)   # 一次完整 LLM 调用
...
yield _sse("done", {...})                                    # 标题算完才发 done
```

答案明明已经流式结束了，前端还要等标题那次调用才收到 `done`：
气泡的 loading 态多停一两秒，赞踩按钮（`page.tsx:236` 的 done 里才拿得到 `message_id`）也跟着晚点亮。

改法：**把 `done` 提到标题之前 yield，`title` 单独后发**。
前端 `page.tsx:227` 已经有独立的 `case "title"`，不依赖 done 里带 title。
纯顺序调整，零风险，属于性价比极高的一类。

### ★ 10. 【沿用 · 未修】无鉴权、无限流

单机自用没问题；一旦放到局域网，任何人可删库删会话。
最低成本：一个 `X-API-Key` 中间件。

## 二、前端

### ★★★ 1. 【新增】后端发的进度提示，前端 100% 丢掉了

`api/chat.py` 一共 yield 了 **6 处** `event: status`：

| 行号 | 文案 |
|---|---|
| 250 | 图片理解模式，正在分析图片... |
| 312 | Agent 模式，正在规划任务... |
| 395 | RAG 模式，正在检索知识库（{kb_id}）... |
| 407 | 检索到 {n} 条片段 |
| 411 | 正在生成答案... |
| 429 | 纯 LLM 模式... |

而 `page.tsx:192-259` 的 switch 只有 `token / sources / tool / title / done / error` 六个 case，
**没有 `status`**（已 grep 确认全项目无 `case "status"`）——这些帧被解析出来后直接掉进 default 的虚空。

后果：Agent 模式动辄十几秒，界面除了打字光标**什么都没有**，
而后端其实一直在汇报"在检索 / 检索到几条 / 在生成"，全被丢进下水道。
这是"感觉慢"和"真的慢"之间最大的那块差距。

改法：加一个 `case "status"`，把文案挂到当前流式气泡的 `statusText` 上，
`Bubble.tsx` 在内容还为空时显示它（样式可以复用 `.stopped-tag` 那一档弱文字）。
半天工作量，等待体验立刻不一样。

### ★★ 2. 【新增】同上「后端第 2 项」——retry 要连后端一起删

前端改 `page.tsx:296` 的 `retryMessage`，在 `sendMessage` 前调一次 `api.deleteMessageTurn`。
单独列在这里是因为它跨前后端，两边改一处都不算完成。

### ★★ 3. 【新增】发送后 blob URL 没释放

`ChatArea.tsx:238` 在 `addFiles` 里 `URL.createObjectURL(f)`；
只有 `removeAttachment`（249 行）和 Esc 清空（796 行）会 `revokeObjectURL`。

而 `submit()`（294-312）只做了 `setPending([])`，**不释放**。
每发一张图就泄漏一个 blob URL，直到关页面才回收。

改法：`submit` 里补一句 `pending.forEach(a => URL.revokeObjectURL(a.url))`；
讲究点再在组件卸载时清一遍。

### ★★ 4. 【沿用 · 未修】会话搜索仍然只搜标题

`Sidebar.tsx:97` 只有 `c.title.toLowerCase().includes(q)`。
需要后端 `GET /api/sessions/search?q=`（SQLite LIKE 扫 messages.content）+ 前端接上。
会话一多，"上周问过的那个天气"就找不回来了。

### ★★ 5. 【沿用 · 未修】没有会话导出

全项目唯一的下载是 `KnowledgePanel.tsx:383` 那个知识库文件链接。
对"问完的每一句都能翻回原文"这个定位，导出是自然延伸，而且**纯前端拼 Markdown 就能做，不用动后端**。

### ★★ 6. 【新增】删掉正在使用的知识库后，会话仍绑着它

`useKnowledge.ts:84-92` 的 `deleteKb` 删完只 `refreshKbs()`，**不会解绑任何会话**。

后果链：会话的 `kb_id` 指向一个已经不存在的库 → 下次提问时
`pipelines.exists(kb_id)` 因为注册表里没了而返回 `False`（`pipelines.py:207-212`）
→ `chat.py:221` 把 mode 悄悄降级成 `agent` → 用户界面上看不出为什么突然不检索了。

改法：删库成功后，把 `sessions` 里 `kb_id === 被删 id` 的全部 PATCH 成 `null`，
并 toast 一句"已解绑 N 个会话"。

### ★ 7. 【沿用 · 未修】流式重渲染粒度

`page.tsx:197` 每个 token 都全量 map 一遍。Bubble 有 memo 兜底，长会话下是实打实的开销，
但暂时不痛——等放宽历史窗口再做。

### ★ 8. 【沿用 · 未修】无虚拟滚动

现在靠后端 `MAX_HISTORY_TURNS=10` 兜着，一旦放宽会立刻变成瓶颈。**和后端第 2 项联动**：
先修掉重试污染，才敢放宽窗口。

### ★ 9. 【沿用 · 部分改善】输入框只收图片

`ChatArea.tsx:752` 仍是 `accept="image/*"`。
不过比昨天好一点：附件条的提示文案（697-705）已经把"仅图片参与回答"写清楚了，
不再只有选完之后才告知。

### ★ 10. 【沿用 · 未修】间距阶梯仍未做完

纯打磨，不影响功能。界面完成度依然高于功能完整度，继续押后。
