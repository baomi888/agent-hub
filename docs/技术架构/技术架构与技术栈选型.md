### 1.4 检索链路（已实现，且是申报书的技术点）

```
候选池扩召回（top_k × 3，下限 12）
  → 余弦相似度离群过滤（RETRIEVE_MIN_SIM = 0.25）
  → MMR 多样性去重（λ = 0.65，字符 2-gram Jaccard）
  → 置信度示弱（RETRIEVE_LOW_SIM = 0.45，低于则提示"依据不足"）
```

切块 500 / 重叠 50，embedding 批 10、并发 4。

## 3. 关键决策点（真正需要团队讨论的）

每个决策点格式：**现状 → 选项 → 我的推荐 → 讨论时要问的问题**。

### D1 向量库：继续用 Chroma 还是换？

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. Chroma 本地持久化（现状）** | 零运维、单机够用、已跑通三段式重排 | 单写者；多副本部署要各自一份；无原生多租户 |
| B. pgvector（PostgreSQL 扩展） | 与关系数据同库、原生事务、真多租户、可上云托管 | 需引入 PG（运维 +1）；向量检索生态不如专用库成熟 |
| C. Milvus / Qdrant（专用服务） | 规模与并发最优、原生分区 | 多一个服务要管；**Demo 阶段完全用不上** |
| D. 混合：Chroma 起步 + 预留 pgvector 迁移路径 | 现在不折腾，将来可迁 | 需要现在就定好抽象边界（别让 `rag_core` 到处裸用 Chroma API） |

**推荐 D**。理由：Demo 阶段 3 个用户、单库，"换向量库"不是痛点；但**抽象边界要现在就留**——
把向量库操作收在 `kb/rag_core.py` 一处（现在基本是），将来换 pgvector 只改这一层。

**讨论时要问**：院赛演示是否要多副本？如果是，Chroma 的共享问题会先暴露。

### D2 会话/业务数据：SQLite 还是 PostgreSQL？

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. SQLite + WAL（现状）** | 零运维、单文件备份、实测单次查询 0.06ms | 单写者；多副本不可共享；无连接池 |
| B. PostgreSQL | 真并发、多副本、可托管 | 运维 +1；本地开发要起服务 |
| C. SQLite 起步 + SQLAlchemy 抽象 | 平滑迁移 | 现在代码是**直接写 SQL**，没有 ORM 层 |

**推荐 A 保持现状，但补一条纪律**：新代码继续用参数化 SQL（现状如此），**不要**为了"将来迁 PG"
现在就引入 ORM——那是为假想的规模付真实的复杂度。

**讨论时要问**：3 个用户 → 院赛几十人 → 立项后几百人，哪一步必须换？我的判断是**几百人且要对外时**才必须换。

### D3 后端形态：单体还是拆服务？

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 单体 + 独立 worker（现状）** | 部署简单；worker 已实现故障隔离 | worker 是第三个进程要管 |
| B. 全拆微服务（问答 / 知识库 / 调度） | 各自伸缩 | 团队 3 人，**运维成本会吃光开发时间** |
| C. 无服务器（Serverless） | 免运维 | SSE 长连接 + 定时任务都不适合；冷启动伤体验 |

**推荐 A**。**讨论时要问**：谁会运维？如果没人负责运维，任何"多一个服务"的方案都该否掉。

### D4 大模型：只用 DeepSeek 还是多供应商？

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. DeepSeek 单供应商（现状）** | 便宜、OpenAI 兼容、一处配置 | 单点依赖；限流/故障无兜底 |
| B. 多供应商 + 自动降级（DeepSeek → 通义/智谱） | 可用性高 | 要处理能力差异（function calling 支持度不一） |
| C. 本地模型（Ollama / vLLM） | 数据不出校、零边际成本 | 需要 GPU；小模型 function calling 不稳 |

**推荐 A + 预留 B 的接口**：现在别接第二家，但把"模型选择"收在 `core/llm.py` 一处（现状如此），
将来加降级只改一层。**申报书/答辩时**，"多供应商可切换"是个能讲的点，但别在 Demo 前真做。

**讨论时要问**：如果比赛当天 DeepSeek 挂了，有没有 Plan B？（我建议：现场录屏 + 预生成的 Mock 数据兜底。）

### D5 Embedding：API 还是本地？

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 百炼 API（现状）** | 质量好、免部署 | 按量计费；**数据出校**（申报书要提"资料不出校"就有冲突） |
| B. 本地中文 embedding（bge-m3 / m3e） | 数据不出本机、零边际成本 | 需 CPU/GPU；首次加载慢；效果需自测 |
| C. 混合：本地优先、API 兜底 | 兼顾 | 两套向量空间**不可混用**（换模型必须重建索引） |

**推荐**：Demo 期用 A（已在跑）；**但如果申报书里写了"资料不出校"**，
这一条现有实现是**不成立**的——embedding 走了阿里云。这是个必须澄清的对外承诺问题。

**讨论时要问**：申报书里到底怎么写的？要么改文案，要么换本地 embedding。

### D6 联网搜索：Serper 还是换？

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. Serper（现状）** | 便宜、快、已锚定中国区 | 境外服务，稳定性受网络影响 |
| B. 博查 / 智谱 Web 搜索（国内） | 国内网络稳 | 需重新对接、比价 |
| C. SearXNG 自建 | 免费、可控 | 要自己维护实例、结果质量不稳 |

**推荐 A 保持，但登记为风险项**（境外依赖）。**讨论时要问**：演示环境能否稳定访问境外 API？

### D7 定时任务：独立 worker 还是回到进程内？

现状已选独立 worker（APScheduler + 独立进程）。这是本轮刚做的决定，**建议先别翻**。
**讨论时要问**：`deploy.sh` 要多管一个进程，谁负责它的存活监控？
（已有 `GET /api/schedule/health` 按心跳年龄判 `stalled`/`down`，但需要有人看。）

### D8 蒸馏检索：做不做、怎么入库？

| 选项 | 优点 | 缺点 |
| --- | --- | --- |
| **A. 只出接口设计，不实现**（当前状态） | 20 号前不冒险 | 答辩时"蒸馏检索"讲不出实感 |
| B. 实现"候选池 + 人工确认"（契约已冻结） | 有实感、可控 | 约 2~3 天 |
| C. 自动入库 | 最"智能" | **会把幻觉固化成"看起来很确定的知识"** |

**推荐 B**，且**必须保留溯源闸门**（指不回原文的条目一律丢弃）。**讨论时要问**：
评委更看重"能自动学"还是"能证明不瞎学"？我押后者。

## 4. 三套整包方案（挑一套当基线）

### 方案一 · 省事优先（最小改动）

**适合**：20 号前只想稳，不为院赛做提前量。

- 保持现状全套：Chroma + SQLite + 单体 + 独立 worker + DeepSeek + 百炼 + Serper
- 只补两件事：**改掉申报书里与实现冲突的表述**（资料不出校 / 不做编码）
- 不引入任何新依赖

**代价**：院赛若要多副本、要数据不出校，届时改动会比较大。

### 方案二 · 均衡（推荐）

**适合**：想在院赛前把"能讲的技术点"补齐，但不想引入运维负担。

- 技术栈不变，**加抽象边界**：向量库操作收口 `rag_core`、模型选择收口 `llm.py`
- 实现**蒸馏检索候选池**（不含自动入库）
- 补 **embedding 本地化可行性验证**（一次实验：bge-m3 在本机的效果与速度）
- 加**可观测性**：结构化日志 + `/api/schedule/health` 接入前端面板

**代价**：约 3~5 天工作量；收益是答辩有实感 + 数据合规可讲。

### 方案三 · 面向院赛（最大改动）

**适合**：确定要冲院赛，且有人能负责运维。

- PostgreSQL + pgvector 替换 SQLite + Chroma（真多租户、可托管）
- 后端保持单体但**无状态化**（会话落 PG），支持多副本
- embedding 换本地模型（数据不出校）
- 加 CI/CD、监控、备份
- 多供应商模型降级

**代价**：运维复杂度显著上升，**3 人团队在院赛周期内风险偏高**。建议至少等校赛结束再评估。

## 5. 风险清单（按优先级）

| # | 风险 | 影响 | 缓解 |
| --- | --- | --- | --- |
| 1 | **申报书表述与实现冲突**（"资料不出校" vs embedding 走阿里云；"不做编码" vs 已实现） | 答辩被问住 | 20 号前统一口径，二选一 |
| 2 | 境外依赖（Serper / DeepSeek / GitHub） | 演示当天不可用 | 预生成 Mock + 录屏兜底 |

## 6. 给讨论会的三个问题

1. **申报书那句"资料不出校"要不要保留？** 保留就必须换本地 embedding（方案二/三），
   不保留就要改文案。这是**对外承诺**，不能含糊。
2. **院赛是否要多副本？** 要，就得在院赛前动 D1/D2；不要，方案二足够。
3. **谁负责运维那个新 worker 进程？** 没人负责的话，任何加服务的方案都该先否掉。
