# 落地报告 2026-10-20：P0 并发三件套（issue #15）

**目标**：200+ 人同时在线（今晚 21:00 前）。前置分析见
《并发承载测试报告_2026-10-20.md》——结论是"框架层余量 25 倍以上，真正的风险在
LLM 并发与 SSE 长连接"。本报告记录三条 P0 的实现与验收结果。

**结论先说**：三条全部落地并验收通过，全量测试 **397 passed**。200 人同时在线（浏览、
翻会话、偶尔提问）可以撑；"200 人同时发问"现在会**体面地排队**（429 + Retry-After），
而不是一起打爆上游。

---

## 一、做了什么

### P0-1 多 worker（吃多核）

- `deploy.sh`：新增 `detect_workers` —— 自动探测 `min(vCPU, 4)`，**内存 < 3G 封顶 2**
  （每个 worker 全量 import langchain + chromadb，常驻约 300MB；2 核 2G + Next.js +
  2G swap 的 ECS 上开 4 个会被 OOM Killer 随机杀）。优先级：环境变量 > `.env` > 自动探测；
  非法值直接 die。
- `systemd/install-systemd.sh`：同步把 `__WORKERS__` 替换进 unit（同一套探测逻辑）。
- `.env.example`：补齐 `WORKERS` / `LLM_MAX_CONCURRENCY` / `LLM_QUEUE_TIMEOUT` /
  `LLM_GATE_ENABLED` 四项说明。

### P0-2 LLM 并发闸（`core/llm_gate.py`，新文件）

- 每进程一个信号量，闸在**一轮问答**层（不是单次 HTTP 调用）：
  - `acquire()`：阻塞排队，`LLM_QUEUE_TIMEOUT`（默认 20s）抢不到名额 →
    **429 + `Retry-After`**，前端提示"稍后重试"。
  - `try_acquire()`：非阻塞，给后台任务（标题生成 / 标签 / 上下文压缩）用——
    **满了就跳过**，绝不让后台任务把用户问答挤出闸。
- `LLM_GATE_ENABLED=0` 一键回滚；`/health` 附 `llm_gate` 快照
  （inflight / waiting / rejected），排障第一眼就看它。
- ⚠️ 口径：这是**每进程**的值，N 个 worker 时全局上限 = N × `LLM_MAX_CONCURRENCY`。
  默认 16 × 2 worker = 32 条并行流，已接近常见账号的并发/TPM 上限，先保守设。

### P0-3 SSE 断连取消（`api/chat.py`）

- 用 `aclosing` 包住上游 `astream`：客户端中途关页面 → 流立刻停、**上游请求取消**，
  不留幽灵请求继续烧 token。
- `_Acc.aborted` 标记：断连的问答**不落库**（半截答案不进历史）。
- 放票走 `BackgroundTask`：响应结束后才归还名额，避免流还没结束名额就被别人抢走。

## 二、验收

### 2.1 闸的端到端验收（`tools/gate_acceptance.py`）

真起服务 + 桩 LLM（首帧后挂住不放），`LLM_MAX_CONCURRENCY=1`、6 个客户端同时发问：

| 指标 | 结果 |
|---|---|
| 拿到名额的 | **1 × 200**（首帧正常，桩生效挂住） |
| 被闸拒的 | **5 × 429**，全部带 `Retry-After: 1` |
| 429 响应耗时 | ~329 ms（没有干等） |
| 判定 | **pass** |

原始数据：`.loadtest/gate_acceptance.json`（不入库）。

### 2.2 worker 数对照（200 并发 = 4 进程 × 50，持续 8s，同机同脚本）

| 场景 | worker | RPS | p50 | p95 | p99 | 错误 |
|---|---|---|---|---|---|---|
| `/api/auth/me`（JWT + 查库） | 1 | 615 | 277 ms | 1537 ms | 2336 ms | 0 |
| `/api/auth/me` | 2 | **776**（+26%） | 167 ms | 897 ms | 1586 ms | 0 |
| `/api/auth/me` | 4 | **1050**（+71%） | 121 ms | 678 ms | 1012 ms | 0 |
| `/health` | 1 / 2 | 827 / 718 | — | — | — | ~0 |

读法：

1. 鉴权接口随 worker 数近似线性涨，p99 从 2336 → 1012 ms（**-57%**）。
2. `/health` 在 1w/2w/4w 下都在 700~1000 RPS 之间波动——这是**压测机生成能力**的
   上限（4 个生成器进程合计约 1000 RPS），不是服务端上限；其波动属于噪声。
3. 更早一轮 1w 跑出过 693 RPS（p99 1781 ms），与本轮 615 的差异是同机波动，
   趋势结论不变。

## 三、顺带修掉的相关隐患

- **限流在多 worker 下失效**（原 P1-4 / 审计 A3）：`core/quota.py` 从纯进程内字典改为
  双层——进程内滑窗超限后再查一次落库计数，`RATE_LIMIT_SHARED=0` 可回退旧行为。
  多 worker 下限流强度不再悄悄变成 N 倍。

## 四、遗留口径（写清楚，别当 bug 再查一遍）

1. **闸和限流的"全局上限"都是每进程值 × worker 数**。要收紧就调小
   `LLM_MAX_CONCURRENCY`，不要靠减 worker。
2. `deploy.sh` 的 `nohup` 路径仍可用，但已迁移 systemd 的服务器**不要混用**
   `deploy.sh start`（抢端口），以 `systemd/` 为准。
3. 真实 LLM 的并发/TPM 上限未压测（要烧钱），`LLM_MAX_CONCURRENCY=16` 是保守起点，
   上线后按 `/health` 的 `rejected` 增长情况再调。
4. 200 人同时登录仍需 15~20s 消化（PBKDF2 成本），属预期，见前置报告。

## 附：复现方式

```bash
# 闸验收（桩 LLM，不烧 token）
set LLM_MAX_CONCURRENCY=1 && python tools/gate_acceptance.py

# worker 对照（数据目录隔离）
python -m uvicorn main:app --host 127.0.0.1 --port 8125 --workers 2
python tools/loadtest_concurrency.py --base-url http://127.0.0.1:8125 \
    --mode all --concurrency 200 --processes 4 --duration 8 \
    --json-out .loadtest/r2w.json
```
