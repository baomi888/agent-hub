# 设置页账号自助：头像 / 姓名 / 密码

> 方案文档 · 2026-11-03 · 待审核，**尚未动代码**

## 0. 一句话

用户反馈"头像不能自定义、设置里改不了密码"，本次把这三件事（头像、姓名、密码）做成用户自己能改的；群聊里提到的"吉祥物个性化"按你们商量的结果**本期不做**。

## 1. 需求范围

### 来自群聊的原话

- 「有用户反应现在头像自己不能自定义，设置那块不能修改密码，然后想要我们的那个吉祥物可以也个性化定制，例如变成猪什么的」
- 「这个头像可以用户自己随便改」
- 「这个可以放后，设置那块可以支持修改头像姓名和密码就行」

### 本期做

| # | 功能 | 用户可见效果 |
|---|---|---|
| 1 | 改头像 | 点自己头像 → **既能挑内置形象，也能传自己的照片** → 侧栏、设置页立刻变 |
| 2 | 改姓名 | **昵称**（展示用，随便改）+ **登录名**（可改，要输密码，限 3 次） |
| 3 | 改密码 | 旧密码 + 新密码 → 改完新密码能登、旧密码登不上 |

### 本期不做

- **吉祥物个性化**（群聊结论"可以放后"，且产品上"吉祥物被用户改成猪"会破坏品牌识别）
- 头像裁剪框（拖拽选区、缩放）、多图相册、头像历史
- 两步验证、手机绑定

> 头像必须是"上传自己的照片"——这条已确认，不是可选项。所以 §5.4 的限额与 §5.5 的省资源设计是本次的重点之一。

## 3. 需要你拍板的决策（D1 已定，剩 D2 / D3）

### D1 头像做成什么形态？—— ✅ 已定：内置图标 + 上传照片都做

你的补充已经很明确："头像要支持自己上传"，所以**上传是必做项**，内置图标作为默认兜底（不想传图的人一键选一个，也省服务器空间）。

剩下的只是**上线顺序**：

- 第 1 批：昵称 + 密码 + 内置图标头像
- 第 2 批：上传自定义头像

这样拆是因为上传涉及文件存储、图片解码、并发内存、旧文件清理四件事，值得单独验证一轮再上。**但两批都会做，不是二选一。**

**关键约束（你提的"轻量化服务器"）**：设计原则是「用户能传大图，但服务器只承受小流量、只存小文件」。具体见 §5.4 和 §5.5 —— 结论先说：**1000 个用户用满，头像总共占 18MB 左右**，比 `venv` 的 540MB 小两个数量级。

### D2 姓名：昵称和登录名**都让改**（按你的追问修正）

你说得对，我原来的建议只解决了半个问题。用户"不喜欢自己注册的用户名"，如果只给他一个昵称、登录还得输那个难看的名字，他会觉得"这不还是老样子吗"。

改成两个字段分工，各管一件事：

| 字段 | 叫法 | 能改吗 | 唯一 | 干什么用 |
|---|---|---|---|---|
| `nickname` | 昵称 | 随便改，不限次数 | **可重复** | 别人看到的称呼、头像旁边那个字 |
| `username` | 登录名 | 能改，但要输密码 | **唯一** | 登录凭证 |

于是用户有两条路：

- 只是觉得名字不好听 → **改昵称**，零成本、立刻生效、不影响登录
- 连登录名也嫌难看/难记 → **改登录名**，输一次密码 + 查重就行

#### 为什么不干脆合并成一个字段

因为两者改动的**代价完全不同**：

- 昵称改一万次，都只是换个显示文案
- 登录名一改，凭证就变了 —— 用户可能第二天就忘，而且我们**没有手机号/邮箱可以找回**

分开之后，想天天换着玩就去改昵称（安全）；真要动登录名时，会因为"要输密码"而意识到这是一件正事。

#### 为什么昵称不要求唯一

如果昵称唯一，"小猪佩奇"这种名字第二天就被占完了，改个显示名还要面对"该昵称已被占用"，体验很荒唐。反正昵称不参与登录，重复没有歧义。

#### 「改完忘了登录名怎么办」—— 四条兜底

这是真实风险，必须提前防：

1. **设置页永久显示**「登录名：xxx」，放在账号卡最显眼的位置，不是藏在折叠区
2. **改成功后明确提示**：「你的新登录名是 `xxx`，下次登录用它，请记好」，要求点一下"我知道了"
3. **改名写审计日志**（`users.username` 变更记一条到日志表），用户真忘了，管理员能查历史协助找回
4. **限制次数：登录名最多改 3 次**（`name_change_count` 计数）。够用了 —— 正常人改名一两次，反复改多半是出了问题；这条同时挡住"改来改去把账号搞乱"

#### 技术上要动什么（已核实，成本很低）

- `username` **没有被任何其它表外键引用**（只在 `users` 表和 JWT claim 里用到），改名安全
- 唯一索引 `idx_users_name ON users(username COLLATE NOCASE)` 会在重名时抛 `IntegrityError`，API 层翻译成 409「这个登录名已被占用」，跟注册同一套路
- 改名后给当前会话**重发 Cookie**（JWT 里的 `username` 是展示用冗余，重发一次就同步）
- 长度/字符沿用现有 `check_name()`：3~32 字符，`[\w.\-]+`

### D3 改完密码，其它设备要不要强制下线？—— 要，否则等于没改

| 方案 | 效果 | 实现 |
|---|---|---|
| **A 全部踢下线，当前这台自动续上**（推荐） | 安全直觉正确：改密码就该是"别人进不来了" | `users` 加单调鉴权代数；每次改密 +1，令牌带 `af`，校验时精确比较；同时给当前会话重发 Cookie |
| B 不踢 | 实现最省事，但"改了密码别人还能继续用"是真实缺陷 | 什么都不做 |

#### 为什么必须踢：不踢的话，改密码只改了"以后"，没关"已经开着的门"

具体三种真实场景：

1. **在别人的电脑/图书馆机器上登录过，忘了退出**。你改密码，心想"这下安全了"。但那台机器上的 Cookie 还活着，**照样能看到你的所有对话、知识库、日报**。
2. **密码在别处泄露了**（比如你在别的网站用了同一个密码，那边被拖库）。有人用你的密码登了进来，你发现后改密码 —— 如果旧会话不失效，他还能继续待着，而你已经"以为把他赶出去了"。
3. **手机丢了/借给别人了**。改密码是唯一能远程"断掉那台手机"的手段，不踢就等于没做。

#### 这个风险有多大？一个具体数字

我们的登录有效期是 `AUTH_TTL_DAYS = 7` 天（`core/config.py:134`）。也就是说：

> **不踢的话，已经进来的那个会话最长还能用 7 天。**

7 天足够把一个人所有的对话记录翻一遍、把知识库里的资料下走。

#### 技术上为什么不能"顺手就踢"（说明代价真实存在）

- 现在的令牌是 **JWT，本身无状态** —— 签发出去就收不回来，服务端不记录谁在用哪一枚，只能靠"到期"或"主动吊销"
- 项目里已经有 `revoked_tokens` 表（`core/session.py:112`），但它**只能精确吊销某一枚令牌**（需要拿到那枚令牌的 `jti`），做不到"把这个人的所有令牌一次作废"
- 所以要么每次登录都把 jti 记下来（要新增一张表、长期维护），要么用 `token_valid_after` 存单调鉴权代数 —— **后者只有一条 SQL 的代价**

两种做法的对比：

| 做法 | 实现成本 | 结果 |
|---|---|---|
| 记录每个用户的全部 jti | 新增表 + 每次登录写一行 + 定期清理 | 能精确踢，但要长期维护 |
| **`token_valid_after` 代数**（选这个） | 加一列 + 每次改密原子 +1 + 校验一次整数 | 能全踢；同秒连续改密、时钟回拨也不会漏旧令牌，**存量用户不受影响**（默认 0） |

#### 用户体验上会不会被骂

不会，因为**只踢别的设备，当前这台你正在用的不会掉**：改完密码后端立刻给你重发一枚新 Cookie，页面无感。

真正被踢的是"另一台你不在跟前的设备"—— 那正是你想要的效果。

#### 一个类比

改密码不踢下线，等于**换了门锁，但没换钥匙**：新钥匙只发给以后的自己，旧钥匙还在别人兜里，照样能开门。

代价只有十几行，但它是"改密码"这个功能存在的意义所在。

## 4. 数据模型

沿用 `_ensure_columns()` 的幂等补列方式，不写迁移脚本、不停机：

```python
# core/account.py::_ensure_columns() 追加
if "nickname" not in cols:
    # 显示名。NULL / 空串都表示"没设过"，读取时回落到 username。
    # **故意不加唯一索引**：昵称不参与登录，重名不产生歧义，
    # 加了反而让用户改个显示名还要撞名。
    conn.execute("ALTER TABLE users ADD COLUMN nickname TEXT")
if "avatar" not in cols:
    # 统一用一个字段，用前缀区分类型，以后加新形态不用再改表：
    #   ""            -> 没设过，前端用昵称首字母
    #   "icon:star"   -> 内置图标（CornIcon 的 name）
    #   "img:<hash>"  -> 上传的图片，文件名是内容 hash，天然带缓存
    conn.execute("ALTER TABLE users ADD COLUMN avatar TEXT NOT NULL DEFAULT ''")
if "token_valid_after" not in cols:
    # 改密码 / 强制下线的鉴权代数（列名兼容保留）。
    # 每次改密 +1；0 = 从未触发，对存量令牌零影响
    conn.execute(
        "ALTER TABLE users ADD COLUMN token_valid_after INTEGER NOT NULL DEFAULT 0"
    )
if "name_change_count" not in cols:
    # 登录名改过几次。上限 3 次，防"改来改去把自己搞晕"，也防滥用。
    # 默认 0，存量用户不受影响。
    conn.execute(
        "ALTER TABLE users ADD COLUMN name_change_count INTEGER NOT NULL DEFAULT 0"
    )
```

`username` 仍然保持**唯一索引**（现有 `idx_users_name ... COLLATE NOCASE` 不动）—— 它是登录凭证，必须唯一。`nickname` 才是随便重复的那个。

**为什么头像用内容 hash 而不是 `<uid>.jpg`**：
- 换头像后 URL 自动变（`/api/auth/avatar/<hash>`），**不需要处理浏览器缓存**
- 多个用户用同一张图时可以共用一份文件（可选优化）
- 文件名不受用户输入影响，天然防路径穿越

## 5. 接口设计

> 项目规矩：新端点**不带尾斜杠**（`normalize_api_slash` + `redirect_slashes=False`），下面已按此写。

### 5.1 改昵称 / 选内置头像（不需要密码）

```
PATCH /api/auth/profile
Content-Type: application/json

{ "nickname": "小猪佩奇", "avatar": "icon:star" }
```

- 两个字段都可选，只传哪个改哪个
- `nickname`：1~20 字符，去掉首尾空白；空串 = 清空（回落 username）
- `avatar`：只接受 `icon:<name>`，且 `name` 必须在白名单里（防前端塞任意字符串进库）
- 返回更新后的 `MeOut`
- 限流：复用 `quota.hit`，按用户 10 次/分

**为什么不叫 `PATCH /api/auth/me`**：`/me` 现在是纯读端点，混进写操作会让"探活"和"改资料"共用一条路径，缓存和日志都不好分。单独开 `/profile`。

### 5.2 改登录名（需要旧密码 + 查重 + 次数限制）

```
POST /api/auth/username
Content-Type: application/json

{ "password": "当前密码", "new_username": "新登录名" }
```

后端流程：

1. `verify_password(password, row["password_hash"])` 失败 → 400「密码不对」
2. `check_name(new_username)` 不合规 → 400 带具体原因（3~32 字符，`[\w.\-]+`）
3. 与当前登录名相同 → 400「和现在的一样」
4. `name_change_count >= 3` → 429「登录名最多改 3 次」
5. 查重：`get_user_by_username(new)` 有值 → 409「这个登录名已被占用」
6. `UPDATE users SET username=?, name_change_count=name_change_count+1 WHERE id=?`
   （唯一索引 `COLLATE NOCASE` 会兜住并发抢注，`IntegrityError` 同样翻译成 409）
7. **给当前会话重发 Cookie**（JWT 里的 `username` 是展示冗余，重发即同步）
8. 写一条审计日志（谁、从什么改成什么、什么时候）
9. 返回新 `MeOut`

**为什么这里要输密码**：登录名是凭证。如果只凭一个已登录的会话就能改，等于"只要偷到一台没锁屏的电脑，就能把账号改成自己的名字"。

### 5.3 改密码（需要旧密码）

```
POST /api/auth/password
Content-Type: application/json

{ "old_password": "abc123", "new_password": "def456" }
```

后端流程（顺序不能乱）：

1. 取 `row = account.get_user(uid)`，`verify_password(old, row["password_hash"])` 失败 → 400「原密码不对」
2. `account.check_password(new)` 不合规 → 400 带具体原因（复用现有中文提示）
3. `old == new` → 400「新密码和原密码相同」
4. `UPDATE users SET password_hash=?, token_valid_after=token_valid_after+1`
   （带旧 `password_hash` 做条件更新，防止两个并发改密请求都返回成功）
5. **给当前这台重发 Cookie**（`auth.set_cookie(response, create_token(...))`），否则用户改完自己就被踢了
6. 返回 200 + 新 `MeOut`

### 5.4 上传头像：三层限额（这是轻量服务器的关键）

```
POST /api/auth/avatar         multipart/form-data，字段名 file
GET  /api/auth/avatar/<hash>  返回图片，公开可读（头像本来就不是秘密）
```

#### 业界怎么做的（你问的"学习其他软件"）

| 产品 | 上传上限 | 做法 |
|---|---|---|
| GitHub | 1 MB | 建议 200×200 以上，服务端裁方 |
| Gmail | 4 MB | 客户端先压 |
| 微博 / 知乎 / QQ | 5 MB | 客户端压缩后上传 |
| 微信 | 原图较大 | 客户端压到几百 KB 再传 |

**共同规律**：上限都落在 **2~5 MB**，而且**都在客户端先把图压小再传**。没有哪家会让用户把 20MB 原图直接怼给服务器。

我们取 **5 MB 作为硬上限**（对齐主流），但真正走网络的平均只有 100~200 KB。

#### 我们的三层限额

| 层 | 限制 | 作用 |
|---|---|---|
| **第 1 层 前端压缩** | canvas 把长边压到 640、JPEG q0.85 | 5MB 手机原图 → **80~150KB** 实际传输，流量降 95% |
| **第 2 层 后端硬限** | 文件 ≤ **5 MB** | 防绕过前端（curl / 改 JS / 其它客户端） |
| **第 3 层 落盘** | 只存 **192×192** JPEG q85 ≈ **12~18 KB** | **原图处理完立刻删除，绝不保留** |

第 1 层是省服务器的那一层，第 2 层是防滥用的那一层，第 3 层是省磁盘的那一层。三层缺一不可 —— 只做前端压缩等于没有限制，只做后端限制等于用户每次传 5MB 白烧流量。

#### 具体参数（服务端，全部自己校验，不信前端）

| 项 | 值 | 理由 |
|---|---|---|
| 文件大小 | ≤ 5 MB | 对齐主流；超了直接 400 |
| 类型白名单 | `image/jpeg` `image/png` `image/webp` | **明确不收 SVG**（能带脚本，是 XSS 入口） |
| 真实校验 | `PIL.Image.open()` 打得开，且解析出的 `im.format` 必须是 JPEG / PNG / WEBP | 只看 Content-Type / 扩展名能被伪造 |
| 像素上限 | ≤ 4000×4000 | 防解压炸弹，见 §5.5 |
| 输出 | 居中裁正方形 → 192×192 → JPEG q85 | 统一尺寸，省流量 |
| 存储 | `${DATA_DIR}/avatars/<sha256前16位>.jpg` | 内容 hash 做文件名，换图自动破缓存，且天然防路径穿越 |

#### 直接复用现有代码，不重复造

- **`core/upload.py::save_stream(f, path, limit_bytes)`** 已经实现了「分块写盘 + 超限立即中断 + 删掉半成品」，头像上传直接调它，**不要用 `await file.read()` 整块读进内存**（5MB 乘上并发会直接顶满内存）

  `ops/nginx-baomi.conf` 与 `https/agent-hub.conf.template` 都已加入该位置块

### 5.5 轻量服务器真正的风险不是磁盘，是峰值内存

这点必须单独说，因为容易想错：

**一张 5MB 的 JPEG，Pillow 解码成位图后可能占 50~100 MB 内存。** 更狠的是「解压炸弹」——一个只有几十 KB 的 PNG，能解出几 GB 的位图，直接把进程打死。2 核 2G 的机器上，两个这样的请求同时到就 OOM 了，而且是**整个后端一起挂**，不是只挂一个上传。

五条对策（都要做）：

1. **先读尺寸再解码**：`Image.open(p)` 只读文件头，不 `load()` 就不解像素。拿到 `width/height` 先判断，超过 4000×4000 直接拒 —— 解压炸弹在这一步就死了
2. **显式设 `Image.MAX_IMAGE_PIXELS`**：Pillow 默认只在超限时发 warning，**不报错**，等于没有保护
3. **用 `thumbnail()` 而不是 `resize()`**：前者按需降采样、峰值内存更低
4. **并发信号量限 2**：`asyncio.Semaphore(2)` 包住解码段，宁可让第 3 个人等 200ms，也不要一起 OOM
5. **处理完立即删原图**：临时文件用 `try/finally` 保证清理

#### 磁盘占用算给你看（这是你关心的"占空间"）

每张头像按要求压完后约 **12~18 KB**：

| 用户规模 | 头像总占用 | 对比 |
|---|---|---|
| 100 人 | ≈ 1.8 MB | 一张手机照片的大小 |
| 1,000 人 | ≈ 18 MB | 项目 `venv` 的 1/30 |
| 10,000 人 | ≈ 180 MB | 仍然小于 `venv`（540MB） |

**结论：只要坚持"不存原图、只存 192×192"，头像永远不是空间问题。** 会出问题的只有一种情况 —— 把用户原图原样存下来，那 1000 个用户就是 5GB，直接爆盘。所以「处理完删原图」这条是硬规矩。

#### 旧头像怎么清理

换头像后旧文件不会自动消失，两种做法：

- **推荐**：上传成功后，如果旧 `avatar` 是 `img:` 开头，查一下还有没有别的用户在引用这个 hash，没有就删掉（一句 SQL）
- 兜底：`worker` 里加个每周任务，扫 `data/avatars/` 删掉无引用的文件

不做这件事，一年下来会攒一堆没人用的碎图（虽然总量也不大，但没必要）。

### 5.6 令牌校验加一条（配合 D3）

`core/auth.py` 的 `get_current_user` 里，在现有 `is_revoked` 之后加：

```python
# 改密码后旧会话作废：令牌里的鉴权代数与库中当前值不相等就拒
auth_version = int(row.get("token_valid_after") or 0)
if int(claims.get("af") or 0) != auth_version:
    raise HTTPException(401, "登录状态已失效，请重新登录")
```

**必须精确相等，不能用时间戳比较**：同一秒连续改两次密码时，时间水位不变；
服务器时钟回拨也会让旧代数重新“合法”。单调 +1 后，每枚令牌只认签发那一刻的代数。

**对存量的影响**：现有用户 `token_valid_after = 0`，历史令牌没有 `af` 也按 0 处理，
所有人不受影响。这是"加字段不破坏老数据"的关键。

### 6.4 前端压缩怎么做（第 1 层限额，省服务器的关键）

选完图**先在前端压，再上传**。用 canvas，不引第三方库：

```ts
// lib/imageCompress.ts
export async function compressAvatar(file: File): Promise<Blob | null> {
  // createImageBitmap 比 new Image() 内存更省，也不会阻塞主线程渲染
  const bmp = await createImageBitmap(file).catch(() => null);
  if (!bmp) return null;                    // 解不了（如 HEIC），交给调用方兜底

  // 居中裁成正方形：最终展示就是圆的，先裁后传，用户看到的就是成品
  const side = Math.min(bmp.width, bmp.height);
  const sx = (bmp.width - side) / 2;
  const sy = (bmp.height - side) / 2;

  const out = 640;                           // 长边 640 足够 192 显示，还留了视网膜余量
  const canvas = document.createElement("canvas");
  canvas.width = canvas.height = out;
  const ctx = canvas.getContext("2d")!;
  ctx.drawImage(bmp, sx, sy, side, side, 0, 0, out, out);
  bmp.close?.();                             // 主动释放，别等 GC

  return new Promise((res) =>
    canvas.toBlob((b) => res(b), "image/jpeg", 0.85)
  );
}
```

几个参数的理由：

- **长边 640**：最终只显示 192px，640 已经留了 3 倍余量，再大纯属浪费
- **q 0.85**：肉眼无损的甜点；降到 0.7 以下人像脸会发灰发脏
- **先裁方再缩放**：否则后端裁方时会把已经缩掉的部分放大，白丢画质
- **兜底**：`compressAvatar` 返回 `null`（老浏览器 / HEIC）时，直接把原图传上去，让后端的 5MB 限制和 Pillow 兜 —— **宁可让后端多干活，也不要让用户传不上去**

实测预期：一张 iPhone 拍的 4~5MB 照片，压完 **80~150KB**。
