## 一、后端可更新点

### ★★★ 1. RAG 主链路的检索是裸同步调用，每次堵事件循环约 250 ms

**文件**：`api/chat.py:411`（RAG 主分支）、`api/chat.py:269`（图片理解模式的附加载入）

```python
# chat.py:407-411  async def event_generator() 内部
elif mode == "rag":
    yield _sse("status", {...})
    try:
        pipe = pipelines.get_or_create(kb_id)
        docs_scores = pipe.retrieve_with_score(req.question, req.top_k)   # ← 同步阻塞
    except Exception as e:
        ...
```

**为什么这条最值钱**：它不是理论上"可能慢"，而是**实测 250 ms** 且堵的是事件循环。

`retrieve_with_score()`（`kb/rag_core.py:419-439`）内部做了三件事：

| 步骤 | 实测耗时 |
| --- | --- |
| `self.count()` → 读 Chroma 的 sqlite | 0.79 ms |
| `similarity_search_with_score()` → **先调 embedding 接口向量化提问** | **248.27 ms**（其中 `embed_query()` 独占 258.96 ms） |
| `select_diverse()` 重排 | 纯 CPU，可忽略 |

⇒ 一次 RAG 问答，**在第一个 token 吐出来之前，整个 FastAPI 进程有约 250 ms 什么都做不了**
（别的请求、正在流式输出的 SSE、后台上传全排队）。

**更关键的是：这是「同一个规则 A 处遵守、B 处漏了」的第三例。**
`api/kb.py:139` 写对了：

```python
# kb.py:136-139
# 检索 + LLM 都是同步阻塞调用，丢到线程里跑，别占着事件循环
answer, refs = await asyncio.to_thread(pipe.answer, question, top_k)
```

同一个类的同一个方法 `answer()` 内部也要调 `retrieve_with_score()`，在 `kb.py` 里正确包了线程，
在 `chat.py` 里（人流量最大的 `/api/chat/stream`）反而裸着。
说明 10-03 那次「读路径补 `to_thread`」的扫街**是按端点推进的（`kb.py` 六个函数），没按调用点推进**，
于是 `chat.py` 内部的三条分支（vision / rag / agent）除 agent 的 `build_agent` 外都没扫到。

同文件另外几处同源问题（`event_generator()` 是 async，全是裸调同步 SQLite，实测 2.09 ms/次）：

| 位置 | 调用 |
| --- | --- |
| `chat.py:282` | `store.get_messages(...)` |
| `chat.py:443` | `store.get_messages(...)` |
| `chat.py:496`（`_build_messages` 内，由 `:427` 调用） | `store.get_messages(...)` |
| `chat.py:464` | `store.add_message(...)` |

**怎么改**（核心 2 行）：

```python
# chat.py:411
docs_scores = await asyncio.to_thread(pipe.retrieve_with_score, req.question, req.top_k)
# chat.py:269（vision 分支同样处理）
docs_scores = await asyncio.to_thread(pipe.retrieve_with_score, req.question, req.top_k)
```

SQLite 那四处同理，`await asyncio.to_thread(store.get_messages, req.sid, include_system=False)`。

**验证方式**：并发打 3 条 `/api/chat/stream`，看第一条 token 的到达时间是否不再线性叠加
（`tools/stress_live.py` 已有现成脚本，改前改后各跑一次对比 P50）。

### ★★ 2. **`_ensure_vs()` / `get_or_open()` 绕过了 Chroma 单例** —— 这条是昨天第 1 条推荐修法里的坑

**文件**：`kb/rag_core.py:266-274`（`_ensure_vs`）、`kb/rag_core.py:409-416`（`get_or_open`）

```python
# rag_core.py:269  和  rag_core.py:412，两处写法一样
self._vs = Chroma(
    persist_directory=config.PERSIST_DIR,   # ← 没传 client=，langchain 会自己 new 一个 PersistentClient
    embedding_function=get_embeddings(),
    collection_name=self.collection_name,
)
```

而项目自己的规矩（`MEMORY.md` 四节 + `rag_core.py:34` 的注释）是
**「全项目只允许这一处 `PersistentClient`，都用 `chroma_client()`」**。
同文件 `:309`、`:395`、`:403` 以及 `pipelines.py:241/413` 都遵守了，**唯独这两个方法没遵守**。

**实测证据**（本机 A/B 对比，`_client is 单例` 直接判 identity）：

```
A  Chroma(persist_directory=)   163.54 ms/次   → a._client is 单例 : False  ← 绕过了
B  Chroma(client=单例)            73.14 ms/次   → b._client is 单例 : True
```

三个后果：

1. **慢 2.2 倍**（164 ms vs 73 ms），而且这个开销是**每个知识库各来一次**；
2. 每个库持有一个**独立的 `PersistentClient`** ⇒ N 个库 = N 条到 `chroma.sqlite3` 的连接，
   在 2 核 2G 的 ECS 上是实打实的内存与 SQLite 锁竞争压力；
3. **这是昨天那条 ★★★ 建议的陷阱**：昨天第 1 条的修法写的是「把 `get_or_open()` 换成 `_ensure_vs()`」，
   而 `_ensure_vs()`（`:269`）**恰恰就是没走单例的那个**。照着改等于从一条慢路径换到另一条同样绕开单例的路径。

**怎么改**（2 行 + 1 个 import）：

```python
self._vs = Chroma(
    client=chroma_client(),        # ← 复用进程级单例
    embedding_function=get_embeddings(),
    collection_name=self.collection_name,
)
```

两处都改。改完可以用 `:53` 那行 `chromadb.PersistentClient(path=...)` 的 grep 数确认只剩 1 处。

## 二、前端可更新点

### ★★★ 6. `d2c96e1` 的热修引入了一个新竞态：切换会话会串台

**文件**：`frontend/src/lib/hooks/useSessions.ts:90-101`（`selectSession`）、对照同文件 `:50-75`（初始化 effect）

昨天晚上的热修给 init effect 加了「自动选中最近会话并拉取它的历史」这一步（`:58-70`），
这一步**是正确的**，但它是新起的一个异步分支，而同文件的 `selectSession` **没有对应的竞态保护**：

```ts
// useSessions.ts:50-75  初始化 effect —— 有 alive 守卫
useEffect(() => {
  let alive = true;                      // ← 有
  ...
  const recent = s?.sessions?.[0];
  setActiveSid(recent.id);
  const detail = await api.getSession(recent.id);
  if (alive) setMessages(toUiList(detail.messages));   // ← 但 alive 只挡"组件卸载"
}, [showToast]);

// useSessions.ts:90-101  selectSession —— 完全没有守卫
const selectSession = async (sid: string) => {
  setActiveSid(sid);
  setMessages([]);
  const detail = await api.getSession(sid);
  setMessages(toUiList(detail.messages));              // ← 谁最后回来谁赢
};
```

**两个缺陷叠起来才是真 bug**：

1. `selectSession` 没有 generation 保护 ⇒ 快速连点会话 A→B 时，A 的请求晚于 B 返回就会**把 B 的界面写成 A 的消息**；
2. init effect 的 `alive` 只判断"组件还在不在"，**不判断"这条连接还属不属于当前 activeSid"**。
   而 init 新增的这次 `getSession` 是在**页面加载后立刻发出**的。

⇒ **实际可达路径**：打开页面 → init 开始拉会话 A 的历史 → 用户在 200~500 ms 内点了会话 B →
`selectSession(B)` 先清空再请求 B → **A 的请求后返回** → 会话 B 的界面显示会话 A 的历史。
服务器那边 RTT 是 33~78 ms（`tools/stress_live.py` 实测），但页面一起还要并发拉会话列表/知识库/defaults，
首屏几百毫秒窗口很容易命中，慢网络下几乎必现。

**雪上加霜**：`app/page.tsx:456-459` 的 `onSelect` **只调 `selectSession`，没有 `abortRef.current?.abort()`**，
所以在流的那条 conversational 请求也不停 ⇒ 旧的 SSE `done` 事件还会再认 `setMessages` 一次。
（这条单独看是昨天已经记过的"切会话不 abort"，今天是它和 init 自动加载**首次相遇**。）

**怎么改**（两个 hook，共 6 行）：

```ts
// useSessions.ts 顶部加一个自增序号
const reqSeq = useRef(0);

// selectSession：请求前后对齐序号
const selectSession = async (sid: string) => {
  const seq = ++reqSeq.current;
  setActiveSid(sid);
  setMessages([]);
  try {
    const detail = await api.getSession(sid);
    if (seq !== reqSeq.current) return;          // ← 已经有更新的请求，丢弃这次
    setMessages(toUiList(detail.messages));
  } catch (e) { ... }
};

// init effect 里那次自动加载同样用 ++reqSeq.current 保护
```

再给 `page.tsx:456` 的 `onSelect` 补一行 `abortRef.current?.abort();`。
