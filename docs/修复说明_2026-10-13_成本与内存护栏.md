# 修复说明 2026-10-13：成本与内存护栏（第一档）

针对知识库 / 大模型 / 联网搜索三块的 review，按 ROI 分档落地。本档三项均为
"小改动、直接省钱或防风险"，全部带回归测试，全量 29 项 pytest 通过。

---

## 1. 标题生成：输入截断 + 输出上限

**文件**：`api/chat.py` `_generate_title`

**问题**：首轮问答会自动生成会话标题，原实现把**完整用户问题**塞进标题 prompt，
且 `get_llm(temperature=0)` 没有 `max_tokens`。首问若是粘贴的长文档（几千字），
一次标题生成就吃掉全部输入 token；模型跑偏时输出也无兜底。

**改法**：
- 输入只取 `question[:200]`——标题只反映开头主题，截断不损质量；
- `get_llm(temperature=0, max_tokens=32)`——标题只要 ≤15 字，32 token 足够，
  同时防止模型把正文复述一遍。

**收益**：长文首问的标题成本从"整篇输入 + 无界输出"压到 ~200 字 + 32 token。

## 2. 导入去重：has_source 轻量判存

**文件**：`kb/rag_core.py`（新增 `has_source`）、`kb/importer.py`（两处去重换用）

**问题**：`import_url` / `download_and_index` 的同名去重原来调
`pipe.get_source_chunks(name)`——它会把该文件**全部片段的正文 + 元数据**拉回内存，
只为回答"这个文件入过库吗"。几百片的大文件每次导入都白拉一遍。

**改法**：新增 `RagPipeline.has_source(source)`，用
`collection.get(where={"source": ...}, limit=1, include=[])` 只取一条 id 判断，
无论文件多大都是 O(1) 的一次 sqlite 查询；空库 / 查询异常一律返回 False，
不炸导入流程。

**收益**：大文件的去重检查从 O(文件片段数) 的内存与 IO 降到 O(1)。

## 3. 网页抓取 / 下载：真流式 + 大小闸

**文件**：`kb/importer.py`

**问题（两层）**：
1. `fetch_url_text` 的 `resp.text` 把整个 HTML 读进内存，且**没有任何大小上限**——
   伪装成网页的大文件（或异常巨页）可以直接吃爆内存。下载链路有 200MB 闸，网页没有。
2. 更深一层：旧 `_safe_get` 用 `httpx.get`，**返回时响应体已全部进内存**，
   之后 `iter_bytes` 只是在现成的内存块上切片。也就是说下载的 200MB 流式闸
   一直是马后炮——闸触发前内存已经吃完了。

**改法**：
- `_safe_get`（httpx.get 缓冲式）→ `_safe_stream`（httpx.stream 上下文管理器），
  保留原有的逐跳重定向 SSRF 校验语义不变；
- 新增 `_read_capped`：流式累计读取，超 5MB 立即 `ValueError` 中止，
  内存里最多只有上限大小的数据；
- 新增 `_decode_html`：响应头 charset 优先，缺失/失败时用 charset_normalizer
  探测（httpx 自带依赖），行为与旧 `resp.text` 兜底一致；
- `download_file` 同走 `_safe_stream`——至此 200MB 下载闸**真正生效**。

**收益**：网页抓取内存钉死在 5MB；下载内存从"整文件入内存"变为分块常量级。
