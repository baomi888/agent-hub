## 一、总体结论（先说真话）

**这套代码库整体质量已经很高，不是需要推倒重来的「屎山」。**

逐文件通读后可以确认：模块边界清晰、关键设计意图都有成段的中文注释在解释「为什么这么写」
（例如 `core/tool_registry.py` 说明为何要把「能否重试」从自然语言上升到声明式字段、
`hybrid/expr.py` 说明为何不直接用 `eval`、`core/session.py` 说明为何连接要按线程复用）。
这类注释的价值高于代码本身——它把「踩过的坑」固化下来了。

因此本轮不做「大规模重构」，而是**定向清偿**：用逐文件通读 + AST 死符号扫描，
把可确证的债务（死代码、重复、多余的 IO、崩溃路径、缺失的契约注释）一条条挑出来处理掉，
并用离线用例把改动点的行为钉住。共处理 **12 处**，其中 **2 处是真实缺陷路径**。

## 三、逐条改动

### A. 等价改动（零行为变化，均可论证）

| # | 位置 | 改法 | 等价性依据 |
|---|---|---|---|
| A1 | `api/delegate.py` | 删除死函数 `_enabled_count`，收敛为纯函数 `_count_enabled(items)`，供建/改两处复用 | 两处原表达式 `sum(1 for d in items if d.get("enabled"))` 完全一致；`_enabled_count` 传入的是 uid、内部又查一次库，与调用方手上的列表同源。传列表不改变结果，还少一次查库 |
| A2 | `api/delegate.py` | `import json` 提到模块级 | 函数体内 `import json as _json` 每次调用都执行一次 import 语句（Python 有缓存，功能无损，但属噪声） |
| A3 | `api/delegate.py` | 去掉 `ScheduleIn(**d) if isinstance(d, dict) else d` 中不可达的 `else` 分支 | `model_dump()` 已把嵌套模型转成 dict，`else` 分支永远走不到 |
| A4 | `hybrid/store.py`、`core/session.py` | `_db_path()` 改为纯计算（去掉 `os.makedirs`），目录创建挪到 `_conn()` 建连前 | `_conn()` 每次操作都取一次路径，此前顺带一次 `makedirs(exist_ok=True)`，等于每条 SQL 前白做一次系统调用。目录在建连前建好即可；测试 monkeypatch `_db_path` 到临时目录时，建目录仍跟着走（`core/session.py` 的 `_db_path` 被 `tests/test_auth_gate.py` 替换，已专门验证） |

| 位置 | 符号 | 核查结论 |

| `core/account.py` | `count_users`、`list_users` | 管理侧辅助函数，未接任何端点 |
| `core/scheduler.py` | `today_local` | 与 `core/quota.day_key()` 同语义的重复来源，无调用方（删除顺带消除「两处各写一套日界口径」的隐患） |

> 删除前一律先做「全仓库 AST 引用 + 定点 grep」双重核查。上一轮曾因把
> `RagPipeline.answer` 当死代码删掉而**实际有端点调用**（导致 `/api/kb/{id}/query` 500），
> 所以本轮对「疑似死代码」处理得格外保守：只删核查为**零引用**且**无副作用**的纯函数/未用异常类。

### C. 缺陷修复（2 处，**属行为变更**，已单独记录）

| 缺陷 | 修复前 | 修复后 | 影响面 |
|---|---|---|---|
| `hybrid/expr.py::eval_condition` | 函数 docstring 承诺「任何异常都按 False 处理」，实现却只 `except ExprError`。含 NUL 的表达式会让 `ast.parse` 抛 `ValueError`、超深嵌套会抛 `RecursionError`——二者**都会漏进编排主循环** | `safe_eval` 把 `ValueError`/`RecursionError` 收敛为 `ExprError`；`eval_condition` 兜 `Exception` | 此前会崩的输入现在退成「条件不成立」。**合法输入的行为一字未变**（用例逐条钉住） |
| `api/hybrid.py::upsert_rule` | 条件表达式只兜 `SyntaxError`；含 NUL 的条件会让 `ast.parse` 抛 `ValueError` → **500** | 同时兜 `ValueError` → **400**（「条件表达式语法错误」） | 非法条件从 500 变为语义正确的 400 |

> 修复方向按「条件不成立 ≠ 流程崩溃」与「用户写错 → 400」两项既有设计意图选定；
> 只影响**此前本就报错**的输入，任何正常配置的行为不变。

### D. 契约注释（消除「只能靠读代码猜」的隐含约定）

`hybrid/workflow.py::_exec_llm` 节点的产出**直接写 `ctx.shared[key]`**，而 `resume_value`
这类有界字面量走 `shared_set()`。这个差异此前没有任何说明，容易被后来者「统一」成
`shared_set()` 而引入 bug。已在三处补明文契约：

- `workflow.py::_exec_llm` docstring：说明产出不走 `shared_set()` 的两个原因
  （① 全文要被下游 `render_template` 逐字读取，落盘成指针会破坏渲染；② 命名空间校验会
  把 `plan`/`agent_result` 与 `node_*` 前缀判成冲突）；
- `context.py::shared_set` docstring：反向指出「节点产出刻意不走这里」；
- `agent_engine.py` 产出落库处：一句交叉引用。

## 四、优化前后可维护性对比

| 维度 | 治理前 | 治理后 | 说明 |
|---|---|---|---|
| **可读性** | 死代码与未来 API 混在一起，无法区分「在用」与「废弃」 | 扫描范围内无死符号 | 阅读时不再需要反复确认某个函数是否真的被调用 |
| **可测试性** | 条件求值的崩溃路径无法断言（异常会穿透） | 200 条用例，含 NUL / 超深嵌套 / 白名单拒绝 / delegate 契约 | 崩溃路径也进入用例覆盖 |
| **可扩展性** | 「节点的 shared 写入规则」是隐含约定 | 成文契约 + 交叉引用 | 后来者改 shared 写入时有据可依 |
| **性能** | 每条 SQL 前一次 `makedirs` 系统调用 | 去掉了 | 会话库是每请求多次命中的热路径 |
| **一致性** | 同一统计口径写两遍；同语义日界函数有两份 | 收敛为单点 | 避免「改一处漏一处」 |
| **历史保护** | —— | 8/10 脚本自检 + 200 用例与基线逐项对齐 | 后续改动有回归网兜底 |

## 五、后续代码规范建议（降债的根本手段）

1. **把死代码扫描接进 CI**。本轮用的 AST 脚本（几十行、无第三方依赖）可作为
   `scripts/` 常驻工具；对 `api/*` 的端点误报做白名单。**前置条件**是人工复核——
   历史上正好踩过「误删有调用方的函数」的坑。
2. **异常兜底要区分对待**。守卫型函数（如 `eval_condition`）应**写明并遵守**自己的异常契约，
   宽 `except Exception` 只在「该函数明确以 `False`/降级为返回值」时使用；反之，
   业务代码里不要用宽 `except` 静默吞掉异常。本次 `eval_condition` 的 bug 正是
   **注释承诺与实现不符**造成的——建议把「docstring 承诺的异常行为」也纳入 code review 检查项。
3. **DB 路径函数保持纯计算**。`_db_path()` 只返回路径，(建目录 / 建连接) 这类 IO
   放在 `_conn()` 里。规则简单、收益确定（每查询省一次系统调用），值得写进开发指南。
4. **「为将来预留」的 API 要么补一条测试、要么删掉**。无测试、无调用方的预留函数
   会随代码库膨胀而变成噪声；若确有前瞻价值，至少加一个最小用例把它钉住。
5. **命名以「能说清用途」为准**。如 `_out()` 这类过短名字可改为更语义化的
   `to_public()`（本轮未改，避免无谓 churn，列为建议）。
6. **给「隐含约定」补一条守卫测试**。例如「节点产出的 shared 内容不得被落盘成指针」，
   可加一条断言：构造一个 > `SHARED_MAX_VALUE_CHARS` 的 LLM 节点产出，断言下游模板仍渲染出全文。
