## 1. 审计方法

这批缺口不是靠"通读代码"找出来的，是靠**四种针对性扫描**。方法本身可复现，值得留档。

### 1.1 反向扫描：搜"应该存在但不存在的东西"

判断一个机制是否生效，最快的办法不是看它怎么写，而是搜它**是否被引用**。

```bash
# A1：全仓搜 finish_reason —— 零命中，说明截断从未被检测
grep -rn "finish_reason\|response_metadata" --include=*.py .
```

零命中比"写错了"更危险：写错了至少有人在看这段逻辑，零命中说明**这个念头从未进入过代码**。

### 1.2 口径扫描：同一件事搜出几种做法

```bash
# A2：时区有三种取法并存
grep -rn "localtime\|datetime.now()\|ZoneInfo" --include=*.py .
```

结果：`core/scheduler.py` 用 `ZoneInfo(config.SCHEDULER_TZ)`，`core/quota.py:103` 用 `time.localtime()`，`service/daily.py:152` 用 `time.localtime()`。**同一个"哪一天"的问题，三处两种答案。**

### 1.3 状态扫描：找进程内可变状态

```bash
# A3：找模块级 dict / set / list，逐个判断"多进程下还对不对"
grep -rn "^_[A-Z_]* *[:=].*\(dict\|{}\|set()\|\[\]\)" --include=*.py core/ kb/ api/
```

`quota._HITS` 是唯一一个**语义上要求全局一致、实际却是进程内**的状态。其余（检索缓存、BM25 索引、Agent 图缓存）都是"每个进程各自一份也不影响正确性"的加速结构——这两类必须区分开。

### 1.4 边界扫描：找"外部输入决定内部解释"的地方

A4 属于这类：`config.EMBEDDING_MODEL` 是一个环境变量，改它不需要改代码、不需要过评审，但它会让**库里所有向量的语义空间和查询向量的语义空间不再一致**。凡是"改一个 env 就让历史数据失去意义"的配置项，都必须有校验。

按这个标准又扫了一遍，除 `EMBEDDING_MODEL` 外还有 `CHUNK_SIZE`（改了只影响新片段，检索仍能工作，降级可接受，不修），`SCHEDULER_TZ`（A2 已覆盖）。

## 2. 八项逐项

### A1 输出截断检测

**缺陷机制**
`api/chat.py::_stream_llm` 只累加 `chunk.content`，从不读 `chunk.response_metadata`。而 OpenAI 兼容接口在触发 `max_tokens` 时，会在最后一个 chunk 的 `finish_reason` 里给 `"length"`。这个字段被完整地收到、完整地丢掉。

**影响面**
五条生成路径（vision / hybrid / agent / rag / llm）全部受影响。最坏情况：用户问"列出全部 12 条"，模型答到第 7 条被截断，界面显示完整结束，用户以为只有 7 条。

**为什么这是最贵的一类**
截断不是错误，是**不完整但形式合法**的输出。它不触发任何异常分支，不产生 5xx，日志干净，前端照常渲染。区别于"答错"——答错用户会怀疑并追问，截断用户不会。

**修复方案**
1. `_Acc` 增加 `finish_reason: str | None` 与 `truncated: bool`；
2. `_stream_llm` 每帧尝试从 `chunk.response_metadata` / `chunk.generation_info` 取 `finish_reason`，取到非空就覆盖（最后一帧才是终值）；
3. 流结束后若 `finish_reason in {"length", "max_tokens"}` → 置 `truncated`，并向 SSE 追加一帧 `event: truncation`，带 `{"reason": "length", "hint": "回答达到长度上限被截断，可要求继续"}`；
4. 消息落库时写 `messages.truncated=1`（见下）；
5. 计数器 `chat_truncated_total{path=...}` 自增。

**落库为什么值得加一列**
这是唯一能回答"我们有多少回答是残缺的"的数据。归到 `refs` 里会污染来源引用，另建表又不值得——加一个 `INTEGER NOT NULL DEFAULT 0` 列，成本一行迁移。

**回归风险**
`response_metadata` 在不同 provider 上位置不同（`AIMessageChunk.response_metadata` / `generation_info`）。取不到时**必须当作"未截断"**，绝不能因为读不到就报警——那会让所有正常回答被标截断，比不检测更糟。

**开关**：`TRUNCATION_DETECT_ENABLED`，默认 `1`。
**验收**：造一个只吐 `finish_reason="length"` 的假 LLM，断言 SSE 出现 `truncation` 帧、`add_message` 收到 `truncated=True`；再造一个没有 `response_metadata` 的假 LLM，断言**不**报警。

### A2 时区口径统一

**缺陷机制**
三处两套答案：

| 位置 | 取法 | 服务器 TZ=UTC 时的行为 |
|---|---|---|
| `core/scheduler.py::now_local` | `datetime.now(ZoneInfo("Asia/Shanghai"))` | 正确 |
| `core/quota.py:103 day_key` | `time.localtime()` | **偏移 8 小时** |
| `service/daily.py:152 active_hours` | `time.localtime()` | **偏移 8 小时** |

`service/daily.py::_day_bounds` 又是第三种：`time.mktime(time.strptime(...))`，本地时区解释 + `start + 86400` 硬加一天。

**后果的具体形状**
服务器 `TZ=UTC` 时，北京时间 10-21 07:00 的请求会落到 `day_key() == "2026-10-20"`。于是：每天的配额在北京时间 08:00 才重置（用户看到的是"我明明过零点了怎么还没恢复"），而每日总结按上海日历日切分数据、统计却按 UTC 日聚合——**报告里的数字和报告里的内容不是同一天的**。

**为什么现在没暴露**
服务器 TZ 恰好是 `Asia/Shanghai`，`localtime()` 与 `ZoneInfo("Asia/Shanghai")` 结果相同。这不是"没问题"，是"问题被部署环境掩盖了"。

**修复方案**
新增 `core/timeutil.py` 作为**唯一时区入口**，导出 `TZ` / `now_local()` / `now_ts()` / `today()` / `day_str(ts)` / `hour_of(ts)` / `day_bounds(date)`。`core/scheduler.py` 改为从这里导入（保留原公开名，不动调用方）；`core/quota.py::day_key` 与 `service/daily.py` 全部改走它。

`day_bounds` 用 `datetime(..., tzinfo=TZ) + timedelta(days=1)` 而非 `+86400`：亚洲无夏令时所以当前等价，但 `+86400` 是错的写法，遇到有夏令时的时区会少/多一小时。

**回归风险**
`quota.day_key` 的返回值在 TZ 正确时**完全不变**，所以历史 `usage` 表数据不需要迁移。若服务器 TZ 不是上海，切换后会出现一次"跨日跳变"——这是修复本身，但运维要知道。

**开关**：`TZ_STRICT`，默认 `1`；置 0 退回 `localtime()` 旧行为（用于紧急回退）。
**验收**：把 `TZ` 环境变量设成 `UTC`，断言 `day_str(北京 07:00 的 ts)` 仍是当天上海日期；再断言 `day_bounds(d)` 的跨度恰好是 86400 且端点是上海零点。

### A3 quota 多 worker 双层限流

**缺陷机制**
`quota._HITS` 是模块级 `dict[str, list[float]]`。`uvicorn --workers 4` 会 fork 出 4 个进程，各自持有一份 `_HITS`。`RATE_PER_MINUTE=10` 的实际放行量是 **40/min**。

**为什么必须在这次修**
`--workers 4` 正是压测报告给出的 P0 建议。也就是说：**修 A3 是启用多 worker 的前置条件**。不修，第一个 P0 优化会静默拆掉一道护栏。

**修复方案（双层）**
- **快路径（不变）**：进程内滑窗做主判据。未超限 → 直接放行，**零额外 DB 操作**，单进程性能与现在完全一致。
- **确认路径（新增）**：进程内已超限时才查落库计数——如果全局限额还有余量（说明是别的 worker 在放行、本进程窗口恰好满了），放行并记录；否则抛 `RateLimited`。
- **汇总**：放行后异步把命中写进 `rate_hits(user_id, ts)` 表，供确认路径统计。

关键设计：**快路径不查库**。若每个请求都查库，限流自己就成了写入热点（卷七的结论），为了修一个多进程问题引入一个单点瓶颈，是负收益。

**残余语义**
双层方案给出的是"约 N+ε"而不是严格 N：确认路径的统计窗口有毫秒级延迟。这是**刻意的取舍**——严格限流需要 Redis 或 DB 原子计数，两者都比这个方案贵。报告如实标注：**这是护栏，不是闸门。**

**回归风险**
单 worker 下确认路径几乎永不触发（只有进程内满额时才查），行为与现在一致。
死锁风险：确认路径查库时不能再持有 `_lock`，必须先把需要的数据取出来再释放。这一点用测试锁住。

**开关**：`RATE_LIMIT_SHARED`，默认 `1`。置 0 严格退回进程内单层（当前行为）。
**验收**：用两个独立进程模拟双 worker，各发 10 次，断言总放行量 < 20；断言单 worker 路径零 DB 读写（打桩计数）。

### A4 embedding 模型一致性校验

**缺陷机制**
`config.EMBEDDING_MODEL` 默认 `text-embedding-v3`。改这个环境变量不需要改一行代码，但库里所有既有向量是用旧模型算的。新查询向量在**另一个语义空间**里——余弦相似度在数学上仍然算得出来（维度通常相同），只是**数值不再可比**。

**为什么比报错更糟**
它不报错。`text-embedding-v3` 和 `text-embedding-v2` 都是 1024 维，`_to_similarity` 照常换算，阈值判断照常执行，检索照常返回 top_k 条——只是排序接近随机。用户看到的是"它开始答非所问了"。

**修复方案**
新增 `core/embed_guard.py`：

- `fingerprint()` → `{"model": EMBEDDING_MODEL, "base": 主机名, "dim": 维度}`
- `stamp(collection)` → 把指纹（JSON 字符串）写进 Chroma collection 的 metadata
- `check(collection)` → 读指纹比对，不一致抛 `EmbeddingMismatch`（**可读中文错误，不是降级**）

挂载点：写入路径（`add_chunks` / `build_index`）末尾 stamp；检索路径（`retrieve_with_score`）入口 check。
`check` 结果按 collection 缓存（一个进程内只校验一次），写入时失效缓存。

**为什么"报错"而不是"降级"**
降级（比如"检测到不一致，自动全量重建"）会触发一次未预期的批量 embedding 计费，这是账单事故。而且重建会丢掉原库，用户没有撤销手段。**这里正确的失败方式是拒绝服务并说清原因**——符合卷十二定律 1「失败时不产生不可恢复的后果」。

**回归风险**
Chroma 的 `collection.modify(metadata=...)` 在 0.5.23 可用；若 metadata 里已有 HNSW 相关键，合并写入而不是覆盖。已存在的库没有指纹 → 视为"未知"，**不报错**（首次检索时补写指纹），否则所有现网库会在升级后立刻不可用。

**开关**：`EMBED_GUARD_ENABLED`，默认 `1`。
**验收**：建库 → 改 `EMBEDDING_MODEL` → 断言检索抛 `EmbeddingMismatch` 且错误信息含两个模型名；断言无指纹的老库不报错且被补写指纹。

### A5 可观测性埋点

**缺陷机制**
现有信号只有 `/health` 的 ok 和 `probe-health.sh` 的心跳三态。能回答"活没活"，回答不了：
- 检索的 top1 相似度分布是什么？（→ `RETRIEVE_LOW_SIM=0.45` 到底卡掉多少？）
- 闸门拦截了多少次？（→ `RETRIEVE_MIN_SIM=0.25` 是不是太狠？）
- 有多少回答被截断？（→ A1 的量化面）
- 有多少 SSE 客户端中途走了？

**为什么这是"零成本但一直没做"**
写埋点不需要新依赖、不需要改架构，只需要在建指标的时候顺手 `+1`。卷十二 §12.7 把这条列为"最可惜的缺失"：**七个检索参数至今没有一个是靠数据定的。**

**修复方案**
新增 `core/metrics.py`：纯标准库，进程内计数器 + 直方图，`threading.Lock` 保护，无外部依赖。

- `inc(name, labels=None, n=1)`
- `observe(name, value, labels=None)`（直方图，桶由注册时给定）
- `snapshot()` → 结构化 dict
- `render_prometheus()` → Prometheus 文本格式（`# TYPE` / `# HELP` 齐全）

新增 `api/metrics.py`：`GET /api/metrics`，**仅允许管理员或回环来源**，返回 `text/plain; version=0.0.4`。
同时 `probe-health.sh` 增加一步：把 `/api/metrics` 里的关键项写进 textfile，让 Prometheus 能采到（不用应用侧加导出器）。

埋点清单（8 项）：
`retrieval_top1_similarity`（直方图 0.1~0.9）、`retrieval_grounding_total{level}`、`retrieval_gate_blocked_total`、`retrieval_cache_total{kind="hit|neg"}`、`chat_truncated_total{path}`、`chat_client_disconnect_total`、`llm_error_total{class}`、`quota_rejected_total{kind}`

**回归风险**
指标写入在热路径上，必须廉价：计数器就是 `dict` 自增 + 一把锁。锁竞争风险实测：每次操作 ~0.5μs，相对一次 LLM 调用（百毫秒级）完全可忽略。但**不要**在 `_stream_llm` 的每帧里写指标——只在收尾写一次。

**开关**：`METRICS_ENABLED`，默认 `1`；端点另有权限门（不是靠开关保护）。
**验收**：打桩制造一次低相似度检索 + 一次截断，断言 `/api/metrics` 文本里出现对应行且数值正确；断言非管理员访问返回 403。

### A6 `to_thread` 裸调

**缺陷机制**
`api/chat.py:973` 在 async 生成器里直接调同步 SQL（项目规则要求一律 `asyncio.to_thread`）。2ms 的阻塞在单请求下无害，但在事件循环上是**串行**的：并发 200 时，这条路径会变成主循环上的一颗小石子。

**修复方案**：改成 `await asyncio.to_thread(...)`。一行。
**回归风险**：`to_thread` 会切换线程，`contextvars` 的传播在 3.9+ 是自动的，但**如果被调函数依赖 `threading.local()` 连接**（`core/session.py::_get_conn` 正是），换线程等于换连接——这是正确行为（连接本就该按线程走），但会让"同一请求复用同一连接"的假设失效。已确认调用点不依赖该假设。
**验收**：静态检查——新增一条测试扫描 `api/chat.py` 中 `store.` 同步调用是否都包在 `to_thread` / 非 async 上下文里。

### A7 JWT `header` 校验

**必须先说清楚的话**
当前实现**不可利用**。`decode_claims` 的验签是硬编码 `hmac.new(secret, ..., sha256)`，不读 `header.alg`，所以经典的 `alg: none` / `HS256→RS256` 混淆打不进来。

**那还修什么**
修的是**未来迁移路径**。文件顶部注释写着"将来想换随时能换（PyJWT）"。PyJWT 的行为是**按 `header.alg` 分派算法**——迁移那天，如果不校验 `alg`，历史注释里的宽松会直接变成漏洞。这是典型的"当前安全、迁移不安全"，而迁移恰恰是最容易漏测的时刻。

**修复方案**：解码 header（base64 + JSON），校验 `alg == "HS256"` 且 `typ`（缺省允许）为 `JWT`；失败返回 None（对外仍是统一 401）。
**回归风险**：老令牌的 header 就是 `{"alg":"HS256","typ":"JWT"}`（本模块自己签的），全部兼容。**唯一的破坏面**：外部手工构造的令牌若省略 `typ`，需要放行——所以 `typ` 缺失时允许，存在时必须是 `JWT`。
**验收**：构造 `alg=none` / `alg=RS256` / `typ=xxx` 三种令牌，断言全部被拒；构造正常令牌，断言通过。

### A8 `TOOL_PLAYBOOK` 填充

**缺陷机制**
`core/tool_registry.py` 有 `assert_playbook_complete()`，但 `TOOL_PLAYBOOK` 是空字典——校验函数对一个空集合做全称判断，**恒为真**。这是"校验存在但校验不到东西"。

**修复方案**：为五个工具各写 playbook（何时用 / 何时不用 / 参数怎么填 / 失败怎么办），让 `assert_playbook_complete()` 真正有约束对象。playbook 同时会被 `build_guarded_tools` 之外的工具描述层消费（`discover` 已暴露字段）。
**回归风险**：`assert_playbook_complete()` 在 import 时执行。**若某个工具漏写 playbook，进程直接起不来**——这是刻意的（卷六的结论：宁可起不来也不要静默缺一层）。所以本次必须五个全写，不能写四个。
**验收**：`test_tool_registry.py` 增加一条断言：`set(TOOL_PLAYBOOK) == set(TOOL_META)`，且每个 playbook 四个字段非空。

`tools/audit_e2e.py`：起真 uvicorn（子进程），真打 SSE，验证**接线**而非**函数**。

**实测**：**18/18**。过程中真抓出三个"单测全绿但接线是断的"的问题：

| 现象 | 根因 | 修法 |
|---|---|---|
| `/api/metrics` 带正确 token 仍 401 | 端点用了 `Depends(get_current_user)`，采集器无 Cookie → 依赖先 401，token 这条路**永远走不到** | 移除依赖，认证下移到 `_authorized()`，用户身份改由 `_uid_of()` 尽力取 |
| `chat_total` 始终不涨 | 同上（拿不到指标就看不到计数） | 同上；另修脚本侧一处：该计数器声明名就叫 `chat_total`，渲染器不会二次追加 `_total`，脚本原先找 `chat_total_total` 永远为 0 |
| 日志里 `Task exception was never retrieved` | `_generate_title` 里 `get_llm()` 在 try **外面**，无 Key 时抛在协程里没人接 | 移进 try，`except` 记 `llm_error{class="title"}` |

第三条尤其值得留档：**它由"服务端日志必须干净"这一条断言抓出来，任何一层单测都覆盖不到**——后台任务的异常不会让请求失败，只在日志里留痕。

### 层 4 量化评估集
`tools/eval_retrieval.py` + `tools/eval_corpus/`：3 篇中文文档 + 16 道题（12 道有期望来源、4 道离题）。
输出：`recall@1/3/5`、`MRR`、top1 相似度分布、闸门强度分布、离题示弱率、可分性 AUC。

**实测（假向量）**：

| 指标 | 值 |
|---|---|
| 剔除字面盲区题后 recall@1/3/5 | 1.0 / 1.0 / 1.0（MRR 1.0） |
| 全量 recall@1/3/5 | 0.75 / 0.75 / 0.75（MRR 0.75） |
| 离题题被判 weak 的比例 | 1.0（4/4） |
| 相关/离题可分性 AUC | 0.90（公平口径）/ 0.79（全量） |
| top1 相似度 | 相关题均值 0.144，离题题均值 0.082 |

**必须诚实标注的局限**：无 `.env` 时用**确定性假 embedding**（字符 n-gram 的 TF-IDF 哈希向量，文档侧做主题词稀疏化）。此时评估的不是向量质量，而是**管道口径与排序逻辑**——距离换算、离群过滤、MMR、RRF、阈值判定这些环节在假向量下同样被完整走过。配了 `EMBEDDING_API_KEY` 时脚本自动切真模型，同一套语料与问题集可拿到可比对的真值；`--fake` 可强制假向量。两套数字的**绝对值**不能互相比较，**AUC 可以**（它只比排序）。

**为什么必须区分"字面盲区题"**：16 道题里有 7 道与期望文档几乎无共有 n-gram（例如"备案还没下来的时候怎么先让服务能被访问"→ 文档里写的是"cloudflared 出站隧道"）。字面模型给它们低分是**字面模型的正确行为**，不是管道缺陷。把它们混进召回率会把一个已知的基线天花板误报成回归，所以指标分两栏列。

## 6. 量化评估跑出来的意外发现：检索阈值是「未标定的跨模型参数」

这一节不在原计划里，是层 4 第一次跑出来的数字逼出来的结论。

### 6.1 现象

层 4 首轮（等权哈希假向量）跑完，14 道题**无一例外**判 `low`。
第一反应是"假向量太弱"，于是加了 IDF 与主题词稀疏化，把相似度尺度抬进工作区间。
结果更耐人寻味：

> **召回完全正确（剔除盲区后 recall@1 = 1.0、MRR = 1.0），
> 但相关题被判 weak 的比例仍然是 100%。**

也就是说：**系统找到了正确答案，却告诉用户"没找到依据"。**

### 6.2 机制

`RETRIEVE_MIN_SIM = 0.25` / `RETRIEVE_LOW_SIM = 0.45` 这两个数字不是从数据里标定出来的，
是当初凭直觉写进 `core/config.py` 的常量。而**相似度的绝对值完全由 embedding 模型决定**——
同一个检索管道，换一个向量化模型，top1 相似度的整体分布会平移一大截：

| embedding | 相关题 top1 典型值 | 0.25 这条线意味着什么 |
|---|---|---|
| 字面向量（本轮实测） | 0.06 ~ 0.29 | 几乎所有题都在线下 → **一律示弱** |
| 真实语义模型（待实测） | 通常 0.4 ~ 0.8 | 大多数题在线上 → 正常作答（前提是模型没换错） |

阈值是**跨模型的**常量，相似度是**模型内**的量。两者之间没有任何标定记录把它们对齐。

### 6.3 这为什么属于 A1~A4 那一类

它完美符合「未标定边界的决策」的全部特征：

- 代码不报错、测试不失败、日志无异常；
- 结果已经错了——用户看到的是"知识库里没有相关资料"，而答案其实就在库里；
- 不会在代码评审里暴露，只会在**某次配置变更或模型升级之后**突然变成事故。

而且它和 A4（换 embedding 模型不校验）是**同一条链上的两段**：
A4 修的是"换了模型要拒绝"，这一条是"换了模型之后阈值也要重新标定"。
A4 拦住了最坏情况（检索退化成噪声），但拦不住"模型换了、阈值没跟着动"这种**部分失效**——
后者更隐蔽，因为检索其实还是好的。

### 6.4 建议（本次**不做**，属演进议题）

1. 把 `RETRIEVE_MIN_SIM` / `RETRIEVE_LOW_SIM` 的标定值记进 `部署说明.md`，写明**它是针对哪个 embedding 模型**标定的；
2. 换 `EMBEDDING_MODEL` 的操作手册里加一步：跑 `tools/eval_retrieval.py`，用**真模型**重跑这套语料，按新的 top1 分布重定阈值；
3. 中期：让 `assess_grounding` 支持"相对于本批候选的分布"判定（例如 top1 与第 2 名的差距），
   补上一个与模型绝对尺度无关的判据——本轮的可分性 AUC 就是这个方向的雏形。

这三条都要动操作手册与判定逻辑，超出"修复"范围，所以单列一节不做，只留结论与证据。
