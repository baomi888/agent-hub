## 1. 先建立直觉：这个模块防的三个事故

### 事故 A：worker 悄悄死了，没人发现

部署时把后端 `uvicorn` 起好了，页面能开、能聊天，一切看起来正常。但负责"发每日委托、生成每日总结"的是一个**独立进程**，它不监听任何端口。

它挂掉时：

- 页面上没有任何红点；
- 用户不会报错，只会觉得"今天怎么没收到早报"；
- 你去看后端日志，一切正常。

这就是"无端口进程"的经典故障：**不可见**。模块 2 的答案有两层：

1. 进程层：systemd `Restart=always`，挂了 10 秒内拉起来；
2. 业务层：worker 每分钟写一次心跳到 `worker_heartbeat`，Web 端 `GET /api/schedule/health` 读心跳年龄，超过 300 秒判 `stalled`、超过 600 秒判 `down`。

关键点：**判据是"多久没心跳"，不是"进程在不在"**。进程在但卡死（比如卡在一次 LLM 调用上）同样会被抓到。

### 事故 B：同一封早报发了两遍

APScheduler 在 worker 重启、或者运维手滑起了两个 worker 时，同一分钟的 cron 可能被触发两次；`run-now` 手动触发也可能和定时触发撞上。

如果没有幂等，用户会在 7:00 收到两条一模一样的早报；如果这条早报还带扣费（LLM + 推送），就是重复烧钱。

模块 2 的答案：`job_runs` 表上有 `UNIQUE(idem_key)`，幂等键是 `job_key|subject_id|planned_at`。插入时 `ON CONFLICT DO NOTHING`，第二次插入直接"没插进去"，于是**同一对象、同一计划时刻，只可能有一行**。

### 事故 C：失败后无限重试，或者一次失败就永久放弃

LLM 超时是临时故障，应该重试；"会话已删除"是确定性故障，重试一万次也一样。如果两者都用同一套策略：

- 全重试 → 确定性故障每次都烧一遍钱；
- 全不重试 → 一次网络抖动就让今天的总结永久缺失。

模块 2 的答案：`classify_error` 把失败分成 `retry` / `fatal` / `quota` 三类，分别对应"指数退避重试""立即停""延后到明天同刻"。

## 2. LangChain 零基础补丁

先给结论：**本模块是四个模块里 LangChain 用量最少的**。调度本身和 LangChain 没有关系，LangChain 只出现在"任务真正执行业务"的那一小段（生成每日总结时调用一次模型）。

### 2.1 这里用到的三个概念

**（1）`BaseChatModel` / `ChatOpenAI`**

白话：一个"聊天模型的统一接口"。你给它一组消息，它回一条消息。不同厂商（OpenAI、DeepSeek、通义）都有自己的实现，但对外都长成 `.invoke(messages)` 这个样子。

本项目在 [core/llm.py#L35-58](file:///c:/biancheng/agent-hub/core/llm.py#L35-L58) 里用 `ChatOpenAI` 连 DeepSeek（DeepSeek 提供 OpenAI 兼容接口），并按 `(temperature, max_tokens, timeout)` 缓存客户端实例。调度任务通过 `get_llm()` 拿到它。

**（2）消息类型 `SystemMessage` / `HumanMessage`**

白话：聊天模型吃的不是一段字符串，而是"带角色的消息数组"。`SystemMessage` 是"你是谁、必须遵守什么"，`HumanMessage` 是"用户说了什么"。

`service/daily.py` 的 [_call_llm](file:///c:/biancheng/agent-hub/service/daily.py#L280-L292) 就是：

```python
# service/daily.py
resp = llm.invoke([SystemMessage(content=_SYS_SUMMARY), HumanMessage(content=prompt)])
```

这里没有 Agent、没有工具、没有流式，就是一次最朴素的"给系统提示 + 给任务文本 → 拿回 JSON"。

**（3）`Runnable`**

白话：LangChain 里"可以被调用/流式/批处理的东西"的统称。`ChatOpenAI` 是 Runnable，`prompt | model` 拼起来的链也是 Runnable。它提供 `.invoke()`、`.stream()`、`.batch()` 等统一入口。

本模块只用到 `.invoke()`。你会在模块 4 看到 `.astream()` 和 `astream_events`，那是 Agent 场景才需要的。

### 2.2 本模块**没用**的 LangChain 能力，以及为什么

| 能力 | 本模块用了吗 | 为什么 |
|---|---|---|
| `create_agent` / LangGraph | 没用 | 定时任务是"固定步骤 + 一次模型调用"，不需要自主决策 |
| `Tool` / `StructuredTool` | 没用 | 任务不调用工具；它读的是数据库 |
| `Checkpointer` | 没用 | 任务状态在 `job_runs` 表里，不需要 LangGraph 的检查点 |
| `init_chat_model` | 没用 | 原因见模块 4；本模块只是继承了这个决定 |
| 流式 `astream` | 没用 | 每日总结是一次性产出，不需要边生成边推 |

一句话：**LangChain 在这里只是一个"模型客户端库"，不是一个"编排框架"**。真正的编排（谁先跑、失败怎么办、跑几次）全部由 `core/scheduler.py` 的 SQL 决定。

这其实是本项目的核心取舍：**能用数据库表达的状态，就不放进框架内存**。因为调度最怕的是"进程重启后状态没了"，而 SQLite 恰好能扛住这件事。

## 3. 核心代码逐段吃透

### 3.1 三张表：调度底座的"事实来源"

见 [core/scheduler.py#L125-175](file:///c:/biancheng/agent-hub/core/scheduler.py#L125-L175)。

```sql
-- core/scheduler.py（节选）
CREATE TABLE IF NOT EXISTS schedule_jobs (      -- 任务定义
    job_key TEXT PRIMARY KEY,
    cron TEXT NOT NULL,
    tz TEXT NOT NULL DEFAULT 'Asia/Shanghai',
    enabled INTEGER NOT NULL DEFAULT 1,
    next_run_at INTEGER
);

CREATE TABLE IF NOT EXISTS job_runs (           -- 每次执行的账本
    run_id TEXT PRIMARY KEY,
    job_key TEXT NOT NULL,
    subject_id TEXT NOT NULL,   -- delegation_id 或 date
    planned_at INTEGER NOT NULL,
    idem_key TEXT NOT NULL,     -- job_key|subject_id|planned_at
    status TEXT NOT NULL,       -- pending/running/succeeded/failed/skipped
    attempts INTEGER NOT NULL DEFAULT 0,
    next_attempt_at INTEGER,    -- 只对 failed 有意义
    trigger TEXT NOT NULL DEFAULT 'schedule'
);
CREATE UNIQUE INDEX ux_job_runs_idem ON job_runs(idem_key);

CREATE TABLE IF NOT EXISTS worker_heartbeat (   -- 只有一行，id=1
    id INTEGER PRIMARY KEY CHECK (id = 1),
    ts INTEGER NOT NULL,
    pid INTEGER,
    version TEXT
);
```

**在干什么**：把"有哪些任务"（定义）、"每次跑得怎么样"（账本）、"worker 还活着吗"（心跳）拆成三张表。

**为什么这样写**：

- 定义和账本分离，才能做到"运维改 cron 只改表，不改代码"。`job_defs()` 只提供默认值，`ensure_tables()` 用 `ON CONFLICT DO NOTHING` 补齐，**已有行不会被覆盖**（[core/scheduler.py#L220-241](file:///c:/biancheng/agent-hub/core/scheduler.py#L220-L241)）。这就是"周期改这张表，不改代码"的实现。
- 心跳单独一张表、只有一行（`CHECK (id = 1)`），是为了让健康检查变成一次极轻的读：`SELECT ts FROM worker_heartbeat WHERE id=1`。如果混进 `job_runs`，每次心跳都会长出一行，90 天后要清理表，健康检查还要做聚合。

**换个写法会怎样**：

- 如果把任务定义写死在 Python 里：每次调 cron 都要发版，运维无法热改。
- 如果心跳也写进 `job_runs`：心跳是每分钟一次、98% 的无意义行，会把执行账本污染成"心跳流水"，`/runs` 翻页全是噪声。
- 如果把三张表合成一张：定义行和执行行混在一起，"某任务最近执行情况"要在一堆执行行里反查定义，查询复杂度和出错面都上升。

**这一段为什么这么写（图 4 圈到的 systemd）**

[systemd/agent-hub-worker.service](file:///c:/biancheng/agent-hub/systemd/agent-hub-worker.service) 里两条关键配置：

```ini
ExecStart=__APP_DIR__/venv/bin/python -m worker.scheduler
Restart=always
RestartSec=10
```

- `python -m worker.scheduler` 而不是 `uvicorn`：这个进程不服务 HTTP，它只跑调度循环。用 `-m` 是为了让 `worker` 成为一个包、支持相对导入，且 `sys.path` 从项目根开始，和 `uvicorn main:app` 的口径一致。
- 不写 `Port` / 不配 `--port`：**它本来就不该有端口**。无端口进程挂了最难发现，所以 `Restart=always` 是必需的补偿，而不是"顺手加上"。
- `RestartSec=10` 比后端（5 秒）长：worker 启动会初始化数据库、加载 handler，重启太频繁反而会在"坏配置"上形成重启风暴。
- backend unit 的注释里明说"不配 `EnvironmentFile`"，因为 `core/config.py` 自己 `load_dotenv`，让 systemd 解析带中文/引号的 `.env` 容易导致起不来。这是**配置入口只留一个**的取舍。

### 3.2 幂等键：为什么必须是 `job_key|subject_id|planned_at`

见 [core/scheduler.py#L257-263](file:///c:/biancheng/agent-hub/core/scheduler.py#L257-L263)。

```python
def idem_key(job_key: str, subject_id: str, planned_at: int) -> str:
    return f"{job_key}|{subject_id}|{int(planned_at)}"
```

**在干什么**：给"这一次投递"生成一个稳定指纹。

**为什么这样写**：三个维度各回答一个问题。

| 维度 | 回答的问题 | 少了它会怎样 |
|---|---|---|
| `job_key` | 是哪类任务 | 早报和午报会互相顶掉 |
| `subject_id` | 是给谁/哪一天 | A 用户的早报会让 B 用户的早报插不进去（全表只剩一行） |
| `planned_at` | 是哪一次计划 | 今天的早报和明天的早报会被当成同一次，明天永远发不出去 |

**换个写法会怎样**：如果用 `run_id`（每次执行随机生成）做幂等键，那它根本不叫幂等——每次重试都是新 run_id，约束永远不触发，重复投递照样发生。这正是 [core/scheduler.py#L479-481](file:///c:/biancheng/agent-hub/core/scheduler.py#L479-L481) 注释强调的："重试如果新插一行会直接撞约束——这也是为什么幂等键里必须有 planned_at 而不是 run_id。"

**落库动作**在 [core/scheduler.py#L343-362](file:///c:/biancheng/agent-hub/core/scheduler.py#L343-L362)：

```sql
INSERT INTO job_runs (...) VALUES (...)
ON CONFLICT(idem_key) DO NOTHING
```

`cur.rowcount` 为 0 就说明"已经有人排过这一条了"，`enqueue_job` 返回 `(None, key)`，调用方据此判断"这次没排进去"。

> **审查视角**：`ON CONFLICT DO NOTHING` 不会告诉你"冲突的是哪一行"。如果你需要区分"重复"与"真失败"，得在冲突后回查 `idem_key`。当前代码不需要这个区分，所以没做——这不是缺陷，是需求边界。

### 3.3 领任务：为什么"先 SELECT 再 UPDATE"是安全的

见 [core/scheduler.py#L365-394](file:///c:/biancheng/agent-hub/core/scheduler.py#L365-L394)。

```sql
UPDATE job_runs
SET status = 'running', attempts = attempts + 1, started_at = ?
WHERE run_id IN (
    SELECT run_id FROM job_runs
    WHERE status = 'pending'
    ORDER BY planned_at ASC
    LIMIT ?
)
AND status = 'pending'
RETURNING *;
```

**在干什么**：一次性把最多 N 条 `pending` 行原子地翻成 `running`，并把新行返回。

**为什么这样写**：

- 外层 `AND status = 'pending'` 是 **CAS**（Compare-And-Swap，比较并交换）：先读到的状态是 `pending`，写回时再确认一次它仍然是 `pending`。如果另一个 worker 已经把它改成了 `running`，这次的 `WHERE` 就不匹配，`rowcount` 为 0。
- 内层子查询负责"挑哪几条"，外层负责"只有还处于 pending 的才能被领走"。两层合起来，两个 worker 同时领同一条时**只有一个能成功**。
- `RETURNING *` 让"改完再查"合并成一次往返。没有它，就要 `UPDATE` 完再 `SELECT`，中间存在窗口（虽然同事务内问题不大，但多一次 IO、多一段代码）。
- `ORDER BY planned_at ASC` 保证积压时先跑最老的，不会出现"新任务一直插队、老任务饿死"。

**换个写法会怎样**：

最典型的错误写法是：

```python
rows = conn.execute("SELECT * FROM job_runs WHERE status='pending' LIMIT ?").fetchall()
for r in rows:
    conn.execute("UPDATE job_runs SET status='running' WHERE run_id=?", (r["run_id"],))
```

两个 worker 会同时 `SELECT` 到同一条，然后各自 `UPDATE` 成功——**同一条任务被执行两次**。这就是"检查后使用"（check-then-act）竞态。修法只有两种：把判断并进 `UPDATE ... WHERE status='pending'`（本项目做法），或者上 `SELECT ... FOR UPDATE`（SQLite 没有行锁，做不到）。

**这一段为什么这么写（图 4 圈到的"进程编排"）**

图 4 圈的是 backend / frontend / worker 三份 unit、重启策略、环境变量、日志。它们共同回答"三个进程各自是什么角色"：

| unit | 角色 | 端口 | 重启策略 |
|---|---|---|---|
| backend | FastAPI/uvicorn，对外 HTTP + SSE | 8000 | `Restart=always`，`RestartSec=5` |
| frontend | Next.js | 3000 | `Restart=always` |
| worker | 调度循环 | **无** | `Restart=always`，`RestartSec=10` |

后端 unit 里有一条容易读错的注释：

```
# 多进程下进程内状态各存一份：每分钟限流强度变为 N 倍、
# LLM 并发闸全局上限 = N × LLM_MAX_CONCURRENCY
```

它的意思是：`--workers N` 时，限流器、LLM 并发闸这些**进程内**状态会变成 N 份，实际总上限是 N 倍。所以生产默认 `WORKERS=1`，要扩容得先接受这个事实，或者把状态外置（Redis）。这不是"配置项"，是**架构约束**。

### 3.4 worker 主循环：先心跳，再干活

见 [worker/scheduler.py#L339-359](file:///c:/biancheng/agent-hub/worker/scheduler.py#L339-L359)。

```python
def _tick(job_key: str) -> None:
    _beat()                       # 1. 先写心跳
    run_pending()                 # 2. 领手动触发（pending）
    _run_job(job_key, planned_at) # 3. 跑本轮 cron 对应的任务
    run_retries()                 # 4. 跑到点的重试
    if job_key == "housekeeping":
        run_housekeeping()        # 5. 顺手清理
    _sync_next_run()              # 6. 回写 next_run_at
```

**在干什么**：这是每个 cron tick 的固定顺序。

**为什么这样写**：

- **心跳在最前**：哪怕后面的任务卡住，心跳也已经刷新了。反过来说，如果心跳在最后，任务一卡，健康检查立刻误报 `down`——你会收到"worker 挂了"的告警，但其实它只是在跑一个慢任务。这个顺序决定了**告警语义是"循环停了"还是"任务慢了"**。
- **`run_pending` 在 `_run_job` 前**：手动触发的优先级高于定时。用户点了"立即运行"，不应该排在下一个 cron 后面。
- **`run_retries` 在 `_run_job` 后**：先把本轮新任务跑掉，再处理历史欠账。
- **`_sync_next_run` 在最后**：把 APScheduler 算出的下次触发时间写回表，前端 `/jobs` 才看得到。

**这里有一个真实踩坑**：[worker/scheduler.py#L361-381](file:///c:/biancheng/agent-hub/worker/scheduler.py#L361-L381) 的 `_sync_next_run` 里用了

```python
nrt = getattr(job, "next_run_time", None)
```

而不是 `job.next_run_time`。原因是：APScheduler 在 `scheduler.start()` 之前，job 对象的 `next_run_time` 属性**还不存在**（pending job 还没被调度器赋时间），直接访问会 `AttributeError`，整个 `_sync_next_run` 炸掉。`getattr(..., None)` 是在"属性可能不存在"这个边界上做的防御，不是风格问题。

### 3.5 心跳三态：`up` / `stalled` / `down`

见 [core/scheduler.py#L749-790](file:///c:/biancheng/agent-hub/core/scheduler.py#L749-L790)。

```python
age = heartbeat_age(now=now)
if age is None or age > threshold:      # threshold 默认 600
    status = "down"
elif age > HEARTBEAT_STALL_SECONDS:     # 300
    status = "stalled"
else:
    status = "up"
```

**在干什么**：把"多久没心跳"映射成三个状态。

**为什么是三个而不是两个**：

- `stalled`（>300 秒，约一个 dispatch 周期）：黄灯。意思是"它可能只是慢，也可能刚开始卡"，此时**先给人看，不急着自动重启**。
- `down`（>600 秒）：红灯。两个 dispatch 周期都没心跳，基本可以判定进程或循环已经停了。

**为什么用"年龄"而不是"进程表"**：

- 进程在 ≠ 循环在。一次 LLM 调用卡 10 分钟，进程活着，任务全停。
- 反过来，进程刚被 systemd 拉起、还没写第一次心跳时，进程表显示"在"，但 `heartbeat_age()` 返回 `None`，代码判 `down`——这是一个**刻意的误报**：宁可刚启动时短暂红一下，也不要让"从没心跳过"被当成健康。

> **审查视角**：`age is None` 判 down，意味着 worker 首次部署、还没写心跳的几秒内，`/health` 会返回 `down`。如果你的监控按"down 就告警"，会在每次部署时收到一条噪音。正确做法是给部署留一个启动宽限期，或者接受这条噪音。这是**已知的语义边角**，不是 bug。

### 3.6 错误分级：`retry` / `fatal` / `quota`

见 [core/scheduler.py#L414-459](file:///c:/biancheng/agent-hub/core/scheduler.py#L414-L459) 与 [core/scheduler.py#L461-515](file:///c:/biancheng/agent-hub/core/scheduler.py#L461-L515)。

**优先级顺序**（这是审查时最该看的一点）：

1. **异常类型**优先：`TimeoutError` / `ConnectionError` → `retry`；`PermissionError` → `fatal`。
2. 其次 **HTTP 状态码**：401/402 → `fatal`；429/5xx → `retry`。
3. 再次 **文案关键词**：`timeout`、`超时`、`连接`、`429`、`500`… → `retry`；`会话不存在`、`库不存在`… → `fatal`。
4. 都判不出 → **按 `fatal`**。

**为什么判不出就 fatal**：这是"默认保守"的选择。把未知错误当成可重试，会在一个坏配置上无限重试（每次重试都烧 token、写日志、可能重复打扰用户）；当成 fatal，最坏结果是"少重试一次，人工介入"。**在调度系统里，少跑一次比跑错一百次便宜。**

**重试策略**：

```python
MAX_ATTEMPTS = 3
BACKOFF_MINUTES = (1, 5, 15)

def _backoff_target(attempts: int, finished_at: int) -> int | None:
    if attempts >= MAX_ATTEMPTS:
        return None
    idx = max(0, min(int(attempts) - 1, len(BACKOFF_MINUTES) - 1))
    return int(finished_at) + BACKOFF_MINUTES[idx] * 60
```

- 第 1 次失败 → +1 分钟；第 2 次 → +5；第 3 次 → +15；第 4 次不再排。
- 用 `min(...)` 夹住索引，是为了"配置里多加了退避档位"时不越界。
- **重试不改行，只改 `status` 和 `next_attempt_at`**。这是幂等键设计的直接结果：同一 `(job_key, subject_id, planned_at)` 只允许一行，所以重试必须复用原行（[core/scheduler.py#L479-481](file:///c:/biancheng/agent-hub/core/scheduler.py#L479-L481)）。

**配额触顶特殊处理**：

```python
if cls == CLASS_QUOTA:
    next_at = int(row["planned_at"]) + QUOTA_DEFER_SECONDS   # 86400
    if next_at <= ts:
        next_at = ts + QUOTA_DEFER_SECONDS
```

为什么不是"重试 3 次"：配额是按**天**恢复的，1 分钟后重试必然还是超限，只会白写 3 次失败记录。直接延后 24 小时，且如果原计划时刻已经过去（补跑场景），就顺延到"从现在起 24 小时"。

### 3.7 七个定时任务：谁在跑、跑什么、花什么配额

见 [core/scheduler.py#L78-123](file:///c:/biancheng/agent-hub/core/scheduler.py#L78-L123)。

| job_key | 默认 cron | 业务职责 | 配额口径 |
|---|---|---|---|
| `delegate.dispatch` | `*/5 * * * *`（每 5 分钟） | 扫到点的每日委托并投递 | `quota.consume(subject_id, "auto")`，受 `DAILY_AUTO_LIMIT`（默认 120） |
| `delegate.retry` | `7,22,37,52`（错开 5 分钟节点） | 重试失败的委托投递 | 同上，复用原行的 `next_attempt_at` |
| `report.daily` | `30 23 * * *`（默认 23:30） | 生成当日每日总结 | `quota.consume(subject_id, "auto")` |
| `report.backfill` | `0 4 * * *` | 补生成过去 7 天内 failed/empty 的总结 | 业务未实装（`due_subjects` 返回空） |
| `housekeeping` | `15 4 * * *` | 清理 >90 天运行记录、历史上传件 | 无 LLM |
| `profile.aggregate` | `30 2 * * *` | 基于 `user_tags` 权重生成画像快照 | **零 LLM**，纯 SQL 聚合 |
| `prompt.evolve` | `20 */6 * * *` | Prompt 自进化一轮，只产 shadow 候选 | 有独立的评测配额/开关，默认不自动 promote |

三个细节值得单独记：

1. **`delegate.retry` 的分钟是 `7,22,37,52`，不是 `*/5`。** 注释写得很直白：错开 dispatch 的分钟，"避免抢 SQLite 写锁"。SQLite 是单写者，两个 job 同一分钟抢写锁，`busy_timeout=5000` 会让其中一个等 5 秒然后可能失败。
2. **`report.daily` 的 cron 由 `REPORT_HOUR/REPORT_MINUTE` 拼出来。** 改时间只改环境变量或改表，不改代码——这是"定义表存在"的收益。
3. **`profile.aggregate` 刻意不走模型。** 画像聚合是可被 SQL 交叉验证的确定性计算；让它走 LLM 只会引入不可复现的漂移。

`due_subjects` 的选择口径（[service/daily.py](file:///c:/biancheng/agent-hub/service/daily.py)）：

- `report.daily`：当天有消息的 owner；
- `delegate.dispatch`：`enabled=1 AND next_run_at <= planned`；
- `profile.aggregate`：`get_owners_with_tags()`；
- 其余返回 `[]`（backfill/housekeeping 的业务还没实装）。

> **审查视角**：`report.backfill` 和 `housekeeping` 目前是"有 cron、有 handler、但 `due_subjects` 返回空"的空转任务。它们不是 bug，但读代码时要能识别"这个任务现在什么都不做"。文档里如实标注，比假装它完整更有用。

### 3.8 Web 进程与 worker 进程的分工

见 [api/schedule.py#L1-20](file:///c:/biancheng/agent-hub/api/schedule.py#L1-L20)。

这个文件的顶部注释把边界写死了：

```
1. 本文件不 import apscheduler。web 进程只读调度表、写一行「待执行」，
   真正的执行在独立 worker 进程。
2. 同步 I/O 一律 asyncio.to_thread。
3. 健康判定只看心跳年龄，不看进程表。
```

**为什么 web 不 import apscheduler**：两个理由。

- **少一个重依赖**：Web 进程启动要加载 LangChain/Chroma 已经很重，再挂 APScheduler 没必要。
- **健康端点不能依赖被检查的对象**：`/api/schedule/health` 要回答"worker 是不是挂了"，如果它自己 import 了 worker 的调度器、甚至因为 worker 没起而 500，那这个端点就失去意义。

**手动触发 `POST /run-now`** 的写法（[api/schedule.py#L108-160](file:///c:/biancheng/agent-hub/api/schedule.py#L108-L160)）：

- 不另开执行路径，只 `enqueue_job` 写一行 `status=pending, planned_at=now`；
- worker 下一轮 `run_pending` 扫到就执行；
- 全量触发用 `subject_id="*"`，这样幂等键稳定：同一秒内点两次只会排进一次。

**为什么手动和定时必须共用一条路径**：否则会出现"手动能跑、定时不能跑"这种只在生产暴露的差异。共用路径的代价是手动触发有最多 5 分钟的延迟（等 worker 下一轮），收益是**只有一套执行语义**。这个取舍是对的。

### 3.9 worker 怎么执行一次任务

见 [worker/scheduler.py#L153-208](file:///c:/biancheng/agent-hub/worker/scheduler.py#L153-L208)。

`_execute_one(job_key, subject_id, planned_at, run_id, module)`：

1. 调业务模块的 `run_one(...)`；
2. 成功 → `finish_job(run_id, ok=True, tokens_out=...)`；
3. 失败 → `finish_job(run_id, ok=False, error=..., error_class=...)`；
4. 返回一个状态字符串给 `_run_job` 记账。

`_run_job` 先枚举对象（`due_subjects`），再对每个对象 `claim_job`（enqueue + 抢 run_id），然后 `_execute_one`。

**`claim_job` 与 `claim_pending` 的区别**：

- `claim_job` 是"定时触发时，先插一行再抢"——插入可能撞幂等键，返回 `None` 表示"这次已被别人排过"；
- `claim_pending` 是"手动触发时，领已经存在的 pending 行"——用 CAS 翻状态。

两者都在解决同一个问题的两半：**插入时去重（UNIQUE）** 和 **领取时原子（CAS）**。

### 3.10 备份与加固：图 4 的另一半

**备份**（[ops/backup.sh#L1-88](file:///c:/biancheng/agent-hub/ops/backup.sh#L1-L88)）：

```bash
# ★ 为什么不用 cp 直接拷 .db：SQLite 开着 WAL 时，cp 出来的可能是"半个事务"，
#   恢复时轻则少几条记录，重则整库损坏。这里用 sqlite3 的 backup API，
```

它备份三个库：

- `scheduler.db`：定时任务与 `job_runs` 记账；
- `hybrid.db`：工作流与切换规则；
- 另外还有 `data/kb_*.json`（知识库注册表）和 `chroma_db/`（向量库，最不可再生）。

**为什么用 backup API 而不是 `cp`**：WAL 模式下，数据分布在 `.db` 主文件和 `-wal` 文件里，`cp` 只拷主文件会拿到一个"缺最近事务"的旧快照；如果拷的时机不巧，还可能拿到主文件和 WAL 不一致的组合。`sqlite3.Connection.backup()` 是 SQLite 官方提供的一致性快照接口，且不阻塞正在跑的读写。

**为什么保留 7 份**：一周的窗口足够覆盖"周末改坏了、周一才发现"这种最常见的回滚需求；再多就是磁盘成本。

**加固**（[hardening/harden-server.sh#L1-19](file:///c:/biancheng/agent-hub/hardening/harden-server.sh#L1-L19)）：

脚本开头就把三条安全约定写死了：

**为什么这些是脚本级硬约束而不是文档建议**：因为"把自己的 SSH 锁死"是**不可逆**操作（服务器在云上，你进不去就只能重装）。这类操作不能靠人记得，必须让脚本在动手前检查前置条件。

> **审查视角**：`has_nonroot_sudo_key_user()` 只检查"存在这样的用户"，不检查"这个用户的 key 真的能登录"。它防的是"完全没有退路"，不是"退路一定可用"。要验证后者，得实际另开终端登录——脚本里也用 `warn` 提示了这一点。这是**能力边界**，不是漏洞。

## 4. 一条端到端数据流

场景：**早上 8:00，用户 A 发了一条问题；同一时刻 `delegate.dispatch` 正在跑。**

```
08:00:00  worker 进程 cron 触发 delegate.dispatch
          │
          ├─ _beat() 写 worker_heartbeat(ts=08:00:00)
          ├─ run_pending()        领手动触发（今天没有）
          ├─ _run_job("delegate.dispatch", planned_at=08:00)
          │     ├─ due_subjects() → 查 delegations 表
          │     │     WHERE enabled=1 AND next_run_at <= 08:00
          │     ├─ 对每个委托 claim_job(...)
          │     │     INSERT job_runs(...) ON CONFLICT(idem_key) DO NOTHING
          │     ├─ _execute_one(...)
          │     │     ├─ quota.consume(subject_id, "auto")   ← 120/天
          │     │     ├─ 组装 prompt（读该用户当天对话）
          │     │     ├─ llm.invoke([SystemMessage, HumanMessage])
          │     │     ├─ 投递到 deliver_sid
          │     │     └─ finish_job(ok=True, tokens_out=...)
          │     ├─ _bump_next_run(compute_next_run(...))
          │     └─ _record_manual_run(...)
          ├─ run_retries()        处理昨天失败的 1 条（+5 分钟退避）
          └─ _sync_next_run()     把下一次 08:05 写回 schedule_jobs

08:00:03  api/chat.py 处理用户 A 的提问
          │
          ├─ 鉴权 → 会话归属校验 → 读 SQLite 历史
          ├─ router.decide() 判 workflow / agent
          ├─ 生成回答（SSE 流式）
          └─ 落 messages 表 + 异步压缩 + 标签抽取
```

两个进程在同一秒写同一个 `scheduler.db` 吗？**不会**——聊天写的是 `sessions.db`，调度写的是 `scheduler.db`。这是"分库"的直接收益：两个高频写入方不在同一个 SQLite 文件上抢写锁。

如果它们真的要跨库联表（比如"某用户今天有没有收到早报"），SQLite 做不到跨文件 JOIN，只能在应用层分两次查、再在内存里拼。这是模块 2 的一个重要坑点，见第 5 节。

## 5. 工程坑点（已知问题，不是"待修 bug"）

### 5.1 SQLite 单写者 + 两个库文件跨库联表

SQLite 在 WAL 模式下**允许多读者、单写者**。同一时刻只有一个写事务能提交，其他写会排队（`busy_timeout=5000` 等 5 秒）。

本项目的三个库（`sessions.db` / `scheduler.db` / `hybrid.db`）**各自独立**。好处是写热点分散；代价是：

- 不能写 `SELECT ... FROM scheduler.job_runs JOIN sessions.conversations ...`；
- 任何跨库统计都要在 Python 里做两次查询 + 内存合并；
- 内存合并时要注意"两次查询之间数据可能变了"，不能假设快照一致。

**审查时看到"跨库 JOIN"的写法，第一反应就该是"这在 SQLite 里跑不了"。**

### 5.2 APScheduler 多开会重复触发

`worker/scheduler.py` 用 `BlockingScheduler` + `SQLAlchemyJobStore`。如果运维不小心起了两个 worker：

- APScheduler 自己的 jobstore 有锁，**同一个 job 通常不会被两个进程同时触发**；
- 但 `job_runs` 的幂等键是最后一道防线：即使触发了两次，`INSERT ... ON CONFLICT DO NOTHING` 也只会留下一行。

**注意**：幂等保护的是"同一次计划时刻"。如果两个 worker 的时钟差了几秒，`planned_at` 可能不同（比如 08:00:00 和 08:00:01），幂等键就不同，两条都会插入。所以**幂等不是"多开无害"的证明**，只是"多开时大概率不重复"的兜底。真正的正确做法仍然是"只起一个 worker"。

### 5.3 `recursion_limit=10` 是轮次上限，不是语义终止

这条在模块 4 会详细讲，但模块 2 也需要知道，因为 `prompt.evolve` 之类任务可能触发 Agent。`recursion_limit` 数的是"图走了多少步"，不是"任务是否完成"。撞到上限抛 `GraphRecursionError`，被 `agent_engine` 翻译成 `budget_exhausted` 信号——它是**预算耗尽**，不是"任务做完了"。

### 5.4 `guard_scope` 生产未显式包

`core/tool_guard.py` 的 `guard_scope()` 用来隔离"本轮封禁了哪些工具 / 哪些工具待确认"。不包它也能工作，但状态会退化成**进程级共享**：A 用户把 `kb_search` 拉黑后，B 用户在同一进程里也会被拒。

`api/chat.py` 的 Agent 路径目前没有显式 `with tool_guard.guard_scope():`（见模块 4 的审查题）。这是**已知坑**，不是"设计如此"。

### 5.5 切换规则由用户配置，无法证明收敛

`hybrid` 的切换规则可以由用户改 `signal` / `condition` / `priority` / `cooldown`。系统只保证两件事：

- `HYBRID_MAX_SWITCHES=5` 硬上限；
- 同规则冷却 + 同方向全局冷却 30 秒。

但"用户配了一组互相触发的规则"这件事，系统**无法静态证明不会乒乓**。5 次上限是最后的保险丝，不是收敛性证明。模块 4 会展开。

### 5.6 压缩只发生在两轮之间

上下文压缩（模块 3）在**回答结束后**异步触发，不会在"一轮进行中"压缩。所以：

- 如果单轮输入本身就超长（比如用户粘贴 5 万字），压缩救不了这一轮；
- 如果任务在两轮之间被调度触发，它读到的历史是"上一轮压缩后的结果"，不是"实时最新"。

这是有意为之：在轮内压缩会改变模型正在看的上下文，导致"前半段和后半段依据不同"。

### 5.7 `misfire_grace_time=300` 的语义

`build_scheduler()` 给每个 job 设了 `misfire_grace_time=300`、`coalesce=True`、`max_instances=1`：

- `misfire_grace_time=300`：如果 worker 卡了 4 分钟才恢复，错过的触发在 5 分钟内还允许补跑；超过就丢弃。
- `coalesce=True`：如果错过了 3 次触发，恢复后只补跑 **1 次**，不是 3 次。
- `max_instances=1`：同一个 job 不会并发跑两份。

这三个参数合起来回答"宕机恢复后会不会补跑一堆"。答案是：**最多补一次，且只在 5 分钟内**。这个取舍避免了"恢复瞬间雪崩"，代价是"长时间宕机期间的任务会丢"——丢的那部分由 `report.backfill` 这种补跑任务兜底（虽然当前业务未实装）。

## 附：本模块的"读错清单"

1. **把 `misfire_grace_time=300` 读成"重试 300 秒"**：它是"错过触发后允许补跑的宽限期"，不是重试间隔。
2. **把 `stalled` 读成"已挂"**：它是黄灯，`down` 才是红灯。
3. **把 `ON CONFLICT DO NOTHING` 读成"保证不重复执行"**：它只保证"同一幂等键不重复插入"。执行层是否重复，还取决于 `claim_pending` 的 CAS 和"只起一个 worker"的部署约束。
4. **把 `delegate.retry` 读成"独立的第二遍 dispatch"**：它复用原 `job_runs` 行，不新建行。
5. **把 systemd 的 `Restart=always` 读成"万能"**：它只拉起进程，不修复"配置坏到一启动就崩"的重启风暴；真正的可观测性还是心跳。
