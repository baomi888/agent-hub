# 04 · 混合编排

> 本模块回答一个问题：**同一个任务，什么时候该"照着剧本走"，什么时候该"让模型自己看着办"？**
>
> 答案是两个引擎 + 一套规则：
>
> 1. **工作流（workflow）**——节点、边、条件写死在图里，可预期、可回放、出错能定位到某个节点；
> 2. **Agent**——`create_agent` 的 ReAct 循环，模型自己决定调哪个工具、调几次，能应变；
> 3. **切换规则**——引擎上报"信号"（节点失败 / 预算耗尽 / 子目标完成），规则决定是否换引擎，带冷却和硬上限，防止两个引擎来回甩锅。
>
> 读这份文档前请先确认一件事：**本项目 90% 的"混合"不是模型在混，是规则在混。** 模型只负责两件事：路由判一句话要不要多步（`core/router.py`），以及在 Agent 段里自己选工具。其余全是代码。

## 1. 先建立直觉：三个会真实发生的故障

### 故障 A：只用工作流——一个节点挂了，整轮任务陪葬

你写了一个"搜索 → 抓取 → 摘要 → 成表"的四节点工作流。第三节点 `摘要` 的模型返回格式不对，节点抛错。

- 纯工作流引擎的默认行为：节点失败 → 上报 `node_failed` → 没有 `on_fail` 补偿边 → 整轮 `failed`。
- 用户拿到的是一句"混合执行失败"，前面抓到的资料全白费。

**更糟的版本**：节点带 `retry: 2`，但模型每次都以同样的方式失败（比如它拿不到 `kb_id`，因为 `kb_id` 根本不进 schema）。重试只是把同一笔错误账单付三遍。

**如果没有 Agent 兜底**：工作流的可预期性反过来变成脆弱性——只要剧本里有一格不按你预想的走，整场演出停摆。

### 故障 B：只用 Agent——它每次都能跑完，但每次跑法不一样

用户要"把这三篇论文按 方法/数据集/结论 对比成表"。

- Agent 完全能做到，但：第一轮它调 3 次 `kb_search`，第二轮调 5 次，第三轮直接凭记忆编；
- 输出结构每次不同，"数据集"这一列有时叫"数据"有时消失；
- 你不知道它下一步要干什么，也没法在它第 8 步时插一句"够了"。

**如果没有可预期的那一半**：所有"要格式、要可复现、要审计"的任务都不能交给它。而这类任务恰好是业务主体。

### 故障 C：两引擎随便切——一晚上烧掉几百次调用

最直觉的接法是：工作流失败就转 Agent，Agent 完成就转回工作流，工作流再失败再转 Agent……

- `wf_node_failure` 转 Agent，Agent 一上来就 `budget_exhausted` 又转回工作流；
- 工作流从断点继续，同一个节点又失败，又转 Agent；
- 一次提问变成 40 次引擎段，配额和 token 全部烧光，用户看到的是转圈。

**如果没有冷却 + 硬上限**：切换机制本身会成为最大的故障源。代码注释写得很直白——"比'不出事'更重要的是'出事能兜底'"（[hybrid/switcher.py#L9-14](file:///c:/biancheng/agent-hub/hybrid/switcher.py#L9-L14)）。

## 2. LangChain 零基础补丁

这一节按"概念 → 本项目用没用 → 在哪一行 → 替我们做了什么"逐个过。

### 2.1 `BaseChatModel` 与 `ChatOpenAI`

白话：LangChain 里"聊天模型"的统一基类叫 `BaseChatModel`，它是一个 `Runnable`——也就是说它有 `.invoke()` / `.ainvoke()` / `.astream()` 这些统一方法。`ChatOpenAI` 是它的 OpenAI 兼容实现。

本项目用的是 [`ChatOpenAI`](file:///c:/biancheng/agent-hub/core/llm.py#L35-L70)，包了一层 `get_llm(temperature, max_tokens, timeout)`，按这三个参数缓存实例：

```python
# core/llm.py（节选，行号见链接）
def get_llm(temperature=0.7, *, max_tokens=None, timeout=None) -> ChatOpenAI:
    ...
```

**它替我们做了什么**：把"HTTP 请求 + 鉴权 + SSE 解析 + 重试"收敛成一个对象，并且这个对象能被 LangChain 的 Agent / 链直接消费。

### 2.2 为什么**不用** `init_chat_model`（反框架选择 ①）

[core/llm.py#L1-13](file:///c:/biancheng/agent-hub/core/llm.py#L1-L13) 顶部写明了原因，原文意思是：

- `init_chat_model("deepseek:...")` 依赖 provider 注册表，本项目用的第三方 OpenAI 兼容网关（deepseek / dashscope）在 LangChain 1.4.1 的注册表里匹配不稳；
- 走 `init_chat_model` 会多一层 provider 解析，参数（`base_url` / `extra_body` / 超时）传递路径变长，出问题时报错信息也更绕；
- 直接 `ChatOpenAI(model=..., base_url=..., api_key=...)` 就只有一条路径，**看得见、改得动**。

**动机一句话**：`init_chat_model` 解决的是"多 provider 自动适配"，本项目只有一种协议（OpenAI 兼容），引入它只增加不确定性。

### 2.3 `Runnable` 与 `.ainvoke` / `.astream`

白话：`Runnable` 是 LangChain 的"可执行单元"协议。任何实现了它的对象都能 `.invoke()`（同步）、`.ainvoke()`（异步）、`.astream()`（流式）、`.batch()`。

本项目哪里用了：

| 位置 | 用法 | 说明 |
|---|---|---|
| [core/router.py#L119-141](file:///c:/biancheng/agent-hub/core/router.py#L119-L141) | `await asyncio.wait_for(llm.ainvoke(messages), timeout=...)` | 路由判一句话，要一个完整 JSON，不需要流式 |
| [hybrid/workflow.py#L477](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L477) | `async for chunk in llm.astream(prompt)` | LLM 节点配 `stream: true` 时逐字上屏 |
| [hybrid/workflow.py#L486](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L486) | `resp = await llm.ainvoke(prompt)` | 节点不流式时等完整结果 |

**它替我们做了什么**：同一份模型对象，既能在路由里"问一句就走"，也能在工作流节点里流式吐字，不用写两套 HTTP 代码。

**本项目绕过的地方**：没有用 `RunnableSequence` / LCEL 的管道语法（`prompt | llm | parser`）。原因是工作流节点要同时产出 `ExecEvent`、要写 `ctx.shared`、要检查 `control()` 人工指令——这些都发生在"步骤之间"，用 LCEL 串起来反而把控制流藏进闭包里。

### 2.4 `Tool` / `StructuredTool` / `@tool`

白话：
- `Tool`：一个"名字 + 描述 + 可调用函数"，模型看到名字和描述，决定要不要调；
- `StructuredTool`：带**参数 schema**（`args_schema`，通常是 pydantic 模型）的工具，模型按 schema 生成 JSON 参数。函数签名和 docstring 会被自动转成 schema。

本项目四个工具都用 `@tool` 装饰器定义（[agent/tools.py](file:///c:/biancheng/agent-hub/agent/tools.py)），装饰器返回的就是 `StructuredTool`：

- [`kb_search`#L49](file:///c:/biancheng/agent-hub/agent/tools.py#L49)
- [`web_search`#L123](file:///c:/biancheng/agent-hub/agent/tools.py#L123)
- [`get_weather`#L318](file:///c:/biancheng/agent-hub/agent/tools.py#L318)
- [`download_file`#L551](file:///c:/biancheng/agent-hub/agent/tools.py#L551)

**它替我们做了什么**：把 Python 函数变成模型能调用的工具，并自动生成 JSON Schema。**关键点**：工具的参数里**没有** `kb_id` / `owner_id`——这些由服务端从 `RunnableConfig.configurable` 注入（`_runtime(config)`，[agent/tools.py#L38-43](file:///c:/biancheng/agent-hub/agent/tools.py#L38-L43)）。模型只能决定"查不查"，决定不了"查谁的库"。

### 2.5 `bind_tools` / `create_agent`

白话：`bind_tools(tools)` 是"把这个模型和这组工具绑一起"，模型每次请求都会带上工具 schema，需要时输出 `tool_calls`。`create_agent(model, tools, system_prompt, checkpointer)` 是 LangChain v1 的 Agent 工厂：它组装出一个 LangGraph 状态图（模型节点 ↔ 工具节点循环），也就是常说的 **ReAct 循环**。

本项目：[agent/builder.py#L346-351](file:///c:/biancheng/agent-hub/agent/builder.py#L346-L351)

```python
agent = create_agent(
    model=llm,
    tools=tools_to_bind,
    system_prompt=system_prompt,
    checkpointer=_CHECKPOINTER,   # ← 恒为 None
)
```

**它替我们做了什么**：不用自己写"调模型 → 看有没有 tool_calls → 执行工具 → 把结果塞回 messages → 再调模型"这个循环。这个循环写错很容易死循环。

**本项目绕过的地方**：`create_agent` 只在这一处用；工作流的 `tool` 节点不走 Agent，直接 `tool.ainvoke(args, config)`（[hybrid/workflow.py#L490-572](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L490-L572)）。因为工作流节点是**单次工具调用**，不需要 ReAct 循环，套 Agent 等于为了一个函数调用启动一台发动机。

### 2.6 `Checkpointer` / `State` —— 以及为什么**故意传 `None`**（反框架选择 ②）

白话：
- `State`：LangGraph 图在节点之间传递的状态（`create_agent` 里就是 `messages` 列表）；
- `Checkpointer`：把每一轮 State **存下来**的组件。有了它，同一个 `thread_id` 下次可以"接着上次的状态继续"，也就是跨进程的记忆。

本项目的选择：[agent/builder.py#L122-148](file:///c:/biancheng/agent-hub/agent/builder.py#L122-L148)，`_make_checkpointer()` **返回 `None`**。注释列了三条实测理由：

1. 会话历史本来就在 SQLite（`core/session.py`），每轮由 `api/chat.py` 重建成 messages 一起喂进去。再挂 checkpointer 等于**记两份**。
2. 两份同时用会**重复累积**：第 2 轮状态里第 1 轮消息出现 2 次，第 3 轮出现 3 次，3 轮后 12 条（本应 6 条）。
3. 原来的 `SqliteSaver.from_conn_string(path)` 是 `@contextmanager`，返回的不是 saver 而是上下文管理器，直接抛 `TypeError: Invalid checkpointer provided ... Received _GeneratorContextManager`；换成 `SqliteSaver(sqlite3.connect(path))` 也不行，因为同步 saver 不支持 `astream`，必须用 `AsyncSqliteSaver` 且在 lifespan 里 async 打开。

**动机一句话**：记忆的**唯一事实来源**放在 SQLite，Agent 只做"无状态执行器"。这样重启不丢、受 `MAX_HISTORY_TURNS` 截断保护、不用再维护第二套生命周期。

⚠️ 一个必须记住的配套条件：**如果将来有人把 checkpointer 打开，就必须同时改 `api/chat.py`，只发当前这一条消息、不再重放历史**。否则立刻踩第 2 条。

### 2.7 `RunnableConfig` / `configurable`

白话：`RunnableConfig` 是 LangChain 运行时的"旁路参数包"。`configurable` 是里面的一个字典，**不会发给模型**，只用于给工具/节点传运行时依赖。

本项目两处：

- [api/chat.py](file:///c:/biancheng/agent-hub/api/chat.py) 的 Agent 分支：`config={"configurable": {"owner_id": uid, "kb_id": kb_id, ...}}`
- [hybrid/agent_engine.py#L142-153](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L142-L153)：混合模式下同样注入 `owner_id` / `kb_id` / `download_allowlist` / `user_urls`

**它替我们做了什么**：把"权限上下文"从模型可见的 prompt 里挪到框架旁路。这是整份代码里最重要的一条安全边界——**模型能改的是自己的输出，改不了 configurable**。

### 2.8 `astream` 的 `stream_mode`，以及为什么**不用** `astream_events`

白话：
- `astream(stream_mode="updates")`：每个节点执行完给你一次"这个节点输出了什么"；
- `astream(stream_mode="messages")`：给你**逐 token** 的消息块；
- `astream_events(version="v2")`：给你所有内部事件（链开始/结束、模型开始/结束、工具开始/结束……），粒度最细但**噪音最大**。

本项目：[hybrid/agent_engine.py#L157-159](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L157-L159)

```python
agen = agent.astream(
    {"messages": msgs},
    config=config_,
    stream_mode=["updates", "messages"],
)
```

**为什么不用 `astream_events`**：
1. 它输出的是**扁平事件流**，要把 `on_chat_model_stream` / `on_tool_start` / `on_tool_end` 重新拼回"哪一步在干什么"，逻辑量比直接用两种 mode 大；
2. 事件里带大量 `run_id` / `parent_ids` / 序列化对象，落库前还得再裁剪；
3. 本项目只需要三种东西：**token**（上屏）、**工具调用**（轨迹面板）、**步数/字符数**（预算）。`updates + messages` 恰好够。

### 2.9 `recursion_limit` / `GraphRecursionError`

白话：LangGraph 给图设了一个"最多走多少步"的硬限制（默认 25）。超了不是"返回最后一版答案"，而是**抛异常** `GraphRecursionError`。

本项目：[hybrid/agent_engine.py#L140](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L140) 设 `recursion_limit = config.HYBRID_AGENT_MAX_STEPS`（默认 10，[core/config.py#L251](file:///c:/biancheng/agent-hub/core/config.py#L251)），并在 [L281-287](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L281-L287) 接住它转成 `budget_exhausted` 信号。

⚠️ **这里有个极易读错的点**：`recursion_limit=10` 限制的是**图循环轮次**，不是"语义上做完了没有"。模型第 3 轮就说"完成了"也很正常；模型第 10 轮还没找到答案也很正常。它**不是终止条件**，只是止损线。文档第 5 节会再展开。

## 3. 核心代码逐段吃透

### 3.1 `TaskContext`：两引擎之间唯一的交换通道

[hybrid/context.py#L134-243](file:///c:/biancheng/agent-hub/hybrid/context.py#L134-L243)

**在干什么**：一个 pydantic 模型，字段分三组：

- 公共：`task_id` / `run_id` / `owner_id` / `goal` / `status` / `current_mode`；
- 各模式私有段：`workflow_state`（`completed` / `next_node` / `node_outputs`）、`agent_state`（`steps` / `chars` / `consec_failures`）；
- 跨模式共享：`shared`。

**为什么这样写**：
1. **私有段 + 共享段分开**，是为了让"谁能写什么"变成结构约束，而不是约定。对方模式可以读你的私有段做决策，但不能往里写。
2. `version` 乐观锁：每次 `bump()` +1，切换移交时可比对，防并发撕裂。
3. `goal` 只读：`set_goal` 第一次赋值后置位 `_goal_locked`，`__setattr__` 里再拦一道（[L185-198](file:///c:/biancheng/agent-hub/hybrid/context.py#L185-L198)）。想改必须 `override_goal(value, reason)`，它会在 `mode_trace` 里留一条记录。

**换个写法会怎样**：
- 若 `goal` 可随便改：回放时 `mode_trace` 里那段"为什么切到 Agent"就失去意义——你不知道当时的目标是什么。
- 若不做 `version`：两段并发写 `shared` 后，后写覆盖前写，且没有任何痕迹。

**shared 的三条防线**（[L30-47](file:///c:/biancheng/agent-hub/hybrid/context.py#L30-L47)）：

| 防线 | 实现 | 不做会怎样 |
|---|---|---|
| 值上限 8000 字符 | `shared_set` 超限调 `spill_value` 落盘、只留指针 | 每次切换整体快照落 `workflow_runs.context`，长文会让库无声膨胀 |
| 键命名空间 | 同名不同前缀（`node:` / `agent:` / `wf:`）抛 `SharedKeyError` | 两方撞名，后写静默覆盖 |
| goal 只读 | `set_goal` + `__setattr__` | 目标漂移，回放不可解释 |

**一个反直觉的细节**：节点产出**刻意不走** `shared_set`，而是 `ctx.shared[key] = content` 直接赋值（[hybrid/workflow.py#L457-465](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L457-L465)）。原因是下游 `render_template` 要**逐字**读产出，而 `shared_set` 对超长值会落盘成指针字符串，模板解析不了；另外命名空间校验会把 `plan` / `agent_result` 这类正常输出键判成冲突。

> 这就是"防御代码"和"业务正确"冲突时该怎么选的一个范本：**防线要放在它真能保护的地方**。超长值落盘在这里是坏主意，因为这里的消费者是模板而不是人。

### 3.2 工作流的五类节点

[hybrid/workflow.py#L377-455](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L377-L455) 是分发入口。

| 节点类型 | 干什么 | 产出写到哪 | 关键约束 |
|---|---|---|---|
| `llm` | 把模板渲染成 prompt 调模型 | `shared[output_key]` | 有历史时前置 `history_prefix`；可流式 |
| `tool` | 单次工具调用（**不是** Agent） | `shared[output_key]` | 服务端注入 `owner_id` / `kb_id` |
| `agent` | 启动一个 Agent 段 | `shared[output_key]` | 若节点声明 `requires_agent`，**执行前**就让出（信号在 `stream` 主循环 [L206-214](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L206-L214) 上报，不在 `_exec_agent` 里） |
| `condition` | **不做事**，只是路由汇合点 | 无 | 分支逻辑写在**边的 condition** 上 |
| `human` | 人工确认：挂起或自动通过 | `shared[output_key]` | `suspend: true` 才真挂起 |

**为什么 `condition` 节点"不做事"**：图模型里把判断放在**边**上，节点就保持纯函数化，回放时能清楚看到"在哪条边上分叉"。如果把 if/else 写进节点，节点输出就同时承担"数据"和"控制"两种语义，调试时会分不清是数据错了还是分支错了。

**人工节点的挂起为什么必须用异常**（[L407-431](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L407-L431)）：

```python
# 错误写法（注释里记录的踩坑）：生成器里 return
if should_suspend:
    ...
    return          # ← 调用方会当成"节点正常执行完毕"，继续跑下一个节点
```

`_exec_human` 是**异步生成器**。生成器里的 `return` 只是"正常结束迭代"，不是"抛出"。上层 `_run_with_retry` 看到 `StopAsyncIteration` 就判定成功，挂起就静默失效了。所以现在抛 `_Suspend(node.id, nxt)`，并在 `_run_with_retry` 里**原样穿透**（[L353-356](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L353-L356)）——若落到 `except Exception` 就会被转成 error 事件再重试，同样静默失效。

**换个写法会怎样**：改成 `return` → 人工节点永远不生效，流程一路绿灯跑到底，用户以为"确认"了但系统从没等过。这是最难发现的一类 bug：**没有报错、日志还显示"节点成功"**。

### 3.3 断点锚点：为什么指向"被挂起的节点本身"

[hybrid/workflow.py#L254-269](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L254-L269)

```python
except _Suspend as sp:
    wf_state["next_node"] = sp.node_id          # ← 锚点是"自己"，不是下游
    wf_state["suspended_at"] = sp.node_id
    ctx.status = "awaiting_human"

```

**在干什么**：挂起时把续跑锚点设为当前节点，并且**不把它计入 `completed`**。

**为什么这样写**：恢复时要**重新进入这个节点**，才能在那里执行"记录人工批准值 → 路由到下游"的逻辑（[L220-237](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L220-L237)）。若锚点直接指向下游，恢复后就直接跑下游了，`resume_value` 永远写不进 `shared`。

**换个写法会怎样**：锚点指向下游 → 恢复后 `shared` 里缺了一个本该存在的键 → 下游模板渲染出空值（`render_template` 对缺失键的处理见 [L118-137](file:///c:/biancheng/agent-hub/hybrid/workflow.py#L118-L137)）→ 模型拿到一份带空格的 prompt，输出跑偏。

### 3.4 Agent 引擎：三重预算

[hybrid/agent_engine.py#L133-290](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L133-L290)

**在干什么**：跑一段 Agent，边跑边记三笔账：

1. **步数**：`recursion_limit = HYBRID_AGENT_MAX_STEPS`（默认 10）；
2. **时长**：`deadline = time.monotonic() + HYBRID_AGENT_MAX_SECONDS`（默认 300s）；
3. **token 近似**：`st["chars"] // 2 >= HYBRID_AGENT_TOKEN_BUDGET`（默认 8000）。`chars` 累加的是 token 事件字符数 + `ToolMessage` 内容字符数。

任一笔先到 → `EngineResult(status="switched", signal="budget_exhausted")`，交给编排器决定是换引擎还是收工。

**为什么用 `chars//2` 而不是 tokenizer**：注释写得很清楚——"比起真实 tokenizer 零开销，量级够用"。中文 1 字符 ≈ 1 token 量级，英文 1 字符 ≈ 0.25 token，取 `//2` 是个中间保守值。

**换个写法会怎样**：真上 tokenizer → 每次事件都要编码，CPU 开销进入流式路径，首字延迟变差；而且模型换了 tokenizer 口径会漂。

**`thread_id` 为什么带 `len(ctx.mode_trace)`**（[L147](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L147)）：

```python
"thread_id": f"hybrid-{ctx.run_id}-{len(ctx.mode_trace)}",
```

每个执行段独立 thread —— 混合模式下 Agent 段是"子任务"，不该继承别段的中间推理状态。虽然本项目 `checkpointer=None`（thread_id 实际不生效），但保留它是**为将来打开 checkpointer 留的正确语义**：一旦启用，不同段不会互相污染。

**工具连续失败 3 次 → `agent_stuck`**：[L52-58](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L52-L58) 定义 `_MAX_CONSEC_FAILURES=3` 和 `_FAIL_HINTS`，每次 `ToolMessage` 内容命中失败词就 +1，成功归零。

**为什么需要它**：`recursion_limit` 只保证"最多 10 步"，不保证"10 步里没有原地打转"。模型连续 3 次拿同样的失败结果还在试，第 10 步一定也是失败，不如提前止损。

**换个写法会怎样**：只靠 `recursion_limit` → 最坏情况是 10 步全部花在同一个失败工具上，用户等了 5 分钟拿到一句"执行失败"。

### 3.5 切换引擎：priority → 规则冷却 → 方向冷却 → condition

[hybrid/switcher.py#L56-82](file:///c:/biancheng/agent-hub/hybrid/switcher.py#L56-L82)

**在干什么**：

```python
# 1. 硬上限最先查
if len(ctx.mode_trace) >= config.HYBRID_MAX_SWITCHES:   # 默认 5
    return SwitchDecision(action="terminate", rule="__max_switches__", ...)

# 2. 按 priority 升序遍历
for rule in self.rules:
    if rule.signal != signal: continue
    if rule.cooldown_seconds > 0:
        # 2a. 同名规则冷却（默认 30s）
        # 2b. 同方向全局冷却（HYBRID_SWITCH_COOLDOWN，默认 30s）
    if not rule.condition or self._eval(rule.condition, ...):
        return SwitchDecision(action=rule.action, rule=rule.name, ...)
return SwitchDecision(action="continue")
```

**为什么这样写**：

- **先查上限，再查规则**：如果规则层先跑，可能出现"第 6 次切换被规则允许"的边角，然后才被上限拦。顺序反了不影响结果但影响理由文案（你希望日志说"达到上限"而不是"某规则命中"）。
- **`cooldown_seconds == 0` 是显式豁免**，不是"没配"。`requires_agent` / `goal_satisfied` 是流程语义的一部分——节点声明"这活我要交给 Agent"，如果被防抖吃掉，工作流会卡在一个永远过不去的节点上。
- **方向冷却只看 `to_mode`**，不看 `from_mode`：`workflow→agent` 与 `agent→workflow` 是两条独立的防抖通道。

**换个写法会怎样**：
- 去掉方向冷却，只留规则冷却 → 两条不同规则可以在 1 秒内触发两次**同方向**切换（比如 `wf_node_failure` 刚转 Agent，`wf_requires_agent` 又转 Agent），第二次是空操作但会写进 `mode_trace`，让"切换次数"这个指标虚高。
- 把上限检查放到循环里 → 前 5 次判定都正常，第 6 次才终止；用户多等一段。

### 3.6 四条默认规则与"为什么 `wf_node_failure` 不是 terminate"

[hybrid/store.py#L122-159](file:///c:/biancheng/agent-hub/hybrid/store.py#L122-L159)

| 规则 | signal | action | priority | cooldown | 语义 |
|---|---|---|---|---|---|
| `wf_requires_agent` | `requires_agent` | `to_agent` | 10 | **0** | 节点自己声明"这活要自主执行" |
| `wf_node_failure` | `node_failed` | `to_agent` | 20 | 30 | 节点失败且无补偿边，Agent 降级接管 |
| `agent_budget_exhausted` | `budget_exhausted` | `to_workflow` | 20 | 30 | Agent 预算烧完，收编回工作流 |
| `agent_goal_satisfied` | `goal_satisfied` | `to_workflow` | 30 | **0** | Agent 子目标完成，工作流从断点继续 |

**`wf_node_failure` 选 `to_agent` 而不是 `terminate` 的理由**：一个节点失败，往往意味着"这一步不该按剧本走"。Agent 拿到 `ctx.shared` 里前面节点已经产出的东西，换个路子把目标补上，比整轮失败更有价值。而 `terminate` 只在"两引擎都救不了"时用——也就是撞上限。

**为什么规则要落库而不是写死在代码里**：用户可以覆盖同名规则（`list_rules` 先取系统默认、再取用户同名覆盖，[hybrid/store.py#L410-431](file:///c:/biancheng/agent-hub/hybrid/store.py#L410-L431)）。代价是**无法证明收敛**——见第 5 节。

### 3.7 编排器主循环

[hybrid/orchestrator.py#L119-241](file:///c:/biancheng/agent-hub/hybrid/orchestrator.py#L119-L241)

**在干什么**（按顺序）：

1. `store.save_run(ctx)` —— **起跑即落库**。不这么做的话，起跑阶段的人工指令 `POST /runs/{id}/switch` 会因为查不到 run 而 404。
2. `for _segment in range(HYBRID_MAX_SWITCHES + 2)` —— 迭代护栏，兜底的兜底。
3. 先 `_take_manual()` 消费人工指令（可能是在两段之间由 API 线程写入的）。
4. `engine = self._make_engine(ctx.current_mode)`，`async for ev in engine.stream(ctx, lambda: _peek_manual(...))` —— **注意 `_peek`（偷看）而不是 `_take`（消费）**：引擎只负责"看到有人要切，我让出"，消费权在编排器，避免引擎自己把指令吃掉导致编排器永远看不到。
5. 段结束，`store.save_run(ctx)` 快照。
6. 分四种情况：`manual` 信号 → 人工优先；`awaiting_human` → 挂起落库并 break；无 signal → 按引擎结果落终态；有 signal → `switcher.decide`。
7. `ctx.record_switch(target, rule, reason)` → `save_run` → 发 `switch` 事件 → 下一段。

**`aborted` 标志为什么必须有**（[L127-131](file:///c:/biancheng/agent-hub/hybrid/orchestrator.py#L127-L131) 与 [L232-241](file:///c:/biancheng/agent-hub/hybrid/orchestrator.py#L232-L241)）：

生成器被关闭（客户端断开，`GeneratorExit` 从 `yield` 处抛出）或异常逃逸时，上面所有"正常收尾"都到不了。没有 `finally` 兜底，run 会**永远停在 running**——`/runs` 列表出现"幽灵执行中"，人工切换还会对它误报 ok。这是 10-14 联调实测的。

**换个写法会怎样**：
- 去掉 `finally` → 幽灵 run 永久存在，且 `_MANUAL` 里那条指令永远没人消费（内存里小小的泄漏，但更麻烦的是日志里全是"执行中"）。
- 引擎用 `_take_manual` 而非 `_peek` → 引擎在节点边界把指令拿走后 `return`，编排器再 `_take` 拿到的就是 `None`，走 `L158-161` 的"反向切换兜底"，行为不可预期。

### 3.8 执行前路由：`decide()` 永远不抛异常

[core/router.py#L143-180](file:///c:/biancheng/agent-hub/core/router.py#L143-L180)

**在干什么**：一次 `llm.ainvoke`，让模型输出 `{"route":"workflow|agent","reason":"..."}`。

**四层加固**：
1. `ROUTER_ENABLED=0` → 直接 `agent`，不建客户端；

**为什么兜底是 `agent` 而不是 `workflow`**（[core/router.py#L83-98](file:///c:/biancheng/agent-hub/core/router.py#L83-L98)）：

**换个写法会怎样**：让路由异常穿透 → `api/chat.py` 是裸 `await`，整个提问 500，而**额度往往已经扣了**（[core/router.py#L147-155](file:///c:/biancheng/agent-hub/core/router.py#L147-L155) 的注释）。

### 3.9 图 1 圈出的部分：工具元数据、激活、审批、守卫

这张图圈的是 `core/tool_registry.py` + `core/tool_guard.py` + 安全工具（`netsafe` / `urltools`）。

#### 这一段为什么这么写：`ToolMeta` 是 `frozen dataclass` + `__post_init__` 校验

[core/tool_registry.py#L66-98](file:///c:/biancheng/agent-hub/core/tool_registry.py#L66-L98)

```python
@dataclass(frozen=True)
class ToolMeta:
    category: str
    defer: bool = False
    retryable: bool = True
    needs_approval: bool = False
    max_output_chars: int = 4000
    cost_hint: str = COST_NORMAL

    def __post_init__(self) -> None:
        if self.category not in _CATEGORIES: raise ValueError(...)
        if self.cost_hint not in _COSTS: raise ValueError(...)
        if self.max_output_chars <= 0: raise ValueError(...)
```

**在干什么**：把"这个工具怎么执行"声明成数据，**引擎读它，模型看不到它**（docstring 第一行）。

**为什么 `frozen=True`**：元数据是**导入时**就该定死的常量。运行时可变意味着某个请求能改掉全局策略（比如把 `download_file` 的 `needs_approval` 改成 False），这是权限旁路。

**为什么校验放在 `__post_init__`**：模块**导入时**就炸，而不是等第一次调用工具时才炸。早失败原则——一个拼错的 `category="readonly"` 不应该活到生产流量里。

**换个写法会怎样**：改成普通 `dict` 字面量（很多项目这么干）→ 拼错的 key 静默被忽略，`meta.needs_approval` 退化成 `False`，审批层"看起来在跑"但从不触发。

#### 这一段为什么这么写：`defer` / 激活状态在**请求开始**取定

`defer=True` 表示"这个工具不默认下发，要先 `discover` 激活"。当前四个工具全是 `defer=False`（[L105-137](file:///c:/biancheng/agent-hub/core/tool_registry.py#L105-L137)），这个字段是给未来的定时类工具留位。

关键在于**什么时候读激活集**：`api/chat.py` 在请求开始时调一次 `tool_registry.activated_for(uid)`，整轮不变，再透传给 `build_agent`（[api/chat.py#L1164](file:///c:/biancheng/agent-hub/api/chat.py#L1164) / [hybrid/agent_engine.py#L110-113](file:///c:/biancheng/agent-hub/hybrid/agent_engine.py#L110-L113)）。

**为什么不能在 Agent 跑到一半再读**：工具 schema 是请求**前缀**的一部分。跑到一半才加一个工具，前缀变了 → KV 缓存失效（项目实测命中率 90%→0%）。这条在 [agent/builder.py#L329-332](file:///c:/biancheng/agent-hub/agent/builder.py#L329-L332) 有注释。

**换个写法会怎样**：agent 段每轮重新读激活集 → 同一会话的工具前缀不稳定 → 每次请求都全量重算 prompt，成本翻倍且首字变慢。

#### 这一段为什么这么写：`needs_approval` 的确认串是 `(工具名, 参数)` 的 hash

[core/tool_guard.py#L96-101](file:///c:/biancheng/agent-hub/core/tool_guard.py#L96-L101) 与 [L161-178](file:///c:/biancheng/agent-hub/core/tool_guard.py#L161-L178)

```python
def approval_token(tool_name, args):
    payload = json.dumps({"tool": tool_name, "args": args},
                         ensure_ascii=False, sort_keys=True, default=str)
    return "confirm:" + hashlib.sha256(payload.encode()).hexdigest()[:12]
```

- 第一次调用：**不执行**，返回"需要确认 + 确认串"，并登记到 `st.pending[tool_name]`；
- 第二次调用：`st.pending.get(tool_name) == token` 才执行，然后 `pop`。

**为什么 hash 参数而不是"调两次就放行"**：参数改了 hash 就变，等于**批准的是这一次**，不是"以后这个工具都可以"。用户批了"下载 A 文件"，模型不能拿这个批准去下载 B。

**为什么状态放 `contextvars` 而不是 schema 字段**（[tool_guard.py#L24-27](file:///c:/biancheng/agent-hub/core/tool_guard.py#L24-L27)）：schema 会发给模型，加一个 `confirm` 参数等于**教模型怎么绕守卫**。状态走 contextvar，工具签名与 docstring 一字不改。

**换个写法会怎样**：把 `confirm` 做成工具参数 → 模型看到"只要填上 confirm 就能执行"，它会自己编一个串填进去。

#### 这一段为什么这么写：守卫用"重建"而不是"包裹套壳"

[core/tool_guard.py#L234-265](file:///c:/biancheng/agent-hub/core/tool_guard.py#L234-L265)

```python
guarded_fn = _make_guarded_fn(t.name, fn)
StructuredTool.from_function(
    func=guarded_fn,
    name=t.name, description=t.description, args_schema=t.args_schema,
)
```

**为什么不能在外面包**：LangChain 的 `StructuredTool` 会在**两层**做签名内省并注入框架参数——`_run` 层注入 `config` / `run_manager`，`func` 层再注入 `config`。从外面包 `_run` 或 `func` 都会破坏这件事（注释说实测两次踩坑）。

**`functools.wraps(fn)` 为什么必要**：保留原签名，`config` 这类 `RunnableConfig` 参数才会被 LangChain 正确注入。没有 `wraps`，签名变成 `(*args, **kwargs)`，框架就不知道该注入什么。

**换个写法会怎样**：包成 `lambda **kwargs: guarded_run(...)` → `kb_search` 里 `_runtime(config)` 拿到的 `config` 是空 dict → 拿不到 `owner_id` / `kb_id` → 所有检索返回"当前绑定的知识库为空"。

#### 这一段为什么这么写：`prompt_guard` 按 path 分开维护黑名单

#### 这一段为什么这么写：URL 白名单是"归一后完全相等"

[core/urltools.py#L93-113](file:///c:/biancheng/agent-hub/core/urltools.py#L93-L113) + [core/netsafe.py#L61](file:///c:/biancheng/agent-hub/core/netsafe.py#L61)

`download_file` 的下载闸门（[agent/tools.py#L573-575](file:///c:/biancheng/agent-hub/agent/tools.py#L573-L575)）：

```python

    allowed = list(cfg.get("download_allowlist") or []) + list(cfg.get("user_urls") or [])
    if not url_allowed(url, allowed):
        return "下载失败：该链接不在允许清单内"
```

**为什么用"归一后完全相等"而不是前缀匹配**：

- 前缀匹配 `https://a.com` 会放行 `https://a.com.evil.com/x`（域名后缀不是路径）；
- 归一化（去 fragment、scheme/host 小写、去默认端口、**保留 query 顺序**）后再比，`https://a.com/x?b=2&a=1` 与 `https://a.com/x?a=1&b=2` 是**两个不同 URL**——这是故意的：参数顺序变化往往意味着请求语义变化（签名 URL）。

`netsafe.assert_safe_url` 另外拦：非 http/https、带 `user:pass`、云元数据 host、解析出的每个 IP 落在内网/回环/链路本地/保留段。**它明确不负责 DNS rebinding**（注释里写了），那是另一个层级的防护。

**换个写法会怎样**：只做前缀匹配 → 一次下载就能把内网 `169.254.169.254` 的元数据接口或任意子域打穿。

## 5. 工程坑点

### 5.1 `recursion_limit=10` 是轮次上限，不是语义终止

- 它保证"最多转 10 圈"，**不保证**"任务做完了"；
- 模型第 2 圈就说完成 → 正常结束，`recursion_limit` 一点没用上；
- 模型第 10 圈还在找 → 抛 `GraphRecursionError` → 转 `budget_exhausted` → 规则转回工作流；
- **最常见的误读**：以为"设 10 就是最多调 10 次工具"。不是——一轮里模型可以同时输出多个 `tool_calls`，10 圈可能对应 20+ 次工具调用。

### 5.2 `guard_scope` 生产链路未显式包

`core/tool_guard.py#L67-83` 的 docstring 写得很诚实："不加也能工作（退化为进程级共享），但并发会话间会互相影响，所以调用方应尽量加上。"

现状：`api/chat.py` 的 Agent 路径与 `hybrid` 路径都**没有**显式 `with tool_guard.guard_scope():`。后果：

- `_state_var` 默认 `None`，首次 `_state()` 会 `set` 一个 `_GuardState`，**之后一直复用**；
- 在**单进程、单请求并发**下 ContextVar 天然按 asyncio task 隔离，所以看起来没事；
- 一旦同一 task 里连跑两轮（或测试里直接调工具函数），封禁集合会**跨轮延续**：A 用户的 `kb_search` 失败被封，B 用户的第一次调用直接被拒。

这是"文档说该加、代码没加"的典型缺口——读代码时要**以调用点为准，不以注释为准**。

### 5.3 切换规则由用户配置，无法证明收敛

规则存在 `switch_rules` 表，用户可以 upsert 同名覆盖、可以加新规则、可以改 `priority` 与 `cooldown`。系统只保证：

- 单次判定按 `priority` 升序、第一个命中者胜；
- 有 5 次硬上限；
- 有同方向 30s 冷却。

**不保证**：任意用户配置下都能在 5 次内到达终态。比如用户把 `wf_node_failure` 改成 `terminate`（priority 1），又把 `agent_budget_exhausted` 改成 `to_workflow`（priority 1）——当两个信号交替出现时，行为取决于当次顺序，只能在撞上限时收工。

严格说这是一个**有界但不收敛**的系统：有界由护栏保证，收敛由用户配置决定。

### 5.4 压缩只在两轮之间

`maybe_compress` 由 `api/chat.py` 的 `_compress_after_turn` 在**一轮结束后**触发（[api/chat.py#L1817](file:///c:/biancheng/agent-hub/api/chat.py#L1817)）。混合编排一跑可能是 3-4 个引擎段、几十次工具调用，**这一段中间不会压缩**。

后果：一次混合执行的实际上下文 = 历史 + 本轮所有中间产物。如果工作流的 `plan` 节点产出了 3000 字，`agent_result` 又是 5000 字，再加上 `history` 60 条 × 500 字，能轻松顶到模型上限。

这解释了为什么 `shared` 要有 8000 字符上限、为什么 `history_messages` 单条截 `[:500]`——**系统用"每处都截一点"来替代"中途压缩"**。

### 5.5 两个库文件跨库联表做不到

`hybrid/store.py` 的 `_conn` 指向 `hybrid.db`，`core/scheduler.py` 的 `_conn` 指向 `scheduler.db`。SQLite 的 `ATTACH` 可以跨库，但**不能跨库做带索引优化的 JOIN**（实际会退化成全表扫描），且两个连接各自持锁时容易互相阻塞。

现状是**应用层拼装**：先查 `exec_logs` 拿 `run_id`，再用 `run_id` 去另一个库查。这没有性能问题（数据量小），但**没有事务一致性**——`run` 已落库而 `log` 还没落库的中间态是可能的。

### 5.6 APScheduler 多开会重复触发

`worker/scheduler.py` 用 `BlockingScheduler` + `SQLAlchemyJobStore`。如果 `systemd` 配了 `Restart=always` 但**没有**做单例保护（比如同一个 job store 被两个进程同时打开），两个 worker 会各自触发同一 cron。

项目里的防线是**幂等键**（`job_key|subject_id|planned_at`）+ `UNIQUE(idem_key)` + `ON CONFLICT DO NOTHING`——第二个 worker 的 `enqueue` 会静默失败，不会重复执行。但**这只防重复入队，不防重复调度**：cron 的 `next_run_time` 仍会被两个调度器各算一遍（结果相同，无害）。

真出问题的是：两个 worker 同时 `claim_pending` 抢到同一行——这由 CAS（`UPDATE ... WHERE status='pending' RETURNING *`）挡住。

### 5.7 `astream` 生成器提前关闭会丢终态

`aborted` 机制（3.7 的 `finally`）只覆盖**编排器自己的生成器**。如果 `AgentEngine` 内部的 `agen` 被提前 `aclose`，它的 `result` 可能还是 `None`，外层会拿到 `EngineResult(status="failed", error="引擎未返回结果")`。这不算 bug，但会**把"用户主动断开"记成"引擎失败"**——统计口径上要区分开。
