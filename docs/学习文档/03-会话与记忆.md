# 03 · 会话与记忆

> 本模块回答一个问题：**模型没有记忆，系统靠什么让它"记得"？**
>
> 答案不是"把全部聊天记录塞进去"，而是三层协作：
>
> 1. **SQLite 存原文**——事实来源，可追溯、可删除；
> 2. **压缩块管长期**——把旧轮次压成稳定前缀，省 token 且不破坏 KV 缓存；
> 3. **标签喂检索**——跨会话只保留"兴趣画像"，不保留全文。
>
> 第 3 点很重要：很多人会以为"跨会话记忆"等于"能翻到另一个会话的原文"。**本项目做不到，也没打算做到。**

## 1. 先建立直觉：三个会真实发生的故障

### 故障 A：聊到第 30 轮，模型忘了第 2 轮定下的约束

用户在开头说"回答不要超过三句话，我在准备答辩"。聊到第 20 轮，模型开始输出长段落。

原因不是"模型笨"，而是：

- 上下文窗口有上限；
- 项目对每个会话只保留 `MAX_HISTORY_TURNS=30` 轮（见 [core/session.py#L37](file:///c:/biancheng/agent-hub/core/session.py#L37)）；
- 更早的内容被截掉了，约束也随之消失。

**如果没有"长期记忆"层**：用户要么每轮重复约束，要么接受模型逐渐跑偏。

### 故障 B：直接把长摘要拼进 system prompt，KV 缓存全废

一个直觉的修法是：把旧对话压成一段摘要，拼到 system prompt 里。听起来很合理，实际会把成本打爆：

- system prompt 是**前缀**；
- KV 缓存（很多推理框架用来避免重复计算前文的机制）依赖"前缀逐字不变"；
- 摘要每轮都在变 → 前缀每轮都变 → 缓存永远不命中 → 每次请求都按全量重算。

项目实测的代价是**命中率从 90% 掉到 0%**（见 [agent/builder.py#L262-266](file:///c:/biancheng/agent-hub/agent/builder.py#L262-L266) 的注释）。

**如果没有正确的放置方式**：省下的 token 会以"缓存失效"的形式加倍还回去。

### 故障 C：标签乱写，检索被带偏

系统想"记住用户兴趣"，于是让模型随便输出标签。模型输出"学习""知识""问题"这种万能词，权重越堆越高，检索时所有片段都被"偏置"到这几类，真正相关的内容反而排后面。

**如果没有受控词表**：标签系统会从"辅助排序"退化成"随机扰动"。

## 2. LangChain 零基础补丁

本模块用到的 LangChain 概念不多，但有两个必须认识。

### 2.1 `Document`

白话：LangChain 对"一段文本 + 它的元数据"的封装。典型形态：

```python
Document(page_content="Transformer 的注意力机制……", metadata={"source": "note.pdf", "page": 3})
```

本项目的知识库检索返回的就是 `(Document, distance)` 列表。`kb_search` 工具里读 `d.metadata.get("source")`、`d.page_content`，就是在用它。

**它替我们做了什么**：把"文本"和"出处"绑在一起。没有它，检索结果就只是一段字符串，无法标注"第几页、哪个文件"，溯源和展示都会退化。

**本项目绕过它的地方**：没有用 LangChain 的 `VectorStore` / `Retriever` 抽象，而是直接用 Chroma + 自己的 `pipelines.retrieve_with_score`。原因是项目需要 BM25 + 向量混合召回、需要 `_to_similarity` 的统一口径、需要把 `distance is None` 的关键词独有召回保留原位——这些细节在通用 Retriever 接口里表达不了。

### 2.2 `BaseChatModel` / `ChatOpenAI` + `HumanMessage`

标签抽取那一步要调模型，见 [api/chat.py#L1776-1787](file:///c:/biancheng/agent-hub/api/chat.py#L1776-L1787)：

```python
llm = get_llm(temperature=0, max_tokens=48)
resp = llm.invoke([HumanMessage(content=prompt)])
```

- `get_llm` 返回 `ChatOpenAI`（OpenAI 兼容客户端），**不用 `init_chat_model`**——原因和模块 4 一样：第三方 provider 路由不稳。
- `temperature=0`：标签抽取要稳定，不要创造性。
- `max_tokens=48`：只允许输出一个短 JSON 数组，给长度兜底，防止模型写解释。
- `HumanMessage`：这里没有 system message，因为整段指令都写在一个 prompt 里。**注意这不是最佳实践**，只是这一步足够简单。

### 2.3 本模块**没用**的 LangChain 记忆类

| 常见写法 | 本项目 | 为什么不用 |
|---|---|---|
| `ConversationBufferMemory` / `ConversationSummaryMemory` | 没用 | 它们把记忆放在进程内存或框架对象里，重启丢、多进程不一致；项目要的是"SQLite 为唯一事实来源" |
| `VectorStoreRetrieverMemory` | 没用 | 会把每条消息向量化存一遍，成本和一致性都不可控 |
| `RunnableWithMessageHistory` | 没用 | 历史拼装规则要同时服务 vision / hybrid / agent / rag / llm 五条路径，框架封装反而藏住了"压缩块放哪、保留几轮"这些关键决策 |
| `Checkpointer` | **故意为 `None`** | 见模块 4；这里只需要知道：**历史由 `assemble_history` 手工拼，不交给 LangGraph** |

一句话：本模块的记忆是**自己写的 SQLite + 自己拼的消息数组**，LangChain 只提供模型客户端和 `Document` 容器。

## 3. 核心代码逐段吃透

### 3.1 连接管理：线程局部 + WAL + busy_timeout

见 [core/session.py#L65-99](file:///c:/biancheng/agent-hub/core/session.py#L65-L99)。

```python
_LOCAL = threading.local()

def _conn() -> sqlite3.Connection:
    path = _db_path()
    conn = getattr(_LOCAL, "conn", None)
    if conn is not None and getattr(_LOCAL, "path", None) == path:
        return conn
    if conn is not None:
        try: conn.close()
        except Exception: pass
    os.makedirs(os.path.dirname(path), exist_ok=True)
    conn = sqlite3.connect(path)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA synchronous=NORMAL")
    conn.execute("PRAGMA busy_timeout=5000")
    _LOCAL.conn = conn
    _LOCAL.path = path
    return conn
```

**在干什么**：每个线程一条连接，连接按 `path` 缓存；路径变了（测试换库）就关旧的、开新的。

**为什么这样写**：

- SQLite 连接**不能跨线程共享**（默认 `check_same_thread=True` 会直接报错）。`threading.local()` 是最便宜的隔离方式。
- FastAPI 的同步端点跑在线程池里，线程会复用；每次请求新建连接会反复做 `open` + `PRAGMA`，成本高。
- `WAL` 让读写不互相阻塞；`busy_timeout=5000` 让写锁竞争时"等 5 秒再报错"，而不是立刻 `database is locked`。

**换个写法会怎样**：

- 全局一个 `conn`：多线程并发会抛 `SQLite objects created in a thread can only be used in that same thread`。
- 每次请求 `sqlite3.connect()` 且不关：文件描述符泄漏，跑几天后 `Too many open files`。
- 用连接池（如 SQLAlchemy）：对这个项目是过度设计，SQLite 的并发度不值得。

### 3.2 `add_message`：为什么写之前还要再验一次归属

见 [core/session.py#L407-435](file:///c:/biancheng/agent-hub/core/session.py#L407-L435)。

```python
def add_message(owner, sid, role, content, refs="", truncated=False) -> int:
    if not _owned(owner, sid):
        raise NotOwned(sid)
    ...
    conn.execute("INSERT INTO messages ...")
    conn.execute("UPDATE conversations SET updated_at = ? WHERE id = ?", (now, sid))
    row = conn.execute("SELECT last_insert_rowid() AS id").fetchone()
    return row["id"]
```

**在干什么**：写入一条消息、更新会话时间、返回自增 id。

**为什么写前再验 `_owned`**：注释（[core/session.py#L398-404](file:///c:/biancheng/agent-hub/core/session.py#L398-L404)）说得很清楚——API 层通常已经用 `get_conversation(owner, sid)` 验过一次，这里是**纵深防御**。消息写入比读取更危险：写错会话等于把 A 的内容写进 B 的对话。

**为什么返回 `last_insert_rowid()`**：调用方（比如压缩、反馈、溯源）需要知道"这条消息的 id"。没有它，就要再查一次"最新一条"，而并发下"最新一条"可能已经是别人的。

**换个写法会怎样**：

- 只在 API 层验归属、DAO 不验：任何新调用方（定时任务、后台钩子）忘记验，就是一个越权写入口。
- `add_message` 不返回 id：压缩的 `compressed_upto` 无从确定，只能按时间戳猜，而同一秒可能有多条消息。

### 3.3 `get_messages`：为什么先倒序取 `limit*2+10` 再截断

见 [core/session.py#L612-669](file:///c:/biancheng/agent-hub/core/session.py#L612-L669)。

```python
cap = limit_turns * 2 + 10
rows = conn.execute(
    f"SELECT * FROM (SELECT {cols} {join} ORDER BY m.id DESC LIMIT ?) ORDER BY id ASC",
    (sid, owner, cap),
).fetchall()
...
user_indices = [i for i, m in enumerate(msgs) if m["role"] == "user"]
if len(user_indices) > limit_turns:
    start = user_indices[-limit_turns]
    msgs = msgs[start:]
```

**在干什么**：只取"最近 N 条"，再按"最后 N 个 user 消息"对齐轮次。

**为什么这样写**：

- 长会话全量载入既慢又占内存，而窗口截断只需要最近部分。
- **不能简单地 `LIMIT limit_turns*2`**：一轮不一定正好是 2 条——Agent 一次可能产出多段 assistant 消息、RAG 路径可能插 system 消息。多留 10 行缓冲，保证窗口起点不会把某一轮切半。
- 倒序取再翻转，等价于"全量后截断"，但只读 `cap` 行。这是用 SQL 的排序换 IO 的典型手法。
- 最后的截断以 **user 消息**为锚点，而不是按条数：这样不会出现"保留了一条 assistant 但没有对应的 user 提问"。

**换个写法会怎样**：

- 直接 `LIMIT limit_turns*2`：遇到多段 assistant 时窗口起点切半，模型看到"没有提问的回答"，容易答非所问。
- 全量 `SELECT` 再 `msgs[-limit*2:]`：30 轮还好，300 轮时每轮都读 300 轮的数据，白白浪费 IO。

### 3.4 为什么需要压缩块：滑动窗口的死结

先看问题。假设每轮请求都发"最近 6 轮原文"：

- 第 10 轮，发第 5~10 轮；
- 第 11 轮，发第 6~11 轮；
- 前缀（前 5 轮）每轮都在变 → **KV 缓存永远不命中**。

如果发"全部历史"：

- 第 30 轮时上下文巨大，token 成本线性上涨；
- 超过窗口上限直接被截断，而且截断点每轮都在动。

压缩块的解法是：**把"最近 K 轮之前"的旧内容压成一段，放在历史最前面；它只在压缩事件时增长，两次压缩之间逐字不变。** 这样：

- 前缀稳定 → KV 缓存命中；
- 旧内容变短 → token 可控；
- 最近 K 轮仍是原文 → 细节不失真。

核心常数（[core/context_compress.py#L44-52](file:///c:/biancheng/agent-hub/core/context_compress.py#L44-L52)）：

```python
MAX_SUMMARY_CHARS = 4000       # 压缩块最大字符
TRIGGER_RATIO = 0.8            # 超过上下文上限的 80% 才触发
KEEP_TURNS = 6                 # 默认保留最近 6 轮原文
KEEP_TURNS_EXPANDED = 12       # L2 安全阀扩容后的 K
MAX_SEGMENTS = 12              # 压缩块最大段数，超过就折叠最早的段
```

### 3.5 `assemble_history`：五条路径唯一的历史拼装入口

见 [core/context_compress.py#L767-798](file:///c:/biancheng/agent-hub/core/context_compress.py#L767-L798)。

```python
def assemble_history(owner, sid, raw_messages, *, keep_turns=None):
    if not getattr(config, "COMPRESS_ENABLED", True):
        return _clean(raw_messages)
    try:
        plan = plan_context(owner, sid, raw_messages, keep_turns=KEEP_TURNS ...)
    except Exception:
        return _clean(raw_messages)          # 压缩失败 → 降级为原样返回
    if not plan.summary_text:
        return _clean(raw_messages)          # 还没压缩过 → 原样直通
    out = [
        {"role": "user", "content": PRELUDE_HEAD + plan.summary_text},
        {"role": "assistant", "content": PRELUDE_ACK},
    ]
    out.extend(_clean(plan.kept))
    return out
```

**在干什么**：把"压缩块 + 最近 K 轮原文"拼成模型能吃的消息数组。

**为什么这样写**（这一段是本模块最值得反复读的）：

1. **异常一律降级为原样返回**。压缩是优化，不能成为对话失败的原因。如果压缩逻辑抛异常，用户应该看到"正常的全量历史"，而不是 500。
2. **没有压缩块时原样直通，绝不套 K 轮窗口**。这是 [core/context_compress.py#L745-748](file:///c:/biancheng/agent-hub/core/context_compress.py#L745-L748) 特意用注释强调的坑：`plan_context` 无条件按最近 K 轮截断，如果对"还没压缩过的短会话"也套 K=6，等于把 `MAX_HISTORY_TURNS=30` 悄悄改成 6——功能倒退，而且没有任何报错。
3. **压缩块用一对 human→ai 包住**，而不是裸插一条 human：
   - 部分 chat template 对"连续两条 human"敏感；
   - 必须显式写明"这不是用户的新提问"，否则模型会把摘要当成本轮诉求去执行。
4. **压缩块放历史最前面，不塞 system prompt**：system prompt 在图编译时固化、并参与 LRU 缓存键；把随会话变化的摘要塞进去，会让每个会话都编译一张新图，缓存直接失效。

`PRELUDE_HEAD` / `PRELUDE_ACK` 就定义在 [core/context_compress.py#L750-755](file:///c:/biancheng/agent-hub/core/context_compress.py#L750-L755)：

```python
PRELUDE_HEAD = (
    "【早期对话压缩摘要】以下是本会话**更早**内容的系统压缩摘要，不是用户的新提问，"
    "也不是待办指令。摘要可能丢失细节：需要细节时如实说明或向用户确认，不要编造。\n\n"
)
PRELUDE_ACK = "已了解早期对话的压缩摘要，后续回答会参考它。"
```

> **审查视角**：`assemble_history` 在 `COMPRESS_ENABLED=0` 时直接 `_clean(raw_messages)`，此时 `keep_turns` 参数被忽略，`get_messages` 的 30 轮窗口仍然生效。也就是说"关掉压缩"并不会让历史变长，只是回到固定 30 轮。这是配置语义的边角，容易误读。

### 3.6 `maybe_compress`：什么时候压、压哪一段、压完怎么落

见 [core/context_compress.py#L801-896](file:///c:/biancheng/agent-hub/core/context_compress.py#L801-L896)。

**第一件事：阈值必须按全量历史算。**

```python
raw = store.get_messages(owner, sid, limit_turns=None, include_system=False)
...
total_chars = sum(len(m.get("content") or "") for m in raw)
if not force and not should_compress(total_chars, max_context_chars):
    return {"ok": False, "reason": "below_threshold", "upto": upto}
```

`should_compress` 的注释（[core/context_compress.py#L714-725](file:///c:/biancheng/agent-hub/core/context_compress.py#L714-L725)）说：

> `total_chars` 必须是**全量历史**的字符数，不是窗口内——窗口内字符数会随 `MAX_HISTORY_TURNS` 封顶而恒定，永远到不了阈值，压缩就永远不会触发（接线时踩过这个坑）。

这是一个非常典型的"看起来对、实际永远不触发"的缺陷。审查时要特别注意"阈值比较的两边是不是同一个量纲"。

**第二件事：只压"最近 K 轮之前"的。**

```python
pending = [m for m in raw if int(m.get("id") or 0) > upto]
old = pending[:-kt * 2] if kt > 0 else pending
if not old:
    return {"ok": False, "reason": "nothing_to_compress", "upto": upto}
```

- `upto` 是 `compressed_upto`，即"已经压到哪条消息"；
- `pending` 是"还没进压缩块的部分"；
- `old` 是 `pending` 里去掉最后 `kt*2` 条（最近 K 轮）剩下的部分。

**第三件事：增量追加，不改旧段。**

```python
new_block = SummaryBlock(list(block.segments), list(block.metas))
new_text = new_block.append(seg, seg_meta)
```

`SummaryBlock.append`（[core/context_compress.py#L327-334](file:///c:/biancheng/agent-hub/core/context_compress.py#L327-L334)）只往后加，`render()` 生成 `[COMPRESSED-1] … [COMPRESSED-2] …`。**旧段的文字逐字不变**，所以前缀稳定，KV 缓存能命中。这是"增量"的全部意义。

**第四件事：安全阀 + 乐观锁。**

```python
decision = apply_safety_valve(seg_raw, new_text, prev, ...)
if decision.action == ACT_EXPAND_KEEP and decision.keep_turns != kt:
    return maybe_compress(..., keep_turns=decision.keep_turns, force=True)
if decision.action == ACT_ROLLBACK:
    return {"ok": False, "reason": decision.reason, "upto": upto}
new_upto = int(old[-1].get("id") or 0)
ok = commit_summary(owner, sid, new_text, new_upto, expected_upto=upto, ...)
```

`commit_summary`（[core/context_compress.py#L533-569](file:///c:/biancheng/agent-hub/core/context_compress.py#L533-L569)）用 `compressed_upto` 做 CAS：

```sql
UPDATE conversations SET compressed_summary = ?, compressed_upto = ?
WHERE id = ? AND owner_id = ? AND COALESCE(compressed_upto, 0) = COALESCE(?, 0)
```

**为什么需要乐观锁**：压缩是回答结束后的异步动作。用户可能在压缩完成前就发了下一轮，那一轮也可能触发压缩。两边都读到 `upto=100`、都想写 `upto=120`，如果没有 CAS，后写的会覆盖先写的，可能出现"压缩块里包含了已被另一版压缩的原文"——同一段内容在上下文里出现两遍，token 翻倍。

CAS 失败时返回 `race_lost（并发压缩，本轮放弃）`，下一轮再试。**放弃是安全的**，因为原文还在 SQLite 里，不会丢。

### 3.7 L0–L3 安全阀：压坏了怎么救

```python

    if prev_summary:
        return ValveDecision(ACT_ROLLBACK, "L0 实体丢失 → 回退上一版压缩块", base_keep_turns)
    return ValveDecision(ACT_EXPAND_KEEP, "L0 实体丢失且无上一版 → 扩大 keep_turns 重压", KEEP_TURNS_EXPANDED)

# L3 预判：token 仍超硬顶
if est_tokens_after > hard_limit_tokens:
    return ValveDecision(ACT_TRUNCATE, "压缩后仍超硬顶 → 硬截断最旧原文", base_keep_turns)

return ValveDecision(ACT_ACCEPT, "通过 L0 校验且未超硬顶", base_keep_turns)
```

**四档的实际含义**：

| 档位 | 触发条件 | 动作 | 为什么 |
|---|---|---|---|
| L0 | 新摘要丢了原文明明有的实体（URL、ID、文件名、待办关键词） | 有 prev → 回退；无 prev → 扩 K 重压 | 实体丢了就是事实丢失，不能接受 |
| L1 | L0 回退 | **保持库里现状不动** | 注释特别强调：不是把 prev 写回去，那会让 `compressed_upto` 倒退，已压缩的原文重新进上下文 |
| L2 | L0 丢实体且无 prev | 把 `keep_turns` 从 6 扩到 12，重压一次 | 压得更少、更保守；只重试一次，避免无限递归 |
| L3 | 压缩后 token 仍超硬顶 | 硬截断最旧原文 | 再压也没用，只能牺牲最旧内容 |

**为什么 L0 用规则而不是模型判断**：实体识别是确定性任务（正则匹配 URL / 编号 / 文件名），用模型判断会引入"这次觉得 URL 不重要、下次觉得重要"的漂移。安全阀本身必须稳定。

### 3.8 压缩失败怎么退化：三处降级

这是"工程坑点"里最该掌握的一条。压缩有三层降级，每一层都不让对话失败：

1. **生成失败**（`build_compressed_segment` 返回空）：`maybe_compress` 返回 `compressor_empty`，本轮不压，原文还在。
2. **写入冲突**（`commit_summary` 返回 False）：返回 `race_lost`，本轮放弃，下一轮再试。
3. **读取/组装异常**（`plan_context` 抛异常）：`assemble_history` 捕获后 `return _clean(raw_messages)`——**退化为"原始历史直通"**。

第 3 条的结果是：压缩坏了，用户看到的是"没有压缩的全量历史"，可能超长、可能慢，但**不会报错、不会丢消息**。这就是"压缩是优化项"的落地方式。

> **审查视角**：三层降级里，只有第 3 层是"静默"的（不写日志）。如果生产出现"上下文突然变长、缓存命中率下降"，最可能的原因就是 `plan_context` 在抛异常。建议给 `assemble_history` 的 `except` 加一条 warning 日志——这是当前代码可以改进的点，但不是缺陷。

### 3.9 压缩块的折叠：为什么只折"已入库"的低 salience 段

见 [core/context_compress.py#L336-362](file:///c:/biancheng/agent-hub/core/context_compress.py#L336-L362)。

当压缩块超过 `MAX_SEGMENTS=12` 或字符预算时，要折叠一些段。选择顺序：

1. v2 关闭 → 永远折最早的（v1 行为）；
2. meta 齐全且有 `staged`（已入库）段 → 从 staged 里挑 `salience` 最低的；
3. 否则 → 折最早的。

**为什么优先折"已入库"的**：注释写得很直白——"已入库的内容折掉只是释放，信息还在知识库里"。如果一段内容已经沉淀进知识库，压缩块里再保留一份就是冗余；折掉它不丢信息，只省 token。

**为什么 salience 低的先折**：`salience` 是"这段内容有多值得长期保留"的打分，四信号加权（[core/context_compress.py#L88-89](file:///c:/biancheng/agent-hub/core/context_compress.py#L88-L89)）：

```python
_W_TYPE, _W_SINGLETON, _W_OUTLIER, _W_EMOTION = 0.4, 0.25, 0.2, 0.15
```

- `type`：这段话属于哪类知识（约束/待办/偏好/纠正 权重最高）；
- `singleton`：这段是否只出现一次（只出现一次的信息更可能珍贵）；
- `outlier`：和其他段差异多大（差异大更可能是新信息）；
- `emotion`：强调强度（"必须""记住""不对"）。

**全是规则信号、零 LLM**。冷启动就能用，不依赖模型判断。

### 3.10 `user_tags` 的产生：三步 + 一道硬闸门

**第一步：抽取**（[api/chat.py#L1756-1804](file:///c:/biancheng/agent-hub/api/chat.py#L1756-L1804)）。


三个细节：

3. **`filter_known_tags(tags, limit=3)` 是硬闸门**。它先归一（"CET6 / 六级"→"英语四六级"），再丢弃一切词表外的标签。这一步决定了标签表不会爆炸。

**第二步：落库**（[api/chat.py#L1807-1814](file:///c:/biancheng/agent-hub/api/chat.py#L1807-L1814)）。


fire-and-forget（发起就返回，不等结果）：不阻塞 SSE 的 `done` 帧。整个函数外面还包了 `except: pass`，因为画像失败不能影响问答。

**第三步：权重累加**（[core/session.py#L441-472](file:///c:/biancheng/agent-hub/core/session.py#L441-L472)）。

```sql
INSERT INTO user_tags (owner_id, tag, weight, updated_at) VALUES (?, ?, ?, ?)
ON CONFLICT(owner_id, tag) DO UPDATE SET weight = weight + ?, updated_at = ?
```

同一个标签每出现一次，权重 +1。这里**只归一、不过滤**（注释 L447-449）：词表外的主题词（"数学""英语"）原样保留，因为检索偏置那边也会写词表外的主题。硬闸门只拦"模型自动抽标签"那条路。

**手选标签不同**（[core/session.py#L483-522](file:///c:/biancheng/agent-hub/core/session.py#L483-L522)）：

- 权重 `PICK_WEIGHT=3.0`：一次手选 ≈ 3 次对话证据；
- `MAX_PICKS=6`：再多就变"全选"，推荐退化成"什么都有"；
- **幂等**：`ON CONFLICT DO NOTHING`，反复提交不会把权重越堆越高；
- **可取消**：这次没选的、上次手选过的，从 picks 表删掉，但 `user_tags` 里那条记录保留（它可能同时是聊出来的证据）。

**这一段为什么这么写（图 2 圈出的"落库与副作用"）**

图 2 圈的是 `add_message`、标签、画像标签 fire-and-forget。这里的关键取舍是：

- **写原文是同步的、必须成功**：它是事实来源，写失败就应该报错；
- **写标签/画像/压缩是异步的、允许失败**：它们是优化项，失败只影响"下一轮会不会更懂你"，不影响"这一轮答不答"。

用一个判断标准就够了：**丢了它，用户这一轮还能不能用？** 能 → 异步；不能 → 同步。

**顺带一个真实坑**：`_schedule_compress`（[api/chat.py#L1839-1850](file:///c:/biancheng/agent-hub/api/chat.py#L1839-L1850)）里

```python
_t = asyncio.create_task(_compress_after_turn(uid, sid))
_BG_TASKS.add(_t)
_t.add_done_callback(_BG_TASKS.discard)
```

`_BG_TASKS` 是**强引用集合**。原因（L1853-1854）：后台任务在完成前如果只剩弱引用，会被 GC 回收，报 `Task was destroyed but it is pending!`，压缩就静默丢失。完成后 `discard` 避免集合无限增长。这是 asyncio fire-and-forget 的标准写法，缺一不可。

### 3.11 `user_tags` 怎么喂给检索：`_bias_rerank`

见 [kb/rag_core.py#L584-633](file:///c:/biancheng/agent-hub/kb/rag_core.py#L584-L633)。

```python
profile = _session.get_user_tags(owner, limit=config.RETRIEVAL_BIAS_TOP)   # 默认 8

return _bias_rerank(docs_scores, profile_tags, config.RETRIEVAL_BIAS_ALPHA) # 默认 0.08
```

`_bias_rerank` 的逻辑：

```python
for p in profile_tags:
    if any(p in s or s in p for s in segs):   # 双向包含
        overlap += 1
biased = max(0.0, float(distance) - alpha * overlap) if overlap else float(distance)
```

- 文档的 `metadata["topics"]` 是 `"数学分析|概率论"` 这种竖线分隔的主题串；
- 画像标签和任一主题**双向包含**即算命中（兼容"数学"粗标签命中"数学分析"细主题）；
- 命中越多，`distance` 减得越多（距离越小越相关）；
- `alpha=0.08` 很小：偏置是"微调排序"，不是"改写相关性"。

**为什么最终返回的是原始 `distance`**：调用方还要按它换算相似度和阈值。如果返回减过的值，阈值判断会被悄悄放宽，用户会觉得"检索不准"。

**这里有一个真实的线上 bug（已修）**：`distance is None`。

混合检索里，BM25 命中的片段可能没有向量距离。原代码直接 `float(distance)` → `TypeError`。触发条件是"用户有画像标签 + 命中关键词独有片段"两个同时成立，表现为**静默 500**（有日志但用户只看到失败）。

现在的处理（[kb/rag_core.py#L609-631](file:///c:/biancheng/agent-hub/kb/rag_core.py#L609-L631)）：

```python
if distance is None:
    slots.append((d, None, None, idx))   # 占位，待原样放回
...
ranked = iter(sorted((s for s in slots if s[2] is not None), key=lambda s: s[2]))
for slot in slots:
    if slot[2] is None:
        out.append((slot[0], None))      # 原位放回
    else:
        d, dist, _biased, _idx = next(ranked)
        out.append((d, dist))
```

**这段的精妙之处**：`None` 条目既不参与排序，也不改变位置，只是被"跳过"。重排只会重新分配那些有距离的槽位，`None` 继续占着它原来的第 i 格。这样既不会崩，也不会把关键词独有召回挤走。

**这一段为什么这么写（图 2 圈出的"压缩与长期记忆"）**

图 2 的第二个框是 `context_compress` / salience / 抽取式摘要 / 安全阀 / `commit_summary`。一句话总结动机：

> **长期记忆不是"记住更多"，而是"在有限预算下，把最该记住的留在稳定前缀里，把其余的可回退地折掉"。**

四个设计决定都可以用这句话解释：

- 压缩块前置而不是进 system：前缀稳定；
- 增量追加不改旧段：前缀只增长、不重写；
- 只折已入库的低 salience 段：折掉不丢信息；
- `compressed_upto` 乐观锁：宁可这轮不压，也不让两版摘要叠在一起。

## 4. 一条端到端数据流

场景：**早上 8:00，用户在一个已经聊了 40 轮的会话里，问"我上周说的那个复习计划，帮我按它排今天"。**

注意这个问题的陷阱：它听起来像"跨会话"，实际上系统**只能看到当前会话**。如果"上周那个计划"是在另一个会话里说的：

- 当前会话的 SQLite 原文里没有它；
- 压缩块里也没有它；
- **唯一可能跨会话带过来的，是 `user_tags` / 用户画像**（比如"考研数学""时间管理"），它影响检索排序，但不含具体计划内容。

所以正确的产品行为是：模型会回答"我这里看不到你上周的具体计划，能贴一下吗"，而不是编造一个。这一点在第 5 节会展开。

现在走当前会话的链路：

```
08:00:00  api/chat.py 收到提问
          ├─ 鉴权 + get_conversation(owner, sid) 验归属
          ├─ store.get_messages(owner, sid, limit_turns=30)
          │     └─ 倒序取 30*2+10=70 条，再按最后 30 个 user 消息对齐
          ├─ ctxcompress.assemble_history(owner, sid, raw_messages)
          │     ├─ load_summary_state → 拿到 compressed_summary + compressed_upto
          │     ├─ plan_context → summary_text + kept（id > upto 且最近 6 轮）
          │     └─ 拼成 [user: PRELUDE_HEAD+摘要, assistant: PRELUDE_ACK] + kept
          ├─ router.decide() 判 workflow / agent
          ├─ 生成回答（SSE 流式）
          ├─ add_message(user) → 返回 user_msg_id
          ├─ add_message(assistant) → 返回 ai_msg_id
          └─ 收尾：
                ├─ _record_user_tags(uid, question, answer)   fire-and-forget
                │     └─ llm.invoke → filter_known_tags → add_user_tags（权重 +1）
                └─ _schedule_compress(uid, sid)               fire-and-forget
                      └─ maybe_compress
                            ├─ get_messages(limit_turns=None)  全量
                            ├─ should_compress(total_chars)     > 12000*0.8
                            ├─ old = pending[:-12]             去掉最近 6 轮
                            ├─ build_compressed_segment        extractive（零 LLM）
                            ├─ SummaryBlock.append            旧段不动
                            ├─ apply_safety_valve              L0 实体 / L3 token
                            └─ commit_summary(compressed_upto CAS)
```

**08:00:05 下一轮用户提问时**：

- `assemble_history` 读到的压缩块已经多了一段；
- 前缀从 `[COMPRESSED-1] …` 变成 `[COMPRESSED-1] … [COMPRESSED-2] …`，**旧段逐字不变**，KV 缓存只失效新增的那一小段；
- 最近 6 轮仍是原文，所以"今天排计划"能接上刚才的上下文。

**08:05 调度任务 `delegate.dispatch` 触发**（跨进程，写 `scheduler.db`）：

- 它读的是 `delegations` 表和 `messages` 表（`sessions.db`）；
- 它**不会**读压缩块——每日总结要的是"今天真实说了什么"，不是"压缩后的摘要"；
- 两个库不同文件，写入不抢锁。

## 5. 工程坑点

### 5.1 "跨会话记忆"其实不存在

这是最容易被宣传语误导的一点。系统里跨会话的只有：

- `user_tags` / `user_profiles`（兴趣画像，特征是粗粒度的主题，不含事实）；
- 用户手选的标签。

**不跨会话的**：

- `messages` 原文（按 `conversation_id` 隔离）；
- `compressed_summary`（存在 `conversations` 表，按会话一行）；
- hybrid 的 `workflow_runs`（按 run 隔离）。

所以"帮我把上周在另一个会话里说的计划找出来"这种请求，正确的行为是**明确说看不到**。如果模型答得很具体，那大概率是编的。审查时看到"跨会话回忆"的功能描述，第一反应应该是查它到底读了哪张表。

### 5.2 SQLite 单写者 + 两个库文件不能联表

`session.py` 写 `sessions.db`，`scheduler.py` 写 `scheduler.db`，`hybrid/store.py` 写 `hybrid.db`。

- WAL 允许多读单写；
- `busy_timeout=5000` 只是"等 5 秒"，不是"并发写"；
- **SQLite 不支持跨文件 JOIN**（没有 `ATTACH` 的情况下）。

"某用户今天有没有收到早报"需要：

```python
# 伪代码，示意两次查询 + 内存合并
msgs = session.get_messages(owner, sid, ...)          # sessions.db
runs = scheduler.list_runs(job_key="report.daily")    # scheduler.db
```

两次查询之间数据可能变，所以不能把它当一致快照。

### 5.3 压缩只在两轮之间发生

`maybe_compress` 在回答结束后调用。这带来两个后果：

- **单轮超长救不了**：用户粘贴 5 万字，这一轮的上下文仍然超限，压缩要等下一轮才生效；
- **压缩有延迟**：刚聊完的 6 轮不会立刻进摘要，它们是"最近 K 轮原文"，这是设计如此（保留细节）。

### 5.4 标签写入失败是静默的

`add_user_tags` 里 `except Exception: pass`（[core/session.py#L471-472](file:///c:/biancheng/agent-hub/core/session.py#L471-L472)）。这意味着：

- 数据库锁冲突、磁盘满、schema 迁移失败，都会表现为"标签没增长"；
- 没有任何日志。

这是刻意的（画像不能拖垮问答），但排障时要主动去查 `user_tags` 表有没有在涨，而不是等日志。

### 5.5 压缩块的 `staged` 依赖"已入库"，而入库是异步的

`_pick_fold_indices` 只折 `staged=True` 的段。如果入库流程慢/失败，段一直是 `staged=False`，折叠就退化成"折最早的"（v1 行为）。这不是 bug，是**降级路径**；但如果你以为"v2 一定会按 salience 折"，就会读错。

### 5.6 KV 缓存的三个前提，缺一不可

1. system prompt 逐字不变（定位信息挪到末尾，见 [agent/builder.py#L321-327](file:///c:/biancheng/agent-hub/agent/builder.py#L321-L327)）；
2. 压缩块旧段不重写（`append` 不改旧段）；
3. 工具清单稳定（激活集在请求开始时取定，整轮不变）。

任何一条被破坏，缓存命中率都会掉。这不是"优化建议"，是**功能约束**。

### 5.7 压缩块里的实体丢失，L0 只能"回退"不能"修复"

`missing_entities` 只能发现"新摘要少了某个实体"，不能自动把它补回去。有 prev 就回退，没 prev 就扩 K 重压。**如果重压仍然丢**，代码不会再救——它会接受 L2 的结果。也就是说 L0 是"尽力而为"，不是"保证不丢"。真正的兜底是"原文还在 SQLite 里"。

R1：默认 30 轮（`MAX_HISTORY_TURNS`）；压缩后保留最近 6 轮原文（`KEEP_TURNS`），L2 扩容到 12。

R2：已经压进压缩块的最大 message id。`maybe_compress` 只处理 `id > upto` 的 pending 消息，所以不会重复压。

R3：30 条。`normalize_tag` 只做归一（"CET6"→"英语四六级"），归不上原样返回；`filter_known_tags` 是硬闸门，会把词表外的全部丢掉。

R4：原样直通（`_clean(raw_messages)`），**不套 K 轮窗口**。

R5：`alpha=0.08`；`biased = max(0.0, distance - alpha * overlap)`，即命中越多距离减得越多。
</details>

### 第二层：理解

**U1.** 为什么压缩块要放在历史最前面，而不是塞进 system prompt？

**U2.** 为什么 `maybe_compress` 的阈值必须用"全量历史"而不是"窗口内历史"？

**U3.** `commit_summary` 用 `compressed_upto` 做乐观锁。如果两个压缩同时成功提交，会发生什么？

**U4.** 为什么 `add_message` 在 API 层已经验过归属后，DAO 里还要再验一次？

**U5.** 为什么 `_bias_rerank` 返回原始 `distance` 而不是偏置后的值？

**U6.** 为什么标签抽取里 `get_llm()` 必须写在 `try` 里面？

<details>
<summary>答案要点</summary>

U1：system prompt 参与图编译的 LRU 缓存键，且是 KV 缓存前缀；把随会话变化的摘要塞进去会让每个会话编译一张新图、前缀每轮变化。压缩块放历史最前面，是"稳定前缀"，只在压缩事件时增长。

U2：窗口内字符数被 `MAX_HISTORY_TURNS` 封顶，永远到不了 80% 阈值，压缩永远不会触发。

U3：第二个提交的 `WHERE COALESCE(compressed_upto,0)=COALESCE(旧值,0)` 不匹配，`rowcount=0`，返回 False，调用方记 `race_lost` 放弃。**不会**出现两版摘要叠加。

U4：纵深防御。API 层校验可能被新调用方（定时任务、后台钩子）遗漏；消息写入比读取更危险，多一次约 0.1ms 的 EXISTS 很便宜。

U5：调用方要按 `distance` 换算相似度和阈值。返回偏置后的值会悄悄放宽阈值，表现为"检索不准"。

U6：`ChatOpenAI` 构造时就会校验 key，没配 key 是构造即抛；放在 try 外，"失败返回空列表"的承诺失效。
</details>

<details>
<summary>答案与判分标准</summary>

**C1（10 分）**

- 缺陷（4 分）：去掉了 `try/except` 和 `llm_gate.try_ticket()`。后台任务抛异常会冒到事件循环，`create_task` 的异常没人 await，可能只打一条 "Task exception was never retrieved"；更糟的是压缩失败会影响后续 `_BG_TASKS.discard` 的执行。
- 影响（4 分）：压缩静默中断；日志里出现未回收异常；如果异常类型是 `BaseException` 子类（如 `CancelledError` 处理不当），可能影响整个请求的收尾。
- 修复（2 分）：恢复 `try/except: pass` + `finally` 释放 ticket；闸满时直接 return。

**C2（10 分）**

- 缺陷（4 分）：读取用了 `limit_turns=30`，`total_chars` 变成"窗口内"字符数，被 `MAX_HISTORY_TURNS` 封顶。
- 影响（4 分）：压缩永远不会触发（除非单窗口本身就超 9600 字）；长期看上下文一直膨胀到窗口上限，然后被硬截断，早期约束丢失。
- 修复（2 分）：`get_messages(..., limit_turns=None)`。

**C3（10 分）**

- 缺陷（4 分）：`WHERE conversation_id = ?` 没有 JOIN `conversations` 校验 `owner_id`。任何人拿到别人的 `sid` 就能读别人的聊天记录。
- 影响（4 分）：越权读取——这是**严重级别最高**的一类缺陷，直接泄露用户隐私；而且因为 sid 是 12 位 hex、可枚举性低，容易被误判为"不可利用"。
- 修复（2 分）：`JOIN conversations c ON m.conversation_id = c.id WHERE m.conversation_id = ? AND c.owner_id = ?`。

**判分建议**：缺陷 4 分、影响 4 分（能说"越权/隐私泄露"才给满）、修复 2 分。
</details>

## 附：本模块的"读错清单"

1. **把"跨会话记忆"读成"能翻另一个会话的原文"**：做不到。跨会话只有粗粒度标签。
2. **把 `compressed_upto` 读成"压缩了多少条"**：它是"压到哪条消息 id"，不是计数。
3. **把 `assemble_history` 的"无压缩块直通"读成"永远只用 6 轮"**：只有存在压缩块时才按 K 轮保留。
4. **把 `filter_known_tags` 读成"标签白名单"**：它同时做归一（别名 → 规范名），不只是过滤。
5. **把 `_bias_rerank` 的偏置读成"改写相似度"**：返回的仍是原始 distance，偏置只影响排序。
6. **把压缩失败读成"对话失败"**：三层降级保证对话继续，只是上下文可能变长。
7. **把 `distance is None` 读成"数据缺失"**：它是 BM25 关键词独有召回的合法状态，不是脏数据。
