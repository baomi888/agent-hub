# 05 · AI 代码审查能力诊断包

> **先说结论：在你没有做题之前，我无法判断你现有的代码审查水平。**
>
> 这份包不是教程，是**基线测量工具**。它测的不是"你知不知道 LangChain"，而是四件更底层的事：
>
> 1. 你能不能在一段看似正常的代码里**定位**缺陷；
> 2. 你能不能把缺陷翻译成**生产影响**（而不是只说"这里不对"）；
> 3. 你能不能给出**最小修复**（只改必要行，不顺手重构）；
> 4. 你会不会因为注释写得专业就**放过**实现里的问题。
>
> 14 道题，满分 28 分。请**先做完再看答案**。中途查文档、问 AI 都算无效——这份包要测的是"你独立面对一段陌生代码时的第一反应"。

## 使用方式（3 分钟读完）

1. **计时**：整套 90 分钟。单题建议不超过 6 分钟；超时就写下"我卡在哪"，那本身就是诊断信息。
2. **作答格式**：每题写三行——`缺陷位置` / `为什么是缺陷` / `生产影响`。第三组（最小修复）额外给 diff。
3. **不要跳过第四组**：抗误导题最容易"一看就懂"，也最容易全军覆没。
4. **判分只看要点命中，不看措辞**。答案里给了"给几分"的口径，自己按条勾。
5. 做完把分数填进文末的[自评表](#自评表)，然后按[30 天训练法](#30-天训练法)练。

**评分总表**

| 分数 | 等级 | 含义 |
|---|---|---|
| 0–7 | L0 能读但不辨风险 | 能看懂代码在做什么，但看不出哪里会炸；给 diff 往往是整段重写 |
| 8–14 | L1 能定位但说不清影响 | 能找到可疑行，但"会怎样"只能说到"可能出错" |
| 15–21 | L2 能定位 + 说影响，修复不最小 | 判断基本对，但修复常顺带重构、改超范围 |
| 22–28 | L3 接近可独立 review | 定位准、影响分级清楚、修复克制，且不被注释带偏 |

> 28 分不是"满分毕业"。L3 的含义是"你可以开始给别人的 PR 写 review 了"。

### Q1 · 并发 / 幂等

**这段缺陷代码对应项目真实逻辑**：[core/scheduler.py#L365-394](file:///c:/biancheng/agent-hub/core/scheduler.py#L365-L394)（`claim_pending`）。真实版本用 `UPDATE ... WHERE status='pending' AND run_id IN (...) RETURNING *` 做 CAS；下面是**去掉 CAS 的错误改写**。

```python
# 缺陷版本（改写自 core/scheduler.py 的 claim_pending）
def claim_pending(limit=50, now=None):
    ts = now_ts() if now is None else int(now)
    with _get_conn() as conn:
        rows = conn.execute(
            "SELECT * FROM job_runs WHERE status = 'pending' "
            "ORDER BY planned_at ASC LIMIT ?", (limit,)
        ).fetchall()
        ids = [r["run_id"] for r in rows]
        for rid in ids:
            conn.execute(
                "UPDATE job_runs SET status='running', attempts=attempts+1, started_at=? "
                "WHERE run_id = ?", (ts, rid),
            )
        return [dict(r) for r in rows]
```

**考点**：SELECT 与 UPDATE 之间的时间窗；两个 worker 并发时的双领。

**参考作答要点**：
- 缺陷：`SELECT` 和 `UPDATE` 分成两条语句，中间没有条件保护。两个 worker 同时执行时，两边 `SELECT` 都能看到同一批 `pending` 行。
- 正确做法：把状态判断放进 `UPDATE ... WHERE status='pending'`（CAS），靠 `rowcount` 或 `RETURNING` 决定谁赢。
- 影响：同一个 `planned_at` 的早报被两个 worker 各发一遍；`attempts` 被加两次，重试次数提前耗尽。

**判分**：指出"SELECT/UPDATE 非原子"给 1 分；说清"两个 worker 会领到同一行"给 1 分。只说"有并发问题"不给分。

### Q2 · 异常吞掉

**对应真实逻辑**：[core/session.py#L441-472](file:///c:/biancheng/agent-hub/core/session.py#L441-L472)（`add_user_tags`）。真实版本是"整批一个 `try`，失败静默但不影响主流程"；下面是改成**逐条 try + continue** 的错误版本。

```python
# 缺陷版本（改写自 core/session.py 的 add_user_tags）
def add_user_tags(owner: str, tags: list[str], delta: float = 1.0) -> None:
    if not owner or not tags:
        return
    now = int(time.time())
    for t in tags:
        try:
            t = tag_taxonomy.normalize_tag(t).strip("|").strip()
            if not t:
                continue
            with _get_conn() as conn:
                conn.execute(
                    "INSERT INTO user_tags (owner_id, tag, weight, updated_at) VALUES (?, ?, ?, ?) "
                    "ON CONFLICT(owner_id, tag) DO UPDATE SET weight = weight + ?, updated_at = ?",
                    (owner, t, delta, now, delta, now),
                )
        except Exception:
            continue
```

**考点**：逐条吞异常导致**部分写入**；调用方以为"三个标签都记上了"，实际只记了一个。

**参考作答要点**：
- 缺陷：每条标签一个独立事务，中间失败就跳过，前面的已提交、后面的丢失，**没有整体成功/失败语义**。
- 缺陷（更隐蔽）：`except Exception: continue` 把"数据库锁超时""磁盘满""schema 变更"全部吞掉，日志里一个字都没有。
- 影响：画像标签长期只记上一部分；检索偏置看起来"生效了"但只偏了一半；排查时无从下手——因为没有任何失败记录。

**判分**：答出"部分写入"给 1 分；答出"静默吞异常导致不可观测"给 1 分。只说"异常被吞了"给 0.5。

### Q3 · 边界值

**对应真实逻辑**：[core/session.py#L612-669](file:///c:/biancheng/agent-hub/core/session.py#L612-L669)（`get_messages`）。真实版本先用 `limit_turns * 2 + 10` 多取缓冲，再按最后一个 user 锚点截断；下面是**直接切片**的错误版本。

```python
# 缺陷版本（改写自 core/session.py 的 get_messages）
def get_messages(owner: str, sid: str, limit_turns: int = 30) -> list[dict]:
    with _get_conn() as conn:
        rows = conn.execute(
            "SELECT m.id, m.role, m.content, m.created_at "
            "FROM messages m JOIN conversations c ON m.conversation_id = c.id "
            "WHERE m.conversation_id = ? AND c.owner_id = ? "
            "ORDER BY m.id DESC LIMIT ?",
            (sid, owner, limit_turns * 2),
        ).fetchall()
    msgs = [dict(r) for r in reversed(rows)]
    return msgs
```

**考点**：`limit_turns * 2` 假设"一轮 = 一条 user + 一条 assistant"，但实际一轮可能产出多条 assistant（工具调用中间态、分段输出）。

**参考作答要点**：
- 缺陷：窗口可能从**半轮中间**开始——第一条是 assistant 或 tool 消息，历史里出现"没头"的回复。
- 缺陷：只取 `limit_turns * 2` 行，若某轮 assistant 有多条，user 轮数实际不足 30，模型"记得"比预期更少。
- 影响：模型看到一段以 assistant 开头的历史，容易把上一轮的回答当成本轮上下文复述；部分模型对"首条非 user"直接报错。
- 正确做法：多留缓冲（真实代码 `* 2 + 10`），再按 `user` 锚点倒着数，从第 `limit_turns` 个 user 的位置切。

**判分**：说清"会在轮中间切开"给 1 分；说清"round ≠ 2 条消息"给 1 分。

### Q4 · 资源泄漏 + SQL 拼接

**对应真实逻辑**：[core/session.py#L65-99](file:///c:/biancheng/agent-hub/core/session.py#L65-L99)（`threading.local` 连接复用）与 [core/session.py#L612-651](file:///c:/biancheng/agent-hub/core/session.py#L612-L651)（归属校验 JOIN）。

```python
# 缺陷版本（两处缺陷）
def list_conversations(owner: str) -> list[dict]:
    conn = sqlite3.connect(db_path())          # ① 每次新建，从不 close
    sql = "SELECT id, title FROM conversations WHERE owner_id = '" + owner + "'"   # ② 拼接
    rows = conn.execute(sql).fetchall()
    return [{"id": r[0], "title": r[1]} for r in rows]
```

**考点**：SQLite 连接是文件句柄 + 内存页缓存，不关会导致 fd 泄漏和锁堆积；字符串拼接是注入入口。

**参考作答要点**：
- 缺陷 ①：`sqlite3.connect()` 返回的连接没有 `close()`，也没有 `with` 上下文。高频请求下 fd 耗尽，表现是 `OSError: too many open files` 或 `database is locked`。
- 缺陷 ②：`owner` 直接拼进 SQL。若 `owner` 来自 token 之外的任何输入（比如管理员后台传的 `owner_id` 参数），可以构造 `' OR '1'='1` 读出全表；SQLite 里还能用 `' UNION SELECT ...` 拼接。
- 影响分级：注入 = **高危**（越权读全量会话）；泄漏 = **中危**（服务运行数小时后开始 500）。
- 修复方向：用参数化 `?`；用模块级 `threading.local` 连接或 `with conn:` 确保释放。

**判分**：两处各 1 分。只发现拼接、没发现泄漏，给 1 分；只说"SQL 不安全"但说不出怎么利用，给 0.5。

**对应真实逻辑**：[core/session.py#L831](file:///c:/biancheng/agent-hub/core/session.py#L831)（`delete_messages`）与 [core/session.py#L612-636](file:///c:/biancheng/agent-hub/core/session.py#L612-L636)（`get_messages` 的 JOIN 归属校验）。

```python
# 缺陷版本
def delete_messages(conversation_id: str, ids: list[int]) -> int:
    if not ids:
        return 0
    with _get_conn() as conn:
        cur = conn.execute(
            "DELETE FROM messages WHERE conversation_id = ? AND id IN ({})".format(
```

### Q6 · 调度重复执行

**对应真实逻辑**：[worker/scheduler.py#L383-470](file:///c:/biancheng/agent-hub/worker/scheduler.py#L383-L470)（`build_scheduler`）与 [core/scheduler.py#L83](file:///c:/biancheng/agent-hub/core/scheduler.py#L83)（`RUN_KEEP_DAYS`）。

```python
# 缺陷版本
def build_scheduler():
    sch = BlockingScheduler(
        jobstores={"default": SQLAlchemyJobStore(url=f"sqlite:///{SCHED_DB}")},
    )
    sch.add_job(run_pending, CronTrigger.from_crontab("*/5 * * * *"), id="pending")
    sch.add_job(run_housekeeping, CronTrigger.from_crontab("30 2 * * *"), id="cleanup")
    return sch
```

**考点**：`max_instances` / `coalesce` / `misfire_grace_time` 全部用默认值；多 worker 同时开同一个 job store。

**参考作答要点**：
- 高危方向：两个 `agent-hub-worker` 进程同时打开同一个 `SQLAlchemyJobStore`，同一个 cron 被触发两次。项目用幂等键 + `UNIQUE(idem_key)` 挡住了**重复入队**，但挡不住"两次 `run_pending` 同时扫表"——这要靠 `claim_pending` 的 CAS。**若 CAS 也缺（见 Q1），就是重复发早报。**
- 中危方向：`run_pending` 本身耗时超过 5 分钟时，下一次 cron 会在上一轮还没结束时启动，两次同时对同一批 pending 行操作。默认 `max_instances=1` 在**同一调度器实例内**会跳过，但多进程不生效。
- 低危方向：默认 `misfire_grace_time` 让错过触发的任务在恢复后补跑；`coalesce` 默认 False 时会补跑多次。
- 分级答案：**高危**（重复执行，用户收到两条早报、配额被扣两次）。

**判分**：定级正确给 1 分；说清"多进程 × 默认参数 × 缺 CAS"这条链路给 1 分。只写"可能重复执行"给 0.5。

### Q7 · 压缩失败静默

**参考作答要点**：
- 高危：如果实现改成"先 `UPDATE compressed_upto` 再 `INSERT` 摘要"且两步不在一个事务里，摘要没写进去但 `compressed_upto` 已推进 → `assemble_history` 把 `id <= compressed_upto` 的消息全部丢弃 → **用户历史凭空消失**，且没有任何报错。

- 关键判断：真实代码用 `compressed_upto` 做 CAS（`WHERE compressed_upto = <旧值>`）并要求"这次提交的块必须包含上一块"，就是为了让"摘要没写成"时**不推进游标**。

**判分**：定级高危给 1 分；说清"游标前进但摘要为空 = 丢历史"给 1 分。

### Q8 · 审批绕过

**对应真实逻辑**：[core/tool_guard.py#L161-178](file:///c:/biancheng/agent-hub/core/tool_guard.py#L161-L178)（`pending` 里存 `(工具名 → 确认串)`，必须**相等**才执行并 `pop`）。下面是**只比工具名**的错误版本。

```python

        pass
```

- 分级答案：**高危**（越权写外部状态 / SSRF 下载）。

**判分**：定级高危给 1 分；说清"参数变了还能过"给 1 分。

### Q9 · CAS

**对应真实逻辑**：[core/scheduler.py#L365-394](file:///c:/biancheng/agent-hub/core/scheduler.py#L365-L394)。真实版本在内外两层 `WHERE` 都带 `status = 'pending'`。

```python
# 缺陷版本
rows = conn.execute(
    "UPDATE job_runs SET status = ?, attempts = attempts + 1, started_at = ? "
    "WHERE run_id IN (SELECT run_id FROM job_runs WHERE status = ? "
    "ORDER BY planned_at ASC LIMIT ?) RETURNING *",
    (STATUS_RUNNING, ts, STATUS_PENDING, n),
).fetchall()
```

**要求**：给最小 diff。

**参考作答要点**：

```diff
 rows = conn.execute(
     "UPDATE job_runs SET status = ?, attempts = attempts + 1, started_at = ? "
     "WHERE run_id IN (SELECT run_id FROM job_runs WHERE status = ? "
-    "ORDER BY planned_at ASC LIMIT ?) RETURNING *",
+    "ORDER BY planned_at ASC LIMIT ?) AND status = ? RETURNING *",
-    (STATUS_RUNNING, ts, STATUS_PENDING, n),
+    (STATUS_RUNNING, ts, STATUS_PENDING, n, STATUS_PENDING),
 ).fetchall()
```

- 为什么外层也要带：内层 `SELECT` 只是"挑候选"，两条并发 UPDATE 各自的 `SELECT` 都可能挑到同一行；外层 `AND status='pending'` 才是真正的 CAS——第二个 UPDATE 执行时那一行已是 `running`，`rowcount` 为 0。
- 为什么改了参数元组：多一个占位符必须多一个值，否则 `sqlite3` 抛 `ProgrammingError`。
- **只看 diff 行数**：这是 2 行改动（含参数行）。改成"先 SELECT 再逐条 UPDATE"或"加锁"都算超范围，扣分。

**判分**：外层加条件给 1 分；参数同步给 1 分。只改条件不改参数（会直接崩）给 1 分——说明"读懂了但没跑过"。

```diff
+            "WHERE m.conversation_id = ? AND c.owner_id = ? ORDER BY m.id ASC",
+            (sid, owner),
         ).fetchall()
     return [dict(r) for r in rows]
```

- 为什么是"加条件"不是"删参数"：删掉 `sid` 参数只能让调用方没法传，但数据库层仍然允许按会话 id 直查——下次有人加个新接口就绕过了。**校验要在数据层**。
- 返回空列表而不是抛 404 也可以（真实代码就是返回 `[]`），但调用方必须知道"空"有两种含义：会话不存在 / 会话是别人的。两者对外应统一为"不存在"，避免侧信道。
- **diff 行数**：4 行（函数签名、SELECT、WHERE、参数元组）。

**判分**：JOIN + owner 条件给 1 分；参数同步给 1 分。改成"先用 `get_conversation` 查再调"也算正确但多一次查询，给 1 分。

### Q11 · 重试退避

**对应真实逻辑**：[core/scheduler.py#L461-466](file:///c:/biancheng/agent-hub/core/scheduler.py#L461-L466)（`_backoff_target`）与 [core/scheduler.py#L62-63](file:///c:/biancheng/agent-hub/core/scheduler.py#L62-L63)（`MAX_ATTEMPTS=3`、`BACKOFF_MINUTES=(1,5,15)`）。

```python
# 缺陷版本
def _backoff_target(attempts: int, finished_at: int) -> int | None:
    if attempts > MAX_ATTEMPTS:
        return None
    idx = min(attempts, len(BACKOFF_MINUTES) - 1)
    return finished_at + BACKOFF_MINUTES[idx] * 60
```

**要求**：给最小 diff，并列出**两处**边界错误。

**参考作答要点**：

```diff
-    if attempts > MAX_ATTEMPTS:
+    if attempts >= MAX_ATTEMPTS:
         return None
-    idx = min(attempts, len(BACKOFF_MINUTES) - 1)
-    return finished_at + BACKOFF_MINUTES[idx] * 60
+    idx = max(0, min(int(attempts) - 1, len(BACKOFF_MINUTES) - 1))
+    return int(finished_at) + BACKOFF_MINUTES[idx] * 60
```

- 错误 1：`>` 而不是 `>=` → `attempts=3` 仍会返回时间，**多跑一次**（第 4 次）。真实语义是"最多 3 次"，第 3 次失败后不再重试。
- 错误 2：`attempts` 从 1 开始计，`BACKOFF_MINUTES[0]=1` 应该对应第 1 次失败；`idx=attempts` 让第 1 次失败等 5 分钟（因为 `attempts=1` → `idx=1`），第 2 次等 15 分钟，第 3 次也是 15 分钟（被 `min` 夹住）。退避整体右移一档。
- **diff 行数**：3 行。

**判分**：两处各 1 分。只改 `>=` 没改 `idx`，给 1 分；两处都改对，2 分。

### Q12 · "线程安全"的注释

**对应真实逻辑**：[hybrid/orchestrator.py#L50-75](file:///c:/biancheng/agent-hub/hybrid/orchestrator.py#L50-L75)。真实版本用 `threading.Lock` 包住 `_MANUAL` 的所有读写。

```python
# 缺陷版本
# 人工切换指令表。模块级 dict 由 CPython 的 GIL 保护，
# 写操作是原子的，无需额外加锁；peek/take 都是 O(1) 字典操作。
_MANUAL: dict[str, str] = {}

def request_manual_switch(run_id: str, action: str) -> None:
    _MANUAL[run_id] = action

def _peek_manual(run_id: str) -> str | None:
    return _MANUAL.get(run_id)

def _take_manual(run_id: str) -> str | None:
    return _MANUAL.pop(run_id, None)
```

**考点**：GIL 保证单条字节码原子，**不保证复合操作原子**；`pop` 与 `get` 之间的"检查后消费"是竞态。

**参考作答要点**：
- 缺陷：注释说"GIL 保护、写操作原子"——单条 `_MANUAL[run_id]=` 确实原子，但业务需要的是**两条操作**的组合原子性：`_peek` 看到有指令 → 引擎让出 → `_take` 消费。在这两步之间，API 线程可能又写入一条新指令，或另一个执行线程把同一条 `pop` 走。
- 更实际的问题：`dict.pop` 在 CPython 里是原子的，但"先 peek 再 take"不是。真实代码用 `threading.Lock` 是对的。
- 影响：**中危**——最坏情况是人工切换指令被消费两次或丢失，任务切到错误模式；不会崩，但行为不可解释。
- 判断依据：**看有没有锁，不看注释怎么写**。注释里出现"GIL 保证""无需加锁""原子"这几个词，第一反应应该是去找复合操作。

**判分**：指出"peek + take 不是原子组合"给 1 分；指出注释在误导/应加锁给 1 分。只说"dict 不是线程安全的"给 0.5（这句话本身不准确）。

### Q13 · "幂等"的注释

**对应真实逻辑**：[core/scheduler.py#L257](file:///c:/biancheng/agent-hub/core/scheduler.py#L257)（`idem_key = job_key|subject_id|planned_at`，`planned_at` 由 cron 算出的**计划时刻**，同一次计划恒定）。

```python
# 缺陷版本
def enqueue_job(job_key: str, subject_id: str, trigger: str = "manual") -> str:
    """登记一次任务。使用唯一幂等键，重复调用不会产生重复行。"""
    planned_at = int(time.time())        # ← 每次调用都不同
    key = f"{job_key}|{subject_id}|{planned_at}"
    with _get_conn() as conn:
        conn.execute(
            "INSERT INTO job_runs (job_key, subject_id, planned_at, idem_key) "
            "VALUES (?, ?, ?, ?) ON CONFLICT(idem_key) DO NOTHING",
            (job_key, subject_id, planned_at, key),
        )
    return key
```

**考点**：幂等键必须由**业务计划**决定，不能由"调用时刻"决定。

**参考作答要点**：
- 缺陷：`planned_at = now` 让每次调用的 `idem_key` 都不同。`ON CONFLICT` 永远不会命中，重复调用就是多行。
- 反例场景：用户狂点"立即执行"三次 → 三行 pending → 三次早报。
- 真实做法：`planned_at` 来自 cron 计算出的计划时刻（同一个 08:00 只对应一个整数），手动触发则传一个"用户显式指定的时刻"（`run-now` 用 `planned_at` 传当前分钟取整或调用方给的键）。
- 附带缺陷：注释说"重复调用不会产生重复行"，但实现根本不满足——**注释在描述意图，没描述事实**。
- 影响：**中危**（重复执行，可能重复扣配额；配合 Q1 的缺 CAS 会升级为高危）。

**判分**：指出 `time.time()` 让 key 不稳定给 1 分；指出注释与实现不符给 1 分。

### Q14 · "已校验"的注释

**对应真实逻辑**：[core/tool_registry.py#L143-146](file:///c:/biancheng/agent-hub/core/tool_registry.py#L143-L146) 与 [core/tool_registry.py#L227](file:///c:/biancheng/agent-hub/core/tool_registry.py#L227)。项目曾在 `TOOL_PLAYBOOK` 为空字典时，`assert_playbook_complete()` 对空集合做全称判断**恒为真**——审计报告把这叫"假校验"。

```python
# 缺陷版本
def assert_playbook_complete(playbook: dict[str, str]) -> None:
    """校验每个工具都有完整的 playbook。缺任何一条就拒绝启动。"""
    for name, text in playbook.items():
        missing = [s for s in PLAYBOOK_SECTIONS if s not in text]
        assert not missing, f"{name} 缺少小节：{missing}"

def assert_meta_complete(meta: dict[str, object], tool_names: set[str]) -> None:
    """校验工具元数据覆盖全部工具。"""
    assert set(meta.keys()) == tool_names, "TOOL_META 与 AGENT_TOOLS 名字集合不一致"
```

**考点**：`for ... in dict` 对空集合**一次都不执行** → 函数成功返回 → 调用方以为"校验通过"。

**参考作答要点**：
- 缺陷 1：`assert_playbook_complete({})` 直接返回，什么都不校验。它就差一句 `assert set(playbook) >= tool_names`。
- 缺陷 2（更隐蔽）：这个校验函数**只检查"已经写进 playbook 的条目"**，不检查"应该有的条目是否都在"。一个工具有 meta 没 playbook，照样过。
- 对比 `assert_meta_complete`：它用 `set(meta.keys()) == tool_names`，是**双向**集合比较，空集合会失败——这才是"真校验"的写法。
- 影响：**中危**（如果 playbook 是功能依赖，模型会缺"何时不用"的信息，选错工具；如果只是文档，低危）。但如果这个校验被当作"启动门禁"，它给的是**虚假的安全感**——比没有校验更危险。
- 审查习惯：看到 `for ... in collection: assert ...` 和 `all(... for ... in collection)`，**先问"集合为空时会怎样"**。

**判分**：指出空集合下恒真给 1 分；指出"只校验已有、不校验缺失"给 1 分。

## 30 天训练法

### 每天 30 分钟：一段真实代码，三行记录

选一段**你正在维护的**真实代码（不要选教程代码），按固定格式写：


**关键约束**：
- "第一眼以为的问题"必须在**读代码之前**写。写完再读——这样才能测出你的直觉偏差。
- "实际的问题"允许是"没有问题"。**能判断"这段没问题"也是能力**，而且比"硬找一个问题"更难得。
- 每天只审**一段**（30–50 行）。审多了会退化成扫读。

### 每周日 45 分钟：回炉误判清单

1. 把本周 7 条"误判类型"统计一遍，找出**出现最多的一类**；
2. 针对这一类，去项目里**主动找 3 段同类代码**（比如"本周最常漏并发"，就去找所有 `SELECT ... UPDATE` 分成两句的地方）；
3. 给这 3 段各写一句"如果这里并发会怎样"。写不出来，说明你还没真懂这一类。

| 周 | 主题 | 每天找什么 | 周末自检 |
|---|---|---|---|
| 第 1 周 | 并发与幂等 | 两步操作、缓存、`get` 后 `set`、重试 | 能不能说出"两个请求同时到会怎样" |

### 每周一次的"反向练习"（20 分钟）

从项目里挑一段**你认为没问题的代码**，然后**故意**改坏一处（并发、边界、权限任选），再让 AI 或同事 review。

- 如果对方**一眼发现**：说明你之前"认为没问题"的判断标准偏松，记进误判清单。
