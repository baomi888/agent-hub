## 1. 时间口径（唯一标准，全看板共用）

| 项 | 规定 |
|---|---|
| 时区 | `core/timeutil.TZ`（默认 `Asia/Shanghai`，可由 `TZ` 环境变量覆盖） |
| "今日" | **自然日** `[今天 00:00:00.000, 今天 23:59:59.999]`，**不是滚动 24 小时** |
| "近 N 天" | **含今日**，即 `[today-(N-1) 00:00, now]`。`days=7` → 今天往前数共 7 个自然日 |
| 存储 | 表内一律存 **Unix 秒（INTEGER，UTC 基准）** |
| 展示 | 查询时用 `timeutil.day_bounds()` 换算成自然日边界，**禁止**在 SQL 里用 `datetime('now','localtime')` |
| 边界实现 | `day_bounds()` 用 `+timedelta(days=1)` 而非 `+86400`（夏令时/跨月安全） |

**为什么写死这条**：2026-10-20 审计的 A2 缺口就是"时区口径分裂"——`localtime` 与 `ZoneInfo` 两套算法并存，
日界偏移 8 小时。看板是**唯一会把日期直接展示给人看**的地方，口径错了会被一眼看出来。

**口径自测**：`select count(*) from api_call_logs where ts >= <today_start>` 与看板"今日"数字必须相等。

## 2. 指标定义表

### 2.1 总用户数

| 项 | 内容 |
|---|---|
| 看板名称 | 总用户数（注册用户） |
| 业务定义 | 系统内已注册的账号总数，**含已停用（status=0）账号** |
| 数据源 | `users` 表，`COUNT(*)` |
| 过滤条件 | 无 |
| 去重键 | `users.id`（主键，天然唯一） |
| 时间字段 | 无（这是"当前快照"，不随时间筛选变化） |
| 时区 | 不适用 |
| 刷新 | 每次请求实时查 |
| **对账 SQL** | `SELECT COUNT(*) FROM users;` |
| 已知局限 | 不区分测试账号（系统没有"测试账号"标记）；停用账号仍计入——因为口径是"注册过多少人"，不是"现在能登录多少人" |

**看板上必须标注**："总用户数不随时间筛选变化（是当前快照）"。否则用户切到"今日"看到用户数没变，会以为筛选坏了。

### 2.2 新增用户数

| 项 | 内容 |
|---|---|
| 业务定义 | `created_at` 落在所选区间内的账号数 |
| 数据源 | `users.created_at` |
| 过滤条件 | `created_at >= start AND created_at <= end` |
| 时间字段 | `users.created_at`（注册时刻，写入即定，不更新） |
| 对账 SQL | `SELECT COUNT(*) FROM users WHERE created_at BETWEEN ? AND ?;` |

### 2.3 API 调用次数

| 项 | 内容 |
|---|---|
| 业务定义 | **HTTP 请求条数**。1 个请求 = 1 行日志 = 1 次调用 |
| 数据源 | `api_call_logs` 表，`COUNT(*)` |
| 过滤条件 | `ts` 落在区间；**不含**被排除的路径（见 §3） |
| 是否含失败 | **含**。4xx / 5xx 都计入"调用次数"——这是流量口径 |
| 去重键 | 无（每次请求都是一次真实发生的调用，不去重） |
| 时间字段 | `api_call_logs.ts`（请求结束时刻，秒级） |
| 对账 SQL | `SELECT COUNT(*) FROM api_call_logs WHERE ts BETWEEN ? AND ?;` |
| 已知局限 | ① 秒级精度，同一秒内多条不区分先后 ② 进程被 `kill -9` 时缓冲里未落库的几十条会丢（见 §5）③ 多 worker 各自缓冲，但最终都写同一张表，**合计正确** |

### 2.4 成功 / 失败次数与成功率

| 项 | 内容 |
|---|---|
| 成功定义 | `status < 400` |
| 失败定义 | `status >= 400`（含 429 限流、4xx 业务错误、5xx 服务错误） |
| 成功率 | `成功数 / 调用总数`，**分母是区间内全部调用**（含失败，不含被排除路径） |
| 显示规则 | 分母为 0 时显示 `—`，**不显示 0% 或 100%**（空数据不能伪造出一个比率） |
| 对账 SQL | `SELECT SUM(status<400), SUM(status>=400) FROM api_call_logs WHERE ts BETWEEN ? AND ?;` |

**注意**：429（限流）算失败。理由：从"用户是否拿到了他要的东西"看，429 就是没拿到。
如果将来要区分"系统故障"与"用户超限"，拆 `status>=500` 单独一列，**本期不做**。

### 2.5 平均耗时

| 项 | 内容 |
|---|---|
| 业务定义 | 区间内请求耗时的算术平均 |
| 数据源 | `api_call_logs.dur_ms`（整数毫秒，`perf_counter` 差值，不含网络传输） |
| 单位 | 毫秒 |
| 为何不给 p95 | 按接口分组的 p95 需要对每组做窗口/排序子查询，2核2G 上每次刷新都跑一遍代价不划算。本期给 `avg` + `max`，**看板上明确写"均值，非 p95"** |
| 已知局限 | **SSE 流式请求的 dur_ms 是整条流的时长**（可能几十秒），会把均值拉高。看板对 `/api/chat/stream` 单独标注 |

### 2.6 接口排行（"调用什么 API"）

| 项 | 内容 |
|---|---|
| 分组键 | `api_call_logs.path`，值为**路由模板**（如 `/api/sessions/{sid}`），不是真实路径 |
| 为什么用模板 | 真实路径 `/api/sessions/abc123` 每次不同，直接 GROUP BY 会得到上千个只有 1 次的"接口"，排行失去意义（高基数问题） |
| 排序 | 调用次数降序；**并列时按 `path` 字典序升序**（保证两次刷新顺序不变，不出现"跳动"） |
| 展示字段 | 路径、方法、次数、失败数、平均耗时、最大耗时 |
| 对账 SQL | `SELECT path, method, COUNT(*) n FROM api_call_logs WHERE ts BETWEEN ? AND ? GROUP BY path, method ORDER BY n DESC, path ASC LIMIT ?;` |

### 2.7 用户反馈

| 项 | 内容 |
|---|---|
| 数据源 | `user_feedback` 表 |
| 计数口径 | "待处理"= `status IN ('open')`；"处理中"= `'doing'`；"已处理"= `'done'` |
| 时间字段 | `created_at`（提交时刻） |
| 状态流转 | 只允许 `open → doing → done`，以及任意状态 `→ closed`（不处理）。**不允许回退**（见 §4.3） |
| 对账 SQL | `SELECT status, COUNT(*) FROM user_feedback GROUP BY status;` |

## 3. 采集范围与排除规则

### 3.1 记录哪些请求

**只记录 `/api/` 前缀的请求。** 理由：`/health`、静态资源、Next 的 `/_next/*` 不是业务调用，
记进去会淹没真实数据（尤其 `/health` 被探活和监控每 15 秒打一次，一天 5760 条噪声）。

### 3.2 排除清单（写死在代码常量，改动要改文档）

| 路径 | 为什么排除 |
|---|---|
| `/health` | 探活高频，无业务含义 |
| `/api/metrics`、`/api/metrics/json` | Prometheus 采集器按秒抓，会把排行全部占满 |
| `/api/admin/*` | 看板自己的请求。**必须排除**，否则"打开看板"本身会推高统计数字，形成观测者效应 |
| 非 `/api/` 前缀 | 静态资源 / 前端路由 |

### 3.3 记录的字段

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 自增 |
| `ts` | INTEGER NOT NULL | 请求结束时刻（Unix 秒） |
| `path` | TEXT NOT NULL | **归一化后的路由模板** |
| `method` | TEXT NOT NULL | GET/POST/... |
| `status` | INTEGER NOT NULL | HTTP 状态码 |
| `dur_ms` | INTEGER NOT NULL | 耗时（毫秒），向上取整 |
| `uid` | TEXT NULL | 登录用户 id；未登录（如登录接口本身）为 NULL |

**不记录**：请求体、查询串、响应体、IP、User-Agent。
理由：看板只需要"谁调了什么、多少次、多慢"；记录内容会让这张表变成隐私风险面，
且体积会失控（2核2G 的磁盘不是无限的）。**需要排障时看应用日志，不看看板日志。**

## 4. 字典（前后端共用，由后端下发，前端不得硬编码）

### 4.1 反馈分类 `category`

| 值 | 显示名 | 用途（DeepSeek 式按钮） |
|---|---|---|
| `bug` | 出错了 | 页面报错、功能不响应、数据错乱 |
| `answer` | 回答不满意 | 答非所问、胡编、引用不对 |
| `feature` | 功能建议 | 希望增加/改造某个能力 |
| `ui` | 界面与体验 | 排版、可读性、操作别扭 |
| `other` | 其他 | 兜底 |

**为什么分类由后端下发**：前端硬编码一份、后端校验另一份，加一个分类就要改两处，
迟早不一致（而这类不一致的表现是"用户能点、提交 400"）。

### 4.2 反馈状态 `status`

| 值 | 显示名 | 颜色语义 |
|---|---|---|
| `open` | 待处理 | warn |
| `doing` | 处理中 | info |
| `done` | 已处理 | ok |
| `closed` | 不处理 | 灰 |

### 4.3 状态流转规则（强制校验，不靠前端）

```
open   → doing | done | closed
doing  → done  | closed
done   → closed
closed → （终态，不可改）
```

**不允许回退**（`done → doing`）：状态是给开发者自己看的处理进度，
允许回退会让"处理耗时"这类后续统计失去意义。真要是处理错了，用 `closed` 关掉重开一条新的。

### 4.4 导出字典（本期不做）

2026-10-27 明确不做 CSV / Excel 导出，原 `core/csvio.py` 与 `GET /api/admin/export` 已下线。
若将来恢复，必须先补两件事：**导出审计**（谁在什么时候导了多少行）与**字段脱敏**
（反馈里的联系方式、`uid` 不能原样出库），否则等于开了一个不受控的数据出口。

需要明细时直接查库（只读）：

```sql
-- 原始调用明细（最近 7 天）
select ts, path, method, status, dur_ms, uid from api_call_logs
where ts >= strftime('%s','now') - 7*86400 order by ts desc limit 100;
```

## 5. 采集的时效与丢失口径（"准实时"到底是什么）

| 环节 | 时延/风险 |
|---|---|
| 请求 → 内存缓冲 | 立即（微秒级，无 IO） |
| 缓冲 → SQLite | **最多 3 秒**，或缓冲满 50 条立即落库 |
| 查询 | 无缓存，请求即查（所见即最新已落库数据） |
| 因此看板数字的滞后 | **≤ 3 秒** |
| 丢失场景 | 进程被 `kill -9` / 断电时，缓冲中未落库的最多 50 条丢失 |
| 丢失为什么可接受 | 这是**统计**不是**账本**。丢几十条不影响"调用什么 API 更多"这类判断。真正的账（配额用量）在 `quota_usage` 表，与这张表无关 |

**为什么不做成"每个请求同步写库"**：2核2G + SQLite，每请求一次 INSERT 就是每请求抢一次写锁。
压测里 `/api/auth/me` 能到 1000+ RPS，同步写库会把这把锁变成吞吐上限（掉一个数量级）。
这是本期最重要的一个取舍，写在这里防止后人"优化"回去。

## 7. 接口契约（请求/响应/错误码）

统一响应约定：错误一律 `{"detail": "中文说明"}`，状态码语义化。

### 7.1 `POST /api/user-feedback/`

```
Request:  { "category": "bug", "content": "点击导出没反应", "contact": "", "page": "/dashboard" }
Response 200: { "ok": true, "id": 12 }
```

| 校验 | 规则 | 违反时 |
|---|---|---|
| category | 必须在字典内 | 400 `分类不合法` |
| content | 去空白后 5~2000 字 | 400 `内容太短/太长` |
| contact | 可选，≤120 字 | 400 |
| page | 可选，≤120 字 | 400 |
| 频率 | 每用户每分钟 5 条（`quota.hit(uid, 5)`） | 429（全局处理器） |

### 7.2 `GET /api/user-feedback/mine?limit=20&offset=0`

```
Response 200: { "items": [{id, category, category_label, content, status, status_label, created_at, updated_at}],
                "total": 3 }
```

### 7.3 `GET /api/admin/overview?days=7`

```
Response 200: {
  "range": {"days": 7, "start": 1761580800, "end": 1762185599, "tz": "Asia/Shanghai"},
  "users":  {"total": 42, "new": 3},
  "calls":  {"total": 1802, "ok": 1750, "failed": 52, "success_rate": 0.9711,
              "avg_ms": 84, "max_ms": 1203},
  "feedback": {"total": 17, "open": 5, "doing": 2, "done": 10, "closed": 0},
  "series": [{"day": "2026-10-26", "calls": 320, "failed": 6}]      // 按自然日
}
```

`users.total` **不受 days 影响**（当前快照），`users.new` 受 days 影响。响应里两者并列，
前端必须在 UI 上标出来，否则用户会误以为筛选坏了。

### 7.4 `GET /api/admin/apis?days=7&limit=20`

```
Response 200: {"items": [{path, method, calls, failed, avg_ms, max_ms}], "total_paths": 24}
```

### 7.5 `GET /api/admin/feedback?status=&limit=20&offset=0`

```
Response 200: {"items": [...], "total": 17, "counts": {"open":5,"doing":2,"done":10,"closed":0}}
```

### 7.6 `PATCH /api/admin/feedback/{id}`

```
Request:  {"status": "done"}
Response 200: {"ok": true, "status": "done"}
非法流转 → 409 {"detail": "不允许从 done 改为 doing"}
```

### 7.7 `GET /api/admin/apis?sort=` 的三种排序

```
sort=calls（默认）  ORDER BY calls DESC, path ASC, method ASC
sort=slow           ORDER BY avg_ms DESC, calls DESC, path ASC   HAVING COUNT(*) >= 3
sort=fail           ORDER BY failed DESC, calls DESC, path ASC   HAVING SUM(status >= 400) > 0
非法值              静默回落 calls（不报错：这是展示偏好，不是数据契约）
```

**`slow` 为什么要 `COUNT(*) >= 3`**：只调用过 1 次且恰好很慢的接口（首次冷启动、
建表迁移、首次加载模型）会把"最慢"榜整个占满，而那些不是性能问题。
门槛的作用是让榜单回答"常态下哪里慢"，不是"哪里偶然卡了一次"。

## 8. 性能预算（不是 P2，写在开发前置）

| 项 | 预算 | 依据 |
|---|---|---|
| 看板单接口 P95 | < 800ms（近 7 天数据） | 2核2G，同时 1 人在看 |
| 采集中间件单请求开销 | < 0.3ms | 只做 deque.append + 时间算差，无 IO |
| `api_call_logs` 日增行数预估 | 1000~20000 | 当前日活个位数，按 20 倍余量估 |
| 30 天保留期内最大行数 | ~600000 | 600k 行 + 索引，COUNT/GROUP BY 在 SQLite 上 < 100ms |
| 必须存在的索引 | `(ts)`、`(path, ts)`、`(status, ts)` | 无索引时 600k 行全表扫 ≈ 秒级 |
| 数据清理 | 保留 90 天，worker 每日清一次 | 超过 90 天的日志无人看，且会让备份变慢 |

**为什么把性能写进 Gate**：你的评审里指出"缓存/聚合表是 P2 但验收要求大数据量不超时"是自相矛盾。
这一期不建聚合表——因为 600k 行不需要。**什么时候必须建**：日增 > 20 万行，或看板 P95 > 800ms。
这个判据也写在这里，将来触发时不用重新讨论。

## 9. 数据质量与对账

| 检查项 | 方法 | 频率 | 差异容忍 |
|---|---|---|---|
| 口径一致性 | 看板"今日调用" vs §2.3 对账 SQL | 每次改查询逻辑后 | 0 |
| 丢失率 | 抽查：`api_call_logs` 行数 vs 应用日志行数 | 上线后首周 | < 0.5% |
| 时区正确性 | 跨零点时看"今日"是否归零 | 上线后首周 | 必须归零 |
| 反馈状态字典 | 后端 dict 与前端渲染逐项比对 | 改字典后 | 0 |

**抽样对账脚本**：`tools/check_dashboard.py`（本期交付）。
它做四件事，任何一项不过就以非 0 退出码失败，可直接挂到 CI 或上线前手跑：
① 看板"今日调用"与 §2.3 对账 SQL 相等；
② 最近 N 条日志里不存在未归一化的 id 路径（uuid / 纯数字 / 32 位 hex）；
③ 日志里不出现 `/health`、`/api/metrics`、`/api/admin/*`；
④ 同一请求在排行里的 `calls` 之和不超过区间总调用数（不该出现重复计数）。

### 11.3 开发中真实发现并修掉的两个问题（写在这里，因为单测都测不到）

**① `include_router` 的 `route.path` 是相对前缀的**

`/api/auth/me/` 命中的 `route.path` 是 `/me/`，不含 `/api/auth`。
直接拿它当聚合键，会被"只记 `/api/` 前缀"的规则**整批过滤掉**——
表现是"中间件明明执行了，但一条日志都没有"。
修法：按**段**从尾部对齐，把前缀接回去（`main.py::_route_template`）。
（`main.py` 里处理尾斜杠的注释提过 `_IncludedRouter` 的同类问题，这次是它在
`scope["route"]` 上的又一次表现。）

**② 只靠"请求结束时判断该不该 flush"不够，低流量会漏**

`record()` 返回 False 时不调度 flush，于是**最后几个请求会一直卡在内存缓冲里**，
直到下一个请求把它们带走。真机验证时 4 个请求只有 1 条落库，正是这个原因。
这与 §5 承诺的"延迟 ≤ 3 秒"直接矛盾，而 TestClient 单测永远发现不了（测试里手动 flush）。
修法：`lifespan` 里起一个每 3 秒的 `_apilog_flush_loop`，
并在停机时最后 flush 一次。

## 12. 页面形态选型（为什么是"内嵌路由页"）

看板的信息只有三类：**有多少人 / 在调什么 / 反馈堆了多少**。
但"放在哪儿看"有五种做法，代价差很多。这一节记录选型理由，
防止后来者凭"感觉更专业"换成一套更重的方案。

| 形态 | 做法 | 优点 | 代价 | 适配度 |
|---|---|---|---|---|
| **A. 内嵌路由页**（采用） | `/dashboard`，复用 `ConsoleShell` 与登录态 | 零新增部署、零新增依赖、与产品同一套鉴权；改一个文件就上线 | 与业务共用进程，看板查询会占一点 CPU（毫秒级） | ★★★★★ |
| B. 独立运维子应用 | 另起一个端口/域名，独立鉴权 | 隔离彻底，运维面板挂掉不影响业务 | 要多一套构建、登录、CORS；2核2G 上多一个常驻进程 | ★★☆ |
| C. 接 Grafana / Metabase | 直连 SQLite 副本或加只读账号 | 图表能力最强，能做任意切片 | 多一个服务（Grafana 起步 200MB+ 内存）；SQLite 被两个进程同时读要处理锁；口径散落在面板 JSON 里，**没有唯一真相** | ★★ |
| D. CLI / 终端面板 | SSH 里 `python tools/check_dashboard.py` 或类似 | 最轻，零前端；服务器上排障最快 | 不能交互、不能给非技术成员看 | ★★★（**已作为辅助形态提供对账脚本**） |
| E. 定时快照 / 日报推送 | 每早把数字推企业微信或邮件 | 不用主动去看，异常能主动冒头 | 有延迟；要接推送通道 | ★★★（**建议作为下一步**，见下） |

**为什么选 A**：省赛/校赛阶段只有 2 核 2G、一个运维（还是兼职），
任何"多一个常驻服务"的方案都会把有限的运维预算吃掉。
看板的查询是 `COUNT` + `GROUP BY` + 三个索引，实测毫秒级，
放在业务进程里不构成负担；而它带来的好处是**登录态、导航、样式全部免费**。

**为什么把 D 也做了**：`tools/check_dashboard.py` 既是"对账工具"，
也是"服务器上没有浏览器时的看板"——四条检查里包含今日调用数、路径归一化、
采集范围、计数一致性，SSH 上去一条命令就能判断"数据是不是对的"。
它和 A 共用 `core/dashboard.py`，**不存在两套口径**。

**建议的下一步（E）**：当看板开始有人"忘记看"的时候再做。
形态是每天 09:00 由 worker 生成一段文本（今日调用量、失败 Top3 接口、
待处理反馈数），推到企业微信/邮件。它不替代 A，只是把"人找数"变成"数找人"。
判据：连续两周没有人主动打开 `/dashboard`，就该做 E 了。
