## 1. 目标与范围

**做**

1. 长对话压缩时，后台 worker **默认**把知识句沉淀进「个性化知识库」：按主题自动建库（同一主题复用），`staged` 回写，可开关（关掉 = 只做正常压缩）。
2. 两个「建库建议」场景，都走**用户确认制**：
   - `检索` 开关打开但会话无库（D7）；
   - `智能联网` 回答完成后，询问是否把本轮收集到的信息沉淀（D11）。
3. 提供交互工具（B 板块）需要的知识库服务层函数：写入知识库、文档管理。
4. 设置页「自动沉淀」开关的服务端存储与接口。

**不做**

- 不改执行路由、工作流判定、工具绑定逻辑（A/B）。
- 不改模式条 / 能力弹层（C）。
- 不自动删除用户已有知识库文档。

## 4. 用户偏好

### GET `/api/prefs`

```json
{
  "auto_sediment": true,
  "auto_create_kb": true
}
```

- `auto_sediment`：长对话压缩时是否自动沉淀（默认 `true`，D10）
- `auto_create_kb`：是否允许「检索无库时提示建库」（默认 `true`）
- 无行时返回默认值，不报 404。

### PUT `/api/prefs`

请求体（字段可选，只改传入项）：

```json
{ "auto_sediment": false }
```

响应：同 GET 的完整对象。

校验：非 bool → 422；未登录 401。

## 5. 建库建议（proposal）

### 5.1 SSE 事件 `kb_proposal`

由 A 板块在聊天流里**替 D 发**（D 提供 `maybe_propose()` 生成数据，见 §12）；发生在 `done` 之前，每轮最多 1 次。

```text
event: kb_proposal
data: {
  "proposal_id": "prop_9f2c…",
  "topic": "考研数学复习计划",
  "source": "web_search",              // web_search | no_kb_retrieval
  "candidates": 12,                     // 可沉淀的对话知识句数量（web 场景可含来源条数）
  "kb_hint": "对话沉淀·考研数学复习计划", // 建议库名
  "expires_at": 1762000000,
  "reason": "本轮联网收集了 5 条外部信息"   // 给用户看的一句话，≤40 字
}
```

触发条件（A 负责判定并调用 D 的 `maybe_propose`）：

| source | 条件 |
|---|---|
| `no_kb_retrieval` | 本轮 `use_kb=true` 且会话无可用库 |
| `web_search` | 本轮 `use_web=true` 且确实产生了联网调用/外部信息 |

同会话同 `source` 的 pending 建议 10 分钟内不重复发。

### 5.2 POST `/api/kb/proposals/{proposal_id}/confirm`

请求体：

```json
{ "name": "可选，覆盖 kb_hint", "bind": true }
```

响应 200：

```json
{
  "proposal_id": "prop_9f2c…",
  "status": "confirmed",
  "kb_id": "kb_xxx",
  "name": "对话沉淀·考研数学复习计划",
  "imported": 12,
  "chunks": 12,
  "staged_segments": 3,
  "bound": true,
  "batch_id": "sed_xxx"
}
```

行为：

1. 校验 proposal 归属 + `status=pending` + 未过期；
2. 建库（或复用同名主题库）——`kb.pipelines.create_kb`；
3. 入库：对话知识候选（`source=no_kb_retrieval` 时为本会话消息；`web_search` 时为 proposal.payload 里保存的联网来源 + 本轮回答要点）；
4. 回写 `mark_segments_staged`；
5. `bind=true` 时把库绑到 `sid`（`store.bind_kb`）；
6. 记 `sediment_batches`（供撤销/审计）。

错误：404（不存在/非本人）、409（非 pending：已确认或已忽略）、410（过期）。

### 5.3 POST `/api/kb/proposals/{proposal_id}/dismiss`

响应：`{"proposal_id":"…","status":"dismissed"}`；状态非 pending → 409。

### 5.4 GET `/api/kb/proposals/{proposal_id}`（可选）

响应同 confirm 的结构（status 为当前状态）。用于前端刷新后恢复卡片。

## 9. Worker 任务契约

### 9.1 触发

`core/context_compress.py::maybe_compress` 在 `commit_summary` 成功返回前调用：

```python
if ok:
    try:
        from service import sediment
        sediment.enqueue(owner, sid, new_upto)
    except Exception:
        log  # 沉淀失败绝不阻塞压缩
```

`enqueue` → `core.scheduler.enqueue_job("sediment.dialogue", f"{owner}:{sid}", new_upto, trigger="compress")`。

### 9.2 注册与调度

1. `worker/scheduler.py::_load_handlers` 增加：

```python
try:
    from service import sediment
    register_handler(sediment.JOB_KEY, sediment)
except Exception as e:
    _log_json("handler_missing", job_key="sediment.dialogue", reason=f"{e}"[:200])
```

2. `core/scheduler.py::job_defs()` 增加一条 tick：

```python
"sediment.dialogue": {"cron": "* * * * *", "description": "对话沉淀（事件驱动，每分钟排空待办）"},
```

`run_pending()` 在每次 tick 执行，会排空 pending 行；`_run_job` 因该模块没有 `due_subjects`/`run_job` 而空转（无副作用）。

3. `tests/test_scheduler.py::EXPECTED_CRONS` 同步更新（否则该用例红）。

### 9.3 幂等与重试

| 层 | 键 |
|---|---|
| 调度 | `(job_key, subject_id, planned_at=boundary_id)` 唯一（`enqueue_job` 的 ON CONFLICT） |
| 入库 | `sediment_batches` 上 `(owner_id, sid, content_hash)` 唯一；同批候选已存在则跳过 |
| 失败 | 交给现有 scheduler 分级：429/5xx/超时 = `retry`（1/5/15 分钟后重试，最多 3 次）；库不存在/会话删除 = `fatal`；额度触顶 = `quota`（次日） |

### 9.4 `run_one` 伪代码

```text
owner, sid = subject_id.split(":", 1)
if not prefs.auto_sediment: return {}
msgs = store.get_messages(owner, sid, limit_turns=None, include_system=False)
cands = dialogue_import.extract_candidates(msgs)       # 零 LLM
if not cands: return {}
topic = sediment_store.topic_of(owner, sid)
kb_id = reuse_or_create_topic_kb(owner, topic)          # 名称=「对话沉淀·{topic}」，同 owner 同名复用
quota.guard(owner, "embed")
n = pipe.add_chunks(dialogue_import.build_documents(cands, sid, topic))
mark_segments_staged(owner, sid, refs)
add_batch(owner, sid, kb_id, source="auto", refs, n)
bump_usage(owner, "embed", n)
return {"tokens_out": n}
```

## 10. 数据模型（沿用 `data/sessions.db`，`CREATE TABLE IF NOT EXISTS`）

```sql
CREATE TABLE IF NOT EXISTS user_prefs (
  owner_id     TEXT PRIMARY KEY,
  auto_sediment INTEGER NOT NULL DEFAULT 1,
  auto_create_kb INTEGER NOT NULL DEFAULT 1,
  updated_at   INTEGER NOT NULL
);

CREATE TABLE IF NOT EXISTS kb_proposals (
  proposal_id  TEXT PRIMARY KEY,
  owner_id     TEXT NOT NULL,
  sid          TEXT NOT NULL,
  topic        TEXT NOT NULL,
  source       TEXT NOT NULL,              -- web_search | no_kb_retrieval
  payload_json TEXT NOT NULL,              -- refs / web_sources / answer_message_id
  status       TEXT NOT NULL DEFAULT 'pending',  -- pending|confirmed|dismissed|expired
  kb_id        TEXT,
  created_at   INTEGER NOT NULL,
  expires_at   INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_kbprop_owner ON kb_proposals(owner_id, status);

CREATE TABLE IF NOT EXISTS sediment_batches (
  batch_id     TEXT PRIMARY KEY,
  owner_id     TEXT NOT NULL,
  sid          TEXT NOT NULL,
  kb_id        TEXT NOT NULL,
  source       TEXT NOT NULL,              -- manual | auto | web_confirm | tool
  refs_json    TEXT NOT NULL,              -- 入库的来源 message id / url
  content_hash TEXT NOT NULL,
  chunk_count  INTEGER NOT NULL,
  created_at   INTEGER NOT NULL,
  status       TEXT NOT NULL DEFAULT 'active'   -- active | removed
);
CREATE UNIQUE INDEX IF NOT EXISTS uq_sediment_hash
  ON sediment_batches(owner_id, sid, content_hash);
```

> 不修改 `core/session.py` 的建表函数：D 自建 `core/sediment_store.py::ensure()`（模式照抄 `core/user_feedback.py:118-142`），避免与 A/B/C 改同一文件。

## 14. 关键时序

```text
[压缩自动沉淀]
chat 回答结束 → maybe_compress() → commit_summary ok
  → sediment.enqueue(owner, sid, new_upto)        (web 进程，仅写 job_runs pending)
worker 下一 tick（≤60s）→ run_pending → sediment.run_one
  → 偏好开？→ 抽候选 → 同主题建库/复用 → 入库 → staged → batch

[检索无库 → 确认建库]
chat 请求 use_kb=true, 会话无库
  → 正常作答（纯 LLM / 若 use_web 则联网）
  → done 前：maybe_propose(source=no_kb_retrieval) → SSE kb_proposal
前端卡片「建库」→ POST confirm → 建库(主题名)+入库(本会话候选)+绑会话 → 卡片变成功
下一轮：检索链路可用（有引用）

[联网后 → 询问建库]
use_web=true，本轮有联网来源
  → done 前：maybe_propose(source=web_search, web_sources=[...]) → SSE kb_proposal
确认 → 建库 + 存入联网来源摘要 + 本轮回答要点；不确认 → dismissed
```

## 15. 验收清单（D 自测）

1. 偏好接口：默认 true；PUT false 后 GET 一致；未登录 401；非 bool 422。
2. 压缩触发：`maybe_compress` 成功后 1 分钟内 job_runs 出现 pending，worker 跑完变 succeeded（`sediment.dialogue`）。
3. auto_sediment=false：压缩成功但不建库、不产生 batch。
4. 按主题复用：同标题会话第二次沉淀复用同一个 kb_id；不同标题建新库。
5. staged 回写：入库后压缩段 `staged=True`；未入库段不标。
6. 幂等：同一 boundary 重复入队只有一行；同 content_hash 不重复入库。
7. proposal 三态：pending→confirmed / dismissed；重复 confirm 409；过期 410；越权 404。
8. confirm 后可检索：新会话检索到「对话·<标题>」来源条目。
9. 离线可测：所有单测不联网、不调真 LLM（embedding 用 `DeterministicFakeEmbedding`，参考 `tests/test_compress_v2.py`）。
10. 全量 `pytest -q` 无回退（新增表/路由不影响既有 655+ 用例）；`ruff check` 通过。
