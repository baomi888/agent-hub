# 卷四 · 模型接入层

> 本卷解决的问题：**把三家异构的模型 API 包装成一套可预测的调用面，并且让每一次调用都"带了紧箍咒"。**
> 这一层的选型自由度最小（供应商决定能力边界），但可设计空间最大（超时、重试、限长、温度、错误翻译全在自己手里）。

---

## 4.1 `ChatOpenAI` 直连，不用 `init_chat_model`

### 背景：LangChain v1 的多供应商抽象

LangChain 提供了一个 `init_chat_model("deepseek:deepseek-chat")` 之类的统一入口，会按 provider 前缀自动路由到对应的集成包（`langchain-deepseek`、`langchain-openai`、`langchain-anthropic`...）。

这是"更 LangChain"的写法。为什么不用？

### 理由（`core/llm.py:3-7`）

> `init_chat_model` 会根据 provider 名称自动路由，但 LangChain 1.4.1 对 deepseek / dashscope 这类第三方 provider 支持不稳定（见经验 1251481）。
> DeepSeek 和百炼都严格遵循 OpenAI 兼容接口，直接用 `ChatOpenAI` / `OpenAIEmbeddings` 绕过 provider 路由层，更可靠。

这段注释的结构值得注意：它先说"抽象是什么"，再说"为什么这个抽象在这里不划算"，最后说"绕过它的成本是零"。

第三点是关键：**如果绕过抽象的代价是"放弃很多功能"，那就不该绕。但这里绕过只是换一个类名，因为两家都兼容 OpenAI 协议。**

### 兼容 OpenAI 协议意味着什么

DeepSeek 的 API 文档明确写了"OpenAI 兼容"：同样的 `/v1/chat/completions`、同样的 `messages` 结构、同样的 `tools` 参数、同样的 `stream: true` 语义。

百炼（DashScope）也提供了 OpenAI 兼容模式（`https://dashscope.aliyuncs.com/compatible-mode/v1`）。

所以"用 `ChatOpenAI` 接 DeepSeek"不是 hack，是**供应商官方支持的接入方式**。区别只在于 `base_url` 和 `api_key`。

### 代价与风险

**代价 1：失去多供应商切换的"自动"能力。**

如果将来要接 Claude 或 Gemini，需要写新的分支，而不是改一个字符串。但这个"能力"在当前是虚的——本项目不打算多模型路由。

**代价 2：供应商特有的能力无法通过统一接口访问。**

比如 DeepSeek 的 `reasoning_content`（思维链）、某些模型的 `cache_control`（显式缓存标记）。这些需要：
- 要么用 `extra_body` 透传（`ChatOpenAI` 支持）；
- 要么自己解析原始响应。

本项目对 reasoning 的处理就是走 `extra_body` + 自定义字段解析（`api/chat.py` 的 `reasoning` 事件，仅在配置了 `DEEPSEEK_REASONER_MODEL` 时出现）。

**风险：`ChatOpenAI` 本身是 `langchain-openai` 的类，它会随 LangChain 版本演进。** 锁定 `langchain-openai==1.6.2` 是必要的，否则某次升级可能改了 `extra_body` 的传递方式。

### 反转条件

- 需要接入 3 家以上模型并做 A/B 或成本路由 → `init_chat_model` 或自建路由层的收益才开始为正；
- 需要利用某家特有的能力（如 Anthropic 的 prompt caching、Gemini 的长上下文）→ 需要专用集成包。

## 4.2 双供应商：一个被迫的架构

### 事实

`core/config.py:24-25`：

> DeepSeek 不提供 embedding 接口，必须单独配置（阿里百炼等 OpenAI 兼容服务）

这是一条**能力缺口**，不是设计选择。后果：

| 能力 | 供应商 | 模型 | 配置项 |
|---|---|---|---|
| 对话 | DeepSeek | `deepseek-chat` | `DEEPSEEK_API_KEY` |
| 向量化 | 阿里百炼 | `text-embedding-v3` | `EMBEDDING_API_KEY` + `EMBEDDING_BASE_URL` |
| 视觉理解 | 阿里百炼 | `qwen-vl-plus` | `VISION_API_KEY`（默认回落 `EMBEDDING_API_KEY`） |

### 这个架构的连锁后果

**① 密钥数量变成 3 个（必填）+ 2 个（可选）。**

`config.validate()` 检查的必填项：

```python
if not DEEPSEEK_API_KEY: missing.append("缺少 DEEPSEEK_API_KEY（大模型对话密钥）")
if not EMBEDDING_API_KEY: missing.append("缺少 EMBEDDING_API_KEY（向量化服务密钥）")
if not EMBEDDING_BASE_URL: missing.append("缺少 EMBEDDING_BASE_URL（向量化服务地址）")
```

注意 `EMBEDDING_BASE_URL` 也必须显式配（没有默认值）。为什么？因为百炼的兼容端点地址有多个区域变体，猜错会得到 404 而不是清晰的错误。**没有默认值，是为了让配置错误在启动时就暴露。**

**② 向量与查询必须同一个模型。**

`core/llm.py:66-68`：

> 更换向量化模型后必须删除 chroma_db/ 目录重建向量库！

这是向量检索的硬约束：不同模型的向量空间不可比。混用会导致"检索结果完全随机"，而且**不会报错**——又是一个静默失败。

这句话应该被当作**运维红线**，但它的措辞不够强（放在 docstring 里，容易被忽略）。更好的做法是：把 embedding 模型名写进 collection 的 metadata，检索前比对，不一致就拒绝。当前没做，属于已知缺口。

**③ README 里有一句诚实的不利声明**

`README.md:43`：

> 向量化走阿里百炼 API —— 因此「数据不出校」的说法在当前实现下**不成立**，本项目对外只声称「用户数据按 owner 强制隔离、不进入公共语料」。

这一句非常重要。它承认了：只要用了外部 embedding API，**文档内容就离开了本地**。这对"校园场景"是一个真实的产品约束（学校可能有数据合规要求）。

而"不进入公共语料"和"数据不出校"是两个完全不同的承诺：前者是供应商条款问题，后者是物理隔离问题。混淆这两者是很多 AI 产品的通病。

**④ 视觉密钥可以回落到 embedding 密钥**

```python
VISION_API_KEY = os.getenv("VISION_API_KEY", EMBEDDING_API_KEY)
VISION_BASE_URL = os.getenv("VISION_BASE_URL", EMBEDDING_BASE_URL)
```

因为两者都是百炼（同一个账号同一个 key）。这个回落设计让"只配 2 个 key 就能用全部功能"成立——降低了上手门槛。

但代价是：如果用户想用不同的百炼账号跑视觉和 embedding（比如分别计费），需要显式配 `VISION_API_KEY`。

### 一个被低估的成本：跨供应商的延迟叠加

一次 RAG 问答的调用链：

```
用户问题
  → [如果像追问] DeepSeek 改写（约 0.5~1s）
  → 百炼 embedding 查询向量（约 250ms，有缓存）
  → Chroma 本地检索（约 10~50ms）
  → DeepSeek 生成（首字 0.5~1.5s）
```

关键路径上的**网络往返是 2~3 次跨供应商**。这意味着：

- 首字延迟（TTFT）的下界由"最慢的那一跳"决定；
- 任何一跳抖动，用户都能感知；
- 无法通过本地缓存消除（embedding 可缓存查询向量，但不能缓存生成）。

这解释了为什么 `_embed_query` 要做 LRU + single-flight（省 250ms 很值），也解释了为什么查询改写要"条件触发"而不是"每题都改"（多一跳 1 秒，只在必要时付）。

### 反转条件

- DeepSeek 若推出 embedding 接口 → 可以合并成单供应商，减少一个密钥和一个故障点；
- 若合规要求"数据不出境/不出校" → 必须换本地模型（`bge-m3` + `qwen2.5-vl` 本地部署），代价是显存/内存与推理延迟。

## 4.3 客户端缓存：为什么不是"每次 new 一下"

### 问题（`core/llm.py:9-13`）

> 构造 `ChatOpenAI` / `OpenAIEmbeddings` 会建 httpx 连接池，每次请求 new 一个纯属浪费（实测每请求会 new 2~3 个：标题生成 + 流式生成 + 可能的视觉模型）。实例本身不带会话状态，一次请求的 invoke / astream 各自独立，可安全地跨请求、跨线程复用。

### 关键判断：为什么"可安全复用"

这是缓存的正确性前提，必须论证清楚：

1. **`ChatOpenAI` 不持有对话状态。** 消息是通过 `invoke(messages)` / `astream(messages)` 传入的，实例本身只是"配置 + HTTP 客户端"。
2. **httpx 的 `AsyncClient` 是并发安全的。** 它内部有连接池，多个协程可以共享。
3. **`temperature` / `max_tokens` 是构造参数，不是调用参数。** 所以不同参数必须不同实例。

第 3 点决定了缓存键的设计：

```python
_LLM_CACHE: dict[tuple[float, int | None], ChatOpenAI] = {}
key = (temperature, max_tokens)
```

### 这个键的隐含假设

假设"同一个 (temperature, max_tokens) 组合一定可以共用实例"。这在当前成立，但如果将来要支持：
- 不同的 `top_p` / `frequency_penalty`；
- 不同的 `extra_body`（比如按请求开关 reasoning）；
- 不同的超时（长文生成 vs 短标题）；

缓存键就必须扩展。而**扩展缓存键是一个容易漏的改动**：漏了会导致"参数设置了但不生效"，又是一个静默失败。

**更好的设计**：用一个 frozen dataclass 作为 key，把所有构造参数纳入，这样新增参数时"忘了加进 key"会在类型层面暴露（字段不在 key 里，但构造时传了）。当前用的是 tuple，属于"简单够用"。

### 缓存没有失效机制

`_LLM_CACHE` 只增不减，但有上界：键空间是 `(temperature, max_tokens)` 的组合。实际使用中：

| 用途 | temperature | max_tokens |
|---|---|---|
| 主回答（RAG/LLM） | 0.1 | 2048 |
| Agent 主循环 | 0.1 | `AGENT_LLM_MAX_TOKENS or None` |
| 标题生成 | 0 | 32 |
| 查询改写 | 0 | 64 |
| 用户画像 | 0 | 48 |
| 主题标签 | 0 | 64 |
| 视觉理解 | 0.1 / 0 | 2048 |

大约 7~8 个组合。缓存不会膨胀。

### 单例的写法：双重检查锁

```python
if _EMBEDDINGS is None:
    with _CLIENT_LOCK:
        if _EMBEDDINGS is None:
            _EMBEDDINGS = OpenAIEmbeddings(...)
```

这是标准的 double-checked locking。在 CPython 下其实不是严格必要（GIL 保证了赋值原子性），但它避免了"多个线程同时构造"——构造过程包含配置解析和 httpx client 创建，重复构造会浪费资源。

## 4.4 `check_embedding_ctx_length=False`：一个必须解释的开关

### 它默认做什么

`OpenAIEmbeddings` 默认 `check_embedding_ctx_length=True`，行为是：

1. 用 `tiktoken` 把文本编码成 token；
2. 检查是否超过模型的上下文长度；
3. 如果超了，**自动截断**；
4. 把 token id 数组发给 API。

第 4 点是关键：**它发的是 token id，不是文本**。这是 OpenAI 官方 API 支持的一种输入格式（为了省带宽）。

### 为什么必须关掉

```python
check_embedding_ctx_length=False,  # 第三方兼容接口关闭 token 长度检查
```

第三方兼容端点（百炼）**只接受文本输入**，不接受 token id 数组。开着这个开关，请求体里会是 `{"input": [1234, 5678, ...]}`，百炼会返回 400 或更奇怪的错误。

同时，`tiktoken` 的编码表是 OpenAI 的（`cl100k_base` 或 `o200k_base`），对中文的切分与百炼模型的实际 tokenization 不同。所以"长度检查"本身也是错的——它检查的是"OpenAI 视角下多长"，不是"百炼视角下多长"。

### 关掉之后的后果

1. 不再自动截断。超长文本会**直接失败**（400 或静默截断，取决于服务端）。
2. 请求体是纯文本，兼容性最好。

所以关掉这个开关，把"长度控制"的责任转移到了应用层。应用层确实做了：

- 切片 500 字符（远小于任何模型的上限）；
- `EMBED_BATCH_SIZE=10`（百炼单次批量上限）；
- `_join_head` 截到 4000 字符（抽主题标签时）。

**这是一个正确的责任转移**：不要依赖一个"猜别人 tokenizer"的逻辑，而是自己按字符数控制在安全范围内。

### 引申：这是一个通用模式

**任何"框架帮你检查第三方 API 的限制"的功能，都要怀疑它的假设。** 因为框架只知道自己的规则，不知道对方的规则。类似的情况：

- `max_tokens` 的单位（有的模型是"输出 token"，有的是"输入+输出总和"）；
- 图片的尺寸上限（不同视觉模型不同）；
- 批量大小上限（百炼 10，OpenAI 2048）。

这些都必须由应用层显式控制，不能依赖默认值。

## 4.5 超时的真实语义：流式下是"字节间隔"

### 配置

```python
LLM_TIMEOUT = float(os.getenv("LLM_TIMEOUT", "60"))
```

### 注释里的关键说明（`core/config.py:56-58`）

> 单次 LLM 请求的超时秒数。流式下这是「字节间隔」超时：只要还在出字就不会触发，只有整段卡死（服务端长时间不吐字节）才中断。默认 60s 够宽松，不会误杀长回答。

这段话纠正了一个常见误解：**很多人以为 60s 超时意味着"回答超过 60 秒就断"**。

实际上 httpx 的 timeout 分几种：
- `connect`：建连超时；
- `read`：**两次读取之间的最大间隔**；
- `write`：写超时；
- `pool`：从连接池取连接的超时。

长连接流式场景下，`read` 超时的语义是"服务端 60 秒没有发任何字节"。一个生成 5 分钟的回答（每 100ms 一个 token）**永远不会触发**。

### 三种超时策略的对比

| 策略 | 行为 | 适用场景 |
|---|---|---|
| **总时长超时**（`asyncio.wait_for` 包整体） | 到点无条件断，不管是否在出字 | 有硬性 SLA 上限（如"单次请求不超过 120s"） |
| **字节间隔超时**（httpx read timeout） | 只在卡死时断 | 流式生成，长度不可预测 |
| **不设超时** | 可能永久挂起 | 永远不该用 |

本项目用第二种，同时在 hybrid 引擎里用第一种（`HYBRID_WORKFLOW_TIMEOUT=600`、`HYBRID_AGENT_MAX_SECONDS=300`）——**两层超时：内层防卡死，外层防失控**。

这是一个值得学的组合：单次 I/O 的超时和整个任务的超时是两件事，不能只做一件。

### 为什么是 60 秒

推断：DeepSeek 在高峰期偶尔会有 10~30 秒的首字延迟（排队）。60 秒留了 2 倍余量。如果设成 30 秒，高峰期会误杀正常请求。

而如果设成 300 秒，卡死的请求会占用连接 5 分钟，在 3 并发的压测下会积压。

**60 秒是"高峰期容忍度"与"故障发现速度"的折中。**

## 4.6 重试：一个会重复计费的操作

### 配置

```python
LLM_MAX_RETRIES = int(os.getenv("LLM_MAX_RETRIES", "2"))
```

注释：

> 失败自动重试次数（含 429 / 5xx / 超时）。**重试会重复计费，别调太大。**

### 为什么重试会重复计费

这是 LLM API 与普通 REST 的核心差异：

- 普通 REST 的重试通常安全（幂等 GET）；
- LLM 生成的计费是**按实际计算量**（输入 token + 输出 token）。如果请求已经生成了一半才超时，前半部分可能已经被计费。

更糟的是"重复计费 + 重复生成"：重试后得到的是**另一个回答**，与第一次不同（temperature > 0 时）。用户看到的是第二个。第一个的钱白花了。

### 为什么还需要重试

因为 429（限流）和 5xx（服务端错误）重试**确实是有效的**：这类失败发生在生成开始之前，没有计费。

所以真正的判据是：**失败发生在"开始生成"之前还是之后。**

| 失败类型 | 是否已计费 | 重试是否有意义 |
|---|---|---|
| 429 限流 | 否 | ✅ 高（等一会儿再试） |
| 5xx | 否 | ✅ 中 |
| 401/402 认证/余额 | 否 | ❌ 无意义（重试还是失败） |
| 超时（首字前） | 否 | ✅ 中 |
| 超时（流式中途） | **部分** | ⚠️ 会得到不同回答 |
| 连接重置（流式中途） | 部分 | ⚠️ 同上 |

当前实现是 2 次统一重试，没有区分"流式中途失败"。这是一个可以改进的点：**流式已经产出 token 之后，不应该重试**——应该直接把已产出的内容作为不完整回答返回（或者发 error 帧，让用户手动重试）。

`_stream_llm` 的实现实际上就是这样处理的：

```python
except Exception as e:
    acc.error = describe_api_error(e)
    yield _sse("error", {"detail": acc.error})
```

它捕获异常后发 error 帧，不重试。**重试是 httpx 层做的（`max_retries=2`）**，而 httpx 的重试发生在连接层——对于流式响应，如果已经开始读取 body，httpx 通常不会再重试。所以实际行为是安全的。

但这依赖 httpx 的实现细节，**不是一个显式的保证**。理想的做法是显式配置"只对建连阶段重试"。

### 与定时任务重试的区别

注意：这里的 `max_retries` 是 **HTTP 层**重试。`core/scheduler.py` 里的 `MAX_ATTEMPTS=3` 与 `BACKOFF_MINUTES=(1,5,15)` 是 **业务层**重试。

两层重试叠加的最坏情况：3 次业务重试 × 3 次 HTTP 尝试（1 初始 + 2 重试）= 9 次实际调用。这在定时任务里是可接受的（有 `DAILY_AUTO_LIMIT` 兜底），但在用户主动问答里是危险的。

**这说明了一个通用原则：重试次数要在"整个调用栈"上算总和，不能只看一层。**

## 4.7 `max_tokens` 分层：本卷最重要的一张表

### 完整的分层

| 用途 | max_tokens | 温度 | 代码位置 | 依据 |
|---|---|---|---|---|
| 主回答（RAG） | 2048 | 0.1 | `api/chat.py:1019` | 足够长文；防止无界生成 |
| 主回答（纯 LLM） | 2048 | 0.1 | `api/chat.py:1049` | 同上 |
| 视觉理解 | 2048 | 0.1 | `api/chat.py:680` | 图片描述通常不长 |
| Agent 主循环 | `AGENT_LLM_MAX_TOKENS or None` | 0.1 | `agent/builder.py:197` | 默认 0 = 平台默认（保持旧行为） |
| 标题生成 | 32 | 0 | `api/chat.py:1173` | 只要 ≤15 字 |
| 查询改写 | 64 | 0 | `kb/rag_core.py:731` | 只输出一条问题 |
| 用户画像 | 48 | 0 | `api/chat.py:1221` | 0~3 个标签 |
| 主题标签 | 64 | 0 | `kb/rag_core.py:810` | 3~6 个标签 |
| 每日总结 | 未显式设 | 默认 | `service/daily.py` | 见下 |
| 报告 JSON | —— | —— | —— | 受 `_MAX_CHUNK_CHARS` 控制 |

### 为什么这张表重要

`max_tokens` 是**唯一能真正封住成本的参数**。其他所有护栏（配额、预算、步数）都是"事后的"或"外层的"。

`agent/builder.py:194-196` 的注释说得最清楚：

> 显式传 `max_tokens`：hybrid 的 Agent 引擎有步数/时长/token 三重预算护栏，但护栏在"外面"计数；主循环自己不封顶的话，单次回答仍可无界增长。

这是一个精确的区分：**外层预算 vs 内层上限**。

- 外层预算（`HYBRID_AGENT_TOKEN_BUDGET=8000`）是"累计到 8000 就收编"；
- 内层上限（`max_tokens`）是"单次生成不超过 N"。

如果没有内层上限，单次生成可能就到 50000 token，外层预算在下一次检查时才发现，已经烧完了。

### 一个刻意的例外：Agent 主循环默认 `None`

```python
AGENT_LLM_MAX_TOKENS = int(os.getenv("AGENT_LLM_MAX_TOKENS", "0"))
# 默认 0 是为了不动既有行为（改默认值会让现有回答长度突变），
# 生产建议按 HYBRID_AGENT_TOKEN_BUDGET 同量级设置（如 2048）。
```

这是一个"保守的默认值"，理由是**兼容性**：如果突然给 Agent 加 2048 上限，现有用户的问答会突然变短，可能截断在句子中间。

但这留下了一个敞口：默认部署下 Agent 路径没有单次上限。

**判断**：这个取舍在"已有用户"场景下是对的，在"新部署"场景下是错的。更好的做法是"新部署默认 2048，通过 migration flag 保留旧行为"——但那样引入配置复杂度。

**这类决策的共同特征**：为了不破坏兼容性，把安全默认值让给了兼容性。这是一个需要定期复审的债。

### `TITLE_MAX_TOKENS` 的演化

```python
# 标题生成：只要 ≤15 字，给输出兜底防跑偏（原为硬编码 32，提到配置便于调）
TITLE_MAX_TOKENS = int(os.getenv("TITLE_MAX_TOKENS", "32"))
```

注释说"原为硬编码 32，提到配置便于调"。这个改动看起来微不足道，但它揭示了一个模式：**当某个参数是"成本护栏"时，它应该可调**——因为成本随用户量变化，而代码不该随用户量发版。

`api/chat.py::_generate_title` 里还有两道护栏：

> 两道成本护栏（2026-10-13）：
> - 输入截到前 200 字：首问若是粘贴的长文档，完整问题会原样进标题 prompt，一次标题生成就吃掉几千 token 输入，而标题只反映开头主题，截断不损质量；
> - `max_tokens=32`：标题只要 ≤15 字，给输出兜底，防止模型跑偏成复述正文。

**"输入截断"和"输出限制"是两个不同的护栏，缺一不可。** 很多人只做输出限制，忽略了输入——而输入往往是大头（粘贴 5000 字的文档，一次标题生成就烧 5000 token）。

## 4.8 温度：为什么几乎所有调用都是 0 或 0.1

| 用途 | temperature | 理由 |
|---|---|---|
| 主回答 | 0.1 | 要稳定，但不要死板 |
| Agent | 0.1 | 工具选择需要一点灵活性 |
| 标题 | 0 | 只要一个短标签，不需要创意 |
| 改写 | 0 | 改写是"补全指代"，不是"创作" |
| 画像 | 0 | 分类任务 |
| 主题标签 | 0 | 分类任务 |

规律很清晰：**凡是"生成给用户看的内容"用 0.1，凡是"生成给程序用的结构化数据"用 0。**

为什么不是 0 和 1 的二分？因为 0 会让模型陷入"最可能的续写"，在中文问答里表现为"正确的废话"。0.1 保留一点随机性，让表达更自然。

为什么不是 0.7？因为 RAG 场景下模型应该"忠于资料"，温度高会增加"自由发挥"（即编造）的概率。这是**用温度对抗幻觉**的一种手段——效果有限，但成本为零。

## 4.9 错误翻译：把英文栈变成用户能懂的话

### 问题

LLM API 的错误有 6 类，但异常类型来自不同的 SDK 层：

- `openai.AuthenticationError`（401）
- `openai.RateLimitError`（429）
- `openai.APIConnectionError`（网络）
- `httpx.ConnectError`（更底层）
- 裸字符串里带 "402"（余额不足，没有专用异常类）
- `openai.NotFoundError`（模型名错）

如果直接把这些抛给前端，用户看到的是：

```
openai.AuthenticationError: Error code: 401 - {'error': {'message': 'Incorrect API key provided...'}}
```

这对学生用户毫无意义。

### 实现（`kb/rag_core.py:71-88`）

```python
def describe_api_error(e: Exception) -> str:
    cls_name = type(e).__name__
    if cls_name == "AuthenticationError" or "401" in str(e):
        return "401 认证失败：密钥无效，请检查 .env 中各接口对应的 Key 与 BASE_URL"
    if cls_name in ("APIConnectionError", "ConnectError", "ConnectionError") or "connect" in str(e).lower():
        return "网络连接失败：请检查网络/代理以及各 BASE_URL 配置"
    if cls_name == "RateLimitError" or "429" in str(e):
        return "429 请求受限：请求过于频繁或额度不足，请稍后再试"
    if "402" in str(e):
        return "402 余额不足：请到对应平台充值"
    if cls_name == "NotFoundError" or "404" in str(e):
        return "404 模型不存在：请检查 EMBEDDING_MODEL / DEEPSEEK_MODEL 名称"
    return f"{cls_name}: {e}"
```

### 这段代码的设计取舍

**① 用类名字符串而不是 `isinstance`**

为什么？因为不想 `import openai` 的异常类。如果 import 了，`openai` 就成了硬依赖（虽然它已经被 `langchain-openai` 间接依赖，但显式 import 会让"换供应商"变难）。

用 `type(e).__name__ == "AuthenticationError"` 是一种**鸭子类型的异常识别**：只要类名对得上就认，不管来自哪个包。

**代价**：如果某个库有个不相干的 `AuthenticationError`（比如 LDAP），会被误判。在这个上下文里风险极低。

**② 字符串匹配兜底**

`"401" in str(e)` 覆盖了"异常类名不认识但消息里带状态码"的情况。这是必要的，因为 httpx 的异常层次和 openai SDK 的包装层次不一定对应。

**③ 每条错误都给出"下一步"**

注意这五条都不是"出错了"，而是"出错了 + 该改哪里"：

- 401 → 检查 `.env` 中的 Key 与 BASE_URL
- 网络 → 检查网络/代理以及各 BASE_URL
- 429 → 稍后再试
- 402 → 去平台充值
- 404 → 检查模型名

**这是一个产品级的错误处理原则：错误消息的价值在于"减少用户的下一步搜索"。**

**④ 最后一行保留原始信息**

`return f"{cls_name}: {e}"` —— 不认识的错误原样返回。这很重要：不要试图翻译一切，否则会丢失排查线索。

### 代价

- 中文消息无法被日志系统按英文关键字检索（比如 grep "timeout" 找不到）。需要 grep "网络连接失败"。
- 如果错误消息里同时含 "401" 和 "429"（罕见），会命中第一个分支。

## 4.10 视觉链路：三个必须的工程处理

### 处理 1：图片压缩（`api/chat.py:462-480`）

```python
im.thumbnail((1024, 1024))
im.save(buf, format="JPEG", quality=85)
```

- `thumbnail` 会**保持宽高比**（不是 `resize`）；
- 长边 1024 是视觉模型的常见"有效分辨率"上限，再大也不会提升理解质量；
- JPEG q85 是"肉眼无损"与"体积减半"的平衡点；
- `RGBA/P/LA` 先转 `RGB`——否则 JPEG 保存会失败（不支持透明通道）。

注释说明了动机："20MB 原图直接 base64 发 qwen-vl-plus 既慢又易被拒收。"

一个 20MB 的 PNG 截图，压缩后可能只有 300KB。base64 之后是 400KB。传输时间从 20 秒降到 0.5 秒。

### 处理 2：Pillow 可选，失败降级

```python
try:
    from PIL import Image
    ...
except Exception:
    pass
# 退回原图
mime, _ = mimetypes.guess_type(path)
with open(path, "rb") as f:
    return f.read(), mime or "image/png"
```

`requirements.txt` 里 Pillow 的注释：

```
# ---------- 图片处理（聊天附件压缩；缺失时自动降级原图，不硬依赖）----------
pillow>=10.0
```

**"不硬依赖"这个设计是对的**：图片压缩是优化，不是功能。缺了 Pillow，用户还能用图片理解（只是慢一点）。

但注意 `except Exception` 的范围太宽——它也会吞掉"图片文件损坏"的错误，然后尝试读原图字节，最终发给视觉模型一个坏文件。这是可以接受的（视觉模型会返回错误，走 `describe_api_error`）。

### 处理 3：data URL 而不是上传

```python
return f"data:{mime};base64,{base64.b64encode(data).decode()}"
```

为什么用 data URL？因为百炼的 OpenAI 兼容接口支持 `{"type": "image_url", "image_url": {"url": "data:image/jpeg;base64,..."}}`，不需要先把图片上传到某个 URL。

**这避免了"需要一个公网可访问的图片存储"** —— 又一个依赖的消除。

代价：base64 会使体积增大约 33%，且整个图片在内存里。对于 9 张图 × 300KB = 2.7MB，base64 后 3.6MB，在 2G 机器上可接受。

## 4.11 reasoning 模型：可选接入的设计

### 事件协议

```
event: reasoning { text: "..." }  思考增量（delta，前端自行累加）
仅在服务端配置了思考模型时出现（.env 的 DEEPSEEK_REASONER_MODEL）。
未配置时此事件**完全不出现**。
```

### 两个设计亮点

**① "未配置时完全不出现"，而不是"配置了才有内容"**

这两个说法看起来一样，实现上完全不同：
- 前者：不 yield 这个事件；
- 后者：yield 空字符串。

前端的解析逻辑因此可以简单：**收到 reasoning 就累加，收不到就不显示**。不需要判断"是不是空"。

**② `done` 帧里带完整 reasoning**

```python
# reasoning 是**完整思考文本**：流式期间前端逐帧累加，
# 断线重连/刷新的前端只能靠这一份拿回完整思考块（未启用时为空串）
```

这与 §2.5 的 `done.answer` 是同一个模式：**流式给增量，收尾给全量**。

为什么需要这个冗余？因为流式是不可重放的。用户刷新页面后，前端只有数据库里的 assistant 消息（answer），没有 reasoning——除非 done 帧里带了。

但注意：reasoning 是否落库？如果只放在 done 帧，刷新后就丢了。这是一个设计缺口：**reasoning 没有持久化**。对"思考过程"这种可能很长的内容，可能需要单独存一列。

## 4.12 模型选择的成本模型

### 为什么是 DeepSeek

没有在代码里写明，但从配置和用法可以反推三个理由：

1. **价格**：DeepSeek 的定价在同类中处于最低档（约为 GPT-4 类的 1/20）。对一个学生项目、日配额 60 次问答的场景，这是决定性的。
2. **中文能力**：中文问答质量对"知识库问答"这个场景足够。
3. **OpenAI 兼容**：零适配成本。

### 成本估算（按 2026 年价格量级）

一次典型 RAG 问答：
- 输入：system（约 300 token）+ 3 条片段（约 800 token）+ 历史（约 500 token）= 1600 token
- 输出：约 400 token

按 DeepSeek 的价格（输入约 1 元/百万 token，输出约 2 元/百万 token）：

```
单次成本 ≈ 1600 × 1/1e6 + 400 × 2/1e6 = 0.0016 + 0.0008 = 0.0024 元
```

一天 60 次问答 ≈ 0.14 元/用户/天 ≈ 4.3 元/用户/月。

加上 embedding（入库时）：一篇 1 万字的文档约 7000 token，切片 14 片，embedding 成本约 0.0005 元。几乎可以忽略。

**这就是为什么 `DAILY_ASK_LIMIT=60` 是合理的：它对应的月成本约 4 元，低于任何订阅制产品的定价下限。**

而"embedding 是按 token 计费的"这句话（`core/quota.py`）提醒的是另一件事：**建库是批量操作**。一次上传 100 篇论文，可能是 100 万 token 的 embedding，成本 0.5 元——单次不贵，但如果被刷，就是 `DAILY_EMBED_LIMIT=1000` 片的上限在挡（1000 片 × 500 字 ≈ 50 万字符 ≈ 35 万 token ≈ 0.2 元/天/用户）。

### 这个成本模型的意义

它解释了为什么所有成本护栏的粒度都是"次"和"片"，而不是"token"：

- 按 token 计费需要精确知道每次调用的 token 数，而流式响应的 token 数是**事后才知道**的；
- 按次/片计量是**事前可知**的，可以在调用前拦截。

**这是一个"可执行性"驱动的设计**：不是最精确的方案，但是唯一能"在花钱之前拦住"的方案。

## 4.13 结构化输出：为什么到处都是 JSON 容错代码

### 三处相同的模式

```python
# kb/rag_core.py:820-828（主题标签）
raw = (resp.content or "").strip()
if raw.startswith("```"):
    raw = raw.strip("`")
    if raw[:4].lower() == "json":
        raw = raw[4:]
    raw = raw.strip()
tags = _json.loads(raw)
```

```python
# api/chat.py:1232-1240（用户画像）
raw = (resp.content or "").strip()
if raw.startswith("```"):
    raw = raw.strip("`")
    if raw[:4].lower() == "json":
        raw = raw[4:]
    raw = raw.strip()
tags = _json.loads(raw)
```

这段"剥代码块"的逻辑出现了两次（几乎逐字相同）。这是一个**双轨的雏形**：如果哪天要修 bug（比如模型用了 ```JSON 大写，或者用了单引号），要改两处。

### 为什么模型会包代码块

提示词写的是"只输出一个 JSON 数组，不要 Markdown 代码块"。但模型仍然经常包。原因是：

- 训练数据里 JSON 几乎总是出现在代码块里；
- 指令遵循是概率性的，"不要"这种否定指令尤其容易被忽略。

**结论：在提示词里禁止格式，永远只能降低概率，不能消除。所以解析侧必须容错。**

### `_json.loads` 之后还有校验

```python
vocab_set = set(USER_PROFILE_TAGS)
out = [str(t).strip() for t in tags if str(t).strip() in vocab_set]
return out[:3]
```

这是**受控词表**机制：模型可以输出任何词，但只有词表内的才被接受。

为什么需要？因为标签会写进 `user_tags` 表，而表会随标签种类增长。如果模型自由发明标签（"考研数学复习计划"、"考研数学复习"、"考研数一"），表会爆炸，且后续聚合（`profile.aggregate`）无法归并。

**用受控词表把"开放生成"收敛成"封闭分类"**，是一个非常重要的模式。同样的思路也用在：

- `mode` 的白名单（`VALID_MODES = ("auto", "rag", "agent", "llm")`）
- `scenario` 的白名单（"非白名单值按未选处理"）
- `rating` 的 CHECK 约束（`CHECK(rating IN ('up','down'))`）

### 一个缺失的容错

如果模型输出了 `{"tags": [...]}` 而不是 `[...]`，`_json.loads` 会成功（返回 dict），然后 `for t in tags` 会遍历 key（字符串），得到 `"t","a","g","s"` 这样的垃圾。这些会被词表过滤掉（因为不在词表里），所以最终返回空列表——**失败是安全的，但原因被掩盖了**。

更好的做法是显式检查 `isinstance(tags, list)`，不匹配就返回空。这是一个可以改进的小点。

## 4.14 模型层的失败矩阵

把这一层的所有失败模式整理成一张表，这是运维时最有用的东西：

| 失败 | 表现 | 当前处理 | 用户感知 |
|---|---|---|---|
| Key 无效 | 401 | `describe_api_error` → 中文提示；启动时 `config.validate()` 报缺失 | "401 认证失败：密钥无效" |
| 余额不足 | 402 | 同上 | "402 余额不足：请充值" |
| 模型名错 | 404 | 同上 | "404 模型不存在：请检查模型名" |
| 限流 | 429 | httpx 重试 2 次；仍失败则中文提示 | "请求过于频繁" |
| 网络断 | ConnectError | 重试 2 次 | "网络连接失败" |
| 首字迟迟不来 | 60s read timeout | 重试 → 失败 | error 帧 |
| 流式中途断 | 异常 | 发 error 帧，不重试 | 已出内容 + 错误提示 |
| 输出被截断（达 max_tokens） | 无异常，内容不完整 | **没有检测** | 回答突然断在半句 |
| 输出格式不符（JSON） | 解析失败 | 静默返回空（标签/画像） | 无感知（功能降级） |
| embedding 模型变更 | 检索结果乱 | **没有检测** | 回答与问题无关 |

最后两行是本层最重要的两个缺口：

**缺口 1：`finish_reason == "length"` 没有处理。**

OpenAI 兼容接口的响应里有 `finish_reason` 字段，值为 `"stop"`（正常）或 `"length"`（到达 max_tokens）。当前代码完全不检查这个字段。

后果：用户看到一句断在半截的回答，不知道是"模型说完了"还是"被截断了"。对于 `max_tokens=2048` 的主回答，长回答很容易触发。

修复成本极低：在 `done` 帧里加一个 `truncated: true` 标志，前端显示"回答较长已截断，可让我继续"。

**缺口 2：embedding 模型一致性没有校验。**

见 §4.2。这是一个"静默失败"（卷一形态 2 的恶性变体）。修复方案：把模型名写进 collection metadata，检索前比对。

## 4.15 本卷小结：模型层是一个"约束翻译器"

这一层做的事，本质上是把**外部 API 的不可控性**翻译成**内部的可控性**：

| 外部不可控 | 翻译成内部可控 |
|---|---|
| 供应商可能限流 | 重试 2 次 + 配额 |
| 生成可能无限长 | `max_tokens` 分层 |
| 错误信息是英文栈 | 5 类中文提示 + 下一步 |
| 模型可能输出任意格式 | 受控词表 + 代码块剥离 |
| 响应可能卡死 | 60s 字节间隔超时 |
| 一次问答会 new 2~3 个客户端 | 按参数缓存实例 |
| 两家供应商能力不同 | 三个客户端 + 可选回落 |

翻译的质量，决定了这一层"漏不漏"。当前的主要漏洞都在**静默失败**上（截断未检测、embedding 不一致未检测），而不是在崩溃上。

下一卷进入检索层。这是本项目最厚的一层，也是"技术的深度"最集中的地方——因为检索的质量直接决定回答的质量，而检索的错误几乎都是静默的。
