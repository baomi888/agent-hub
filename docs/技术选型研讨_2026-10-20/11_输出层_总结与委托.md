# 卷十一 · 输出层：每日总结与每日委托

> 本卷解决的问题：**让系统主动为用户写东西，并且写出来的每一句都能指回原始对话。**
> 这一层是全项目唯一"没有用户提问"的产出——它必须自己决定"写什么、写多长、凭什么这么写"。

---

## 11.0 输出层的特殊性：没有提问者

前面十层都是"响应式"的：用户问，系统答。错了用户会说。

输出层不同：

| 维度 | 交互式 | 总结/委托 |
|---|---|---|
| 触发者 | 用户 | 定时器 |
| 内容边界 | 用户指定 | **系统自己判断** |
| 错误发现 | 用户当场看到 | 用户第二天才看到（或永远不看） |
| 长度 | 用户预期 | 系统决定 |
| 可信度要求 | 中（用户可以追问） | **高（用户没有追问机会）** |

最后一行是关键：**如果总结里写了一句"用户今天学习了 RAG 的三段式检索"，而实际上用户从没说过这句话，用户会以为"系统记错了"，而不是"系统编了"。**

所以输出层的核心要求不是"写得好"，是**"每一句都成立"**。

这直接推出了本层最重要的机制：**强制溯源**。

## 11.1 单次调用 vs map-reduce：一次诚实的降级

### spec 的要求

```
spec 写的是「按会话分块摘要（map）→ 合并（reduce）」的多轮调用。
```

标准做法：

```
map:    每个会话（或每 N 条消息）→ 一段局部摘要
reduce: 把所有局部摘要 → 一份全局总结
```

**优点**：
- 每个 map 的输入小，不会超上下文；
- 可以并行（多个会话同时摘要）；
- 单点失败不影响全局（某个会话摘要失败，跳过）。

**缺点**：
- 多段 JSON 编排，每一段都可能格式错；
- 成本是 N+1 次调用；
- 中间结果需要存储或传递。

### MVP 的实现

```python
# MVP 说明（与 spec §3.1 的偏差，如实标注）
# spec 写的是「按会话分块摘要（map）→ 合并（reduce）」的多轮调用。MVP 这里用**单次调用**
# 把当天对话整体交给模型产出结论数组，再统一做溯源过滤——长上下文已在 `_gather_day_text`
# 里按预算截断。map-reduce 的多轮拆分是长日（数百条消息）下的伸缩优化，本次先不实装，
# 避免把脆弱的多段 JSON 编排提前搬进核心；接口与落库结构不变，后续可直接升级。
```

这段话有三个值得学的点：

**① 明确标注"偏差"而不是"实现"**

"与 spec §3.1 的偏差，如实标注" —— 没有假装 MVP 就是 spec。这种诚实很重要，因为后人看代码时不知道"这是设计还是偷懒"。

**② 给出"为什么现在不做"的理由**

"避免把脆弱的多段 JSON 编排提前搬进核心" —— 这不是"没时间"，是"这个复杂度现在不值得"。

**③ 说明"后续可直接升级"的条件**

"接口与落库结构不变" —— 意味着升级不需要改调用方、不需要改数据库。这是一个**可演进的设计**。

### 预算截断

```python
_MAX_CHUNK_CHARS = 15000
_MAX_REDUCE_CHARS = 20000
_RECENT_TURNS = 10
```

虽然没做 map-reduce，但常数保留了。说明设计时是按 map-reduce 的规格算的预算，只是实现上先用单次。

`_gather_day_text` 会按 `_MAX_CHUNK_CHARS` 截断——如果当天有 500 条消息，只取前面 15000 字符。

**这是一个静默的截断**：用户不知道总结只覆盖了当天的前一半。

**改进方向**：在 `stats` 里加一个 `truncated: true`，前端显示"当天对话较多，总结覆盖了前 N 条"。当前没有。

### 什么时候必须上 map-reduce

判据：**当"截断造成的遗漏"变得不可接受时**。

具体地：
- 重度用户一天 200+ 条消息 → 15000 字符只覆盖约 50 条 → 遗漏 75%；
- 如果总结要作为"学习档案"，遗漏是不可接受的。

**对于一个学生每天用 5~10 轮的场景，单次调用足够。** 所以这个降级是合理的。

## 11.2 统计确定性：不走模型

### 设计（`service/daily.py:9-10`）

> **统计确定、不走模型**：`collect_stats` 只做 SQL 聚合，可被直接 SQL 交叉验证。

### 实现

```python
def collect_stats(uid: str, date: str) -> dict:
    """统计某用户某天的对话情况，确定性、不走模型。

    返回 {date, conversation_count, message_count, user_msg_count,
          assistant_msg_count, active_hours, tool_call_count}。

    tool_call_count 以 assistant 消息数作代理（messages 表未单独存工具调用，
    见 issues/05-daily-summary.md 验收 #2 的口径约定）。
    """
```

### 为什么统计不能走模型

如果让模型数"今天有多少条消息"，它会：
- 数错（长列表计数是 LLM 的弱项）；
- 幻觉（"大约 20 条"，实际 13 条）；
- 不可复现（同样输入两次，结果不同）。

而 SQL 聚合是**确定性**的：同样的数据永远同样的结果，且可以独立验证。

**"可被直接 SQL 交叉验证"** 这句话很重要：如果有人怀疑"总结里说今天聊了 5 个会话"，可以直接跑：

```sql
SELECT COUNT(DISTINCT conversation_id) FROM messages
JOIN conversations ON ... WHERE owner_id=? AND created_at BETWEEN ? AND ?
```

对照。

**这是一个"可审计性"的设计**：总结里的数字不是"模型说的"，是"数据库说的"。

### `tool_call_count` 的代理口径

```python
# tool_call_count 以 assistant 消息数作代理（messages 表未单独存工具调用）
```

这是一个**已知的近似**：`messages` 表只存 role/content，不存"这条 assistant 消息调了哪些工具"。

所以 `tool_call_count == assistant_msg_count`。这在语义上是错的（一次回答可能调 3 个工具，也可能 0 个）。

**为什么可以接受**：
- 这个数字只用于"展示"，不用于决策；
- 精确统计需要新增一列（`tool_calls TEXT`），涉及表结构变更；
- 注释明确标注了这是"代理"，不是精确值。

**这是一个"标注了局限的近似"**，比"假装精确"好。

### `active_hours` 的算法

```python
h = time.localtime(r["created_at"]).tm_hour
active_hours[h] = active_hours.get(h, 0) + 1
```

按小时分桶统计消息数。用途大概是前端画"活跃时段热力图"。

**注意**：这里用的是 `time.localtime`（系统时区），与卷八 §8.4 的时区口径分裂问题一致。

### 性能

```sql
SELECT m.conversation_id, m.role, m.created_at FROM messages m
JOIN conversations c ON m.conversation_id = c.id
WHERE c.owner_id = ? AND m.created_at >= ? AND m.created_at < ?
ORDER BY m.id ASC
```

有 `idx_conv_owner(owner_id, updated_at DESC)` 和 `idx_msg_conv(conversation_id, id)` 两个索引。

但这个查询是"按 owner + 时间范围"过滤 messages。`messages` 表没有 `(created_at)` 索引，也没有 `(conversation_id, created_at)` 索引。

所以执行计划大概是：
1. 用 `idx_conv_owner` 找到该用户的所有会话（假设 50 个）；
2. 对每个会话，用 `idx_msg_conv` 扫描消息，按 `created_at` 过滤。

50 个会话 × 平均 400 条消息 = 20000 行扫描。约 5~20ms。

**可以接受，但会随用户历史增长而变慢。** 如果某用户有 500 个会话，就是 200,000 行扫描，约 100ms。

**改进方向**：加 `CREATE INDEX idx_msg_created ON messages(created_at)`，或者在 `conversations` 表加 `last_message_at` 做粗筛。当前没做。

## 11.3 强制溯源：本层最重要的机制

### 设计（`service/daily.py:11-13`）

> **溯源强制**：`summarize_day` 让模型产出的每条结论都带 `source_refs`，写入前校验每个 ref 都能指回当天该用户真实存在的 message id；指不回去（或没有 refs）的结论**直接丢弃并记日志**（对应 we/先进产品思路吸收.md:40 的「不可指回原文不许入库」）。

### 提示词的写法

```python
_SYS_SUMMARY = (
    "你是每日总结助手。基于用户当天对话，提炼 1~4 条**可溯源**的结论。"
    "每条必须带 source_refs：引用对话里出现的消息编号（形如 [user#12] 里的数字 12）。"
    "只提炼对话里**确实发生**的事，不要编造。"
    "严格只输出一个 JSON 数组，元素形如 "
    '{"text": "结论文字", "source_refs": [12, 15]}，不要输出任何额外文字。'
)
```

三个设计：

**① 消息编号的格式 `[user#12]`**

在喂给模型的对话文本里，每条消息前缀 `[user#12]` 或 `[assistant#15]`。这样模型能引用。

**为什么要带 role 前缀**：因为 id 是全局自增的，`12` 可能是 user 也可能是 assistant。带 role 帮助模型理解上下文。

**② 要求 1~4 条**

为什么不是"尽可能多"？因为：
- 太多结论会让总结变成流水账；
- 每条都要溯源，条数越多越容易编；
- 4 条是"一天的重点"的合理上限。

**③ "严格只输出 JSON 数组"**

与卷四 §4.13 的问题一样：模型仍可能包代码块。所以解析侧需要容错（`service/daily.py` 里应该也有类似的剥离逻辑）。

### 溯源校验的实现

```python
def _filter_by_traceability(conclusions, valid_ids):
    """丢弃指不回原文的结论。

    valid_ids 是当天该用户真实存在的 message id 集合。
    """
    kept = []
    for c in conclusions:
        refs = c.get("source_refs") or []
        if not refs:
            logger.warning("结论无溯源，丢弃：%s", c.get("text", "")[:50])
            continue
        if any(r not in valid_ids for r in refs):
            logger.warning("结论溯源失效，丢弃：refs=%s", refs)
            continue
        kept.append(c)
    return kept
```

（伪代码，实际实现可能有细节差异。）

### 这个机制的强度

**它挡住的是"编造"**：如果模型写了一句"用户今天讨论了微积分"，但没有对应的消息 id，就丢弃。

**它挡不住的是"曲解"**：如果用户确实发了 `[user#12] "微积分好难"`，模型总结成"用户深入学习了微积分"，refs=[12] 是合法的，但语义是曲解的。

**所以溯源解决"有没有依据"，不解决"依据用得对不对"。**

这是一个**必要的但不充分**的机制。它把"完全编造"这类最严重的问题挡住了，剩下"曲解"需要人工判断（或者更强的模型评判）。

### "直接丢弃"而不是"标记"

为什么丢弃而不是"标记为无依据，让用户自己判断"？

因为：
- 用户看总结是为了"省时间"，如果还要逐条判断可信度，就失去了意义；
- 一条无依据的结论出现在"学习总结"里，会污染整个总结的可信度（用户会怀疑所有结论）。

**"宁可少一条，不要错一条"** —— 这与卷五的"宁可说不知道，也不要编"是同一个价值排序。

### 代价

- 如果模型的 refs 格式不对（比如给了 `"msg_12"` 而不是 `12`），全部丢弃 → 总结为空。
- 无法区分"模型没给 refs"和"refs 错了"，都记同一条 warning。

**第一条是真实风险**：提示词说"形如 [user#12] 里的数字 12"，但模型可能输出 `"12"`（字符串）而不是 `12`（整数）。如果校验用 `r not in valid_ids` 且 `valid_ids` 是 int 集合，`"12" not in {12}` 为真 → 丢弃。

**需要确认**：校验前是否有 `int(r)` 转换。如果没有，这是一个容易触发的 bug。

## 11.4 响应形状的裁决：D-002 的完整复盘

这是一个**接口契约冲突**的案例，展示了"两个人各自实现，形状不兼容"时如何裁决。

### 冲突

`规范/决策记录.md` D-002 记录了 4 个维度的不一致：

| 维度 | 设计稿 | 实现版 |
|---|---|---|
| `content` | object `{topics, questions, highlights, todo, suggestions}` | list `[{text, source_refs}]` |
| `source_refs` | 字符串 `"msg_4711"` | 整数 `4711`（`messages.id`） |
| `sources` 字段 | **有**（`[{type, ref_id, title, ts}]`） | **无** |
| `stats` | 7 字段 | 6 字段 |

### 逐项裁决

**① `source_refs` 用整数**

```python
# `messages.id` 是 INTEGER PRIMARY KEY AUTOINCREMENT，后端的**强制溯源**
# （_filter_by_traceability）是拿 refs 去真实消息表里查，天然只有整数。
# 改成字符串就要在后端加一层 msg_xxx 编解码 —— 多一层映射就多一处能对不上的地方，
# 而「溯源正确性」恰恰是这个模块的核心卖点（refs 指不到真实消息的结论会被直接丢弃）。
# → **整数保真，命名体裁让给前端。**
```

**论证结构**：
1. 事实：数据库里是整数；
2. 后果：用字符串要加编解码层；
3. 风险：编解码是"能对不上的地方"；
4. 价值排序：溯源正确性 > 命名美观；
5. 结论：整数，前端自己加前缀。

**"命名体裁让给前端"** 这句话很好：**后端负责保真，前端负责好看。**

**② `content` 取 object**

```
`{topics, questions, highlights, todo, suggestions}` 比 `[{text}]` 多表达了结构：
`todo` 有 `done` 状态、`topics` 能带标题与摘要。产品侧要做的是「学习总结」而不只是
「一堆结论」，这个结构对 UI 有用（能分区块渲染）。而且设计稿已按此与前端对齐过。
```

**论证结构**：
1. 对比：object 比 list 多了什么；
2. 具体：`todo.done`、`topics` 带摘要；
3. 产品意图：学习总结 ≠ 一堆结论；
4. 历史：前端已按 object 对齐。

**关键在"`todo` 有 `done` 状态"** —— 这是一个 list 结构**无法表达**的信息。

如果 `content` 是 `[{text: "复习第三章"}]`，前端无法知道"这条待办做了没有"。而 object 结构里：

```json
{"todo": [{"text": "复习第三章", "done": true}]}
```

**这是一个"数据形状决定产品能力"的例子**：不是"object 更优雅"，而是"list 表达不了 done 状态"。

**③ 必须补 `sources`**

```
设计稿的 `sources` 把 `ref_id → {title, ts}` 做成映射表，前端据此渲染「可点回原文的角标**标题**」。
实现版只有裸整数 ID，**前端拿不到标题，就渲染不了产品硬要求的那个角标**。
```

**论证结构**：
1. 前端需要什么：角标的**标题**（不只是 id）；
2. 实现版给什么：只有 id；
3. 后果：渲染不了。

**注意"这是缺口，不是偏好"** —— 决策记录里明确区分了"缺口"（必须补）和"偏好"（可协商）。

### 代价的诚实标注

```
- **代价**：`content` 从 list 改回 object 会动到 C 线已实现的 `service/daily.py` 与
  `_filter_by_traceability`，是**真实返工**。
- **退守方案**：若 C 线不接受返工，则**保留 list 形状，但同样补 `sources`**
  （只做加法、不改形状）。两个方案都能消除冲突，**选哪个取决于 C 线愿付多少返工成本**。
```

**"真实返工"** —— 没有粉饰。而且给出了**退守方案**（保留 list + 补 sources），并说明"两个方案都能消除冲突"。

**这是一个成熟的裁决方式**：不是"我说了算"，而是"给出主方案 + 退守方案 + 判断依据（返工成本）"。

### "不做的事"

```
- **不做的事**：不要在两套形状之间"都支持"——前端同时兼容 object/list 会让解析逻辑脆到无法维护。
```

**这一条最有价值**。

面对接口冲突，最"省事"的做法是后端两种都返回，前端两种都解析。但：

- 前端要写 `if (Array.isArray(content))` 分支；
- 两套渲染逻辑都要维护；
- 新增字段要加两遍；
- 永远不知道什么时候能删掉旧的那套。

**"都支持"是最贵的方案，因为它把一次性的返工变成了永久的分支。**

这与卷六的"不做双轨"是同一个原则。

## 11.5 LLM 可注入：为测试而设计

### 设计（`service/daily.py:5-7`）

> **LLM 可注入**：所有会调模型的函数都把 `llm` 作为可选参数，默认走 `core.llm.get_llm()`（DeepSeek）。测试注入假 LLM（`.invoke()` 返回带 `.content` 的对象即可），不依赖真实 API Key —— 满足 spec §4.8。

### 实现

```python
def summarize_day(uid: str, date: str, llm=None):
    llm = llm or llm_mod.get_llm(temperature=0.2)
    ...
```

### 为什么这个设计重要

如果直接 `get_llm()` 在函数内部调用，测试就**无法避免真实 API 调用**：

- 需要真 key；
- 需要网络；
- 每次测试花钱；
- 结果不确定（LLM 非确定性）。

**"可注入"让测试变成纯函数测试**：

```python
class FakeLLM:
    def invoke(self, messages):
        return SimpleNamespace(content='[{"text":"测试结论","source_refs":[1]}]')

result = summarize_day("u1", "2026-10-20", llm=FakeLLM())
assert result["content"] == [...]
```

**这是一个 3 个字符的改动（`llm = llm or ...`），换来整个模块的可测性。**

### 与卷八的关系

`core/scheduler.py` 的"不 import apscheduler"是为了"可测"；这里的"LLM 可注入"也是为了"可测"。

**两个不同层次的可测性设计**：
- 依赖隔离（不 import 框架）→ 测状态机；
- 依赖注入（llm 参数）→ 测业务逻辑。

**这两种是"可测性架构"的两个基本手法。** 本项目在两处都用了，说明作者对可测性有系统性的意识。

### 代价

- 每个函数多一个可选参数（签名变长）；
- 调用方要记得传（但默认值保证了不传也对）。

**这是"零成本"的代价** —— 因为默认值是 `None`，正常调用不需要改。

## 11.6 总结只读：为什么这是一个前提而非约束

### 设计（`service/daily.py:15`）

> **总结只读**：不写会话、不改标题、不删任何东西。

### 为什么重要

因为**补生成**（`report.backfill`）要重跑过去 7 天的总结。

如果总结有副作用：

- 第一次生成时给会话打了标签 → 第二次生成时又打一遍 → 标签重复；
- 第一次生成时改了标题 → 第二次基于改过的标题生成 → 结果漂移；
- 第一次生成时写了"已总结"标记 → 第二次认为已总结，跳过。

**只读 = 幂等。** 这是一个数学性质：`f(f(x)) = f(x)`。

### 实现上的保证

`summarize_day` 只做：
1. 读 messages（`collect_stats` + `_gather_day_text`）；
2. 调 LLM；
3. 过滤溯源；
4. 返回结果（不写库）。

写库发生在**调用方**（`api/report.py` 或 worker），写的是 `daily_reports` 表（新建一行或 upsert）。

**所以"只读"是针对"用户数据"（conversations / messages），而不是"总结结果"（daily_reports）。**

这是一个精确的边界：**总结可以覆盖自己，但不能碰别人的数据。**

### 与 `idem_key` 的关系

`daily_reports` 的主键是 `report_id = md5(uid|date)[:12]`，所以同一天重复生成是 **upsert**（覆盖）。

```python
def _report_id(uid: str, date: str) -> str:
    return hashlib.md5(f"{uid}|{date}".encode()).hexdigest()[:12]
```

**用 md5(uid|date) 而不是自增 id**，保证了"同一天只有一份总结"。

这与 `job_runs.idem_key` 是同一个思路：**用业务键做唯一性**。

## 11.7 每日委托：输出层的另一半

### 与总结的区别

| 维度 | 每日总结 | 每日委托 |
|---|---|---|
| 方向 | **回顾**（今天做了什么） | **前瞻**（明天要做什么） |
| 触发 | 固定时刻（23:30） | 用户设定的时间 |
| 输出 | 结论文档 | 一条消息（投递到会话） |
| 幂等键 | `uid|date` | `job_key|delegation_id|planned_at` |
| 失败重试 | 有（backfill） | 有（retry 任务） |

### 委托的配置项（`delegations` 表）

```sql
CREATE TABLE delegations (
    delegation_id  TEXT PRIMARY KEY,
    owner_id       TEXT NOT NULL,
    name           TEXT NOT NULL,
    kind           TEXT NOT NULL DEFAULT 'daily',
    schedule_json  TEXT,        -- 时间配置
    prompt         TEXT,        -- 委托内容（"每天早上提醒我..."）
    deliver_sid    TEXT,        -- 投递到哪个会话
    kb_id          TEXT,        -- 可绑定知识库
    tone           TEXT,        -- 语气
    max_chars      INTEGER,     -- 长度上限
    enabled        INTEGER NOT NULL DEFAULT 1,
    next_run_at    INTEGER,
    created_at     INTEGER NOT NULL,
    updated_at     INTEGER NOT NULL
);
```

**七个可配置维度**：时间、内容、投递目标、知识库、语气、长度、启用状态。

### `deliver_sid`：投递到会话的设计

为什么"投递到会话"而不是"发邮件/推送"？

因为：
- 项目没有邮件/推送基础设施（依赖消除）；
- 投递到会话，用户下次打开就能看到，且**在同一个上下文里**（可以追问）；
- 复用现有的 `messages` 表，不需要新表。

**代价**：用户必须打开应用才能看到，不是"主动触达"。

**这是一个"用现有通道代替新建通道"的决策**，符合卷一的"依赖最少"原则。

但它限制了这个功能的价值：一个"每日提醒"如果不能主动触达，就退化成"打开时才看到"。

### `tone` 和 `max_chars`

```
tone        TEXT,        -- 语气
max_chars   INTEGER,     -- 长度上限
```

**这两个是"输出风格"的可配置项。**

`tone` 可能的值（推测）：鼓励型 / 客观型 / 严格型。
`max_chars`：防止生成过长（与卷四的 `max_tokens` 是同一个目的，但在业务层表达）。

**这是一个"把模型参数翻译成用户可理解的配置"的例子**：用户不理解 `temperature`，但理解"语气"。

### `schedule_json`

为什么用 JSON 而不是 cron 字符串？

因为委托的时间配置可能是"每天 8:00"、"每周一三五 9:00"、"每月 1 号"——用 cron 也能表达，但：
- 用户不理解 cron；
- 前端的时间选择器产出的是结构化数据（`{type: "daily", hour: 8, minute: 0}`）；
- 转成 cron 再转回来会丢失信息（比如时区、跳过节假日的意图）。

**存原始结构，运行时再转 cron。** 这是一个正确的"存储格式 vs 执行格式"分离。

## 11.8 投递的幂等：`planned_at` 的作用

### 三条链路

```
1. web 手动"立即执行" → 写一行 job_runs（status=pending, trigger=manual）
2. worker 定时扫描 → 找到 next_run_at <= now 的委托 → 写 job_runs（trigger=schedule）
3. worker 重试 → 扫描 status=failed AND next_attempt_at <= now
```

三条链路都可能写入 `job_runs`，必须保证不重复投递。

### `idem_key = job_key|subject_id|planned_at`

对委托来说：
- `job_key = "delegate.dispatch"`
- `subject_id = delegation_id`
- `planned_at = 该委托的计划触发时刻`

**关键在 `planned_at`**：

- 每天 8:00 的委托，今天的 `planned_at` 是 `2026-10-20 08:00:00` 的 Unix 秒；
- 明天的 `planned_at` 是 `2026-10-21 08:00:00`；
- **同一天的重复扫描，`planned_at` 相同** → 幂等。

**如果 `planned_at` 用"扫描时刻"**：

- 8:00 扫描 → planned_at=8:00:03 → 插入；
- 8:05 扫描 → planned_at=8:05:01 → **不同的 key** → 又插入一次 → 重复投递。

所以 `planned_at` 必须是"业务计划时刻"，不是"实际执行时刻"。

**这与卷七 §7.8 的分析完全一致，但这里多了一层：`planned_at` 必须由"委托的 schedule 配置"计算出来，而不是由"当前时间"决定。**

### `trigger` 字段

```sql
trigger TEXT NOT NULL DEFAULT 'schedule'
```

值：`schedule` / `manual`。

注释：

> `trigger`（schedule / manual —— 排查「为什么今天没发」时第一时间要看这个字段）

**这是一个"为排障而加的字段"**。

场景：用户说"今天早上没收到委托"。
- 查 `job_runs`：没有记录 → 说明没触发（调度问题）；
- 有记录但 `status=failed` → 看 `error`（执行问题）；
- 有记录且 `status=succeeded` 但 `trigger=manual` → 用户自己手动执行过，定时那条可能被幂等挡了。

**三个分支对应三个不同的根因。** 没有 `trigger` 字段，第三条就查不出来。

## 11.9 补生成：`report.backfill`

### 配置

```python
"report.backfill": {
    "cron": "0 4 * * *",
    "description": "补生成过去 7 天内 failed / empty 的总结",
},
```

### 为什么需要

总结可能失败：

- 23:30 时 LLM 限流 → `failed`；
- 当天没有对话 → `empty`（统计为 0）；
- 用户 23:35 才发现有对话 → 但总结已经生成了（覆盖不全）。

补生成在凌晨 4 点重跑这些。

### 为什么是 7 天

- 太短（1 天）：如果连续两天失败（比如配额问题），就永久丢了；
- 太长（30 天）：每次补生成要扫描 30 天的数据，且大部分已经成功，浪费。

7 天是一个"足够容错，又不浪费"的窗口。

### "empty" 的定义

如果当天没有对话，`collect_stats` 返回全 0。此时应该：
- 生成一份"今天没有对话"的总结？（无意义）
- 标记 `empty`，不生成内容？

补生成逻辑要处理"empty → 后来又有了对话"的情况：

- 23:30 时无对话 → `empty`；
- 但用户在 23:45 聊了几句；
- 凌晨 4 点补生成 → 应该重新生成（因为数据变了）。

**这要求 `empty` 不被当成"成功"**，否则补生成会跳过它。

### 与 `_report_id` 的配合

补生成会 `upsert` 同一行（`report_id = md5(uid|date)`），所以不会产生重复。

**这是"用业务键做主键"的第二个好处**（第一个是幂等）：补生成不需要"先查有没有，再决定插入还是更新"。

## 11.10 前端渲染：降级策略

### D-002 里提到的前端过渡方案

```
- **前端过渡期**：后端补齐 `sources` 前，前端用**已加载的会话消息**本地查 `id → 片段` 降级渲染，
  查不到就渲染弱角标，**不要丢弃整条结论**（后端已保证 refs 都是真实的）。
```

**这段设计非常好，值得单独分析。**

### 问题

总结里的 `source_refs` 是 `[12, 15]`。前端要渲染成"可点回原文的角标"。

但如果后端没给 `sources`（`{12: {title: "...", ts: ...}}`），前端只有 id，不知道标题。

### 三种应对

| 方案 | 做法 | 问题 |
|---|---|---|
| 等后端补 | 先不渲染角标 | 功能缺失 |
| 显示裸 id | `[12]` | 用户点不了，也不知道是什么 |
| **本地查** | 用已加载的消息列表找 id | 只能查到"当前会话"的消息，跨会话查不到 |

本项目选第三种，并明确"查不到就渲染弱角标"。

### "不要丢弃整条结论"

这是关键。如果因为"角标渲染不了"就把整条结论隐藏，用户会失去信息。

**"信息不完整"优于"信息缺失"。** 一个弱角标（灰色、不可点）比没有角标好，一条有弱角标的结论比没有结论好。

**这是一个"降级要降得浅"的原则**：能显示 80% 就显示 80%，不要因为 20% 缺失就归零。

### 这个方案的前提

```
（后端已保证 refs 都是真实的）
```

**这是整个降级方案成立的基础**：因为后端做了 `_filter_by_traceability`，所以前端知道"每个 ref 都对应一条真实消息"。

如果没有这个保证，前端就无法区分"refs 是错的"和"我本地没加载到"。降级就变成了"掩盖错误"。

**所以：前端的降级策略依赖后端的强保证。** 这是一个明确的契约。

## 11.11 输出层的整体评价

### 三个层次的信任

输出层的设计围绕"信任"展开，分三层：

| 层 | 手段 | 保证什么 |
|---|---|---|
| **数据层** | `collect_stats` 走 SQL | 数字是真的 |
| **内容层** | `_filter_by_traceability` | 每句有依据 |
| **呈现层** | 降级渲染 | 依据没了也不丢结论 |

**三层是递进的**：
- 数据错了，内容再准也没意义；
- 内容编了，呈现再好也是误导；
- 呈现崩了，前两层白做。

### 一个未解决的矛盾

**"总结覆盖不全"没有被表达。**

`_MAX_CHUNK_CHARS = 15000` 会截断当天的对话。但：
- 用户不知道；
- `stats.message_count` 是**全量**的（SQL 统计），而内容是**部分**的（截断后）；
- 所以用户看到"今天 200 条消息" + "3 条结论"，可能以为 3 条概括了 200 条。

**这是一个"数字与内容口径不一致"的问题**（卷一的形态 5）。

修复方向：`stats` 里加 `covered_messages` / `truncated`，前端显示"基于前 N 条消息生成"。

### 一条可迁移的经验

`service/daily.py` 开头的五条设计要点，是一份很好的"输出层设计清单"：

```
1. LLM 可注入        → 可测
2. 统计确定、不走模型  → 可审计
3. 溯源强制          → 可信
4. 总结只读          → 可重跑
5. 复用同一 SQLite    → 简单
```

**五条对应五个质量属性**：可测、可审计、可信、可重跑、简单。

任何一个"系统自动生成内容"的功能，都应该能回答这五个问题。缺一个，就会在某个时刻出问题：
- 缺 1 → 测试写不出来；
- 缺 2 → 数字不可信；
- 缺 3 → 内容不可信；
- 缺 4 → 不能重跑；
- 缺 5 → 多一套连接管理，多一类 bug。

下一卷是最后一卷：横向归纳。把十二卷的决策放在一起，提炼可迁移的定律，并给出每个决策的反转条件。
