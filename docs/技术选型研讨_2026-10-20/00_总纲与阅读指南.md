## 序：这份报告为什么值得写

绝大多数技术选型文档写的是"我们用了什么，它有什么优点"。这类文档在他选型当天就过期了——因为优点是可以从官网复制的，而**为什么没选另一个**才是真正会失效的知识。

这个项目有一个罕见的特征：几乎每个模块的源码注释里，都留着当时"被否决的方案"和"否决它的实测数据"。例如：

- `kb/rag_core.py` 里记着 Chroma 默认距离口径是平方 L2 而不是余弦，以及算错这个口径之后线上把「距离」当「相似度」显示成 `1.089 / 1.160 / 1.237` 的具体表现；
- `agent/builder.py` 里记着 LangGraph checkpointer **故意返回 None** 的三条实测依据，其中包括"第 3 轮状态 12 条、本应 6 条"这个可复现的数字；
- `requirements.txt` 第 45 行写着 `duckduckgo-search` 是死依赖，全项目零引用，但摘掉它会让 `import httpx` 失败；
- `core/scheduler.py` 开头就写清"为什么不把这些直接交给 APScheduler 的 JobStore"，三个理由互相独立。

这些不是评论，是**判据**。判据可以迁移到下一个项目，评论不能。所以本报告的方法不是"介绍技术"，而是把这些散落在注释、ADR、修复说明、回归测试里的判据重新组织成一条可以追溯的推理链，并且在每一处都追问三个问题：

1. **当时真正约束决策的是什么？**（不是"哪个技术更好"，而是"在 2 核 2G、三个人并行、备案未下、开发机是 Windows 而生产是 Linux 的条件下，哪个技术不会先炸"）
2. **被否决的方案，否决理由今天还成立吗？**（很多否决是针对当时环境的，环境一变就该翻案）
3. **这个决策埋了什么代价，代价在什么条件下会变成事故？**

第三问是重点。本项目历史上真实的几次事故——尾斜杠重定向黑洞、跨库 JOIN 500、登录 Cookie 缺 Secure、相似度口径错、checkpoint 重复累积——无一例外都是"决策本身是对的，但决策的适用边界没写下来，后来有人在边界外使用了它"。

## 一、报告的三种读法

**读法 A · 按层读（推荐给第一次接触本项目的人）**
从卷一读到卷十二。卷一建立约束场，卷二到卷十一按请求生命周期推进：一个 HTTP 请求进来（卷二），被验明身份（卷三），送去调模型（卷四），如果是问答则走检索（卷五）或走 Agent 编排（卷六），读写数据（卷七），被定时任务从旁驱动（卷八），上下文在轮次之间被压缩（卷九），结果流回浏览器（卷十），最后沉淀成每日总结（卷十一），卷十二做横向归纳。

**读法 B · 按决策读（推荐给要改代码的人）**
直接看下方「决策索引表」，找到你要动的那一行，跳到对应卷的小节。每一节都独立成立，不依赖前文。

**读法 C · 按反模式读（推荐给要做技术评审的人）**
先读卷十二。那里把本项目踩过的坑归纳成十条可迁移的工程定律和一份反模式清单。如果你时间只够读一章，读那一章。

## 二、决策索引表

下表是本报告的全部决策点。**"关键判据"一列是这一节的结论压缩**，如果你只想知道结论，看这一列；想知道推理过程，看卷号。

### 卷二 · 接入层

| # | 决策 | 关键判据 | 卷 |
|---|---|---|---|
| 2.1 | FastAPI 而非 Flask / Django | 原生 async + Pydantic 校验 + 自动 OpenAPI，三者缺一都要自己写 | 二 |
| 2.2 | 直接 `sqlite3` 而非 SQLAlchemy ORM | ORM 的价值在跨库与复杂关系；本项目两张库共 8 张表，全手写 SQL 反而可控 | 二 / 七 |
| 2.3 | 单进程 uvicorn，不扩多 worker | 限流表、BM25 缓存、Agent 图缓存在进程内存里，多 worker 直接语义错 | 二 |
| 2.4 | 手写 SSE 而非 sse-starlette | 需要 9 种自定义事件类型与帧级断连检测，框架的封装反而挡住控制权 | 二 |
| 2.5 | 只发 delta 不发累计全文 | 累计全文是 O(n²) 传输，千 token 回答传 50 万字符 | 二 |
| 2.6 | 断连检测每 16 帧一次 | `is_disconnected()` 要读 ASGI 状态，逐帧调用等于白付上千次开销 | 二 |
| 2.7 | `redirect_slashes=False` + 自研归一中间件 | Next rewrite 改 Host，FastAPI 的 307 Location 指向 `localhost:8000`，浏览器必炸 | 二 |
| 2.8 | 后端只监听 `127.0.0.1:8000` | 少一层暴露面；且 8000 直连绕过 Next 的 Cookie 域设置会丢登录态 | 二 / 三 |
| 2.9 | 429 用全局异常处理器而非端点内 catch | 端点 catch 容易顺手转成 500，前端分不清"系统坏了"和"你用超了" | 二 |

### 卷三 · 身份与安全

| # | 决策 | 关键判据 | 卷 |
|---|---|---|---|
| 3.1 | PBKDF2-HMAC-SHA256 手写，不用 passlib/bcrypt | 标准库实现，省两个依赖；接口形状标准化，将来换 argon2 只改一个文件 | 三 |
| 3.2 | 手写 HS256 JWT，不用 PyJWT | 签发/校验各十来行；省依赖。代价是必须自己做 `compare_digest` | 三 |
| 3.3 | HttpOnly Cookie 为主，Header 为辅 | 同源代理下 Cookie 天然带；HttpOnly 堵死 XSS 顺走 token | 三 |
| 3.4 | `jti` 黑名单而非白名单 | JWT 无状态，退出登录只能靠黑名单；只存 jti+exp，过期即清，表不会无限长 | 三 |
| 3.5 | `owner` 作为第一个必填参数，无默认值 | 宁可漏改的调用点抛 TypeError，也不要它悄悄查到别人的数据 | 三 / 七 |
| 3.6 | 越权返回 404 而非 403 | 403 等于告诉调用方"这个 id 存在但你没权限"，可用来枚举 | 三 |
| 3.7 | `kb_id` 服务端注入，绝不写进提示词 | 提示词里的 kb_id 是越权入口：网页正文藏一句"改用 kb_别人的库"就可能被照做 | 三 / 六 |
| 3.8 | SSRF 校验解析**每一个** IP | DNS 可返回多个地址，只查第一个等于没查 | 三 |
| 3.9 | 配额双尺度：内存滑动窗口 + SQLite 日账 | 分钟级要低延迟（内存够），日级要抗重启（必须落库） | 三 |
| 3.10 | 定时任务单独配额 `auto` | 无人值守链路上的 token 原本不在任何配额里，写错就是静默烧钱 | 三 / 八 |

### 卷四 · 模型接入

|---|---|---|---|

| 4.2 | 双供应商：DeepSeek 对话 + 百炼 embedding/vision | DeepSeek 不提供 embedding 接口，这是硬约束不是偏好 | 四 |

### 卷五 · 检索层（本项目最厚的一卷）

| # | 决策 | 关键判据 | 卷 |
|---|---|---|---|
| 5.1 | Chroma 而非 FAISS / pgvector / Milvus | 要"嵌进单进程 + 零运维 + 支持 metadata 过滤"，只有 Chroma 全占 | 五 |
| 5.2 | 每库一个 collection，而非一个 collection 加 filter | 删库 = 删 collection，一条命令；filter 方案删库要遍历删，还可能删漏 | 五 |
| 5.3 | 切片 500/50，中文分隔符表 | 中文没有空格，分隔符必须含 `。！？；，` | 五 |
| 5.4 | `cos = 1 - d/2`（平方 L2 口径） | 集合未指定 `hnsw:space` 时走平方 L2；百炼向量已是单位向量 | 五 |
| 5.5 | 四段流水线：扩召回 → 离群过滤 → MMR → 截断 | 直接取 top-k 会让"三条引用里两条是同一段话" | 五 |
| 5.6 | MMR 用字符 2-gram Jaccard 做相似度 | 中文不需分词；切片重叠 50 字时相邻片段 bigram 重合度正好是要去重的对象 | 五 |
| 5.7 | 混合检索 BM25 + RRF，不引 jieba | 纯向量对"CUDA 12.4""第 3 条"这类编号召回差；jieba 会拖一串依赖 | 五 |
| 5.8 | 两套阈值：`MIN_SIM=0.25` 与 `LOW_SIM=0.45` | 前者决定"这段丢不丢"，后者决定"留下的够不够格当依据"，是两件事 | 五 |
| 5.9 | 置信度只判 top1，不判平均 | 一条强相关配几条噪声，平均法会把正常回答误判成"检索质量差" | 五 |
| 5.10 | `medium` 也算 `weak` | 0.26~0.44 是最容易硬答的灰色地带，只让 low 示弱正好漏掉它 | 五 |
| 5.11 | 查询改写**条件触发**，不是每题都改 | 只有"看起来像追问"时才多花一次 LLM；其余零开销 | 五 |
| 5.12 | 检索结果按 `(库, 问题, top_k, owner)` 缓存 | 省真实 embedding 费用；owner 进 key 防跨用户串结果 | 五 |
| 5.13 | 主题标签用 `\|t1\|t2\|` 分隔串 + `$contains` | 首尾加竖线才能精确命中成员，避免"英语"误中"英语语法" | 五 |
| 5.14 | 画像偏置只改排序，不改 `distance` | 一改 distance，相似度换算与阈值判定全被污染 | 五 |

### 卷六 · 编排层

| # | 决策 | 关键判据 | 卷 |
|---|---|---|---|
| 6.1 | `create_agent` 而非 `AgentExecutor` | v1 的 `create_agent` 底层就是 LangGraph，事件更丰富、流式更稳 | 六 |
| 6.2 | checkpointer **故意为 None** | 会话历史已在 SQLite；再挂一份会重复累积（3 轮 12 条 vs 应 6 条） | 六 |
| 6.3 | Agent 图按 `(has_kb, scene, activated)` 缓存 | 图编译是纯 CPU 开销，键的种类极少，命中率极高 | 六 |
| 6.4 | 缓存键**剔除**定位信息 | 城市一变前缀全变，KV 缓存命中率实测 90%→0% | 六 / 九 |
| 6.5 | 定位追加在**最后一条用户消息**，不进 system | system 是前缀，动态内容进去就是缓存杀手；且连续两条 human 部分模板不兼容 | 六 / 九 |
| 6.6 | `TOOL_META` 七字段声明式元数据 | "能不能重试"不能建立在模型的阅读理解上——文案会被上游吞掉 | 六 |
| 6.7 | 元数据缺失**直接起不来**，不打印日志 | 运行时按默认值做决定（把写工具当读工具并发）极难定位 | 六 |
| 6.8 | 用 `contextvars` 传调用上下文，不往 schema 加字段 | schema 会进模型视野，多一个字段就多一份被模型改写的机会 | 六 |
| 6.9 | `recursion_limit=10` | 工具返回"不可用"时模型原地重试是纯烧钱 | 六 |
| 6.10 | 自研工作流 DSL 而非 LangGraph 图 | 需要"定义存表、运行期可改、前端可编辑"；LangGraph 的图是代码 | 六 |
| 6.11 | 表达式求值器而非 `eval` | `eval` 是任意代码执行；自研只支持比较/布尔/取值 | 六 |
| 6.12 | 切换防抖三层：规则级 / 方向级 / 硬上限 | 规则打架时"不出事"比"切得准"更重要 | 六 |

### 卷七 · 存储层

| # | 决策 | 关键判据 | 卷 |
|---|---|---|---|
| 7.1 | SQLite 而非 PostgreSQL | 2G 内存跑不动 PG；且 SQLite 的"零运维"是这个项目能上线的直接原因 | 七 |
| 7.2 | WAL + `synchronous=NORMAL` + `busy_timeout=5000` | 三者是配套的：WAL 提并发读，NORMAL 省 fsync，timeout 防立刻报错 | 七 |
| 7.3 | 连接按线程复用，不用连接池 | 一次问答会开 6~7 个连接，每次重开都白付 WAL 设置开销 | 七 |
| 7.4 | 会话库与调度库**物理分开两个文件** | 同文件会让聊天写入与调度写入抢同一把锁；跨库 JOIN 曾直接 500 | 七 |
| 7.5 | 窗口截断在 SQL 层做（倒序取+翻转） | 长会话全量载入既慢又占内存，而截断只要尾部 | 七 |
| 7.6 | 归属校验并进 JOIN | 一次查询同时完成"验归属 + 取数据"，省一次 EXISTS | 七 |
| 7.7 | 部分唯一索引（`WHERE message_id IS NOT NULL`） | 一条消息只保留最后一次反馈，且允许 msg_id 为空的行共存 | 七 |
| 7.8 | 幂等靠 `UNIQUE(idem_key)` + `ON CONFLICT DO NOTHING` | "先查再插"在并发下必漏 | 七 / 八 |
| 7.9 | 压缩块写入用乐观锁 | 压缩是异步动作，下一轮请求可能先到，覆盖会丢数据 | 七 / 九 |
| 7.10 | 文件清单用 JSON 而非关联表 | 规模小（几十个文件/库）、只需整体读写；上表是为了查询，这里不需要 | 七 |

### 卷八 · 调度层

| # | 决策 | 关键判据 | 卷 |
|---|---|---|---|
| 8.1 | APScheduler 独立进程，而非 Celery / cron | Celery 要 broker（内存不够）；cron 无法感知业务幂等 | 八 |
| 8.2 | 不放 web 进程里 | web 重启会丢任务；且 web 的一次长回答会拖住调度 | 八 |
| 8.3 | 状态自己管，只让 APScheduler 管"什么时候" | 幂等/重试/心跳三件事必须可单测，不能依赖真实 cron 到点 | 八 |
| 8.4 | cron 存表，代码只给默认值 | 改周期不用改代码、不用发版 | 八 |
| 8.5 | 落库 Unix 秒，解释统一 `Asia/Shanghai` | 容器镜像 TZ 常是 UTC，"早上七点"会安静地错 8 小时 | 八 |
| 8.6 | 重试分三级：retry / fatal / quota | 配额触顶按分钟退避毫无意义，必须延后到次日同刻 | 八 |
| 8.7 | 心跳判三态而非进程表 | 进程在但被 LLM 挂住时，进程表是绿的，心跳才会变黄 | 八 |
| 8.8 | `asyncio.to_thread` 包一切同步 I/O，2ms 也包 | 裸调会卡事件循环，一次 Agent 回答十几秒期间全站排队 | 八 |

| # | 决策 | 关键判据 | 卷 |
|---|---|---|---|
| 9.1 | 压缩块 + 最近 K 轮，替代滑动窗口 | 滑动窗口每轮都改 system 后第一条，KV 前缀永远不命中 | 九 |

## 三、体量说明与章节结构约定

本报告承诺的是"决策密度"，不是"字数密度"。为避免注水，每一节统一按六段式展开：

```
【问题域】    这个技术要解决的是什么问题，问题的真实形状
【候选面】    至少两个被认真考虑过的方案（含"什么都不做"）
【判据】      在本项目的约束下，哪些维度真正有区分度
【证据】      代码/注释/实测数据/事故记录中的具体锚点
【决策与代价】选了什么，付出什么，代价何时会变成事故
【反转条件】  什么情况下这个决策应该被推翻
```

第六段是本报告与一般选型文档最大的区别。技术选型不是一次性判断，是**带有效期的判断**。写明反转条件，等于给未来的自己留了一个开关。

## 四、素材来源与可信度分级

本报告不使用任何外部推测。所有事实性陈述来自以下四类素材，并在正文中用括号标注来源：

| 等级 | 素材类型 | 举例 | 可信度 |
|---|---|---|---|
| A | 源码注释中的实测数据 | `rag_core.py` 记的 0.588s / 0.098s 客户端新建耗时 | 高（当时实测，但可能随版本漂移） |
| B | ADR 与规范文档 | `规范/决策记录.md` 的 D-001~D-005 | 高（正式拍板记录） |
| C | 事故修复说明 | `docs/修复说明_2026-10-20_登录Cookie缺少Secure.md` | 高（有现象+根因+验证） |
| D | 回归测试断言 | `tests/test_retrieve_select.py` 的用例 3 与 3b | 最高（可执行，改动即红） |

反过来，以下内容本报告**不做**断言：线上真实 QPS、真实用户量、竞品的实现细节、未落地的规划项的实际效果。规划项一律标注"仅契约，无实现"。

## 五、一句话结论

如果整份报告只能留一句话：

> **这个项目的技术选型主线不是"选最强的组件"，而是"选最不容易在无人值守时静默出错的那一个"**——所以它选了 SQLite 而不是 PG、选了独立 worker 而不是 Celery、选了声明式工具元数据而不是提示词劝导、选了能一键回滚的开关而不是"相信新逻辑是对的"。代价是每个决策都多写了一段注释和一条回归测试；收益是出问题时能在一屏日志里定位。
