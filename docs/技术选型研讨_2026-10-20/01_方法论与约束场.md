# 卷一 · 方法论与约束场

> 本卷解决的问题：**在讨论"为什么选 A 不选 B"之前，先确定"什么在约束选择"。**
> 大部分技术选型讨论失败，不是因为分析不深，而是因为分析的是错的自变量。

---

## 1.1 技术选型的真自变量不是"技术优劣"

先做一个思想实验。

假设有人在 2026 年 10 月问："一个带 RAG 和 Agent 的知识库产品，后端该用什么？"标准答案几乎是条件反射：FastAPI + PostgreSQL + pgvector + Redis + Celery + Docker Compose。

这个答案在绝大多数场景下是对的。但把它放进本项目的真实条件里，会立刻出现四个致命冲突：

| 标准答案的组件 | 在本项目的冲突 | 冲突后果 |
|---|---|---|
| PostgreSQL | 官方建议最低 1GB 内存，实际跑起来常驻 150~300MB 且要独立调参 | 2G 机器上，PG + 两个 Node 进程 + uvicorn + Chroma 直接 OOM |
| Redis | 又一份常驻 50~100MB 的内存 | 同上的边际成本 |
| Celery + broker | 需要 worker 进程池 + 结果后端 | 进程数翻倍，2 核被调度开销吃掉 |
| Docker Compose | Docker daemon 本身 100MB+，镜像层占磁盘 | 磁盘与内存双爆 |

也就是说：**在 2 核 2G 的阿里云 ECS 上，"标准答案"不是一个更优解，而是一个跑不起来的解。**

这不是"小项目就该用差技术"的自我安慰。它揭示了一个更本质的东西：技术选型的自变量是**约束场**，而不是技术本身的排名。约束场包含六个维度：

```
约束场 = { 资源上限, 运维能力, 团队并行度, 时间窗口, 合规/外部依赖, 失败代价 }
```

六个维度里任何一个发生数量级变化，最优解就可能整体翻盘。所以本卷要做的第一件事，是把本项目的约束场写清楚——不是为了给决策找借口，而是为了**标定每条决策的有效期**。

## 1.2 本项目的约束场（逐项标定）

### 约束 1 · 资源：2 核 2G，单台 ECS，磁盘约 40G

这是最硬的一条，且它同时约束了内存、CPU、并发、进程数、数据库选型、监控方案。

它的具体表现散落在很多地方：

- 部署文档里明确记着"2 核 2G 跑两套实例吃紧，**不要同时构建两端**"（`规范/决策记录.md` D-004）。前端 `next build` 是单进程吃满一个核、峰值内存可达 800MB 的操作，此时再跑生产构建，必然触发 OOM。
- Prometheus + node-exporter 的 compose 文件里给 node-exporter 显式写了 `mem_limit 256m`（`monitoring/`）。在一个"标准"部署里这个限制是多余的自律，在这里是保命。
- 图片上传的代码注释写着"分块写盘：以前是 `await f.read()` 整份读进内存再判大小，1GB 的附件在 2G 内存的机器上等判出来时进程已经被 OOM killer 带走了"（`api/chat.py:399-401`）。

这条约束直接否决的候选：PostgreSQL、Redis、Milvus、Elasticsearch、任何 JVM 系、Docker 化多容器编排。

### 约束 2 · 运维：没有专职运维，作者同时是开发者

没有运维意味着三件事：

1. **不能有需要调参才能稳定运行的组件**。PG 的 `shared_buffers`、`work_mem` 需要按机器调；SQLite 的 `PRAGMA` 写死在连接建立处就完事。
2. **故障必须能在一屏日志里定位**。所以错误信息全部翻译成中文（`describe_api_error`），而不是抛英文栈。
3. **不能有"慢故障"**。没人盯着 dashboard，所以必须有自证机制：心跳三态（`up/stalled/down`）、`probe-health.sh` 写 textfile 指标、定时任务 `idem_key` 幂等。这些设计的共同点是：**假设没有人会去看，所以让系统自己喊**。

这条约束直接否决的候选：Kubernetes、服务网格、需要专职 SRE 的多副本架构。

### 约束 3 · 团队：3 人并行，职责按目录切分

三个人同时改一个仓库，技术选型必须支持**物理隔离**：

- 模块边界要能用目录表达（`agent/` 归 A，`kb/` 归 B，`service/` 归 C）；
- 共享文件要尽量少（`api/*.py`、`main.py`、`core/config.py`、`core/session.py` 被明确标为"交叉区需协商"）；
- 新增功能不能要求动别人的文件。

这条约束解释了为什么这个项目**没有 Service 层抽象**——如果引入 `services/` 统一层，三个人每次加功能都要往同一批文件里塞代码，冲突率会翻倍。现在每个业务域直接暴露 `api/xxx.py` + `core/xxx.py` 两个文件，归属清晰。

它也解释了一个看起来很奇怪的设计：`core/config.py` 里有 60 多个配置项，全部集中在**一个文件**里。集中配置在大型项目里是反模式（应该按域拆），在这里是正解——因为它把"新增配置"这件事变成一个显式的、需要通知申请人的动作，而不是散落各处、谁也说不清现在有几个开关。

### 约束 4 · 时间窗口：8 周课程作业长成了产品

项目的起点是三次课程作业（RAG、会话、Agent），W1~W6 的路线图记录了每一周的交付。这意味着：

- 每一轮的技术选择都必须**当周可验证**。选一个需要两周才能调通的技术，等于这一轮交不了。
- 因此大量决策偏向"先用能跑的，把不可替换的部分做对"。典型例子：embedding 用百炼的托管 API 而不是本地部署 `bge-m3`——本地部署要下模型、配 GPU/CPU 推理、处理 OOM，一周做不完；托管 API 是 20 行代码。
- 这也解释了 `service/daily.py` 里那句诚实的自我标注："spec 写的是 map-reduce 的多轮调用，MVP 这里用单次调用……map-reduce 是长日（数百条消息）下的伸缩优化，本次先不实装"。

**这条约束是所有"技术债"的总源头**。它不是失误，是显式的期限交易：用"以后要还的复杂度"换"这一轮能交付"。

### 约束 5 · 外部依赖：模型供应商的能力边界

这不是自选，是被迫：

- DeepSeek **不提供 embedding 接口**。所以向量化必须另找一家（百炼 `text-embedding-v3`）。这不是"双供应商架构"的设计选择，是能力缺口的补丁。
- 视觉理解也必须另找（百炼 `qwen-vl-plus`）。
- 联网搜索需要 Serper（Google 结果），天气需要高德 + Open-Meteo 双源。

结果是：一个"AI 应用"实际上依赖 5 家外部 API。任何一家的 key 失效、限流、协议变更，都会让某条链路挂掉。这在架构上产生了一个反复出现的模式：**每一条外部依赖都必须有降级路径**。后面卷四、卷五会看到大量这种模式（检索失败退回纯向量、改写失败退回原问题、逆地理失败退回坐标、定位失败退回手动输入）。

### 约束 6 · 失败代价：静默失败比崩溃可怕

这条约束最容易被低估，但它是本项目最深的架构基因。

崩溃是可发现的。静默失败不可发现：定时任务漏投一次邮件、检索把不相关片段当依据、配额算错导致月底账单一万块——这些都不会报错。

所以本项目的选型有一条隐含的偏好：**在"高效但可能静默错"和"低效但错了一定响"之间，永远选后者。**

具体表现：

| 场景 | 高效但可能静默错的做法 | 本项目选择 |
|---|---|---|
| 工具元数据缺失 | 用默认值兜底，打个 warning | 导入时抛异常，服务起不来 |
| 幂等判定 | 先 SELECT 再 INSERT | UNIQUE 索引 + ON CONFLICT，判 rowcount |
| 归属校验 | 在 API 层验一次 | 每个 DB 函数都验，`owner` 无默认值 |
| 相似度换算 | 直接拿 distance 当相似度显示 | 换算不出来就返回 `None`，前端隐藏该字段 |
| 压缩块丢失实体 | 接受（反正省了 token） | 硬规则校验 + 拒收 + 回退上一版 |
| 定时任务 | 进程在就算活着 | 心跳年龄 > 600s 判 down |

## 1.3 约束如何变成判据（映射表）

约束本身不构成判据。判据是"在约束下可比较的维度"。本报告后续每一节的【判据】段落，使用的都是下表中的维度：

| 判据 | 定义 | 高权重条件 |
|---|---|---|
| **可运维性** | 出故障时定位所需的信息量与技能门槛 | 无专职运维时权重最高 |
| **静默失败风险** | 出错时不报警的概率 | 无人值守链路权重最高 |
| **依赖面** | 引入的进程数/端口数/常驻内存 | 2G 内存时权重最高 |
| **可测性** | 能否在不启服务、不联网的前提下验证 | 三人并行 + CI 时权重高 |
| **可回滚性** | 出问题后能否不改代码回退 | 线上有真实用户时权重高 |
| **性能上限** | 峰值吞吐 / 延迟 | 当前用户量下权重**低** |
| **扩展成本** | 加一个新同类功能要改几处 | 长期演进时权重高 |
| **认知负担** | 新人理解所需时间 | 团队小时权重高（反直觉但真实） |

注意最后两行的反直觉之处：

- **性能上限在本项目权重很低**。实测基线是"只读接口 P50 33.7ms、SSE 问答 P50 1.64s、并发 1→3 延迟基本持平"。这个量级下，任何"为了性能换架构"的提议都是过早优化。反过来，项目里做的所有性能优化都不是吞吐优化，而是**费用优化**（embedding 缓存省真金白银）和**体验优化**（首字延迟）。
- **认知负担权重高**。三个人、每周一轮交付、还要写文档，意味着"每次改动都要重新理解一遍"的成本极高。这是选择"一个文件一个域"而不是"分层架构"的直接原因。

## 1.4 一次提问的技术接触点解剖

为了让后面十卷有一条共同的主线，这里把"用户在输入框敲一句话，到屏幕上出现答案"拆成完整的接触点序列。这是本项目的**真实调用链**，不是理想架构图。

```
[1] 浏览器输入框  →  POST /api/chat/stream
      │  前端 fetch（lib/api.ts 唯一出口），同源，Cookie 自动带
      ▼
[2] Next.js rewrite 代理 /api/*  →  http://localhost:8000/api/chat/stream
      │  此步改 Host，是"尾斜杠黑洞"事故的根源
      ▼
[3] uvicorn / FastAPI
      ├ normalize_api_slash 中间件：尾斜杠归一（防 307 指回 localhost）
      ├ CORS 中间件（同源下实际不生效，但仍配了）
      └ 路由匹配 → chat_stream
      ▼
[4] 鉴权依赖 get_current_user
      ├ extract_token：X-Auth-Token → Authorization → Cookie 三级
      ├ decode_claims：HMAC-SHA256 验签 + exp 检查
      └ token_store.is_revoked(jti)：查吊销名单
      ▼
[5] 会话存在性校验（to_thread）
      └ 不存在 → 404，且**不扣配额**（无效请求不该消耗额度）
      ▼
[6] 配额 consume(uid, "ask")
      ├ 每分钟滑动窗口（进程内存）
      └ 每日 ask 计数（SQLite usage 表，原子 upsert）
      ▼
[7] 模式路由 _pick_mode
      ├ kb_id 归属校验：不是自己的库 → 视为未绑定
      ├ exists() 探库（to_thread，读 sqlite）
      └ auto → rag（有库）/ agent（无库）
      ▼
[8] 计划类请求：detect_plan_topic（本轮 → 历史回看）→ 拼接格式要求（不落库）
      ▼
[9] 定位解析：浏览器坐标 → 逆地理补城市 → 兜底只留城市名
      ▼
[10] 用户消息落库（原始问题，不含格式块）
      ▼
[11] SSE 流开始（此后无法再返回 429/500，只能发 error 帧）
      ├ RAG 分支：
      │   ├ rewrite_query（条件触发，只在像追问时）
      │   ├ retrieve_with_score
      │   │    ├ 结果缓存查 (collection, question, top_k, owner)
      │   │    ├ _embed_query（LRU + single-flight）
      │   │    ├ Chroma 向量检索 fetch_k = max(k*3, k+6, 12)
      │   │    ├ BM25 关键词通道（缓存 + 负缓存 + 20000 文档闸）
      │   │    ├ RRF 融合
      │   │    ├ select_diverse：离群过滤 0.25 → MMR(λ=0.65) → 截断 top_k
      │   │    └ 画像偏置（减距离重排，不改原始 distance）
      │   ├ assess_grounding：只判 top1，分 high/medium/low
      │   ├ grounding_note：low/medium 追加"不许硬答"约束
      │   └ 组装 messages（压缩块前置 + 最近 K 轮 + 参考资料）
      │
      ├ Agent 分支：
      │   ├ build_agent：图缓存键 (has_kb, scene, activated)
      │   ├ configurable 注入 owner_id / kb_id（模型改不了）
      │   ├ astream(stream_mode=["updates","messages"])
      │   └ 工具调用 → tool_guard（输出截断/审批/重试封禁）
      │
      └ hybrid 分支：classify_task → 工作流 or Agent → 切换规则
      ▼
[12] LLM 流式：astream → delta 帧（不发累计全文），每 16 帧查一次断连
      ▼
[13] 落库 assistant 消息（取回 message_id）
      ▼
[14] 并行任务：标题生成（首轮，与答案流并行）、画像标签、上下文压缩判定
      ▼
[15] done 帧：answer / refs / title / mode / message_id / run_id / plan_topic
      ▼
[16] 前端累加 delta 渲染，角标 [1][2] 可点开原文
      ▼
[17] 事后：worker 定时聚合 → 每日总结（强制溯源）→ 每日委托投递
```

这 17 个接触点里，有 9 个是本报告要单独展开的决策现场（3、4、6、7、11、12、13、14、17）。它们分别对应卷二到卷十一。

**这张图最重要的信息不是"有多少组件"，而是"第 11 步之后就再也无法返回 HTTP 错误"**。SSE 一旦开始，响应头 200 已经发出去了，此后的任何失败只能变成 `event: error` 帧——这解释了为什么配额检查放在流外面（`api/chat.py:554-562` 的注释），也解释了为什么整个流式路径需要 `_Acc` 累加器 + `acc.error` 双保险。很多看起来"过度设计"的地方，根因都是这一个物理事实。

## 1.5 技术债的六种形态

本项目的技术债不是随机分布的。它们有形态，且每种形态对应一种特定的认知失误。识别形态比记账更重要——因为同一种形态会重复出现。

### 形态 1 · 版本锁（Version Lock）

**特征**：两个包必须同版本区间，单独升任一个都炸。

本项目最典型的一处写在 `requirements.txt:16-18`：

```
# 注意：langchain-chroma 1.x 要 chromadb 1.x（沙箱限制无法安装），
# 先用 0.2.3 + chromadb 0.5.23 组合，两者互相兼容
langchain-chroma==0.2.3
chromadb==0.5.23
```

以及 `requirements.txt:36-39`：

```
# 版本卡在 3.x：4.x 的 API 与 SQLAlchemyJobStore 的用法都变了
apscheduler>=3.10,<4
```

**成因**：依赖生态的版本耦合，而项目没有能力（也没有必要）跟上最新。

**代价**：`chromadb==0.5.23` 在 Python 3.14 上装不了——这一条直接导致"手上没有 Python 3.12 会装不上"。也就是说，版本锁会**反向约束运行环境**，形成一条隐性依赖：代码 → 库版本 → Python 版本 → 机器镜像。

**判据**：什么时候该解？当"锁住的版本"出现安全漏洞，或者需要的新能力只在新区间。解法不是单独升包，而是**成对升级 + 全量回归**，因为这对包之间是兼容性契约而不是版本号。

### 形态 2 · 静默降级（Silent Degradation）

**特征**：失败不报错，功能降级，日志里可能只有一行。

本项目的降级点极多，且都是刻意的：

| 位置 | 降级行为 |
|---|---|
| `_extract_topics_one` | 抽标签失败 → 返回空列表，入库照常 |
| `add_user_tags` | 写画像失败 → `except: pass` |
| `rewrite_query` | 改写失败 → 原样返回原问题 |
| `_hybrid_candidates` | BM25 出错 → 退回纯向量 |
| `_image_to_data_url` | Pillow 不可用 → 退回原图 |
| `token_store` 写文件失败 | 只读文件系统 → 每次重启生成新密钥（最多掉登录） |

**这是一个必须警惕的模式**。降级本身是对的（画像/标签/改写都是增益不是必需），但它有一个恶性变体：**降级路径掩盖了配置错误**。

项目里已经踩过一次，而且注释写得很清楚（`kb/rag_core.py:802-806`）：

> ⚠️ `get_llm()` 必须在 try 之内。它构造的是 `ChatOpenAI`，**没配 key 时会直接抛 `openai.OpenAIError: Missing credentials`**，不是等到 invoke 才失败。历史上这行曾在 try 之外，导致「没配 key 的机器上建库直接 500」，而文档承诺的是"静默降级"——两处不一致就是这么来的。

判据：**"静默降级"必须配合"可观测性"**。降级可以静默，但"发生了降级"这件事不能静默。当前项目的做法是降级时返回可读的状态（前端能看到"知识库检索失败，已仅按图片作答"），这是正确方向。

### 形态 3 · 双轨（Dual Track）

**特征**：同一个能力有两套实现，因为迁移没做完。

已记录在案的一处（`规范/01_架构与模块职责.md` §3.4）：

```
⚠️ 已知双轨：搜索能力同时存在于 agent/tools.py 与 core/serper.py。
收口方向：所有搜索调用一律走 core/serper.py。
```

**成因**：并行开发。B 线在做"搜索统一入口"的同时，C 线在写工具集，两边都在实现搜索，合并时没人删。

**代价**：不是性能问题，是**行为不一致**。`core/serper.py` 补了 `gl=cn / hl=zh-cn` 中国区锚定，`agent/tools.py` 里的实现可能没有——于是同一个问题在 Agent 路径和直接调用路径上，返回的结果地区不同。

判据：双轨的判据不是"有没有重复代码"，而是"两条轨道的行为是否已经分叉"。一旦分叉，就是 bug 源。

### 形态 4 · 默认值陷阱（Default Trap）

**特征**：某个默认值在当时是对的，环境变了之后变成错的，但没有任何信号。

本项目最严重的一次默认值陷阱是 Chroma 的距离口径（`kb/rag_core.py:113-136`）：

> 距离口径（已实测确认，2026-10-03）：集合创建时没有指定 `hnsw:space`，走的是 Chroma 默认的**平方 L2**；而百炼 `text-embedding-v3` 返回的向量**已经是单位向量**……平方 L2 在单位向量上有 `d = ||a-b||² = 2 - 2cos`，因此 `cos = 1 - d/2`，**d 的合法值域是 [0, 4]**。
>
> ⚠️ 此前这里按余弦距离的 [0, 2] 判定，导致 d ∈ (2, 4]（即 cos < 0，明显不相关的片段）被当成"换算不了"。后果有两个：① `select_diverse` 里 `all(...)` 短路 → **`RETRIEVE_MIN_SIM` 这道阈值整条被跳过**；② `relevance()` 退化为批次内相对排序 → 负余弦片段反而拿到虚高的相关度。
> 线上表现：参考资料卡片把类目「相似度」标成 1.089 / 1.160 / 1.237（实为距离）。

这个案例的教学价值极高，因为它同时具备三个特征：

1. **默认值是隐式的**：没人"选"过平方 L2，是没指定 `hnsw:space` 的结果；
2. **错的那一侧是"看起来正常"**：相似度显示 1.089，用户只会觉得"分数挺高"，不会觉得错；
3. **错的后果是放行而非拦截**：阈值被整条跳过，于是不相关片段进了 prompt，模型被迫硬答。

判据：**任何"换算"都必须在代码里写死合法值域，并且配一条能红的回归测试**。这个项目后来确实补了 `tests/test_retrieve_select.py`，且注释里写明"把守卫改成 [0,2] 重跑，用例 3 与 3b 都会失败"——这是负向验证，比正向断言强得多。

### 形态 5 · 口径漂移（Caliber Drift）

**特征**：同一个概念在两处被计算，且阈值/规则各自维护。

已经修掉的一处（`kb/rag_core.py:1294-1300`）：

> 原先 `build_sources` 与 `_format_refs` 各自算一遍 basename、页码、`_to_similarity`，还各写了一遍"强 / 中 / 弱"的阈值判断（两处注释都要求同步维护）。合并成一次计算，阈值口径不会再漂。

还没修但被显式标注的一处（`kb/rag_core.py:318-323`）：

> ⚠️ **判定只看 top1，且和 build_sources 用同一个阈值**。这两条都是踩过的坑……和 build_sources 用不同阈值 → 引用卡片上标着「弱」，回答侧却认为够格，用户看到的就是"卡片说这条没用、正文却在用它答"。

判据：口径漂移的检测手段是**用同一个函数产出两个消费方**（现在 `_source_meta` 就是这个函数）。而不是"在两处注释里都写上要同步"。

### 形态 6 · 假绿（False Green）

**特征**：CI 是绿的，但测试根本没跑。

这是本项目最有价值的一次工程发现（`规范/决策记录.md` D-003）。当时的 `ci.yml` 把 4 个"脚本式自测"文件混在 pytest 命令里跑。pytest 在**收集阶段**就 import 模块，于是模块级检查被立即执行：

- 全通过 → 报 `collected 0 items`，**绿色但零覆盖**；
- 有失败 → 模块里的 `sys.exit(1)` 直接把 pytest 进程干掉，看不到是哪一项挂的。

结果是 `test_agent_guard.py`（14 项）、`test_grounding.py`（27 项）、`test_scenarios.py`、`test_retrieve_select.py` **从未被真正校验**。

判据：`grep -c '^def test_' tests/test_xxx.py` 输出 0 即为脚本式，必须用 `python` 直接跑。CI 拆两个 step。

**这六种形态构成本报告的一个隐性框架**：后面每一卷在讲"代价"时，都可以归到这六类之一。反过来说，如果某个决策的代价无法归类，那说明我们还没看清它。

## 1.6 架构风格判定：这是什么形态的系统

用标准分类术语，本项目的形态是：

> **带进程内状态的单机单体（Stateful Monolith on Single Node），以文件系统为持久化边界。**

拆开说：

**"单体"**：一个 FastAPI 进程挂 14 个 router、34+ 端点。没有服务拆分，没有 RPC，没有消息队列。

**"带进程内状态"**：这是关键特征，也是所有约束的汇聚点。进程内存里同时住着：

| 状态 | 位置 | 丢了会怎样 |
|---|---|---|
| 每分钟限流窗口 | `core/quota.py::_HITS` | 重启后限流清零（可接受） |
| BM25 索引缓存（最多 8 个库） | `kb/rag_core.py::_BM25_CACHE` | 下次检索懒加载重建（可接受，慢一点） |
| 检索结果缓存（200 条） | `_RETRIEVE_CACHE` | 重建（可接受） |
| 查询向量缓存（500 条） | `_EMBED_CACHE` | 重建（花真钱） |
| Agent 编译图缓存（32 个） | `agent/builder.py::_AGENT_CACHE` | 重编译（CPU 开销） |
| LLM 客户端实例 | `core/llm.py::_LLM_CACHE` | 重建 httpx 连接池 |
| 延迟工具激活集 | `core/tool_registry.py::_activated_by_owner` | 用户要重新 discover |
| Chroma 客户端单例 | `kb/rag_core.py::_CHROMA_CLIENT` | 重开 sqlite + 重建内部缓存 |

这张表有一个直接推论：**这个系统不能水平扩多副本**。

不是因为"代码写得不好"，而是因为语义上不允许：

- 限流窗口在多副本下变成 N 倍额度；
- Agent 图缓存与激活集在多副本下不一致，用户体验会随负载均衡漂移；
- BM25 缓存多份，内存直接乘 N（2G 机器上等于自杀）。

这个推论非常重要，因为它把"扩展性"这个通常被视为缺点的属性，**转换成了一个显式的架构前提**：单副本是设计约束，不是待偿还的债。

什么时候必须打破它？判据是明确的：**当单进程的 CPU 或内存成为瓶颈，且无法通过优化单请求成本解决时**。届时需要做的不是"加副本"，而是先把 8 项进程内状态外移（Redis + 共享缓存），再谈副本。这是一次架构级手术，不是配置调整。

**"以文件系统为持久化边界"**：所有数据最终落在三个位置：

```
data/sessions.db     会话 / 消息 / 反馈 / 用量 / 画像 / 日报 / 委托
data/scheduler.db    调度三表 + APScheduler JobStore
chroma_db/           向量库（每库一个 collection）
data/*.json          知识库名映射 / 文件清单 / 归属表
data/kb_sources/     上传原文留档
```

这个边界的意义在于：**备份 = 打包这几个路径**，迁移 = 拷贝这几个路径，测试 = 把它们指到临时目录。没有对象存储、没有外部数据库、没有跨机一致性。这是单机能带来最大收益的设计。

它的代价也很清楚：**无法多机部署**、**无法做读写分离**、**文件锁成为并发上限**。以及一个隐蔽的坑：`data/sessions.db` 和 `data/scheduler.db` 必须是两个文件——这是踩过的事故（`README.md:169`）：

> 调度库与会话库是**两个独立的 SQLite 文件** —— 跨库查表是本项目踩过的坑（`GET /api/delegate/{id}/runs` 曾因此 500）。

## 1.7 为什么 ADR 不够用（本报告的方法论补丁）

本项目已经有一份不错的 ADR（`规范/决策记录.md`，D-001~D-005）。但只有 5 条，而代码里的实际决策超过 80 条。为什么？

因为 ADR 的启动门槛太高：它要求"这个决策值得被记录、值得被讨论、可能被推翻"。而绝大多数技术选择在当时看来是"显然的"——显然到没人觉得需要记录。于是真正有价值的信息（当时考虑过什么、为什么否决）就只留在写代码那个人的脑子里，以及——运气好的话——注释里。

本报告用三个补丁来弥补：

### 补丁 1 · 把注释当作一等公民

本项目的注释密度异常高，而且写的不是"这行代码做什么"，而是"为什么不是另一种写法"。例如 `_make_checkpointer` 的注释里，连"改成 `SqliteSaver(sqlite3.connect(...))` 也不行——同步 saver 不支持 `astream`，必须用 `AsyncSqliteSaver`"这种三级失败路径都记下来了。

这类注释的价值在于：它记录的是**搜索空间**，不是结论。读结论只能照抄，读搜索空间才能在新条件下重新推理。

### 补丁 2 · 用回归测试反向锚定决策

一个决策如果没有测试兜着，它就只是一句话。本项目用测试锚定的决策包括：

| 决策 | 锚定测试 |
|---|---|
| 检索四段流水线 + 相似度换算守卫 | `tests/test_retrieve_select.py` |
| 不挂 checkpointer | `tests/test_agent_checkpointer.py` |
| 尾斜杠不 307 | `tests/test_slash_no_redirect.py` |
| Chroma 客户端单例 | `tests/test_chroma_singleton.py` |
| 多库并发读写 | `tests/test_pipelines_concurrency.py` |
| 上传分块写盘 + 失败清理 | `tests/test_upload_stream.py` |
| IP 定位三级降级 | `tests/test_geo_locate.py` |
| Cookie Secure 按协议补齐 | `tests/test_auth_cookie_secure.py` |
| Agent 路径 grounding 与 RAG 同源 | `tests/test_agent_grounding.py` |

注意这些测试的共同点：**它们测的不是"功能对不对"，而是"决策还在不在"**。`test_agent_checkpointer.py` 甚至断言"checkpointer 必须是 None"——它测的是一个否定命题。这是很少见的做法，但非常正确：如果一个决策是"不做某事"，那么唯一能防止后人"顺手做了"的手段，就是一条会红的测试。

### 补丁 3 · 反对称论证（Why-Not 优先）

常规论证是对称的：A 有优点 a1,a2，B 有优点 b1,b2，加权打分选 A。这种做法在本项目条件下会失效，因为**权重本身不可靠**（见 §1.3 的反直觉行）。

本报告改用反对称论证：**不问"为什么选 A"，只问"为什么不选 B"，并且要求否决理由必须是可验证的事实，不能是"感觉更重"。**

例：

- 不选 PostgreSQL —— 可验证事实：2G 内存 + PG 常驻 150~300MB + 两个 Node 进程 + uvicorn + Chroma，会 OOM。这不是"PG 不好"，是"这个组合跑不起来"。
- 不选多副本 —— 可验证事实：8 项进程内状态在多副本下语义错。
- 不选 checkpoint —— 可验证事实：3 轮后状态 12 条（应 6 条）。
- 不选累计全文 SSE —— 可验证事实：千 token 回答是 O(n²) 传输。

每条否决都指向一个**可以在别人的机器上复现的现象**，而不是一个偏好。这是本报告对"深刻"的定义：深刻不是长篇，是**可反驳**。

## 1.8 三代演进：技术选择是被历史塑造的

不理解演进史，会把"历史包袱"误认为"设计意图"。本项目有三个清晰的世代：

### 第一代：`rag-knowledge-base-demo`（单文件 demo）

特征：固定 3 个 collection（`main/left/right`），单用户，无鉴权，无会话，检索直接 top-k。

遗留痕迹：
- `kb/rag_core.py` 开头写着"迁移自 `rag-knowledge-base-demo/rag_core.py`，适配 LangChain v1.x"；
- `pipelines.py` 开头写着"与 `rag-knowledge-base-demo` 固定 `main/left/right` 三个 collection 不同，这里支持任意数量的知识库"。

**这一代决定了技术栈的骨架**：LangChain + Chroma + 百炼 embedding。后面的所有争论都发生在这个骨架之内，没有人提议换掉 Chroma——因为换掉等于重写。

这是技术选型里最常见的隐形约束：**第一周的选择决定了后面十周的选择空间**。所以第一周的选择要格外慎重，而它往往是最仓促的。

### 第二代：单体 Web（多会话 + SSE + 多用户）

新增：SQLite 会话库、SSE 流式、多用户鉴权、配额、知识库动态注册。

这一代的核心矛盾是**"Web 的异步模型" vs "生态里的同步 API"**。

FastAPI 是 async 的，但 LangChain 的 `invoke`、`Chroma` 的 `similarity_search`、`sqlite3` 的 `execute`、`embed_documents`——全是同步的。于是产生了一条贯穿全项目的纪律（`core/quota.py:16-18`）：

> 调用注意：本文件的函数全是同步的（SQLite 写约 2ms），在 async 端点里一律用 `asyncio.to_thread(...)` 包一层——这是本项目既定规则，别因为它只有 2ms 就裸调。

这条纪律的严格执行程度可以从代码里验证：`api/chat.py` 里几乎每一个 store/quota/pipelines 调用都包了 `to_thread`。而没有包的（`store.get_messages` 在 RAG 分支第 973 行是裸调的）反而是例外。

**这一代还埋了一个重要的乐观决策**：不挂 LangGraph checkpointer。这个决策的理由在卷六会详细展开，但它的历史背景是——当时的会话库已经能承载历史了，checkpoint 是"看起来更 LangChain 原生"的额外一层。

### 第三代：AI 模块（工具元数据 + 独立 worker + 总结/委托 + 混合引擎）

新增：`TOOL_META` 声明式元数据、APScheduler 独立进程、每日总结/委托、hybrid 工作流引擎、上下文压缩、标签画像。

这一代的特征是从"能跑"转向"能无人值守地跑"。所有新增模块都带三件套：**幂等键、心跳、配额**。

这一代也是技术债最集中的一代，因为它引入了最多的新概念。但它的债务形态很干净：几乎全是"形态 3 双轨"和"形态 5 口径漂移"，而没有"形态 1 版本锁"——说明依赖层已经稳定，复杂性转移到了业务层。

**演进史给技术选型的最重要教训**：不要问"现在最优解是什么"，要问"三年后回头看，今天哪个选择最不可能被推翻"。第一代选了 Chroma，三年后仍然没被推翻，因为它的约束（零运维、单进程、metadata 过滤）没有变。而如果第一代选了 pgvector，今天很可能已经在为"PG 吃内存"还债。

## 1.9 本卷小结：十条约束 → 一条主线

把约束场压缩成一句话：

> **资源只有 2G，运维只有零个人，团队只有三个人，时间只有六周，外部依赖有五家，而失败必须响。**

这六个条件共同推出了本项目的选型主线：

> **优先选择"故障可见、依赖最少、可单测、可回滚"的方案，而不是"性能最好、生态最全、最符合教科书"的方案。**

主线会带来一个副作用：这个项目在很多地方看起来"不够现代"——没有容器、没有微服务、没有消息队列、没有 ORM、没有分布式锁。但如果把每个"不够现代"逐一展开，会发现它们都是同一句话的不同表述：**在 2G 和零运维的条件下，现代架构的每一层抽象都要用内存和注意力来支付，而这个项目付不起。**

卷十二会回到这条主线，并检验它在什么条件下会失效。现在进入卷二，从请求接触系统的第一个环节开始。
