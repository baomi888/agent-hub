# 卷十二 · 横向反思：十条定律、反模式与演进判据

> 本卷解决的问题：**把十二卷的具体决策，压缩成可以带到下一个项目的东西。**
> 前面十一卷讲"这个项目怎么选的"，这一卷讲"为什么这么选会在别处也成立，以及什么时候不成立"。

---

## 12.0 一个总的观察

把 80 多个决策放在一起看，会发现它们的**分布极不均匀**：

| 类别 | 数量 | 典型 |
|---|---|---|
| "不用更流行/更强的方案" | 约 30 | SQLite 不用 PG、单进程不用多副本、手写 SSE 不用框架 |
| "加一层机制而不是加一段提示词" | 约 15 | TOOL_META、owner 必填、强制校验 |
| "加一个开关以便回滚" | 约 7 | COMPRESS_ENABLED、HYBRID_ENABLED... |
| "把动态信息挪到末尾" | 约 5 | 定位、历史注入 |
| "消除双轨" | 约 5 | grounding 对齐、_source_meta 合并 |
| "用约束代替查询" | 约 4 | idem_key、ON CONFLICT |
| 其他 | 约 20 | 缓存、超时、错误翻译 |

**第一类占了近 40%。** 这说明这个项目的技术选型主要不是"选什么"，而是"拒绝什么"。

而拒绝的理由几乎都可以归到一句话：

> **在我这个约束下，那个方案会引入一个我无法承受的失败模式。**

这句话是整份报告的压缩版。下面展开成十条定律。

---

## 12.1 十条工程定律

### 定律 1 · 默认值必须落在安全侧

**陈述**：任何"忘了配置/忘了传参/忘了处理"的情况，结果都应该是"更安全"而不是"更方便"。

**本项目的证据**：

| 位置 | 默认行为 | 如果是反方向会怎样 |
|---|---|---|
| `owner` 无默认值 | 漏传 → TypeError | 有默认 None → 静默查到空数据，排查跑偏 |
| `redirect_slashes=False` | 路径不对 → 404 | 自动重定向 → Location 指错 host，全站 API 挂 |
| `AUTH_RETURN_TOKEN=0` | 不回吐 token | 回吐 → XSS 直接偷走 7 天令牌 |
| `LEGACY_OWNER` 数据 NULL | 谁都看不到 | 自动认领 → 第一个注册的人拿到别人的历史 |
| `secure` 拿不准 → 不加 | 安全性略降 | 加了但走 http → Cookie 被拒，**登录彻底不能用** |
| `PERSONAL` 图片路径校验 | 不在白名单 → 拒绝 | 放行 → 任意文件读取 |

**注意最后两行**：默认值落在安全侧的"安全"不一定等于"更严格"。`secure` 那条选择了"不加"（更宽松），因为**"登录不能用"比"Cookie 可能泄露"更糟**——后者是概率风险，前者是确定性故障。

**所以"安全侧"的准确含义是：失败时不产生不可恢复的后果。**

**反例警告**：`AGENT_LLM_MAX_TOKENS=0`（无上限）是为了兼容旧行为，这是**默认值落在方便侧**。它被显式标注了（"生产建议设置 2048"），说明作者知道这是一个例外。

### 定律 2 · 用机制替代纪律

**陈述**：如果一个规则需要"每次记得做"，它迟早会被漏掉。应该让"没做"这件事在机制层面不可能，或者立刻失败。

**本项目的证据**：

| 纪律型做法 | 机制型做法 |
|---|---|
| "记得给新端点加鉴权" | `APIRouter(dependencies=[Depends(get_current_user)])` |
| "记得校验 kb 归属" | `owner_of(kb_id) == uid` 写在每个读写函数第一行 |
| "记得别跨库 JOIN" | （**未实现**，仍是纪律） |
| "记得包 to_thread" | （**未实现**，仍是纪律） |
| "记得别同时构建两端" | （**未实现**，仍是纪律） |
| "记得停服务别用 pkill" | `deploy-staging.sh` 按端口精确匹配 |
| "记得别把 staging 指向生产数据" | 脚本检查并拒绝启动 |

**注意表中三处"未实现"**：它们是这个项目最脆弱的地方，因为它们**依赖人的记忆**。

而卷八提到的 `api/chat.py:973` 那处裸调 `store.get_messages`，正是"纪律被遗忘"的实例。

**定律的推论**：技术债的严重度，应该按"这条规则是机制还是纪律"来加权。**纪律型的债，比机制型的债严重一个量级**——因为机制型的债最多是"性能不好"，纪律型的债是"某天突然坏了"。

### 定律 3 · 静默失败是最贵的失败

**陈述**：崩溃会被发现，静默错误不会。所以"会不会静默"应该成为技术选型的一级判据。

**本项目的证据（静默失败清单）**：

| 静默失败 | 表现 | 发现难度 |
|---|---|---|
| 相似度口径错（平方 L2 当余弦） | 显示 1.089 的"相似度" | 极高（数字看起来正常） |
| embedding 模型换了没重建库 | 检索结果随机 | 极高（不报错） |
| checkpoint 重复累积 | 3 轮 12 条 vs 应 6 条 | 高（要数消息条数） |
| Chroma 单例被绕过 | 每次请求慢 90ms | 高（是"慢"不是"错"） |
| 尾斜杠 307 | 所有 API 挂 | 中（有明确症状） |
| Cookie 缺 Secure | http 下正常工作 | 极高（只在攻击时暴露） |
| 输出被 max_tokens 截断 | 回答断在半句 | 中（用户会问） |
| 定时任务漏投 | 用户没收到 | 高（用户可能不说） |
| `float(None)` TypeError | 静默 500（被 except 吞） | 高（条件组合触发） |
| 假绿测试（收集 0 项） | CI 全绿 | **极高**（绿就是"没问题"的信号） |

**"假绿"是这张表里最贵的** —— 因为它的失败模式是"你以为验证过了"。

**定律的推论**：每个设计决策都应该问一句"如果这一步错了，我怎么知道？"如果答不上来，就需要加一个显式的检测（日志、断言、指标）。

### 定律 4 · 缓存键必须包含所有影响输出的变量

**陈述**：缓存的价值与风险都来自同一个事实——它跳过了计算。所以"哪些变量影响输出"必须穷举。

**本项目的证据**：

| 缓存 | 键 | 漏了会怎样 |
|---|---|---|
| 检索结果 | `(collection, question, top_k, owner)` | 漏 owner → 甲看到乙的排序（画像偏置不同） |
| 查询向量 | `question` | 漏问题 → 不可能（键就是问题） |
| Agent 图 | `(has_kb, scene, activated)` | 曾经含 `note`（城市）→ LRU 抖动 + KV 缓存失效 |
| LLM 客户端 | `(temperature, max_tokens)` | 漏 max_tokens → 标题和正文共用一个实例，长度限制失效 |
| 切分器 | `(chunk_size, chunk_overlap)` | 漏 overlap → 不同参数共用，切片结果错 |

**最后一行的教训最深**：`_splitter(chunk_size, chunk_overlap)` 的键包含两个参数，因为切分器"无状态但参数化"。如果只按 `chunk_size` 缓存，两个库用同样的 chunk_size 但不同 overlap，会拿到错误的切分器。

**"Agent 图缓存曾经含 note"这一行是反向证据**：键里多一个变量不是"更安全"，是"命中率下降 + 前缀失效"。**缓存键要恰好等于"影响输出的变量集"，多一个少一个都错。**

### 定律 5 · 前缀必须稳定，动态信息放末尾

**陈述**：任何被重复发送的长文本（system prompt、工具定义、历史），其"稳定部分"必须在前面，"变化部分"必须在后面。

**本项目的证据**：

| 位置 | 做法 | 效果 |
|---|---|---|
| 定位信息 | 从 system 挪到末尾用户消息 | KV 命中率 0% → 90% |
| 工具 schema | 包装时保持 `name/description/args_schema` 不变 | 前缀不变 |
| 压缩块 | `[COMPRESSED-n]` 增量追加，不改旧段 | 压缩时刻只损失 10% |
| 激活工具集 | 请求开始时定死，整轮不变 | 工具前缀稳定 |

**这条定律的物理基础**：LLM 的 KV 缓存是"前缀匹配"，不是"最长公共子序列匹配"。改一个字在中间，后面全部失效。

**推论**：任何"把动态内容拼进 system prompt"的做法都是错的，即使它"看起来更符合语义"（定位确实属于"系统级信息"）。**物理约束优先于语义优雅。**

### 定律 6 · 一个事实只能有一个产出点

**陈述**：同一份数据/判断如果由两处计算，两处就会漂移。必须收敛到一个函数，所有消费方都调它。

**本项目的证据**：

| 漂移的事实 | 修复方式 |
|---|---|
| 相似度 + 强弱分级（`build_sources` vs `_format_refs`） | 合并到 `_source_meta` |
| grounding 提示（RAG 路径 vs Agent 路径） | `kb_search` 复用 `grounding_note` |
| 搜索结果（`agent/tools.py` vs `core/serper.py`） | **未修**（已知双轨） |
| 时区（`SCHEDULER_TZ` vs `time.localtime`） | **未修**（三处两种语义） |
| 窗口截断（SQL LIMIT vs Python 轮次截断） | 两层，有意为之（但要理解） |

**注意第 3、4 行未修**：双轨和时区是当前最明显的"口径漂移"。

**"两处注释都要求同步维护"是漂移的最强信号** —— 如果你需要在两个地方写"记得同步"，说明它们应该合并。

### 定律 7 · 降级要降得浅，失败要失败得响

**陈述**：功能可以降级，但不能"因为 20% 缺失就把 80% 也丢掉"；而"发生了降级"这件事必须可观测。

**本项目的证据**：

| 场景 | 降级深度 | 是否可观测 |
|---|---|---|
| 前端没有 `sources` | 渲染弱角标，**不丢结论** | 用户能看到角标是灰的 |
| 检索全被过滤 | 强留最相关一条，让模型示弱 | 有 `grounding` 事件 |
| BM25 库太大 | 退回纯向量 | **不可观测**（静默） |
| 主题标签抽取失败 | 跳过，照常入库 | **不可观测**（静默） |
| 查询改写失败 | 用原问题 | 有 status 事件（"已改写"只在成功时出现） |
| Pillow 不可用 | 原图上传 | **不可观测**（静默） |
| 混合模式开关关闭 | 静默回退 agent | `done.mode=agent`（可观测） |

**前两行是正例**（降级浅 + 可观测），中间三行是缺口（静默降级）。

**"降级要降得浅"的一个好例子**：`select_diverse` 的"别把结果砍空：一条不剩时至少留最相关的那条"。

如果全丢，系统会走"硬拒答"分支，用户得到零信息。留一条 + 示弱，用户至少知道"知识库里最接近的是什么"。

### 定律 8 · 幂等靠约束，不靠查询

**陈述**："先查有没有，没有再插入"在并发下必然漏。唯一可靠的做法是让数据库约束来拒绝重复。

**本项目的证据**：

| 场景 | 约束 |
|---|---|
| 定时任务 | `UNIQUE(idem_key)` + `ON CONFLICT DO NOTHING` + 判 rowcount |
| 每日用量 | `PRIMARY KEY(user_id, day, kind)` + `ON CONFLICT DO UPDATE SET count = count + excluded.count` |
| 用户画像 | `PRIMARY KEY(owner_id, tag)` + `ON CONFLICT DO UPDATE SET weight = weight + ?` |
| 每日总结 | `report_id = md5(uid|date)` 作主键 → upsert |
| 消息反馈 | 部分唯一索引 + "先删再插" |

**注意最后一行的例外**：SQLite 对部分唯一索引的 upsert 支持不好，所以退化成"两步写"。但因为两步在同一个事务里，仍然原子。**这是一个"约束不可用时的次优方案"，且有明确注释。**

**定律的前提**：先把"什么是重复"定义清楚（`idem_key = job_key|subject_id|planned_at`）。**定义不清，约束也救不了。**

### 定律 9 · 可测性决定架构，而不是反过来

**陈述**：如果一个模块"没法测"，那么它的正确性只能靠"读代码确认"。而读代码确认的可靠性随代码量指数下降。

**本项目的证据**：

| 可测性设计 | 带来的架构后果 |
|---|---|
| `core/scheduler.py` 不 import apscheduler | 状态管理独立成层，可单测幂等/重试/心跳 |
| `service/daily.py` 的 `llm` 可注入 | 业务逻辑可脱离真实 API 测试 |
| `core/session.py` 的路径可 monkeypatch | 测试不碰生产数据 |
| `_get_conn` 的路径参与判断 | 同上（必须的配套） |
| 脚本式自测 + pytest 分离 | 两类测试各自可跑（D-003） |
| `test_agent_checkpointer.py` 断言"必须为 None" | 否定性决策被固化 |

**第 1 行是最典型的**：因为想测幂等，所以把状态管理从框架里剥离了。**这不是"测试驱动开发"（TDD），是"可测性驱动架构"。**

**第 6 行最反直觉**：为"不做某事"写测试。因为 LangChain 的所有文档都在教你挂 checkpointer，只有一个会红的测试能阻止后人照做。

### 定律 10 · 性能优化的对象是"钱"和"第一秒"，不是"吞吐"

**陈述**：在用户量不足时，"为了吞吐换架构"是过早优化。真正值得优化的是"每次调用都花钱的地方"和"用户等待感知最强的地方"。

**本项目的证据**：

| 优化 | 目标 | 收益 |
|---|---|---|
| 查询向量缓存（LRU 500） | **钱** | 省一次 embedding（约 250ms + 费用） |
| 检索结果缓存（LRU 200） | **钱** | 省 embedding + 向量查询 |
| 标题生成并行 | **第一秒** | 省一次 LLM 往返（1~2s） |
| 输入截到 200 字（标题） | **钱** | 防长文档烧几千 token |
| `max_tokens` 分层 | **钱** | 防失控长文 |
| 断连检测每 16 帧 | **CPU** | 省千次 ASGI 状态读取 |
| Chroma 客户端单例 | **第一秒** | 省 90ms/请求 |
| 并发 embedding（4 路） | **第一秒** | 把 N 个 RTT 压成 N/4 |
| 分窗处理（防 OOM） | **可用性** | 峰值内存钉死 |

**注意没有一条是"提高 QPS"。** 压测基线（8 并发 P50 33.7ms）在这个用户量下完全够用。

**"第一秒"指什么**：首字延迟（TTFT）。用户能感知的是"多久看到第一个字"，不是"总共多久"。所以并行化标题生成、缓存查询向量、单例 Chroma，都是直接改善体感。

## 12.2 反模式清单（本项目踩过或差点踩的）

### 反模式 1 · 用自然语言实现机器策略

**症状**：提示词里写"不要重复调用这个工具""最多试三次""输出不要超过 500 字"。

**为什么错**：模型对否定指令的遵循是概率性的，且会被中间层改写（"请改用 web_search，不要重复调用" 被吞成 "暂时不可用" 后模型重试 2~3 次）。

**正确做法**：`retryable=False`、`recursion_limit`、`max_output_chars`。

### 反模式 2 · "两种格式都支持"以规避冲突

**症状**：接口冲突时，后端两种都返回，前端两种都解析。

**为什么错**：一次性的返工变成永久的分支。而且"永远不知道什么时候能删旧的"。

**正确做法**：选一个，明确说"不做的事"（D-002 的写法）。

### 反模式 3 · 依赖"猜别人 tokenizer"的长度检查

**症状**：`check_embedding_ctx_length=True`（默认），用 tiktoken 检查第三方模型的上下文长度。

**为什么错**：tiktoken 的编码表是 OpenAI 的，对中文的切分与对方模型不同。"检查通过"不代表"对方接受"。

**正确做法**：关掉，按字符数自己控制在安全范围（500 字切片 << 任何模型的上限）。

### 反模式 4 · 用框架的默认值决定安全属性

**症状**：没指定 `hnsw:space`，于是用了平方 L2；没检查 `header.alg`，于是靠"没实现多算法"侥幸安全。

**为什么错**：默认值不是"中性的"，它总是一个具体选择，而那个选择未必符合你的假设。

**正确做法**：显式指定 + 在代码里写死合法值域 + 配负向回归测试。

### 反模式 5 · 注释承诺了代码没做的事

**症状**：`"""Secure 只在 https 下加"""` 而 `kwargs` 里没有 `secure`。

**为什么错**：后人读注释就以为做了，不会再看代码。

**正确做法**：凡"注释说做了某事"，就要有一条测试验证。或者：注释只写"为什么"，不写"做了什么"（让代码自己说）。

### 反模式 6 · 把状态管理交给框架

**症状**：幂等/重试/心跳全塞进 APScheduler 的 JobStore 或 Celery 的 result backend。

**为什么错**：① 不可单测（要起框架、等 cron）；② 跨进程不可见（web 读不到 worker 的状态）；③ 框架升级会改内部结构。

**正确做法**：框架管"什么时候"，自己管"跑没跑过、失败算谁的、还活着吗"。

### 反模式 7 · 静态数据与动态数据同权重投入

**症状**：模板广场（用一次）做得比每日委托（天天用）还精致。

**为什么错**：代码量应该与使用频次成正比。

**正确做法**：识别"一次性供给"与"持续性机制"，把工程复杂度投给后者。

### 反模式 8 · CI 只看 exit code

**症状**：`pytest -q` 返回 0 就算通过。

**为什么错**：收集 0 项也是 0；全 skip 也是 0；测试目录没配上也是 0。

**正确做法**：断言"跑了多少个测试"；区分 pytest 风格与脚本式自测（D-003）。

### 反模式 9 · 在 async 里裸调同步 I/O

**症状**：`history = store.get_messages(...)` 直接写在 `async def` 里。

**为什么错**：单次 2ms 看起来无害，但一次问答 6~7 次 + 并发 3 个 = 事件循环阻塞 40ms+，所有请求一起变慢。

**正确做法**：`await asyncio.to_thread(...)`。**规则要工具化**（lint），不能只靠记。

### 反模式 10 · 为"想象中的未来"抽象

**症状**：加一堆"以后可能要用"的配置项、插件机制、多态。

**正确做法**：为"已知的未来"留接口。区别在于：
- 已知的未来有具体形态（"定时类工具"→ 所以有 `defer`）；
- 想象中的未来没有（"以后可能要支持多租户"→ 所以不做）。

`TOOL_PLAYBOOK` 是空的但结构存在——这是"已知未来"（注释明确说"给未来的定时类工具留位"）。

## 12.3 未标定边界的决策（最危险的一类）

**定义**：一个决策在当前配置下是正确的，但它的正确性依赖一个**没有被写下来**的前提。一旦前提改变，决策就错了，而且不会报错。

这是本报告认为最值得警惕的一类技术债，因为它**不表现为代码问题**。

### 清单

| # | 决策 | 隐含前提 | 前提破了会怎样 |
|---|---|---|---|
| 1 | 单进程 uvicorn | 所有状态都在进程内 | 加 `--workers 4` → 限流 4 倍、缓存碎片、锁失效 |
| 2 | `sqlite3.Connection` 线程本地复用 | 同一 `with _get_conn()` 块内没有 `await` | 有人在块内 await → 事务边界混乱 |
| 3 | 后端只听 `127.0.0.1:8000` | 前端与后端同源（经 Next 代理） | 分域名部署 → CORS 拒绝、Cookie 丢 |
| 4 | `SameSite=Lax` 防 CSRF | 所有写操作都是非 GET | 加一个 `GET /xxx/delete` → CSRF 成立 |
| 5 | 阈值 0.25 / 0.45 | embedding 是 `text-embedding-v3` | 换模型 → 全部误判（但不会报错） |
| 6 | `credential` 走 Cookie | 浏览器客户端 | 移动端/小程序 → 必须开 `AUTH_RETURN_TOKEN` |
| 7 | `metrics` 靠 textfile probe | 脚本能访问 sqlite | 容器化 → 脚本在容器外，路径不通 |
| 8 | 两个 db 文件不跨库 JOIN | 无跨库查询 | 新代码写 JOIN → 运行时 `no such table` |
| 9 | WAL 可用 | 本地文件系统 | 挂 NFS/SMB → WAL 失效，SQLite 报错 |
| 10 | `time.localtime` 与 `SCHEDULER_TZ` 一致 | 部署时设了 `TZ=Asia/Shanghai` | 没设 → 额度在北京时间 8 点重置 |
| 11 | 缓存键 `(temperature, max_tokens)` 完备 | 没有别的构造参数 | 加 `top_p` 参数 → 设置了不生效 |
| 12 | `token_store` 黑名单有效 | 单进程 | 多副本 → 各进程黑名单不一致（已退出还能用） |
| 13 | 上传路径校验用 `realpath` 前缀 | 上传目录与数据目录不重叠 | 如果 `chat_uploads` 放在 `data/` 下，`data/.env` 仍可读（因为都在前缀内？不，`.env` 在根目录）|
| 14 | Agent 图缓存可跨请求复用 | `checkpointer=None` | 一旦挂 checkpointer → 跨请求状态污染 |

### 第 13 条的补充说明

`_resolve_upload_path` 校验的是 `real.startswith(CHAT_UPLOAD_DIR + os.sep)`。

`CHAT_UPLOAD_DIR = data/chat_uploads`。所以：

- `data/chat_uploads/xxx.jpg` → 通过 ✅
- `data/sessions.db` → 前缀不匹配（`data/chat_uploads` vs `data/sessions.db`）→ 拒绝 ✅
- `data/chat_uploads/../sessions.db` → `realpath` 解析成 `data/sessions.db` → 拒绝 ✅

所以当前是安全的。但如果有人把 `CHAT_UPLOAD_DIR` 改成 `data/`，那么整个 `data/` 都可读——包括 `sessions.db` 和 `.auth_secret`。

**这是一个"参数改了就不安全"的设计**。更稳的做法是"白名单扩展名 + 内容嗅探"，或者把上传目录放到数据目录之外。

### 为什么这类债最危险

因为它们**不会在代码评审中暴露**。评审看的是"这段代码对不对"，而"隐含前提"不在代码里。

**唯一的管理手段是：把前提写进注释，并且写清"前提破了会怎样"。**

本项目做得好的例子（`core/llm.py`）：

```python
# 更换向量化模型后必须删除 chroma_db/ 目录重建向量库！
```

做得不好的例子：大部分隐含前提没有被记录（上表 14 条里，只有 3~4 条在注释里出现过）。

**建议**：给每个"架构级假设"建一个清单文件（比如 `docs/架构假设.md`），列出"我们假设了什么、破了会怎样、怎么检测"。

## 12.4 如果重做一次：会改什么、不会改什么

这是检验"决策是否真的成立"的最好方法——**如果重做还会做同样的选择，说明它不依赖路径依赖。**

### 不会改的（12 项）

| 决策 | 为什么重做也这么选 |
|---|---|
| SQLite 而非 PG | 约束没变（2G 内存） |
| 单进程 | 约束没变（状态在进程内） |
| 裸机 + venv | 约束没变（1 台机器） |
| 同源 rewrite 代理 | 免 CORS 的收益是永久的 |
| 手写 SSE | 12 种事件 + 时序控制，框架帮不上 |
| Chroma | 零运维 + metadata 过滤，约束没变 |
| 不挂 checkpointer | 重复累积是物理事实（3 轮 12 条） |
| 四段检索流水线 | "三条引用两条重复"是普遍问题 |
| 强制溯源 | 输出层的信任基础 |
| 压缩块 + 增量分段 | KV 缓存的物理特性 |
| TOOL_META 声明式 | 提示词劝导的概率性 |
| owner 必填参数 | TypeError 优于静默 |

### 会改的（8 项）

| 当前 | 改成 | 理由 |
|---|---|---|
| 手写 JWT（不校验 alg） | PyJWT 或显式校验 `alg == "HS256"` | "因为没实现所以安全"不是安全 |
| `AGENT_LLM_MAX_TOKENS=0` 默认 | 新部署默认 2048 | 兼容性不该以敞口为代价 |
| 前端 `AuthGate` 组件 | Next middleware 统一拦截 | 纪律 → 机制 |
| 三处时区语义 | 统一用 `SCHEDULER_TZ` | 口径漂移 |
| `time.localtime` 做 day_key | `datetime.now(TZ)` | 同上 |
| 注释"滑动窗口" | 更新为"压缩块" | 注释过时比没注释更糟 |
| 截图式文档 + 手写报告 | 决策记录进 `docs/decisions/`，一决策一文件 | 80 个决策只有 5 个 ADR |
| `messages` 无上限 | 加容量监控（不只磁盘告警） | 知道"是什么占的"才知道怎么清 |

### 会改但成本高的（3 项）

| 当前 | 改成 | 成本 |
|---|---|---|
| 无 schema 版本号 | Alembic 或自建 migration 表 | 1 周（12 张表的迁移历史要补齐） |
| 无应用埋点 | `prometheus_client` + `/metrics` | 3 天（每个关键路径加计数） |
| `to_thread` 靠纪律 | lint 规则或统一包装层 | 2 天（要处理误报） |

**"不会改"的 12 项有一个共同点**：它们的正确性来自**物理约束或数学事实**（内存、KV 缓存前缀匹配、并发丢失更新），不是来自"当时的偏好"。

**"会改"的 8 项有一个共同点**：它们的错误来自**人的疏忽或口径不统一**，不是来自约束。

**这个区分很有用**：约束驱动的决策是稳的，疏忽驱动的决策是要修的。

## 12.5 演进路线与触发条件

技术选型的有效期由"触发条件"定义。下面给出每个关键决策的"何时该翻案"。

### 触发条件表

| 决策 | 触发条件 | 翻案动作 | 预估成本 |
|---|---|---|---|
| SQLite | 需要多副本 / 写 QPS > 200 / 库 > 10GB / 合规要求行级权限 | 迁 PostgreSQL | 2~3 周 |
| 单进程 uvicorn | 单进程内存 > 1.4G 且优化无效 | 先外移 8 项进程内状态（Redis），再加副本 | 3~4 周 |
| Chroma | 片段 > 100 万 / 需要跨库检索 / 需要 GROUP BY | 换 Qdrant 或 Chroma Server | 2 周 |
| 裸机部署 | 第 2 台机器出现 | Docker Compose（先迁移，再考虑编排） | 1 周 |
| 手写 JWT | 需要 SSO / 令牌轮换 / 多端登录管理 | OIDC + 成熟库 | 1 周 |
| 不挂 checkpointer | 需要"中途暂停、断点续跑"的 Agent | AsyncSqliteSaver + 不再重放历史（成对变更） | 1~2 周 |
| 混合检索 BM25 内存索引 | 库普遍 > 2 万片 | SQLite FTS5 或 Tantivy | 1 周 |
| 阈值 0.25/0.45 | 换 embedding 模型 | 重新标定 + 建评估集 | 1 周（含标注） |
| 自研工作流 DSL | 放弃"用户可编辑工作流" | 迁回 LangGraph | 省 2000 行 |
| 单次调用总结 | 重度用户（200+ 消息/天）占比 > 10% | 上 map-reduce | 1 周 |
| 无 HTTPS | **备案通过** | 跑 `https/setup-https.sh` | 1 小时 |
| `AuthGate` 组件 | 页面数 > 5 | Next middleware | 2 天 |

### 优先级排序（按"不做会怎样"）

**P0（不做会出事）**

1. **HTTPS** —— 只被备案卡住，脚本已就绪。不做的话：Cookie 无 Secure、geolocation 不可用、中间人风险。
2. **`header.alg` 校验** —— 3 行代码。不做的话：一个未来的"支持多算法"改动会引入经典 JWT 漏洞。
3. **双轨收口（`agent/tools.py` vs `core.serper.py`）** —— 行为已分叉（地区锚定不一致）。

**P1（不做会积累）**

4. **时区口径统一** —— 三处两种语义。
5. **`to_thread` 工具化** —— 纪律 → 机制。
6. **应用埋点** —— 现在只有"活着/死了"，没有"活得好不好"。
7. **embedding 模型一致性校验** —— 写进 collection metadata，检索前比对。

**P2（不做会难看）**

8. **`AuthGate` → middleware**
9. **注释更新**（"滑动窗口"那条）
10. **`messages` 容量监控**
11. **`GraphRecursionError` 中文翻译**

**P3（可以等）**

12. `AGENT_LLM_MAX_TOKENS` 默认值
13. 主题标签的消费方（或关掉省成本）
14. `TOOL_PLAYBOOK` 填内容

## 12.6 这套方法论能不能迁移到别的项目

### 能迁移的部分

**① 六段式决策记录**

```
问题域 → 候选面 → 判据 → 证据 → 决策与代价 → 反转条件
```

这套结构不依赖任何具体技术。任何"选 A 还是 B"的场景都能用。

**它的核心价值在最后一段**：写清"什么情况下该翻案"，等于给决策设了保质期。没有保质期的决策，会变成"祖传代码"。

**② 约束场优先于技术排名**

先写清"资源/运维/团队/时间/依赖/失败代价"，再评估技术。这个顺序是反直觉的（大多数人是"先看技术对比表"），但它能避免"选了一个正确但跑不起来的方案"。

**③ 六种技术债形态**

版本锁 / 静默降级 / 双轨 / 默认值陷阱 / 口径漂移 / 假绿。

这六种是**跨项目通用的分类**。任何项目都能用它们给债打标签，而标签决定修复策略：

- 版本锁 → 成对升级 + 全量回归；
- 静默降级 → 加可观测性；
- 双轨 → 判断行为是否已分叉；
- 默认值陷阱 → 写死值域 + 负向测试；
- 口径漂移 → 合并到一个函数；
- 假绿 → 断言"跑了多少个"。

**④ "机制 vs 纪律"的二分**

这个二分能快速给一个规则定优先级：**纪律型的债优先修。**

**⑤ 十条定律中的前三条**

默认值落安全侧、机制替代纪律、静默失败最贵。这三条几乎适用于所有后端系统。

### 不能迁移的部分

**① 具体的阈值**（0.25 / 0.45 / λ=0.65 / 16 帧 / 500 字 / 20000 片）

这些与 embedding 模型、数据分布、机器性能绑定。**迁移数字是错的，迁移"怎么定数字的方法"才对。**

比如 0.45 的定法：

> "同一份资料里的原文提问通常能到 0.6+，换个说法问大约 0.5，只是用词沾边但讲的是另一件事落在 0.3 附近。"

这个方法（找三个锚点，卡在中间）是可迁移的。

**② 具体的组件选择**（Chroma / APScheduler / DeepSeek）

这些与约束场绑定。换了约束场（比如 8G 内存、3 台机器），最优解全变。

**③ "手写"的偏好**

这个项目大量手写（JWT、BM25、表达式求值、SSE 解析、工作流引擎）。理由是"省依赖 + 完全可控"。

但在一个 10 人团队、6 个月工期的项目里，"手写"是灾难——没人维护、没有文档、招不到人。

**所以"手写"不是原则，是"小团队 + 少依赖"这个约束的产物。**

## 12.7 一个反问：这个项目的技术选型有什么系统性缺陷

前面十一卷都在解释"为什么这么选是对的"。这一节反过来问。

### 缺陷 1 · 缺少量化评估，所有"效果类"参数都是猜的

具体地：

| 参数 | 定值方式 | 有没有验证过"这个值更好" |
|---|---|---|
| `RETRIEVE_MIN_SIM=0.25` | 经验 | 没有（没有评估集） |
| `RETRIEVE_LOW_SIM=0.45` | 三个锚点估计 | 部分（锚点是实测的，但 0.45 本身没验证） |
| `RETRIEVE_MMR_LAMBDA=0.65` | 经验 | 没有 |
| `RETRIEVE_FETCH_MULT=3` | 经验 | 没有 |
| `RETRIEVAL_BIAS_ALPHA=0.08` | 经验 | 没有 |
| `HYBRID_RRF_K=60` | 业界惯用 | 没有（对中文场景是否适用未知） |
| `COMPRESS_KEEP_TURNS=6` | 经验 | 没有 |

**这意味着：这些参数"能跑"，但不知道是否"最优"。**

而更严重的是：**没有评估集，就无法知道"改一个参数是变好还是变坏"。**

**这是这个项目最大的方法论缺口。** 它导致了：

- 不敢动参数（怕变坏）；
- 无法证明"某个功能（如主题标签、画像偏置）真的有用"。

### 缺陷 2 · 大量"半成品"没有清理

| 半成品 | 状态 |
|---|---|
| 主题标签 | 在写入（每次入库一次 LLM 调用），`$contains` 过滤没有实际使用 |
| `TOOL_PLAYBOOK` | 空字典 |
| `TOOL_RESOURCES` | 空字典 |
| 蒸馏检索 | 只有接口契约，无实现 |
| 打卡记录后端 | 前端"接口待上线" |
| 混合引擎的切换规则 | 初始为空（自动切换可能不生效） |

**半成品的成本不是"没做完"，是"每个读代码的人都要花时间确认它做没做完"。**

而且有些半成品在**持续消耗资源**（主题标签每次入库调一次 LLM），这与"没做完"的直觉相反。

### 缺陷 3 · 可观测性只有"活着/死了"

有：
- 心跳三态；
- 磁盘告警；
- 组件 up/down。

没有：
- 错误率（5xx 比例）；
- LLM 调用失败率（按供应商分）；
- 检索的平均相似度分布（**这个能直接反映检索质量**）；
- 压缩触发频率与拒收率；
- 各模式的请求占比与延迟分布。

**最后一行"检索平均相似度分布"是最可惜的缺失** —— 它是零成本的（每次检索都有 `assess_grounding` 的结果），只要记一下就能画分布图。有了它，就能回答"用户的问题有多少是知识库覆盖不了的"。

### 缺陷 4 · 测试覆盖"决策"但不覆盖"路径"

现有测试很强的地方：锁住关键决策（`test_agent_checkpointer`、`test_retrieve_select`、`test_auth_cookie_secure`）。

弱的地方：

- 端到端路径（一次完整问答，从鉴权到落库）；
- 并发场景（两个用户同时写）；
- 错误路径（LLM 超时时 SSE 的表现）；
- 前端（完全没有测试）。

`tests/test_w1/w2/w3.py` 是端到端，但它们"需要后端已启动"——所以在 CI 里跑不了（CI 不启服务）。

**所以 CI 跑的是"离线回归"，端到端测试只能手动跑。** 这是一个现实的取舍（起服务要 key、要网络），但代价是"集成问题只能靠人工发现"。

### 缺陷 5 · 文档与代码的同步没有机制

已经发现的过时注释：
- `agent/builder.py` 说"窗口截断"，实际是压缩块；
- `core/auth.py` 说"Secure 只在 https 下加"，曾经代码没做；
- `规范/01` 的端点表说"队友新增的四个路由（均需补进本表）"，说明表没跟上。

**文档不会自动过期，但它会静默过期。** 而"静默过期"正是这个项目最警惕的失败模式——**它对代码用了十条定律，对文档一条都没用。**

## 12.8 结语：技术选型的本质是"选择失败的方式"

如果把整份报告压缩成一个判断：

> **技术选型不是选"最好的方案"，是选"你愿意承受哪种失败"。**

因为所有方案都会失败。问题不是"会不会坏"，是"坏的时候是什么样子"。

这个项目的每一种选择，都可以读成一句"我愿意承受这种失败"：

| 选择 | 承受的失败 |
|---|---|
| SQLite | 不能多机；单写锁 |
| 单进程 | 不能利用多核；进程崩溃全站挂 |
| 手写 JWT | 可能漏掉某个边界检查（alg） |
| 不挂 checkpointer | 无法"中途暂停、断点续跑" |
| 压缩块 | 摘要可能丢细节 |
| 裸机部署 | 环境漂移；回滚慢 |
| 自研工作流引擎 | 2000 行要自己维护 |

而它拒绝的每一种方案，也是"不愿意承受那种失败"：

| 拒绝 | 不愿意承受的失败 |
|---|---|
| PostgreSQL | OOM（确定性故障） |
| 多副本 | 限流/缓存/锁的语义错（静默故障） |
| Redis | 又一份常驻内存 |
| Celery | broker 内存 + 复杂度 |
| Docker | 100MB + 调试多一层 |
| LangGraph 做工作流 | 不能运行期编辑 |
| 挂 checkpointer | 上下文平方级膨胀（可复现） |

**注意两列的对比**：选择的那一列，失败大多是"能力不足"；拒绝的那一列，失败大多是"正确性问题"。

**这个项目愿意牺牲能力，不愿意牺牲正确性。**

这是它的技术性格，也是它能在 2 核 2G 上跑住 34 个端点、5 个工具、3 条流式路径、6 个定时任务、1 个混合引擎的原因——**不是因为它聪明，是因为它知道自己付不起什么。**
