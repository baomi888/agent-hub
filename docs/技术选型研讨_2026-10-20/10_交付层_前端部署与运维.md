# 卷十 · 交付层：前端、部署与运维

> 本卷解决的问题：**把"能跑"变成"别人能用"，并且在只有一个人的运维能力下，让它持续能用。**
> 这一层的技术选择自由度最大（前端框架、部署方式都可以选），但也最容易被"最佳实践"绑架——因为网上的教程默认你有 4 台机器、1 个 K8s 集群、1 个 SRE。

## 10.1 前端：Next.js 16 + React 19 + Tailwind v4

### 为什么是 Next.js 而不是 Vite + React

单页应用（SPA）用 Vite + React 完全够用，而且更轻。选择 Next.js 的**唯一决定性理由**是 rewrite 代理。

`next.config.ts` 里配一条：

```js
async rewrites() {
  return [{ source: "/api/:path*", destination: "http://localhost:8000/api/:path*" }]
}
```

带来的后果（全部是收益）：

| 问题 | SPA 方案 | Next rewrite 方案 |
|---|---|---|
| CORS | 需要后端配 `allow_origins` + 前端带 `credentials: "include"` | **不需要**（同源） |
| Cookie 域 | 后端 `:8000` 设置 Cookie，前端 `:3000` 读不到（跨域） | **自动**（都在 `:3000`） |
| 后端地址 | 需要 `VITE_API_BASE` 环境变量，构建时注入 | **不需要**（相对路径 `/api/*`） |
| 部署端口 | 需要暴露两个端口 | **只暴露 3000** |
| HTTPS 证书 | 两份（前端 + 后端） | **一份**（nginx 或 Next） |

**注意最后两行**：这直接呼应卷二 §2.8 的"后端只听回环"。两者是同一个决策的两面——因为这个代理存在，后端才能不暴露；因为后端不暴露，代理才必须存在。

### 代价：Next.js 的重（相对）

- `next build` 是单进程吃满一个核、峰值 800MB 的操作。在 2G 机器上，**必须在没有其他服务跑的时候构建**（`规范/决策记录.md` D-004 明确写了"不要同时构建两端"）。
- `node_modules` 是 15566 个文件（项目结构快照里的数字）。占磁盘约 300~500MB。
- 运行时：Next 的 Node 进程常驻约 150~250MB。

**这是一笔不小的内存开销**，换来的是"零 CORS 配置 + 单端口"。在 2G 机器上，这个交易的判据是：**没有 CORS 配置意味着少一类线上故障**（CORS 配置错误的排查成本很高，且症状是"请求发了但浏览器说失败"）。

### App Router vs Pages Router

项目用 App Router（`src/app/page.tsx`、`src/app/templates/page.tsx`）。

理由不是"更新"，而是 **App Router 的默认行为更接近"静态壳 + 客户端交互"**：

- 页面默认是 Server Component（在服务端渲染）；
- 交互组件用 `"use client"` 标记；
- 流式渲染（Suspense）内建。

对于一个"登录后重交互"的应用，Server Component 的收益有限（大部分内容是客户端渲染的对话）。但 App Router 的**路由约定**（`page.tsx` / `layout.tsx`）比 Pages Router 更清晰。

**代价**：App Router 的心智负担更高（Server/Client 边界、`"use client"` 的传播、缓存语义）。对一个三人团队，这是真实成本。

**判断**：如果重做，Pages Router 可能更简单。但这不是一个"错"的选择——App Router 是 Next 的方向，迁回去反而不划算。

## 10.2 `lib/api.ts` 单一出口

### 规则（`规范/01` 前端硬规则 1）

> 后端调用**只允许**出现在 `src/lib/api.ts`。组件里直接写 `fetch("/api/...")` 一律打回。

### 这条规则防什么

三处口径漂移：

**① 鉴权**

如果组件直接 `fetch`，可能忘记带 `credentials: "include"` → 请求不带 Cookie → 401。

集中在 `api.ts` 里，只需要写一次：

```typescript
const res = await fetch(url, { credentials: "include", ... })
```

**② 错误处理**

后端返回 429 / 404 / 500，前端要怎么处理？

- 429 → 显示"太频繁" + 禁用按钮；
- 401 → 跳登录；
- 500 → "服务器出错"。

如果每个组件自己处理，会有 20 种不同的文案。集中在 `api.ts` 里，一套逻辑。

**③ 基址**

虽然用相对路径 `/api/*`，但如果将来要支持"多环境"（本地直连 8000、测试环境走代理），基址需要一个地方配置。

### SSE 的特殊情况

SSE 不能用 `EventSource`（只能 GET，不能带自定义头）。所以 `lib/sse.ts` 用 `fetch` + `ReadableStream` 手动解析：

```typescript
const reader = res.body.getReader()
const decoder = new TextDecoder()
let buffer = ""
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  buffer += decoder.decode(value, { stream: true })
  // 按 "\n\n" 切帧，解析 event: / data:
}
```

**这个解析器必须处理三个边界**：

1. **跨 chunk 的半帧**：一个 `event: token\ndata: {...}` 可能被拆在两个 TCP 包里。所以要用 buffer 累积，只在遇到 `\n\n` 时切。
2. **UTF-8 多字节**：`decoder.decode(value, { stream: true })` 的 `stream: true` 是关键，否则一个中文字符被拆在两个 chunk 里会乱码。
3. **`data:` 多行**：SSE 规范允许多个 `data:` 行（用 `\n` 拼接）。本项目的 `_sse()` 只发一行，但解析器理论上应该处理多行。

**这三个边界是手写 SSE 解析的必修课。** 用现成的库（如 `eventsource-parser`）可以避免，但那多一个依赖。

### 为什么 `sse.ts` 独立于 `api.ts`

因为 SSE 的解析逻辑（buffer、帧切分、事件分发）与普通 JSON 请求完全不同。混在一起会让 `api.ts` 变成 500 行的大文件。

**这是"按协议分文件"而不是"按资源分文件"的划分方式**，对于流式场景是正确的。

## 10.3 设计令牌：为什么需要一个 `tokens.css`

### 结构（`规范/01` 前端硬规则 2）

> 颜色 / 间距 / 字号**只能**用 `styles/tokens.css` 的变量，禁止硬编码色值。

### 令牌体系（README）

- 明暗双主题：暖米黄纸 ↔ 深棕木桌；
- 明度三级阶梯、圆角四档、字号七档、中性填充四级；
- 语义色成对出现：实心版压白字，文字版上纸底，逐档验过 WCAG AA（≥4.5:1）。

### 为什么"硬编码色值"是错的

考虑一个具体场景：`#C8892A`（玉米金）用在 8 个地方。切换深色主题时，需要把它改成 `#E0A93F`。

- **硬编码**：全局搜索 `#C8892A`，替换 8 处。如果有一处写成了 `#c8892a`（小写），漏掉。
- **令牌**：`--color-accent` 在 `[data-theme="dark"]` 里覆盖一次。8 处自动生效。

**更糟的是"未定义颜色的使用"**：如果某个组件用了 `#F5F0E6`（一个接近背景色的米白），在深色主题下它会变成一个刺眼的亮块——而这个颜色在令牌表里可能根本没有对应项，说明它是"随手取的"。

**令牌体系的价值不只是"能换主题"，而是"限定可用的颜色数量"** —— 一旦只能从 20 个令牌里选，就不会出现第 21 种颜色。

### WCAG AA 的验证

> 逐档验过 WCAG AA（≥4.5:1）

这是**对比度计算**：

```
contrast = (L1 + 0.05) / (L2 + 0.05)
其中 L 是相对亮度（sRGB 线性化后加权）
```

4.5:1 是正文的标准。大字号（18pt+ 或 14pt+ 粗体）可以降到 3:1。

**为什么这个项目要做这件事**：因为"暖米黄纸 + 玉米金"这个配色很容易踩坑——金色在浅色背景上的对比度天然低。

`docs/设计令牌对照_LobeHub.md` 记录了"令牌体系参照 LobeHub 的 DESIGN.md 做过逐层对照"。这是一个**借鉴定价体系**而非"抄配色"的做法——学的是"怎么组织令牌"，不是"用什么颜色"。

### 代价

- 令牌表需要维护（20+ 个变量 × 2 个主题）；
- 新增颜色要走"是否已有相近令牌"的检查；
- 设计稿必须用令牌名标注，不能用色值。

**对一个三人团队，这套流程的成本不低。** 但收益是"双主题不会崩"——而双主题是这个产品最显性的视觉特征。

## 10.4 `100dvh` 而不是 `vh`

### 问题

移动端浏览器的地址栏会收放，导致视口高度变化。

- `100vh` = "**最大**视口高度"（地址栏收起时的高度）；
- `100dvh` = "**动态**视口高度"（当前实际高度）。

如果用 `100vh`：

- 地址栏展开时，页面比视口高 → 底部内容（输入框）被裁掉；
- 用户要滚动才能看到输入框 → 体验崩。

`100dvh` 会随地址栏收放动态调整。

### 浏览器的支持

`dvh` 是 2022 年的新单位。支持情况：

- Chrome 108+、Safari 15.4+、Firefox 101+；
- 老旧浏览器（Android WebView 旧版）不支持 → 会退回 `auto`（高度塌陷）。

**没有做 fallback**。这意味着在旧浏览器上布局会坏。评估：目标用户是大学生（设备较新），可以接受。

**这是一个"用新特性换代码简洁"的决策**，代价是兼容性，收益是不用写 JS 监听 `resize`。

### 移动端可滚动的实现

README：

> 手机端整体可滚动 —— 用的是 `100dvh` 而不是 `vh`，因为移动端地址栏收放会改变视口高度。

但 `100dvh` 只解决"容器高度正确"，还需要处理"内容超出时能否滚动"：

```css
.container {
  height: 100dvh;
  display: flex;
  flex-direction: column;
  overflow: hidden;
}
.scroll-area {
  flex: 1;
  overflow-y: auto;
  -webkit-overflow-scrolling: touch;   /* iOS 惯性滚动 */
}
```

`-webkit-overflow-scrolling: touch` 是 iOS 的必需项（否则滚动很"粘"）。

**这是一个"看起来一行 CSS，实际三个坑"的例子**：视口高度、flex 布局、iOS 滚动。

## 10.5 `AuthGate` 的已知缺口

### 现状

```typescript
// src/components/AuthGate.tsx  登录门禁（⚠️ 目前只包了 page.tsx，/templates 未覆盖）
```

规范里明确列为缺口：

```
| 3 | /templates 不在 AuthGate 内 | frontend/src/app/templates/page.tsx | A 线 | 中 |
```

### 这意味着什么

未登录用户可以访问 `/templates` 页面并看到模板内容。

**严重度评估为"中"**，因为：
- 模板内容是静态的（`core/templates_catalog.py`），不是用户数据；
- 真正需要鉴权的是"用模板建库"这个动作（那是 API 调用，后端会 401）。

**所以这是一个"信息暴露"而非"越权"**。

但它暴露了一个更普遍的问题：**"每个页面都要记得包 AuthGate"是一种纪律，不是机制。**

对比后端的做法（`APIRouter(dependencies=[Depends(...)])`）——那是机制，忘了写也安全。

**前端缺一个等价物**：比如在 `layout.tsx` 里统一判定，或者在 middleware 里拦截。

Next.js 的 `middleware.ts` 可以做到：

```typescript
export function middleware(req) {
  if (!req.cookies.get("baomi_session") && !req.nextUrl.pathname.startsWith("/login")) {
    return NextResponse.redirect("/login")
  }
}
```

**但这里有个技术问题**：`middleware` 在 Edge Runtime 里跑，只能读 Cookie 的**存在性**，不能验签（没有 crypto 的 HMAC 或者配置复杂）。所以它只能做"粗筛"，真正的鉴权还是后端的 401。

**当前没做 middleware，靠 AuthGate 组件。** 这是一个"能用但不可靠"的方案。

## 10.6 模板广场的转型：一个产品层的技术决策

README 里有一段很长的说明：

> 原先的 8 个校园场景模板仍在，但**它的定位变了**。盘完现状后确认：模板广场是「一次性的起点供给」（建库 + 开场白，用一次就完），而每日委托 / 每日总结是「持续性的陪伴机制」（天天用）；而模板谁来都一样，恰恰**不体现个性化**。首屏因此从「四宫格平级」改成**主次两层** —— 主线放天天用的三个入口，模板广场退到辅路；同时给每个模板加「设为每日委托」，把一次性资产接进持续机制。

### 为什么这算"技术选型"

因为它决定了一组技术资源的分配：

- 首屏渲染什么（性能预算给谁）；
- 哪些接口是"高频"（需要缓存）；
- 哪些数据是"长生命周期"（需要持久化）。

模板是静态数据（`templates_catalog.py`，169 行），不需要数据库、不需要缓存。而每日委托是动态数据（`delegations` 表 + `job_runs`），需要事务、幂等、调度。

**"把模板从主位挪到辅位"这个动作，等于把工程重心从"静态内容展示"转到"状态机与调度"。** 这是一个架构级的取向变化。

### 一个可迁移的判断

> **"用一次就完"的功能 vs "天天用"的功能，前者应该做成静态资源，后者才值得投入工程复杂度。**

模板广场做得很精致（8 个场景、开场白、建库参数），但它的使用频次是"一次"。而每日委托、每日总结的代码量更大（`service/daily.py` + `worker/` + `core/scheduler.py` + 4 个 api 文件），因为它们要天天跑。

**代码量应该与使用频次成正比，而不是与"功能的新鲜感"成正比。**

## 10.7 部署：裸机 + venv，不用 Docker

### 候选面

| 方案 | 磁盘 | 内存 | 隔离 | 部署复杂度 |
|---|---|---|---|---|
| **裸机 + venv** | 最小 | 最小 | 无（进程级） | 低（一个 shell 脚本） |
| Docker + compose | +1~2GB（镜像） | +100MB（daemon） | 容器级 | 中 |
| Docker + K8s | +2GB+ | +500MB（控制面） | Pod 级 | 高 |

### 为什么不用 Docker

**理由 1：内存。** Docker daemon 本身约 80~100MB 常驻。在 2G 机器上，这是 5%。加上镜像层（Python 3.12 + 依赖 + Node），至少 1.5GB 磁盘。

**理由 2：这个项目已经是"单进程 + 文件系统"**。容器化的核心价值是"环境一致性"和"隔离"，而：
- 环境一致性：用 `requirements.txt` + venv 已经解决（"干净机器测试"是同一个目的）；
- 隔离：单机单应用，没有"多租户"需求。

**理由 3：调试成本。** 出问题时，裸机可以直接 `ps` / `lsof` / `strace` / 看 `/root/.pm2/logs`。容器里要多一层 `docker exec`。

**理由 4（隐性的）：Chroma 的 sqlite 在容器里挂卷，会有文件锁问题。** WAL 模式在 bind mount 上可能失效（取决于文件系统）。这是一个真实的风险。

### 代价

- **环境漂移**：服务器上的 Python 版本、系统库（libsqlite3、libffi）可能与开发机不同。项目踩过这个坑（`chromadb==0.5.23` 在 Python 3.14 上装不上）。
- **无法快速复制**：要开第二台机器，需要重新走一遍部署流程。
- **回滚靠 git**：`git checkout <tag>` + 重装依赖。没有镜像层的"秒级回滚"。

**判断**：在"1 台机器、1 个人运维、2G 内存"的条件下，裸机是唯一合理选择。但它的有效期与"机器数量"绑定——第 2 台机器出现时，应该考虑 Docker。

## 10.8 `deploy.sh` → systemd：一次正确的演进

### 三个阶段

**阶段 1：nohup（原始）**

```bash
nohup venv/bin/python -m uvicorn main:app --port 8000 > backend.log 2>&1 &
```

问题：
- 机器重启后不自动拉起；
- 进程崩溃后不重启；
- 日志无限增长（要自己配 logrotate）；
- 停止靠 `pkill -f uvicorn`（可能误杀）。

**阶段 2：`deploy.sh`（当前主路径）**

```bash
bash deploy.sh start      # 首次部署
bash deploy.sh deploy     # 完整更新（动了 frontend/src/** 必须用这条）
bash deploy.sh restart    # 只改了 Python，跳过前端构建
bash deploy.sh status     # 看服务状态
bash deploy.sh logs       # 看日志
```

它管理三个进程（backend / frontend / worker），并区分"要不要重建前端"。

**为什么区分**：`next build` 要 1~2 分钟 + 800MB 内存。如果只改了 Python，重建前端是纯浪费。

**阶段 3：systemd（2026-10-20 新增）**

```
systemd/：3 个 unit（backend/frontend/worker）+ install-systemd.sh（含 --rollback）
```

收益：
- `Restart=always` → 崩溃自动拉起；
- 开机自启；
- `journalctl -u agent-hub-backend` 统一日志；
- 资源限制（`MemoryMax=`）可以配。

**一个关键的迁移提醒**：

> **迁移后别再用 deploy.sh start/restart（抢端口）**

因为 systemd 已经占用了端口，`deploy.sh` 再起一个会失败（`Address already in use`），或者更糟——两个进程抢同一个端口（取决于 SO_REUSEPORT）。

**这是一个"工具切换期"的经典陷阱**：两套管理方式并存，忘记切换会导致"看起来启动了但其实是旧的"。

### `install-systemd.sh --rollback` 的设计

```bash
bash systemd/install-systemd.sh --rollback      # 回滚到 nohup
```

**为什么需要回滚**：systemd 的 unit 文件写错（比如 `WorkingDirectory` 不对），会导致服务起不来。此时需要快速回到"已知能用"的状态。

**这是一个"迁移必须有回滚路径"的原则**。而且回滚要**一键**——如果需要手动 `systemctl disable` + 删文件 + 重新 nohup，那在故障时来不及。

### 一个技术细节：unit 不配 `EnvironmentFile`

> unit 不配 `EnvironmentFile`（应用自己 `load_dotenv`，避免 systemd 解析 `.env` 报错）

systemd 的 `EnvironmentFile` 对格式要求严格：

- 不支持 `export` 前缀；
- 不支持行内注释（`KEY=value # comment` 会被当成值的一部分）；
- 不支持多行值；
- 引号处理与 shell 不同。

而 `.env` 是给人写的，经常有这些写法。所以 `EnvironmentFile` 会报错，或者更糟——**静默地把值解析错**（比如值里带 `#`）。

**让应用自己 `load_dotenv`（python-dotenv 容错性好），systemd 只负责启动** —— 这是一个正确的职责划分。

## 10.9 staging 同机分端口：四重隔离

### 设计（`规范/决策记录.md` D-004）

| 维度 | 生产 | Staging |
|---|---|---|
| 端口 | 3000 / 8000 | **3001 / 8001** |
| 数据 | `data/`、`chroma_db/` | **`data-staging/`、`chroma-staging/`** |
| 配置 | `.env` | **`.env.staging`** |
| 代码 | `/root/agent-hub` | **`/root/agent-hub-staging`**（独立 git 工作区） |

### "为什么必须用两个工作区"

> 同一目录切分支会让生产代码在构建期间**处于半成品状态**，前端 `.next` 也会被覆盖。代价只是多一份 `venv` 与 `node_modules`。

展开：如果 staging 和生产共用一个目录：

```
1. git checkout staging          ← 生产代码此刻变成 staging 的代码
2. npm run build                 ← 但生产进程还在跑旧代码，此时如果重启，会用半成品
3. .next 被覆盖                   ← 生产前端的构建产物没了
4. 出问题 → git checkout main    ← 又要 rebuild
```

**关键在于"构建不是原子的"**。文件系统是共享状态，构建过程会短暂地让目录处于不一致状态。

两个工作区 = 两份文件系统 = 构建互不影响。

**代价**：`node_modules` 再来 300~500MB。磁盘可能吃紧（40G 的机器可以承受）。

### 安全护栏

```bash
# 已写进 deploy-staging.sh：
# - DATA_DIR/PERSIST_DIR 指向生产目录 → 脚本拒绝启动
# - 停服务按端口精确匹配，不用宽泛的 pkill -f "uvicorn main:app"，不误杀生产
```

**第一条**：如果 staging 的配置错误地指向 `data/`，会污染生产数据。脚本主动检查并拒绝。

**第二条**：`pkill -f "uvicorn main:app"` 会杀掉所有匹配的进程——包括生产的。所以必须按端口精确匹配：

```bash
lsof -t -i:8001 | xargs kill
```

**这两条都是"防止运维手滑"的护栏**，而且是**脚本主动拦截**，不是文档提醒。

**这是一个正确的做法：把运维纪律写进脚本，而不是写进文档。**

### 代价

2 核 2G 跑两套实例吃紧。所以：

> **不要同时构建两端**

这是一个"已知的容量约束"，只能靠纪律遵守（没有强制手段）。

## 10.10 HTTPS：一个被现实条件卡住的计划

### 目标架构

```
用户 → 443 (nginx, TLS 终结) → 127.0.0.1:3000 (Next)
                              → 127.0.0.1:8000 (API)
```

### 为什么需要 nginx

Next.js 自己可以跑 HTTPS，但：

- 证书管理（续期）要自己写；
- 一个域名要同时代理前端和 API（Next 的 rewrite 只处理 `/api/*`，其他路径是页面）；
- nginx 提供 gzip、安全头、访问日志、限流。

**关键是第二点**：Next 的 rewrite 是"应用层代理"，它不适合做"TLS 终结 + 静态资源缓存"。nginx 是专门做这个的。

### `setup-https.sh` 的设计

```
https/setup-https.sh + https/agent-hub.conf.template（域名占位 __DOMAIN__）
用法：bash setup-https.sh <域名> [邮箱]
```

流程：
1. DNS 预检（域名是否解析到本机）；
2. 装 nginx + certbot；
3. 写反代配置（`/` → 3000，`/api/` → 8000，SSE 关缓冲）；
4. 申请 Let's Encrypt 证书；
5. 配 `certbot.timer` 自动续期。

**"幂等可重跑"** —— 这一点很重要：部署脚本经常在"跑了一半失败"后需要重跑。如果脚本不幂等（比如重复写配置导致重复的 `server` 块），重跑会搞坏配置。

### SSE 的特殊配置

```nginx
location /api/chat/stream {
    proxy_buffering off;
    proxy_cache off;
    proxy_set_header Connection '';
    proxy_http_version 1.1;
    chunked_transfer_encoding off;
    proxy_read_timeout 3600s;
}
```

逐行解释：

- `proxy_buffering off`：**最关键**。nginx 默认缓冲上游响应，SSE 会被攒成一大块。
- `proxy_cache off`：防止缓存 SSE 流（虽然 POST 一般不缓存，但显式关掉更安全）。
- `proxy_set_header Connection ''`：配合 `proxy_http_version 1.1` 保持长连接。
- `proxy_read_timeout 3600s`：默认 60s，长回答（比如 30 秒生成 + 网络抖动）会被断开。
- `chunked_transfer_encoding off`：避免二次分块。

**这五行是 SSE 通过 nginx 的标准配方。** 缺任何一行都可能出问题，而且症状都是"流式失效"（等待很久然后全部出现）。

### 为什么现在不能切 HTTPS

`部署说明.md` 和用户长期记忆都记着：

- 域名 ICP 备案未通过；
- DNS 未指向服务器；
- **Let's Encrypt 不给裸 IP 发证书**。

所以整个 HTTPS 计划被"非技术因素"卡住。

**这是一个值得记录的观察**：技术方案可以准备好（脚本已就绪、幂等可重跑），但无法执行。**技术选型的有效性依赖外部条件。**

而"公网 http 下浏览器 geolocation 不可用"这个问题（`api/geo.py` 存在的原因），正是"没有 HTTPS"的直接后果——所以定位必须做服务端 IP 兜底。

**一个非技术约束（备案）导致了一个技术设计（IP 定位兜底）。** 这种因果链在真实项目里非常常见，但在技术文档里几乎从不出现。

## 10.11 监控：Prometheus + textfile probe

### 架构

```
node-exporter ──┐
                ├──> Prometheus ──> 告警规则（3 条）
probe-health.sh ┘   （textfile collector）
```

`probe-health.sh` 是"定时跑一个脚本，把结果写成 Prometheus 文本格式的文件"，node-exporter 的 textfile collector 会读取它。

### 为什么要绕这一圈

因为**业务指标不在 node-exporter 的视野里**。

node-exporter 只知道"CPU / 内存 / 磁盘 / 网络"。它不知道：

- worker 心跳多久没更新了；
- 有多少任务失败了；
- 数据库文件多大。

而 Prometheus 的标准做法是"应用暴露 `/metrics` 端点"。但那需要 `prometheus_client` 库 + 一个端点 + 埋点代码。

**textfile 方案的好处：不需要改应用代码。**

```bash
# probe-health.sh 大概这么写
age=$(sqlite3 /root/agent-hub/data/scheduler.db "SELECT strftime('%s','now') - ts FROM worker_heartbeat WHERE id=1")
echo "agent_hub_worker_heartbeat_age_seconds $age" > /var/lib/node_exporter/textfile/agent_hub.prom
```

**代价**：脚本要跑在能访问 sqlite 的机器上，且要配 cron（或者 systemd timer）。

**这是一个"低侵入"的监控方案**，适合"不想改应用"的场景。

### 三条告警的阈值

| 告警 | 阈值 | 依据 |
|---|---|---|
| 组件挂 | `up == 0` 持续 5 分钟 | 避免抖动误报 |
| 主机失联 | node-exporter 无数据 | 与上一条互补（服务挂了 vs 机器挂了） |
| 磁盘 < 10% | `avail/size < 0.1` | SQLite 写失败前留缓冲 |

**缺少的**：错误率、延迟 P99、LLM 失败率、配额触顶率。

这些需要应用埋点，当前没有。**这是一个明确的缺口**——系统"活着"，但"活得好不好"看不到。

## 10.12 CI：两类测试必须分开跑

### 事故（`规范/决策记录.md` D-003）

`ci.yml` 把 4 个"脚本式自测"文件混在 pytest 命令里跑。结果：

- 全通过 → `collected 0 items`，**绿色但零覆盖**；
- 有失败 → 模块级 `sys.exit(1)` 把 pytest 进程干掉。

**结果：4 个文件、14+27+... 项检查，从未被真正校验。**

### 判据

```bash
grep -c '^def test_' tests/test_xxx.py   # 输出 0 = 脚本式
```

### 修复

`ci.yml` 拆两个 step：

```yaml
- name: Run offline test subset (pytest 风格)
  run: pytest -q tests/test_retrieve_select.py tests/test_chroma_singleton.py ...

- name: Run script-style self-checks (脚本式自测)
  run: |
    python tests/test_agent_guard.py
    python tests/test_grounding.py
    ...
```

### 这个事故的普适性

**"测试跑绿了"不等于"测试跑了"** 这一点，在以下场景都会出现：

- 测试框架的收集规则与实际文件结构不匹配（本例）；
- 测试被 `skip` 但没有提示（`pytest -q` 会显示 skipped 数，但如果 CI 只看 exit code，skipped 也算通过）；
- 测试目录不在 `testpaths` 里；
- 覆盖率统计包含了未执行的代码（覆盖率工具的问题）。

**判据：CI 必须断言"跑了多少个测试"**，而不只是"exit code 是 0"。

当前 CI 用 `pytest -q`，输出里有 `237 passed`。如果有人误删了一批测试，`237` 会变小——但没有断言，所以不会红。

**改进方向**：`pytest --strict-markers` + 一个"最少测试数"的断言。

### `ruff` 的历史遗留

用户长期记忆里记着：

> **ruff 全仓 523 处错误属历史遗留**（`worker/scheduler.py` 旧式 `%` 格式化、E501、UP009），不是回归；CI 只跑 offline-tests，**不跑 lint**。

**这意味着 lint 是"建议"而不是"门禁"。** 这是一个有意的取舍：523 处错误如果设成门禁，要么全修（几天），要么加大量 `noqa`（噪音）。

**当前状态**：lint 不阻塞合并。代价是代码风格逐渐漂移。

**这是一个"技术债的显式接受"**，比"假装没有"好。

## 10.13 交付层的整体评价

### 一条主线：把"最佳实践"按约束重新排序

这一层拒绝了很多"标准做法"：

| 标准做法 | 本项目 | 理由 |
|---|---|---|
| Docker Compose | 裸机 + venv | 内存 |
| K8s | 无 | 机器数 = 1 |
| 独立前后端域名 | 同源 rewrite | 免 CORS + 免双证书 |
| PM2 / supervisor | systemd | 系统自带，无额外依赖 |
| Sentry | 无 | 内存 + 成本 |
| 应用埋点 / `/metrics` | textfile probe | 不改应用 |
| Prettier + ESLint 门禁 | 无（或非阻塞） | 523 处历史债 |
| 覆盖率门禁 | 无 | 测试基线靠人工 |

**每一条拒绝都有一个具体的约束**，不是"懒得做"。

### 三个真实风险

1. **没有 HTTPS**：Cookie 无 Secure、geolocation 不可用、中间人风险。这是**最高的单点风险**，且被非技术因素卡住。
2. **没有错误聚合**：线上报错只能靠 `journalctl` 逐条看。用户报障时，无法快速定位"哪个请求、哪条链路"。
3. **没有前端错误上报**：`window.onerror` 无人接收。前端白屏时，用户只能截图。

第 2、3 条是"可观测性缺口"，比"性能不足"更影响运维效率。

### 一条可迁移的经验

`deploy-staging.sh` 的两个护栏，值得单独记：

> - `DATA_DIR`/`PERSIST_DIR` 指向生产目录 → **脚本拒绝启动**
> - 停服务按端口精确匹配，**不用宽泛的 `pkill -f`**

**把"人会犯的错"变成"脚本会拒绝的操作"** —— 这是运维自动化的正确层次。

对比"文档提醒"：文档会过期、会被跳过、会被新人不读。而脚本拒绝是**不可绕过**的。

这与卷三的"owner 必填参数"是同一个思路：**用机制替代纪律**。

下一卷进入输出层。交付层解决"用户怎么看到"，输出层解决"系统自己产出什么"——每日总结与每日委托，是本项目唯一"系统主动为用户写东西"的地方。
