## 一、这一版做了什么

按 roadmap，B1 原本是「建 `controlled_terms` 表」。**我改成了先定文件契约、表留到后面。**
理由很实际：建表前必须知道词表长什么样，而这个答案只有 X1 能给，X1 还没到。
所以先把「读什么列、多值怎么分隔、编码怎么容错」定死，X1 一到只换文件、代码不动。

| 文件 | 作用 |
|---|---|
| `core/query_enhance/vocab.py` | 词表契约 + 加载器（BOM/分隔符/重复条目/别名冲突全容错） |
| `core/query_enhance/matcher.py` | 匹配器：最长优先 + 词条内反例 + 歧义拦截 + 叠字防护 |
| `ops/derive_temp_vocab.py` | 从金标集 `reason` 里抽出「别名→标准词」，生成临时词表（101 条） |
| `ops/eval_enhance.py` | 金标回归：精确率 / 召回率 / 反例误替换，A/B/C 三组对照 |
| `tests/test_query_enhance.py` | 20 条单测，含金标指标护栏 |

**接口只有两个**，`display_text` 恒等于原话——「不改展示」这条原则在类型层面就锁死了，
调用方拿不到被改过的展示文本：

```python
vocab, warns = load_vocab("data/vocab/vocab_v1.csv")
r = match("高数怎么复习", vocab)
r.display_text    # "高数怎么复习"    ← 原话，永不改
r.retrieval_text  # "高等数学怎么复习" ← 只给检索用
```

## 三、四条结论（这几条会改后续设计，请看完）

### 1. 反例必须按词条挂，不能做全局黑名单 ← 用 C 组证明的

C 组把金标里 226 个「本句反例」灌成全词表禁用词，结果：**误替换降到 0，但召回从 99.0% 掉到 94.1%，白丢 5 处该换的**。

具体例子：「实习」在某条金标里是反例（不该换），做成全局后，`远程实习 → 线上实习` 也被一起挡掉了。
但这明显是该换的。

⇒ **给 X1 的硬要求：`negative_aliases` 是词条级字段（term-scoped），表示「这个词条在此处的例外」，不是「全词表禁用词」。** 写进词表评审清单。

### 2. X4 和金标几乎是两批不同的词

70 个 X4 歧义词，和金标的 101 个别名只重叠 **1 个**（综述），和 101 个标准词只重叠 1 个（摘要）——覆盖率 **1.4%**。

所以 B 组（高风险词一律不换）对当前金标几乎没影响：只挡掉 1 处，精确率不变、召回掉 1 个点。
**不是 X4 没用，是 X4 覆盖的是「系统/模型/网络」这类通用词，而金标换的是考研/校园类词。**
X4 的价值要等长尾 query 才体现得出来。

### 3. 「二战」这类词，词级反例根本解决不了

金标第 3 行 `二战在家复习，数分怎么安排` 明确写了「二战歧义，需结合上下文，不替换」。

但同一批数据里，`二战考研怎么准备` 里的「二战」**是该换的**。同一个字符串，两种上下文，两个答案
——**任何词级黑名单都无解**，只能靠 X4 裁决表给出「什么上下文下换」。

⇒ 这就是为什么 X4 那 210 个裁决点必须做，而且要做成「触发条件」而不是「换/不换」二值。
⇒ 顺带发现：**X4 的 70 词里没有「二战」，但金标已经用它举证了歧义** —— 这是 X4 的漏收，需要补。

### 4. 金标本身有 3 处要修

| 行 | 问题 | 建议 |
|---|---|---|
| 3 | 反例写了「二战」，但金标的换词目标是「数学分析」，`二战` 是**别的词条**的别名 | 保留（这条恰好证明了上面的结论 3） |
| 20 | `思修的大题` 里「大题」被换成「主观题」，但 gold 只要求换「思修」，且 must_not 里没写「大题」 | 二选一：把「大题」加进 `must_not_replace`，或把「主观题」加进 `replace_to` |
| 32 | `秋招投简历` 里「简历」被换成「个人简历」，但 gold 只要秋招/春招 | 同上，把「简历」写进 `must_not_replace` |
| 2 | `二战考研怎么准备` 要求把「二战」换成「考研二战」，换完是「考研二战**考研**怎么准备」——**叠字** | 把替换跨度标成整段「二战考研」→「考研二战」，或改成不换 |

匹配器对这 4 条的处理是：第 2 行**主动不换**（叠字防护），第 20/32 行照换（数据没禁止），第 3 行照换（真误替换）。

> 注：这 3 处都是**标注口径**问题，不是组员能力问题。正因为事先跑了一遍，
> 才没有等到 B6 接入 CI 时才发现"金标自己对不上"。

## 四、给 X1 词表的硬要求（评审清单）

1. **`negative_aliases` 必须挂在具体词条下**，不能只交一份全局禁用词表（结论 1）。
2. 别名 / 反例用 `|` 分隔，反例里能写「更长片段」就别写单词——
   `二战考研` 比 `二战` 安全，因为前者不会误伤 `二战在家复习`。
3. 编码用 **UTF-8（可带 BOM）**，不要 GBK。
4. 一行一个 canonical；同一个人分头写出现同名行，loader 会合并别名，但**别指望它猜对**。
5. 长标准词（≥7 字，如「毛泽东思想和中国特色社会主义理论体系概论」）建议另给一个「检索用短名」，
   否则替换后 query 会膨胀。这一条等 X1 到货看数据再定。

# 追加：X4 裁决表（70 词 / 210 义项，本版自己填完）

产物：`data/vocab/adjudication.csv`（70 行，词级裁决）
　　　`data/vocab/adjudication_points.csv`（210 行，义项级依据）
　　　`ops/build_adjudication.py`（生成规则，可复核可复现）
　　　`core/query_enhance/ambiguous.py`（加载 + 按句生效）

## 1. 决策单位是「词」，不是「义项」

210 个义项**不是 210 个待决事项**，它们是 70 个词的依据。理由是：
「换 / 不换」这个二值对歧义词本身无意义——`栈` 换成什么？数据结构栈、函数调用栈、还是进程栈区？
**没有上下文就没有答案**。所以裁决是词级的三分类，义项只作为依据留档。

| 裁决 | 词数 | 含义 | 下游怎么用 |
|---|---|---|---|
| 禁止入表 | 37 | 本身就是标准术语，替换只会把正确说法改坏 | 进 `block_words()`，永远不许被换 |
| 禁止入表·需澄清 | 31 | 含日常义，替换必错，但用户可能真要问那个日常义 | 同上 + 生成追问句 |
| 可入表·有条件 | 2 | 有压倒性高频义项，靠搭配短语圈定 | 命中触发词才放行 |

判定规则写死在脚本里，不是拍脑袋：义项里出现「日常/生活」类场景 → 需澄清；全是学科术语 → 禁止入表；
极少数有压倒性高频义项的词进 `_OVERRIDES`，逐词写理由。

## 2. 触发条件用「搭配短语」，不是「学科标签」← 这是踩出来的

一开始想用学科标签当触发条件（「计算机」「AI」），做完发现**根本命中不了**：
X4 的 85 个学科标签里有一半是「编程」「科研写作」「计算机组成」这种用户不会说出口的词。

实测直接打脸：金标第 5 条 `跑模型要租显卡吗` 要求换成「模型训练」，
而 X4 判「模型」禁止入表 → 召回率从 99.0% 掉到 98.0%。

改成搭配短语后解决：`模型` 的触发词是 `跑模型|训练模型|模型微调|部署模型…`，
`综述` 的触发词是 `综述部分|写综述|论文|答辩…`。**搭配是用户会真的打出来的，学科标签不是。**

## 3. 接入后指标没变，但这个结论本身有价值

| 组 | 配置 | 精确率 | 召回率 | 反例误替换 |
|---|---|---|---|---|
| A | 按词表换 | 97.1% | 99.0% | 1 |
| **D** | **A + 裁决表（推荐上线）** | **97.1%** | **99.0%** | **1** |

A→D 完全持平。**不是裁决表没用，而是 X4 和金标几乎不重叠**（70 词 vs 101 别名只交集 1 个「综述」）。
裁决表的价值在另外两处：

- **评审闸门**：以后谁想往 `vocab_v1.csv` 里加「系统→操作系统」，这里会直接拦下并给理由。
- **澄清追问**（新能力，指标测不到）：94 条里有 **5 条**会触发追问，例如
  `数二不考概率…` → 「你说的「概率」是指：数学概率 / 日常可能性 / 成功或发生比率？」
  这比闷头换词更适合「歧义词」——用户点一下就行，换错一次要重新问一遍。

## 4. 三个待办（需要人处理，不是代码能解决的）

1. **8 个词的标注不可靠**：`缓存、框架、收敛、发散、综述、摘要、论点、论据` ——
   X4 的「常见使用场景」列标签数与义项数对不上（比如 3 个义项只写了 2 个场景），
   这 8 个词的裁决依据不牢，已在表里标了「需人工复核」。
2. **「二战」该不该换，需要林宝澄回答**：第 3 行 `二战在家复习，数分怎么安排` 的
   `must_not_replace` 写了「二战」，理由是「二战歧义，需结合上下文」。
   但「在家复习」已经排除了「第二次世界大战」这个义项，语义上就是「考研二战」。
   **我的判断是这条该换**（换成「考研二战在家复习」对检索更有利），
   但金标写着不换，所以现在指标上仍是 1 处误替换。这是个标注口径问题，不是匹配器 bug。
3. **X4 漏收「二战」**：金标已经在用它举证歧义，X4 的 70 词里却没有。建议补进 X4 并给上下文条件。

# 追加：B3 接口（`/api/query`）

产物：`api/query.py`（HTTP 层）　`service/enhance.py`（业务层 + 词表热加载）
　　　`tests/test_query_api.py`（14 条）　`core/config.py` 三个 `ENHANCE_*` 开关

## 1. 两个端点

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/query/enhance` | 预览一句话的增强结果 |
| GET | `/api/query/vocab` | 当前生效的词表 / 裁决表规模与文件 |

都要登录（挂 `Depends(get_current_user)`），都**不带尾斜杠**，
限流走 `quota.hit(uid)`（每用户每分钟 10 次，和 KB 预览同一档）。

## 2. 为什么业务逻辑在 `service/enhance.py` 而不在 `api/query.py`

因为 B4 要把同一件事接进聊天链路。写进 HTTP 层，worker / 聊天 / 预览就得各抄一份，
然后三份慢慢走偏。`service/daily.py` 当初也是这么分的（手动触发与定时触发共用一套）。

## 3. 字段契约（前端按这个接）

```json
POST /api/query/enhance   {"text": "综述部分怎么写才不像凑字数", "with_clarify": true}

{
  "original":  "综述部分怎么写才不像凑字数",       // ★ 展示与聊天记录只能用这个
  "retrieval": "文献综述部分怎么写才不像凑字数",   // ★ 只喂检索
  "changed":   true,
  "hits":      [{"raw": "综述", "canonical": "文献综述", "start": 0, "end": 2}],
  "skipped":   [],                                  // 命中但没换的原因，排障用，不展示
  "clarify":   ["你说的「综述」是指文献综述这一节吗？"],
  "vocab":     {"file": "temp_from_golden.csv", "terms": 101},
  "warnings":  []
}
```

**三条前端必须遵守的**：

1. **`hits[].start / end` 是在 `original` 上的下标**，直接 `original.slice(start, end)` 做高亮。
   **不要用 `raw` 去 `indexOf`** —— 同一个词在一句话里出现两次时，两次都会定位到第一个位置。
2. **展示永远用 `original`**。`retrieval` 只许出现在检索请求里，一旦渲染到界面上，
   用户会看到自己的话被偷偷改了，这是三个原则里最不能破的一条。
3. `clarify` 可能为空数组。有内容时它是一句可直接渲染的追问，不需要前端拼文案。

## 4. 三种输入边界（两种状态码，前端按 4xx 统一处理）

| 输入 | 状态码 | 说明 |
|---|---|---|
| `""` / 缺 `text` | **422** | pydantic 字段约束（`min_length=1`），到不了业务层 |
| `"   "` 纯空白 | **400** | 业务判断：`内容为空，没什么可校准的` |
| 超 `ENHANCE_MAX_CHARS`（默认 2000） | **400** | 文案带实际长度与上限 |

## 5. 词表热加载（这条决定了组员敢不敢改词表）

比对 `(路径, mtime_ns, size)`，变了才重读，**不重启进程**。
词表是组员一天改十几版的文件，每次改都要重启服务等于没人愿意改。

路径留空时自动挑：`vocab_v1.csv` → `temp_from_golden.csv`。
**X1 到货那天只需要把文件放进 `data/vocab/`**，不改 `.env`、不重启。

`vocab_dir()` 是函数不是模块级常量 —— import 时算死会让"谁先 import 谁决定路径"，
测试里已经踩过（全量跑时读到别人改过的 `DATA_DIR`）。

## 6. 裁决表是增强项，缺了不能把接口搞挂

`load_adjudication()` 文件不存在返回 `{}`，`preview()` 随即退化成「不做歧义拦截、不问澄清」。
理由：歧义拦截是锦上添花，它挂了不该连换词一起挂。

## 7. 测试（14 条，含两组反证）

| 组 | 覆盖 |
|---|---|
| 鉴权 | 两个端点匿名都要 401 |
| 不改展示 | `original` 逐字等于输入；`retrieval` 才是被替换的那份 |
| 下标 | 同一句两次出现同一词，两个 `start` 必须不同且都能切片 |
| strip 一致性 | 前后空格被去掉后，下标仍与返回的 `original` 对齐 |
| 反例 / 裁决 | 「二战考研」不换但 `skipped` 有原因；「综述」按搭配短语判 |
| 入参 | 空串 422、纯空白 400、超长 400（文案带长度与上限） |
| 词表版本 | `/vocab` 报出实际路径、词条数、裁决表三类计数 |
| 路由形态 | 带尾斜杠不许 3xx（线上曾因此把浏览器带到 `localhost:8000`） |
| 冒烟 | 随包词表能被解析器读（只断言非空，不断言词条数） |

**反证做过两组**（证明测试不是空的）：

- 把 `hits` 的 `start/end` 整体 +1 → `test_hit_offsets_index_original_string`
  与 `test_leading_whitespace_is_stripped_consistently` 双双失败。
- 把 `preview(text, body.with_clarify)` 写死成 `True` → `test_clarify_can_be_switched_off` 失败。

# 追加：B4 接进聊天检索链路

产物：`api/chat.py::_retrieval_query` / `_enhance_note`
　　　`service/enhance.py::enhance_for_retrieval`
　　　`core/config.py::ENHANCE_CHAT_ENABLED`（默认 1）
　　　`tests/test_query_enhance_in_chat.py`（11 条）

## 1. 接了哪两处，为什么必须两处一起接

| 位置 | 场景 |
|---|---|
| `api/chat.py` 图片理解模式 | 有图片附件、同时又挂了知识库时，会先检索再拼参考资料 |
| `api/chat.py` RAG 模式 | 正常问答的主链路 |

只改一处会造成「同一句话在两种模式下命中的片段不一样」。这类 bug 不报错，
只会让人觉得"有时候检索不准"，靠人工几乎发现不了。所以测试里直接断言
源码中 `_retrieval_query` 的调用点 ≥ 2 处，并且不允许残留直接调 `rewrite_query(req.question, ...)`。

## 2. 顺序：先补全指代，再换口语词（反了会漏词）

```
用户原话 "那它呢"
   ↓  rewrite_query（LLM，只在像追问时触发）
"高数那章怎么复习"          ← 注意：补出来的文本里才第一次出现「高数」
   ↓  enhance_for_retrieval（纯本地，零 LLM 成本）
"高等数学那章怎么复习"      ← 检索用
```

反过来先换词，`match()` 看到的还是"那它呢"，一个词都换不出来。反证做过：
把两行调换，`test_rewrite_runs_before_enhance` 立刻红。

## 3. 三条硬约束（每条都有测试钉着）

1. **展示不改**：`_retrieval_query` 只返回检索用文本，`req.question` 一个字都不动。
2. **开关能当场关**：`ENHANCE_CHAT_ENABLED=0` 退回"只有改写"的旧行为，不用改代码。
3. **词表坏了不许把聊天搞挂**：`enhance_for_retrieval` 吞掉所有异常、原样放行。
   词表是组员每天在改的文件，删一列就能让 `load_vocab` 抛 `ValueError`。
   预览接口红着脸报错是对的（谁改坏的谁立刻看见），聊天挂掉是灾难。

降级时**会打一次 warning**（`[检索词增强] 词表加载失败…`），只打一次：
不设这个标志，日志会被同一行刷满，真问题反而被淹掉。
静默降级等于"接了跟没接一样却没人知道"，这个必须留痕。

## 4. 状态条：只发一条

以前是「已结合上下文改写检索词：xxx」。现在把两件事合成一句：

```
已结合上下文改写，按规范术语校准（高数→高等数学），检索词：xxx
```

理由：状态条是**覆盖式**的，连发两条用户只看得到最后一条，第一条等于白发。
替换超过 2 处只报前 2 个 + 总数，避免状态条刷成一整段。

## 5. ★ 影响面实测（这条决定上线后要不要留观察期）

同一份代码，两批提问，被改动的比例差了两个数量级：

| 样本 | 条数 | 检索词被改动 | 平均替换处数 |
|---|---|---|---|
| 金标集（模拟学生口语） | 94 | **93（98.9%）** | 1.11 |
| 本地历史真实提问（技术类） | 58 | **0（0%）** | 0 |

例（金标集）：

```
二战在家复习，数分怎么安排   → 考研二战在家复习，数学分析怎么安排
跨考计算机要提前多久准备     → 跨专业报考计算机要提前多久准备
择校到底看排名还是看地域     → 院校选择到底看排名还是看地域
```

**怎么读这两个数**：

- 98.9% 说明当前词表**就是照着学生口语写的**，对上口语提问时几乎每句都会变。
- 0% 说明本地那 58 条技术提问（"帮我解释一下向量检索的原理"）本来就用的是
  规范术语，词表里没有可换的词。**0% 不等于"没接上"**，别拿它当接失败的证据。
- 真实用户落在两者之间，取决于他们怎么说。**上线后要看真实提问的改动率**，
  而不是看这两个数。如果多数请求都在被改，说明词表选词与真实语料有偏差，
  这时应该先改词表，不是先调匹配器。

**回退方式（不用改代码）**：`.env` 写 `ENHANCE_CHAT_ENABLED=0` 后重启后端，
检索立刻回到旧行为；`/api/query/enhance` 预览接口不受这个开关影响，仍然可用。

## 6. 还没验证的（诚实列出）

- **检索质量本身没有对照过**。上面统计的是"检索词变了多少条"，不是"命中片段的
  relevance 变好了多少"。要回答后者需要同一批问题、同一个知识库，跑替换前/后两遍
  检索再人工比对 top_k——这一步要烧 embedding 且需要人工判分，没做。
  在 X1 正式词表到货、且词表扩到 300+ 词之后再跑才有意义（现在 101 词，
  对照的噪声大于信号）。
- 图片理解模式的 status 帧没发（那个分支已经在"图片理解模式"状态里，
  再叠一条会让用户以为出了岔子），只静默换词。


## 2. 三条原则怎么落到界面上

| 原则 | 界面上的具体形态 |
|---|---|
| 可见 | 输入停顿 700ms 自动出现，明说"几处"，展开能看到原话与检索词两行对照 |

| 不改展示 | 界面下方那行小字："只改检索，你发出去的话和聊天记录都不变" |

第三句不是装饰。用户最怕的就是"你偷偷改了我的问题"，这句话必须一直在。

## 3. 四个刻意决定（都是踩过才知道的）

**① 浮层，不占布局。** 锚点 `.qe-anchor` 高度为 0，面板绝对定位向上弹出。
一开始做成输入框上方的一个普通 div，结果提示条出现/消失会把输入框顶下去 30px——
打字时输入框上下跳是最烦的。探针里直接断言 `.input-row` 的 `getBoundingClientRect().top` 前后不变。

**② 高亮是实线下划线，不是淡底。** 第一版用 `--accent-soft`（alpha .12）当底色，
深色主题下几乎看不见。这个组件的**全部价值**就是让用户看见哪几个词被换了，
看不见等于没做。改成 `border-bottom: 1.5px solid var(--accent)` + 极淡金底。

**③ 只在会检索的模式出现。** `rag` / `hybrid` / `auto && 已绑库`。
`llm` 模式不检索、`agent` 走工具调用，在它们下面提示换词是纯噪音。
判断条件与后端 `_pick_mode` 保持一致。

**④ 请求失败一律静默。** `lib/api.ts::previewEnhance` 吞掉 429 / 401 / 超时。
这是"每打一句话就可能跑一次"的辅助能力，一旦弹红字，用户会以为聊天坏了，
而实际换词只是增益。唯一的例外是真正的 bug（渲染异常）——那由 React 抛。

## 4. 一个 React 19 的坑

第一版在 effect 里用 `setResult(null)` 清理过期结果，`eslint` 直接报错：

```
error  Calling setState synchronously within an effect can trigger cascading renders
       react-hooks/set-state-in-effect
```

改法不是加 `eslint-disable`，而是换数据形状：**结果连同"它是哪句话的结果"一起存**。

```tsx
const [state, setState] = useState<{ text: string; data: EnhanceResult } | null>(null);
// 渲染时三件事对不上就整个不渲染：
if (!state || state.text !== q || q === dismissed) return null;
```

文本一变，`state.text !== q`，自动失效，一个 setState 都不用发。

# 追加：把「替换」改成「追加」（2026-10-24，修 X2 暴露的病句）

产物：`core/query_enhance/matcher.py`（`retrieval_text` / `_already_said`）
　　　`service/enhance.py`（`preview` 新增 `added`）
　　　`api/chat.py`（状态条措辞）
　　　`frontend/src/components/chat/QueryEnhance.tsx` + `styles/enhance.css` + `lib/types.ts`
　　　`ops/eval_enhance.py`（新增「原话被改写」指标）
　　　`tests/test_query_enhance.py`（+5 条，含 X2 全量护栏）

## 1. 起因：142 条真实问法把方案打穿了

X2 验收（`docs/验收记录_2026-10-24_X2.md`）把刘立轩的 142 条真实问法塞进换词器，
**32 条触发增强，其中 12 条变成了病句**：

| 原话 | 替换式的输出 | 错法 |
|---|---|---|
| 文献综述怎么写才有逻辑 | **文献文献综述**怎么写才有逻辑 | 叠字 |
| 学分绩点怎么算 | 学分**平均学分绩点**怎么算 | 替换点吞掉原字再还一个 |
| 查重率多少算安全 | **重复率检测率**多少算安全 | 术语自带「率」，与原字撞车 |

而此前用金标 94 条测了两天，四个指标一直是 95.7% / 97.1% / 99.0%，**一条都没报**。

## 2. 为什么不补 heuristic

第 1 条（叠字）可以补一条判断，只影响那一条。
但第 2、3 条补不住：**2 字口语词换成 5–6 字术语，替换后必然与原句相邻的字重新组合**。
`查重`+`率` → `重复率检测率`、`学分`+`绩点` → `学分平均学分绩点`。
词表一扩（X1 要到 300+ 词），这类碰撞只会更多，排除法追不上。

## 3. 修法：OR 扩展（原话 + 追加术语）

```
高数怎么复习
  ↓ 识别：高数 → 高等数学
检索文本：高数怎么复习 高等数学
          └──── 原话，一字未动 ────┘ └─ 追加 ─┘
```

`retrieval_text = original + " " + " ".join(added_terms)`。术语串去重、保持出现顺序
（同一句话任何时候生成的串都一样，A/B 与缓存才可信）。

这是 query expansion 的标准做法——**同义词扩展是 OR，不是替换**。之前用替换，
本质上是把「扩展」实现成了「改写」。

## 4. 一条新的不变量，比原来强得多

```python
assert r.retrieval_text == q or r.retrieval_text.startswith(q + " ")
```

原来只有 `display_text == original`（展示不改），检索侧是自由的。
现在**整条检索文本都以原话开头**，所以「增强把用户问题改坏」在结构上不可能发生。
`hits[].start/end` 也因此在这条文本上同样有效，前端不用做偏移换算。

## 5. 一个必须写下来的发现：旧指标对病句是瞎的

改动后重跑 `ops/eval_enhance.py`，四个数**一位没变**：

```
逐条全对 90/94 = 95.7%   精确率 97.1%   召回率 99.0%   反例误替换 1
```

因为 `evaluate()` 比的是 `r.canonicals`（识别了哪些词），**根本不看这些词怎么拼回去**。
所以「97.1%」这件事从来没证明过句子通顺。这解释了为什么替换式能带着 12 条病句活两天。

**修法**：新增第五个指标「原话被改写」——检索文本不以原话为前缀的条数，必须为 0。

反证（把 `retrieval_text` 临时退回替换式）：

```
原话被改写    93  ❌ 增强不该动用户的原话
exit=1
```

金标 94 条里有 93 条被改写。**如果昨天就有这个指标，替换式根本过不了 CI。**

## 6. 顺带修掉的一个方向

`_adjacent_already_standard` 原来只判两个方向：别名前面是标准词的**后缀**、
别名后面是标准词的**前缀**。漏了第三个：**别名前面是标准词的前缀**（`文献` + `[综述]`）。

改成追加式后这个函数改名为 `_already_said`，职责也变了：不再是"救语法"，
而是"别把同一个术语塞两遍"。判据变成三条：

```python
if canonical in query:                    # 原话已含标准词 → 不追加（修 106 行）
    return f"原话里已有标准词「{canonical}」，不必追加"
# 以下两条保留：前文已含词尾 / 后文已含词头
```

## 7. 前后端契约变更

| 位置 | 变更 |
|---|---|
| `GET/POST /api/query/enhance` | 新增 `added: string[]`（去重后的术语）；`retrieval` 语义从"替换后的句子"变成"原话 + 术语" |
| `POST /api/chat/stream` 状态条 | 「按规范术语校准（高数→高等数学）」→「补充规范术语检索（高数→高等数学）」 |

| 前端提示条 | 「会把 N 处口语词换成规范术语」→「会额外按 N 个规范术语检索」，N 改为去重后的术语数，与 chips 一一对应 |

`hits[].start/end` 契约不变，仍在 `original` 上。
