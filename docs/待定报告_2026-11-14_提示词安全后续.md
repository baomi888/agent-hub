## 一、待你拍板（会影响部署形态，不适合我单方面决定）

### D-1 L4 真实审批在多 worker 部署下失效 —— **阻断 L4 上线**

**现状**：`core/approval_store.py` 的 `_PENDING` / `_TOKENS` / `_DEDUPE` 全是
**进程内** dict（文件头写明"刻意不持久化"）。而生产是 `uvicorn --workers N`
（`deploy.sh::detect_workers` = `min(vCPU,4)`，内存 < 3 G 封顶 2）。

**断点位置**（三个请求可能落在三个不同 worker）：

| 步骤 | 落点 | 失败表现 |
|---|---|---|
| 工具触发 pending | worker A | — |
| 用户点确认 → `POST /api/chat/approval` | 任意 worker | 概率 (N−1)/N 返回 **404** |
| 重发 `/api/chat/stream` 带 token | 任意 worker | `consume` 失败 → **工具再次被拒** |

N=4 时端到端成功率约 **1/16**。也就是说：**L4 现在只有 `WORKERS=1` 才真的能用。**

**为什么没直接做**：三条路的成本与影响面差别很大，且会改部署形态。

| 选项 | 改动 | 代价 | 风险 |
|---|---|---|---|
| **A. 落 SQLite**（复用 `core/session.py` 已有连接） | 加两张表 + 迁移，`issue_token`/`consume` 改读写 DB | 中（约 150~200 行 + 测试） | 审批路径引入 I/O；需处理 TTL 清理 |
| **B. 先锁 `WORKERS=1`** | `.env` 改一行 | 极低 | **并发能力回退**（10-20 压测结论作废）；8 核机器等于只用 1 核 |
| **C. 反代一致性哈希** | nginx `hash $cookie_xxx consistent` 或按 uid 哈希 | 低 | 重启/扩缩容即失效；伪粘性，不推荐当终态 |

**建议**：走 A。理由：① approval 是**低频**事件（只有 `download_file` 一个工具需要），
落 SQLite 的额外 I/O 完全可接受；② 现成连接池与建表逻辑都在 `core/session.py`，
不需要新依赖；③ B 会把已落地的 P0 并发三件套打回去。

**验收口径**（写进 PR 前必须满足）：
1. `--workers 4` 下跑通「触发 → 点确认 → 重发」全链路（不同 worker 也要成）；
2. token 仍然一次性：同一 token 二次 `consume` 必须 False；
3. 过期清理：`_prune` 等价逻辑改成 SQL 条件删除，不留垃圾行；
4. 不做持久化承诺（重启后 pending 作废是**预期行为**，要在文档里写清）。

### D-2 `dev → main` 合并 —— 没有做

**现状**：`origin/main` 领先 dev 157 个提交，dev 领先 6（现在会变成 7）。
`git merge-tree` 干跑确认 **3 处内容冲突**：

```
CONFLICT (content): agent/tools.py
CONFLICT (content): api/chat.py
CONFLICT (content): core/config.py
```

**为什么没做**：这三处正好是接线的关键点（工具装配 / 流式出口 / 开关表），
main 在分叉后又改过 `api/chat.py` 5 次、`core/config.py` 6 次。合并不是 fast-forward，
需要人工裁决，且项目规范要求 `main` 走 PR + approve（不能直推）。

**建议顺序**：
1. 先在一台新 worktree 上做合并，逐块解冲突，**每解一块跑一次全量 pytest**；
2. 特别注意 `api/chat.py` 里 agent 流式循环的 `with tool_guard.guard_scope():`
   不能被 main 的旧版本覆盖回去（这是 C-001 的修复点，冲突时最容易丢）；
3. 开 PR 到 main，说明"合入四层防护 + 本次修复"，附全量测试结果。

## 二、技术债（不阻断上线，按需再做）

### D-3 低慢分段导出对 L3 不可见（原 M-005）

**现象**：指纹长度 24、canary 27 字符。模型每次只吐 10 个字，
**任何一段都短于窗口** → 恒 pass。分 30 轮就能拿完 300 字提示词。

**为什么没做**：这是**新功能**不是修 bug——要引入"跨轮累积缓冲区"
（同一会话最近 N 轮的 assistant 输出拼起来做指纹检测），涉及会话级状态存储，
和 M-003 的存储改造是同一类问题，建议一起做。

**最小实现**：`LeakFilter` 已经维护 `_raw_tail`，只要把它的初始值从"会话历史最后 N 轮"
恢复即可；关键是决定状态存哪（进程内 = 多 worker 失效，DB = 与 M-003 同源）。

### D-4 `SHORT_FINGERPRINTS` 是硬编码整句（原 m-006）

**现象**：`"你是一个智能问答助手"` 这类 5 条整句写死在代码里。
`core/agent_prompts.py` 改一个字，这 5 条就静默失效——不报错、不告警、测试也不会红
（除非专门断言子串仍在）。

**建议**：改成"从 `AGENT_SYSTEM_PROMPT` / `RAG_SYSTEM_PROMPT` / `PLAIN_SYSTEM_PROMPT`
各自取首句"派生，或在 `_check_invariants()` 里加一条断言：
"每条 SHORT_FINGERPRINTS 必须仍是某条受保护文本的子串"。
后者改动更小、收益更大（把静默失效变成启动即失败）。

### D-5 W5 工作流把 LLM 产出标成「知识库」（原 m-004）

**位置**：`hybrid/workflow.py::render_template(tag_shared=True)` 一律用
`data_boundary.SOURCE_KB` 包装上游节点产出。

**问题**：LLM 生成内容不是知识库资料，标签口径不准；会污染"来源"语义与后续统计，
也可能让模型误以为是已核实的检索结果。

**建议**：`_MARKERS` 增加 `SOURCE_NODE`（如【资料开始·上游产出】），
`render_template` 用它；改动小，但要同步 `data_boundary.clause()` 的标签清单
（它已经是从 `_MARKERS` 生成的，所以只改一处）。

### D-6 指纹匹配换 Aho-Corasick（原 i-003）

**现状**：建库按步长 6 切片进 frozenset，匹配按步长 1 滑动 → 命中率天然 1/6，
每个位置白查 5 次。当前每帧 0.46 ms，已可接受。

**收益**：建库 O(总长)、匹配 O(n + 命中数)，且能直接返回"命中的是哪条受保护文本"，
`_shingle_labels` 表可以整体删掉。

**做法**：`pyahocorasick` 是 C 扩展（需加依赖）；纯 Python 实现约 120 行但会慢于
现在的 frozenset 方案。**建议先评估依赖成本，不急。**

### D-7 `GuardState` 改走 `RunnableConfig.configurable`（C-001 的加固遗留）

**现状**：C-001 的修复是"在父上下文开 `guard_scope`"，靠纪律保证。
一旦将来有人在别处直接调工具、或 LangChain 换了执行模型，这个约定会再次静默失效。

**更稳的做法**：把 `_GuardState` 塞进 `configurable`（`turn_id` / `owner_id` 已经走那条路），
彻底不依赖 contextvars 传播。改动面中等，收益是"防未来踩坑"，不是修当前 bug。

## 三、需要你确认的「已接受差异」

这三条不是缺陷，是**刻意的取舍**，但会影响线上表现，值得你点头：

### E-1 `_normalize` 的整串 NFKC 会合成组合记号

整串 `unicodedata.normalize("NFKC", s)` 会把「基字母 + 组合记号」（`e` + U+0301）
合成一个字符 `é`；原来的逐码点版本不会。对检测而言合成后更规范、更难绕过，
中文语料上两种写法输出完全一致（有等价性测试）。

**影响**：仅影响含组合音的西文文本（如越南语、带声调拼音）。**判断：可接受。**

### E-2 40 字以下的"变形"片段召回约 45%

索引按步长 6 切片：片段越短，刚好对齐到索引窗口的概率越低（约 1/6 ~ 1/2）。
80 字以上是 100%。这与原设计一致（短片段本来就只有 1/6 概率命中），
不是本次修复引入的退化。

**判断**：可接受。若将来要求"20 字也要抓住"，需要把索引步长降到 2~3（内存 ×2~3）。

### E-3 核心 system prompt 不参与 LRU，可用池实际是 61 条

`_PINNED_LABELS` 固定了 3 条核心 prompt。`_MAX_PROTECTED` 仍是 64，
所以非核心（场景变体 / 工具描述）最多 61 条。

**判断**：可接受。若场景数量涨到 60+，需要调大 `_MAX_PROTECTED`
（代价是指纹库重建变慢——现在有切片缓存，压力已小很多）。

## 四、回滚与验收

**开关**（`.env`，全部默认开启；`0` 关闭）：

| 开关 | 作用 | 关闭后果 |
|---|---|---|
| `PROMPT_LEAK_GUARD_ENABLED` | L1+L3 总闸 | 输入拦截与输出过滤全关 |
| `PROMPT_LEAK_INPUT_GUARD_ENABLED` | 只管 L1 | 输出去兜 |
| `PROMPT_LEAK_OUTPUT_GUARD_ENABLED` | 只管 L3 | 输入去兜 |
| `PROMPT_LEAK_DENSE_MIN_HITS` | dense 判 hard 的窗口数（≥2） | 调小更早拒答 |
| `INSTRUCTION_DATA_SEPARATION_ENABLED` | L0 资料边界 | 回到改造前 |
| `TOOL_APPROVAL_ENABLED` | L4 总闸 | 危险工具直接执行 |
| `TOOL_APPROVAL_REAL_CONFIRM_ENABLED` | 真实 token vs 旧确认串 | 回到"纸糊审批" |
| `TOOL_REPEAT_GUARD_ENABLED` | 重复调用看门狗 | 允许无限同参重试 |

> 注意：`TOOL_APPROVAL_*` 关掉等于**取消人类确认**，只在排障时短时使用。

**回归命令**：

```bash
python -m pytest -q                       # 期望 888 passed / 1 skipped
python -m pytest tests/test_prompt_security_hardening_2026_11_14.py -q   # 22 passed
```

**上线后必须观测的三个指标**（`core/metrics.py`）：
- `prompt_leak_blocked{stage=input|output}` —— 突增说明拦截过严或真被攻击；
- `chat_leak_soft` —— soft 档计数，持续增长说明有人系统性试探；
- `tool_guard_approval_wait` —— L4 待确认次数；若与用户实际点击数差异大，
  说明 D-1（多 worker）已经在影响线上。
