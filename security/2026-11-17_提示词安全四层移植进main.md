## 三、`api/chat.py` 的三处手改（唯一必须动脑的地方）

1. **`with tool_guard.guard_scope():` 包住 agent 流式循环（C-001 真因）**
   工具是同步函数，LangChain 走 `run_in_executor`：它 `copy_context()` 后在副本里跑，
   副本里的 `ContextVar.set()` **不回传父上下文**。不套这一层，`banned` /
   `call_counts` 在每个线程副本里各自新建，于是 `retryable=False` 的封禁永远不生效、
   重复调用看门狗永不触发 —— 每次用户触发重试都在白烧额度。

2. **`leak_guard.StreamGuard` → `prompt_security.LeakFilter`**（`_stream_llm` 与 agent 路径各一处）
   新过滤器多一层"检测视图"（去标点/空白后匹配），并带 `flush()` 收尾判定。

3. **入站判定换成 `detect_prompt_extraction` + `ChatRequest.question = max_length 8000`**
   长请求会阻塞事件循环。

## 五、L4 审批：**故意不上线**

`0052454` 自带的《待定报告》第一节就写明 D-1：`core/approval_store.py` 的
`_PENDING`/`_TOKENS` 是**进程内 dict**，而生产是 `uvicorn --workers min(vCPU,4)`。
N=4 时"触发 → 点确认 → 重发"端到端成功率约 **1/16**（大概率 404）。
报告的原话是「阻断 L4 上线」。

处置：生产 `.env` 置 `TOOL_APPROVAL_ENABLED=0`，即 `download_file`
（唯一 `needs_approval` 的工具）行为与 main 今天**完全一致**，不多一次往返。
其余三层（L0 分离 / L2 指纹 / 重复调用看门狗）全部按默认开启。
D-1 的正解是报告里的方案 A（落 SQLite），属独立一批。
