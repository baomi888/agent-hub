## 1. 问题：面板被我们自己的验证流量骗了

2026-11-15 的面板上写着「**3 个活跃真实用户，人均 100 次调用**」。查下去发现：

| 账号 | 区间调用 | 对话次数 | 会话数 | 消息数 | 客户端 |
|---|---|---|---|---|---|
| A | 136 | 0 | 0 | 0 | HeadlessChrome |
| B | 147 | 0 | 0 | 0 | HeadlessChrome |
| C | 33 | 0 | 0 | 0 | HeadlessChrome |

三条证据独立指向同一件事：**它们从没对话过**（不是"今天没聊"，是历史会话/消息总数为 0）；
出口 IP 全是同一家宽；一次进页会扇出 6~11 个读接口，136 次 ≈ 20 次页面加载。

所以「人均 100 次」不是使用深度，是**页面加载次数**。根因有两层：

1. **判据错**：`real` 桶只要求"账号存在、没被标内部"，于是任何脚本带着登录态跑一遍界面
   就算"活跃真实用户"。页面扇出天然能造出这个数。
2. **采集层不区分自动化**：我们自己的截图/取证脚本和真人走同一批接口、同一个账号，
   日志里长得一模一样。

## 2. 任务三：口径改造（判据换成"有没有发起过对话"）

### 2.1 新的五桶

| 桶 | 判定（按顺序，先命中先落） | 含义 |
|---|---|---|
| `anonymous` | `uid` 为空 | 身份探测（401）、注册/登录本身、公开页 |
| `orphan` | `uid` 非空但 `users` 里查不到 | 账号已删，日志还在 |
| `internal` | `al.internal = 1`，或 `is_internal = 1`，或 uid 在管理员名单 | 自测号、管理员、自动化验证流量 |
| `real` | 账号正常，且**区间内至少 1 次 `POST /api/chat/stream`** | 真的在用产品 |
| `passive` | 账号正常，但区间内只有读接口 | 登录了只翻页面 |

恒等式：`全量调用 = real + passive + internal + orphan + anonymous`。

### 2.2 为什么用"对话"当判据

对话是唯一**无法被页面扇出伪造**的行为：它会真的调用模型、扣额度、落消息。
其余读接口一次进页就会打 6~11 个，把它们当"使用"等于把"页面刷新"当"用户在干活"。

### 2.3 两个实现细节（都会让数字悄悄错，所以写下来）

1. **对话窗口必须用整个区间，不是当天**。否则"昨天聊、今天只翻列表"的人，今天的调用会从
   `real` 里消失，而卡片上的 `real` 是按区间算的 —— `sum(series) == real` 立刻对不上。
2. **`calls.chat` 是 `real` 的子集，不是第 6 个桶**。页面上单独标"其中对话 N 次"，
   不与五桶相加；相加会凭空多出一块，用户一减就发现账不平。

### 2.4 顺带纠正的两个指标

- `users.total` 原标签是「真实账号」，其实是"未标内部的注册账号数"（含注册了从没聊过的）。
  改名「注册账号」，另加 `users.chatted` =「用过对话的真实账号」——这个才是真实账号数。
- 人均调用仍然含页面扇出（数值天然偏大），所以卡片上并列显示"其中对话 N 次"，
  让人能立刻判断这个人均是"聊出来的"还是"刷页面刷出来的"。

## 3. 任务二：`X-Verify` 自动化流量打标

### 3.1 判据：声明 + 身份，缺一不可

| 条件 | 是否打标 |
|---|---|
| `X-Verify: 1`，uid 是内部账号 / 管理员 | ✅ |
| `X-Verify: 1`，uid 是普通用户 | ❌ **忽略** |
| `X-Verify: 1`，未登录 | ✅（它本来就在 anonymous 桶，打标只为可辨认） |
| 没这个头 / 值不是 `1` | ❌ |

**为什么普通用户发的不算**：这个头是客户端自报的。若只看头，任何真实用户加一行
`X-Verify: 1` 就能把自己从看板上抹掉 —— 那不是清洗数据，是给了个把证据藏起来的开关。

**为什么打在请求上而不是账号上**：同一个内部账号里既可能是人点、也可能是脚本在跑
（截图/取证都用同一份登录态）。按账号排除会把真人使用一起抹掉；只按 UA 排除又能被伪造。

### 3.2 实现

| 位置 | 改动 |
|---|---|
| `api_call_logs` | 新增 `internal INTEGER NOT NULL DEFAULT 0`；老库用 `PRAGMA table_info` + `ALTER TABLE` 补齐 |
| `core/verify_tag.py` | 判定 + 内部账号集合（60s 缓存，标记后 `invalidate()` 立即失效） |
| `main.py` | `collect_api_call` 中间件读头、写标记（`call_next` 之后才拿得到 uid） |
| `api/admin.py` | 标记/取消内部账号后失效缓存（否则那一分钟内的验证流量还会计入真实用户） |

**迁移必须有的原因**：`CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做。漏了 `ALTER`，
升级后所有写入都会因为列不存在而失败 —— 而 `flush()` 吞异常（统计不能影响业务），
表现是「看板突然不再更新」，没有任何报错。这条已有测试守着。

### 3.3 线上 A/B（同一账号、同一接口、相差 1 秒）

```
带 X-Verify: 1  →  /api/auth/me/  200  internal=1
不带           →  /api/auth/me/  200  internal=0
```

截图脚本加上这个头跑一轮，库里新增 9 条 `internal=1`（其中 5 条带管理员 uid、
4 条未登录），**没有一条进 `real` 桶**。

## 4. 数据来源与统计口径（页面底部也有同样一份）

### 4.1 数据来源

- 表：`api_call_logs`（SQLite，线上 `/root/data/sessions.db`）
- 写入方：FastAPI 中间件 `collect_api_call`，每个 `/api/` 业务请求一行
- 字段：`ts` / `path`（**路由模板**，不是真实 id）/ `method` / `status` / `dur_ms` / `uid` / `internal`
- 保留：90 天，worker 每日清理；只记 `/api/`，`/health`、`/api/metrics`、`/api/admin/*` 排除
- **没有任何模拟数据、占位数据、缓存快照**：每次请求现算，页面刷新就是重新查库

### 4.2 统计口径

| 指标 | 算法 |
|---|---|
| 真实用户调用 | 满足"区间内至少 1 次对话"的账号产生的**全部**调用（含其读接口） |
| 其中对话 | 上述子集中 `path = /api/chat/stream` 的条数（子集，不与五桶相加） |
| 活跃真实用户 | 上述账号在区间内出现过的去重个数 |
| 人均调用 | 真实用户调用 ÷ 活跃真实用户 |
| 回访用户 | 其中 ≥2 个自然日有调用的人数（`days=1` 时算不出，显示「—」） |
| 注册账号 | `users` 里 `is_internal = 0` 且非管理员，**快照**，不随区间变 |
| 用过对话的真实账号 | 日志保留期内存在 `chat/stream` 且非内部/非管理员的账号数 |

对账 SQL 见 `docs/数据看板_2026-10-27/口径与数据字典.md` §2.8.6。

## 7. 仍未解决 / 需要知道的

1. **`calls.internal` 会很大（本次 76.8%）**。因为管理员账号（我们自己的截图、看板刷新）
   被正确归为内部。这不是 bug，但看"真实用户占比 1.2%"时要知道分母里全是自己人。
2. **`users.chatted = 61` 与「活跃 4」并存**：61 是"近 90 天聊过"，4 是"近 7 天聊过"，
   口径不同，页面上已分别标注。里面仍可能混着未标记的旧测试号。
3. **自动化脚本需要自己带头**。本批只保证"带头就一定能被正确归桶"，
   `.workbuddy/` 下的历史截图脚本没有逐个改（数量太多），新脚本按 §3 的方式加一行头即可。
