## 1. 事实：污染到底在哪

用 nginx `baomi-access.log` 按 UA 分类（11-14 23:00 这一小时）：

| 客户端 | 请求数 | 占比 |
|---|---|---|
| `HeadlessChrome`（CDP 截图脚本） | 2,877 | 85.6% |
| 普通浏览器 | 384 | 11.4% |
| 脚本（curl / python） | 102 | 3.0% |

来源 IP 只有一个（`112.96.232.103`），打的接口覆盖全站：
`/api/kb`、`/api/kb/favorites`、`/api/kb/public`、`/api/sessions`、`/reminders`、
`/settings`、`/delegate`、`/report`、`/` —— 是逐页翻的截图扫描，不是人在用。

同一个 IP 既是**真人**（`苞米呀` 的日常使用）又是**脚本**（我的截图），所以**按 IP 区分不了**。
UA 是请求里唯一不会被脚本忘掉的东西。

## 2. 根因：第一层判据依赖"脚本自觉"

上一版的自动化判据是 `X-Verify: 1` + 身份可信。它有个致命前提：**脚本得记得带头**。
而截图脚本走的是浏览器导航（CDP 打开页面），**加不了自定义请求头** —— 于是 100% 漏标，
`internal` 全是 0，这些调用就散进了各个桶，谁也说不清。

同时 `api_call_logs` 当时**不存 UA、不存 IP**，事后想复核只能回头翻 nginx 日志按秒匹配，
而日志只留 14 天。这是这次最贵的教训：**采集时省下的一个字段，排查时要花一天**。

## 3. 修复（三层）

### 3.1 采集层：多存一个 `client`

`api_call_logs` 新增 `client TEXT NOT NULL DEFAULT ''`，取值 `browser` / `headless` /
`script` / `''`。只存**分类**、不存 UA 原文 —— 与"不记 UA"的隐私取舍一致，
但它能回答"这条调用是谁打的"。索引 `idx_apilog_client_ts`。

老库用 `PRAGMA table_info` + `ALTER TABLE` 补列。**这一步不能省**：
缺列会让整批 `flush` 失败，而 flush 吞异常 —— 表现为"看板突然不再更新"，没有任何报错。

### 3.2 判定层：UA 自动识别（不再依赖脚本配合）

`core/verify_tag.py` 新增 `classify_ua()`：

| UA | 判定 | 是否算自动化 |
|---|---|---|
| 含 `headless`（`HeadlessChrome` / `HeadlessFirefox`） | `headless` | ✅ |
| 不以 `mozilla/` 开头且含 `curl/`、`python-requests`、`go-http-client`、`okhttp/` … | `script` | ✅ |
| 以 `mozilla/` 开头（含 App 内置 WebView、手机浏览器） | `browser` | ❌ |
| 缺失 | `''` | ❌ |

**UA 判定不要求身份**：判据是"用什么客户端发的"，不是"谁在发"。若也要求身份，
普通账号的脚本流量永远洗不干净 —— 这正是要解决的问题。

刻意的取舍：**真实用户自己写脚本刷**也会进 `internal`。为了不把它藏起来，
`client` 一起入库，面板上把自动化调用按来源单列（"无头 M / 脚本 K / 来自 P 个账号"），
安全审计仍然看得见谁在用什么刷。**这不是"把证据洗掉"，是把证据归位。**

判错方向也是刻意的：**宁漏不误**。把真人判成自动化，他会从"真实用户"里消失且没人发现；
把自动化判成真人，只是数字偏高，下次复查还能抓出来。

### 3.3 历史层：用 nginx 日志回填

`tools/backfill_auto_calls.py`。库里是路由模板（`/api/sessions/{sid}`），日志里是真实路径
（`/api/sessions/9f3c…`），先归一成"形状"（`{xxx}` / uuid / 纯数字 / 长 hex → `*`，
去尾斜杠），再按 `(形状, 秒±1)` 对齐。

标记条件加严：**该 `(形状, 秒±1)` 上出现过自动化 UA，且没有任何浏览器请求**。
同秒既有脚本又有真人时一律不标（分不清是哪条，宁可数字偏高）。

实测：

| 轮次 | 窗口 | 可回填 | 无头 | 脚本 | 同秒冲突放弃 |
|---|---|---|---|---|---|
| 第 1 轮 | 7 天 | 8,438 | 8,206 | 232 | 44 |
| 第 2 轮（修 UTC/东八区天边界后） | 15 天 | 1,946 | 1,605 | 341 | 65 |

合计 10,384 条。每轮写库前自动 `shutil.copy2` 备份：
`/root/data/sessions.db.bak-backfill-20261115-165839`、`…-170912`。

**工具自己也踩过一个坑（被我新写的单测抓到）**：天序号用了 `ep // 86400`（UTC 天），
而 `wanted_days` 是东八区的天 —— 08:00 之前的请求会落到前一天。生产上第一轮之所以
"看起来对"，是因为前一天仍在 7 天窗口内；**窗口首日 00:00–08:00 的行会被静默漏掉**。
改成 `(ep + 8*3600) // 86400`。

## 4. 口径（现在的唯一解释）

五桶仍是互斥且穷尽，`internal` 的判定多了一个来源：

```
internal ← al.internal = 1                       （X-Verify 打标）
         ← al.client ∈ {headless, script}        （UA 自动识别）★ 新增
         ← users.is_internal = 1                 （人工标记的内部账号）
         ← uid ∈ ADMIN_UIDS / ADMIN_USERNAMES    （管理员）
```

`real` 同时要求：账号正常、`internal = 0`、`client` 不是自动化、**区间内至少 1 次对话**。
`_real_where`（趋势/明细/按功能）与 `_bucket_counts` 的 CASE（五桶）**必须用同一组取值**，
只改一处会让"被 real 排除的调用"在桶里凭空消失。

## 6. 局限（必须知道，别当它不存在）

1. **回填只覆盖 nginx 日志保留期（11-01 起）**。30 天视图里 10-17~10-31 的历史
   没有 UA 可查，那一段的 `internal` 仍偏低。要更正只能靠日志之外的证据，做不到。
2. **直连 `127.0.0.1:8000` 的请求不进 nginx 日志**，回填看不到（也是审计盲区）。
3. **历史行的 `client` 是空串**，语义是"当时没记录"，不是"当时是真人"。
   它按"不误杀"原则留在 `real` 里 —— 4 个真实账号的全部调用都是这种行，
   靠"有对话、有真实消息内容"佐证，而不是靠 UA。
4. **凌晨时段的边界**：第 1 轮回填用的是未修天边界版本，窗口首日 00:00–08:00 可能漏标；
   第 2 轮（15 天）已覆盖同一批日志，理论上补上了，但没有逐条复核。
5. `注册用户 171`（顶部总览）与 `注册账号 151`（真实用户卡）**不是同一个分母**：
   后者排除了内部账号与管理员。已在卡面标注"（不含内部/管理员）"。

## 8. 这一批立下的规矩

1. **探针必须复刻看板的全部排除条件**（含管理员名单）。只写 `is_internal = 0` 会得出
   "管理员占了 96%"这种吓人且假的结论 —— 我这一批就报错过一次。
2. **断言必须写在对的那条 SQL 上**。`calls["real"]` 来自五桶 CASE，而趋势/明细/按功能
   走 `_real_where`；只断言前者时，删掉后者里的条件照样绿。反证脚本就是这样抓到的。
3. **反证的判据是输出里出现 `N failed`**，不是 returncode。
4. 采集时省一个字段，排查时花一天。UA 只是分类，值得存。
