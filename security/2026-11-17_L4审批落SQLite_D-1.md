# L4 真实审批落 SQLite（D-1）：多 worker 下「触发 → 点击 → 重发」全链路可用（2026-11-17）

## 一、结论先行

`core/approval_store.py` 原来把 pending / token 存在**进程内 dict** 里，文件头还写着
「刻意不持久化」。审批天然要跨**三个请求**（工具触发 → 用户点击 → 带 token 重发），
只要后端不是单进程，这三个请求就可能落在不同进程上：

| 步骤 | dict 版（多进程时） | 落库后 |
|---|---|---|
| 工具触发 pending（进程 A） | 写进 A 的堆 | 写进 `tool_approvals` 表 |
| 用户点确认（任意进程） | 概率 (N−1)/N 返回 **404** | 读同一张表，必中 |
| 带 token 重发（任意进程） | `consume` 找不到 → 工具再次被拒 | 一条 DELETE 判真假，必中 |

N=4 时端到端成功率约 **1/16**。

**线上的真实情况（2026-11-17 实测，必须说清）**：生产后端现在是
`uvicorn main:app --host 127.0.0.1 --port 8000`，**没有 `--workers`**，即**单进程**。
`ops/systemd/baomi-backend.service` 的 ExecStart 里也没写 `--workers`
（`deploy.sh::detect_workers` 的探测逻辑存在，但这条 unit 没走它）。
所以在这次改动之前，L4 在线上其实是「能用、但只因为恰好是单进程」——
真正的拦路虎不是 D-1，而是**L4 从来没接前端**：没有确认卡片、
没有 `POST /api/chat/approval`，`TOOL_APPROVAL_ENABLED=0` 是这个原因才置的。

因此本次做两件事，缺一件 L4 都开不起来：

1. **落库（D-1）**：把「扩 worker 就废」这个耦合拆掉。不落库的话，
   「升到 4 worker」和「开 L4」两件事会互相锁死——想要并发就得关掉审批。
2. **接线**：`POST /api/chat/approval` + 前端确认卡片 + 带 token 重发。
   没有第 2 件，第 1 件只是换了个更贵的失效方式（代码落库了，但没人能点）。

### 2.1 表结构与三个不变量

```sql
CREATE TABLE tool_approvals (
  request_id, user, tool_name, args_hash, args_preview,
  turn_id, created_at, expires_at, token
);
UNIQUE (user, tool_name, args_hash, turn_id)   -- 同一次申请只留一行
UNIQUE (token) WHERE token IS NOT NULL         -- 一行只挂一个 token
INDEX  (expires_at) / (user, turn_id, expires_at)
```

1. **幂等登记**：`INSERT OR IGNORE` + 唯一索引。模型用同参数重试时复用同一行，
   不会给用户刷出两张一模一样的卡片（dict 版的 `_DEDUPE` 只在**本进程**有效）。
2. **签发只有一个赢家**：`UPDATE ... SET token=? WHERE token IS NULL`。
   双击时另一个 worker 读回前者写的那一枚，而不是 404。
3. **消费是「一条 DELETE 判真假」**：`DELETE ... WHERE token=? AND user=? AND
   tool_name=? AND args_hash=? AND turn_id=? AND expires_at>?` 再按 `rowcount==1` 放行。
   写成「先 SELECT 再 DELETE」的话，两个 worker 同时带同一 token 重发会**都返回 True**，
   工具就执行两次——这条是落库后新增的风险点，专门有并发用例守。

### 2.2 为什么落库不会把 token 变成「可重放」

能重放的前提是「用完还留着」。`consume` 删的就是那一行，删与判是同一条语句。
落库换掉的是「状态存在谁的堆里」，**不是**「token 能不能重复用」。
过期行在每次写操作前顺手 `DELETE`（`_prune`）；`pending_for_turn` 是每轮 Agent 都会
走到的读路径，所以它**只过滤不删**，不在热路径上抢写锁。

### 2.3 两个刻意的产品决定

- **SSE 帧里不放 token**。模型就在这条流的另一端，帧里带 token 等于把「人工确认」
  原路退回给模型，纸糊审批立刻复活。
- **带 token 的重发不重复落库用户消息**。前端重发的是同一句话（第一次尝试已经写进
  库了），再写一遍，用户刷新后会看到同一句出现两次。所以 `api/chat.py` 在
  `approval_token and turn_id` 时把 `user_msg_id` 回 0、跳过 `add_message`。

## 四、开关怎么开

两个开关**必须一起开**，只开一个都会掉进坑里：

| 环境变量 | 值 | 说明 |
|---|---|---|
| `TOOL_APPROVAL_ENABLED` | `1` | L4 总闸（默认 1；生产此前为降级置 0） |
| `TOOL_APPROVAL_REAL_CONFIRM_ENABLED` | `1` | 真实 token 模式。**默认是 0**（代码默认值），不显式开就是旧的「纸糊确认串」 |

只开总闸不开 `REAL_CONFIRM` = 回到「模型自己回填确认串就放行」，比全关更糟
（看起来有审批，实际没有）。`.env` 改完必须 restart backend。

回滚：`TOOL_APPROVAL_ENABLED=0` → `download_file` 直接执行，与移植前一致；
代码本身不需要回滚。

## 五、仍未解决 / 已知边界

1. **`--workers 4` 真起 uvicorn 的压测没做**。自动化守的是「状态跨进程可见」这个
   不变量（独立解释器 + 同一库），线上靠手工取证。压测要一台能起 4 worker 的机器，
   本机 2 核起 4 个进程量出来的数字没有意义。
2. **重发会重跑整轮**。用户点允许后，模型那一轮是从头跑的：会再花一次配额、
   再生成一条回答气泡（用户消息不重复，回答是新的）。这是「token 只能在工具执行
   那一刻校验」的必然结果——真要免掉重跑，得把工具执行搬到审批端点上，
   那是另一个设计（工具结果怎么回填成回答）。
3. **刷新页面后卡片不再出现**。pending 活在库里（TTL 120 秒），但前端没有
   「按会话恢复待确认」的接口（`kb_proposal` 有，approval 没有）。
   影响很小：过期后重新提问即可。
4. `approval_store._db()` 的建表用 `executescript`（隐式 commit），
   每个进程每个库路径只跑一次，被 `_READY` 缓存挡住。多 worker 同时首启时
   可能撞写锁，靠 `busy_timeout=5000` 兜。
