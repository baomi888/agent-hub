### 3.3 有没有第三方反代（把我们当上游）—— 没有证据

判据是三条同时成立才算：

1. 一个 IP 承载多个**互不关联**的账号；
2. 该 IP 的 UA 种类数与账号数同步膨胀（多设备/多用户经一跳汇聚）；
3. 该 IP 落在云厂商/IDC 段（个人反代必然有服务器）。

实测：多账号簇一共 7 个（见 4.2），**全部落在电信/移动/联通的家宽或移动网络段，没有一个是云厂商 IP**；
携带账号的 IP 里也没有任何一个同时满足"多组无关联账号 + 多 UA"。

云厂商 IP 只做探活/扫描，**没有任何一条携带 uid**：
阿里云 47.92.246.83 用 2011 年的 Firefox UA 抓首页与 favicon（200）；腾讯云 43.153.74.75 带 `Referer: http://myzhisui.cn`
抓首页（链接预览类爬虫）；腾讯云 114.132.52.44 打 `/api/capture/capabilities` 拿 401；
AWS 18.218.118.203 的 UA 直接写着 `visionheight.com/scan`；Linode 45.79.207.111 发 Oracle TNS 握手。
没有登录成功，没有产生账号，也没有进过任何业务端点。

### 3.4 **真实风险**：X-Forwarded-For 第一跳可伪造

nginx 五个 location 全部用 `$proxy_add_x_forwarded_for`（**追加**客户端自带的头），
而后端 `api/auth.py::_client_ip()` 取 `split(",")[0]`（**第一跳**）。两者叠加等于：

```
客户端发  X-Forwarded-For: 1.2.3.4
nginx 变成 X-Forwarded-For: 1.2.3.4, <真实IP>
后端取到   1.2.3.4              ← 伪造成功
```

实测（直接调函数）：

```
伪造单跳      -> 1.2.3.4
伪造+真实追加 -> 1.2.3.4
无 XFF        -> 127.0.0.1
```

影响面：

- `SIGNUP_IP_PER_DAY = 50`、`SIGNUP_IP_PER_MINUTE = 10` **可被旋转 header 绕过**；
- `login:ip:<ip>` 的 30 次/分钟同理；
- 任何"按 IP 风控"的后续设计都会继承这个洞。

旁证：`usage` 里存在 `signup:ip:127.0.0.1`（18 次）和 `signup:ip:8.163.62.25`（10 次）——
127.0.0.1/本机公网 IP 不可能来自真实用户，说明这个维度拿到什么值**完全取决于调用方是否老实**。

### 3.5 另一个会伪装成"批量注册"的口径偏差

`api/auth.py::register()` 的顺序是：**先扣 signup 配额，再 `create_user()`**。
于是 409（重名）/ 400（校验失败）也会消耗 `signup_ip` 与 `signup_global`：

| 日期 | 注册请求 200 | 409 | `signup_global` 计数 | 实际新增用户 |
|---|---|---|---|---|
| 2026-11-07 | 20 | 20 | 40 | 9 |
| 2026-11-13 | 21 | 5 | 44 | 0 |

11-13 那天"44 次注册、0 个新用户"曾经被当成攻击，实际是自查脚本的重试（密码/用户名不合规）+ 注册后按 id 清理。
**看 `usage` 判"批量注册"会把数字放大 4 倍以上**，必须和 `users.created_at` 对照。

## 4. 任务三：同 IP / 同网络用户归并 + 禁用

### 4.1 归并方法（不是猜，是可复现的对齐）

1. **uid → IP**：把 nginx 的 `(ip, 秒, 具体路径)` 与 `api_call_logs` 的 `(uid, 秒, 路由模板)` 做窗口对齐——
   同秒 ±1s、路径前缀相同、且该秒 nginx 候选 ≤3 条时计一票，取票数最高的 IP。
   231 个 uid 里 93 个拿到归属（其余是低频用户，一天几条请求，无法唯一对齐）。
2. **注册事件 → IP**：`users.created_at` 与 nginx `/api/auth/register` 的 200 秒级对齐（±2s），一一对应。
3. **同网络**：IP 按 /24 归并（用于判断"同一出口 NAT/同一校园网"）。

### 4.4 实际执行的禁用：75 个幽灵身份

**手段（这套系统里"禁用"有三种实现，用错一种等于没禁用）：**

| 对象 | 正确做法 | 为什么 |
|---|---|---|
| 账号还在 | `status = 0` **且** `token_valid_after += 1` | `status` 只在 `account.login()` 最后一步看，**挡不住已发出的 cookie**（有效期 7 天）；代数 +1 才会让旧令牌在下一次请求就 401 |
| 账号已删（幽灵） | 往 `deleted_users` 写墓碑 | 没有 `users` 行可改；`current_user_id` 只在查不到人时才查墓碑 |
| 单枚令牌 | `revoked_tokens` 写 jti | 用于"退出登录"与精确踢某台设备 |

本次执行：

```bash
python3 security/scripts/disable_accounts.py --db data/sessions.db --orphans           # 预演：75 个
python3 security/scripts/disable_accounts.py --db data/sessions.db --orphans --apply   # 执行
# 审计留痕：{"event":"security_disable","tombstoned":75,"reason":"security_audit_20261114"}
```

结果：`deleted_users` 2 → 77（另加 1 条验证用对照 uid，共 78）；脚本重复跑 `targets=0`（幂等）。

**验证（正/负双向，不是"看着像好了"）：**

| 请求 | 结果 |
|---|---|
| 墓碑 uid → `GET /api/sessions` | **401** `账号已注销，请重新登录` |
| 墓碑 uid → `GET /api/kb` | **401** 同上 |
| 墓碑 uid → `GET /api/tasks` | **401** 同上 |
| 墓碑 uid → `GET /api/today` | **401** 同上 |
| 同一密钥签发的对照令牌（无墓碑）→ 同四个端点 | **200** `{"sessions":[]}` / `{"kbs":[]}` / … |

对照组是关键：它证明"拦住的是墓碑，不是别的什么碰巧生效了"。
`users` 仍 171 行、`status=0` 仍为 0 —— **没有误伤任何现存账号**。
机制层回归：`pytest tests/test_deleted_user.py` → 4 passed。

### 4.5 回滚

墓碑只影响鉴权，不删数据：

```sql
delete from deleted_users where reason = 'security_audit_20261114';
```

（这些账号本身已不存在，正常情况下不需要回滚。）

## 6. 复现

```bash
# 只读审计（不上线、不改库）
python3 security/scripts/audit_accounts.py --db data/sessions.db

# 预演封堵（默认不写库，加 --apply 才执行）
python3 security/scripts/disable_accounts.py --db data/sessions.db --orphans
```
