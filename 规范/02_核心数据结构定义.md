# 02 · 核心数据结构定义

> 目的：把「数据结构」从代码里拎出来变成**契约**。前后端、模块之间对齐字段时以本文为准。
>
> **修改规则**：任何字段增删改，必须①改本文 ②改代码 ③通知受影响方。三者缺一即为契约破坏。

---

## 1. 数据存储总览

| 存储 | 位置 | 内容 | 归属 |
| --- | --- | --- | --- |
| SQLite | `data/sessions.db` | `conversations` / `messages` / `feedbacks` / `users` | 申请人 |
| SQLite | `data/scheduler.db` | 调度三张表（队友新增，见 §7） | 刘佳林 |
| Chroma | `chroma_db/` | 向量库，按 `kb_id` 分 collection | 林宏亮 |
| 文件 | `data/kb_sources/`、`data/uploads/`、`data/chat_uploads/` | 上传原文 | 林宏亮 / 申请人 |
| 文件 | `data/kb_files.json`、`data/kb_names.json`、`data/kb_owners.json` | 索引元数据 | 林宏亮 |

**SQLite 连接约定**（`core/session.py`）

- 连接**按线程复用**，不是每次新建（一次问答原本要开 6～7 个连接）。
- 路径参与判断：测试会 `monkeypatch _db_path` 到临时目录，路径变了必须换连接。
- 统一 PRAGMA：`journal_mode=WAL`、`synchronous=NORMAL`、`busy_timeout=5000`。
- 取值用 `row_factory = sqlite3.Row`，返回 dict-like 对象。

> ⚠️ **`job_runs` 在 `data/scheduler.db`，不在 `data/sessions.db`** —— 这是刻意的隔离，别合并。

## 2. 用户 `users`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `username` | TEXT | **PK** | 登录名，唯一 |
| `password_hash` | TEXT | NOT NULL | PBKDF2-SHA256 散列，轮数见 `AUTH_PBKDF2_ROUNDS`（默认 200000） |
| `created_at` | INTEGER | NOT NULL | Unix 秒 |

**配套规则**

- 重名抛 `sqlite3.IntegrityError`，由 API 层翻译成 **409**，`core/account.py` 不自己吞异常。
- `ADMIN_USERNAMES`（逗号分隔）内的用户**不受配额与限流约束**，相当于主账号。
- `ALLOW_SIGNUP=0` 时关闭自助注册。
- `LEGACY_OWNER = "legacy"`：改造前的历史数据锁在此名下，谁都看不到，
  必须由 `tools/migrate_owner.py` 明确指派给真人账号后才恢复可见——**刻意的默认拒绝**。

## 3. 会话 `conversations`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | TEXT | **PK** | `uuid4().hex[:12]`，短 ID 便于前端展示 |
| `owner_id` | TEXT | 可空 | **归属人**。NULL = 老数据，一律判不可见 |
| `title` | TEXT | NOT NULL | 会话标题，默认「新对话」 |
| `kb_id` | TEXT | 可空 | 绑定的知识库；NULL = 不挂知识库 |
| `created_at` | INTEGER | NOT NULL | Unix 秒 |
| `updated_at` | INTEGER | NOT NULL | Unix 秒，列表按它倒序 |

**索引**：`idx_conv_updated(updated_at DESC)`、`idx_conv_owner(owner_id, updated_at DESC)`

**多用户隔离铁律**

```python
def _owned(owner: str, sid: str) -> bool:
    """会话 sid 是否属于 owner。老数据 owner_id 为 NULL，一律判 False。"""
```

- **每个**读写会话的入口都必须先过 `_owned`，否则就是越权。
- `owner_id IS NULL` 的行**永远返回 False**，不做"无主即公开"的推断。
- 对应测试：`test_owner_isolation.py` / `test_kb_isolation.py` / `test_auth_gate.py`。

## 4. 消息 `messages`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | INTEGER | **PK AUTOINCREMENT** | 自增，同时充当排序键 |
| `conversation_id` | TEXT | NOT NULL, FK | 外键 → `conversations(id)` **ON DELETE CASCADE** |
| `role` | TEXT | NOT NULL, CHECK | 仅允许 `system` / `user` / `assistant` |
| `content` | TEXT | NOT NULL | 消息正文（Markdown） |
| `refs` | TEXT | 可空 | **溯源引用**，JSON 字符串；由老库 ALTER 补列而来 |
| `created_at` | INTEGER | NOT NULL | Unix 秒 |

**索引**：`idx_msg_conv(conversation_id, id)`

**约定**

- `MAX_HISTORY_TURNS = 30`：喂给模型时最多保留 30 轮（1 轮 = user + assistant 两条）。
- `role` 有 CHECK 约束：**新增角色类型必须先改表结构**，不能直接塞新值。
- `refs` 是字符串不是数组，前端拿到后需自行 `JSON.parse`。

## 5. 反馈 `feedbacks`

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| `id` | INTEGER | **PK AUTOINCREMENT** | — |
| `conversation_id` | TEXT | NOT NULL | 关联会话 |
| `message_id` | INTEGER | 可空 | 关联消息 |
| `rating` | TEXT | NOT NULL, CHECK | 仅允许 `up` / `down` |
| `comment` | TEXT | 可空 | 用户补充说明 |
| `created_at` | INTEGER | NOT NULL | Unix 秒 |

**唯一索引**：`idx_fb_msg(conversation_id, message_id) WHERE message_id IS NOT NULL`

> **语义**：一条消息只保留**最后一次**反馈——点赞后再点踩是**改**，不是追加。
> 用部分唯一索引实现，不要用「查有没有再决定插入还是更新」的写法（并发下会双写）。

**索引**：`idx_fb_conv(conversation_id)`

## 6. 知识库 `kb` 契约

### 6.1 标识与归属

| 概念 | 规则 |
| --- | --- |
| `kb_id` | `md5(owner \| name)` 派生 → **同名即同库** |
| 归属 | `data/kb_owners.json` 记录 `kb_id → owner` |
| 名称 | `data/kb_names.json` 记录展示名 |

> ⚠️ `kb_id` 由 `owner + name` 派生，所以「同名复用已有库」在服务端**本来就成立**；
> 导入时按名复用是**正确行为**，不要改成每次新建（会产生同名重复库）。

### 6.2 切片参数

| 参数 | 配置键 | 默认 | 约束 |
| --- | --- | --- | --- |
| `chunk_size` | `CHUNK_SIZE` | 500 | `> 0`（**当前无上界，见已知缺口**） |
| `chunk_overlap` | `CHUNK_OVERLAP` | 50 | `>= 0` |
| `top_k` | `TOP_K` | 3 | `> 0`（**当前无上界**） |
| `EMBED_BATCH_SIZE` | — | 10 | 阿里百炼单次批量上限 |
| `EMBED_CONCURRENCY` | — | 4 | 并发批次数；太高撞 429，3~4 足够 |

### 6.3 检索结果 `refs`

`refs` 是**字符串形式的 JSON**，前端消费前必须 `JSON.parse`。每条引用包含来源文件名与片段信息。

### 6.4 检索调参（阈值语义，**别合并**）

| 常量 | 默认 | 语义 |
| --- | --- | --- |
| `RETRIEVE_FETCH_MULT` | 3 | 候选池倍数（先多取几倍再挑，避免 top_k 被相邻重复切片占满） |
| `RETRIEVE_MIN_FETCH` | 12 | 候选池下限 |
| `RETRIEVE_MMR_LAMBDA` | 0.65 | MMR 相关度权重，1.0 = 等同旧行为 |
| `RETRIEVE_MIN_SIM` | 0.25 | **丢不丢**：低于它当不相关丢弃；丢完一条不剩时**强留**最相关那条 |
| `RETRIEVE_LOW_SIM` | 0.45 | **够不够格当依据**：不丢，但回答里要**示弱** |
| `GROUNDING_NOTICE` | 1 | 低置信提示总开关，可一键回退而不回滚代码 |

> ⚠️ `RETRIEVE_MIN_SIM` 与 `RETRIEVE_LOW_SIM` 是**两件事**，代码注释里明确写了不许合并。
> 依据：用户调研（56 份）中「答案不准还装自信」占 **83.9%**，是压倒性第一担忧。

## 7. 调度数据 `data/scheduler.db`（C 线）

> 由 `core/scheduler.py`（+853 行）定义：**三张表 + 幂等键 + 重试分级 + 心跳**。

| 表 | 用途 |
| --- | --- |
| 任务定义表 | job 定义（对应 `GET /api/schedule/jobs`） |
| 执行历史表 | 每次执行记录（对应 `GET /api/schedule/runs`，游标分页） |
| 心跳表 | worker 存活心跳 |

**健康判定口径（重要）**

- 看**心跳年龄**，不看进程表：`> 300s` → `stalled`；`> 600s` → `down`。
- 原因：`worker` 是**独立 APScheduler 进程**，与 web 彻底隔离，进程存在不代表在正常跑。
- 时区固定 `Asia/Shanghai`，五个 job。

**端点**（均挂 `Depends(get_current_user)`）

```
GET  /api/schedule/health     worker 心跳 + 各 job 最近执行
GET  /api/schedule/jobs       任务定义表
GET  /api/schedule/runs       执行历史（游标分页）
POST /api/schedule/run-now    手动触发（管理员）
POST /api/schedule/retry      重排失败执行（管理员）
```

## 8. 每日总结 `report`（C 线）

**真实响应形状**（这是契约，前端按此解析）：

```jsonc
{
  "report_id": "...",
  "date": "2026-10-13",
  "status": "...",
  "stats": {
    "conversation_count": 0,
    "message_count": 0,
    "user_msg_count": 0,
    "assistant_msg_count": 0,
    "active_hours": 0,
    "tool_call_count": 0
  },
  "content": [
    { "text": "结论文本", "source_refs": [123, 456] }   // ← 溯源消息 id 列表
  ],
  "model": "...",
  "generated_at": "...",
  "read_at": null
}
```

> ⚠️ **`content` 不是思维导图树**。
> 后端做了**强制溯源**（`_filter_by_traceability`）：`source_refs` 指不到真实消息的结论**会被直接丢弃**。
> 因此 **UI 里每条结论必须有可点回原文的角标** —— 这既是产品硬要求，也是后端已在执行的口径。

### 8.1 🔴 形状冲突的裁决（2026-10-13 已定，见下方）

设计稿与已实现代码对 `report` 的形状不一致。**两者各有优点，但混用会导致前端解析错**。
本节的裁决是**最终口径**，改它必须走 `03_流程规范.md` §2 的契约变更流程。

| 维度 | 设计稿（HTML） | 实现版（代码） | 裁决 |
| --- | --- | --- | --- |
| `content` | **object**：`{topics, questions, highlights, todo, suggestions}` | **list**：`[{text, source_refs}]` | ✅ **取设计稿的语义，保留实现版的溯源强度** |
| `source_refs` 类型 | `["msg_4711"]` **字符串** | `[123, 456]` **整数**（`messages.id`） | ✅ **整数**（见下「为什么」） |
| `sources` 字段 | **有**：`[{type, ref_id, title, ts}]` | **无** | ✅ **补上**（前端要靠它渲染角标标题） |
| `stats` | 7 字段（`sessions/messages/active_minutes/first_message_at/last_message_at/kb_queries/tools_used`） | 6 字段（`conversation_count/message_count/user_msg_count/assistant_msg_count/active_hours/tool_call_count`） | ✅ **合并**：以实现的 6 字段为准，补 `first_message_at`/`last_message_at`/`tools_used` |

**为什么 `source_refs` 用整数而不是 `msg_4711`**

`messages.id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT`（见本文 §4）。
后端的强制溯源是拿 refs 去**真实消息表里查**，它天然只有整数。
若改字符串就要在后端造一层 `msg_xxx` 编解码 —— 多一层映射就多一处能对不上的地方，
而**溯源正确性正是这个模块的核心卖点**（refs 指不到真实消息的结论会被直接丢弃）。
**结论：整数 ID 保真，命名体裁让给前端。**

**为什么必须补 `sources`**

设计稿的 `sources` 把 `ref_id → {title, ts}` 做成映射表，前端据此渲染「可点回原文的角标标题」。
实现版只有裸整数 ID，**前端拿不到标题，就无法渲染产品硬要求的那个角标**。
这不是可选项，是缺口。补法：

```
GET /api/report/{date} 响应增加：
  "sources": [
    { "type": "message", "ref_id": 4711, "title": "会话「数据结构答疑」第 3 轮", "ts": 1760271120 }
  ]
```

**过渡期（前端先动，不必等后端）**

后端补齐 `sources` 之前，前端可按下面的规则**降级渲染**，不要写死等待：

1. 收到 `source_refs` 里的整数 id；
2. 用已加载的会话消息（前端本来就有）本地查 `id → content` 片段；
3. 查不到就渲染成「第 N 条消息」之类的弱角标，**不要丢弃整条结论**（后端已保证 refs 都是真实的）。

后端补上 `sources` 后，前端优先用 `sources.title`，本地查表只作兜底。

**最终契约（实现方按这个改，前端按这个解析）**

```jsonc
{
  "report_id": "...",
  "date": "2026-10-13",
  "status": "ready | generating | empty",
  "stats": {
    // 实现版已有（保留）
    "conversation_count": 0, "message_count": 0,
    "user_msg_count": 0, "assistant_msg_count": 0,
    "active_hours": 0, "tool_call_count": 0,
    // 从设计稿补入
    "first_message_at": 1760270400, "last_message_at": 1760286600,
    "tools_used": { "kb_search": 5, "web_search": 1 }
  },
  "content": {                       // ← 恢复为 object（设计稿语义）
    "topics": [ { "title": "...", "summary": "...", "source_refs": [4711, 4718] } ],
    "questions": ["..."],            // 纯字符串，无溯源
    "highlights": ["..."],           // 纯字符串，无溯源
    "todo": [ { "text": "...", "done": false, "source_refs": [4718] } ],
    "suggestions": ["..."]           // 纯字符串，无溯源
  },
  "sources": [                       // ← 新增（补齐前端角标缺口）
    { "type": "message", "ref_id": 4711, "title": "...", "ts": 1760271120 }
  ],
  "model": "deepseek-chat",
  "generated_at": 1760311800,
  "read_at": null
}
```

> **注意 `content` 从 list 改回 object 是有代价的**：会动到 C 线已实现的 `service/daily.py` 与 `_filter_by_traceability`。
> 若组会决定**不接受这个返工**，则退守方案是：**保留 list 形状，但同样补 `sources` 字段**
> （即只做"加字段"这个加法，不做"改形状"这个改动）——前端照样能渲染角标。
> 两个方案都能消除冲突，**选哪个取决于 C 线愿意付多少返工成本**；README 记录最终选择。


**端点**

```
GET  /api/report/today        今日总结（无则 404）
GET  /api/report/{date}       指定日期总结
POST /api/report/generate     触发生成（同步返回）
```

**已知缺口**：`stats` 里**没有 `streak`**，后端也**没有 `/checkin/*` 端点**。打卡页只能由 report / runs 派生，或等后端认领。

## 9. 每日委托 `delegate`（C 线）

**端点**

```
GET    /api/delegate/            列表
POST   /api/delegate/            新建
GET    /api/delegate/{id}/       取
PATCH  /api/delegate/{id}/       改
DELETE /api/delegate/{id}/       删
POST   /api/delegate/{id}/run    立即执行（支持 dry_run）
GET    /api/delegate/{id}/runs   执行历史
```

**业务规则（硬约束）**

| 规则 | 说明 |
| --- | --- |
| `kind` 取值 | `study_plan` / `review` / `encourage` / `custom` |
| 启用上限 | **最多 5 条**启用中 |
| 同名 | 返回 **409** |
| `name` | **建后不可改**（它是唯一标识） |
| `dry_run` | `POST .../run?dry_run=true` 只生成内容、**不投递** |

> **`dry_run` 的产品价值**：实现「系统先生成好、给用户确认/修改」，
> 而不是让用户每天填表。这是产品方向要求的核心交互。

> ⚠️ **语义未对齐**：会议纪要是「学生填当日产出 → Agent 反馈」；
> 实现出来的是**定时委托 CRUD + 定时投递到会话**，**没有 `/submit` 端点**。
> 需要在组会上拍板：是补 `/submit`，还是改纪要与申报书口径。

## 11. 统一响应与错误约定

| 场景 | 状态码 | 响应体 |
| --- | --- | --- |
| 正常 | 200 / 201 | 业务对象 |
| 未登录 | 401 | `{"detail": "..."}` |
| 越权 / 不存在 | 404 | `{"detail": "..."}`（**不区分**，避免探测他人资源） |
| 重名冲突 | 409 | `{"detail": "..."}` |
| 限流 | **429** | `{"detail": "...", "retry_after": 12.3}` + `Retry-After` 头 |
| 配额超限 | **429** | `{"detail": "...", "kind": "...", "limit": 60}` |
| 系统错误 | 500 | `{"detail": "..."}` |

**429 的实现方式（不要改）**

限流/配额异常注册为**全局异常处理器**（`main.py`），不在各端点里 `try/except`。

> **原因**：端点自己 catch 容易顺手把它转成 500，前端就分不清「系统出错」和「你今天用超了」。

**统一错误模型**：`api/schemas.py` 的 `ErrorResponse{ detail: str }`

> ⚠️ **已知问题**：8 处 `detail` 会**回显用户输入**。改动错误文案时不要引入新的回显。
