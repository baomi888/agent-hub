## 三、`dev` 的 5 个冲突逐条分析

### 3.1 `core/config.py` — 1 处撞车，**最容易解**

两边都在文件**同一区域（73-78 行）追加配置常量**：

| 侧 | 追加了什么 |
| --- | --- |
| `main` | `RETRIEVE_LOW_SIM`（0.45）、`GROUNDING_NOTICE` —— 可信度判定相关 |
| `dev` | `TOP_K_MAX`（20）、`HYBRID_ENABLED`/`HYBRID_RRF_K`/`HYBRID_KEYWORD_TOP`/`HYBRID_MAX_DOCS`、`QUERY_REWRITE_*` —— 混合检索与查询改写相关 |

**两侧都是纯新增（`-0` 删除）**，没有任何一行被对方改掉。

**建议解法**：**两边都保留**，把 `dev` 的常量块追加在 `main` 的常量块之后即可。
这是纯粹的"文本位置撞车"，语义上零冲突。

> ⚠️ 注意 `RETRIEVE_LOW_SIM` 与 `dev` 新增的检索参数**互不相干**，不要试图合并它们。

### 3.2 `agent/tools.py` — 1 处撞车，**⚠️ 这里有个会丢东西的坑**

| 侧 | 改动 |
| --- | --- |
| `main` | +18/-3，4 个 hunk |
| `dev` | +5/-11，1 个 hunk（`main[121-130] × dev[113-134]`） |

撞车处是**搜索调用**。`main` 侧有联网搜索中国区锚定（`edc781b`），`dev` 侧把搜索收口到了
`core/serper.py`（`bb7352a`）。

**⚠️ 必须注意（已实测核实，与 `docs/团队分支分析_20261013.md` 的说法不一致）：**

> 团队分支分析文档写的是"他们**已把** `gl=cn/hl=zh-cn` 补回 `core/serper.py`"。
> **实测不是这样**：`git grep` 在 **`origin/dev` 全分支上搜不到任何 `gl=cn` / `zh-cn`**；
> 而 `origin/main` 上这两行**确实存在**于 `agent/tools.py:142` 与 `kb/importer.py:176`。

**结论：中国区锚定只在 `main` 上，`dev` 没有。** 所以这一处**不能简单"取 dev 侧"** ——
那样会把 `main` 的中国区锚定**丢掉**，导致联网搜索结果退回到偏向非中文的结果。

**建议解法**：
1. 以 `dev` 的 `core/serper.py` 收口结构为准（规范 `01` §3.4 定的方向）；
2. **把 `main` 的 `gl=cn / hl=zh-cn` 补进 `core/serper.py` 的请求体**；
3. 删掉 `agent/tools.py` 里的直连搜索实现。

**验收（必须做）**：
```bash
git grep -n 'zh-cn' -- '*.py'        # 合并后应至少有一处，且位于 core/serper.py
```
若合并后**搜不到**，说明锚定被合丢了，会直接影响中文搜索质量。

## 四、`feat/ai-module` 为什么无冲突

它已经做过一次 `merge: 把 main 的 AI 模块地基并入 dev`（`f06831c`），
把 `main` 的接口文档线并了进来。因此它相对 `main` 是**快进式**的，`git merge-tree` 报无冲突。

**关于 `git diff main feat` 里那 43 个 `D` 条目 —— 别误读**：

我实测确认，它们**不是 `feat` 删掉的文件**，而是**「`main` 有、`feat` 没有」的文件**。
验证方式：反向 diff 得到**同样 43 个 `A` 条目**，一一对应。

```
git diff --name-status main feat  →  D: 43（main 有而 feat 没有）
git diff --name-status feat main  →  A: 43（同一批文件）
```

这 43 个里包含我刚合进 `main` 的 `规范/`、`CODEOWNERS`、`deploy-staging.sh`、
`docs/实机截图/*` 等 —— 都是 `main` 新加的，`feat` 自然还没有。
**合并 `feat` → `main` 时，`main` 的这些文件会保留，不会被删。**（合并方向是"把 feat 加进 main"，
不是"用 feat 覆盖 main"。）

**但无冲突 ≠ 无风险**。`feat` 带进来的是**新增包**（`service/`、`worker/`、
`core/scheduler.py`、`core/tool_registry.py`）与四个新路由，合并后需要：

1. **`worker` 是独立进程** —— `deploy.sh` 要多管一个进程、多一条日志、多一处存活检查。
2. **`api/report.py` 两处同步调用未包 `to_thread`** —— 违反既定规则，属高优先级缺口。
3. **`api/delegate.py` 曾被 `git reset --hard` 清掉过一次**（队友自述），是重写的，留意。
4. **`feat` 侧改动了 30 个已存在文件**（含 `.github/workflows/ci.yml`、`CONTRIBUTING.md`、
   `core/config.py`、`api/chat.py`、`frontend/src/app/page.tsx` 等）——
   虽然 `merge-tree` 报无冲突，但这些改动**会与 `main` 上的新版本叠在一起**，
   合完**必须跑一遍完整验证**（见 §六）。

**合并后新增的 17 个端点（`feat` 带进来的）**

```
/api/agent      GET  /tools                       POST /tools/discover
/api/schedule   GET  /health   GET /jobs   GET /runs
                POST /run-now (202)               POST /retry
/api/report     GET  /today    GET /{date}        POST /generate
/api/delegate   GET  /         POST / (201)       GET|PATCH|DELETE /{delegation_id}/
                POST /{delegation_id}/run         GET  /{delegation_id}/runs
```

> ⚠️ 注意 `feat` 的委托路由用的是 `{delegation_id}`（不是我文档里写的 `{id}`）——
> 合并后以**实际代码为准**，规范 `04` §4.3 的端点索引需要同步更新。
> 另：`/api/report/today` 与契约里的 `/{date}` 并存，两者都在，此前记的"不一致"实为**都有**。

## 五、建议的合并顺序（供组会决策）

```
第 1 步  main + feat/ai-module      ← 无冲突，先合（队友 C 线，刘佳林）
第 2 步  main + dev                 ← 5 处冲突，解完再合（队友 B 线，林宏亮）
第 3 步  验证：pytest + 真机冒烟 + 前端 tsc
```

**为什么先合 feat 再合 dev**：`feat` 无冲突，合完 `main` 就包含了 C 线全部成果；
再合 `dev` 时，冲突面不会因为 `feat` 的并入而变大（两者改动文件几乎不重叠：
`feat` 主要是**新增文件**，`dev` 是**改已有文件**）。

**为什么这两步都该由队友自己执行**：`dev` 是林宏亮的分支、`feat` 是刘佳林的分支
（账号归属已确认，见 `决策记录.md` D-001）。按 `01_架构与模块职责.md` §6，
跨模块改动要**先通知**。他们自己合最清楚哪边该留。
