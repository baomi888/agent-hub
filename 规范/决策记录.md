> 用途：**把已经拍板的技术决策和理由留下来**，避免同一件事被反复讨论、或在合并/交接时丢失上下文。
>
> 规矩：决策一旦写进这里就是**权威口径**；要推翻它，必须在此追加一条**新记录**说明为什么推翻，
> **不要直接删改旧记录**——旧记录解释了"当时为什么这么想"，删掉它下次还会踩同一个坑。
>
> 格式：编号 / 日期 / 决策 / 状态 / 背景 / 选项 / 结论 / 影响与代价。

## D-002 · 每日总结 `report` 的响应形状

| 项 | 内容 |
| --- | --- |
| **日期** | 2026-10-13 |
| **状态** | ✅ 已裁决（实现待返工） |
| **决策** | `content` 取**设计稿的 object 语义**；**补 `sources` 字段**；`stats` **合并**为 9 字段；`source_refs` 用**整数** ID |

### 背景

设计稿（`docs/接口文档/*.html` 的 Mock）与已实现代码（队友 `feat/ai-module-20261013`）
对同一端点给出了**两套不兼容的形状**。前端必须二选一，所以必须裁决。

| 维度 | 设计稿 | 实现版 |
| --- | --- | --- |
| `content` | object `{topics, questions, highlights, todo, suggestions}` | list `[{text, source_refs}]` |
| `source_refs` | 字符串 `"msg_4711"` | 整数 `4711`（`messages.id`） |
| `sources` 字段 | **有**（`[{type, ref_id, title, ts}]`） | **无** |
| `stats` | 7 字段（`sessions/messages/active_minutes/first_message_at/last_message_at/kb_queries/tools_used`） | 6 字段（`conversation_count/message_count/user_msg_count/assistant_msg_count/active_hours/tool_call_count`） |

### 逐项裁决与理由

**① `source_refs` 用整数（不用 `msg_4711`）**

`messages.id` 是 `INTEGER PRIMARY KEY AUTOINCREMENT`，后端的**强制溯源**
（`_filter_by_traceability`）是拿 refs 去真实消息表里查，天然只有整数。
改成字符串就要在后端加一层 `msg_xxx` 编解码 —— **多一层映射就多一处能对不上的地方**，
而「溯源正确性」恰恰是这个模块的核心卖点（refs 指不到真实消息的结论会被直接丢弃）。
→ **整数保真，命名体裁让给前端。**

**② `content` 恢复 object（取设计稿语义）**

`{topics, questions, highlights, todo, suggestions}` 比 `[{text}]` **多表达了结构**：
`todo` 有 `done` 状态、`topics` 能带标题与摘要。产品侧要做的是「学习总结」而不只是「一堆结论」，
这个结构对 UI 有用（能分区块渲染）。而且设计稿已按此与前端对齐过。

**③ 必须补 `sources` 字段（这是缺口，不是偏好）**

设计稿的 `sources` 把 `ref_id → {title, ts}` 做成映射表，前端据此渲染「可点回原文的角标**标题**」。
实现版只有裸整数 ID，**前端拿不到标题，就渲染不了产品硬要求的那个角标**。

### 最终契约

见 [`02_核心数据结构定义.md`](./02_核心数据结构定义.md) §8.1（含完整 JSON）。

### 影响与代价

- **代价**：`content` 从 list 改回 object 会动到 C 线已实现的 `service/daily.py` 与 `_filter_by_traceability`，是**真实返工**。
- **退守方案**：若 C 线不接受返工，则**保留 list 形状，但同样补 `sources`**（只做加法、不改形状）。
  两个方案都能消除冲突，**选哪个取决于 C 线愿付多少返工成本** —— 一旦选定，把结果追加到本记录。
- **前端过渡期**：后端补齐 `sources` 前，前端用**已加载的会话消息**本地查 `id → 片段` 降级渲染，
  查不到就渲染弱角标，**不要丢弃整条结论**（后端已保证 refs 都是真实的）。
- **不做的事**：不要在两套形状之间"都支持"——前端同时兼容 object/list 会让解析逻辑脆到无法维护。

## D-003 · CI 必须区分 pytest 风格与脚本式测试

| 项 | 内容 |
| --- | --- |
| **日期** | 2026-10-13 |
| **状态** | ✅ 已生效（CI 已拆两个 step） |
| **决策** | 脚本式自测**必须用 `python tests/xxx.py` 跑**，不能交给 pytest |

### 背景

`tests/` 下混着两类文件：

1. **pytest 风格**：有顶层 `def test_*` → `pytest` 能正常收集。
2. **脚本式自测**：**没有** `test_*`，检查写在**模块级**，结尾 `sys.exit(1)` 或 `print("ALL PASS")`。

pytest 在**收集阶段**就会 import 模块，于是模块级检查被立即执行：

- **全部通过** → 报 `collected 0 items`，**绿色但零覆盖（假绿，比红更危险）**；
- **有失败** → 模块里的 `sys.exit(1)` 直接把 pytest 进程干掉，**看不出是哪一项挂的**。

### 发现过程（这是一次真实事故）

整理 CI 时发现改造前的 `ci.yml` **一直把 4 个脚本式文件混在 pytest 命令里跑**：

| 文件 | 模块级检查 | 实际状态 |
| --- | --- | --- |
| `test_agent_guard.py` | 14 项 | ❌ 从未被真正校验（假绿） |
| `test_grounding.py` | 27 项 | ❌ 从未被真正校验（假绿） |
| `test_scenarios.py` | — | ❌ 同上 |
| `test_retrieve_select.py` | — | ❌ 同上 |

**即「离线检查全绿」里有一批其实没跑。** 这是"CI 绿灯 ≠ 测试真的跑了"的典型案例。

### 结论与判据

```bash
grep -c '^def test_' tests/test_xxx.py   # 输出 0 = 脚本式，必须用 python 跑
```

`ci.yml` 拆成两个 step：
- `Run offline test subset (pytest 风格)` —— 4 个真·pytest 文件
- `Run script-style self-checks (脚本式自测)` —— 用 `python` 逐个跑 6 个脚本式文件

### 影响

新增测试文件时**必须先判断属于哪一类**，别放错 step。
详见 [`04_环境与部署.md`](./04_环境与部署.md) §2.7。

## D-004 · Staging 与生产同机分端口并存

| 项 | 内容 |
| --- | --- |
| **日期** | 2026-10-13 |
| **状态** | ✅ 已生效 |
| **决策** | staging 与生产**同一台 ECS**，靠端口/数据目录/配置/工作区**四重隔离** |

**背景**：只有一台 2 核 2G 的阿里云 ECS，另开机器成本高。

**选项**：① 另开一台服务器（隔离最彻底，要花钱）② 同机分端口（成本最低）③ Docker 本地起（与现有裸机部署不符）

**结论**：选 ②。隔离方式：

| 维度 | 生产 | Staging |
| --- | --- | --- |
| 端口 | 3000 / 8000 | **3001 / 8001** |
| 数据 | `data/`、`chroma_db/` | **`data-staging/`、`chroma-staging/`** |
| 配置 | `.env` | **`.env.staging`** |
| 代码 | `/root/agent-hub` | **`/root/agent-hub-staging`**（独立 git 工作区） |

**为什么必须用两个工作区**：同一目录切分支会让生产代码在构建期间**处于半成品状态**，
前端 `.next` 也会被覆盖。代价只是多一份 `venv` 与 `node_modules`。

**安全护栏**（已写进 `deploy-staging.sh`）：
- `DATA_DIR`/`PERSIST_DIR` 指向生产目录 → **脚本拒绝启动**；
- 停服务按端口精确匹配，**不用宽泛的 `pkill -f "uvicorn main:app"`**，不误杀生产。

**影响**：2 核 2G 跑两套实例吃紧，**不要同时构建两端**。

## D-005 · API 前缀：暂缓拍板，但先定管理规则

| 项 | 内容 |
| --- | --- |
| **日期** | 2026-10-13 |
| **状态** | 🅿️ 挂起（按申请人指示） |
| **决策** | 前缀本身**不定**；管理规则**即刻生效** |

**背景**：规划文档 T5 要求 `/api/v1`，但队友已实现的 35 个端点全是 `/api`。
申请人指示此项暂缓（当前更缺整体架构图）。

**已生效的管理规则**（保证将来迁移成本最低）：
1. **前缀只在 `main.py` 定义一次**，路由文件内只写相对路径 → 迁到 `/api/v1` 只改一处。
2. 路径全小写 + 连字符分词；资源用名词复数；动作型用动词子路径。
3. 新增端点必须同步三处：`main.py` 挂载点、`04` 文档端点索引、前端 `lib/api.ts`。
4. 鉴权默认开启（业务 router 一律挂 `Depends(get_current_user)`，只有 `auth` 例外）。
5. **契约零破坏**：现有 35 个端点的路径/请求字段/响应形状一律不改。

**注意**：**合分支（`feat/*` → `main`）是从 `/api` 迁 `/api/v1` 成本最低的时机**。
若最终要迁，建议趁合并一并做，不要等上线后再动。
