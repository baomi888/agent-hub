## 1. 环境总览

| 环境 | 位置 | 前端端口 | 后端端口 | 数据目录 | 用途 |
| --- | --- | --- | --- | --- | --- |
| **本地开发** | 各人电脑 | 3000 | 8000 | 本地 `data/` | 日常开发 |
| **Staging** | 阿里云 ECS（**与生产同机**） | **3001** | **8001** | `data-staging/` | 联调、验收、演示预演 |
| **生产** | 阿里云 ECS | 3000 | 8000 | `data/` | 对外 |

> **为什么 staging 与生产同机分端口**：只有一台 2 核 2G 的 ECS，另开机器成本高。
> 靠**端口 + 数据目录 + .env 三重隔离**，做到「同一份代码、两套完全独立的运行实例」。

**硬件约束（务必记住）**：2 核 2G，前端构建约需 3～8 分钟，已启用 swap，
构建参数为 `NODE_OPTIONS=--max-old-space-size=1536`。
**不要在 ECS 上跑 `pytest` 全量集成测试**，会挤爆内存。

## 2. 开发环境配置

### 2.2 后端环境搭建

> 曾因写成三引号把整次部署卡死（2026-10-03），别再犯。

### 2.3 配置文件 `.env`

```bash
copy .env.example .env      # Windows
# cp .env.example .env      # Linux / macOS
```

**必须填的三项**（与后端 `core/config.py` 的 `validate()` 保持一致）：

| 变量 | 含义 |
| --- | --- |
| `DEEPSEEK_API_KEY` | DeepSeek 对话密钥 |

### 2.4 启动

```bash
# 后端（只监听回环 127.0.0.1:8000）
python main.py

# 前端（另开终端）
cd frontend && npm install && npm run dev
```

验证：`curl http://127.0.0.1:8000/health` → `{"status":"ok","version":"0.3.0 (W3)"}`

> **后端为什么不监听 0.0.0.0**：前端靠 Next 的 `/api/*` rewrite 访问它，功能不受影响；
> 少一层暴露面就少一层风险，而且 `:8000` 直连会绕过 Next 的 Cookie 域设置，容易踩登录态丢失的坑。

### 2.6 `pytest.ini` 的收集规则（别乱改）

`tests/` 下混着两种文件：

1. **pytest 风格**（定义 `test_*` 函数）——由 pytest 收集。
2. **脚本式自测**（模块级执行 + `sys.exit` / `assert` 结尾）——设计上就是 `python tests/test_xxx.py` 直接跑的。

脚本式文件被 pytest 收集会在**收集阶段**整段执行，导致两个副作用：
每个文件都 monkeypatch `core.session._db_path` 到临时目录，但 `core.account` 的建表
只会在进程内跑一次（import 缓存），临时库里没有表 → `no such table: users`。

**所以 `pytest.ini` 逐文件 `--ignore` 了脚本式自测。新增脚本式用例必须同步加进 `--ignore`。**

### 2.7 ⚠️ 两类测试必须分开跑（CI 里踩过的坑）

`tests/` 下的文件分两类，**用错命令会「假绿」**：

| 类型 | 特征 | 正确跑法 | 文件 |
| --- | --- | --- | --- |
| **pytest 风格** | 有顶层 `def test_*` 函数 | `pytest tests/xxx.py` | `test_chroma_singleton`、`test_upload_stream`、`test_pipelines_concurrency`、`test_agent_checkpointer` |
| **脚本式自测** | **无** `test_*` 函数，检查写在**模块级**，结尾 `sys.exit` 或 `print("ALL PASS")` | `python tests/xxx.py` | `test_agent_guard`、`test_grounding`、`test_scenarios`、`test_retrieve_select`、`test_slash_no_redirect`、`test_usage_stats` |

> 🔴 **为什么不能用 `pytest` 跑脚本式用例**：pytest 收集阶段就会 import 模块，
> 于是模块级的检查逻辑被立即执行，结果是：
> - **全部通过** → pytest 报 `collected 0 items`，**绿色但零覆盖**（假绿，比红更危险）；
> - **有失败** → 模块里的 `sys.exit(1)` 直接把 pytest 进程干掉，CI 报错却**看不出是哪一项挂的**。
>
> 判断方法（照抄就行）：
>
> ```bash
> # 有输出数字且 >0 = pytest 风格；输出 0 = 脚本式，必须用 python 跑
> grep -c '^def test_' tests/test_xxx.py
> ```
>
> `ci.yml` 已按此分成两个 step：`Run offline test subset (pytest 风格)` 与
> `Run script-style self-checks (脚本式自测)`。**新增测试文件时先判断属于哪一类，别放错 step。**

## 3. 测试数据库（连接与隔离）

### 3.1 本项目不用外部数据库服务

**重要**：本项目**没有** MySQL / PostgreSQL 之类的数据库服务，所以**没有"测试数据库连接地址"这种配置**。
数据全部落在**进程本地**：

| 存储 | 默认路径 | 类型 |
| --- | --- | --- |
| 会话 / 消息 / 反馈 | `data/sessions.db` | SQLite |
| 用户 | `data/sessions.db`（同库） | SQLite |
| 调度三张表 | `data/scheduler.db` | SQLite |
| 向量库 | `chroma_db/` | Chroma 持久化目录 |

> 这也是"测试数据库连接地址"这个问题在本项目的真实答案：**它是文件路径，不是连接串**。
> 对应配置项是 `DATA_DIR` 与 `PERSIST_DIR`（见 `.env`）。

### 3.2 测试如何隔离数据库

测试**不连真实库**，靠 `monkeypatch` 把路径改到临时目录：

```python
# core/session.py 的连接管理刻意做了路径判断
_LOCAL = threading.local()


def _conn():
    path = _db_path()
    conn = getattr(_LOCAL, "conn", None)
    if conn is not None and getattr(_LOCAL, "path", None) == path:
        return conn  # 路径没变 → 复用连接
    ...  # 路径变了 → 重建连接
```

> **为什么连接按线程复用**：原本每次操作都新建 sqlite 连接（等于每次重开文件 + 重设 WAL），
> 一次问答要开 6～7 个。改成线程内复用后，连接只建一次、pragma 只设一次。
>
> **为什么路径要参与判断**：正因为测试会 monkeypatch `_db_path`，
> 路径一变**必须**换连接，否则会继续读写上一个库。

### 3.3 各环境的数据库隔离

| 环境 | `DATA_DIR` | `PERSIST_DIR` | 与生产的隔离方式 |
| --- | --- | --- | --- |
| 本地 | `data` | `chroma_db` | 各自电脑，天然隔离 |
| **Staging** | **`data-staging`** | **`chroma-staging`** | **独立目录，绝不共用生产数据** |
| 生产 | `data` | `chroma_db` | — |

> ⚠️ **Staging 绝不能指向生产的 `data/`**。
> 一旦共用，staging 的测试数据会污染生产用户，且 `chroma_db` 并发写可能损坏索引。

### 3.4 数据库备份（改结构前必做）

```bash
# 备份（SQLite 支持在线备份，不用停服务）
cp data/sessions.db  data/sessions.db.bak.$(date +%Y%m%d)
cp data/scheduler.db data/scheduler.db.bak.$(date +%Y%m%d) 2>/dev/null || true
tar czf chroma_db.bak.$(date +%Y%m%d).tar.gz chroma_db/
```

**表结构变更流程**：改 `_init_db()` 的 `executescript` + 加幂等 `ALTER TABLE` 迁移（老库补列）→
同步更新 `02_核心数据结构定义.md` → 通知全员。

> 现有代码的写法是**新建库直接带新列 + 老库靠 `ALTER` 补列**，两条路径得到同一套结构，
> 省得迁移脚本和建表语句各写一遍。新字段照这个模式加。

### 3.5 禁止入库的文件（`.gitignore` 已覆盖）

`*.db`、`*.db-wal`、`*.db-shm`、`data/sessions.db`、`data/.auth_secret`、
`data/kb_owners.json`、`chroma_db/`、`data/uploads/`、`data/chat_uploads/`、`data/kb_sources/`

> ⚠️ **`data/.auth_secret` 迁移机器时必须一起带走**，否则所有人掉登录一次。
> 正式部署应在 `.env` 里显式设一个长随机串 `AUTH_SECRET`。

## 4. API 命名管理方式

### 4.1 现状与待拍板

| 口径 | 值 | 出处 |
| --- | --- | --- |
| 规划文档（T5 统稿） | `/api/v1` | `docs/挑战杯_最终分工与任务清单_v1.md` |
| **实际实现（35 个端点）** | **`/api`（无 v1）** | `main.py` 的 `include_router` |

> 🅿️ **按你的指示，本轮不拍板**。本节只把管理方式定下来，前缀本身留待后续决策。
> 相关背景：`docs/团队分支分析_20261013.md` 第四节 #1。

### 4.2 命名管理规则（**现在就生效**）

**规则 1 · 前缀只在 `main.py` 定义一次**

```python
app.include_router(kb_router, prefix="/api/kb", tags=["知识库"])
```

路由文件内部**只写相对路径**（`@router.get("/{kb_id}/")`），前缀统一在 `main.py` 挂载点决定。
→ 这样将来从前缀 `/api` 迁到 `/api/v1`，**只改 `main.py` 一处**。

**规则 2 · 路径全小写 + 连字符分词**

```
✅ /api/kb/import-search      /api/agent/tools/discover
❌ /api/kb/importSearch       /api/Agent/Tools
```

**规则 3 · 尾斜杠由本项目自己归一（不要动这套机制）**

`main.py` 设了 `redirect_slashes=False`，并用 `normalize_api_slash` 中间件把路径归一到已注册的形式。

> **踩过的坑**：前端走 Next rewrite，Next 默认**去**尾斜杠（308），FastAPI 默认**补**尾斜杠（307），
> 而 307 的 Location 指向 `localhost:8000`（Next 代理把 Host 改成了 localhost:8000），
> 浏览器照做就是去连自己那台机器的 8000 → 必然失败 → 「新建会话失败」。
> **新增端点时保持与现有斜杠约定一致，不要引入新的不一致。**

**规则 4 · 资源路径用名词复数**

```
✅ /api/sessions/     /api/templates/     /api/delegate/
❌ /api/getSessions   /api/createSession
```

**规则 5 · 动作型端点用动词子路径（仅限确实不是 CRUD 的操作）**

```
✅ POST /api/report/generate       POST /api/agent/tools/discover
✅ POST /api/schedule/run-now      POST /api/delegate/{id}/run
```

**规则 6 · 新增端点必须同步三处**

1. `main.py` 的挂载点（若新建路由文件）。
2. 本文档 §4.3 的端点索引表。
3. 前端 `frontend/src/lib/api.ts`。

**规则 7 · 鉴权默认开启**

业务 router 一律挂 `dependencies=[Depends(get_current_user)]`。
**只有 `auth` 路由**不带全局鉴权——登录页总得能打开。

**规则 8 · 契约零破坏**

现有 35 个端点的**路径、请求字段、响应形状一律不改**。
必须变更时：升级版本 + 同步前端 + 同步 `02_核心数据结构定义.md` + 通知全员。

## 5. Staging 环境部署（重点）

### 5.1 设计目标与隔离方式

**目标**：在**同一台 ECS** 上跑起一套与生产完全独立的实例，用于联调、验收、演示预演。

**三重隔离**

| 维度 | 生产 | Staging | 隔离手段 |
| --- | --- | --- | --- |
| 端口 | 3000 / 8000 | **3001 / 8001** | 不同监听端口，互不干扰 |
| 数据 | `data/`、`chroma_db/` | **`data-staging/`、`chroma-staging/`** | 不同目录，**绝不共用** |
| 配置 | `.env` | **`.env.staging`** | 独立密钥与配额；`ALLOW_SIGNUP` 可放开 |
| 代码 | `/root/agent-hub` | **`/root/agent-hub-staging`** | **两个独立 git 工作区**，各自 checkout |
| 日志 | `/tmp/baomi-*.log` | `/tmp/baomi-staging-*.log` | 不同文件 |
| PID | `/tmp/baomi-*.pid` | `/tmp/baomi-staging-*.pid` | 不同文件 |

> **为什么用两个工作区而不是同一目录切分支**：同一目录切分支会让生产代码在构建期间**处于半成品状态**，
> 前端 `.next` 也会被覆盖。两个工作区互不影响，代价只是多一份 `venv` 与 `node_modules`。

### 5.2 部署流程（首次）

```bash
# 0) 前置：确认生产在跑（别把生产搞挂）
bash deploy.sh status

# 1) 在服务器上克隆第二个工作区（分支锁定 dev）
cd /root
git clone git@github.com:baomi888/agent-hub.git agent-hub-staging
cd agent-hub-staging
git checkout dev

# 2) 准备 staging 配置（从模板复制，填独立的值）
cp .env.staging.example .env.staging
nano .env.staging
#    必填：DEEPSEEK_API_KEY / EMBEDDING_API_KEY / EMBEDDING_BASE_URL
#    必须确认：DATA_DIR=data-staging
#             PERSIST_DIR=chroma-staging
#             AUTH_SECRET=<另设一个，别和生产共用>

# 3) 一键部署 staging
bash deploy-staging.sh deploy
```

脚本完成后会自检并打印访问地址。

### 5.3 部署流程（日常更新）

```bash
cd /root/agent-hub-staging
bash deploy-staging.sh deploy     # 拉代码 + 装依赖 + 构建 + 重启
```

**`deploy-staging.sh` 子命令**

| 命令 | 作用 |
| --- | --- |
| `deploy` | 完整部署：拉取 → 依赖 → 构建 → 启动 |
| `start` | 只启动（跳过构建） |
| `stop` | 停止 |
| `restart` | 重启（不改代码） |
| `status` | 查看状态与健康检查 |
| `logs` | 跟踪日志（Ctrl+C 退出） |
| `rollback` | **回滚到上一个可用提交** |

### 5.4 CI/CD 自动部署 staging

**目标流程**：合并到 `dev` → 自动部署 staging。

```yaml
# .github/workflows/deploy-staging.yml（骨架，需配置 Secrets 后启用）
name: Deploy Staging
on:
  push:
    branches: [dev]
  workflow_dispatch:          # 也支持手动触发

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy over SSH
        uses: appleboy/ssh-action@v1
        with:
          host: ${{ secrets.STAGING_HOST }}
          username: ${{ secrets.STAGING_USER }}
          key: ${{ secrets.STAGING_SSH_KEY }}
          script: |
            cd /root/agent-hub-staging
            bash deploy-staging.sh deploy
```

**需要配置的 GitHub Secrets**

| Secret | 内容 |
| --- | --- |
| `STAGING_HOST` | ECS 公网 IP |
| `STAGING_USER` | `root` |
| `STAGING_SSH_KEY` | 部署用私钥（**专用密钥，不要用个人密钥**） |

> ⚠️ **密钥纪律**：CI 里的密钥只放 GitHub Secrets，**永不写进仓库**。
> 部署密钥只授权 staging 目录，不要给整机 root 免密。

### 5.5 健康检查与验收

**部署后必做**（脚本已内置，也可手动执行）：

```bash
# 后端健康
curl -s http://127.0.0.1:8001/health          # 期望 {"status":"ok",...}

# 前端首页
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3001/    # 期望 200

# 进程确认
pgrep -af "uvicorn main:app.*8001"
pgrep -af "next start" 
```

**验收清单（每次 staging 部署后）**

- [ ] `/health` 返回 200
- [ ] 前端首页可打开，**且登录页正常**
- [ ] 能完成一次完整问答（登录 → 新建会话 → 发消息 → 收到流式回答）
- [ ] 知识库列表加载正常（**不与生产串数据**）
- [ ] 若本次涉及调度模块：`/api/schedule/health` 心跳年龄正常（< 300s）
- [ ] 日志无异常堆栈：`bash deploy-staging.sh logs`

### 5.6 端口与防火墙

| 环境 | 需在阿里云安全组放行 |
| --- | --- |
| 生产 | `3000`（后端 8000 **不需要**，只监听回环） |
| Staging | **`3001`**（后端 8001 **不需要**） |

```bash
# 若服务器用 firewalld / ufw，也要放行 staging 前端端口
sudo firewall-cmd --permanent --add-port=3001/tcp && sudo firewall-cmd --reload
# 或
sudo ufw allow 3001/tcp
```

> **后端始终只监听 `127.0.0.1`**（8000 / 8001 都是），公网访问不到，无需放行。

### 5.7 回滚

```bash
cd /root/agent-hub-staging
bash deploy-staging.sh rollback      # 回到上一个可用提交并重启
```

> **原则：staging 上出问题先回滚，再排查**。不要在 staging 上"边修边试"——
> 它存在的意义就是提供一个可信的验收基线，一个坏掉的 staging 比没有更糟。

### 5.8 资源与注意事项

| 事项 | 说明 |
| --- | --- |
| **内存** | 2G 跑两套实例吃紧。**不要同时构建两端**，staging 构建时生产会变慢 |
| **磁盘** | 两套 `node_modules` + `.next` + `venv` 约占 1.5～2G，注意 `df -h` |
| **swap** | `deploy.sh` 已创建并写入 `/etc/fstab`，staging 复用即可 |
| **数据** | staging 数据可随时清空：`rm -rf data-staging chroma-staging`（**确认路径再执行**） |
| **密钥** | staging 用独立 `AUTH_SECRET`，避免有人拿 staging 的 token 打生产 |
| **合规** | staging 上不要放真实用户数据；`ALLOW_SIGNUP=0` 更安全 |

## 7. 常见故障排查

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 「新建会话 / 发消息全失败」 | 前后端尾斜杠不一致导致重定向黑洞 | 确认 `redirect_slashes=False` 与中间件未被改动 |
| 所有人掉登录 | `data/.auth_secret` 丢失或换机器未带走 | 在 `.env` 显式设 `AUTH_SECRET` |
| `no such table: users` | 脚本式自测被 pytest 收集 | 加进 `pytest.ini` 的 `--ignore` |
| `chromadb` 装不上 | Python 版本过高（3.14） | 换 Python 3.12 |
| 部署卡在第 5 步 | `requirements.txt` 注释写成了三引号 | 注释只能以 `#` 开头 |
| 前端构建 OOM | 2G 内存 | 已设 `--max-old-space-size=1536`；确保构建时无人同时构建 |
| staging 看到生产数据 | `.env.staging` 里 `DATA_DIR` / `PERSIST_DIR` 没改 | **立即停 staging**，改回独立目录，重新初始化 |
| 调度状态误报正常 | 只看进程表，没看心跳年龄 | 按心跳判：> 300s `stalled`，> 600s `down` |
