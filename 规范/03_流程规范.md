# 03 · 流程规范（分支 / 提交 / 审核 / CI-CD）

> 目的：让「代码怎么进来、怎么被检查、怎么发布」变成可预期的流水线，而不是靠人盯人。

---

## 1. Git 分支策略

### 1.1 分支模型（三分支 + 短命特性分支）

```
main     ●────────────●────────────────●──────────►  受保护，只接受 PR 合并，随时可发布
          \          /                  \
           \        /                    \
dev  ●──────●──────●──────────────────────●───────►  集成分支，日常开发的汇合点
      \    /        \                    /
       \  /          \                  /
feat/*  ●             ●───────●        ●            短命分支，一个功能一条，用完即删
```

| 分支 | 角色 | 谁能推 | 规则 |
| --- | --- | --- | --- |
| `main` | **稳定主干**，随时可部署生产 | **没人能直推** | 必须 PR + 至少 1 人 approve + CI 全绿 |
| `dev` | **集成分支**，联调与 staging 部署来源 | 开发者可推自己的特性分支合并 | PR 合并，CI 必须绿 |
| `feat/*`、`fix/*` | **短命特性分支** | 归属人 | 从 `dev` 切出，**生命周期 ≤ 5 天** |
| `hotfix/*` | 生产紧急修复 | 归属人 | 从 `main` 切出，修完同时合回 `main` 和 `dev` |

### 1.2 分支命名规范

```
<类型>/<模块>-<简述>-<日期>
```

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| `feat/` | 新功能 | `feat/kb-hybrid-search-20261020` |
| `fix/` | 修复 | `fix/report-to-thread-20261021` |
| `hotfix/` | 生产紧急修复 | `hotfix/login-500-20261022` |
| `docs/` | 仅文档 | `docs/team-standards-20261013` |
| `refactor/` | 重构（不改行为） | `refactor/search-unify-20261025` |

**模块名取值**：`frontend` / `kb` / `agent` / `api` / `core` / `deploy` / `campus`

> `campus` 为「校园工具集」独立板块（2026-10-31 新增），示例：
> `feat/campus-gpa-migrate-20261102`、`fix/campus-dark-theme-20261103`。
> 该板块的边界、版本与审核细则见 `campus/README.md`，提交作用域同样用 `campus`。

> ❌ 反例：`test`、`mybranch`、`临时`、`新分支2` —— 看不出干什么、谁负责、什么时候的。

### 1.3 分支操作标准流程

```bash
# 1) 从最新 dev 切出（永远基于 dev，不是 main）
git checkout dev && git pull origin dev
git checkout -b feat/kb-hybrid-search-20261020

# 2) 开发中定期同步 dev（避免长期分叉）
git fetch origin
git rebase origin/dev        # 或 git merge origin/dev，团队统一用 rebase

# 3) 推送并开 PR（目标分支：dev）
git push -u origin feat/kb-hybrid-search-20261020
```

**合并方向铁律**

- 特性分支 → `dev`：随时可合，CI 绿 + 1 人 approve。
- `dev` → `main`：**按节奏合**（见 §5），必须申请人 approve + 全量 CI 绿。
- `main` → `dev`：合并发布后立刻回流，保持 `dev` 不落后。

> ⚠️ **当前最大的流程问题**：`main` 比 `dev` 少 8 个提交、比 `feat/ai-module-20261013` 少 11 个。
> 队友成果全停在 `dev` / `feat` 上**没有回流 main**。这正是本节要根治的病。
> **建议收口时间：10/17 组会之后、10/18 联调之前**——早合早解决命名冲突，别拖到 10/20 申报稳定期。

### 1.4 合并冲突处理原则

1. **改名前先合**：`dev` / `feat` 不含改名提交（`204bb72` 知穗）与 UI 统一提交（`96e0dda`），
   合并时「苞米 / 知慧 / 知穗」会撞车。**先合代码、后统一改名**，一次只做一件事。
2. **冲突不要用 `--ours` / `--theirs` 一把梭**，逐块看，理解两边意图后再定。
3. **契约冲突优先保契约**：若冲突涉及接口字段，回到 `02_核心数据结构定义.md` 定夺。
4. **合完必须跑测试**，不能只看「无冲突标记」就认为合并成功。

## 2. 提交规范（Conventional Commits 中文版）

### 2.1 提交信息格式

```
<类型>: <简述>
```

或带作用域：

```
<类型>(<作用域>): <简述>
```

**要素**

| 部分 | 要求 |
| --- | --- |
| 类型 | **必填**，取值见下表 |
| 作用域 | 可选，取值：`ui` `kb` `agent` `api` `core` `deploy` `docs` `test` |
| 简述 | **必填**，中文，说清「做了什么」；≤ 50 字，**结尾不加句号** |
| 正文 | 可选，说清「**为什么**这么改」，而不是复述改了什么 |

### 2.2 类型取值

| 类型 | 含义 | 触发版本 |
| --- | --- | --- |
| `feat` | 新功能 | minor |
| `fix` | 修 bug | patch |
| `docs` | 仅文档 | — |
| `refactor` | 重构（**不改外部行为**） | — |
| `perf` | 性能优化 | patch |
| `test` | 增改测试 | — |
| `chore` | 构建 / 依赖 / 杂务 | — |
| `style` | 格式（不影响逻辑） | — |
| `revert` | 回滚 | — |

### 2.3 好提交 vs 坏提交

```
✅ feat(kb): 混合检索加 BM25+RRF，召回率提升 18%
✅ fix(api): report 端点同步调用包 to_thread，避免阻塞事件循环
✅ docs: 新增团队研发规范手册与分角色开发指南
✅ refactor(search): 搜索调用统一收口到 core/serper.py

❌ 改了一下
❌ fix bug
❌ update
❌ 提交
❌ feat: 新增功能、修了bug、改了样式、更新文档（一件事混杂四类改动）
```

> **一个提交只做一件事**。混杂提交无法 revert、无法 review、无法归因。
> 参考现有仓库的良好范例：`fix: 联网搜索偏向中国结果 + 资料库导入按名复用已有库避免建同名库`

### 2.4 提交粒度

- **一个逻辑变更 = 一个提交**。改 A 时顺手修了无关的 B，拆两个提交。
- **不要提交半成品**：每个提交都应让 `ruff check .` 与 `pytest -q` 通过。
- **不要提交生成物**：`data/`、`chroma_db/`、`.next/`、`node_modules/`、`venv/`、`*.db` 已在 `.gitignore`。

### 2.5 提交前自检清单

```bash
ruff check .                    # 静态检查必须无错
pytest -q                       # 离线测试必须全绿
cd frontend && npx tsc --noEmit # 前端类型检查必须 Exit 0
git status                      # 确认没有 .env / *.db / 密钥被误加
git diff --cached               # 逐行看一眼暂存区
```

> **提交 .env 是最高级别的安全事故**。`.env` 已被 `.gitignore` 忽略，但 `git add -f` 能绕过——
> **永远不要用 `git add -f` 加环境文件**。

## 3. 代码审核流程

### 3.1 PR 模板（必须填写）

```markdown
## 改动类型
<!-- feat / fix / docs / refactor / perf / test / chore -->

## 做了什么
<!-- 一两句话，说清这次改动的目的 -->

## 影响范围
- [ ] 前端
- [ ] 后端接口（是否破坏契约？是 / 否）
- [ ] 数据库结构（是否变更表结构？是 / 否）
- [ ] 部署方式
- [ ] 仅文档

## 验证方式
<!-- 贴出实际执行的命令与结果，例：pytest -q → 72 passed -->
- [ ] `ruff check .` 通过
- [ ] `pytest -q` 通过
- [ ] `npx tsc --noEmit` 通过（如涉及前端）
- [ ] 手动验证步骤：___

## 关联
<!-- 关联 issue / 任务编号（T7、T12 等） -->

## 自查
- [ ] 未提交任何密钥 / .env / *.db
- [ ] 已在 `02_核心数据结构定义.md` 同步字段变更（如有）
- [ ] 已补齐配套缺口（前端解析 / 错误文案 / 回归测试）
```

### 3.2 审核责任与时限

| 环节 | 责任人 | 时限 |
| --- | --- | --- |
| 自审 | 提 PR 的人 | 提 PR 前完成 §2.5 自检 |
| 代码审核 | **CODEOWNERS 指定的人**（见 `CODEOWNERS`） | **24 小时内**响应 |
| 最终合并 | 申请人 | — |

**审核意见分级**

| 标记 | 含义 | 处理 |
| --- | --- | --- |
| `[阻塞]` | 必须改，否则不合并 | 必须改完重新请求审核 |
| `[建议]` | 推荐改，可讨论 | 可协商，需说明不采纳理由 |
| `[提问]` | 只是想弄懂 | 回答即可 |
| `[表扬]` | 值得学习的写法 | 无需处理 |

### 3.3 审核清单（reviewer 视角）

**正确性**

- [ ] 边界条件：空值、超长、并发、重复提交
- [ ] 错误处理：异常有没有被吞、状态码对不对（429 vs 500 别混）
- [ ] **越权检查**：动会话/知识库的入口是否过了 `_owned` / 归属校验
- [ ] **`async def` 里有没有同步阻塞**（必须 `await asyncio.to_thread(...)`）

**契约与一致性**

- [ ] 接口字段变更是否同步了 `02_核心数据结构定义.md` 与前端 `lib/types.ts`
- [ ] 是否破坏现有 35 个端点的契约（**路径 / 请求字段 / 响应形状一律不改**）
- [ ] 横切逻辑是否补齐配套缺口（前端解析、错误文案、回归测试）

**工程性**

- [ ] 提交信息符合 §2 规范
- [ ] 测试是否覆盖新逻辑（只增不减，参考队友 28 → 72 的标准）
- [ ] 有没有把别人的文件改出边界（见 `01` §6）
- [ ] 有没有混入无关改动 / 调试代码 / `print` / 注释掉的死代码

**安全**

- [ ] 无硬编码密钥、真实 IP、个人信息
- [ ] SSRF / 鉴权 / 配额的改动同步更新了测试
- [ ] 错误信息没有回显用户输入

### 3.4 不可合并的情形（硬性拦截）

1. CI 未全绿。
2. 无 approve，或 approve 的人不是 CODEOWNERS 指定者。
3. 含 `.env` / 密钥 / `*.db`。
4. 破坏契约但未同步文档与前端。
5. PR 描述为空或未填写验证方式。

## 4. CI/CD 管线要求

### 4.1 现有 CI（`.github/workflows/ci.yml`）

```yaml
触发：push main、PR → main
任务：offline-tests（Python 3.11 / 3.12 / 3.13 矩阵）
执行：pytest 六个离线用例
```

**当前 CI 的两个不足（本次规范要求补齐）**

1. **触发分支漏了 `dev`** —— 而 `dev` 才是队友的集成分支，PR 到 `dev` 目前**完全没有 CI**。
2. **没有 lint、没有前端检查** —— `ruff` 与 `tsc --noEmit` 全靠人自觉。

### 4.2 目标管线（本规范要求）

```
PR 提交 / 推送
      │
      ├─► [job 1] lint          ruff check .                ← 快，先跑
      ├─► [job 2] offline-tests pytest 离线子集（3.11/3.12/3.13 矩阵）
      └─► [job 3] frontend      npm ci + tsc --noEmit + npm run build
                 │
                 ▼
          全绿 + 1 人 approve
                 │
                 ▼
        合并到 dev  → 自动部署 staging
                 │
                 ▼
        合并到 main → 手动批准后部署生产
```

### 4.3 分级测试要求

| 级别 | 用例 | 何时跑 | 要求 |
| --- | --- | --- | --- |
| **离线单元测试** | `test_chroma_singleton`、`test_upload_stream`、`test_retrieve_select`、`test_pipelines_concurrency`、`test_agent_checkpointer`、`test_agent_guard`（+`test_scenarios`、`test_grounding`、`test_slash_no_redirect`） | **每个 PR** | 必须全绿，**数量只增不减** |
| **集成测试** | `test_auth_gate`、`test_kb_isolation`、`test_owner_isolation`、`test_geo_locate`、`test_web_import_creates_index`、`test_w2`、`test_w3` | **合并到 dev 前手动跑** | 需真实后端 + `.env` + 登录态 |
| **真机冒烟** | 起真实 uvicorn 打真实 HTTP | **上 staging 前** | 参考标准：29 项全过 |

> **不写测试的功能不算完成**。新增端点必须带真机冒烟记录（贴命令与输出）。

### 4.4 CI 配置要求

- **必须**：触发分支包含 `main` **和** `dev`。
- **必须**：pip / npm 依赖使用缓存，缩短构建时间。
- **必须**：测试失败时输出可定位的信息，不要只有 exit code。
- **禁止**：在 CI 里跑需要真实 API Key 的用例（会烧钱且不稳定）。
- **禁止**：CI 里使用生产密钥；用 GitHub Secrets 且仅限 staging/prod 部署 job。
- **要求**：CI 时长控制在 **10 分钟内**，超时说明用例设计有问题。

### 4.5 CD（部署）要求

| 环境 | 触发方式 | 批准 |
| --- | --- | --- |
| **staging** | 合并到 `dev` 后**自动**部署 | 无需人工 |
| **生产** | 合并到 `main` 后**手动**触发 | 申请人批准 |

**部署前后置动作**

- 部署前：确认 `.env.staging` / `.env` 齐全、备份 `data/` 与 `chroma_db/`。
- 部署后：**必须**执行健康检查（`/health` 返回 200 + 前端首页可访问）。
- 失败：**立即回滚**到上一个可用提交，不要在 staging 上边修边试（生产同理）。

具体命令见 `04_环境与部署.md` 第 5 节。

### 4.6 版本与发布节奏

| 里程碑 | 内容 |
| --- | --- |
| M0 申报（10-20） | 接口设计 / 功能需求 / 申报书 / Mock Demo |
| M1 院赛 | 真实编码 + 联调 + 答辩 |
| M2 大众推广 | 院赛后收集反馈 |
| M3 校赛（12 月底） | 院赛通过 + 反馈达标才晋级 |

**版本号**：`main.py` 的 `FastAPI(version=...)` 与 `/health` 的 `version` 字段**必须同步更新**。
当前为 `0.3.0 (W3)`。
