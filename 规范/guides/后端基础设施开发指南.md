## 2. 认证体系

### 2.1 为什么全部用标准库实现

`requirements.txt` 会被 `deploy.sh` 逐行 `pip install`。引入 `passlib` / `PyJWT` 意味着
服务器上要多装两个包、还要关心版本锁。因此 `core/auth.py` 全部用标准库：

| 能力 | 实现 |
| --- | --- |
| 口令散列 | `hashlib.pbkdf2_hmac('sha256', ...)`，自带随机盐 + 轮数 |
| 令牌 | `hmac` + `base64` 手工实现的紧凑 JWT（HS256），签发/校验各十来行 |

接口保持标准形状，将来想换 argon2/bcrypt 或 PyJWT，**只改 `core/auth.py`，调用方一行都不用动**。

### 2.2 `core/account.py` —— 用户表与口令

存储串格式：`pbkdf2_sha256$<轮数>$<盐base64>$<摘要base64>`，盐 16 字节，摘要 32 字节。

| 常量 | 值 | 出处 |
| --- | --- | --- |
| `AUTH_PBKDF2_ROUNDS` | **200000** | `core/config.py`，可用 `.env` 覆盖 |
| `MIN_NAME` / `MAX_NAME` | 3 / 32 | `core/account.py` |
| `MIN_PASSWORD` / `MAX_PASSWORD` | 6 / 128 | `core/account.py` |

**几个刻意的设计（改动前先读）**

- **只卡密码长度，不卡复杂度**：自用型部署，复杂度规则逼出来的往往是 `Abcd1234!`
  这种人类记不住、撞库字典里却排前几的口令。
- **用户名不存在与口令错返回同一结果**：`authenticate()` 在用户不存在时会**故意走一次
  等价耗时的散列**（`verify_password(password, "pbkdf2_sha256$1$AA==$AA==")`），
  让两种失败的响应时间一致，避免被用来枚举注册用户。
- **`verify_password` 不抛异常**：存储串格式不对、轮数不是数字，一律返回 `False`。
- **`_public()` 刻意不含 `password_hash`**：漏一次就是全站口令泄露，靠自觉不如靠结构。
- **`COLLATE NOCASE` 唯一索引**：`Abc` 和 `abc` 不能各注册一份。
- **`create_user` 不自己吞 `IntegrityError`**：由 API 层翻译成 **409**。

### 2.3 `core/auth.py` —— 令牌签发与校验

```python
COOKIE_NAME = "baomi_session"  # 登录态 Cookie 名
payload = {"sub": user_id, "iat": now, "exp": now + days * 86400}
```

**为什么用 HttpOnly Cookie 而不是 Authorization 头**：前端走 Next 的 `/api/*` rewrite，
浏览器看来是**同源请求**，Cookie 天然带上，前端不需要存任何凭证；HttpOnly 又让 JS 读不到，
堵死 XSS 顺走 token 这条路。`SameSite=Lax`、`path="/"`。

> `Secure` 标志代码中**未设置**（只在注释里说明"只在 https 下加"）。
> 当前部署是公网 http，加了会直接丢 Cookie。**待确认**：上 HTTPS 后是否补 `secure=True`。

`decode_token` 的任何失败（格式错 / 签名不符 / 过期）统一返回 `None`，
用 `hmac.compare_digest` 做定长比较，不留计时侧信道。

### 2.4 `AUTH_SECRET` 的作用与「迁移机器」这个坑

**`_secret()` 的取值优先级**（`core/auth.py:75-97`）：

1. 环境变量 `AUTH_SECRET`（非空）
2. 数据目录里的 `data/.auth_secret` 文件（`config._AUTH_SECRET_FILE`）
3. 都没有 → 现生成 `secrets.token_urlsafe(48)` 并**落盘** `data/.auth_secret`，`chmod 0600`

落盘的目的就是**重启后登录态不失效**，否则每次重启所有人都要重新登录。

> 🔴 **迁移机器必须带走 `data/.auth_secret`，否则所有人掉登录。**
>
> 这个文件在 `.gitignore` 里（`data/.auth_secret`），所以 `git clone` **不会**把它带过来。
> 换机器 / 删 `data/` 目录 / 重建容器，都会让第 3 步重新生成一个新密钥 ——
> 旧令牌签名全部失效，**所有在线用户当场掉线**。
>
> **正式部署的正确做法**：在 `.env` 里显式设一个长随机串，让第 1 步直接命中：
>
> ```bash
> openssl rand -hex 32        # 生成后写进 .env 的 AUTH_SECRET=
> ```
>
> 这样即使 `data/` 整个丢失，登录态也不受影响。

> ⚠️ `data/.auth_secret` 已在 `.gitignore` 中，**不要为了"方便迁移"把它提交进仓库**。
> 迁移的正确姿势是单独传文件或改用显式 `AUTH_SECRET`。

### 2.5 相关配置项

| 变量 | 默认 | 作用 |
| --- | --- | --- |
| `AUTH_SECRET` | 空 | 令牌签发密钥；空则回落到 `data/.auth_secret` |
| `AUTH_TTL_DAYS` | `7` | 登录态有效期（天），同时决定 Cookie 的 `max_age` |
| `ALLOW_SIGNUP` | `1` | 是否开放自助注册；`0` 时 `POST /api/auth/register/` 返回 **403** |
| `AUTH_PBKDF2_ROUNDS` | `200000` | PBKDF2-SHA256 轮数。机器好可以调高，反之别低于 10 万 |
| `ADMIN_USERNAMES` | `苞米呀` | 管理员名单（逗号分隔），见 §4 |

### 2.6 `LEGACY_OWNER = "legacy"` 的默认拒绝设计

```python
# core/config.py
LEGACY_OWNER = "legacy"
```

多用户改造**之前**建的会话与知识库，其 `owner_id` 是 `NULL`。这套设计的选择是：

- 历史数据**先锁在 `legacy` 名下，谁都看不到**；
- 必须由 `tools/migrate_owner.py`（即 `core.session.claim_orphan_conversations`）
  **显式指派**给某个真人账号后才恢复可用。

> **为什么不做"无主即公开"的推断**：如果按"没人认领就大家都能看"处理，
> **第一个注册的人就把别人的历史数据顺手认领走了**。宁可暂时看不见，
> 也不能让归属在无人察觉的情况下发生转移。

### 2.7 认证端点清单（`api/auth.py`，全站唯一公开路由组）

| 方法 | 路径 | 鉴权 | 说明 |
| --- | --- | --- | --- |
| GET | `/api/auth/config/` | 公开 | 返回 `{"allow_signup": bool}`，登录页开关 |
| POST | `/api/auth/register/` | 公开 | 注册并直接登录；关闭注册时 403；重名 409 |
| POST | `/api/auth/login/` | 公开 | 登录；失败统一 401 |
| POST | `/api/auth/logout/` | 公开 | 退出（未登录时调用也返回 `ok`） |
| GET | `/api/auth/me/` | **需登录** | 当前身份 + 今日用量快照 |

> **登录/注册单独限流**：`_auth_rate_bucket(name)` 按**用户名**分桶、`limit=10`，
> 避免整站共用限流把正常问答也挡住（撞库脚本最爱的就是这两个端点）。
> 这里的 `RateLimited` 在端点内被 catch 后转成 **429**（`_reject(str(e), 429)`）——
> 这是**唯一**在端点内处理限流的地方，原因是需要保留按用户名分桶的语义。
> 其余所有配额/限流一律走 `main.py` 的全局异常处理器（见 §4）。

## 3. 多用户隔离

### 3.1 `_owned()` 是每个会话读写入口的第一道关

```python
# core/session.py:153
def _owned(owner: str, sid: str) -> bool:
    """会话 sid 是否属于 owner。老数据 owner_id 为 NULL，一律判 False。"""
    with _get_conn() as conn:
        row = conn.execute(
            "SELECT 1 FROM conversations WHERE id = ? AND owner_id = ?", (sid, owner)
        ).fetchone()
        return row is not None
```

**两条铁律**

1. **每个读写会话的入口都必须先过归属校验**，否则就是越权。
2. **`owner_id IS NULL` 的行永远判 `False`**，不做"无主即公开"的推断。

### 3.2 `owner` 是每个函数的第一个参数且**没有默认值**

```python
def create_conversation(owner: str, title: str = "新对话", kb_id: str | None = None) -> dict
def get_conversation(owner: str, sid: str) -> dict | None
def add_message(owner: str, sid: str, role, content, refs="") -> int
def add_feedback(owner: str, sid: str, msg_id, rating, comment="") -> bool
```

> **为什么刻意不给默认值**：如果给 `owner` 一个默认 `None` 再在 SQL 里写
> `WHERE owner_id = ?`，漏传的场景会退化成"查不到"（**看起来正常**）；
> 写成必需参数，漏传直接 `TypeError` / 启动失败。
> **宁可让漏改的调用点炸，也不要让它悄悄查到别人的数据。**

### 3.3 归属校验的三种落法

| 落法 | 用于 | 说明 |
| --- | --- | --- |
| 独立 `_owned()` | 写入口：`add_message`、`add_feedback`、`get_message`、`find_turn_ids`、`delete_messages`、`list_feedbacks` | 写比读危险，**纵深防御**值得多跑一次带索引的 EXISTS（约 0.1ms） |
| **并进 JOIN** | `get_messages`、`count_messages`、`feedback_stats` | 一次查询同时完成「验归属 + 取数据」，省掉独立 EXISTS |
| SQL 内联 `AND owner_id = ?` | `get_conversation`、`rename_conversation`、`bind_kb`、`delete_conversation` | 单表操作直接内联 |

**「不存在」与「不属于你」不区分**：`get_conversation` 两种情况都返回 `None`，
API 层都转成 **404**。区分了就等于告诉调用方"这个 id 存在但没权限"——
那是一条可以用来枚举别人会话 id 的信息。

**`NotOwned` 异常**（`core/session.py:252`）：`add_message` 在归属校验失败时抛出。
API 层正常流程下已经用 `get_conversation` 验过一次，这里再验一遍是纵深防御——
**不把写权限寄托在调用方记得校验**。

## 4. 配额与限流

### 4.1 两件事，尺度不同所以实现也不同

| 机制 | 载体 | 挡什么 | 为什么这样选 |
| --- | --- | --- | --- |
| **每分钟请求数** | 进程内滑动窗口 `_HITS` | 脚本式刷接口、手滑连点 | 单进程 uvicorn 下没人能绕过；**落库反而让"限流"自己变成写入热点** |
| **每日用量** | SQLite `usage` 表 | **账单事故**（一次建库几千个分片，embedding 按 token 计费） | 必须落库，否则重启一次就清零，等于没有限额 |

> 多副本部署时把内存窗口换成 Redis，**函数签名不用变**。

### 4.2 两个异常

```python
class RateLimited(Exception):
    def __init__(self, retry_after: float) -> None:
        super().__init__(f"操作过于频繁，请 {retry_after:.0f} 秒后再试")
        self.retry_after = retry_after


class QuotaExceeded(Exception):
    def __init__(self, kind: str, limit: int) -> None:
        label = {"ask": "每日问答", "embed": "每日向量化分片"}.get(kind, kind)
        super().__init__(f"{label}已达上限（{limit}），明天再试或联系管理员调整配额")
        self.kind = kind
        self.limit = limit
```

### 4.3 为什么用**全局异常处理器**而不是各端点 `try/except`

`main.py:166-183` 把这二者注册为 `@app.exception_handler`：

```python
@app.exception_handler(quota.RateLimited)
async def _on_rate_limited(request, exc):
    return JSONResponse(
        status_code=429,
        content={"detail": str(exc), "retry_after": round(exc.retry_after, 1)},
        headers={"Retry-After": str(int(exc.retry_after) + 1)},
    )


@app.exception_handler(quota.QuotaExceeded)
async def _on_quota_exceeded(request, exc):
    return JSONResponse(
        status_code=429,
        content={"detail": str(exc), "kind": exc.kind, "limit": exc.limit},
    )
```

> **原因（这是本节最重要的一段）**：端点自己 `catch` 容易顺手把它转成 **500**，
> **前端就分不清「系统出错」和「你今天用超了」**。
>
> 全局处理器让「抛异常」这一件事本身就意味着 429，
> **新增端点时只要用 `quota.*`，错误语义自动正确**，不需要每个端点重复写一遍。
> 这属于"从机制上堵住"，而不是"靠人记得写对"。

### 4.4 429 响应体的两种形状

| 触发 | 状态码 | 响应体 | 响应头 |
| --- | --- | --- | --- |
| 每分钟限流 `RateLimited` | 429 | `{"detail": "...", "retry_after": 12.3}` | `Retry-After: 13` |
| 配额超限 `QuotaExceeded` | 429 | `{"detail": "...", "kind": "ask", "limit": 60}` | 无 |

> 前端据 `retry_after` 显示「请 N 秒后再试」，据 `kind` 区分是问答还是向量化超限。
> 两种形状**刻意不同**——它们对应两种不同的用户动作（等一下 vs 明天再来）。

### 4.5 调用方式：四个函数，各有适用场景

| 函数 | 语义 | 用在哪 |
| --- | --- | --- |
| `hit(uid, limit=None)` | 记一次请求，超限抛 `RateLimited` | 每个用户主动发起的写操作入口 |
| `ensure(uid, kind)` | **只检查不记账** | 建库这类"动手前算不出会切多少片段"的操作，入口卡一道 |
| `consume(uid, kind, n=1)` | 检查并记账，超限抛 `QuotaExceeded`（**不实际扣**） | `kind="ask"` 这种能预先知道是"一次"的 |
| `guard(uid, kind)` | `hit()` + `ensure()` 的组合 | `kind="embed"` 这种按片段计费的 |

> **"超限时不扣"很重要**：否则重试的请求会继续把计数推高，
> 用户等到第二天零点还是解不开。

**实际用法**（`api/chat.py:297`）：

```python
conv = await asyncio.to_thread(store.get_conversation, uid, req.sid)
if not conv:
    raise HTTPException(status_code=404, detail=f"会话不存在：{req.sid}")

await asyncio.to_thread(quota.consume, uid, "ask")
```

> **先验会话再扣费**：无效请求（会话不存在）不该消耗每日问答额度。
> **必须在 `event_generator` 外面调用**：流一旦开始，响应头（200）就发出去了，
> 那时候再想回 429 已经来不及，只会变成一条断掉的 SSE 流，**前端读不出任何提示**。

### 4.6 `ADMIN_USERNAMES` 不受约束

```python
def _is_admin(uid: str) -> bool:
    """管理员不受配额与每分钟限流约束。"""
    names = getattr(config, "ADMIN_USERNAMES", None)
    if not names:
        return False
    from core import account

    u = account.get_user(uid)
    return bool(u) and u["username"] in names
```

- `hit()` / `ensure()` / `consume()` **三处入口都先判管理员直接放行**。
- `snapshot()` 对管理员附带 `unlimited: True`，前端据此显示"无限制"。
- `history()` 对管理员自然返回全 0（管理员不记账，语义上「管理员没额度」也说得通）。

> **为什么按 uid 反查用户名再比对**：名单写的是**人能读懂的名字**，
> 而配额系统全程只拿得到 **uid**。每次多一次 `users` 表点查，
> 频率极低（仅建库/问答这类用户主动操作），可接受。
>
> ⚠️ 默认值是 `苞米呀`（项目作者账号）。**换部署时必须在 `.env` 里改成自己的用户名**，
> 否则新部署上没有任何管理员。

### 4.7 每日用量表与限额

```sql
CREATE TABLE IF NOT EXISTS usage (
    user_id  TEXT NOT NULL,
    day      TEXT NOT NULL,
    kind     TEXT NOT NULL,
    count    INTEGER NOT NULL DEFAULT 0,
    PRIMARY KEY (user_id, day, kind)
);
```

- `day_key()` 用**本地时区**，形如 `2026-10-06`。理由：限额是给人看的，
  按服务器当地日子解释最好讲清楚。
- `bump_usage()` 用**原子 upsert**（`ON CONFLICT ... DO UPDATE SET count = count + excluded.count`），
  **不做"读-改-写"**。

| kind | 配置键 | 默认 | 语义 |
| --- | --- | --- | --- |
| `ask` | `DAILY_ASK_LIMIT` | 60 | 每日问答次数 |
| `embed` | `DAILY_EMBED_LIMIT` | 1000 | 每日向量化片段数 |
| — | `RATE_PER_MINUTE` | 10 | 每人每分钟请求上限（`0` = 不限） |

> ⚠️ `DAILY_EMBED_LIMIT` 是**防账单事故的闸门**（embedding 按 token 计费，一次建库几千片）。
> **别轻易设 0**（0 = 不限）。

## 5. 数据库与表结构演进

### 5.1 `_conn()` 按线程复用连接

```python
_LOCAL = threading.local()


def _conn() -> sqlite3.Connection:
    """取当前线程复用的 SQLite 连接（路径变了就重建）。"""
    path = _db_path()
    conn = getattr(_LOCAL, "conn", None)
    if conn is not None and getattr(_LOCAL, "path", None) == path:
        return conn
    if conn is not None:
        try:
            conn.close()
        except Exception:
            pass
    conn = sqlite3.connect(path)
    conn.row_factory = sqlite3.Row
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA synchronous=NORMAL")
    conn.execute("PRAGMA busy_timeout=5000")
    _LOCAL.conn = conn
    _LOCAL.path = path
    return conn
```

**为什么要按线程复用**：原本每次操作都新建连接（等于每次重开文件 + 重设 WAL），
**一次问答要开 6～7 个**。改成线程内复用后，连接只建一次、pragma 只设一次。

> 🔴 **为什么路径要参与判断**：**测试会 `monkeypatch core.session._db_path` 到临时目录**。
> 路径一变**必须**换连接，否则会继续读写上一个库 —— 表现为测试之间互相污染，
> 或者测试里写的数据跑到了真实库里。**这个判断不能删。**

`_get_conn()` 是 context manager：正常退出 `commit()`，异常 `rollback()` 后重抛。

> ⚠️ **`_get_conn()` 是跨关注点复用的**：`core/account.py` 与 `core/quota.py`
> 都直接 import 它，**不另开一套 SQLite 参数**——WAL / `row_factory` / 自动提交必须完全一致，
> 否则会出现一边读到另一边没提交的脏东西。

### 5.4 幂等迁移模式（新字段照这个加）

```python
def _init_db() -> None:
    with _get_conn() as conn:
        conn.executescript("""
            CREATE TABLE IF NOT EXISTS conversations (
                id TEXT PRIMARY KEY, owner_id TEXT, title TEXT NOT NULL, ...
            );
            ...
        """)
        # 迁移：老库补 refs 列（已存在则忽略）
        try:
            conn.execute("ALTER TABLE messages ADD COLUMN refs TEXT")
        except Exception:
            pass
        # 迁移：老库补 owner_id 列。旧行留 NULL = 谁都不属于，默认不可见
        try:
            conn.execute("ALTER TABLE conversations ADD COLUMN owner_id TEXT")
        except Exception:
            pass
        conn.execute("CREATE INDEX IF NOT EXISTS idx_conv_owner ON ...")
```

**模式的两条路径**

1. **新建库**：`CREATE TABLE IF NOT EXISTS` 的语句里**直接带新列**；
2. **老库**：靠 `ALTER TABLE ... ADD COLUMN` 补列，`except: pass` 保证已存在时忽略。

> **两条路径得到同一套结构，省得迁移脚本和建表语句各写一遍。**
> `refs` 与 `owner_id` 都是这么做进来的。**新字段照这个模式加。**

**改表结构的完整流程**（[`04_环境与部署.md`](../04_环境与部署.md) §3.4）：

1. **先备份**（SQLite 支持在线备份，不用停服务）：
   ```bash
   cp data/sessions.db data/sessions.db.bak.$(date +%Y%m%d)
   ```
2. 改 `_init_db()` 的 `executescript` + 加幂等 `ALTER TABLE`；
3. 同步更新 [`02_核心数据结构定义.md`](../02_核心数据结构定义.md)；
4. **通知全员**。

## 6. 中间件与路由机制（重点）

### 6.1 尾斜杠重定向黑洞：完整来龙去脉

**症状**：页面能正常打开，但**「新建会话 / 发消息 / 所有 `/api/*` 调用」全部失败**。
后端本身活着（`curl http://localhost:8000/health` 返回 `{"status":"ok"}`）。

**成因链条**（三方各自都"没错"，叠起来才是坑）：

```
前端调 /api/sessions/                （带尾斜杠）
     │
     ├─ ① Next.js rewrite 代理 /api/* → http://localhost:8000/api/*
     │
     ├─ ② Next.js 默认「去尾斜杠」：/api/sessions/ ──308──▶ /api/sessions
     │
     ├─ ③ 浏览器跟到 /api/sessions，Next 代理给后端
     │
     └─ ④ FastAPI 默认「补尾斜杠」：/api/sessions ──307──▶ /api/sessions/
               致命之处：这条 Location 是
               http://localhost:8000/api/sessions/
               （Next 代理把 Host 改成了 localhost:8000）
```

**为什么必然失败**：`localhost` 指的是**浏览器所在的那台机器**，不是服务器。
浏览器照着重定向走，就是去连**用户自己电脑**的 8000 端口 —— 那边什么都没有，
`fetch` 直接挂掉 → 前端报「新建会话失败」。

> 关键点：本项目前端发出的路径与后端路由的斜杠约定**其实完全一致**
> （有斜杠对有斜杠、无斜杠对无斜杠）。所以这不是"谁写错了一处"，
> 而是**两套框架各自的默认重定向叠加，再加上代理改写 `Host`**，
> 共同造出一个「指向你本机」的死重定向。

**本机实测的原始证据**：默认配置下 `GET /api/sessions` → `307`，
`Location: http://testserver/api/sessions/`。同一份代码在服务器上就是 `localhost:8000`。

### 6.2 修复方案 A：`redirect_slashes=False`

```python
app = FastAPI(
    # 关闭自动斜杠重定向：否则 /api/sessions 会被 307 到 /api/sessions/，
    # 而这条 Location 指向 localhost:8000，浏览器经 Next 代理必然拿不到 200
    redirect_slashes=False,
    ...
)
```

**只加这一条不够** —— 实测会变成 `404`（因为路径没被归一，路由匹配不上）。

### 6.3 修复方案 B：`normalize_api_slash` 中间件

```python
@app.middleware("http")
async def normalize_api_slash(request: Request, call_next) -> Response:
    path = request.scope.get("path", "")
    if path.startswith("/api/") and path != "/api/":
        has_slash = path.endswith("/")
        alt = path[:-1] if has_slash else path + "/"
        cache = getattr(request.app.state, "api_paths", None)
        if cache is None:
            cache = _collect_api_paths(request.app.routes)
            request.app.state.api_paths = cache

        def matches_any(p: str) -> bool:
            return any(_exact_matches(t, p) for t in cache)

        # 当前形式命中不了、但翻一个尾斜杠就能命中时，归一到能命中的那一种
        if not matches_any(path) and matches_any(alt):
            request.scope["path"] = alt
            if request.scope.get("raw_path") is not None:
                request.scope["raw_path"] = alt.encode()
    return await call_next(request)
```

**核心思路**：既然「已注册路径的斜杠约定是混合的」，就**按已注册集合来判断**，
而不是"一律补"或"一律去"。

> ⚠️ **不能用「一律补尾斜杠」的简单写法**：`/api` 路由的斜杠约定是**混合**的 ——
> `/api/sessions/`、`/api/kb/{kb_id}/` 带尾斜杠，
> 而 `/api/kb/create`、`/api/chat/stream`、`/api/kb/download` **不带**。
> 一律补会把 `POST /api/kb/create` 打成 **404**。中间件必须按已注册集合判断。

### 6.4 `_collect_api_paths` / `_exact_matches` 的作用

**`_collect_api_paths(routes)`** —— 收集所有已注册路由的完整路径（含 `/api` 前缀）：

```python
for r in rs:
    p = getattr(r, "route_path", None) or getattr(r, "path", None)
    if p:
        acc.add(p)
    erc = getattr(r, "effective_route_contexts", None)
    if callable(erc):
        try:
            for ctx in erc():
                cp = getattr(ctx, "route_path", None) or getattr(ctx, "path", None)
                if cp:
                    acc.add(cp)
        except Exception:
            pass
    sub = getattr(r, "routes", None)
    if sub is not None and sub is not rs:
        walk(sub)
```

> **为什么不能只看 `r.path`**：`include_router` 进来的路由是 `_IncludedRouter`，
> 其 `.path` 为 `None`，真实 `APIRoute` 收在 `effective_route_contexts()` 里、
> 且 `path` 是**相对前缀**的。**必须用 `route_path` 才能拿到带前缀的完整路径。**

**`_exact_matches(template, path)`** —— 判断路径是否**精确命中**模板：

- 按 `/` 切分后**段数必须相等** → 保证**尾斜杠严格**（`/api/sessions` 与 `/api/sessions/` 段数不同）；
- 逐段比较，`{param}` 形式的段视为**通配**。

**缓存**：路径集合缓存在 `request.app.state.api_paths`，**避免每次请求重建**。

**实测的对照结果**（`部署说明.md` §11）：

| 配置 | `GET /api/sessions` |
| --- | --- |
| 默认 FastAPI（修复前） | `307` + `Location: http://testserver/api/sessions/` ← 病根 |
| 只加 `redirect_slashes=False` | `404` |
| 再加中间件（生产版） | **`200`，无 `Location`** ✔ |

> 全量扫描：20 条 `/api` 路由 × 带/不带尾斜杠 × GET/POST = **80 次探测，0 次 3xx**。
> 回归测试已固化：`python tests/test_slash_no_redirect.py`（不联网，可直接跑）。

## 7. `async` 铁律

### 7.1 规则

> 🔴 **`async def` 里禁止同步阻塞调用，一律 `await asyncio.to_thread(...)`。**

**本项目所有同步 I/O 都必须丢线程**，理由是硬件的：

- SQLite 写约 2ms，但**一次问答会调 6～7 次**；
- `embed_query` 实测约 **250ms**；
- 同步 `llm.invoke()` / `agent.stream()` 一次十几秒。

单进程 uvicorn 下，**这些调用一旦裸跑就堵死整个事件循环**，
期间建库 / 上传 / 切会话**全部排队**，用户看到的是"整个网站卡住"。

### 7.2 正确写法

```python
# ✅ 数据库
conv = await asyncio.to_thread(store.get_conversation, uid, req.sid)
await asyncio.to_thread(store.add_message, uid, req.sid, "user", req.question)

# ✅ 配额（quota.py 里全是同步函数，别因为它只有 2ms 就裸调）
await asyncio.to_thread(quota.consume, uid, "ask")
await asyncio.to_thread(quota.hit, uid)

# ✅ 检索（embed_query 实测约 250ms）
pipe = await asyncio.to_thread(pipelines.get_or_create, uid, kb_id)
docs_scores = await asyncio.to_thread(pipe.retrieve_with_score, req.question, req.top_k)

# ✅ 并发取三个互不依赖的聚合
snap, hist, fb = await asyncio.gather(
    asyncio.to_thread(quota.snapshot, uid),
    asyncio.to_thread(quota.history, uid, 7),
    asyncio.to_thread(store.feedback_stats, uid),
)

# ✅ 后台并行任务（注意保留强引用，见下）
title_task = asyncio.create_task(asyncio.to_thread(_generate_title, req.question))
```

```python
# ❌ 反面：这些都会堵住事件循环
conv = store.get_conversation(uid, req.sid)
quota.consume(uid, "ask")
docs = pipe.retrieve_with_score(q, k)
```

### 7.4 两条容易踩的配套细节

**① 必须走 `astream`，不能走同步 `stream()`**

```python
# api/chat.py:464
# 必须走 astream：同步 stream() 会把整个事件循环堵住，
```

## 8. 部署脚本 `deploy.sh` 的 9 个步骤

脚本会**自动补齐运行环境**（Node ≥ 20.9、Python ≥ 3.10），
因为 Next.js 16 必须 Node 20+，LangChain 1.x 必须 Python 3.10+。

**子命令**

| 命令 | 作用 | `SKIP_BUILD` |
| --- | --- | --- |
| `bash deploy.sh` | 完整部署（默认动作） | `0` |
| `bash deploy.sh start` | 只启动 | `1` |
| `bash deploy.sh stop` | 只停止 | — |
| `bash deploy.sh restart` | 重启（=`stop` + `start`） | `1` |
| `bash deploy.sh status` | 状态（端口 / 进程 / 内存 / 磁盘） | — |
| `bash deploy.sh logs` | 跟踪日志（Ctrl+C 退出） | — |
| `bash deploy.sh env` | 只生成/检查 `.env` | — |

> ⚠️ **改了 `.ts` / `.tsx` 必须用 `deploy` 而不是 `restart`**：
> `restart` 带 `SKIP_BUILD=1`，`.next` 已存在就跳过构建 —— 用它等于白改。
> 纯 Python 改动才用 `restart`。

### 步骤 0 · 环境探测

```bash
log "0. 环境探测"
command -v curl >/dev/null 2>&1 || die "缺少 curl。..."
ARCH="$(uname -m)"
case "$ARCH" in
  x86_64|amd64) NODE_ARCH="x64" ;;
  aarch64|arm64) NODE_ARCH="arm64" ;;
  *) die "不支持的 CPU 架构：$ARCH" ;;
esac
```

- 先确认 `curl` 在位（后面所有下载/自检都靠它）；
- 按 CPU 架构决定 Node 包的架构；
- 读 `/etc/os-release` 打印系统信息。

### 步骤 1 · 补齐 Node（≥ 20.9，走 npmmirror）

```bash
NODE_WANT_VER="v20.19.0"          # 国内走 npmmirror，比 NodeSource 快且稳
```

- 已有 Node 且主版本 ≥ 20 → 直接用；
- 否则从 `https://cdn.npmmirror.com/binaries/node/...` 下载（约 25MB），
  解压到 `/usr/local`，`hash -r` 刷新；
- 下载失败时给出 NodeSource 的手动安装命令（dnf / apt 两套）后 `die`。

### 步骤 2 · 补齐 Python（≥ 3.10）+ swap

**Python**：`pick_py()` 按 `python3.13 → 3.12 → 3.11 → 3.10 → python3` 顺序找，
用 `sys.version_info >= (3,10)` 实际验证（不只看命令名存不存在）。
找不到就用 dnf / yum / apt 装 `python3.11`，装完 `hash -r` 再找一次。

**swap**（第 3 步，2 核 2G 的保命符）：

```bash
log "3. 检查 swap（2 核 2G 必做，否则前端构建会内存溢出）"
if swapon --show 2>/dev/null | grep -q .; then
  ok "swap 已存在："
else
  warn "没有 swap，创建 2G（约 1 分钟）"
  $SUDO fallocate -l 2G /swapfile || $SUDO dd if=/dev/zero of=/swapfile bs=1M count=2048
  $SUDO chmod 600 /swapfile
  $SUDO mkswap /swapfile
  $SUDO swapon /swapfile
  grep -q '^/swapfile' /etc/fstab || echo '/swapfile none swap sw 0 0' | $SUDO tee -a /etc/fstab
fi
```

> 写入 `/etc/fstab` 是为了**重启后仍然生效**。
> 创建失败只 `warn` 不 `die`（不影响继续，但构建有 OOM 风险）。

### 步骤 4 · 检查 `.env`（含密钥有效性判断 `key_ok`）

没有 `.env` 就从 `.env.example` 复制一份，然后**打印清单并 `exit 0`**（不盲目往下跑）。

**关键：`key_ok()` 判断一个值是不是"真的密钥"**

```bash
env_val() { grep -E "^[[:space:]]*$1[[:space:]]*=" .env | tail -1 | cut -d= -f2- | tr -d '"'"'"' \r'; }

# 判断一个值是不是"真的密钥"：空值 / 中文占位符 / 常见占位词 / 太短 都不算
# （.env.example 里的占位文本是"在此粘贴你的 xxx_key"，必须能识别出来）
key_ok() {
  local v="$1"
  [ -n "$v" ] || return 1                                          # ① 空值
  printf '%s' "$v" | LC_ALL=C grep -q '[^ -~]' && return 1          # ② 含非 ASCII（中文占位符）
  case "$v" in
    *your*|*Your*|*YOUR*|*xxx*|*XXX*|*changeme*|*placeholder*|*填入*|*粘贴*|*替换*) return 1 ;;   # ③ 常见占位词
  esac
  [ "${#v}" -ge 16 ] || return 1                                    # ④ 长度 < 16
  return 0
}

# 这三项和后端 core/config.py 的 validate() 保持一致
REQUIRED_KEYS="DEEPSEEK_API_KEY EMBEDDING_API_KEY EMBEDDING_BASE_URL"
```

| # | 判为"不是真密钥"的条件 | 为什么 |
| --- | --- | --- |
| ① | 空值 | 没填 |
| ② | 含非 ASCII 字符（`[^ -~]`） | 中文占位符「在此粘贴你的 DeepSeek_API_key」 |
| ③ | 含 `your` / `xxx` / `changeme` / `placeholder` / `填入` / `粘贴` / `替换` | 常见占位词 |
| ④ | 长度 < 16 | 真密钥不会这么短 |

`.env.example` 里的占位文本正是「在此粘贴你的 xxx_key」，**这套判断必须能识别出来**。

**可选密钥只 `warn` 不拦**：

```bash
for k in SERPER_API_KEY AMAP_API_KEY; do
  key_ok "$(env_val "$k")" || warn "$k 未填 —— 对应的「联网搜索 / 天气」工具会不可用，不影响基本对话"
done
```

`bash deploy.sh env` 在此处 `exit 0`（只检查 `.env`）。

### 步骤 5 · 后端 venv 装依赖

```bash
log "5. 后端依赖（venv）"
if [ ! -x venv/bin/python ]; then
  "$PY" -m venv venv || { ... 自动补装 venv 组件 ... }
fi
. venv/bin/activate
python -m pip install -U pip -i "$PIP_MIRROR" -q
pip install -r requirements.txt -i "$PIP_MIRROR" --no-cache-dir
```

- `PIP_MIRROR="https://pypi.tuna.tsinghua.edu.cn/simple"`（清华镜像）；
- venv 创建失败时按 apt / dnf 自动补装 `venv` / `pip` / `devel` 组件，
  仍失败则打印错误详情并 `die`。

> ⚠️ **`requirements.txt` 是 pip 格式，注释只能以 `#` 开头。**
> 曾因写成三引号把整次部署卡死（2026-10-03）：pip 报 `Invalid requirement`，
> **第 5 步直接中止**。`requirements.txt` 头部有醒目注释警告这一点。

### 步骤 6 · 前端构建

```bash
if [ "${SKIP_BUILD:-0}" = "1" ] && [ -d frontend/.next ]; then
  log "6. 跳过前端构建（start 模式且已有 .next）"
else
  log "6. 前端依赖与构建（2G 内存约 3~8 分钟，请耐心等）"

  if [ -f package-lock.json ]; then
    npm ci --no-audit --no-fund || npm install --no-audit --no-fund || die "前端依赖安装失败"
  else
    npm install --no-audit --no-fund || die "前端依赖安装失败"
  fi
  NODE_OPTIONS="--max-old-space-size=1536" npm run build || die "前端构建失败，请把上面的报错发我"
  cd "$ROOT"
fi
```

> - `NODE_OPTIONS=--max-old-space-size=1536` 是**为了 2G 内存机器定的**；
> - 2G 内存下构建约 **3～8 分钟**；
> - **构建期间不要同时跑 staging 构建**，否则两端都会变慢 / OOM。
> - `die` 的话术是「请把上面的报错发我」——**不要把报错吞掉**。

### 步骤 7 · 启动（后台常驻）

```bash

# 前端靠 next.config.ts 的 /api/* rewrite 从本机访问它，功能不受影响；

  > /tmp/baomi-back.log 2>&1 &

PORT="$FRONT_PORT" nohup npm run start > /tmp/baomi-front.log 2>&1 &

```

| 项 | 值 |
| --- | --- |
| 后端端口 | `BACK_PORT=8000`，**`--host 127.0.0.1`** |
| 前端端口 | `FRONT_PORT=3000`，通过 `PORT` 环境变量传给 `npm run start` |
| 后端日志 / PID | `/tmp/baomi-back.log` / `/tmp/baomi-back.pid` |
| 前端日志 / PID | `/tmp/baomi-front.log` / `/tmp/baomi-front.pid` |
| 前端模式 | **生产模式 `next start`**，不是 `next dev`（`dev` 在 2G 机器上会吃满内存） |

> **为什么后端只监听回环**：前端靠 Next 的 `/api/*` rewrite 访问它，功能不受影响；
> 少一层暴露面就少一层风险，而且 `:8000` 直连**绕过了 Next 的 Cookie 域设置**，
> 容易踩登录态丢失的坑。
>
> ⚠️ **注释里那句"后端没有任何鉴权"已过时**（`main.py:208` 已说明现状：
> "现在虽然已经加了登录鉴权，仍然保持回环"）。结论不变，**说明文字待更新**。

## 9. Staging 部署

### 9.1 设计目标与三重隔离

**目标**：在**同一台 ECS** 上跑起一套与生产完全独立的实例，用于联调、验收、演示预演。
只有一台 2 核 2G 的 ECS，另开机器成本高。

| 维度 | 生产 | Staging | 隔离手段 |
| --- | --- | --- | --- |
| **端口** | 3000 / 8000 | **3001 / 8001** | 不同监听端口，互不干扰 |
| **数据** | `data/`、`chroma_db/` | **`data-staging/`、`chroma-staging/`** | 不同目录，**绝不共用** |
| **配置** | `.env` | **`.env.staging`** | 独立密钥与配额；`ALLOW_SIGNUP` 可放开 |
| **代码** | `/root/agent-hub` | **`/root/agent-hub-staging`** | **两个独立 git 工作区**，各自 checkout |
| 日志 | `/tmp/baomi-*.log` | `/tmp/baomi-staging-*.log` | 不同文件 |
| PID | `/tmp/baomi-*.pid` | `/tmp/baomi-staging-*.pid` | 不同文件 |

> **为什么用两个工作区而不是同一目录切分支**：同一目录切分支会让生产代码在构建期间
> **处于半成品状态**，前端 `.next` 也会被覆盖。两个工作区互不影响，
> 代价只是多一份 `venv` 与 `node_modules`。

> `deploy-staging.sh` 里的常量与 `deploy.sh` **刻意错开**：
> `BACK_PORT=8001`、`FRONT_PORT=3001`、`STAGING_BRANCH="dev"`、
> `ENV_FILE=".env.staging"`、日志/PID 全部带 `-staging`。

### 9.2 首次部署

```bash
# 0) 前置：确认生产在跑（别把生产搞挂）
bash deploy.sh status

# 1) 在服务器上克隆第二个工作区（分支锁定 dev）
cd /root
git clone git@github.com:baomi888/agent-hub.git agent-hub-staging
cd agent-hub-staging
git checkout dev

# 2) 准备 staging 配置（从模板复制，填独立的值）
cp .env.staging.example .env.staging
nano .env.staging
#    必填：DEEPSEEK_API_KEY / EMBEDDING_API_KEY / EMBEDDING_BASE_URL
#    必须确认：DATA_DIR=data-staging
#             PERSIST_DIR=chroma-staging
#             AUTH_SECRET=<另设一个，别和生产共用>

# 3) 一键部署 staging
bash deploy-staging.sh deploy
```

**`.env.staging` 与生产的差异**（`.env.staging.example` 实测）：

| 变量 | 生产 | Staging |
| --- | --- | --- |
| `DATA_DIR` | `data` | **`data-staging`** |
| `PERSIST_DIR` | `chroma_db` | **`chroma-staging`** |
| `DOWNLOAD_DIR` | （默认） | `downloads-staging` |
| `AUTH_SECRET` | 显式设置 | **另设一个**（`openssl rand -hex 32`） |
| `ALLOW_SIGNUP` | `0`（正式） | `1` |
| `RATE_PER_MINUTE` | `10` | **`60`**（联调放宽，避免正常测试被 429 打断） |
| `DAILY_ASK_LIMIT` | `60` | **`0`**（不限） |
| `DAILY_EMBED_LIMIT` | `1000` | `2000`（**仍不设 0**，防账单事故） |

> ⚠️ **即使 staging 也不要轻易把 `DAILY_EMBED_LIMIT` 设 0**。

### 9.3 `deploy-staging.sh` 的安全护栏

这是本脚本与 `deploy.sh` 最本质的差别 —— **它必须不可能误杀生产**。

```bash
assert_is_staging_workspace() {

    die "当前目录没有 $ENV_FILE。
     这说明你多半在生产目录里跑了 staging 脚本 —— 请先切到 staging 工作区：
       cd /root/agent-hub-staging"
  fi
  case "$ROOT" in
    *staging*) : ;;
    *) warn "当前目录名不含 'staging'（$ROOT）。确认这是 staging 工作区再继续。" ;;
  esac
}
```

**部署前的硬拦截（`die`，不是警告）**：

```bash
if [ "${DATA_DIR_V:-data}" = "data" ] || [ -z "${DATA_DIR_V:-}" ]; then
  die "DATA_DIR 必须是 data-staging（当前：${DATA_DIR_V:-<空，会退回生产默认 data>}）。
     staging 与生产共用数据目录会污染生产用户数据，脚本拒绝继续。"
fi
if [ "${PERSIST_DIR_V:-chroma_db}" = "chroma_db" ] || [ -z "${PERSIST_DIR_V:-}" ]; then
  die "PERSIST_DIR 必须是 chroma-staging（当前：${PERSIST_DIR_V:-<空，会退回生产默认 chroma_db>}）。
     向量库共用会导致 chroma 并发写损坏索引，脚本拒绝继续。"
fi
```

**停止服务时按端口精确匹配，绝不用宽泛的 `pkill`**：

```bash
# 兜底：按端口精确匹配，绝不用宽泛的 pkill -f "uvicorn main:app"
pkill -f "uvicorn main:app.*--port ${BACK_PORT}" >/dev/null 2>&1 || ...
```

**`status` 会顺带只读地看一眼生产状态**（不干预），避免 staging 挤压生产还不自知。

### 9.4 子命令

| 命令 | 作用 | 说明 |
| --- | --- | --- |
| `deploy` | 完整部署：**拉取 → 依赖 → 构建 → 启动** | `SKIP_BUILD=0; SKIP_PULL=0` |
| `start` | 只启动（跳过构建与拉取） | `SKIP_BUILD=1; SKIP_PULL=1` |
| `stop` | 停止 | 只动 3001/8001 |
| `restart` | 重启（不改代码） | `stop` + `SKIP_BUILD=1; SKIP_PULL=1` |
| `status` | 查看状态与健康检查 | 含数据目录隔离检查 + 生产状态 |
| `logs` | 跟踪日志（Ctrl+C 退出） | `-staging` 两个日志 |
| `env` | 只检查 `.env.staging` | — |
| `rollback` | **回滚到上一个可用提交** | 见 §9.6 |

**拉代码的方式**（`deploy` 模式）：

```bash
if ! git diff --quiet; then
  warn "工作区有未提交改动，已 stash 以避免冲突"
  git stash push -u -m "deploy-staging auto $(date +%Y%m%d-%H%M%S)" || true
fi
git fetch origin "$STAGING_BRANCH" || die "拉取失败，检查 git 凭据/网络"
git checkout "$STAGING_BRANCH" 2>/dev/null || git checkout -b "$STAGING_BRANCH" "origin/$STAGING_BRANCH"
git reset --hard "origin/$STAGING_BRANCH" || die "切换失败"
```

> 注意是 **`git reset --hard origin/dev`**：staging 工作区是**一次性的部署目标**，
> 本地改动一律 stash 后丢弃。**不要在这个工作区里做开发。**

**构建时会带上 staging 标记**：

```bash
NEXT_PUBLIC_STAGING=1 NODE_OPTIONS="$NODE_OPTIONS_BUILD" npm run build
```

### 9.5 CI 自动部署 staging

**目标流程**：合并到 `dev` → 自动部署 staging。

```yaml

  push:
    branches: [dev]
  workflow_dispatch:          # 也支持手动触发
```

### 9.6 回滚

```bash
cd /root/agent-hub-staging
bash deploy-staging.sh rollback      # 回到上一个可用提交并重启
```

`do_rollback()` 的实际动作：

1. 确认当前目录是 git 仓库；
2. **有未提交改动先 `git stash push -u`**（避免丢失）；
3. `git reset --hard HEAD~1`；
4. `do_stop` → `"$0" start`（注意是 `start`，**跳过构建**，用已有的 `.next`）。

> **原则：staging 上出问题先回滚，再排查**。不要在 staging 上"边修边试"——
> 它存在的意义就是提供一个可信的验收基线，**一个坏掉的 staging 比没有更糟**。

- [ ] `/health` 返回 200
- [ ] 前端首页可打开，**且登录页正常**

- [ ] 知识库列表加载正常（**不与生产串数据**）
- [ ] 若本次涉及调度模块：`/api/schedule/health` 心跳年龄正常（< 300s）
- [ ] 日志无异常堆栈：`bash deploy-staging.sh logs`

```bash
curl -s http://127.0.0.1:8001/health                             # 期望 {"status":"ok",...}
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3001/   # 期望 200

```

### 9.8 资源与注意事项

| 事项 | 说明 |
| --- | --- |
| **内存** | 2G 跑两套实例吃紧。**不要同时构建两端**，staging 构建时生产会变慢 |
| **磁盘** | 两套 `node_modules` + `.next` + `venv` 约占 **1.5～2G**，注意 `df -h` |

## 11. 测试收集规则

### 11.1 `tests/` 下混着两种文件

| 类型 | 特征 | 执行方式 |
| --- | --- | --- |
| **pytest 风格** | 定义 `test_*` 函数 | 由 pytest 收集执行 |
| **脚本式自测** | 模块级执行 + `sys.exit` / `assert` 结尾 | 设计上就是 `python tests/test_xxx.py` 直接跑 |

### 11.2 为什么必须逐文件 `--ignore`

```ini
[pytest]
addopts =
    --ignore=tests/test_auth_gate.py
    --ignore=tests/test_geo_locate.py
    --ignore=tests/test_kb_isolation.py
    --ignore=tests/test_owner_isolation.py
    --ignore=tests/test_retrieve_select.py
    --ignore=tests/test_slash_no_redirect.py
    --ignore=tests/test_w1.py
    --ignore=tests/test_w2.py
    --ignore=tests/test_w3.py
```

> 脚本式文件被 pytest 收集时会**整段在「收集阶段」执行**，两个副作用：
>
> 1. 每个文件都 `monkeypatch core.session._db_path` 到自己的临时目录，
>    而 **`core.account` 的建表只会在进程内跑一次（import 缓存）**，
>    一旦先被别的模块导入，`users` 表就建到了**真实库**，
>    临时库里没有 → **`no such table: users`**；
> 2. `sys.exit` / `assert` 直接抛在**收集阶段**，
>    pytest 报一堆和测试本身无关的 error。

**根因链条**（拿 `test_auth_gate.py` 的头部实际看）：

```python
_TMP = tempfile.mkdtemp(prefix="baomi_auth_test_")
import core.config  # 先让 chdir / load_dotenv 跑完
import core.session

core.session._db_path = lambda: os.path.join(_TMP, "sessions.db")
core.session._init_db()  # 在临时库里把 conversations / messages 建出来
...
from core import account  # ← 这个 import 才触发 account._ensure_tables()
```

`core/account.py` 的模块级 `_ensure_tables()` 用 `_get_conn()` 建 `users` 表——
**进程内只跑一次**。多个脚本式文件在同一 pytest 进程里被收集时，
**第一个 import 的那次决定了表建到哪个库**，后面的文件换路径也不会重建。

**所以：`pytest.ini` 逐文件 `--ignore` 了脚本式自测，跑 pytest 就只剩 17 个 pytest 风格用例。**

### 11.3 新增用例时的规则

> 🔴 **新增脚本式用例必须同步加进 `pytest.ini` 的 `--ignore`。**

判断标准很简单：文件末尾是不是 `sys.exit(1)` / `assert` 这种**模块级执行**？
是 → 脚本式 → 加 `--ignore`，并确认 `python tests/test_xxx.py` 能独立跑通。

本模块常用：

```
feat/core-quota-per-user-20261020
fix/api-slash-redirect-20261021
feat/deploy-staging-workflow-20261022
fix/core-owner-isolation-20261023
chore/deploy-node-version-20261024
```

**流程**（永远基于 `dev`）：

```bash
git checkout dev && git pull origin dev
git checkout -b feat/core-quota-per-user-20261020
# 开发中定期同步，避免长期分叉
git fetch origin && git rebase origin/dev
git push -u origin feat/core-quota-per-user-20261020
```

> ❌ 反例：`test`、`mybranch`、`临时`、`新分支2` —— 看不出干什么、谁负责、什么时候的。
>
> ⚠️ 分支**生命周期 ≤ 5 天**。

### 13.3 提交信息

格式：`<类型>: <简述>` 或 `<类型>(<作用域>): <简述>`

| 类型 | 含义 |
| --- | --- |
| `feat` / `fix` / `docs` / `refactor` / `perf` / `test` / `chore` / `style` / `revert` | 见 `03` §2.2 |

**作用域取值**：`ui` `kb` `agent` `api` `core` `deploy` `docs` `test`

**要求**：简述中文、说清「做了什么」、**≤ 50 字、结尾不加句号**；
正文说清「**为什么**这么改」，而不是复述改了什么。

```
✅ feat(core): 配额改为按 uid 落库计数，重启不再清零
✅ fix(api): 会话列表补归属过滤，修复跨用户可见
✅ docs: 新增分角色开发指南
✅ refactor(core): SQLite 连接改为按线程复用，一次问答少开 6 个连接

❌ 改了一下
❌ fix bug
❌ update
❌ feat: 新增功能、修了bug、改了样式、更新文档（一件事混杂四类改动）
```

**粒度**：一个逻辑变更 = 一个提交；**不要提交半成品**
（每个提交都应让 `ruff check .` 与 `pytest -q` 通过）。

### 13.4 PR 必备项

- [ ] 填写 PR 模板（改动类型 / 做了什么 / 影响范围 / **验证方式贴命令与输出** / 关联 / 自查）
- [ ] 明确声明**是否破坏契约**、**是否变更表结构**
- [ ] 自查「未提交任何密钥 / `.env` / `*.db`」
- [ ] 已同步 `02_核心数据结构定义.md`（如有字段变更）
- [ ] 已补齐配套缺口（前端解析 / 错误文案 / 回归测试）

**不可合并的硬性拦截**（`03` §3.4）：CI 未全绿 / 无 approve / 含 `.env` 与密钥 /
破坏契约未同步 / PR 描述为空。
