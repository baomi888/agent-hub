## 2. 本地启动

### 2.1 先起后端（必须）

前端**不直连**后端端口，全靠 `/api/*` rewrite 代理到 `http://localhost:8000`。
**后端没起来 → 前端所有接口连不上，登录门都过不去。**

```bash
# 仓库根目录
python -m venv venv
venv\Scripts\activate                     # Linux/macOS: source venv/bin/activate
pip install -r requirements.txt
copy .env.example .env                    # 填 DEEPSEEK_API_KEY / EMBEDDING_API_KEY / EMBEDDING_BASE_URL
python main.py                            # 监听 127.0.0.1:8000

curl http://127.0.0.1:8000/health         # 期望 {"status":"ok","version":"0.3.0 (W3)"}
```

### 2.2 再起前端

```bash
cd frontend
npm install
npm run dev                               # http://localhost:3000
```

### 2.3 启动自检

| # | 检查项 | 期望 |
| --- | --- | --- |
| 1 | `curl http://127.0.0.1:8000/health` | `{"status":"ok",...}` |
| 2 | 打开 `http://localhost:3000` | 先显示「正在确认登录状态...」，随后进登录门 |
| 3 | 注册 / 登录 | 进入三栏工作台，不是白屏 |
| 4 | 新建会话并提问 | 回答**逐字流式**出现（不是整段蹦出） |
| 5 | DevTools → Network | 请求 URL 都是**相对路径** `/api/...`，不是 `localhost:8000/api/...` |

> **端口约定**：本地前端 `3000` / 后端 `8000`；Staging 前端 `3001` / 后端 `8001`。
> **后端始终只监听 `127.0.0.1`**，公网只暴露前端端口（`04_环境与部署.md` §5.6）。

## 3. 前后端如何通信

### 3.1 rewrite 代理机制

`next.config.ts` 全文只有两项配置，第二项即代理：

```ts
const nextConfig: NextConfig = {
  output: "standalone",
  async rewrites() {
    return [{ source: "/api/:path*", destination: "http://localhost:8000/api/:path*" }];
  },
};
```

所以**前端代码里只写相对路径**：`fetch("/api/sessions/")` 由 Next 服务端转发到 `http://localhost:8000/api/sessions/`。

### 3.2 为什么前端不直连 8000

| 原因 | 说明 |
| --- | --- |
| **避免跨域** | 3000 与 8000 不同源，直连触发 CORS 预检，后端未为此开放 |
| **登录态在 HttpOnly Cookie** | 同源才能稳定携带；`:8000` 直连会绕过 Next 的 Cookie 域设置，丢登录态 |
| **少一层暴露面** | 后端只监听回环，公网只暴露 `:3000`，生产无需放行 8000 |
| **尾斜杠归一** | 后端 `redirect_slashes=False` + `normalize_api_slash` 中间件，直连易踩 307 黑洞 |

> ⚠️ **尾斜杠的坑（踩过）**：Next 默认**去掉**尾斜杠（308），FastAPI 默认**补上**尾斜杠（307），
> 而 307 的 `Location` 指向 `localhost:8000`（代理把 Host 改了），浏览器照做就是去连用户自己那台机器的 8000 → 必然失败。
> 因此 `lib/api.ts` 的 `request()` 会**主动去掉请求路径的尾斜杠**（`cleanPath`）。

### 3.3 请求统一走 `lib/api.ts`

`request<T>()` 是所有 JSON 接口的公共壳，做三件事：

```ts
// frontend/src/lib/api.ts（节选）
const cleanPath = path.length > 1 && path.endsWith("/") ? path.slice(0, -1) : path;
const res = await fetch(cleanPath, {
  credentials: "include",                        // HttpOnly Cookie 同源也要显式带
  headers: { "Content-Type": "application/json" },
  ...init,
});
if (!res.ok) throw await httpError(res);          // 统一错误翻译
return res.json() as Promise<T>;
```

**两个例外**（`FormData` 不能手设 `Content-Type`，故绕过 `request()`，但复用同一个 `httpError`）：
`api.uploadFiles`（`POST /api/kb/{kbId}/upload`）与 `api.uploadChatAttachments`（`POST /api/chat/upload`）。

### 3.4 SSE 流式解析（`lib/sse.ts`）

**为什么不用 `EventSource`**：它只支持 GET，而聊天要 POST（带 sid / question / mode / 附件）。
故 `streamChat()` 用 `fetch` + `ReadableStream` 手写解析，签名是
`AsyncGenerator<StreamEvent>`，帧格式为 `` `event: X\ndata: {json}\n\n` ``。

解析流程（`lib/sse.ts` 真实实现）：

1. `fetch("/api/chat/stream", { method: "POST", credentials: "include", body, signal })`。
2. `res.ok` 为假：若是 **401** 则 `window.dispatchEvent(new Event("baomi:unauthorized"))` 并抛「未登录或登录已过期」；否则尽力 `res.json()` 取 `detail` 抛出。
3. `res.body.getReader()` + `TextDecoder`，chunk 累进 `buffer`。
4. **按 `"\n\n"` 切帧**：`buffer.indexOf("\n\n")` 循环切片，剩余部分留回 `buffer`（处理跨 chunk 的半个帧）。
5. `parseFrame()` 逐行扫描：`event:` → 事件名（默认 `"message"`）；`data:` → **拼接**后 `JSON.parse`，失败回落为 `{ text: dataStr }`。
6. `finally` 里 `await reader.cancel()` + `reader.releaseLock()`——**取消 / 抛错都必须归还 reader**，否则泄漏连接。

**前端消费的 7 种事件**（`app/page.tsx` 的 `for await` 分支）：

| 事件 | 载荷 | 前端处理 |
| --- | --- | --- |
| `token` | `text`（**增量**，非全文）、`refs` | 累加进 `content`；`refs` 有值就覆盖 |
| `sources` | `items: RefSource[]` | 挂到消息 `sources`，角标可展开原文 |
| `grounding` | `Grounding`（含 `weak`） | 单独一帧，赶在正文前显示「依据较弱」提示条 |
| `tool` | `ToolEvent` | 追加进 `toolCalls` |
| `title` | `title` | 更新侧栏会话标题 |
| `done` | `refs`、`message_id` | 收尾 `streaming=false`，**补挂后端 db id**（赞踩要用） |
| `error` | `detail` | 记到 `message.error` |

> ⚠️ `token` 只发**增量**。以前每帧回传全文，长回答流量是平方级——**不要再改回全文语义**。

## 4. 代码组织约定

### 4.1 目录职责

| 路径 | 放什么 | 不放什么 |
| --- | --- | --- |
| `src/app/` | 页面路由（`page.tsx`、`templates/page.tsx`）、`layout.tsx`、`globals.css` | 可复用 UI 组件 |
| `src/app/styles/` | 设计系统 CSS，按域拆分；`tokens.css` 是唯一变量源 | 组件私有的一次性样式 |
| `src/components/` | 全站 UI 组件；`chat/` 子目录放气泡相关 | 接口调用 |
| `src/lib/` | `api.ts`、`sse.ts`、`types.ts`、`id.ts`、`geo.ts`、`chunkProfiles.ts` 等无 UI 逻辑 | React 组件 |
| `src/lib/hooks/` | 有状态逻辑的 hooks | 纯工具函数（放 `lib/` 根） |

### 4.2 五条硬规则

1. **所有后端调用只允许出现在 `src/lib/api.ts`。** 组件 / hooks 里直接写 `fetch("/api/...")` **一律打回**。
   （唯一既有例外是 `sse.ts` 的流式 POST——流式无法用 `request<T>()` 表达。）
2. **颜色 / 间距 / 字号只能用 `styles/tokens.css` 的变量**，禁止硬编码色值（§5.1）。
3. **全站不使用 emoji 或字符图标**，统一 `components/CornIcon.tsx`（§5.2）。
4. **新增页面必须纳入 `AuthGate`**（当前 `/templates` 是已知缺口，见 §9）。
5. **类型定义集中在 `src/lib/types.ts`**，与后端契约对齐（§7）。

### 4.3 样式拆分方式

`src/app/globals.css` **只负责按序 `@import`**，本身不含规则：`tailwindcss` → `tokens.css`（必须最先）
→ `base` → `components` → `welcome` → `chat` → `kb` → `refs` → `interactions` → `layout` → `fx` → `a11y` → `mascot`。

> **顺序有意义**：拆分前是单文件，现顺序即原物理顺序，编译产物与拆分前一致。
> **新增样式写进对应域文件**，不要往 `globals.css` 加规则。

### 4.4 组件文件规模（现状参考）

`ChatArea.tsx` ~976 行、`KnowledgePanel.tsx` ~851、`CornIcon.tsx` ~536、`Sidebar.tsx` ~511、
`chat/Bubble.tsx` ~513、`UsagePanel.tsx` ~315。
单文件超过 ~500 行时优先**抽出子组件**（`chat/` 目录就是这么来的），而不是继续堆。

## 5. 设计系统

### 5.1 `styles/tokens.css` 是唯一变量源

**所有颜色 / 圆角 / 字号 / 行高 / 字距 / 间距 / 阴影 / 过渡只在 `tokens.css` 写一次实际值**，其余全是 `var()` 别名。
UI 规范要求：**令牌值照抄 `tokens.css`，不凭记忆写**。四层结构：

| 层 | 令牌 | 用法 |
| --- | --- | --- |
| 纸张明度 | `--step-0/1/2` | 全站只有三个纸面色值；面板与画布同档，分界交 1px `--line` 描边 |
| 墨与文字 | `--ink`、`--text-2`、`--text-3` | 正文 / 次级 / 弱文字 |
| 金色 | `--accent`、`--accent-ink`、`--accent-soft` | **只做点缀**；浅底小字用 `--accent-ink`（`--accent` 仅 2.6:1） |
| 语义色 | `--success/--info/--warning/--red` + 各自 `-ink` | 本名 = 实心填充压白字，`-ink` = 纸底文字 |

**填充四级**（所有「不是纸面、不是实色」的底色都从这里取，**不带金**）：
`--fill-1` 按下/最重 → `--fill-2` hover → `--fill-3` 静态淡底 → `--fill-4` 分隔与斑马纹。

**Tailwind 桥接**：`tokens.css` 底部的 `@theme inline` 把令牌映射成工具类，故 tsx 里可直接写
`bg-canvas`、`text-ink`、`border-line`、`text-fs-md`、`text-msg`、`shadow-1`。
它还**接管了 Tailwind 自带的 `--radius-*` 与 `--leading-*`**，避免手写 CSS 与工具类长出两套尺寸。

```tsx
<div style={{ color: "#C8892A" }} />        // ❌ 硬编码色值
<div className="text-[#C8892A]" />          // ❌
<div className="text-accent" />             // ✅ 用令牌
<div style={{ color: "var(--accent-ink)" }} />  // ✅
```

> **例外**：`tokens.css` 自身、`CornIcon.tsx` 的品牌固定填充色（玉米金 `#F5B840` 等，见 §5.2）、
> `layout.tsx` 的 `themeColor`（必须是字面量，浏览器读不到 CSS 变量）。除此之外一律用令牌。

### 5.2 图标：全站禁用 emoji，统一 `CornIcon`

**铁律：界面里不得出现 `🎒 ✎ ✕ ✅ ⚠ ＋ → ★` 这类 emoji / 花体字符充当图标。一个都不行。**

```tsx
import CornIcon from "@/components/CornIcon";
<CornIcon name="trash" className="h-5 w-5" />
<CornIcon name="bulb" className="h-5 w-5" title="提示" />
```

| 特性 | 说明 |
| --- | --- |
| 画布 / 描边 | `viewBox="0 0 48 48"`，`stroke="currentColor"`，圆头圆角；描边继承 `currentColor` → 跟随主题墨色，深浅底自动适配 |
| 填充 | 玉米金 `#F5B840` 主填；叶绿 `#7C9A54`/`#8FAF62`、陶橙 `#EF8A56`、纸白 `#FFFDF6` 辅助 |
| 形态 | 粗描边、大圆角、Q 版手绘，**无直角锐角** |
| 兜底 | **未知 `name`（含历史残留 emoji）一律回退 `corn`（mini 知穗）**，永不显示成系统 emoji |

**`CornIconName` 联合类型共 30 枚**：

| 分组 | name |
| --- | --- |
| 场景 | `book` `pen` `notes` `bolt` `briefcase` `globe` `target` `search` |
| 功能 | `store` `tools` `bulb` `warn` `info` |
| 操作 | `plus` `pencil` `trash` `close` `check` `refresh` `upload` `download` `link` `back` `arrow` |
| 元信息 | `clock` `calendar` `star` `user` `settings` |
| 兜底 | `corn` |

**新增图标四步**：① 沿用 `INK_STROKE`；② 主色填 `#F5B840`；③ 注册进 `ICONS` 与 `CornIconName`；④ 同步更新 UI 规范 §3 的表。
**不要引入第三方向标库**（lucide / heroicons / feather 等）。
模板卡片图标走 `Template.icon` 语义 key（历史 emoji 值回退 mini 知穗，见 `lib/types.ts` 注释）。

**其他设计约束**（UI 规范 §0）：**金色只做点缀**——金 = 「选中的 / 这是主操作」，
hover / focus 一律中性色（`--fill-*`），**不用金色表示"鼠标在上面"**。
明暗双主题靠 `.dark` 类重定义同一批令牌；`layout.tsx` 有内联脚本在首帧前写入，避免闪白。
字号档位写在 `html[data-fs]`（`auto`/`s`/`m`/`l`），正文走 `--msg-fs`。

## 6. 状态管理

本项目**不引第三方状态库**，全部用 React hooks + `localStorage`。各 hook 在 `src/lib/hooks/`，由 `app/page.tsx` 编排。

### 6.1 各 hook 职责

| Hook | 状态 / 能力 |
| --- | --- |
| `useToast` | Toast 队列（`success`/`error`/`info`），**2.8s 自动消失**；导出 `ShowToast` 类型供其他 hook 复用 |
| `useAuth` | 登录态 `me: MeOut \| null`、`loading`、`allowSignup`、`refresh/login/register/logout` |
| `useSessions` | 会话列表、`activeSid`、当前会话消息、`create/select/rename/delete/deleteTurn/reload`、`loadError` |
| `useKnowledge` | 库列表、`kbNameMap`、上传建库（含失败回滚空壳库）、联网建库进度、删库/删文件/重建/搜索预览、每库切片参数记忆 |
| `usePrefs` | 偏好持久化（`localStorage` key = `baomi.prefs`） |

**`useAuth` 的两个闭环**（注释写得很清楚）：

1. 刷新页面靠 `GET /api/auth/me/` 找回身份（HttpOnly Cookie，JS 读不到 token）。
2. 任何接口 401 → `api.ts` 广播 `UNAUTHORIZED_EVENT`（`"baomi:unauthorized"`）→ `useAuth` 监听后把 `me` 置 `null` → 界面收回登录门。

> **API 层不跳页面**（那是 UI 的事），所以失败要**广播**而不是 `router.push`。
> 另有 `aliveRef` 防止「先发的请求后回」覆盖后发的结论（StrictMode 下首屏 effect 会跑两次）。

**登录成功后必须补拉一次**（`page.tsx`）：门后面的首屏请求是被 401 挡掉的，不补就是空列表。

```ts
const authedId = auth.me?.user.id ?? null;
useEffect(() => {
  if (!authedId) return;
  void reloadSessions();
  void refreshKbs();
}, [authedId]);
```

### 6.2 `usePrefs` 的作用与已知缺口

`Prefs` 接口定义了 **6 个字段**：`mode`（对话模式）、`topK`（检索条数）、`chunkSize`（切片长度）、
`chunkOverlap`（切片重叠）、`kbPanel`（资料库面板开合）、`fontScale`（字号档位 `auto/s/m/l`）。

**读取（恢复）与写入（落盘）的能力不对等**——**这是已知缺口**，如实记录：

| 字段 | 落盘（写入） | 启动时恢复（读取） |
| --- | --- | --- |
| `mode` | ✅ | ✅ |
| `kbPanel` | ✅ | ✅ |
| `fontScale` | ✅ | ✅ |
| `topK` | ✅ | ❌ **未恢复** |
| `chunkSize` | ✅ | ❌ **未恢复** |
| `chunkOverlap` | ✅ | ❌ **未恢复** |

**只恢复了 3/6 个偏好。** `usePrefs` 挂载 effect 里只有三行 `if (...)`：

```ts
// frontend/src/lib/hooks/usePrefs.ts（现状）
const saved = readPrefs();
savedRef.current = saved;
if (saved.mode) setMode(saved.mode);
if (typeof saved.kbPanel === "boolean") setKbPanelPref(saved.kbPanel);
if (FONT_SCALES.includes(saved.fontScale as FontScale)) setFontScale(saved.fontScale as FontScale);
setPrefsReady(true);
```

`topK` / `chunkSize` / `chunkOverlap` 仍用 `useState` 初始值（3 / 500 / 50）。

**缺口被 `page.tsx` 半掩盖了**：初始化 defaults 时用 `savedRef.current` 做兜底判断
（`if (saved.topK === undefined) setTopK(d.top_k);` …）。
即**本地存过的项不用后端默认值，但也恢复不出用户上次改的值**——用户上次调到 `topK=8`，刷新后得到后端默认的 `3`。
`prefsReady` 的作用是**读回来之前不往回写**，否则初始默认值会覆盖用户设置。

> ⚠️ **修这个缺口时的注意点**：`savedRef` 是「初始化流程的判断依据」，若直接在挂载 effect 里 `setTopK(saved.topK)`，
> 要同步确认 `page.tsx` 的 defaults 逻辑仍然成立（两边语义耦合）。**属跨文件改动，先确认再下手。**

### 6.3 其他状态归属

| 状态 | 位置 | 持久化 |
| --- | --- | --- |
| 深色模式 | `page.tsx` 模块级订阅 + `documentElement.classList` | `localStorage: "theme"` |
| 场景预设 `scenario` | `page.tsx` | `localStorage: "baomi:scenario:{sid}"`（**按会话隔离**） |
| 每库切片参数 / 定位开关与缓存城市 | `lib/kbChunkPrefs.ts` / `lib/geo.ts` | `localStorage` |
| 断点（wide/medium/narrow） | `useSyncExternalStore` 订阅 `matchMedia` | — |

### 6.4 React 19 编译器约束（高频踩坑）

多处注释都记录了同一条规则：**不要「在 effect 里同步 setState」**，会被 React 编译器判成**级联渲染**
（`react-hooks/immutability`）。统一绕法是**推迟到下一个宏任务**：

```ts
const t = window.setTimeout(() => void refresh(), 0);
return () => window.clearTimeout(t);
```

另外：**不要条件调用 hook**——`page.tsx` 的登录门用**提前 `return`**，且必须在所有 hook 之后；
`AuthGate` 里「注册关闭时强制退回登录态」用**派生值** `const currentMode = allowSignup ? mode : "login"` 而非 `useEffect` + `setState`；
需要稳定引用的回调（如 `sendMessage`）用 `useCallback`，配合 `Bubble` 的 `memo`，流式时不连带重渲染旧消息。

## 7. 接口对接流程

### 7.1 四步法（顺序不要颠倒）

```
① 查契约             ② 定义类型          ③ 封装调用         ④ 组件消费
规范/         lib/types.ts        lib/api.ts         components/
02_核心数据结构       与 schemas 对齐      唯一后端调用出口     只调 api，不写 fetch
```

**① 查契约**：先读 `规范/02_核心数据结构定义.md`（响应形状、状态码、字段语义）
与 `规范/04_环境与部署.md` §4.3（35 个端点索引）。字段语义有歧义时**以 `02` 为准**
（`03_流程规范.md` §1.4 明确「契约冲突优先保契约」）。

**② 定义类型**：写进 `lib/types.ts`（文件头注释定位为「与后端 `api/schemas.py` 对齐的前端类型定义」）。
该文件的注释风格是**每个非显然字段写一句语义**（如 `0 表示不限`、`0 表示未启用每分钟限流`），新增类型请保持。
后端 `schemas.py` 字段改名/增删时，**必须同时改 `types.ts`**（`02` §12）。

**③ 封装调用**：在 `lib/api.ts` 的 `api` 对象里加方法，一律走 `request<T>()`：

```ts
usageSummary: () => request<UsageSummary>("/api/usage/summary"),
createSession: (title: string = "新对话") =>
  request<Conversation>("/api/sessions/", { method: "POST", body: JSON.stringify({ title }) }),
```

> **路径照抄 `04` §4.3 的端点索引**，不要凭印象拼。命名规则：路径全小写 + 连字符分词，资源用名词复数。
> 带路径参数时用 `encodeURIComponent()`（如 `api.getFileContent`、`api.importUrl`）。

**④ 组件消费**：`import { api } from "@/lib/api"`，**绝不写 `fetch`**。错误按 §8 展示。

### 7.2 `refs` 是 JSON 字符串，必须 `JSON.parse`

后端 `messages.refs` 字段类型是 **TEXT（JSON 字符串），不是数组**。`02` §4 明确写着：

> `refs` 是字符串不是数组，前端拿到后需自行 `JSON.parse`。

```ts
// ✅ 正确
const refs: RefSource[] = msg.refs ? (JSON.parse(msg.refs) as RefSource[]) : [];

// ❌ 错误：msg.refs 是 string，当数组用会直接报错
msg.refs.forEach(...)
```

| 类型 | 用途 |
| --- | --- |
| `Message.refs?: string` | 后端返回的原始字符串 |
| `RefSource` | `JSON.parse` 后的引用条目（`id/source/page/score/strength/preview/text`），点角标展开原文 |
| `Grounding` | 依据强度（`strength/best/count/weak`），`weak=true` 时回答上方挂「依据较弱」提示条 |

> ❗ **不要单方面把 `refs` 改成数组**（`02` §12 同步要求：保持字符串）。
> 同理，SSE 帧格式变化必须**同时**改后端与 `lib/sse.ts`。

### 7.3 契约变更的处理

改动响应形状 = **跨模块改动**，按 `01_架构与模块职责.md` §6 走：先通知受影响方（涉及 `api/schemas.py`
+ 前端 `lib/types.ts` + 前端解析逻辑三处）→ 建独立分支 `feat/跨模块-简述-日期` → 同步更新 `02`。
现有 35 个端点的**路径 / 请求字段 / 响应形状一律不改**；必须变更时升级版本 + 同步前端 + 通知全员。

## 8. 错误与限流处理

### 8.1 后端状态码约定（`02` §11）

| 场景 | 状态码 | 响应体 |
| --- | --- | --- |
| 正常 | 200 / 201 | 业务对象 |
| 未登录 | **401** | `{"detail": "..."}` |
| 越权 / 不存在 | **404** | `{"detail": "..."}`（**不区分**，避免探测他人资源） |
| 重名冲突 | **409** | `{"detail": "..."}` |
| **每分钟限流** | **429** | `{"detail": "...", "retry_after": 12.3}` + `Retry-After` 头 |
| **每日配额超限** | **429** | `{"detail": "...", "kind": "...", "limit": 60}` |
| 系统错误 | **500** | `{"detail": "..."}` |

### 8.2 429 与 500 的区别，以及前端怎么区分展示

**后端侧**：429 由 `core/quota.py` 抛出，注册为**全局异常处理器**（`main.py`），**不在各端点里 `try/except`**。

> **为什么必须这样**：端点自己 catch 容易顺手转成 500，前端就分不清「系统出错」和「你今天用超了」。
> **这是既定实现，不要改。**

**前端侧**：`lib/api.ts` 的 `httpError()` 是唯一的错误翻译点：

```ts
if (res.status === 401) {
  notifyUnauthorized();                                   // 广播，由 useAuth 收回登录门
  return new Error("未登录或登录已过期，请重新登录");
}
// 解析 detail；429 有两种：每分钟限流带 retry_after，每日配额带 kind/limit
if (res.status === 429) {
  const wait = retryAfter && retryAfter > 0 ? `（约 ${Math.ceil(retryAfter)} 秒后可重试）` : "";
  return new Error(`${detail}${wait}`);
}
return new Error(detail);
```

| 状态 | 前端表现 | 依据 |
| --- | --- | --- |
| **401** | 不发错误 toast，直接收回登录门（广播 `UNAUTHORIZED_EVENT`） | `httpError` 的 401 分支 |
| **429 · 每分钟限流** | 后端中文 `detail` **+ 追加「（约 N 秒后可重试）」** | `retry_after` 字段（秒） |
| **429 · 每日配额** | 展示后端中文 `detail`，**不加等待时间**（今天等不下去） | 响应体只有 `kind`/`limit`，无 `retry_after` |
| **409 / 404** | 展示后端 `detail`，由调用方决定 toast 文案 | `httpError` 兜底 |
| **500** | 展示后端 `detail` 或回落调用方的通用文案 | `httpError` 兜底 |

> **设计意图**（代码注释原文）：429 的 `detail` 已是中文说明，前端只补一个「多久能再试」的**可操作提示**，
> 「避免用户把它当成"系统坏了"而不停重试」。
> **所以 429 不要显示成"请求失败，请稍后重试"这类 500 口径的兜底文案。**

**配额常驻展示**：`me.quota` 有 `ask` / `embed` 两个维度（`QuotaInfo.used/limit`，`limit === 0` 表示不限，
`unlimited: true` 表示管理员）。`ChatArea` 的 `quotaLine()` 渲染成顶栏胶囊：管理员显示「无限额 · 管理员」，
否则「问答 x/y · 向量化 a/b」。

### 8.3 错误展示的分工（组件侧）

| 场景 | 展示方式 | 示例 |
| --- | --- | --- |
| 用户动作的一次性失败 | **Toast** | 新建会话失败、重命名失败、上传失败 |
| 与某条消息绑定的失败 | **气泡内联**（`message.error` + 「重试」按钮） | SSE `error` 帧、流式请求异常 |
| 整个数据区加载失败 | **区域级错误态 + 重试按钮** | 侧栏 `loadError` + `onRetryLoad` |
| 局部读取失败 | 内联小字（`text-red-ink`） | `FilePreviewModal`、`UsagePanel` 的 `status: "err"` |
| 渲染崩溃 | `chat/BubbleErrorBoundary` 边界兜底 | 单条气泡不炸整页 |

- 错误文案**用中文、说清怎么办**（「会话历史加载失败，请稍后重试」），不是「Error 500」。
- **用户主动停止不算错误**：`sendMessage` 里 `if ((e as Error)?.name !== "AbortError")` 才记 `error`，否则标 `stopped: true`（气泡显示「已停止生成」）。
- 失败后**状态要收干净**：`finally` 里 `setSending(false)`、`streaming: false`、`abortRef.current = null`。

### 8.4 需要避免的已知问题

**各组件错误信息会回显用户输入**——`02` §11 记录的已知问题：

> ⚠️ **已知问题**：8 处 `detail` 会**回显用户输入**。改动错误文案时不要引入新的回显。

`03_流程规范.md` §3.3 的 reviewer 清单也把「错误信息没有回显用户输入」列为审核项。
**新增错误文案时，不要把用户输入的内容拼进 `detail`。**
